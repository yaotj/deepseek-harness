# 闸机交易表支撑分析

> **目的**：确认 ITP 平台中闸机交易（AGM 检票）相关的表结构，验证其对交易入库、后续更新、查询操作的支撑能力。
> **核对方式**：基于 `qditp` 源码逐文件核对（Mapper XML、实体类、schema SQL、服务实现），非文档推断。
> **整理时间**：2026-08-18
> **涉及源码**：ticket-server、gate-txn-pay-server、fep-dev-server

---

## 一、闸机交易涉及的表

### 1.1 核心表（4 张）

| 表名 | 所属服务 | 角色 | 写入特征 |
|------|---------|------|---------|
| QRCODE_TXN_DETAIL | ticket-server | 闸机交易明细，一次进站/出站一条记录 | 只追加，不更新 |
| QRCODE_STATUS | ticket-server | 二维码当前状态，一卡一条 | 每次闸机交易 MERGE 覆盖更新 |
| GATE_TXN_PAY | gate-txn-pay-server | 出站/超时出站扣费订单 | 出站匹配后生成，扣费过程反复更新状态 |
| PAY_TXN_DETAIL | fep-dev-server | 支付交易明细 | 与 GATE_TXN_PAY.ORDER_NO 关联，记录实际代扣 |

### 1.2 关联表（2 张）

| 表名 | 所属服务 | 关联点 |
|------|---------|--------|
| USER_ITP_REG_INFO | account-server | HCE 卡的 64 字节卡数据（HCE_DATA 字段）由闸机交易 reserve1 回写 |
| BLACKLIST | blacklist-server | 检票前的黑名单拦截依据 |

### 1.3 表结构要点

**QRCODE_TXN_DETAIL**（`ticket-server/src/main/resources/sql/qrcode-txn-detail-schema.sql`）

- Oracle 月分区表，按 TXN_DATE（VARCHAR2 YYYYMMDD）RANGE 分区，P202606~P202612 + P_MAX 兜底
- 唯一索引 `UK_QRCODE_TXN_DETAIL_BIZ`（CARD_ID, TRX_TYPE, HANDLE_DATE_TIME, TICKET_TRANS_SEQ, DEVICE_ID, TXN_DATE）——闸机断网重传幂等
- 查询索引：按卡号（CARD_ID, TXN_DATE, HANDLE_DATE_TIME）、按设备（DEVICE_ID, TXN_DATE, HANDLE_DATE_TIME）、按用户（ITP_USER_ID, TXN_DATE, HANDLE_DATE_TIME），均带分区键触发分区裁剪
- 序列 SEQ_QRCODE_TXN_DETAIL（CACHE 1000）

**QRCODE_STATUS**

- 主键 CARD_ID，LIST 分区按 CARD_ID_TAIL（P_00~P_99 + P_OTHER）
- 字段：USE_COUNT、CODE_STATUS、GATE_IN_TIME/STATION、LAST_TXN_TIME/STATION、TXN_SEQ、GATE_STATUS、TRX_AMOUNT

**GATE_TXN_PAY**（`fep-dev-server/src/main/resources/sql/gate-txn-pay-schema.sql`）

- 月分区表（按 TXN_DATE）；业务唯一索引 `UK_GATE_TXN_PAY_BIZ`（CARD_ID, TRX_TYPE, OUT_TIME, TICKET_TRANS_SEQ, DEVICE_ID, TXN_DATE）——过闸交易幂等
- 状态索引 `IDX_GATE_TXN_PAY_STATUS_DATE`（DEBIT_STATUS, TXN_DATE, CREATE_TIME）支撑待补扣扫描
- 序列 SEQ_GATE_TXN_PAY

## 二、两张核心表设计深度分析

> 本章基于 schema SQL、实体类、Mapper XML、服务实现逐层核对，聚焦 QRCODE_TXN_DETAIL 与 QRCODE_STATUS 两张表的定位、设计优点与问题。

### 2.1 服务归属与写入关系

闸机交易通知（IF1A-01 `notiVerifyResult`）由 **ticket-server** 服务承接，两张核心表均在 ticket-server 内、同一事务中写入：

```
POST /ci/agm/notiVerifyResult
  TicketAgmController (ticket-server/controller/ci/agm/TicketAgmController.java:34)
    └─ TicketRideStatusServiceImpl.notifyVerifyResult(:174)  @Transactional
         ├─ QRCODE_STATUS 读（校验）→ QRCODE_TXN_DETAIL 插入 → QRCODE_STATUS MERGE 更新
         └─ 出站后经 GateTxnPayClient RPC 触发 gate-txn-pay-server 扣费
```

gate-txn-pay-server 只管扣费单，不直接写这两张表。

### 2.2 QRCODE_TXN_DETAIL（闸机交易明细表）

**定位**：追加型流水表，一次进/出站一条，只插不改——闸机交易的事实记录层。

**设计优点**

1. **幂等靠业务唯一索引**：`UK_QRCODE_TXN_DETAIL_BIZ`（卡号+交易类型+交易时间+计数器+设备号+分区键）。闸机规范要求断网重传、重试至成功，该索引把重复上送变成 `DuplicateKeyException`，服务层捕获后直接返回成功（TicketRideStatusServiceImpl:208），闸机侧无感知。
2. **分区裁剪设计到位**：按月 RANGE 分区（TXN_DATE），三个查询索引（卡号/设备/用户）全部带 TXN_DATE，分页查询均强制传日期范围。
3. **字段与 IF1A-01 报文 1:1**：报文字段全部落库，无信息丢失，可完整重放。
4. **序列 CACHE 1000**：适配闸机交易高并发写入，减少序列锁争用。

**设计问题**

| # | 问题 | 位置 | 影响 |
|---|------|------|------|
| 1 | `selectLatestByCardId` / `selectLatestEntryByCardId` 只按 CARD_ID 查、不带 TXN_DATE | QRCodeTxnDetailMapper.xml:52-115 | 月分区表上退化为全分区扫描；schema 注释自己写明"查询应带 TXN_DATE"，这两个方法未遵守。进出站匹配是每笔出站都调的高频路径，数据量上来后成为性能瓶颈 |
| 2 | 字段复用承载业务语义 | resultMap 映射 | 见第五章 5.1：OVERTIME_AMOUNT→优惠金额、RESERVE1→支付订单号等 |
| 3 | TXN_DATE 类型与兄弟表不一致 | schema | 本表 VARCHAR2(8)，GATE_TXN_PAY/PAY_TXN_DETAIL 是 DATE，跨表关联日期时注意隐式转换 |
| 4 | 无 UPDATE 为有意设计，出站后进站信息变更无法修正明细，只能靠补站新插一条 | 全表 | 与规范一致（明细不可变），但"完整行程"查询需靠 CARD_ID+TXN_SEQ 配对，配对逻辑散在各查询 SQL 中 |

### 2.3 QRCODE_STATUS（二维码状态表）

**定位**：一卡一行的当前态快照表，闸机检票前置校验（IF1A-04 查询票卡状态）和状态流转的热点表。

**状态更新规则**（buildNextStatus，TicketRideStatusServiceImpl:639）：

| 字段 | 进站(01) | 出站(02/03) |
|------|---------|------------|
| USE_COUNT | +1 | +1 |
| CODE_STATUS | resolveCodeStatus(trxType, 补站类型, adviceOpt) | 同左 |
| GATE_IN_TIME/STATION | 写本次 | 保留原值 |
| LAST_TXN_TIME/STATION | 写本次 | 写本次 |
| TXN_SEQ | 保留 | +1（BigInteger，非数字重置为 1） |
| GATE_STATUS | 写 trxType | 写 trxType |
| TRX_AMOUNT | 保留 | 写本次实际交易金额 |

更新方式为 `MERGE INTO ... ON (CARD_ID)` 原子 upsert，与明细插入在同一事务。

**设计优点**

1. **LIST 分区按卡号后两位**（虚拟列 CARD_ID_TAIL，P_00~P_99 + P_OTHER）：卡号均匀散列，100 个分区无热点；点查按 CARD_ID 必中单分区。
2. **一行一卡 + MERGE**：闸机高频读写集中在单行，行锁竞争小、无索引维护放大。
3. **进出站语义分离**：GATE_IN_* 只在进站写、出站保留，天然支持出站时回溯进站信息做票价匹配。

**设计问题**

| # | 问题 | 位置 | 影响 |
|---|------|------|------|
| 1 | **TRX_AMOUNT 字段漂移**：实体类和 Mapper 都读写该字段，但 `ticket-server-schema.sql` 和 tables.md 中均无此列 | schema vs 实体 | 按仓库脚本全新建库会直接报 ORA-00904；说明线上库是手工加的列、schema 未回写。两张核心表中最需要修的问题 |
| 2 | MERGE 无并发保护：ON 只匹配 CARD_ID，无 UPDATE_TIME/版本号条件 | QRCodeStatusMapper.xml:31-70 | 同一张卡的 AGM 通知与 BLE 通知（IF8A-19）并发到达时后写覆盖先写；当前靠业务时序容忍，严格说是丢更新风险点 |
| 3 | CHANNEL 字段注释"渠道"实际存 issueChannelCode，且 VARCHAR2(4) 偏紧 | ticket-server-schema.sql:4 | 命名歧义 |
| 4 | CARD_ID 长度与账户域不一致：本表 32，USER_ITP_REG_INFO 是 64 | 跨表 | 目前卡号 16 位够用，但两域长度标准不统一 |

### 2.4 小结

两张表分工清晰：**明细表管事实（不可变、幂等、分区归档），状态表管现状（单行热点、原子 MERGE）**，同事务写入保证一致性，整体设计符合闸机交易"高并发写入 + 重传幂等 + 点查为主"的特征。

优先处理项：① QRCODE_STATUS 补 TRX_AMOUNT 的 DDL 并回写 schema 文件；② 两个 selectLatest* 查询补 TXN_DATE 条件（可取"近 N 个月"窗口）。

## 三、实际调用链（源码确认）

接口入口：IF1A-01 闸机检票通知 `POST /ci/agm/notiVerifyResult`

```
TicketAgmController.notifyVerifyResult          (ticket-server/controller/ci/agm/TicketAgmController.java:34)
  └─ TicketRideStatusServiceImpl.notifyVerifyResult   (service/impl/TicketRideStatusServiceImpl.java:174)
       1. QRCodeStatusMapper.selectByCardId      —— 校验卡状态（不存在返回 QR_CODE_NOT_FOUND）
       2. QRCodeTxnDetailMapper.insert           —— 交易明细入库（@Transactional）
          └─ DuplicateKeyException 捕获 → 视为重复上送，补同步 HCE 卡数据后返回成功
       3. QRCodeStatusMapper.upsert              —— MERGE INTO 更新二维码状态
       4. updateHceDataFromGateTransaction       —— HCE 卡数据回写 USER_ITP_REG_INFO
       5. 非 HCE 卡：appNotifyService.notifyVerifyResult —— 推送行业数据给 APP_SERVER（IF8B-01）
          支付宝渠道（issueChannelCode=07）：pushAlipayTripData 加推行程数据
       6. 出站交易：经 GateTxnPayClient（RPC）触发 gate-txn-pay-server 生成扣费单
            GateTxnPayMapper.selectByBizKey → insert → 代扣 → updateStatus
```

出站扣费单幂等：`selectByBizKey` 按业务键先查后插，防止闸机重传重复建单。

## 三、入库 / 更新 / 查询支持情况

| 操作类别 | 具体场景 | 支持情况 | 实现依据 |
|---------|---------|---------|---------|
| **入库** | 闸机交易明细落库 | ✅ | `QRCodeTxnDetailMapper.insert`，SEQ_QRCODE_TXN_DETAIL，唯一索引幂等 |
| | 出站扣费单生成 | ✅ | `GateTxnPayMapper.insert` + `selectByBizKey` 先查后插 |
| **更新** | 二维码状态流转 | ✅ | `QRCodeStatusMapper.upsert`（MERGE 全量覆盖）、`updateCodeStatus`（单字段） |
| | 扣费状态推进 | ✅ | `GateTxnPayMapper.updateStatus`（按 ORDER_NO + TXN_DATE），INIT→PROCESSING→SUCCESS/FAIL/RETRY |
| | HCE 卡数据回写 | ✅ | 交易 reserve1 同步至 USER_ITP_REG_INFO.HCE_DATA |
| **查询（APP 侧）** | IF8A-05 查询交易记录 | ✅ | `selectTransList` / `countTransList`，分页 + 日期/卡号/扣款结果过滤 |
| | if8a_34 订单详情 | ✅ | `selectTransDetail`（用户 + TICKET_TRANS_SEQ） |
| | if8a_41 账单统计 | ✅ | `selectTransStatistics`（COUNT + SUM 聚合） |
| | 进出站匹配 / 自助补站 | ✅ | `selectLatestByCardId` / `selectLatestEntryByCardId` / `selectExcessFareDetail` |
| **查询（渠道侧）** | 支付宝出行乘车记录/详情 | ✅ | `selectAlipayTravelList` / `selectAlipayTravelDetail`（ISSUE_CHANNEL_CODE='07' 过滤） |
| **查询（运营后台）** | 交易明细分页 | ✅ | `selectOperationPage`（JOIN STATION_INFO 转站名，组合条件过滤） |
| | 扣费单分页 | ✅ | `GateTxnPayMapper.selectOperationPage`（卡号/用户/渠道/状态/日期组合） |
| | 支付结果/补扣扫描 | ✅ | PAY_TXN_DETAIL、GATE_TXN_PAY 的状态+日期索引 |

**结论：现有表结构能完整支撑闸机交易的入库、更新、查询三类操作**；幂等（唯一索引 + 先查后插）、分区裁剪（索引均含分区键）、断网重传（DuplicateKeyException 容错）设计均已落地。

## 四、发现的问题与建议

### 4.1 字段复用承载业务语义（建议治理）

`QRCodeTxnDetailMapper.xml` 的 resultMap 将交易明细表字段映射为与规范不符的业务含义：

| 表字段 | 规范语义 | 实际映射为 | 位置 |
|--------|---------|-----------|------|
| OVERTIME_AMOUNT | 超时金额 | 优惠金额 discountFee | transRecordResultMap:129 |
| RESERVE1 | 预留字段 1 | 支付交易订单号 payTradeOrderNo | transRecordResultMap:125 |
| RESERVE2 | 预留字段 2 | 优惠详情 discountInfo | transRecordResultMap:130 |
| LAST_TICKET_STATUS | 上次票卡状态 | 扣款结果 debitRequestResult | transRecordResultMap:128 |
| TICKET_TRANS_SEQ | 交易计数器 | 商户订单号 tradeOrderNo | transRecordResultMap:124 |

查询功能可跑通，但字段语义与《ITP 与 APP 接口规范》定义不符，后续维护和新人理解容易踩坑。

### 4.2 规范要求的扣费单字段缺落表位置（已有变更建议，待执行）

IF8A-05 交易记录应答中的以下字段，GATE_TXN_PAY 实体与表中均不存在：

订单异常类型（orderExpType）、优惠金额（discountFee）、优惠详情（discountInfo）、同行票标识（companionFlag）、日票票号（ticketCode）、计次票扣减次数（countingTimes）、计次票标识（countingFlag）、离线码标识（offlineFlag）、订单应收商户（attributableParty）、订单实收商户（receivingParty）、进站设备码（entryDeviceCode，IF8B-01 推送需要）。

对应变更语句见 `ITP补充表建表.sql` 第九章 9.1 节（ALTER TABLE GATE_TXN_PAY ADD ...），建议尽快执行。

### 4.3 debitRequestResult 过滤语义偏差（建议修正）

规范要求 IF8A-05 按扣款结果过滤（空查全部、0 查成功、1 查失败），实现中 `selectTransList` 实际用 `LAST_TICKET_STATUS`（上次票卡状态）作为过滤条件（QRCodeTxnDetailMapper.xml:213-215）。两个字段语义不同，过滤结果可能与用户预期不一致。

### 4.4 分区维护提醒

QRCODE_TXN_DETAIL、GATE_TXN_PAY、PAY_TXN_DETAIL 等月分区表当前仅建到 P202612，2027 年起需按 schema 文件中的 SPLIT PARTITION 模板提前新增分区，避免交易数据长期落入 P_MAX 兜底分区（影响分区裁剪效率与按月清理）。
