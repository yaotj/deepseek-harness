# 签约接口重复调用唯一约束修复计划

## 一、Summary

IF8A-16 请求签约信息接口第一次调用失败后，第二次再调用时报 `ORA-00001: 违反唯一约束条件 (QDITP.UK_APP_PAY_SIGN_INFO_USER_VENDOR)`。原因是第一次调用时已经通过 `saveSignInfo` 将记录插入数据库（状态为 SIGNING），第二次调用时 `getOrInitSignInfo` 查询到记录存在，但 `saveSignInfo` 再次执行 MERGE/upsert 时由于并发或其他原因导致唯一约束冲突。

## 二、Current State Analysis

### 2.1 错误日志分析

```
ORA-00001: 违反唯一约束条件 (QDITP.UK_APP_PAY_SIGN_INFO_USER_VENDOR)
```

唯一约束 `UK_APP_PAY_SIGN_INFO_USER_VENDOR` 定义在 `APP_PAY_SIGN_INFO` 表上，约束字段为 `REQUEST_SIGN_SEQ` + `PAYMENT_VENDOR`。

private PaySignInfo getOrInitSignInfo(String requestSignSeq, String paymentVendor) {

### 2.6 问题根因分析

**场景：** 第一次调用失败后，第二次再调用时报错。

**可能原因1：** 第一次调用时事务已提交（虽然返回了错误，但 `saveSignInfo` 在 `buildRequestStartSdkInfo` 之前执行，且 `buildRequestStartSdkInfo` 失败不会回滚已保存的记录，因为异常被 catch 后返回错误响应，但事务已经提交了 `saveSignInfo`）。

等等，代码中 `@Transactional(rollbackFor = Exception.class)` 包裹了整个方法。如果 `buildRequestStartSdkInfo` 返回空，`saveSignInfo` 应该已经执行了，然后方法返回错误响应，事务提交。所以第一次调用时记录已经插入。

第二次调用时：
1. `getOrInitSignInfo` 查询到记录存在，返回已有记录
2. 设置 `contractStatus = STATUS_SIGNING`
3. `saveSignInfo` 执行 MERGE，应该走 UPDATE 分支，不应该报唯一约束冲突

**那为什么还会报唯一约束冲突？**

仔细看日志：
```
select ... from APP_PAY_SIGN_INFO where REQUEST_SIGN_SEQ = '0052286501522451' and PAYMENT_VENDOR = '03'
fetchRowCount:0  <-- 查询结果为0！
```

查询结果为 0，说明第一次调用时记录**没有**插入成功（可能事务回滚了）。但为什么第二次调用会报唯一约束冲突？

**可能原因2：** 并发问题。两次调用间隔很短，第一次调用的事务还在进行中（未提交），第二次调用查询时看不到第一次未提交的记录，所以 `getOrInitSignInfo` 返回新对象，然后 `saveSignInfo` 执行 INSERT 时与第一次未提交的记录冲突。

**可能原因3：** `selectBySeq` 查询条件有问题。日志中 `fetchRowCount:0`，但 `PAYMENT_VENDOR = '03'` 是转换后的值。如果数据库中存储的是原始值（如 `0802`），则查询不到记录。

等等，看 `getOrInitSignInfo` 的调用：
```java
PaySignInfo signInfo = getOrInitSignInfo(request.getRequestSignSeq(), paymentVendor);
```

`paymentVendor` 是 `normalizeVendor` 后的值（`03`）。如果第一次调用时数据库中存储的 `PAYMENT_VENDOR` 是 `0802`（原始值），那么第二次查询 `PAYMENT_VENDOR = '03'` 就查不到。

但 MERGE 语句的 ON 条件是 `t.REQUEST_SIGN_SEQ = s.REQUEST_SIGN_SEQ AND t.PAYMENT_VENDOR = s.PAYMENT_VENDOR`，如果数据库中已有 `REQUEST_SIGN_SEQ='0052286501522451'` 和 `PAYMENT_VENDOR='0802'` 的记录，而 MERGE 中传入的是 `PAYMENT_VENDOR='03'`，则 ON 条件不匹配，会走 INSERT 分支，然后与唯一约束冲突。

**这就是根因！**

第一次调用时（修改前）：
- `normalizeVendor("0802")` -> `"0802"`（原样返回）
- 插入记录：`REQUEST_SIGN_SEQ='0052286501522451', PAYMENT_VENDOR='0802'`

第二次调用时（修改后）：
- `normalizeVendor("0802")` -> `"03"`（截取映射）
- `selectBySeq('0052286501522451', '03')` -> 查不到（数据库中是 '0802'）
- `getOrInitSignInfo` 返回新对象
- `saveSignInfo` 执行 MERGE，传入 `PAYMENT_VENDOR='03'`
- ON 条件不匹配（数据库中是 '0802'）
- 走 INSERT 分支
- 唯一约束冲突！（因为 `REQUEST_SIGN_SEQ` 已存在）

## 三、Proposed Changes

### 3.1 修改 selectBySeq 查询逻辑

**文件：** `d:\workspace\zr\qditp\pay-sign-server\src\main\resources\mapper\PaySignInfoMapper.xml`

**What：** 修改 `selectBySeq` 的查询条件，同时兼容原始编码和映射后的编码。

**Why：** 数据库中可能存储了原始编码（如 `0802`）或映射后的编码（如 `03`），查询时需要同时匹配。

**How：**
```xml
<select id="selectBySeq" resultMap="BaseResultMap">
    select <include refid="Base_Column_List"/>
    from (
        select <include refid="Base_Column_List"/>
        from APP_PAY_SIGN_INFO
        where REQUEST_SIGN_SEQ = #{requestSignSeq,jdbcType=VARCHAR}
        <if test="paymentVendor != null and paymentVendor != ''">
            and (PAYMENT_VENDOR = #{paymentVendor,jdbcType=VARCHAR}
                 or PAYMENT_VENDOR = '08' || #{paymentVendor,jdbcType=VARCHAR})
        </if>
    )
    where ROWNUM = 1
</select>
```

等等，这个方案不太好。更简单的方案是：在 `getOrInitSignInfo` 中只按 `REQUEST_SIGN_SEQ` 查询，不限制 `PAYMENT_VENDOR`。

### 3.2 推荐方案：修改 getOrInitSignInfo 查询逻辑

**文件：** `d:\workspace\zr\qditp\pay-sign-server\src\main\java\com\chinasofti\huateng\paysign\service\impl\PaySignServiceImpl.java`

**What：** 修改 `getOrInitSignInfo` 方法，先只按 `REQUEST_SIGN_SEQ` 查询，如果查不到再按 `REQUEST_SIGN_SEQ` + `PAYMENT_VENDOR` 查询。

**Why：** 兼容数据库中存储的不同编码格式。

**How：**
```java
private PaySignInfo getOrInitSignInfo(String requestSignSeq, String paymentVendor) {
    // 先按 requestSignSeq + paymentVendor 查询
    PaySignInfo signInfo = paySignInfoMapper.selectBySeq(requestSignSeq, paymentVendor);
    if (signInfo != null) {
        return signInfo;
    }
    // 如果查不到，可能数据库中存储的是原始编码，只按 requestSignSeq 查询
    signInfo = paySignInfoMapper.selectBySeq(requestSignSeq, null);
    if (signInfo != null) {
        // 更新 paymentVendor 为映射后的值
        signInfo.setPaymentVendor(paymentVendor);
        return signInfo;
    }
    PaySignInfo newSignInfo = new PaySignInfo();
    newSignInfo.setRequestSignSeq(requestSignSeq);
    newSignInfo.setPaymentVendor(paymentVendor);
    return newSignInfo;
}
```

### 3.3 修改 Mapper 支持 paymentVendor 为 null

**文件：** `d:\workspace\zr\qditp\pay-sign-server\src\main\resources\mapper\PaySignInfoMapper.xml`

当前 `selectBySeq` 已经支持 `paymentVendor` 为 null：
```xml
<if test="paymentVendor != null and paymentVendor != ''">
    and PAYMENT_VENDOR = #{paymentVendor,jdbcType=VARCHAR}
</if>
```

当 `paymentVendor` 为 null 时，不添加 PAYMENT_VENDOR 条件，只按 REQUEST_SIGN_SEQ 查询。

## 四、Assumptions & Decisions

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 查询策略 | 先按组合条件查，再按 requestSignSeq 单独查 | 兼容新旧数据 |
| 数据修复 | 不修复历史数据 | 通过查询兼容处理 |
| 唯一约束 | 保持不变 | 约束本身是正确的 |
