# route-sentinel 性能测试计划

## 1. 测试目标

验证 `route-sentinel` 用户路由网关在典型压力下的表现，重点回答：

1. 当前 Web MVC 版网关的理论峰值 QPS/TPS 是多少？
2. Caffeine 全量预热 + `LoadingCache` 对 `USER_ITP_REG_INFO` 点查压力的降低效果？
3. 预热缓存命中 vs 未命中（新用户回源）的延迟差异？
4. 路由实时变更（Actuator 写入）对在线流量的影响？
5. 网关自身的 CPU / 内存 / 线程开销？
6. 为后续压测目标（如 2k/4k/5k QPS）提供基线数据。

## 2. 测试范围

| 模块 | 覆盖 | 说明 |
|---|---|---|
| `UserRouteService` | 是 | Caffeine 预热、缓存命中/回源 |
| `UserRouteConfig` | 是 | RouterFunction 路由匹配 |
| `GatewayRouteQueryService` | 是 | 启动/事件触发时加载路由 |
| `GatewayRouteCommandService` | 部分 | Actuator 改路由的并发影响 |
| `TraceIdFilter` | 是 | 请求头注入与 MDC |
| 下游服务 | 否 | 用本地 mock 代替，排除下游波动 |

## 3. 测试环境

### 3.1 推荐环境

| 组件 | 要求 |
|---|---|
| 被测服务 | `route-sentinel` 单实例，本地启动或容器启动 |
| JDK | Oracle GraalVM 25.0.1（与生产一致） |
| 数据库 | 阶段 1 用 H2；阶段 2 用 Oracle `172.20.222.3:1521/AFCITPDB` |
| 负载工具 | `wrk` 首选；备选 `ab` / `hey` / `vegeta` |
| 下游 mock | 本地 3 个轻量 HTTP 服务（collect-pay / face-pay / fep-app） |
| 监控 | Spring Boot Actuator `/actuator/metrics` + 本地 `jconsole` / `jstat` |

### 3.2 路由数据准备

测试前通过 Actuator 或 DB 写入 4 条生产等效路由：

| routeId | uri | predicates |
|---|---|---|
| legacy-route | `http://127.0.0.1:9101` | 7 条精确设备 URL + `/fep-app/**` |
| face-pay-split-route | `http://127.0.0.1:9102` | 7 条精确设备 URL |
| face-pay-default-route | `http://127.0.0.1:9102` | `/itptvm/**`、`/itpbom/**` |
| fep-app-route | `http://127.0.0.1:9103` | `/fep-app/**` |

### 3.3 用户数据准备

| 数据集 | 用户量 | 用途 |
|---|---|---|
| H2 测试用户 | 2 个 | 功能回归 |
| 预热用户（已注册） | 建议 100 / 1k / 10k | 缓存命中场景 |
| 未注册用户 | 动态生成 | 缓存回源场景 |

## 4. 测试场景

### 4.1 S1：缓存命中 — 已注册用户在 7 条精确 URL

- **请求**：`GET /itptvm/ci/tvm/notiTakeTicketResult?bizData={"thirdUserId":"00522967"}`
- **预期路由**：`face-pay-split-route`
- **关注点**：预热后是否 0 DB 查询、延迟基线、QPS 上限。

### 4.2 S2：缓存未命中 — 未注册用户在 7 条精确 URL

- **请求**：`GET /itptvm/ci/tvm/notiTakeTicketResult?bizData={"thirdUserId":"ghost-{uuid}"}`
- **预期路由**：`legacy-route`
- **关注点**：`LoadingCache` 回源查询 Oracle 的延迟与并发下的 Hikari 连接数。

### 4.3 S3：无需查表 — 默认设备 URL

- **请求**：`GET /itptvm/ci/tvm/requestOrder?bizData={"thirdUserId":"ghost-{uuid}"}`
- **预期路由**：`face-pay-default-route`
- **关注点**：不经过 `UserRouteService` 的纯路由转发基线。

### 4.4 S4：APP 域分流

- **请求**：`GET /fep-app/ci/app/requestOrder?bizData={"thirdUserId":"00522967"}`
- **预期路由**：`fep-app-route`
- **关注点**：与 S1 类似，验证不同路径缓存命中。

### 4.5 S5：并发 Actuator 改路由

- **背景**：在线流量持续时，POST `/actuator/gatewayroutes/legacy-route` 修改 URI。
- **关注点**：路由 reload 是否引起请求毛刺、事件消费延迟。

## 5. 测试指标

### 5.1 业务指标

| 指标 | 采集方式 | 目标（参考） |
|---|---|---|
| QPS/TPS | wrk 输出 | 记录基线，不预设上限 |
| 平均延迟 | wrk 输出 | < 10ms（本地 mock） |
| P95 延迟 | wrk 输出 | < 20ms（本地 mock） |
| P99 延迟 | wrk 输出 | < 50ms（本地 mock） |
| 错误率 | wrk 输出 | 0% |

### 5.2 应用指标

| 指标 | 采集方式 | 关注点 |
|---|---|---|
| JVM CPU | `top` / `jconsole` | 热点方法 |
| JVM 堆内存 | `jstat -gc` / Actuator | 缓存增长 |
| Tomcat 线程数 | Actuator `tomcat.threads.busy` | 是否打满 |
| Hikari 活跃连接 | Actuator `hikaricp.connections.active` | 回源场景 |
| Caffeine hitRate | 日志 `UserRouteService cache stats` | 预热后应接近 100% |
| Caffeine size | 日志 / `legacyCache.estimatedSize()` | 与用户数一致 |

### 5.3 数据库指标（Oracle 阶段）

| 指标 | 采集方式 | 关注点 |
|---|---|---|
| `USER_ITP_REG_INFO` 点查 QPS | Oracle AWR / V$SQL | 未命中场景下的真实压力 |
| 索引命中率 | `idx_uii_third_user` | 是否走 RANGE SCAN |
| DB CPU/IO | 青岛 MCP / DBA 协助 | 是否成为瓶颈 |

### 6.3 压测脚本

## 7. 测试步骤

### 7.1 阶段 0：环境自检

1. 确认 `wrk` 已安装：`wrk --version`
2. 启动 mock 下游：`./scripts/start-mock-downstreams.sh`
3. 启动 route-sentinel：`mise exec java@oracle-graalvm-25.0.1 -- mvn spring-boot:run`
4. 注入 4 条测试路由（若 DB 为空）。
5. 单笔 curl 验证 5 个场景返回正确 `X-Route-Id`。

### 7.2 阶段 1：H2 基线（无 Oracle 压力）

| 场景 | 并发 | 持续时间 | 用户数 |
|---|---|---|---|
| S1 缓存命中 | 10 / 50 / 100 | 30s | 1k 预热 |
| S2 缓存未命中 | 10 / 50 / 100 | 30s | 随机 uuid |
| S3 无需查表 | 10 / 50 / 100 | 30s | 随机 uuid |
| S4 APP 命中 | 10 / 50 / 100 | 30s | 1k 预热 |

记录每个并发级别的 QPS、延迟、错误率、应用指标。

### 7.3 阶段 2：Oracle 真实压力

1. 切换 `application.yml` 到 Oracle（默认已配置）。
2. 注入真实生产路由。
3. 预热 `USER_ITP_REG_INFO` 全量用户。
4. 执行 S1 / S2 / S4，重点关注：
   - S1 预热后 Oracle 点查是否降至接近 0
   - S2 新用户回源对 DB 的压力
   - 高并发下 Hikari 连接池是否充足

### 7.4 阶段 3：稳定性与变更测试

1. 持续 S1 流量（如 50% 峰值）。
2. 每 30 秒通过 Actuator 修改 `legacy-route` 的 URI。
3. 观察：
   - 错误率是否抖动
   - 路由事件消费延迟
   - Caffeine 统计是否稳定

## 9. 风险与规避

| 风险 | 影响 | 规避 |
|---|---|---|
| 本地无法连接 Oracle | 阶段 2 无法执行 | 先执行阶段 1 H2 基线；Oracle 阶段换公司网络或申请测试环境 |
| mock 下游成为瓶颈 | 压不到网关极限 | mock 用纯 socket/epoll 或本地 nginx 返回 200 |
| Caffeine 10k 上限不足 | 用户增长后缓存失效 | 测试中观察 size；若超过 80% 则调大或改为分片 |
| 预热时间过长阻塞启动 | 启动慢 | 预热失败降级为按需加载；大表时改为异步预热 |
| Actuator 改路由并发安全问题 | 流量异常 | S5 专项测试，监控事件处理时间 |

## 10. 验收标准（建议）

- 功能：压测前后 `mvn clean test` 22/22 通过。
- 基线：本地 mock 环境下，S3 纯转发 P95 < 5ms。
- 缓存：S1 预热后 Caffeine hitRate ≥ 99%，Oracle 点查 QPS ≈ 0。
- 回源：S2 单并发下新用户首次请求 P95 < 50ms（Oracle）。
- 稳定性：S5 持续 5 分钟路由变更，错误率 0%。
