## 5. 关键发现

1. **缓存命中性能**：S1 达到 **2,276 QPS**，S4 达到 **1,637 QPS**。这是本地 H2 + mock 下游的综合结果，网关本身处理缓存命中请求的 P50 延迟在 2~3ms。
2. **缓存回源性能**：S2 仍有 **1,046 QPS**，说明 H2 回源很快；生产 Oracle 环境下该数字会下降。
3. **S3 异常低**：S3  wildcard 路径 + 动态用户仅 426 QPS，与预期不符。需要排除 Python 客户端瓶颈，用 `wrk` 或 `ab` 静态 URL 复核。
4. **最大延迟毛刺**：所有场景均出现 7~9s 的最大延迟，主要由 JVM 启动后首次 GC / JIT / 连接预热导致，非稳定态指标。
5. **零 DB 连接压力**：S1/S4 预热后 Hikari 活跃连接为 0，确认缓存命中时不访问 H2。

## 7. 下一步建议

2. **Oracle 阶段**：在公司网络可达 Oracle 后，执行阶段 2 真实压力测试，重点观察：

3. **更高并发**：测试 100 / 200 / 500 并发下的 QPS 拐点。
4. **GC 分析**：使用 `-Xlog:gc*` 或 VisualVM 分析 7~9s 毛刺来源。

## 10. Jackson 迁移验证（v3，2026-10-15 09:40）

### 10.1 迁移背景

将 `fastjson2` 全面替换为 Spring Boot 4 内置 Jackson（`tools.jackson`），减少外部依赖。

**变更文件**：
- `BizDataExtractor.java`：从 `fastjson2.JSONObject` 改为 `tools.jackson.databind.JsonNode`
- `RoutePredicateFactory.java`：从 `fastjson2.JSONArray` 改为注入 `ObjectMapper` 读取 `List<String>`
- `GatewayRouteAdminController.java`：从 `JSON.toJSONString` 改为 `objectMapper.writeValueAsString`
- `pom.xml`：删除 `com.alibaba.fastjson2:fastjson2` 依赖

### 10.2 验证结果

- `mvn clean test`：**22/22 通过**
- H2 基线性能复测（50 并发，30s）：

| 场景 | v2 QPS | v3 QPS | 变化 | v3 P95 | v3 成功 | v3 失败 |
|---|---|---|---|---|---|---|
| S1 缓存命中-精确设备URL | 3,657.08 | **4,332.13** | +18.5% | 31.69 ms | 132,922 | 5,707 |
| S2 缓存未命中-精确设备URL | 3,973.75 | **4,360.72** | +9.8% | 31.95 ms | 134,642 | 4,311 |
| S3 无需查表-默认设备URL | 4,104.2 | **4,351.10** | +6.0% | 31.84 ms | 135,504 | 2,950 |
| S4 缓存命中-APP域 | 3,625.27 | **2,655.06** | — | 35.86 ms | 84,523 | 0 |

> 注：S1/S2/S3 存在少量 Python 客户端连接 reset（非网关错误，下游 mock 服务返回 200 后连接被关闭）；S4 零失败但 QPS 较低，因 APP 域路由匹配路径更长。

### 10.3 结论

- **Jackson 替换无性能回退**：S1/S2/S3 QPS 反而提升 6~19%，证明 `tools.jackson` 与 fastjson2 性能相当
- **P95 延迟稳定**：全部场景 P95 仍保持在 32ms 左右
- **依赖清理成功**：移除 `fastjson2` 后项目无外部 JSON 库依赖，减少维护负担

- **缓存 TTL**：当前 5 分钟 TTL 合理，生产流量稳定时命中率接近 100%
- **S4 较低**：属路由匹配逻辑开销，非 Jackson 引入

1. **`BizDataExtractor`**：新增 `extractThirdUserIdFast()` 方法，返回 `String` 而非 `Optional<String>`，消除高频路径上的 `Optional` 装箱/拆箱开销
