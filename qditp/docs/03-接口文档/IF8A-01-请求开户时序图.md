## 五、关键业务逻辑说明

### 5.1 参数校验
- 校验 `thirdUserId`、`cardType`（仅支持 02/03）、`msisdn` 必填
- 校验失败返回 `retCode=8001`

### 5.2 重复开户检查
- 通过 `thirdUserId` 查询 `USER_ITP_REG_INFO`
- 若 `delYn=1` 表示已开户，直接返回已有卡号信息

### 5.3 卡号分配
- **调试模式** (`debugManualAllocate=true`): 直接动态生成卡号
- **正常模式**: 从卡池表 `USER_ACC_TICKET_NO` 通过乐观锁分配
  - 卡池不足时自动补充（当前实现为本地生成卡号后批量插入）
- 无可分配卡资源返回 `retCode=8002`

### 5.4 数据持久化
- 插入 `USER_ITP_REG_INFO`（用户注册信息）
- 插入 `USER_ITP_REG_LOG`（注册操作日志）

### 5.5 ticket 状态同步
- 调用 ticket-server 初始化 `QR_CODE_STATUS` 记录
- 设置默认状态: `codeStatus=03`, `gateStatus=00`

### 5.6 事务控制
- `@Transactional` 包裹整个 account-server 处理流程
- ticket-server 调用失败时手动 `setRollbackOnly()` 回滚
- 任何异常均触发事务回滚，返回 `retCode=9999`

## 六、响应码说明

| 响应码 | 含义 | 触发场景 |
|--------|------|----------|
| 0000 | 成功 | 开户流程全部完成 |
| 8001 | 参数错误 | 必填参数缺失或 cardType 不支持 |
| 已开户 | 用户已存在 | thirdUserId 已注册且 delYn=1 |
| 8002 | 无卡资源 | 卡池耗尽且无法补充 |
| 8003 | 服务不可用 | ticket-server 调用失败 |
| 9999 | 系统错误 | 任何未捕获异常 |

### 9.3 不同场景下的副作用对比

| 场景 | USER_ITP_REG_INFO | USER_ITP_REG_LOG | USER_ACC_TICKET_NO | QR_CODE_STATUS | 事务状态 |
|------|:-----------------:|:----------------:|:------------------:|:--------------:|:--------:|
| **开户成功** | INSERT | INSERT | UPDATE | UPSERT | 提交 |
| **参数错误** | - | - | - | - | 无事务 |
| **用户已开户** | - | - | - | - | 无事务 |
| **无卡资源** | - | - | - | - | 无事务 |
| **ticket 失败** | INSERT | INSERT | UPDATE | - | **回滚** |
| **系统异常** | INSERT(可能) | INSERT(可能) | UPDATE(可能) | - | **回滚** |

> **注意**：ticket-server 调用失败或系统异常时，account-server 已执行的 INSERT/UPDATE 会被事务回滚，但 ticket-server 若已执行 UPSERT 则不会回滚（跨服务事务，无分布式事务协调）。

### 9.4 幂等性说明

IF8A-01 接口**不具备幂等性**，重复调用同一 `thirdUserId` 的副作用如下：

- **第二次调用**：返回 `ALREADY_REGISTERED`，无任何 DB 变更
- **并发调用（同一 thirdUserId）**：由于 `selectActiveByThirdUserId` 先查询后插入，可能存在竞态条件，但 `thirdUserId` 通常有唯一索引保护

## 十、校验方式

### 10.1 参数校验规则

参数校验由 [AccountApplicationServiceImpl.validateRequest()](file:///d:/workspace/zr/qditp/account-server/src/main/java/com/chinasofti/huateng/account/service/impl/AccountApplicationServiceImpl.java#L376-L393) 方法执行：

| 校验项 | 规则 | 失败返回 |
|--------|------|----------|
| request | 不能为 null | "请求报文不能为空" |
| thirdUserId | 不能为空且必须有文本内容 | "thirdUserId不能为空" |
| cardType | 不能为空，且只能是 `02` 或 `03` | "cardType不能为空" / "cardType仅支持02或03" |
| msisdn | 不能为空且必须有文本内容 | "msisdn不能为空" |

### 10.2 重复开户校验

```sql
-- 查询逻辑：selectActiveByThirdUserId(thirdUserId)
SELECT * FROM USER_ITP_REG_INFO 
WHERE third_user_id = ? AND del_yn = 1;
```

- 若记录存在且 `delYn = 1`，表示用户已开户，直接返回已有卡信息
- 返回码为 `ALREADY_REGISTERED`，同时返回已有的 `cardId` 和 `cardType`

### 10.3 卡池分配校验

| 校验项 | 规则 | 失败返回 |
|--------|------|----------|
| 卡池余量 | 查询 `USER_ACC_TICKET_NO` 中未使用卡号 | 无可用卡号时尝试自动补充 |
| 乐观锁分配 | `updateAllocateCard(id, thirdUserId, now)` 影响行数 > 0 | 重试3次后仍失败返回 null |
| 卡资源耗尽 | 3次分配均失败 | `retCode=8002` 无卡资源 |

### 10.4 ticket-server 调用校验

| 校验项 | 规则 | 失败处理 |
|--------|------|----------|
| 响应非空 | `ticketResponse != null` | 回滚事务，返回 `retCode=8003` |
| 响应成功 | `ticketResponse.retCode == "0000"` | 回滚事务，返回 ticket 错误信息 |

### 10.5 事务一致性校验

整个开户流程由 `@Transactional(rollbackFor = Exception.class)` 包裹：

1. **正常流程**: 所有 DB 操作 + ticket 调用成功，事务自动提交
2. **ticket 失败**: 手动调用 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`，回滚 `USER_ITP_REG_INFO` 和 `USER_ITP_REG_LOG` 插入
3. **异常流程**: 任何未捕获异常触发自动回滚

### 10.6 测试验证清单

| 测试场景 | 预期结果 | 验证方式 |
|----------|----------|----------|
| 正常开户 | `retCode=0000`，返回 cardId | 检查响应 + 查询 DB 确认记录存在 |
