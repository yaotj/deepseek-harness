## 一、总体架构

### 1.1 部署拓扑

```
支付宝出行侧
    ↓ HTTP POST（FormData / JSON）
fep-app-server（FepAlipayTripController / FepAlipayTripNotifyController）
    ↓ CommonFormRequest → JSON.parseObject
AlipayTripServiceImpl（业务编排）
    ↓ RPC 调用
account-server / pay-sign-server / ticket-server / blacklist-server

ITP 内部触发
    ↓ HTTP POST（JSON）
fep-alipay-notify-server（AlipayNotifyController）
    ↓ OkHttp POST（JSON）
支付宝出行侧
```

### 1.2 路径规范

| 类型 | 路径前缀 | 说明 |
|------|---------|------|
| 渠道接口 | `/channel/*` | 支付宝出行主动调用 |
| 通知接口 | `/notify/*` | ITP 向支付宝推送（由 fep-alipay-notify-server 统一发送） |
| 会员合约 | `/memberContract/channel/*` | 会员合约专属 |
| 通知触发 | `/notify/*` | fep-alipay-notify-server 内部触发接口 |

### 1.3 与地铁APP体系的关系

| 维度 | 地铁APP（IF8A） | 支付宝出行 |
|------|---------------|-----------|
| 路径前缀 | `/ci/app/*` | `/channel/*` |
| 签约渠道 | `METRO_APP` | `ALIPAY` |
| 签约确认 | 异步回调（支付平台 → `/app/receiveSignResult`） | **同步确认**（返回成功即签约成功） |
| 入口服务 | `FepAppController` | `FepAlipayTripController` |

## 五、技术方案要点

### 5.1 签约结果确认方式

| 渠道 | 确认方式 | 实现要点 |
|------|---------|---------|
| 地铁APP | 异步回调 | 支付平台回调 `/app/receiveSignResult`，更新签约状态 |
| 支付宝 | **同步确认** | `/channel/addContract` 返回成功即视为签约成功，**不需要后续回调** |

**同步确认流程：**
1. 支付宝调用 `/channel/addContract`
2. `PaySignServiceImpl.alipayTripRequestSignInfo()` 接收请求
3. 校验参数、检查是否已签约
4. **不调用支付平台**，直接写入 `APP_PAY_SIGN_INFO`（`SIGN_CHANNEL = 'ALIPAY'`、`SIGN_STATUS = 'SIGNED'`）
5. 写入流水表 `APP_PAY_SIGN_REQUEST`
6. 调用 account 服务补充支付通道（`THIRD_PAY_ID`、`REQ_CONTRACT_NO`）
7. 返回成功响应

### 5.2 渠道隔离

- 支付宝数据与地铁APP数据通过 `SIGN_CHANNEL` 字段隔离
- 开户通过 `channel` 字段区分
- 所有查询需带渠道条件

### 5.3 RPC 客户端

| 客户端 | 新增方法 | 对接服务 |
|--------|---------|---------|
| `AccountClient` | `alipayTripRequestApplication` | account-server |
| `PaySignClient` | `alipayTripAddContract` | pay-sign-server |
| `PaySignClient` | `alipayTripTerminateContract` | pay-sign-server |
| `TicketClient` | `alipayTripFindTravelList` | ticket-server |
| `TicketClient` | `alipayTripFindTravelDetail` | ticket-server |
| `BlacklistClient` | `alipayTripReceiveBlackList` | blacklist-server |

## 六、待实现功能详述

### 6.1 高优先级

#### 1. 通知推送微服务（fep-alipay-notify-server）

**实现内容：**
- 新增独立微服务 `fep-alipay-notify-server`（端口 8080）
- 统一向支付宝发送 4 类通知请求
- 通过 OkHttp 主动推送，记录推送流水

**接口清单：**

| 序号 | 接口名称 | 路径 | 请求参数 | 应答参数 |
|------|---------|------|---------|---------|
| 1 | 业务关闭结果通知 | `/notify/closeResultForAlipay` | `result` (Boolean)、`agreementNo` (String) | `retCode`、`retMsg` |
| 2 | 行程数据推送 | `/notify/pushTransData` | 与 APP 行程数据通知相同 | 通用响应 |
| 3 | 行业数据推送 | `/notify/receiveCardDataFromItp` | 与 APP 行业数据通知相同 | 通用响应 |
| 4 | 黑名单状态变更通知 | `/notify/receiveBlackListFromItp` | 与 APP 黑名单状态变更通知相同 | 通用响应 |

**技术要点：**
- 使用 OkHttp 发送 POST JSON 请求
- 配置项：`alipay.notify.*-url`（支持方法参数覆盖配置）
- 超时设置：connectTimeout=30s，readTimeout=60s，writeTimeout=60s
- 开启连接失败重试：`retryOnConnectionFailure=true`
- 请求/响应日志记录

## 八、风险点与待确认事项

### 8.1 技术风险

| 风险 | 说明 | 缓解措施 |
|------|------|---------|
| 行业数据接口依赖多服务 | `requestIndustryData`、`receiveCardDataFromItp` 需跨服务对接 | 明确接口 owner，提前对齐数据格式 |
| 行程数据推送复杂度高 | `pushTransData` 涉及 ticket-server 和 online-server | 分阶段实现，先完成数据接收，再处理推送逻辑 |
| 签名机制改造影响面大 | 当前 signType 固定为 `"00"`，改造需全链路支持 | 先做兼容（支持 00/01/02），再逐步切换 |
| 卡池资源冲突 | 支付宝用户可能已在地铁APP开户，卡号冲突 | 复用现有卡池分配逻辑，通过 channel 隔离 |

### 8.2 待确认事项

| 序号 | 待确认项 | 当前建议 | 影响 |
|------|---------|---------|------|
| 1 | `channel` 固定值 | 开户阶段固定为支付宝渠道编码（如 `03`） | 影响 `USER_ITP_REG_INFO.CHANNEL` |
| 2 | `thirdPayId` 取值 | 开户阶段为空，签约后由 account 服务补充 | 影响 `USER_ITP_REG_INFO.THIRD_PAY_ID` |
| 3 | `reqContractNo` 取值 | 开户阶段为空，签约后由 account 服务补充 | 影响 `USER_ITP_REG_INFO.REQ_CONTRACT_NO` |
| 4 | `merchantNo` 字段映射 | 当前未使用，确认是否映射到解约表 | 影响 `APP_PAY_SIGN_REQUEST` |
| 5 | 解约状态枚举 | 当前使用通用 `SIGN_STATUS` | 确认支付宝解约状态值是否与地铁APP一致 |
| 6 | `PAYMENT_VENDOR` 编码 | 当前使用支付宝 channel 字段 | 确认是否需要统一编码规范 |
| 7 | `CARD_ID` / `PAY_ACCOUNT_ID` 补充时机 | 支付宝无独立回调 | 确认是否在开卡或签约时回填 |

### 10.3 通知推送链路（fep-alipay-notify-server）

```
ITP 内部服务（ticket-server / blacklist-server / pay-sign-server）
    ↓ HTTP POST /notify/*
AlipayNotifyController
    ↓ @RequestBody
AlipayNotifyServiceImpl
    ↓ 1. 校验 URL 配置（方法参数 > application.properties）
    ↓ 2. JSON 序列化请求报文
    ↓ 3. OkHttp POST JSON
支付宝出行侧
    ↓ HTTP 200 / 非 200
AlipayNotifyServiceImpl
    ↓ 4. 记录响应报文
    ↓ 5. 记录推送日志（TODO: 持久化到 ALIPAY_NOTIFY_LOG）
返回 true / false
```

**技术要点：**
- 统一通过 `fep-alipay-notify-server` 推送，避免各服务重复实现 OkHttp 客户端
- 支持方法参数覆盖配置文件 URL
- 超时：connectTimeout=30s，readTimeout=60s，writeTimeout=60s
- 连接失败自动重试：`retryOnConnectionFailure=true`
