## 1. 报告原结论

> `calculateOfflineFare` 只判 null 不判 `<=0`；第107行 `totalAmount<=0` 直接 SUCCESS，补偿链路 `OfflineFareRecoveryServiceImpl:81-87` 反有 0 元守卫，两路不对称。违反 `docs/business/gate-txn-pay.md:128-129` 三条红线 → **票价参数异常时免费过闸且无补偿入口**。修复：免扣费分支排除离线码 0 元场景转 PENDING 留痕；`FareCalculator` 校验 `>0`。

## 2. 代码核查

### 2.1 首次链路（报告指的问题点）

`GateTxnPayServiceImpl.requestPay`：

- 离线码出站（`isOfflineExit`:385，`OFFLINE_FLAG='Y'` + 出站 TRX_TYPE）走 `fareCalculator.calculateOfflineFare`（`:88`）；
- 算价**抛异常** → catch（`:93`）→ `saveOfflineFarePendingOrder`（`:100`）落 `INIT` + `DISCOUNT_CALC_STATUS='OFFLINE_FARE_PENDING'` + 金额清零，返 8002，等补偿；
- 算价**正常返回** → `totalAmount = trxAmount + overtimeAmount`（`:103-104`）→ 第 `:107` 行 `if (isDailyTicket || totalAmount <= 0 || isBomSupplement)` → 落 `DebitStatus.SUCCESS` 免扣费（`:131-140`）。

`FareCalculator.calculateOfflineFare`（`:121-200`）：

- 票价：`queryTicketPrice` 返 null 才抛（`:139-141`）；
- 换乘减免：`fareAfterTransfer = max(0, originalFare - max(0, transferReductionCents))`（`:157`）；
- 钱包折扣：`discountedFare = (fareAfterTransfer × 折扣率)`，`trxAmount = max(0, discountedFare)`（`:180-185`）；
- 非钱包：`trxAmount = fareAfterTransfer`（`:195`）。

### 2.2 补偿链路（对照）

`OfflineFareRecoveryServiceImpl.recoverSingleOfflineFareOrder`（`:68-105`）：

- 重算抛异常 → `markOfflineFarePending` 保持 PENDING（`:72-77`）；
- 重算后 `totalAmount <= 0` → `markOfflineFarePending` + ERROR 日志「NEVER 按 0 金额收口成 SUCCESS」（`:81-87`）；
- 只有 `>0` 才 `applyOfflineFareRecalculated`（CAS 抢占）+ 发起扣款。

⇒ **"首次链路 0 元 → SUCCESS / 补偿链路 0 元 → PENDING"的不对称客观存在**，报告这一半属实。

## 3. 触发场景核查（报告不成立的部分）

### 3.1 "票价参数异常返回 0"不可达

`docs/domain/decisions.md:2222-2223` 明确记载 gateway 两个方法的分工：

> `queryTicketPrice`：**非 `0000` / `<=0` 返 null，异常照抛**（给"查不到就中断"的路径）

实码 `FareDataGateway.java:62-72` 印证：`originalFare <= 0` → `return null`。于是：

票价查询返回 0 或负数 → `queryTicketPrice` 返 null → `FareCalculator:139-141` 抛异常 → `requestPay` catch → `saveOfflineFarePendingOrder` **PENDING 留痕**，走补偿。

**报告说的"票价参数异常时免费过闸且无补偿入口"这条路径不存在。**

### 3.2 真正能产生 0 元的路径：合法换乘减免覆盖票价

唯一能让 `trxAmount=0` 且算价正常返回的是换乘减免：

```
fareAfterTransfer = max(0, 票价 - 100分)   // transferReductionCents 默认 100
```

当**票价 ≤ 100 分**（如 1 元票、换乘减 1 元）时，减免后为 0 → 非钱包 `trxAmount=0` 或钱包 `discountedFare=0` → `totalAmount=0` → 第107行 SUCCESS 免扣费。

这是**合法票价 + 合法换乘减免**的结果，不是参数异常。此时：

- 首次链路：SUCCESS 免扣费（把"换乘优惠减免到 0"当作免票）；
- 补偿链路：若同样场景在补偿时发生（重建上下文重算到 0），会保持 PENDING 待人工（`:81-87`）。

### 3.3 业务口径只覆盖了一半

`docs/business/gate-txn-pay.md:127-131` 三条红线与 `:674`：

> 这类行 `TOTAL_AMOUNT=0` 但**不是免扣费交易**，NEVER 让它走 `totalAmount <= 0` 的默认 SUCCESS 分支——那等于把该收的钱记成 0（资损）。
> 重算出 0 元是最隐蔽的一条：**票价参数异常时**重算会"成功"返回 0，若按 0 元收口成 SUCCESS，车费永久收不回来。

文档明确针对的是**离线码补偿对象广场**（`DEBIT_STATUS='INIT'` + `OFFLINE_FARE_PENDING` 的"金额未定"行，`:325`、`:327`），也就是**算价失败留痕的那批单**。它担心的是这些单在补偿时算出 0 被误收口。而**首次过闸时因为合法换乘减免到 0** 该不该 SUCCESS，文档**没有裁决**。

⇒ 报告把"补偿链路的红线"直接套到"首次过闸的免扣费分支"上，属于**场景错配**：两处虽然都是 `totalAmount<=0`，但前提语义不同（一个是"金额未定/参数异常"，一个是"优惠减免到零"）。

## 4. 结论与评级

| 维度 | 判定 |
|---|---|
| 报告"票价参数异常免费过闸" | ❌ 不成立：gateway 已把 `<=0` 转 null→异常→PENDING 补偿 |
| 报告"两链路 0 元处置不对称" | ✅ 属实：首次 SUCCESS / 补偿 PENDING，客观存在 |
| 该不对称是否资损 | ⚠️ 取决于"换乘减免把票价减到 0"的业务定性——合法免票（现状合理）还是应收未收（资损） |
| 是否有补偿入口 | 首次 SUCCESS 分支不入补偿队列（本就不需要，因为已收口），报告"无补偿入口"在参数异常场景下不成立 |

**评级建议**：从 P1（直接资损）降为 **P2（待业务裁决）**。若业务确认"换乘减免到 0 也应 PENDING 人工核对"，则升级 P1 并按修复方案改；若确认"减免到 0 = 免票合理"，则此问题降级为文档补充（在 `gate-txn-pay.md` 明确两种 0 元的不同语义），代码不动。

## 5. 三个处置方案

| 方案 | 做法 | 优点 | 缺点 / 风险 |
|---|---|---|---|
| **A：补全交叉判断（报告建议，需先裁决）** | 第107行免扣费分支加条件：`isOfflineExit(request) && totalAmount<=0 && DISCOUNT_CALC_STATUS=SUCCESS` 时改走 PENDING 留痕，不再 SUCCESS | 消除两链路不一致；若减免到 0 属资损则堵住 | **改变业务行为**：合法换乘减免到 0 的乘客会被记 PENDING 而不是放行成功，可能影响过闸体验/对账；须业务先裁决，且需新造一个"减免到0"的留痕状态或复用 OFFLINE_FARE_PENDING（复用会让补偿把它当参数异常反复重算） |
| **B：FareCalculator 加 >0 校验（报告建议）** | `queryTicketPrice` 后校验 `queriedFare > 0`（但 gateway 已做，属重复）；或对 `fareAfterTransfer == 0` 抛异常 | 一行改动 | gateway 已有 `<=0` 校验，重复无收益；对减免到 0 抛异常等价于方案 A 的行为变更，仍需裁决；**NEVER 无脑加** |
| **C：只补文档口径（推荐，待裁决前）** | 在 `gate-txn-pay.md` 明确"两种 0 元的不同语义"：参数异常/金额未定 → PENDING 补偿；合法换乘减免到 0 → SUCCESS 免票。并加一条测试锁定 `票价100分+换乘减100 → trxAmount=0` 的现有行为 | 零业务行为变更；消除文档与报告的口径混淆；测试把隐性规则显性化 | 不消除"不对称"本身——如果业务认为不对称是缺陷，仍需方案 A |

**推荐路径**：先做 **C**（零风险、消除认知混乱），同时把"换乘减免到 0 到底该不该 SUCCESS"作为一个**业务裁决项**提交；裁决为"资损"再上方案 A，裁决为"合理"则以 C 收口。
