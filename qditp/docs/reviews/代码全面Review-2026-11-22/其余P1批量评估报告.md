### 1. ticket-server 通知池（需权衡，不可直接丢弃）

- **属实**：`TicketAsyncConfig.java:22-24` core4/max16/queue2000，`:26-35` 拒绝策略 `runnable.run()`；`AppNotifyServiceImpl.java:37,48,59,70` 四类推送共用。`GateTicketHandler.java:117→150 notifyVerifyResult` 确在过闸应答同步路径。
- **降级理由**：正常 `execute()` 异步零阻塞；只有积压满 2000 才 inline（OkHttp 10s×4 类≈数十秒尾延迟），属条件性延迟、无数据损失。
- **不能直接改丢弃**：该服务**无落库补偿**（`IndustryDataNotifier.java:70` 明示"本次不补偿"），CallerRuns 是"不丢通知"的背压设计。改 Abort/Discard 会真丢通知。
- **改法**：先降 `queueCapacity` 到 100~200 让 max=16 真正生效、拆关键/非关键池；要改丢弃必须先建重试表。

### 2/3/4/5（可直接修）

- **web-admin 探活**：`ServiceStatusService.java:30,33` 无界池属实，但 `ServiceStatusController.java:21-24` 有 `@PreAuthorize` 保护、运维低频接口、3s 超时 → P3。改有界 `(4,8,60s,ArrayBlockingQueue(64),CallerRunsPolicy)`，HttpClient 去自定义 executor。
- **route-sentinel 双发**：`DualQueryService.java:62-66` 无界池属实且已启用（`application.yml:36`），但仅单只读路径 + 2.5s 超时 + 熔断 3 次开 60s → P2 合理。JDK21 已确认（`pom.xml:22`），改虚拟线程执行器最优。
- **daily-ticket 通知池**：`DailyTicketAccNotifyExecutorConfig.java:15-19` 属实，但**有 PENDING 落库补偿**（`DailyTicketAccActiveNotifyService.java:53-59,85-105`），内存任务丢失后 DB 行可被补偿重投 → P3。改 queue100~200 + 优雅关闭 + AbortPolicy。
- **acc-es @Async**：`EsReportServiceImpl.java:81,207`/`EsTaskServiceImpl.java:323` 无 value、classpath 无 TaskExecutor Bean → 落默认无界队列属实。但报告"**全库**无 TaskExecutor Bean"表述不准（`web-server/web-framework/.../ThreadPoolConfig.java:25` 有，只是不在 acc-es classpath）。低频批处理 → P3。声明有界 Bean + 3 处 `@Async("xxx")` 显式指定，须配套 `@AsyncUncaughtExceptionHandler`（与既有"异常被吞"P1 叠加，勿混为一谈）。

## 二、扫表无领取标记导致重复通知（2 项，均降 P3）

### 1. face-pay 通知扫表（报告 P1 → P3）

- **代码属实**：`F2fNotifyDeliverer.java:36,64-66` 捞 PENDING 直接 HTTP、成功才 markSuccess；`F2fNotifyTaskMapper.xml:66-72` 无 CAS/租约。
- **多实例前提不成立**：`deploy/.../face-pay-server.yaml:11` `replicas: 1`；`F2fNotifyJob.java:21-24` 是 `@Scheduled(fixedDelay)`、非 sys_job；`docs/ops/tasks/04-face-pay-server.md:73` 明示 fixedDelay 单轮串行不叠加；`:3` 明示 MUST 单副本。
- **危害夸大**：payload 是出票/退款/支付**结果通知**（`F2fNotifyService.java:18-24`），资金与出票动作在服务端回调已完成，重复投递最多 APP 重复提示，无"重复入账/出票"证据；入队侧本身有唯一键幂等（`:66-73`）。唯一残留是人工 HTTP 重投端点与定时任务的低概率并发。
- **结论**：加固需改 DB 状态机（新增 PROCESSING 态 + 租约列）+ 扫描 SQL + 超时补偿，收益有限，**不建议当 P1 紧急上线**。

### 2. recon 第三方对账扫表（报告 P2 → P3，且 ORA-30926 归因错误）

- **报告自相矛盾**：报告 `:72` 称"多实例并发 MERGE 易 ORA-30926"，但 `:319` 又写"MERGE source 均单行，无 ORA-30926 风险"。核实 source 实为 `<foreach ... UNION ALL>` **多行**（`ReconThirdBillMapper.xml:34-60`）。ORA-30926 成因是单条 SQL 内 source 重复 ON 键，与"多实例"无关；并发 MERGE 只会行锁等待。
- **多实例前提不成立**：`recon-server.yaml:11` 单副本；`@Scheduled` 双开关默认关闭（`ThirdPartyReconProperties.java:12,20`、`application.properties:66,70`）；`docs/business/recon-thirdparty.md:115-116` 明确默认关闭防双跑；quartz `@DisallowConcurrentExecution`。web-server SQL 甚至未注册该 sys_job——现网基本未启用。
- **真正风险（报告未正确指出）**：单个 CSV 内 `(BILL_DATE, CHANNEL_TRADE_NO)` 重复会触发 ORA-30926（文档 `:103-104,173` 承认关联键非唯一）——这是数据去重问题。差异文件按 billDate 幂等覆盖（`TxnDiffFileGenerator.java`），重复跑非资损。
- **结论**：按"多实例并发"上领取锁无收益；真正该做的是 ingest 前按 ON 键去重（另有 `reconcile` 无事务问题在第9轮单列，勿并入）。

## 五、回调无验签无幂等键（1 项，安全红线须裁决）

`PayCenterCallbackController.java:27-44`：事实属实（直接 `@RequestBody` 交 service、DTO 无 sign/notifyId、service 无验签），但报告危害定性夸大。

**现有防护（报告完全略过）**：
1. **状态机 CAS**：`GateTxnPayMapper.xml:185-203 convergeDebitStatus`——失败回调白名单 `('INIT','PROCESSING','RETRY')` **不含 SUCCESS**，伪造失败回调打不回成功；只有成功回调白名单含 `FAIL`（`:198`）→ **FAIL→SUCCESS 是唯一真实资损路径**，报告"双向篡改"是错的。
2. **硬限次+留痕**：`MAX_PAY_CALLBACK_PUSH=2`、`countPayPush`、超限标 MANUAL（`AlipayPayCallbackServiceImpl.java:23,66,76-84`）；退款侧 CAS 幂等（`:113-132`）。
3. **既有裁决**：`alipay-channel.md:76,95,187`、`decisions.md:1200,3010-3013,5210-5211` 多次明确 internal/payNotify 无鉴权属既有缺口、"**按用户裁决本轮不动，单独排期+人工安全复核**"。

**为何不能直接修**：
- §4.2 安全红线（AGENTS.md:34）：涉及签名 NEVER 擅自改，须人工复核。
- **签名体系根本没就绪**：`alipay-channel.md:186` 明确 `PayCenterClient.signRequest` 仍是 `setSign("test")` 占位、私钥为空、支付中心未开验签——单方面给入向加验签会破坏在用契约。
- 端点本就是支付中心的对外回调契约（`pay.center.callback-url` 下发，`alipay-channel.md:37-39`），"内网可达"写窄了暴露面。

**结论**：真实 P2（FAIL→SUCCESS 单向资损路径成立），但属长期挂账的安全专项，须跨模块契约变更 + 支付中心联调 + 用户裁决，**任何 AI 不得擅自加签名逻辑**。
