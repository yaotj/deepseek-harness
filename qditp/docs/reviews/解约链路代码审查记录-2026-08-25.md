## P0（1）

### P0-1 新增内部接口无鉴权 + 无归属校验，可越权解约任意用户
`TerminationInternalController.java:20-54`

三个状态变更型 POST（`checkFailedOrders` / `execute` / `notifyFailed`）无任何鉴权或验签：`pay-sign-server` 未引入 spring-security，全模块无 `HandlerInterceptor` / `WebMvcConfigurer` / `OncePerRequestFilter`，也无 `verifySign` 调用，不存在全局兜底。被暴露的 `TerminationInternalServiceImpl.executeTermination`（92-122 行）仅按 `requestSignSeq` 查询并推进状态，请求中的 `thirdUserId` 只用于写日志、不参与比对；`notifyTerminationFailed` 同理。两者叠加后，任何网络可达方枚举流水号即可强制解约任意用户并触发真实支付平台解约。

补充：全仓库检索 `internal/termination`、`checkFailedOrders`、`notifyFailed` 仅命中本模块自身，rpc 模块无对应 client、无任何服务调用这三个接口——需确认调用方是否漏提交，否则这是无调用方的裸暴露面。

修复方向：

1. 接入内部调用凭证或验签 + 网关/NetworkPolicy 白名单。注意本项目入向验签并非统一 SHA256WithRSA，应对齐现有实现（`AccountRequestVerifier` 摘要式、`ItpRequestSignVerifier`），不要自行新造签名逻辑。
2. service 侧补归属校验：`terminationRequest.getThirdUserId().equals(request.getThirdUserId())`，并对 `requestSignSeq` 做格式白名单。
3. 涉及支付与签名，合入前需人工复核安全合规性。

## P1（5）

### P1-1 事务未提交即提交异步通知
`PaySignWorkflow.java:795-814`

在 `@Transactional` 方法内、状态更新未提交时就提交异步通知任务。异步线程会先发出 HTTP 通知，再 UPDATE 同一行——需等外层事务释放行锁，期间占用 notifyExecutor 线程与数据库连接；若外层事务随后回滚，APP 已收到通知而 DB 状态回退。修好 B1 后回滚会真实发生，此问题从理论变为必然触发路径。

修复方向：用 `TransactionSynchronizationManager.registerSynchronization(...)` 在 `afterCommit` 中触发通知，或把通知职责移出该事务方法。

### P1-2 通知重试次数计算后被丢弃
`AppNotifyServiceImpl.java:275-285`

新增的 `updateNotifyStatus(AppTerminationRequest, ...)` 计算了 `update.setNotifyRetryCount(request.getNotifyRetryCount() + 1)`，但只把 status/time/result 传给 mapper，`APP_TERMINATION_REQUEST.NOTIFY_RETRY_COUNT` 永远为 0，后续按重试次数限次的补偿逻辑失效。`AppTerminationRequestMapper.increaseNotifyRetryCount`（第 39 行，XML 109-111 行）已实现自增却未被调用。另：`notifyRetryCount` 为 `Integer`，历史或外部写入的 null 行会在拆箱时抛 NPE，导致整行通知状态无法更新（`requestTermination` 插入路径已显式置 0，风险范围有限）。

修复方向：失败分支改调 `terminationRequestMapper.increaseNotifyRetryCount(request.getRequestSignSeq())`，删除无效赋值。

### P1-3 解约通知无补偿入口
`AppNotifyServiceImpl.java:210-225`

`compensateNotify` 定时任务只扫 `paySignRequestMapper.selectByNotifyStatus("FAILED", 3)` 重推签约类通知，本次新增的 `APP_TERMINATION_REQUEST.NOTIFY_STATUS='FAILED'` 没有任何补偿入口。异步通知失败后 APP 永远收不到解约结果，用户侧解约状态一直悬挂。

修复方向：按项目既有模式（落库状态 + `@Scheduled` 扫表重试）在 `compensateNotify` 增加 `terminationRequestMapper` 的 FAILED 且 `notifyRetryCount < 3` 扫描分支；需先修 P1-2，否则重试次数恒为 0 会无限重推。Mapper 目前也缺按 `notifyStatus` 查询的方法。

### P1-4 幂等校验漏 PENDING 态
`PaySignWorkflow.java:749-756`

`receiveTerminationResult` 只把 SUCCESS/FAILED 视为已处理。PENDING（仅登记解约申请、尚未经 `/execute` 做扣费失败订单与 T+4 校验）状态的回调同样会走完整清理流程——删除签约记录、清空默认支付通道、写成功状态并通知 APP，绕过前置校验；叠加 P0-1 的无鉴权暴露面可被直接构造触发。（PENDING→SCANNING 的推进只发生在 `TerminationInternalServiceImpl.executeTermination` 99-111 行。）

修复方向：改为状态白名单——仅 SCANNING 允许处理，SUCCESS/FAILED 幂等返回成功，PENDING 及其他状态返回状态不正确并记录告警日志。

### P1-5 account-server 事务内吞异常导致部分提交
`AccountApplicationServiceImpl.java:466-479`

`requestRemovePayChannel` 为 `@Transactional`，方法整体 catch Exception 后返回 SYSTEM_ERROR，异常不外抛。新增的 `UserItpRegLog` 插入若失败，前面的默认支付通道清空仍会提交，出现"通道已清、无解约日志"的部分提交，影响 ACC 对账口径。

修复方向：对不可恢复的持久化异常改为抛出（或标记 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`），确保通道清空与日志写入同生共死。

## 建议的处理顺序

1. **一组处理 B1 + P0-1 + P1-4**：无鉴权入口、PENDING 态可绕过前置校验、清理失败静默成功，三者叠加构成一条可被外部触发的资金侧数据不一致路径。
2. B1 修好后回滚成为常态，紧接着处理 **P1-1**（事务提交后再通知），否则会出现"回滚但 APP 已收到解约成功通知"。
3. **P1-2 → P1-3**：先让重试次数落库，再补解约通知的扫表补偿。
4. **P1-5、P2-2**：收敛事务边界与并发幂等，P3-1 随之消失。
5. 阻塞合入的风格问题（B2~B15）与 P2/P3 复用项可在同一轮清理。
