# 事务内 RPC 与回调幂等审查记录（2026-08-27）

## 背景

2026-08-26 21:07~21:14 生产事故：订单 `GT20260826210647653586419` 的支付成功回调被支付中心循环重推 8 分钟。
根因链路已写入 `AGENTS.md` §5.2（`@Transactional` 内发起 RPC ⇒ 行锁跨网络 ⇒ Druid `remove-abandoned-timeout=60` 强杀连接 ⇒ 事务整体丢弃 ⇒ 响应退化成 UUID retCode ⇒ 上游继续重推）。

本次以该事故为样本做了两轮全仓库审查：

- **事务内阻塞式跨进程调用**：19 处「先写库后调远端」+ 11 处「先调远端后写库」。
- **入向回调幂等**：26 个写类型外部回调入口，仅 4 个真正幂等。

## 已修复（均已编译验证，**尚未部署、未回归**）

### pay-sign-server

- `PaySignWorkflow.receivePayResult` — 去掉 `@Transactional`，方法头补块注释说明为何 NEVER 加回来（尾部要同步 push gate-txn-pay）。
- `PaySignWorkflow.requestPay` — 去掉 `@Transactional`。第二条理由比锁竞争严重：「我要去扣款了」的标记原先直到支付中心返回后才提交，事务丢弃时支付中心可能已扣款成功，属资损级缺陷。
- `PayTxnDetailMapper.updatePayCallback` — 恒真 WHERE 换成列级状态白名单 `(PAY_STATUS IS NULL OR PAY_STATUS IN ('INIT','PROCESSING','RETRY','FAIL'))`；`MERCHANT_ORDER_NO` / `CHANNEL_ORDER_NO` / `PAY_USER_ID` / `PAY_TIME` 补 `NVL`。
  配套改 `PaySignWorkflow` 调用点：影响 0 行时先查当前状态，已是目标状态判为重推、打 INFO 后**继续走 `syncGateTxnPayStatus`**；否则才回非 0000。不配套改就会自造新的重推循环。
- `PayTxnDetailMapper.updateRefundSummary` — 累加改为按 `PAY_REFUND_DETAIL` 重算（`REFUND_STATUS = 'SUCCESS'` 的行求和），方法签名收成只传 `orderNo`，删除 `resolveRefundSummaryStatus`。

### ticket-server（闸机过闸 IF1A-01，频率最高的一处）

- 新增 `GateTicketWriter`（`@Component`，独立事务只做两条本地 SQL），`GateTicketHandler` 改为调它，避免同类自调用导致 `@Transactional` 失效。
- `AgmRideStatusServiceImpl.notifyVerifyResult` 去掉 `@Transactional`（内含 6 次 RPC，最坏 40s）。
- `dailyTicketClient.entryCheck` / `markUsed` 补异常兜底：进站校验不可用即拒绝进站；出站标记失败放行出站并打 ERROR 提示次数未扣减需人工核对。

### alipay-pay-sign-server

- `AlipayPayLogMapper.updateRefundSummary` — 同样改为按 `ALIPAY_REFUND_LOG` 重算（带 `DELETE_FLAG = '0'` 过滤，金额列是字符串故 `TO_NUMBER` 求和后 `TO_CHAR` 回写），`PaymentRefundService` 里的 BigDecimal 计算段删除。
- **本模块无法在本机编译验证**：本机只有 GraalVM JDK 25，Lombok 1.18.34 在其上抛 `ExceptionInInitializerError: com.sun.tools.javac.code.TypeTag :: UNKNOWN`。已用干净 HEAD 的 worktree 复现同一错误，确认是既有工具链问题、与本次改动无关。该模块改动仅一处调用签名收窄 + 删一个 import，**缺编译器背书，合入前需在 JDK 21 环境编译一次**。

## 其它待办（非本次审查范围）

### IF8A-34 订单详情缺原始票价（`originalFare`）

现象：APP 订单详情响应里没有 `originalFare` 字段。**不是代码漏字段**，是库里该列为 NULL，Fastjson2 默认不序列化 null，字段整个消失。

已核实：

- DTO 有字段（`model/.../app/TransRecordDTO.java:33`），详情侧已赋值（`ticket-server/.../TransQueryHandler.java:406`），列表侧也已赋值（`:185` → `TransRecordAssembler.java:40`），`GateTxnPayMapper.xml` 的 resultMap / SELECT / INSERT 都带 `ORIGINAL_FARE`。读取链路是通的。
- `GATE_TXN_PAY` 唯一那行（`GT20260826210647653586419`）`ORIGINAL_FARE` 为 NULL，同时 `EXPECTED_GATE_AMOUNT` / `WALLET_TOTAL_AMT` / `DISCOUNT_LEVEL_AMT` / `DISCOUNT_RATE` / `TRANSFER_FLAG` / `CUMULATIVE_TYPE` 也都是 NULL，只有 `TOTAL_AMOUNT=200` 有值。
- 写入侧「调 para-server 查票价再落 `ORIGINAL_FARE`」这段（`GateTxnPayServiceImpl` 里 `paraClient.requestTicketPriceByStation(...)` → `order.setOriginalFare(...)` → 反推 `expectedGateAmount`）在 `git diff` 里**全是新增行**，属于未提交代码，线上 `gate-txn-pay-server` 从未跑过。所以生产 `ORIGINAL_FARE` 一直是 NULL，不是偶发。

待办：

1. 部署 `gate-txn-pay-server`（当前未随 2026-08-27 那批一起发），新建单才会开始写 `ORIGINAL_FARE`。
2. 部署前确认 para-server 票价接口在生产可达：`gate-txn-pay-server` 的 `service.para.url` 是否正确，以及 `requestTicketPriceByStation` 的入参站点编码口径与 `GATE_TXN_PAY` 里存的进出站编码是否一致。
3. 注意现有失败分支：`fareResult == null || retCode != "0000" || originalFare <= 0` 时会走降级支，此时 `ORIGINAL_FARE` 仍为 NULL 且 `expectedGateAmount` 也算不出来。需要确认降级语义是「放行但金额留空」还是「拒绝建单」，并确保降级时有 ERROR 日志可追。
4. 历史数据（含 08-26 之前的老单）的 `ORIGINAL_FARE` 无法自动补齐，APP 上这批老订单详情会一直缺该字段，需业务确认是否接受，或另做一次性回填。
