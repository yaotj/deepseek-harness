## 本次踩到的方法论坑（下次直接复用）

1. **排除目录 NEVER 用 basename 匹配**：`EXCLUDE = {"web"}` 会误伤包名 `com.chinasofti.huateng.web.*` 与 `resource/micro/web`，一次就虚增 25 个假差集（41 → 16）。MUST 只按绝对路径排除顶层前端目录。
2. **端口正则必须三形态全兼容**：`server.port=9113`、`server.port=${SERVER_PORT:9113}`、yml 的 `server:\n  port: 58101`。只写第一种会把 face-pay / collect-pay / card-pool / recon / trans-query 五个模块误报成"未声明"。
3. **NEVER 对仓库根目录 `grep -rn`**：会扫进 `web/` 的 1.6 万前端文件，直接 SIGTERM。用带索引的检索工具。
4. **末段比对必须先过滤网关路由前缀**：`/itptvm/`、`/itpbom/`、`/fep-app/`、`/itpagm/` 等是 K8s VirtualService 上的前缀，代码里本就没有；不过滤会得到 121 个全假的"缺失"。
5. **内容 grep 验证 URL 时对 `.java` 绝对路径必然零命中**（文件名不会出现在自身内容里），要改成文件存在性判断。
6. **只查类名会漏掉改名的方法**：本轮靠类名查没发现 `archiveUserInfoIfLastChannelRemoved`，补查方法名才抓到（已改名为 `archiveIfLastChannelRemoved`）。方法名比类名漂移更快，MUST 单独过一遍。

## 附：本次顺带识别的工作流程，以及过期为什么会发生

### 流程骨架（`AGENTS.md` §6，5 步）

1. **Analyze** — 理解需求，定影响模块与接口编号
2. **Search** — 在 `model` / `rpc` / `micro` 中找可复用组件
3. **Plan** — 列出改动文件，等确认（简单 bug 可跳过）
4. **Implement** — 编码，受 §5 STRICT RULES 约束
5. **Review** — 自检三查：`javax` 误用 / 新依赖 / 幂等遗漏

前置（业务开发任务专用，§2.2）：读 `docs/business/<域>.md` → 读原始规格 docx → 读核心类源码确认状态机、字段、幂等、异常码。

架构决策另有四条判据，在 `docs/domain/README.md` §二：双向 RPC = 边界画错 / 1:N 子实体 NEVER 是父状态机的一个状态 / 热路径写入定 owner / 域内应能本地事务强一致。

构建部署是独立一套三步序列（§7）：`install model,rpc`（带 `-Djkube.skip=true`）→ `package 业务模块`（**这一步就会推镜像**，NEVER 加 `-am`）→ `kubectl set image`。判成功 MUST 在输出里找 `digest:` / `Pushed`，**NEVER 看退出码**（管道会吃掉 Maven 的退出码）。

### 结构性缺口：流程里没有「文档同步」这一步

§5.3 要求「修改接口时 MUST 同步更新 `docs/business/<域>.md`」，但**这条约束不在 §6 的五步流程里** —— 五步到 Review 就结束了，没有「回写提示词」这一步。本次查出的三条真过期（AppPayOrderMapper、`AccountApplicationServiceImpl`、`archiveUserInfoIfLastChannelRemoved`）**全部是改名/删除时没回写文档**，与这个缺口完全对应。

另有一处衔接不清：§2.2 与 §6 各自写了一套「MUST 按顺序执行」，但没说明两者的先后与叠加关系（实测是 §2.2 的三层阅读作为 §6 的前置）。
