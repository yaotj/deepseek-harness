## 一、现状与目标

### 1.1 现状（实测）

| 项 | 事实 |
|---|---|
| 物理位置 | 单实例 `172.20.222.3:1521 / AFCITPDB`，唯一 schema `QDITP`（用户 `qditp`） |
| 表规模 | **162 张业务表**（另 3 张 `BAK_RECON_*` CTAS 快照；2026-10-14 查库实测 `all_tables WHERE owner='QDITP'`），全部落在同一 schema；分库计划清单当前覆盖 127 张，**34 张漏统待补**（见计划 §3 勘误） |

| 环境约束 | **唯一目标业务库**，无第二套环境；`mcp_database_qd` 无只读保护、删除不可回滚 |
| 双跑风险 | recon / web-admin / face-pay / collect-pay 定时任务**无分布式锁**，两套同跑一库会重复扣费与重复投对账文件 |

### 1.2 目标

在 `AFCITPDB` 内新建 **4 个 schema + 4 个独立表空间 + 4 个独立临时表空间**，把 129 张表按业务聚类迁入：

| 目标 schema | 默认表空间 | 默认临时表空间 | 表数 | 业务域 |
|---|---|---|---:|---|
| `QDITP_USER` | `ITP_USER_TS` | `ITP_USER_TEMP` | 13 | 账户/员工卡/开户/卡池 |
| `QDITP_TXN` | `ITP_TXN_TS` | `ITP_TXN_TEMP` | ~36 | 支付签约/支付宝/闸机扣费/设备购票/日票/对账 |
| `QDITP_RIDE` | `ITP_RIDE_TS` | `ITP_RIDE_TEMP` | 3 | 乘车码/过闸/票卡状态 |
| `QDITP_PLAT` | `ITP_PLAT_TS` | `ITP_PLAT_TEMP` | ~71 | 黑名单/密钥/参数/ACC设备/管理后台/调度 |

## 二、分组原则与跨库共享策略

### 2.1 核心分组原则

- **强耦合表尽量同库**，减少跨库读
- **对账源表 `GATE_TXN_PAY` / `DAILY_TICKET_ORDER` / `F2F_*` 与 `RECON_*` 全部归入 `QDITP_TXN`**，对账不再跨库读源
- **`USER_ITP_REG_INFO` 留在 `QDITP_USER`**，由分流网关 qdscg 用 `itp_ro` 只读账号跨库访问
- **公共引用数据（黑名单/参数/密钥/SYS/QRTZ）全部归 `QDITP_PLAT`**，跨库消费方建同义词 + 只读授权
- **交易数据绝不跨库 JOIN**，跨域需要数据走服务调用或文件，不在 DB 层做跨库事务

### 2.2 跨库共享表清单

| 表 | 拥有库 | 谁跨库用 | 处理策略 |
|---|---|---|---|
| `USER_ITP_REG_INFO`（+LOG） | USER | 分流网关 qdscg（只读路由） | 归 USER；网关用 `itp_ro` 只读账号跨库授权 + 同义词 |
| `APP_USER_PAY_CHANNEL` | USER | 支付域读 | USER 拥有，TXN 只读引用（同义词） |
| `TBL_STATION_INFO`（para） | PLAT | 多域读站线 | 统一收敛到 PLAT，RIDE 的 `STATION_INFO` 下线，改同义词 |
| `BLACKLIST*` | PLAT | 各交易服务黑名单校验 | PLAT 拥有，各库只读授权 + 同义词 |
| `METRO_CA_KEYSTORE` / `METRO_MEMBER_STATIC_KEY` | PLAT | AGM/fep-dev 密钥同步 | PLAT 拥有，设备域只读 |
| `TBL_*` 参数/票价/风险 | PLAT | 计费、闸机、风控多域读 | PLAT 拥有，各库只读授权 + 同义词 |
| `SYS_JOB` / `QRTZ_*` | PLAT | web-admin 内存 JobStore | 留 PLAT；其它模块 `@Scheduled` 属内存任务，不依赖这些表 |
| `RECON_*` 读源表 | TXN 内 | recon 读 GATE/DAILY/F2F | **已同库（TXN），零跨库读** |

## 四、P0 缺陷与风险

### 4.1 三大必炸坑

1. 🔴 **`CREATE TABLE ... AS SELECT` 会剥光分区 + 索引 + 约束**。对分区表、带索引/约束的表，**严禁**用 CTAS 做主迁移。正确做法：用 `DBMS_METADATA.GET_DDL` 取出完整结构 DDL（含 PARTITION 子句、索引、约束），在目标 schema 重建，再 `INSERT /*+ APPEND */` 灌数。

2. 🔴 **`F2F_ORDER` / `F2F_PAYMENT` / `F2F_RESULT_REPORT` 带 GLOBAL 唯一索引**（P0-3）。`DROP/TRUNCATE PARTITION` 或迁移后分区维护会让全局索引 **UNUSABLE**，导致该表读写全挂。M0 优先改 LOCAL；若改不动（唯一键不含分区键），迁移期所有分区 DDL **必须**带 `UPDATE GLOBAL INDEXES`。

3. 🔴 **跨库只读引用靠同义词 + 授权，不能跨库 JOIN 交易数据**。PLAT 拥有公共引用表，USER/TXN/RIDE 建私有同义词 + `GRANT SELECT`；`USER_ITP_REG_INFO` 对网关 `itp_ro` 只读授权。

### 4.2 容量热点表（年增量占全库 81%）

| 表 | 所在域 | 年增量占比 | 优先级 |
|---|---|---|---|
| `PAY_CALLBACK_LOG` | TXN | ~25% | P0，迁移后优先排归档 |
| `GATE_TXN_PAY` | TXN | ~20% | P0，迁移后优先排归档 |
| `ALIPAY_PAY_CENTER_MSG_LOG` | TXN | ~18% | P0，迁移后优先排归档 |
| `ALIPAY_PAY_CALLBACK_LOG` | TXN | ~10% | P0，迁移后优先排归档 |
| `QRCODE_TXN_DETAIL` | RIDE | ~8% | P0，迁移后优先排归档 |

### 4.3 双跑风险

recon / web-admin / face-pay / collect-pay 定时任务**无分布式锁**，迁移窗口内 MUST 停跑或加 `@SchedulerLock`，避免旧库 + 新库双写导致重复扣费与重复投对账文件。

## 六、执行顺序与操作清单

### Step 1：M0 分区补建（2026-12-15 前完成）

```bash
# 1.1 跑 precheck 查出 15 张分区表的真实分区键 + 当前最高上界
sqlplus qditp/qditp@//172.20.222.3:1521/AFCITPDB @scripts/migration/20261014_m0_partition_precheck.sql

# 1.5 打包发给 DBA 审批
# 1.6 DBA 在维护窗口执行 → 验证无 ORA-14xxx 错误
```

### Step 2：M1 基础建设（表空间 + schema + 授权）

```bash
# （参考 export_qditp_{user,ride,txn}.sql 里的完整命令）
```

```bash
# 4.3 USER / RIDE / TXN 并行导入
# （TXN 域导入期 MUST 停 recon/face-pay/web-admin 定时任务）
```

### Step 5：M4 全量校验

```bash
# 5.1 行数比对（每张表 src vs dst）
# 5.2 索引状态校验（F2F_* GLOBAL 索引应为 VALID）
```

## 八、关键设计决策

### 8.1 STATION_INFO 技术债收敛

- **问题**：`STATION_INFO`（ticket-server，RIDE 域）与 `TBL_STATION_INFO`（para-server，PLAT 域）两处并存
- **方案**：RIDE 域不迁实体表，改为指向 PLAT 的 `TBL_STATION_INFO` 的**同义词**
- **效果**：ticket-server **零代码改动**，所有查 `STATION_INFO` 的代码自动路由到 PLAT

### 8.2 F2F_* GLOBAL 唯一索引处理

- **问题**：`F2F_ORDER` / `F2F_PAYMENT` / `F2F_RESULT_REPORT` 带 GLOBAL 唯一索引，分区维护会让索引 UNUSABLE
- **方案 A（推荐）**：M0 裁定是否可改 LOCAL（需唯一键含分区键），可改则一劳永逸
- **方案 B（兜底）**：迁移期所有分区 DDL 带 `UPDATE GLOBAL INDEXES`（等效全索引重建，性能代价高）
- **本手册默认方案 B**（安全优先），若 DBA 裁定可改 LOCAL 则按 §1.3 执行

### 8.3 itp_ro 只读账号

- **用途**：qdscg 分流网关点查 `USER_ITP_REG_INFO` 做路由判定
- **权限**：`CREATE SESSION` + `CREATE SYNONYM` + `SELECT ON USER_ITP_REG_INFO`
- **表空间**：共享 `USERS` + `TEMP`（默认推荐）；DBA 要求隔离时启用附录 B 独立表空间
- **契约**：维持 `USER_ITP_REG_INFO` 对 `itp_ro` 只读（qdscg 已按此实现）

### 8.4 逻辑分库不解决容量

- 逻辑分库（同实例多 schema）**不增加任何容量**
- 容量 P0-4（`RACDG` 89.60%）须配合 M0 磁盘均衡另行处理
- 分库的最实在运维收益：5 张热点表逐库隔离后，分区维护/归档/压缩可**逐库独立**实施
