# 流量切换 Runbook（新旧应用互切 / 入向路由分发）

面向「把某个业务域的流量从一个服务切到另一个服务」的操作。**当前唯一在用的场景**是 TVM / BOM 域在
`face-pay-server`（新）与 `collect-pay-server`（旧）之间来回切，但下面的机制对 `fep-app-vr` 里
**任何一条前缀**都成立。

> 本文是 ADR-D85 的操作化展开。判据与「为什么不能那样做」的依据见 `../domain/decisions.md` ADR-D85、
> `AGENTS.md` §8；本域的业务差异见 `../business/tvm-bom-pay.md`。

## 一、只有两个开关

流量分两条完全独立的路径进来，**切一个业务域通常要同时评估这两处**：

| 入口 | 开关 | 生效方式 | 影响面 |
|---|---|---|---|
| **设备域**（TVM / BOM / AGM 等直连集群的设备） | ns `itp` 的 VirtualService **`fep-app-vr`** 对应前缀那条 route 的 `destination` | 改完**立即生效**，不重启任何服务 | 只影响该前缀的入向流量 |
| **APP 域**（APP → `fep-app` → 下游） | `fep-app` Deployment 的 env（如 **`service.collectPay.url`**，**键名带点**） | 触发 `fep-app` **滚动重启**，期间全部 APP 接口短暂受影响 | 该 env 对应的下游全部 APP 链路 |

**APP 域不经过 `fep-app-vr` 的业务前缀**：APP 先打 `/fep-app/`，由 `fep-app` 再按 `rpc` 的
`service.*.url` 转发，所以改 VS 的 `/itptvm/` 与 `/itpbom/` **不会**改变 APP 侧落点。

## 三、标准操作四步

所有命令都走 `ssh k8s-master`（**本机 kubeconfig 只有 orbstack、没有 ITP 集群凭据**）。

### 第 1 步：查现状并记下原值（回滚依据）

```bash
ssh k8s-master "kubectl get vs fep-app-vr -n itp -o jsonpath='{range .spec.http[*]}{.match[0].uri.prefix}{\" -> \"}{.route[0].destination.host}{\":\"}{.route[0].destination.port.number}{\"\n\"}{end}' | cat -n"
ssh k8s-master "kubectl get deploy fep-app -n itp -o jsonpath='{range .spec.template.spec.containers[0].env[*]}{.name}={.value}{\"\n\"}{end}' | grep -i collectPay"
```

输出里的行号减 1 就是 `spec.http[N]` 的下标。

### 第 2 步：patch，**必须带 `test` op**

`--type=json` 的 `test` op 会在下标漂移或原值不符时整条 patch 失败，避免改错位置。
下例是把设备域两条前缀从 face-pay 切到 collect-pay：

```bash
ssh k8s-master "kubectl patch vs fep-app-vr -n itp --type=json -p '[
{\"op\":\"test\",\"path\":\"/spec/http/4/match/0/uri/prefix\",\"value\":\"/itptvm/\"},
{\"op\":\"test\",\"path\":\"/spec/http/4/route/0/destination/host\",\"value\":\"face-pay-server-svc\"},
{\"op\":\"test\",\"path\":\"/spec/http/5/match/0/uri/prefix\",\"value\":\"/itpbom/\"},
{\"op\":\"test\",\"path\":\"/spec/http/5/route/0/destination/host\",\"value\":\"face-pay-server-svc\"},
{\"op\":\"replace\",\"path\":\"/spec/http/4/route/0/destination/host\",\"value\":\"collect-pay-c23ku-svc\"},
{\"op\":\"replace\",\"path\":\"/spec/http/4/route/0/destination/port/number\",\"value\":30024},
{\"op\":\"replace\",\"path\":\"/spec/http/5/route/0/destination/host\",\"value\":\"collect-pay-c23ku-svc\"},
{\"op\":\"replace\",\"path\":\"/spec/http/5/route/0/destination/port/number\",\"value\":30024}
]'"
```

反向（切回 face-pay）把两个 `test` 的 value 换成 `collect-pay-c23ku-svc`、两个 `replace` 换成
`face-pay-server-svc` + `30025` 即可。**`rewrite.uri` 一律不动**（`/itptvm/` 与 `/itpbom/` 两条的
rewrite 是带前缀的，不是 `/`，改掉会让下游收到错误路径）。

### 第 3 步：三重验证，缺一不可

```bash
# ① VS 读回
ssh k8s-master "kubectl get vs fep-app-vr -n itp -o jsonpath='...' | grep -E 'itptvm|itpbom'"
# ② envoy 实际路由表（VS 写成了不等于 envoy 已下发）
ssh k8s-master "kubectl exec -n itp-gateway <itp-gateway-pod> -- curl -s '127.0.0.1:15000/config_dump?resource=dynamic_route_configs' | grep -o '<目标svc>[^\"]*itptvm[^\"]*'"
# ③ 目标服务探活（从 k8s-master 用 NodePort，NEVER 用 svc DNS）
ssh k8s-master "curl -s -m 8 -w '\nhttp=%{http_code}\n' http://172.20.211.23:<NodePort>/actuator/health"
```

②要看到形如 `collect-pay-c23ku-svc.itp.svc.cluster.local:30024/itptvm/*` 的条目；
③要 `http=200` 且 body 里 `db` / `readinessState` 全 `UP`。

### 第 4 步：落点确认（真流量证据）

切完等设备下一次请求（心跳几秒一次、业务单看操作），确认请求确实落在目标服务：

```bash
ssh k8s-master "kubectl exec -n itp <目标pod> -c <容器> -- sh -c 'grep -h \"receive request url=\" /home/javaapp/app/logs/*/*.log | grep -vi heard | tail -5 | cut -c1-160'"
```

或直接看网关访问日志里 `upstream_cluster` 指向哪个 svc：

```bash
ssh k8s-master "kubectl logs -n itp-gateway <itp-gateway-pod> --since=5m | grep -v notiDeviceHeard | grep -o '\"start_time\":\"[^\"]*\"\|\"path\":\"[^\"]*\"\|\"upstream_cluster\":\"[^\"]*\"' | paste - - -"
```

## 四、NEVER 清单

- **NEVER 假定「按 `ticketLogicNum` 查得到」在两个应用里一致 —— 新应用大小写敏感、旧应用不敏感**
  （2026-09-16 切流后实测确立，ADR-D117）。旧 `TvmSubTicketMapper.selectSubTickettByCondition` 写的是
  `UPPER(TICKET_LOGIC_NUM) = UPPER(#{ticketLogicNum})`；新 `F2fTicketMapper` 的四条语句
  （`selectByLogicNumAndTransDate` / `selectLatestByLogicNum` / `updateStatus` / `updateRefundNo`）
  **全是精确等值**。而设备对**同一张卡**两种大小写都发过（实测 `001707310d00e602` 与 `001707310D00E602` 并存）。
  当前处置是**数据侧把 `F2F_TICKET.TICKET_LOGIC_NUM` 统一成大写**（按用户裁决，未改代码），
  因此**设备送小写时仍会返 `8999`**。彻底修法是把那四条语句的入参侧改成 `UPPER(#{...})` + 落库侧归一化，
  **NEVER 把列侧写成 `UPPER(TICKET_LOGIC_NUM)`** —— 那会让 `UK_F2F_TICKET_LOGIC` 失效，得另建函数索引。
- **NEVER 在有设备正对历史单高频轮询时切流**（2026-09-16 实测发现，ADR-D112 续（四））。设备 `02201101`
  以 **0.8 次/秒** 轮询 `requestOrderResult`（`ticketLogicNum=001707310D013231`），38 分钟内 1855 次、
  旧应用每次都正确返 `0000`，但**该单在新应用上查不到**（旧库旁路已删）。切流等于立刻把这条轮询从
  `0000` 变成 `8999 没有查找到出票信息` —— 设备拿到成功结果时都不停，拿到 `8999` 后行为未知。
  切流前 **MUST** 先按 `BodyCacheFilter` 行数确认没有这种高频轮询（`grep -c "request_url=.../requestOrderResult"`），
  或已由现场 / 厂商停掉仍在跑的查询循环。
- **NEVER 改 K8s Service 的 selector 来切流量。** 两个理由：①`collect-pay-c23ku-svc` 的
  `targetPort` 是 **8080**（collect-pay 靠 Deployment env `server.port=8080` 顶掉 yml 里的 58101），
  而 face-pay 听 **58101**，翻 selector 会把全量流量打到无人监听的端口；②Service 还被
  **不经网关的内部直连方**在用（`recon-server` 的对账源、`gate-txn-pay` 的补款、`web-admin` 的
  Quartz 任务），改 selector 会连带打断它们，而改路由只影响入向流量、内部链路一行不动。
- **NEVER 用 `kubectl get vs -A` 的摘要表判断某个前缀归谁** —— 那张表只显示 name / gateways / hosts、
  **不显示 path**，据它会得出「没有 VirtualService 定义 `/itptvm`」这种错结论（2026-09-15 因此推出两版错方案）。
- **NEVER 不带 `test` op 直接 `replace` 下标**（下标会漂移）。
- **NEVER 只凭「patch 成功」就认为切完了** —— 必须过第 3 步②③与第 4 步。
- **NEVER 为了「切干净」顺手改 `rewrite.uri`**。
- **NEVER 用 `<svc>.itp.svc:<port>` 从 `k8s-master` 探活**（那台不在 Pod 网络、无 CoreDNS，一律 `http=000`）。

## 五、切换后的数据落点差异（TVM / BOM 域）

两个服务写**完全不同的表**，核对数据时别查错：

| | face-pay-server（新） | collect-pay-server（旧） |
|---|---|---|
| 订单 | `F2F_ORDER` | `TBL_TVM_ORDER_PAY` / `TBL_BOM_ORDER_PAY` |
| 支付 | `F2F_PAYMENT` | `TBL_TVM_ORDER_PAY_PRE` 等 |
| 设备上报 | `F2F_RESULT_REPORT` | `TBL_BOM_BUS_RESULT` / `TBL_TVM_TAKE_TICKET_ORDER` 等 |
| 退款 | `F2F_REFUND` | `TBL_BOM_ORDER_REFUND` / `TBL_TVM_ORDER_REFUND` |
| 设备心跳 | `F2F_DEVICE_STATUS` | 旧表另计 |

连带四条：

- **订单号不通用；旧库只读旁路已于 2026-09-13 删除**（本文件此前写「切回新服务后旧单可经 `f2f.legacy.enabled` 查到」**已作废、NEVER 回退**，判据见 `F2fTvmOrderService.loadOrderForQuery` 的 Javadoc 与 ADR-D112 续（二））。
  **2026-09-16 已按用户裁决把旧库订单全量迁进新表**（ADR-D116）：`TBL_TVM_ORDER_PAY` 130 + `TBL_BOM_ORDER_PAY` 185 行进 `F2F_ORDER` / `F2F_PAYMENT`，两张旧退款表 247 行进 `F2F_REFUND`（4 条金额为 0 的失败记录除外）。
  于是「**按订单号**查历史单」在新服务上已经能查到，`requestPayResult` 那类以 `ORDER_NO` 为键的查询不再返 `2002`。
  **但迁移只覆盖订单 / 支付 / 退款三张表，`F2F_TICKET` 与 `F2F_RESULT_REPORT` 一行都没迁** ——
  以 `ticketLogicNum` 为键的 BOM 查询（`requestOrderResult` / 单程票退款）**仍然返 `8999 没有查找到出票信息`**，
  下面 NEVER 清单第一条那场轮询风暴的风险**没有因为这次迁移而消除**。
  对旧单退款：整单退可在新服务发起（已成功退过的会被 `UK_F2F_REFUND_IDEM` 幂等挡住，只有失败记录的单可续退，见 ADR-D116 决定 ③）；
  按票退仍只能走旧入口 `/itptvm/ci/tvm/requestRefund` 或运营后台旧接口。
  另注意 face-pay Deployment 上的 **`F2F_LEGACY_READ_ENABLED` 死 env 已于 2026-09-16 清理**，**NEVER 加回**。
- **迁移可重入，切流前 MUST 再补一次增量**：旧应用仍在写（迁移当时最新一条是 16:55:20），
  六条 `INSERT ... SELECT` 与汇总重算全部带 `NOT EXISTS`，原样重跑、命中 0 行即已追平（SQL 与回滚语句见 ADR-D116）。
- **判断「这笔到底落在哪」MUST 排除迁移行**：迁移单的 `REMARK` 一律以 `LEGACY-MIGRATION src=TBL_` 开头，
  查「某时段有没有新落单」时 **MUST 带 `AND REMARK NOT LIKE 'LEGACY-MIGRATION%'`**，
  否则会把迁进来的旧单误判成「新服务已经在收流量」。
- `collect-pay-server` **NEVER 停掉**：它还承担 `/internal/recon/export`（对账源）、
  `/internal/app-order/**`（补款）、`NoticeAppTask` 4 个旧表通知端点与旧单退款。


## 六、已实测记录（2026-09-16）

同一天在测试环境完成 **3 次来回**切换，每次都按上面四步执行、三重验证全过：

1. 13:2x 切旧（`/itptvm/` + `/itpbom/` → `collect-pay-c23ku-svc:30024`）→ 13:25:32 collect-pay 收到首个请求
2. 13:3x 切新（→ `face-pay-server-svc:30025`）→ 13:31:29 的 BOM 单落在 `F2F_ORDER`
3. 15:0x 再切旧 → envoy 与探活均确认

**第 4 次（2026-09-16 17:31，本次是「全域切新」，ADR-D117）**：设备域 + APP 域一起切到 face-pay。

- 设备域：`/itptvm/` `/itpbom/`（`spec.http[4]` / `[5]`）`collect-pay-c23ku-svc:30024` → `face-pay-server-svc:30025`，
  `test` op 全过；三重验证过（VS 读回 / envoy 出现 `face-pay-server-svc...:30025/itptvm/*` 与 `/itpbom/*` / 探活 200 且 `db` `readinessState` UP）。
- APP 域：`fep-app` 的 `service.collectPay.url` 由 `http://172.20.211.23:30024` 改为 `:30025`，
  滚更成功、探活 200（**回滚就是把这条 env 改回 30024**）。
- 落点证据（按分钟数请求行）：collect-pay 17:30 还有 4 条、17:31 起 **0 条**；face-pay 17:32 起稳定 7 条/分钟。
- 切流前置动作：迁移增量补了 3 条（1 单 + 1 支付 + 1 退款），并按用户裁决补迁
  `F2F_TICKET` +94（→100）、`F2F_RESULT_REPORT` +255（→265，全部 `PROCESSED='1'`，**NEVER 写 '0'**，
  否则 `F2fReportRecoveryJob` 会把历史上报当未处理重放）。
- 切完发现并处置了一个真实回归：**票查询大小写敏感**（见 §四 第一条）。


三次都**只动 VS 两条 route，没动 `fep-app` env**（APP 域全程留在 face-pay），因此
`fep-app` 一次都没重启，APP 侧零影响。三次 patch 的 `test` op 全部通过，未出现下标漂移。
