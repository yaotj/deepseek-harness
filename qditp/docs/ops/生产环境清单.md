### P0 — 支付回调在生产自我放大成 8 分钟死循环（2026-08-26 21:07~21:14，已修复）

2. **自持**：`PaySignWorkflow.receivePayResult` 当时带 `@Transactional`，`UPDATE PAY_TXN_DETAIL` 拿到行锁后**带着锁**调 gate-txn-pay `syncDebitStatus`，锁持到提交为止；借用超 `remove-abandoned-timeout=60` 后 Druid 强杀连接，`commit` 抛 `connection closed`，整个事务丢弃，响应退化成全局异常处理器的 UUID `retCode`，支付中心判失败再推 —— 第一次失败后每一次都注定失败。实测 `UPDATE` 等锁 44997ms、单次请求 287233ms、`V$SESSION` 持续 `enq: TX - row lock contention`、`BLOCKING_SESSION` 随强杀在等待者之间翻转。

**关键教训（推翻了一条原有假设）**：`PAY_CALLBACK_LOG` 的 INSERT 与业务 `UPDATE` 在同一事务，事务被强杀丢弃时**凭据一起回滚**。生产核对：该订单 `PAY_CALLBACK_LOG` 只有 21:21 之后的 2 条（ID 4049/4050），**21:07~21:14 循环期间零条**。所以「回滚不丢证据」这个前提在事务内不成立，`receivePayResult` 必须无事务（或凭据走 `REQUIRES_NEW`）。

已做的修复：
- `receivePayResult` 去掉 `@Transactional`（每条 SQL 自动提交，行锁只持有语句执行期间，RPC 在无锁状态下发起）。

### P1 — 虚拟线程 pinning 风险（全服务，2026-08-26 发现，缓解已上但未取证）

`spring.threads.virtual.enabled=true` 在 `resource/micro/web/src/main/resources/web.properties:6`，**所有服务生效**（日志里 `tomcat-handler-N` 即虚拟线程命名，平台线程会是 `http-nio-<port>-exec-N`）。JDK 21 未落地 JEP 491，虚拟线程在 `synchronized` 内阻塞会 pin 住载体线程；ojdbc8 的 `PhysicalConnection` / `OracleStatement` 大量方法是 `synchronized`，**一条 60s 慢 SQL 就是 60s 的 pin**。载体线程池 `parallelism` 默认等于容器可见 CPU 数，CPU limit 偏小时一两条慢 SQL 即可 pin 满，全 JVM 虚拟线程停止调度 —— 上面 P0 的 287 秒就符合这个特征（reactor-netty epoll 是平台线程、响应早已读入，但 `block()` 所在虚拟线程的续体排不上载体）。

- 已上缓解：`docker/Dockerfile` 加 `ENV JAVA_TOOL_OPTIONS="-Djdk.virtualThreadScheduler.parallelism=8 -Djdk.virtualThreadScheduler.maxPoolSize=256"`，与容器 CPU 数解耦。这是缓解不是治本，治本是不在请求线程上做长阻塞。
- 取证手段（**MUST** 按这个来，`jstack` 看不到虚拟线程）：`jcmd <pid> Thread.dump_to_file -format=json`；按需在 Deployment 追加 `-Djdk.tracePinnedThreads=full`（**NEVER 常态开启**，pin 频繁时刷爆日志）或 JFR 事件 `jdk.VirtualThreadPinned`。
- 仍需核实：pay-sign-server 的 CPU `requests/limits` 与 `container_cpu_cfs_throttled_seconds_total`，以及副本数（单副本时所有回调挤在一个 JVM）。

### 排查工具的已知坑（2026-08-27 记录）

- **`mcp_database_qd` 才是青岛库**（`mcp_database_cc` 是长春）。需先 `createNamedConnection` 建命名连接，参数是 `jdbcUrl` + `dialect`（不是 host/port/database）；`executeQuery` 的参数名是 `connection`，不是 `connectionName`。
- **调用任何 MCP 工具前 MUST 先用 `Skill` 工具加载该 server**（`Skill(name="mcp_database_qd")`），否则一律返回 **`MCP Server mcp_database_qd 未连接`**，与连接是否注册无关。2026-09-11 实测：连着四次直接调 `UseMcpTool` 全是这句，`Skill` 加载后同一批调用立即正常。**这是第三种「未连接」成因**，与下一条记的两种都不同：判据是「连空参的 `listConnections` 都返回这句」。
- **`EXPIRED_LEASE` 的连接照样能用，NEVER 急着重建**。2026-09-11 实测 `qditp_e2e3`（`leaseExpiry` 已过、`status=EXPIRED_LEASE`）执行 `executeQuery` 与 `executeDdlBatch` 全部正常。反倒是新建连接不可靠：`createNamedConnection` 返回 `"Connection created and tested successfully"`，紧接着 `describeConnection` 报 `Connection not found`、`listConnections` 里也没有它。所以**优先复用 `listConnections` 列出的现有连接**，实在要建再建。`createNamedConnection` 的必填参数是 `name` / `jdbcUrl` / `username` / `password` / `dialect` 五个（**不是 `connectionName`**）。
- **DML 不能走 `executeQuery`**：`UPDATE` / `INSERT` 会报 `ORA-17021: Missing defines`（它按查询走、要求结果集），必须用 `executeDdl`。
- **`executeDdl` 的 `affectedRows` 恒返回 0**，`ALTER TABLE` 与 `UPDATE` 都是 0 但实际都生效了。**NEVER** 把 0 当成「没改到行」，判断结果 MUST 回头 SELECT 核对。
- ~~已确认不可用的 MCP 工具：`executeDdlBatch`~~ —— **`executeDdlBatch` 可用，本条已被 2026-09-11 实测推翻**：一次提交 2 条 `ALTER TABLE` 全部 `success`、返回 `succeeded:2 failed:0` 与逐条 `durationMs`。参数名是 `statements`（数组）+ `connectionName`。其余仍不可用：`backupTable`、`showLocks`、`showBlockingTree`。
- **`kubectl get pods` 显示 `2/2 Running` `RESTARTS 0` 不能证明应用活着**：这些服务的 entrypoint 脚本在 Java 进程退出后仍会撐住容器。确认服务真的起来了 MUST 在日志里 grep `Started XxxServer in`。
- **确认部署是否真的生效**：pod 名里的 ReplicaSet hash **与**镜像 tag 两者都必须变。`kubectl rollout status` 可能对着十几小时前那次 rollout 报 "successfully rolled out"，具有误导性。
- **业务 Pod 在 `itp` 命名空间**（不是 `qditp`）。
- **跳板机 `k8s-master` 上没有 `sqlplus` / `sqlcl` / `python3`，只有 Java 8**（2026-09-11 实测）。要在跳板机上跑 SQL 的可行路径：从 `/home/java/ticket-server-*.jar` 里 `jar xf BOOT-INF/lib` 取出 `ojdbc8-19.18.0.0.jar`，再用一个 Java 8 源码级的小 runner（`java -cp ojdbc8.jar Runner.java` 形式）执行。⚠️ **本机 JDK 21 编译该 runner MUST 加 `--release 8`**；**远端 `javac` 是 Java 8 且默认 ASCII 编码，直接在远端编译含中文注释的源码会报 `unmappable character`**，所以要么源码不带中文、要么在本机编好 class 再传。**DB 口令 MUST 从 Deployment env 里取、只经 shell 变量传给进程，NEVER 打印、NEVER 写进脚本或文档。**

### P1 — `PAY_REFUND_DETAIL` 有 6 条 `RETRY` 状态无人补偿（2026-09-15 实测，ADR-D91 / D92 同批发现）

### P1 — `PAY_REFUND_DETAIL` 有 2 行畸形 `TXN_DATE`，落在错误分区且每轮必被扫到（2026-09-15 实测）

两行的 `TXN_DATE` 是 `28063829` / `28064044` —— 取的是 `ORDER_NO` 前 8 位而非 `yyyyMMdd`。
`TXN_DATE` 是该表的**分区键**、也是 `UK_PAY_REFUND_DETAIL_NO` 的组成部分，
因此这两行**物理落在错误分区**，按账期查询与按唯一键防重都会偏。

⚠️ **注意方向，NEVER 记反**：字符串比较下 `'28...' > '2026...'`，
这两个值**恒大于任何 `2026xxxx`**，所以它们**永远落在 `TXN_DATE >= 今天−7天` 的窗口内、
每一轮扫表都会被捞到**（不是「恒小于、永久扫不到」—— 那个说法是错的，已被实测推翻）。
后果是每轮补偿都白跑这两行、且它们的 WARN 会长期出现在日志里。
修数据前 **MUST** 先定位写入点（哪条路径把 `ORDER_NO` 前 8 位当成了日期），
否则改完还会再产生；改行 **MUST** 先记原值并给出还原 SQL。

## 十、查看集群日志（2026-09-08 用户提供）

**本机 `kubectl logs` 用不了**：本地 kubeconfig 只有 `orbstack` 一个 context（`kubectl config get-contexts` 实测），没有 ITP 集群凭据。**NEVER** 再尝试 `kubectl logs -n itp ...`。

### 首选：`scripts/klog.sh`

```bash
scripts/klog.sh <服务名或JAR前缀> [关键字] [-f] [行数]
```

参数顺序不敏感，脚本自动识别数字、`-f` 与关键字。常用形态：

- `scripts/klog.sh para-server` — 最近 100 行
- `scripts/klog.sh para-server 500` — 最近 500 行
- `scripts/klog.sh para-server ERROR 200` — 过滤 ERROR 的最近 200 行
- `scripts/klog.sh para-server -f` — 实时跟踪，`Ctrl+C` 退出
- `scripts/klog.sh para-server Exception -f` — 实时跟踪含 Exception 的行
- `scripts/klog.sh para-server "user login" -f` — 带空格的关键字用引号
- `scripts/klog.sh para-server -2000f` — 最近 2000 行历史
- `scripts/klog.sh para-server ERROR Exception -2000f` — 多关键字 + 历史
- `KLOG_CONTAINER=nginx scripts/klog.sh gateway` — 多容器 Pod 指定容器

实现是 `ssh -t k8s-master "bash /home/java/k8s-logview.sh <参数>"`（`scripts/klog.sh:49`），用 `printf %q` 转义参数防止远端二次解析，`-t` 分配 TTY 是 `-f` 跟踪、颜色输出、`grep --line-buffered` 逐行刷新能正常工作的前提。

同目录还有 `scripts/klog-watcher.sh`（持续监视用）。

### 兜底：手工进容器

`klog.sh` 不通时（远端脚本被改名 / ssh 免密失效 / 目标服务名匹配不到）：

```bash
ssh k8s-master
# 登陆后按 k8s 常规操作定位 Pod 并进容器看日志
```

### 前置条件

本机 `~/.ssh/config` 需有 `k8s-master` 这个 Host 别名及免密配置。**AI 无法自行配置 ssh，缺失时 MUST 让用户补**。

⚠️ **日志路径不以仓库 `logging.file.path` 为准**：打包镜像用的日志配置放在服务器上、不在本仓库内（用户 2026-08-25 说明），容器内实际落盘位置以远端脚本的取值为准。

### 附.一 逐模块 jkube 真实形态（「会不会误推镜像」的唯一判据）

**判据 —— 三项同时成立才会推镜像**：① 该 execution 的 `<phase>` 绑在 `package`；② `<goals>` 里有**未被 XML 注释**的
`build` / `push`；③ 该 execution 所在 profile **本次被激活**。三项里任何一项单独看都会误判，AGENTS.md §7 已记两起
（`fep-acc-server` 栽在 ②、`face-pay-server` 栽在 ③）。

**全局实测（2026-09-16 脚本逐 pom 解析 `<execution>` / `<phase>` / `<goals>` / 所属 `<profile>` / `activeByDefault`）**：

- 声明 jkube 的 pom 共 **25 个**；**所有 execution 的 `<phase>` 都是 `package`，全仓没有一个绑 `install`**。
  这条**闭合** AGENTS.md §7「`build-image-remote` 阶段逐模块不同，`collect-pay-server` / `key-server` / `blacklist-server`
  等尚未逐个核实」的待办。**但那条规则本身 MUST 保留**：`<phase>` 可以被单独改掉，判据 ① 仍 MUST 现查，
  **NEVER 因为本次全是 `package` 就跳过检查**。
- 三种 execution 家族：
  1. **`build-image-after-package`** —— **不在任何 profile 内、恒生效**，8 个模块，goals `build`+`push`，`deploy` 一律在注释里。

- **`app` 字段取 `${appName}`**（即 `other.logging.appName=${spring.application.name}`，`web.properties:45`），

  `_time` / `_msg` / `level` / `logger` / `thread` / `traceId` / `spanId`）。
  **NEVER 把模板改成全量输出 MDC** —— `FirstFilter` 会把**全部请求头**塞进 MDC，含 `authorization`。

  原因（2026-09-08 在 web-admin 1.1.13 实测踩坑、绕了一轮）：**log4j2 把 `AppenderRef` 的 `level` 属性编译成「引用层过滤器」，
  它先于 appender 自己的 `<Filters>` 求值**。只靠 Root 的 `<AppenderRef ref="VictoriaLogs" level="WARN"/>` 时，
  业务的 INFO 事件在「引用」这一层就被 DENY、**永远走不到** appender 上那个 `ThreadContextMapFilter`，
  于是「appender 已启用 + sender 线程在跑 + MDC 键确实写入 + Root 的 WARN 能上报」四项全部成立、却查不到任何 INFO ——
  **现象极像过滤器不匹配，实际是引用层短路**。
- **Root 的 `VictoriaLogs` 引用 NEVER 放到 INFO**：各服务的报文日志（`other.web.enableLogRequestInFilter` /
  `logResponseMaxSize`）会被整体搬进日志后端，**量与敏感面都不可控**。需要单条上报走 `LoggerFactory.getLogger("VLOGS")`
  这个专用 logger（`additivity=false`，全量进 VictoriaLogs、不受 Root 的 WARN 阈值限制，两份配置口径一致、业务代码可无差别使用）。
- **需要 DEBUG 级链路采集时 MUST 交给 Deployment 的 `logging.level.com.chinasofti.huateng`**（Spring Boot 在本配置加载后套用、
  会覆盖文件里的级别），**NEVER 在 `log4j2-linux.xml` 里写死 DEBUG** —— 那份的 `RollingFile` 没有 `ThresholdFilter` 兜底，会被灌满。
  pay-sign 那份**可以**写 DEBUG，因为它的本地文件与 console 各自有 `ThresholdFilter="INFO"` 兜住。
- `log4j2-paysign.xml:26` 记了一条易错点：**`ErrorInterceptorFilter` 四个 `filter()` 重载全部 `return NEUTRAL`**
