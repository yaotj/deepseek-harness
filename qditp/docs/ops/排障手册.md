# 排障手册（qd-itp）

面向**「现象有了、但代码看着没错」**的排查。与同目录其他文档的分工：

- `生产环境清单.md` — 地址、环境变量、外部依赖（**连不通**时读）
- `流量切换.md` — 入向路由分发（**请求落到了哪个服务**时读）
- **本手册** — 现象已确认、但定位不到原因时，按什么顺序查

## ⚠️ 使用前提：本手册不是第二处事实源

本手册只做三件事：**归类症状、给出排查顺序、指向权威出处**。

规则细节以 `AGENTS.md` §5（STRICT RULES）与 §7（构建与运行）为唯一准绳。**NEVER 在本手册里改写或复述规则条文**——规则改了这里没跟，就会变成一份以 `MUST` 语气指挥人的过期副本（2026-09-23 刚清理过一批，见 `docs/reviews/提示词过期检查记录-2026-09-23.md`）。发现本手册与 `AGENTS.md` 冲突时，**以 `AGENTS.md` 为准并回来修本手册**。

引用方式一律是「症状 + 第一查什么 + 出处坐标」，不搬运条文。

## §0 先定性：三步

1. **崩在哪一段** — 编译期 / 启动期 / 运行期 / 部署后没生效
2. **是不是只在生产暴露** — `dm.properties:5` 在达梦环境关闭了 Druid WallFilter，因此 WallFilter 类缺陷**只在 Oracle 生产环境出现**（出处：`AGENTS.md` §5.1）
3. **是不是只在某一支上炸** — 「筛选条件全空」那一支往往正是前台首次进页面、不选任何条件的默认加载，也最容易被漏测

本手册收录的缺陷有个共同点：**编译通过、单测全绿、`xmllint` 也过，只在特定运行时分支上炸**。因此「本地跑一遍没问题」不构成反证。

## §1 六类高频症状

### 1.1 兜底 catch 明明写了却没生效

| 项 | 内容 |
|---|---|
| **典型现象** | 唯一索引冲突兜底失效；并发开户返 `8003 无卡资源` |
| **第一查** | 目标模块**开没开 tracing**（8 个模块名单见 `AGENTS.md` §2.2.1）。单测里没有切面，所以本地永远复现不出来 |
| **第二查** | 沿 `getCause()` **逐层**看异常有没有被换过类型，**NEVER 只看最外层类名** |
| **机理** | `resource/micro/web` 的 `MapperAspectToTrace` / `ServiceAspectToTrace` 曾用 `observation.observe(Supplier)`，Micrometer 会把受检异常之外的一切重包一层 `RuntimeException`，于是所有 `catch (DuplicateKeyException)` 全部落空 |
| **修法** | 切面 MUST 改 `observation.start()` + `openScope()` + `catch (Throwable e) { observation.error(e); throw e; }` + `finally observation.stop()`；调用侧补 `isIntegrityViolation(Throwable)` 沿 `getCause()` 链判定 |
| **样例** | `card-pool-server/.../CardPoolServiceImpl.java`；`face-pay-server` 统一走 `domain/F2fDuplicateKey.isConflict(Throwable)` |
| **出处** | `AGENTS.md` §5.2「NEVER 在切面 / 包装层把异常换类型」 |

> **一个必踩的 grep 陷阱**：`grep -rn 'catch (DuplicateKeyException' face-pay-server/src/main` 仍有 **2 处命中，但两处都在注释里**（`F2fScanPayService.java:217` 的「NEVER 退回」告示与 `F2fDuplicateKey.java:11` 的类注释）。**NEVER 据这个 grep 的计数判断代码已回退**。

### 1.2 加了字段但收不到

| 项 | 内容 |
|---|---|
| **典型现象** | APP 明明上送了新字段，服务端日志里是 `null`；一度误判成「代码没生效」 |
| **机理** | `model` 版本号恒为 2.0.0（NEVER 升号），旧镜像里打进去的是**旧 DTO 的 class**；`mvn install` 只更新本机 `~/.m2`、对已在跑的 Pod 毫无影响。Fastjson2 宽松模式**静默丢弃目标 DTO 里不存在的字段、不报错不告警** |
| **MUST** | 重建链路上**每一个经手该 DTO** 的模块镜像，**NEVER 只重建终点服务** |
| **判据** | 数一数链路上有几个模块的 `parseBizData` / RPC 序列化会经过这个 DTO。APP 类接口至少是 `fep-app-server` + 目标业务服务**两个** |
| **已发生** | IF8A-41 给 `RequestTransStatisticsReqDTO` 加 `cardType`，只重建了 `itp/ticket-server:2.1.51`，端到端打 fep-app 时日志里 `cardType='null'`；重建 `itp/fep-app:2.0.77` 后立即正常 |
| **出处** | `AGENTS.md` §7「给 `model` 的 DTO 加字段后 MUST 重建链路上每一个模块」 |

### 1.3 SQL 看着对、运行时才炸（Druid WallFilter 三陷阱）

三条同源，全部**编译、单测、`xmllint` 都发现不了**：

| # | 触发写法 | 报错 / 现象 |
|---|---|---|
| a | **SQL 正文里写注释**（`--` 或 `/* */`） | `sql injection violation ... comment not allow`，该语句**静默失效** |
| b | **`where 1 = 1` 打头 + 全部谓词都是可选 `<if>`** | `select alway true condition not allow`，只在「筛选条件全空」那一支上踩 |
| c | **子查询起了驼峰别名，外层 `<where>` / `order by` 引用物理列名** | `ORA-00904`，且被全局异常处理器包成 **HTTP 200 + UUID `retCode`**，前台只显示「查询失败」 |

- **(c) 的排查判据**：日志里 `ORA-00904` 指向的表别名若是**子查询自己的别名**（例如 `) O`），就是本条，MUST 回头看那段 `as` 列表。
- **(c) 的修法**：把外层引用换成别名（`O.createTime`），**NEVER 去动子查询里的别名** —— `resultType` 的字段映射依赖它。注意 `order by` 不在 `<if>` 里、每次都拼上，因此**任何筛选组合都失败**。
- **绕过方式 NEVER 用**：放宽 `wall.config.comment-allow` 等于全局降低注入防护等级。注释 MUST 写在 mapper XML 的 `<!-- -->` 或 Java 注释里。
- **只在 Oracle 暴露**：`dm.properties:5` 在达梦环境关闭了 WallFilter。

> **孪生陷阱：mapper XML 的 `<!-- -->` 注释里 NEVER 出现两个连续减号。** XML 规范禁止，MyBatis 解析失败 ⇒ `sqlSessionFactory` 建不起来 ⇒ **整个服务启动即挂**。异常链**最外层报的是某个无关 mapper 的 `sqlSessionTemplate` 注入失败**，极易误判成依赖问题 —— **MUST 一直往下翻到 `Failed to parse mapping resource` 那一行看文件名**。新增或改动 mapper XML 后 MUST 跑 `xmllint --noout <file>` 逐个校验。
>
> 这两条是孪生关系：上一条要求把「禁止在 SQL 正文写注释」的说明写进 XML 注释，而说明里若原样引用那两个符号就会踩这一条。

**出处**：`AGENTS.md` §5.1 前三条。

### 1.4 返回成功但实际没成

三种机理，现象都是「日志一片绿、业务没落地」：

| # | 机理 | 排查第一查 |
|---|---|---|
| a | **boolean RPC 包装方法**内部 `catch` 全部异常后 `return false`，从不抛异常 | **先看调用点有没有接住 boolean**。NEVER 假定「没抛异常就是成功」 |
| b | **`@Transactional` 内发起 RPC**：行锁持有时长 = 对端响应时长，超过 Druid `remove-abandoned-timeout` 后连接被强杀，`commit` 抛 `connection closed`，**整个事务连「留证据」的 INSERT 一起丢** | 看**证据表有没有落库**。已发生事故中 `PAY_CALLBACK_LOG` 零条落库（每轮都被回滚） |
| c | **事务内提交异步通知**：回滚后对方已收到成功通知 | 看通知时机，MUST 走 `@TransactionalEventListener(phase = AFTER_COMMIT)` |

- **(a) 的活例子**只剩 `PaySignClient.updatePaySignDisplayAccount`（`@Deprecated` 兼容壳）。已发生：`syncDisplayAccountToPayDomain` 丢弃返回值，而支付域 UPDATE 影响 0 行时返回 FAIL，于是「该用户在支付域没有签约记录」被写成 `SIGN_SYNC_STATUS='SUCCESS'`，既不重试也不开工单。
- **(a) 的新规**：ADR-D45 起新写 RPC 包装方法 **MUST 返回 `RpcOutcome`**（`Ok` / `BizRejected` / `Unreachable` 穷尽 switch），NEVER 再返回 boolean。「业务拒绝」与「网络不可达」可区分后：前者一次即终态 + 开工单，后者才进补偿队列。
- **(c) 的陷阱**：`fallbackExecution = false` 在**不带事务的类上等于静默不执行**，编译与单测都发现不了。`face-pay-server` 整批服务类是**有意不带事务**的，在那里挂监听器会把通知直接丢掉；改成 `true` 更糟（等于无事务时立刻同步发 HTTP）。**挑改造点前 MUST 先 grep 目标类有没有 `@Transactional`。**

**出处**：`AGENTS.md` §5.2（按「返回 boolean 的 RPC 包装方法」「事务内 NEVER 发起 RPC」「事务内 NEVER 提交异步通知」三条分别查）。

### 1.5 性能类：全 JVM 虚拟线程停止调度

| 项 | 内容 |
|---|---|
| **典型现象** | 对端 17ms 就答完，本端 287 秒后才处理响应；多个线程在同一毫秒集体苏醒 |
| **机理** | `spring.threads.virtual.enabled=true` 是全服务默认。JDK 21 未落地 JEP 491，虚拟线程在 `synchronized` 内阻塞会 **pin 住载体线程**，而 ojdbc8 大量方法是 `synchronized` —— 一条 60s 慢 SQL 就是 60s 的 pin。载体线程池 `parallelism` 默认等于容器可见 CPU 数，**CPU limit 偏小时一两条慢 SQL 即可 pin 满** |
| **取证** | **MUST 用 `jcmd <pid> Thread.dump_to_file -format=json`** —— `jstack` 看不到虚拟线程。辅以 `-Djdk.tracePinnedThreads=full` 或 JFR 事件 `jdk.VirtualThreadPinned` |
| **判据** | 日志里的线程名是 `tomcat-handler-N`（虚拟线程）；平台线程会是 `http-nio-<port>-exec-N` |
| **出处** | `AGENTS.md` §5.2「虚拟线程 pin」条；缓解手段见 `docker/Dockerfile` 的 `JAVA_TOOL_OPTIONS` |

### 1.6 时间窗类判定整体失效（容器时区 ≠ 业务时区）

| 项 | 内容 |
|---|---|
| **典型现象** | 明明在窗内的业务被判定为「超窗」——例如同一张卡的 IF5A-01 对同站返回 `["006","020"]` 而不是 `["005"]`；或日志时间戳比墙钟早/晚整 8 小时 |
| **第一查** | **容器/JVM 时区**，`kubectl -n itp exec deploy/<d> -c <d> -- sh -c 'echo TZ=[$TZ]; cat /proc/1/environ \| tr "\0" "\n" \| grep ^TZ'` |
| **⚠️ 反例** | **容器内 `date` 不可信**：2026-09-23 实测同一容器里 `date` 显示 `CST`、而 `/etc/localtime` 的实体内容却是 UTC（`md5sum /etc/localtime` == `md5sum /usr/share/zoneinfo/Etc/UTC`），JVM 取的是后者。判断时区 **MUST 看 `/etc/localtime` 实体内容或 `TZ` 环境变量，NEVER 只看 `date`** |
| **判据（不依赖任何日志）** | 找一列「**无时区型 `TIMESTAMP`、由 Java `LocalDateTime.now()` 直写**」的字段，与**同一笔的设备上送时间**比对：差 8 小时即命中。本项目可用 `QRCODE_TXN_DETAIL.CREATE_TIME` vs `HANDLE_DATE_TIME`、`QRCODE_STATUS.UPDATE_TIME` vs `LAST_TXN_TIME` |
| **机理** | Deployment 用 **hostPath 把宿主节点的 `/etc/localtime` 挂进容器** ⇒ 容器时区**随 pod 调度到的节点而变**；而业务时间字段来自设备/BOM 的**本地时间**，代码用 `LocalDateTime.now()`（JVM 默认时区）与之相减，两侧时区一旦不一致，窗内判定就会整体翻向「超窗」 |
| **修法** | `kubectl -n itp set env deployment/<d> TZ=Asia/Shanghai`。`TZ` 优先级**高于 `/etc/localtime`**，因此不必动那条挂载，且与落点节点无关 |
| **已修复于** | 2026-09-23，`itp` 命名空间 23 个业务 deployment 全部注入 `TZ`；非业务模块（database / httpbin / victoria-logs / bookinfo 示例）未注入 |
| **⚠️ 会复发的口子** | `TZ` 只存在于**线上 Deployment**，仓库 `deploy/` 里没有 ⇒ **按仓库 manifest 重建 Deployment、或新增业务模块时，这个修复会丢/漏** |
| **连带影响** | `@Scheduled` / Quartz 的 cron 按 JVM 默认时区解释 —— 改时区会**同时改变定时式任务的触发时刻**（间隔式 `fixedDelay` / `0/5` 不受影响）。改前 MUST 先盘点 `@Scheduled` 的 cron 与 `SYS_JOB`（注意 `sys_job_status`：**`0`=正常、`1`=暂停**） |
| **出处** | `AGENTS.md` §7（部署与运行）。本条是**环境级陷阱、尚未上升为 §5 STRICT RULE** |

## §2 部署后「看起来起来了」实际没起来

这一节单独列，因为它最高频，且**每一步的成功信号都不可靠**。

| 信号 | 为什么不可靠 | 可靠替代 |
|---|---|---|
| `exit code 0` | **管道会吃掉 Maven 退出码**（`mvn ... \| tail` 时退出码是 `tail` 的 0） | 判成功找 `digest:` / `Pushed`；判失败找 `[ERROR]` / `BUILD FAILURE` |
| `rollout status` 成功 | 不等于应用起来了（同「Pod `2/2 Running` 但端口不监听」） | 探活：`curl -s -w '\nhttp=%{http_code}\n' http://172.20.211.23:<NodePort>/actuator/health` |
| 日志里搜 `Tomcat started` | `CustomLoggingConfiguration` 是在 `ApplicationEvent` 里才把 log4j2 重载到文件 appender 的，**可能根本不进文件日志** | 探活 200 即端口在监听、上下文起完了。**搜不到 NEVER 当成启动失败** |
| 单次探活 503 | `rollout status` 刚返成功时探活可能就是 503 | **间隔 30 秒复探**，并带 body 看是 envoy「无健康上游」还是 Boot 自己报 DOWN |
| image tag | pom `<version>` **不等于线上版本**（中间那些版本号可能只是「升过号」，镜像从没推） | `kubectl get deploy -n itp -o custom-columns='NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image'` |

**确认「跑着的 Pod 里到底是哪版代码」MUST 在容器内反查字节码，NEVER 只凭 tag**（ADR-D93）：

```
kubectl exec -n itp <pod> -c <容器> -- sh -c "cd /tmp && J=/home/javaapp/soft/jdk-21.0.1/bin; \
  \$J/jar xf /app.jar BOOT-INF/classes/<pkg>/<Class>.class && \
  \$J/javap -p -c BOOT-INF/classes/<pkg>/<Class>.class"
```

看 `ldc` 常量与 `invokevirtual` 方法名。jar 在 **`/app.jar`**（不在 `/home/javaapp/soft`，那里只有 JDK）。容器内**没有 `unzip` / `strings`**，但该 JDK 是完整的（`jar` / `javap` / `jcmd` 齐全）。用完 **MUST** `rm -rf /tmp/BOOT-INF`。

适用场景：tag 被同名覆盖过、不确定某次 push 成没成、pom 版本与 Deployment 不一致。

**出处**：`AGENTS.md` §7（按「推镜像的触发阶段」「rollout status」「确认跑着的 Pod 里是哪版代码」几条分别查）。
