# 敏感配置外置方案（qd-itp）

> 编写日期：2026-08-25
> 依据：对全部 21 个模块 `src/main/resources/application.properties|yml` 的实测扫描
> 本文档**不记录任何密钥明文**，仅记录配置键名与位置。修复过程中同样 **NEVER** 将密钥值写入文档、日志、对话或提交信息。

## 一、现状评估

### 1.1 三级分类

**A 级：明文硬编码，无环境变量占位（必须立即处理）**

| 配置键 | 位置 | 类型 |
|---|---|---|
| `pay.center.private-key`（`private-key`） | `collect-pay-server/src/main/resources/application.yml:25` | 支付中心商户 RSA 私钥 |
| 数据源 `password` | `collect-pay-server/src/main/resources/application.yml:10` | Oracle 口令 |
| `appserver.3des.key` | `key-server/src/main/resources/application.properties:24` | 3DES 密钥 |
| `acc.3des.key` | `key-server/src/main/resources/application.properties:25` | 3DES 密钥 |
| `security.privateKey` | `acc-security-server/src/main/resources/application.properties:25` | 加密机通信私钥 |
| `itp.signKey` | `acc-security-server/.../application.properties:31`、`account-server/.../application.properties:45`、`alipay-account-server/.../application.properties:33` | ITP 验签共享密钥（**三处同值**） |
| `other.sql.password` | `alipay-account-server/.../application.properties:10`、`alipay-pay-sign-server/.../application.properties:10` | Oracle 口令 |
| `spring.datasource.password`、`spring.datasource.druid.master.password` | `web-server/web-admin/.../application.properties:40,45` | Oracle 口令 |
| `spring.datasource.druid.statViewServlet.login-password` | `web-server/web-admin/.../application.properties:74` | Druid 监控台口令（弱口令） |
| `token.secret` | `web-server/web-admin/.../application.properties:83` | JWT 签名密钥（26 位连续字母，强度极低） |

**B 级：有环境变量占位，但默认值就是真实密钥（伪外置，同样泄漏）**

| 配置键 | 位置 | 环境变量 |
|---|---|---|
| `pay.sign.merchant-private-key` | `pay-sign-server/.../application.properties:51` | `PAY_SIGN_MERCHANT_PRIVATE_KEY` |
| `daily-ticket.pay.merchant-private-key` | `daily-ticket-server/.../application.properties:20` | `DAILY_TICKET_PAY_MERCHANT_PRIVATE_KEY` |
| `other.sql.password` | `daily-ticket-server:37`、`ticket-server:73`、`gate-txn-pay-server:15`、`para-server:15` | `DB_PASSWORD`（默认值为真实口令） |

**C 级：已正确外置，作为本方案的目标范式**

- `${DB_PASSWORD:}` / `${DB_USERNAME:}`：`account-server:13`、`blacklist-server:17`、`key-server:17`、`pay-sign-server:21`、`acc-es-server:13-14`
- `ftp.username=${FTP_USERNAME:}`、`ftp.password=${FTP_PASSWORD:}`：`acc-es-server:28-29`
- `acc.secure.sign-key=`（空）：`acc-secure-server:25`
- `pay.center.merchant-private-key=`（空）：`alipay-pay-sign-server:53`

### 1.2 必须知道的三个结论

1. **同一把商户私钥在三处重复**：`pay-sign-server:51`、`daily-ticket-server:20`、`collect-pay-server/application.yml:25` 的 Base64 内容完全一致。一处泄漏即三条资金链路同时沦陷，且轮换必须三处同步。
2. **`itp.signKey` 在三处重复**，是 ITP 入向验签的共享密钥（`AccountRequestVerifier`、`ItpRequestSignVerifier` 使用）。轮换需要与 APP 端、ACC 端协调，**不能单侧修改**。
3. **git 历史已包含全部明文**。仅改当前文件不构成修复 —— 只要历史可访问，密钥即视为已泄漏，**MUST 走轮换流程**。

## 二、目标方案

### 2.1 分层原则

| 配置类型 | 归属 | 载体 |
|---|---|---|
| 非敏感、跨环境一致（表名、路径前缀、超时、重试次数、票种常量） | 保留在 `application.properties` | 代码仓库 |
| 非敏感、随环境变化（`service.*.url`、`other.sql.host`、`ftp.ip`） | 环境变量占位，允许留本地默认 | ConfigMap |
| **敏感**（口令、私钥、signKey、3DES 密钥、token.secret） | 环境变量占位，**默认值必须为空** | **K8s Secret** |

### 2.2 统一写法

所有敏感项统一改为空默认占位：

```properties
# 正确
other.sql.password=${DB_PASSWORD:}
pay.sign.merchant-private-key=${PAY_SIGN_MERCHANT_PRIVATE_KEY:}
itp.signKey=${ITP_SIGN_KEY:}

# 错误：默认值即真值
other.sql.password=${DB_PASSWORD:<真实口令>}
pay.sign.merchant-private-key=${PAY_SIGN_MERCHANT_PRIVATE_KEY:<真实私钥>}
```

`collect-pay-server` 使用 yml，写法为：

```yaml
pay:
  center:
    private-key: ${PAY_CENTER_PRIVATE_KEY:}
```

### 2.3 启动即失败（fail-fast）

空默认值会让配置缺失时退化为"用空密钥跑起来"，比启动失败更危险。**MUST** 在各模块加启动校验，缺失关键密钥直接终止：

在各模块已有的配置类（如 `pay-sign-server` 的支付配置绑定类）上使用 Bean Validation，而非新建工具类：

```java
@Validated
@ConfigurationProperties(prefix = "pay.sign")
public class PaySignProperties {
    @NotBlank(message = "PAY_SIGN_MERCHANT_PRIVATE_KEY 未注入，拒绝启动")
    private String merchantPrivateKey;
    // ...
}
```

对于目前直接 `@Value` 读取的散点配置，最小改动方式是在启动类同包下加一个 `ApplicationRunner`，校验必需项非空后抛异常。**NEVER** 为此新建跨模块的通用校验工具类（违反 AGENTS.md 5.1）。

### 2.4 环境变量命名规范

统一 `大写下划线`，与配置键一一对应，避免同名冲突：

- 数据源：`DB_HOST` / `DB_NAME` / `DB_USERNAME` / `DB_PASSWORD`
- ITP 验签：`ITP_SIGN_KEY`
- 支付私钥：`PAY_SIGN_MERCHANT_PRIVATE_KEY`、`DAILY_TICKET_PAY_MERCHANT_PRIVATE_KEY`、`PAY_CENTER_PRIVATE_KEY`
- 密钥服务：`APPSERVER_3DES_KEY`、`ACC_3DES_KEY`
- 加密机：`SECURITY_PRIVATE_KEY`
- FTP：`FTP_IP` / `FTP_USERNAME` / `FTP_PASSWORD`
- 后台：`WEB_TOKEN_SECRET`、`DRUID_CONSOLE_PASSWORD`

⚠️ 三处共用的 `itp.signKey` 与三处共用的商户私钥，**MUST 使用同一个环境变量名**，由同一个 Secret key 注入，避免轮换时漏改。

## 三、注入方式（对齐现有部署链路）

现状：`docker/Dockerfile`（`FROM .../jdk:21` + `COPY app.jar`）+ 各模块 `kubernetes-maven-plugin`（JKube）+ `scripts/deploy-to-harbor.sh`。因此注入点在 K8s 侧，无需改 Dockerfile。

### 3.1 生产 / 预发：K8s Secret

按"域"拆分 Secret，减小爆炸半径，避免一个 Secret 被所有 Pod 挂载：

- `itp-db-secret`：`DB_USERNAME`、`DB_PASSWORD`
- `itp-pay-secret`：`PAY_SIGN_MERCHANT_PRIVATE_KEY`、`DAILY_TICKET_PAY_MERCHANT_PRIVATE_KEY`、`PAY_CENTER_PRIVATE_KEY`
- `itp-crypto-secret`：`ITP_SIGN_KEY`、`APPSERVER_3DES_KEY`、`ACC_3DES_KEY`、`SECURITY_PRIVATE_KEY`
- `itp-infra-secret`：`FTP_USERNAME`、`FTP_PASSWORD`
- `itp-web-secret`：`WEB_TOKEN_SECRET`、`DRUID_CONSOLE_PASSWORD`

挂载原则：**每个模块只挂它实际需要的 Secret**。例如 `industry-data-server`、`fep-dev-server`、`fep-alipay-server` 无数据库，不挂 `itp-db-secret`。

JKube 侧在模块 `src/main/jkube/deployment.yml` 片段中声明 `envFrom`，由插件合并进生成的 Deployment：

```yaml
spec:
  template:
    spec:
      containers:
        - name: ${project.artifactId}
          envFrom:
            - secretRef:
                name: itp-db-secret
            - secretRef:
                name: itp-pay-secret
```

Secret 创建 **MUST** 由运维在集群内执行，**NEVER** 把 Secret yaml（含 base64 值）提交到仓库。

### 3.2 本地开发

- 优先用 IDE 的 Run Configuration 环境变量，或 `mvn spring-boot:run` 前 `export`。
- 需要文件方式时，新增 `application-local.properties`（`spring.profiles.active=local`）并加入 `.gitignore`。
- 仓库根目录目前**没有 `.gitignore`**（只有 `web/.gitignore`），本方案落地时 **MUST** 先补根 `.gitignore`，至少包含：

```gitignore
application-local.properties
application-local.yml
*.p12
*.jks
*.pem
.env
.env.local
```

### 3.3 提供 `.env.example` 模板

在仓库根目录新增 `.env.example`，只写键名与说明、**不写值**，作为新人与 CI 的契约清单：

```
# Oracle
DB_HOST=
DB_NAME=
DB_USERNAME=
DB_PASSWORD=
# 支付商户私钥（三处共用同一把，轮换需同步）
PAY_SIGN_MERCHANT_PRIVATE_KEY=
...
```

## 四、轮换与善后（不可跳过）

明文已进入 git 历史，改配置只是止血，不是修复。

1. **轮换商户私钥**：与支付中心（bestonepay）/ 银商网关重新申请密钥对并报备公钥。三个模块必须同批切换，切换窗口内 **MUST** 提前与用户确认是否需要停止扣款业务。
2. **轮换 `itp.signKey`**：需与 APP 端、ACC 端协商双跑窗口（旧密钥兼容期），**NEVER** 单侧直接替换，否则全部 APP 入向请求验签失败。
3. **轮换 3DES 密钥与加密机私钥**：涉及 `key-server` 的密钥派生和 HSM 通信，**MUST 由密码/安全负责人执行并人工复核**，AI 不得自行改动派生逻辑。
4. **轮换数据库口令、Druid 监控口令、`token.secret`**：`token.secret` 更换后所有已签发 JWT 失效，需在低峰期执行；Druid 监控台建议直接关闭外网暴露而非只改口令。
5. **历史清理**：评估是否需要 `git filter-repo` 重写历史。这是不可逆且影响所有协作者的操作，**MUST 由用户决策**，本方案不擅自执行。若不重写，则必须假定旧密钥永久泄漏，轮换是唯一出路。

## 六、落地步骤与验收

**执行顺序（建议一次一模块，便于回滚）**

1. 补根 `.gitignore` 与 `.env.example`（不含值）。
2. 运维创建五个 Secret，并向各模块 Deployment 补 `envFrom`。
3. 按 A 级 → B 级顺序，逐模块把敏感项改为 `${VAR:}`。
4. 为每个改动模块加 fail-fast 校验。
5. 逐模块验证：`mvn clean package -pl <module> -am -DskipTests` 通过，且**不注入环境变量时启动必须失败**（这是验收关键，不是缺陷）。
6. 注入环境变量后回归：签约、扣款、退款、乘车码生成、密钥同步各跑一条主链路。
7. 完成后执行轮换（第四章）。

**验收清单**

- [ ] 全仓 grep `password=`、`private-key`、`signKey`、`3des`、`token.secret`，无任何非空明文值
- [ ] 全仓 grep `${`，确认所有敏感项默认值为空
- [ ] 不注入环境变量时，每个模块启动均失败并给出明确提示
- [ ] 根 `.gitignore` 已覆盖本地配置与证书文件
- [ ] `.env.example` 键名与代码中占位一一对应，且不含任何值
- [ ] 轮换记录已归档（谁、何时、轮换了哪些密钥、旧密钥失效时间）

## 七、后续开发约束（已同步至 AGENTS.md 5.2 安全红线）

- 新增配置项时，**MUST** 先判断是否敏感；敏感项 **MUST** 走 `${VAR:}` + Secret，**NEVER** 写默认真值。
- **NEVER** 在对话、日志、提交信息、文档中回显密钥值；引用时只写键名与位置。
- 涉及加密、签名、密钥派生的代码 **NEVER** 擅自修改，**MUST** 提示人工复核安全合规性。
