## 7. Build & Run (构建与运行)
- **本项目的版本控制是 SVN，不是 git**（用户 2026-09-14 明确指出）。工作副本根就是仓库根
  `/Users/tuanjie/workspace/company/chinasofti/qd/qditp`，URL `svn://130.251.101.176/qditp`。
  **取历史版本 / 做基线对比 MUST 用 `svn cat -r BASE <path>`、`svn diff`、`svn log`、`svn ls`**。
  **陷阱：`qditp/` 的上一层 `qd/` 里另有一个旁挂 git 仓库**（最近提交停在 2026-09-10），
  在 `qditp/` 下敲 `git status` / `git show` **不会报错**，而是静默返回那个陈旧快照的内容 ——
  于是「拿到了看起来合理的旧版本」，实际与项目历史无关。**已二次踩中**：
  ADR-D53 续（`docs/domain/decisions.md`）第一次记录「git HEAD 是 1774 行的陈旧快照，
  排查历史版本 MUST 以 SVN 为准」；ADR-D61 又用 `git show :<path>` 取到一个 272 行的假基线，
  据此写下「拆分前版本从未提交、无法逐条 diff」的错误结论（已作废）。
  **因此：在本仓库内 NEVER 用任何 git 命令判断「改动前长什么样」「有没有提交」「是不是新增文件」。**
  判断某文件/目录是否已纳管用 `svn ls <dir>` 或 `svn status`（`?` 即未纳管），
  **NEVER 只对单个文件跑 `svn info`** —— 报 `W155010` 时分不清缺的是一个文件还是整棵树。
- **本机工具链由 mise 管理，Maven 命令 MUST 走 `mise exec -- mvn ...`**（用户 2026-09-07 明确要求）。mise 提供 Maven 3.8.7 + Oracle JDK 21.0.11（`~/.local/share/mise/installs/`），与项目要求的 JDK 21 一致；直接调 `mvn` 会落到系统 Maven 3.9.9，工具链不受控。
- 构建命令: `mise exec -- mvn clean package -DskipTests`
- 单模块构建: `mise exec -- mvn clean package -pl <module-name> -am -DskipTests`（仅限「只想本地编译过一遍」；**`model` / `rpc` 有改动又要出镜像部署时 NEVER 用这条，MUST 走本节末「先 install model/rpc 再构建部署」那条三步序列**）
- 运行测试: `mise exec -- mvn test` (注意：部分集成测试依赖 Oracle 数据库或加密机环境，若失败请提示用户)

  - **确认「跑着的 Pod 里到底是哪版代码」MUST 在容器内反查字节码，NEVER 只凭 image tag**（2026-09-16 实测确立，ADR-D93）：`kubectl exec -n itp <pod> -c <容器> -- sh -c "cd /tmp && J=/home/javaapp/soft/jdk-21.0.1/bin; \$J/jar xf /app.jar BOOT-INF/classes/<pkg>/<Class>.class && \$J/javap -p -c BOOT-INF/classes/<pkg>/<Class>.class"`，看 `ldc` 常量与 `invokevirtual` 方法名。jar 在 **`/app.jar`**（不在 `/home/javaapp/soft`，那里只有 JDK），容器内**没有 `unzip` / `strings`**、但 `/home/javaapp/soft/jdk-21.0.1/bin` 是完整 JDK（`jar` / `javap` / `jcmd` 齐全）；用完 **MUST** `rm -rf /tmp/BOOT-INF`。「tag 被同名覆盖过」「不确定某次 push 成没成」「pom 版本与 Deployment 不一致」三种场景下这是唯一硬证据。

- **`model` / `rpc` 有改动时，MUST 先 `install` 这两个模块、再构建业务模块并部署，顺序 NEVER 颠倒、NEVER 合成一条 `-pl` 里跑**（2026-09-18 确立）。机理：业务模块用 `-pl <模块>`（**不带 `-am`**）构建时，Maven 从 `~/.m2` 取 `model` 2.0.0 / `rpc` 2.0.1 的 jar —— 版本号恒定（见上一条），**没先 install 就会拿到旧 jar**。后果分两档且都难定位：轻则编译期报「找不到符号 / 找不到方法」，被误判成代码写错；重则**编译通过而打进镜像的是旧 class**（新增字段的 DTO 正是这一档，被 Fastjson2 静默丢字段，见下一条）。标准三步序列：
  ```
  mise exec -- mvn -o clean install -pl model,rpc -DskipTests -Djkube.skip=true
  mise exec -- mvn -o clean package -pl <业务模块1>,<业务模块2> -DskipTests   # 这一步会 build+push 镜像
  ssh k8s-master "kubectl set image deploy/<名> <容器名>=<镜像>:<tag> -n itp"   # 逐个滚更
  ```
  第一步 **MUST 带 `-Djkube.skip=true`**（`model` / `rpc` 本身没有镜像，但要拦住聚合构建里的 jkube）；第二步 **NEVER 加 `-am`** —— 加了会把 `model` / `rpc` 拉进同一个 reactor 重复构建，掩盖「到底 install 过没有」这个事实。**判断「第一步真的跑成功了」MUST 在输出里找 `model` 与 `rpc` 各自的 `BUILD SUCCESS` / `Installing ... .jar`，NEVER 只看整体退出码**（管道吃退出码那条同样适用）。**还 MUST 回头确认「谁该重建」**：`model` 的 DTO 改动 ⇒ 链路上每一个经手该 DTO 的模块（下一条）；`rpc` 的 Client / `RpcOutcome` 改动 ⇒ 全部调用方模块（下下条）。
- **给 `model` 的 DTO 加字段后，MUST 重建链路上每一个经手该 DTO 的模块镜像，NEVER 只重建终点服务**。`model` 版本号恒为 2.0.0（见上一条），旧镜像里打进去的是**旧 DTO 的 class**，`mvn install` 只更新本机 `~/.m2`、对已在跑的 Pod 毫无影响。而 Fastjson2 宽松模式**静默丢弃目标 DTO 里不存在的字段、不报错不告警**，于是 APP 明明上送了新字段，接入层用旧 class 一反序列化就没了，再转发给下游时字段也不存在——下游即便已是新 class，收到的也是 `null`。已发生（2026-09-10）：IF8A-41 给 `RequestTransStatisticsReqDTO` 加 `cardType`，只重建了 `itp/ticket-server:2.1.51`，端到端打 fep-app 时 ticket-server 日志里 `cardType='null'`，一度误判成代码没生效；重建并部署 `itp/fep-app:2.0.77` 后立即正常。**排查「加了字段但收不到」MUST 先确认接入层镜像是否也重建过**，判据是「链路上有几个模块的 `parseBizData` / RPC 序列化会经过这个 DTO」，APP 类接口至少是 `fep-app-server` + 目标业务服务两个。
- **改了 `resource/micro/*` 或 `model` / `rpc` 后，`mvn install` 只更新本机 `~/.m2`，对已在跑的 Pod 零影响 —— MUST 逐个重建受影响模块的镜像**。与上一条同一个机理（公共构件版本号恒定 + 旧 class 已打进旧镜像），但**上一条只影响报文字段、这一条能影响行为语义**。活样例：ADR-D53 修 `resource/micro/web` 的两个观测切面（把「异常包一层」改回原样抛出）后，**只重建并滚更了 `card-pool-server:1.0.17`**，因此**其余 6 个 tracing 模块的线上镜像里仍是旧切面、它们的幂等兜底 catch 在线上依然失效**。**判据：改动落在公共构件里时，「谁受影响」= 依赖它且真正走到那段代码的全部模块**（切面这种按开关生效的，就是 §2.2.1 那份 tracing 名单里的 7 个）。**NEVER 认为「`mvn install` 过了 / Deployment env 改过了」就等于生效** —— 只有重建镜像 + `kubectl set image` 才算。

#### MCP 数据库工具（`mcp_database_qd`）的报错与参数名坑

**报 `McpToolException cannot be cast to java.util.Map/List` 有两个成因，NEVER 只按第一个查：**

- ②**语句本身抛了 `DataAccessException`，被同一个 cast 错误包住**
  （2026-09-11 实测：违反唯一索引的 INSERT 报的是 `DuplicateKeyException cannot be cast to java.util.Map`）。
  **因此报文里出现具体异常类名时，那就是真实的数据库错误，不要再去查连接。**
- 这不是服务端 bug（2026-09-08 定位，此前误记为 MCP bug）。

**读写分离与不可用能力**：

| 工具 | 参数名 |
|---|---|
| `executeQuery` / `executeDdl` | `sql` |

| `batchQuery` | `sqls` |

**SQL 解析器的四条限制（2026-09-14 / 09-17 实测）**：

- ③`executeDdl` / `validateDdl` 的解析器**拒绝函数索引**：带 `CASE` 的 `CREATE UNIQUE INDEX`
  一律 `McpSqlValidationException`（同批朴素索引与 `ALTER TABLE ... ADD` 都 `valid:true`，可确定是 `CASE` 本身）。
  裸 `CASE` / `DECODE(a||b,...)` / 嵌套 `DECODE` 也全拒（分别报 `<K_WHEN>` / `<OP_CONCAT>` / `<OPENING_BRACKET>`）；
  `BEGIN EXECUTE IMMEDIATE '...'; END;` 也被直接拒（`DDL statement not allowed: Block [VAL001]`）。
  **现在可行的是两步**：①`ALTER TABLE ... ADD (col ... GENERATED ALWAYS AS (CASE WHEN ...) VIRTUAL)`
  （校验器**接受 `ALTER TABLE` 里的 `CASE`**）；②对虚拟列建**朴素**唯一索引。
  两步都实测执行成功，见 ADR-D135。
  **NEVER 因为验证不过就去改索引形状** —— `UK_UIRI_ACTIVE_USER_CARDTYPE` 那个 `CASE` 承载多卡语义，
  改朴素两列会打挂同行票开户。
- ④`COUNT(<CLOB 列>)` 在 Oracle 非法、却报成同一个 cast 错误；
  数 CLOB 非空行 MUST 写 `COUNT(CASE WHEN col IS NOT NULL THEN 1 END)`。
- ⑥`FROM DUAL` 上并列多个标量子查询会整体失败，逐表 `COUNT(*)` 才稳。
- **`*-schema.sql` 只服务「新建库」，对已存在的库等于没写；新增列 / 索引 MUST 出独立 `*-migration.sql` 并当场执行 + 回查**。2026-09-14 一天内撞了三次同型缺陷，且**成因各不相同**：①`APP_TERMINATION_REQUEST.CHANNEL_SYNC_*` —— 有 `pay-sign-channel-sync-migration.sql`，但**脚本从未执行**；②`APP_USER_PAY_CHANNEL.PAY_ACCOUNT_ID`（ADR-D30）—— **连迁移脚本都没有**，改动只落在 `account-server-schema.sql` 里，于是连一个「待执行」的物证都没留下；③`UK_UIRI_ACTIVE_USER_CARDTYPE` —— 同 ②，索引只写进 schema 文件。三者的共同后果是**代码已经在用那个列 / 索引，库里却没有**，运行时 `ORA-00904` 或幂等保护完全失效，而编译、单测、`xmllint` 全都发现不了。因此 **MUST 两条同时满足**：**（a）** 每个新增列 / 索引都有自己的 `<module>/src/main/resources/sql/*-migration.sql`（命名照 `account-server-{card-type,companion-flag,hce-data,phone-sync,pay-account-id}-migration.sql`），**NEVER 只改 `*-schema.sql` 就算加完（b）** 同一次会话内在 `AFCITPDB` 执行，并用 `USER_TAB_COLS.CHAR_LENGTH` / `USER_INDEXES` + `USER_IND_EXPRESSIONS` 回查，**把回查结果写进对应 ADR**——ADR 只写了 DDL **不算完成**。建唯一索引前还 **MUST** 先按索引的**确切谓词**统计 `COUNT(*)` vs `COUNT(DISTINCT 键)`（`ORA-01452` 防线），有重复只能与业务定归属、**NEVER 删行**（卡号可能已发用户）。

- **`service.*.url` 有三类问题，排查调用不通 MUST 三类都查**：①**键值错配**；②**键缺失**（`fep-app-server` 缺 `service.collectPay.url`、`pay-sign-server` 缺 `service.gateTxnPay.url`，运行时落到 `rpc` 默认服务名 `*-service`，与集群实际 Service 名不一致、DNS 解析不到；**`ticket-server` 缺 `service.paySign.url` 已于 2026-09-11 补齐，NEVER 再列`fep-dev-server` 缺 `service.key.url` 已于 2026-09-14 补齐（ADR-D67），NEVER 再列** —— 这条是本类里**最难发现的形态**：该键在那个文件里**从来没出现过**，而 `KeySyncHandler` 一直在注 `KeyClient`，线上只靠 Deployment 一条 env 兜着，于是**仓库里连一个写错的键都没有**。因此排查一个模块的 `service.*.url` **MUST 先 grep 出本模块用了哪些 `*Client` / `@EnableRpcXxx`，再逐个回头对键**，**NEVER 只顺着 properties 逐行看**——顺着看永远发现不了「压根没写」的那种）；③**键存在但值指向自身 Pod**（`fep-app-server/application.properties` 是 `service.gateTxnPay.url=http://127.0.0.1:9106`，在 K8s 里等于打到自己，表现为响应退化成全局异常处理器的 UUID `retCode`，2026-09-08 实测）。
- **判断线上真实地址 MUST 查 Deployment env，NEVER 只看仓库 properties**：K8s Deployment 的 env 会覆盖 jar 内 `application.properties` 的同名键，因此「仓库里写错」不等于「线上是错的」，反之亦然。改 env 会触发滚动重启并立即生效，**不需要重新构建镜像**；已实测正确形态如 `http://gate-txn-pay-server-jomf4-svc.itp.svc:30019`。仓库配置与集群 env 不一致时改哪一边 **MUST** 先问用户（属改服务间路由）。
- **切设备 / APP 入向流量 MUST 改 `fep-app-vr` 这条 VirtualService，NEVER 改 K8s Service selector**（2026-09-15 实测确立，ADR-D85）。**操作步骤、现成命令与验证清单已收口到 `docs/ops/流量切换.md`，切之前 MUST 先读那份 Runbook，本条只留判据摘要。** 操作 **MUST 用 `kubectl patch --type=json` 且带 `test` op** 校验下标与原值（走 `ssh k8s-master`），改对应前缀那条 route 的 `destination.host` / `port.number`；交互式 `kubectl edit vs fep-app-vr -n itp` 也能改但没有校验、易改错位置；`rewrite.uri` 一般不动（`/itptvm/` 与 `/itpbom/` 两条的 rewrite 带前缀、不是 `/`）。**这是本项目唯一的入向路由开关**：公网 `58.56.166.170:48000` → 节点 `172.20.211.200`（= `k8s02-gateway-866a2`，集群的入向网关节点，不是业务节点）→ `itp-gateway`（ns `itp-gateway`，`image: auto` 的 istio 网关，svc ）→ ns `itp` 的 `fep-app-vr` → 各业务 Service。当前该 VS 里有 8 条前缀：`/fep-app/`、`/fep-dev/`、`/fep-acc/`、`/fep-alipay/`、`/itptvm/`、`/itpbom/`、`/itpagm/`、`/para-server/`。
  - **NEVER 用 `kubectl get vs -A` 的摘要表判断某个前缀归谁** —— 那张表只显示 name / gateways / hosts，**不显示 path**，据它得出的「没有 VirtualService 定义 `/itptvm`」是错的（2026-09-15 因此推出两版错方案）。查现行路由 **MUST** 读 envoy：`kubectl exec -n itp-gateway <itp-gateway-pod> -- curl -s '127.0.0.1:15000/config_dump?resource=dynamic_route_configs'`，或直接 `kubectl get vs fep-app-vr -n itp -o yaml`。
  - **为什么不能改 Service selector**：`collect-pay-c23ku-svc` 的 `targetPort` 是 **8080**（collect-pay 靠 Deployment env `server.port=8080` 顶掉 yml 里的 58101），而目标服务未必听同一个端口 —— 翻 selector 可能把全量流量打到无人监听的端口。**改 selector 还会连带打断所有「直连该 Service、不经网关」的内部调用方**（`recon-server` 的对账源、`gate-txn-pay` 的补款、`web-admin` 的 Quartz 任务都是这种），而改路由只影响入向流量、内部链路一行不动。
  - **APP 域不走这条 VS**：`fep-app` 收到请求后经 `rpc` 的 `service.*.url` 转发，要切 APP 侧目标得改 `fep-app` Deployment 的对应 env（如 `service.collectPay.url`，**键名带点、不是 `SERVICE_COLLECT_PAY_URL`**），会触发滚动重启。因此「切一个业务域的全部流量」通常是**网关路由 + fep-app env 两处**。
  - **改前 MUST 记下原值作为回滚命令**；`patch` 用 `--type=json` 时**建议带 `test` op 校验索引与原值**，避免数组下标漂移打错位置。切完 **MUST** 用「同一份报文分别打新旧服务、比对 retCode」做契约基线核对，并在目标服务日志里确认落点。

- **「代码有 mapper、生产库无表」是本项目的一类高频缺陷**：`acc-es-server` 13 张表全缺（已按 mapper 反推建表，长度待甲方复核）。新增或排查落库功能 **MUST** 先核对生产库实际表结构，**NEVER** 假定「仓库里有 DDL 就等于生产库已建表」；反过来 **NEVER** 仅凭一次「MCP 枚举不到」就断定缺表——`APP_TERMINATION_REQUEST` 曾据此被误记为缺失，2026-08-26 双路径核对确认表存在且解约链路已跑通。详见清单 §六。
- **外部网关地址 MUST 实测，不能只看仓库配置**：2026-08-26 实测支付中心网关路径必须带 `/v1`，不带时返回 `code=600 操作失败`（不是 404，容易被误判成业务原因）。`pay-sign-server` 原有 5 条路径缺 `/v1`，导致免密扣款自上线以来 `GATE_TXN_PAY` 零条 `SUCCESS`（已修复）。同时已把 `pay.sign.*-path` + `gateway-url` 拼接改成 7 条完整 URL（`pay.sign.*-url`），与 `service.*.url` 形态一致；**NEVER 退回拼接**——路径带版本号，拆两半后漏 `/v1` 不报 404、极难定位。改动或排查这组配置 **MUST** 先用只读接口 `/api/v1/contract/queryResult` 验证。**字段名同样 MUST 实测**：2026-09-15 实测退款查询 §3.2 只认 `merchantRefundNo`，按供方文档只送 `refundOrderNo` 时网关返 `code=9999「退款流水号或商户退款流水号必填」`，表现为**退款单永久空转、而端点每轮返 `0000`、调度日志一片绿**（既不报警也不自愈，已修：两个键都送）。因此外部网关的**任何**契约细节（路径、字段名、必填性）都 **MUST 有一次真实应答做证据，NEVER 只凭供方文档就认为对**，见 ADR-D92。
- **解约回调地址不由我方指定**：网关 §2.3 请求解约的 bizData 没有 `notifyUrl` 字段，回调只发往支付中心侧的商户配置地址。解约收口 **MUST** 以主动查 §2.4 `queryResult`（`status=UNSIGNED` 即已解约）为准，回调只作为快速路径，**NEVER** 设计成只等回调。
