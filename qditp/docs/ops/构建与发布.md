## 〇、四条发布路径总览

| 路径 | 产物链 | 目标环境 | 构建入口 | 上线入口 |
|---|---|---|---|---|
| 后端 → 测试（云管台链，**首选**，2026-11-02 起可用） | jar → x86 镜像（平台 buildx） | CloudOS 应用，ns `itp`，Harbor 项目 `itp` | `itp-ops.sh buildx --env test` | `cloudos deploy --env test`（§二·1「云管台链」） |
| 后端 → 测试（k8s 链，保留为兜底） | jar → x86 镜像（远端产出） | k8s ns `itp`，Harbor 项目 `itp` | 本机出 jar（§一） | `itp-ops.sh k8s deploy` + 手工滚更（§二·2「k8s 链」） |
| 后端 → 红岛生产 | jar → x86 镜像（平台 buildx） | CloudOS 应用，ns `itpb`，Harbor 项目 `itpb` | 本机出 jar（§一）+ Dockerfile | `itp-ops.sh buildx` 出镜像 + `cloudos deploy` 切镜像（§三，11 步） |
| 前端 `web/` | zip（**不打镜像**） | CloudOS 应用包（脚本默认红岛云管台） | `npm run build:zip` | `itp-ops.sh web release`（§四） |

**测试环境两条链的关系（2026-11-02 定）**：云管台链与红岛**同一套动作、同一份脚本**（只差 `--env test`），镜像 tag / 应用版本 / env 都在平台侧留痕，是首选；k8s 链（scp + `build-push.sh` + `kubectl set image`）保留为**平台不可达时的兜底**，不再新增功能。两条链产出的镜像都在同一个 Harbor 项目 `itp`，可互相接续。

- 辽阳东与红岛同为生产、部署方式相同，**未实测**，操作前 MUST 现查（`docs/ops/environments/辽阳东.md`）。
- 两条全局前置（任何路径动手前先确认）：**① 发布任务 MUST 显式确认目标是测试还是生产**（`AGENTS.md` §5「AI Workflow (AI 执行工作流)」前置判据）；**② 生产 MUST 二次确认 + 低峰 + 灰度 / 回滚预案**，NEVER 自动执行。

**为什么本机只出 jar**：本机连不上集群 docker 守护进程（`tcp://172.20.211.21:2375` 超时），且本机是 Apple Silicon——本地 buildx 模拟构建 x86 慢、单层与缓存产物动辄数 GB（`AGENTS.md` §5.C 明令 NEVER 本机 buildx）。**一切镜像由远端产出**：测试 = `k8s-master` 上的 `build-push.sh`（podman）；红岛 = 云平台 x86 构建节点 buildx。

## 一、本机构建（后端两条路径共用的前置）

### 1.1 工具链

- MUST `mise exec -- mvn ...`：Maven 3.8.7 / JDK 21 由 `qd/mise.toml` 钉死；裸 `mvn` 落 mise 全局 3.9.10、裸 `java` 落 25.0.1，均非项目版本。
- SVN 服务器不可达 ⇒ 源码提交换有公司网络的环境（本机构建不受影响）。

### 1.2 构建顺序（NEVER 颠倒）

① `resource/micro`（仅当改了自研持久层或 `micro` / `web` 公共构件；**不在根 pom 聚合列表**，需单独 `install`）→ ② `model` + `rpc`（有改动时 `mise exec -- mvn -o clean install -pl model,rpc -DskipTests`；**版本号恒定、NEVER 升**——被全部业务模块 pom 的 `<model.version>` / `<rpc.version>` 引用）→ ③ 目标模块。

判据：输出里找 `model` / `rpc` 各自的 `Installing ... .jar`（NEVER 只看整体退出码）。没先 install 就打包，会拿到 `~/.m2` 里的旧 class——编译通过但打进镜像的是旧代码，新增字段被 Fastjson2 静默丢弃。

### 1.3 验证改动 vs 出 jar（两条命令，别混用）

| 用途 | 命令 | 要点 |
|---|---|---|
| 验证可编译 | `mise exec -- mvn -o clean test-compile -pl <模块>` | 增量会被 target 缓存骗过，MUST `clean`；跑测试且依赖已改 model/rpc 时加 `-am`（新字段在旧 jar 里不可见，典型如 ticket-server） |
| 出 jar | `mise exec -- mvn -o -pl <模块> -am package -Dmaven.test.skip=true` | `-am` 把 model/rpc 一并重编进 jar——给 model 的 DTO 加字段后 MUST 重建链路上每一个经手该 DTO 的模块镜像；MUST `maven.test.skip` 而非 `skipTests`（后者仍跑 test-compile，删过 target 会报「主类找不到」假错）；默认只出 jar 不推镜像（jkube `remote` profile 已无 `activeByDefault`） |

共同红线：NEVER 无 `-pl` 全量跑（`employee-card-acc-simulator` 全量编译必假失败，缺 spring-web 依赖，既存缺陷）、NEVER 靠全量 `mvn compile` 判断改动可编译；`mvn clean` 会失败（`gate-txn-pay-server/target/docker/...` 删不掉）⇒ 手动 `rm -rf <模块>/target/classes` 且**只删目标模块**（连带删了 model/rpc 的 classes 会让 reactor 用半成品目录而不是 `~/.m2` 的 jar；误删后全量 `mvn -o compile` 约 9 秒补回）。

### 1.4 版本号规则（前端/后端统一，2026-11-02 裁定）

升级版本号算法（**真源 `itp-ops.sh version` 与 `docs/ops/environments/scripts/lib/version.sh`**，前端/后端同一套口径）：

- **本地构建只升末位 `+0.0.1`**（最后一分段 +1）；起始版本 MUST 取**线上实际**版本（K8s Deployment image tag / CloudOS 应用详情 `version`），**NEVER** 照仓库 pom / properties 或凭记忆——否则会出现本次 `web` 线上 `1.2.42` 而本地 `package.json` 已跳到 `1.2.44.2` 的口径漂移。
- **任一分段超过 99 则向高位进位**（该段归零、前一分段 +1，即"超过 99 则升 `0.1.0`"）：例 `1.2.99 → 1.3.0`、`1.99.99 → 2.0.0`。
- **CloudOS 中仅为调试而升级的包，版本固定哨兵 `0.0.0.1`**（不占用发布序列，便于事后清理）；前端用 `itp-ops.sh web release --debug`，或 `itp-ops.sh version debug`。

实操：

- 后端：目标模块 `pom.xml` 的 `<version>` 按上述算法 bump；**NEVER 同 tag 覆盖**（`rollout restart` 与同 tag `set image` 都不会重新拉取，节点已缓存该 tag 的镜像层）。
- 前端：`web/` 的 `package.json` version 按上述算法 bump；`itp-ops.sh web release --bump` 可自动从 CloudOS 已部署版本算下一版（无需手填）。
- `web-admin` 例外：tag 取聚合 pom `web-server/pom.xml` 的 `<project.version>`，只改那一处。
- 镜像名取模块 pom 的 **`<image.prefix>`**，≠ 模块目录名（`fep-app-server` 的镜像是 `itp/fep-app`），NEVER 用目录名拼。

## 二、后端 → 测试环境（k8s ns `itp`）

> 环境事实（NodePort / Service 随机后缀 / 探活地址）MUST 现查，见 `docs/ops/environments/测试环境.md`；跳板 `ssh k8s-master`，`kubectl` 只在远端可用。
>
> **发布方式定位（2026-11-03 确认）**：**§二·1 云管台链是测试环境首选发布方式**（与红岛同一套动作、平台侧留痕），§二·2 k8s 链只作云管台不可达时的兜底、不再新增功能。两条链镜像同在 Harbor 项目 `itp`，可互相接续；bump / 出 jar 共用 §一。

### 2.1 云管台链（首选，2026-11-02 起，与红岛同一套动作）

> 前置：`./itp-ops.sh --env test cloudos health` 结论「可以操作」。镜像 tag、应用版本、env 全量在云管台可查。

1. **bump 版本号 + 出 jar**（§1.4 / §1.3，与 k8s 链相同）。
2. **打镜像（平台 x86 节点 buildx）**：

   ```bash
   cd docs/ops/environments/scripts
   # ① 先只读确认 tag 未占用
   itp-ops.sh buildx <镜像名> <版本> --env test --check
   # ② 真构建（镜像名 MUST 现查 cloudos app 的 container_image，NEVER 拿模块目录名推断）
   itp-ops.sh buildx <镜像名> <版本> --env test \
        --jar "$PWD/../../../../<模块目录>/target/<模块目录>-<版本>.jar" \
        --dockerfile "$PWD/buildx.Dockerfile"
   ```

   - `--env test` 会自动取 Harbor 项目 `itp`、账号 `admin`、基础镜像 `itp/jdk:25`；红岛对应 `itpb` / `itpbadmin` / `itpb/jdk21:1.0.0`。两套基础镜像入口契约相同（`sh /startapp.sh`），故共享模板仍只有一份、**NEVER 写 ENTRYPOINT**（IT-031）。
   - 判据：轮询命中 `imgUrl` 且 `osAndArch=linux/amd64`，**NEVER 看 HTTP 200**。
3. **切镜像（预演 → 执行）**：

   ```bash
   ./itp-ops.sh --env test cloudos deploy <应用名> <tag>          # 预演：打印基线、body、回滚点
   ./itp-ops.sh --env test cloudos deploy <应用名> <tag> --yes    # 执行
   ```

   - 「当前镜像」取自**实例实跑**，不是平台 `metadata.container_image`（测试环境 27 个应用里 25 个记录落后，见 IT-034）；预演里出现「平台记录与实跑不一致」告警属正常，回滚点以**实跑 tag** 为准。
   - 应用版本默认取**目标 tag**（与红岛同口径）；要别的值用 `--app-version`。
4. **验证**：预演末行会打印 `cloudos svc` 提示；探活走 NodePort（`172.20.211.23:300xx`，现查 `cloudos svc <app>`），并核对实例容器镜像已换成目标 tag（deploy 收尾自动轮询 20×15s）。

### 2.2 k8s 链（兜底：云管台不可达时）

> 定位：**仅兜底**（scp + 远端 `build-push.sh` + 手工滚更，平台侧无留痕），2026-11-02 起不再新增功能；云管台恢复后回到 §二·1。

六步（1~3 步命令见 §一）：

1. **bump 版本号**（§1.4）。
2. **出 jar**（§1.3）。
3. **构建推送（自动化，不含滚更）**：

   ```
   cd docs/ops/environments/scripts
   ./itp-ops.sh k8s deploy <模块目录名> --yes     # 单/多服务，失败继续，末尾汇总
   ./itp-ops.sh k8s deploy-all --yes              # 有序全量，失败即断
   ```

   行为边界：取 `<模块>/target/` 最新可执行 jar（排除 original/sources/javadoc）→ scp 到 `k8s-master:/home/java` → 远端 `HARBOR_PROJECT=itp ./build-push.sh <服务> <版本>`（podman 构建推送）。**镜像 tag = jar 文件名里的版本号 = bump 后的 pom 版本**，第 4 步滚更用同一字符串。**命令跑完 ≠ 上线完成**——滚更与验证是第 4~6 步。
   - `ALL_SERVICES`（24 个，`domains/k8s.sh` 单一真源）是「可构建推送的模块全集」**不是生产部署清单**，NEVER 擅自对齐任何一边；`web-admin` 不在清单——bump 聚合 pom 后按本节步骤手工执行（出 jar → scp → `build-push.sh` → 滚更）。
   - **一次只传一个 jar**：远端 `build-push.sh` 会 `find ... ! -name 目标jar -delete` 删掉 `/home/java` 下其他 jar；两个服务分批。
   - 推送成功判据 = 输出有 **`digest:` 或 `Pushed`**（两种措辞：`Pushed itp/<name>:<tag>` 与 `Pushed os-harbor-svc...:443/itp/<name>:<tag>`，只按 `Pushed itp/` 过滤会漏后者），NEVER 只看退出码。
4. **滚更**：改前 MUST 先记下原 tag 作为回滚命令：

   ```
   ssh k8s-master "kubectl -n itp set image deployment/<d> <容器>=<镜像>:<新版本> && kubectl -n itp rollout status deployment/<d>"
   ```

   Deployment 名 / 容器名 ≠ 模块名（账户域两者都叫 `account`，不是 `account-server`）。
5. **验证三件（缺一不可）**：
   - `rollout status` 成功 + 新 Pod `1/1 Running`、重启次数 0。**`rollout status` 成功 ≠ 应用起来了**。
   - 探活：`curl -s -w '\nhttp=%{http_code}\n' http://172.20.211.23:<NodePort>/actuator/health`——MUST 从 k8s-master 用 `172.20.211.23:<NodePort>`，打 `<svc>.itp.svc` 一律 `http=000`（宿主节点不在 Pod 网络、无 CoreDNS）。刚滚完可能 503，**间隔约 40 秒复探，单次 503 NEVER 当部署失败**；有 DB 的服务 Oracle 亦须 UP。
   - **digest 比对**：Pod `containerStatuses[].imageID` 与刚推送的 digest 一致——「跑着的真是这一版」的硬证据（多容器时 `containers[0]` 与 `containerStatuses[0]` 索引可能错位，istio sidecar `proxyv2` 常混进来）。
6. **报告与回滚**：向用户报告新版本号、digest、一键回滚命令。回滚 = `set image` 指回原 tag（Harbor 旧 tag 未删）。**若已发生同 tag 覆盖**，MUST digest 强制替换 `kubectl -n itp set image deployment/<d> <容器>=<镜像仓>@sha256:<digest>`（digest 引用必触发重拉；代价是 Harbor 上没有旧镜像可快速回滚、只能重构建旧代码——正是 MUST 升版本号的原因）。

### 2.3 冒烟与排障注意（两条链通用）

- 外部直连 NodePort / Pod 会被 **istio mTLS 拒绝**，不是服务挂了。
- **Pod 内没有 curl**，用 `/dev/tcp`：`kubectl -n itp exec <pod> -- bash -c 'exec 3<>/dev/tcp/127.0.0.1:<容器端口>; printf "GET /actuator/health HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n" >&3; cat <&3'`。容器端口 ≠ Service `port` ≠ `server.port`（`gate-txn-pay` 容器端口 9106 非 8080；`pay-sign-server-hsa9w-svc` 是 8080 非 9096）。
- 「确认 Pod 里到底是哪版代码」的终极手段：容器内 `javap` 反查字节码——jar 在 `/app.jar`，容器无 unzip / strings，用镜像自带完整 JDK（红岛 jdk21 镜像在 `/home/javaapp/soft/jdk-21.0.1/bin`；测试环境现查），**用完 MUST `rm -rf /tmp/BOOT-INF`**。
- 日志：`./itp-ops.sh log tail <服务> -f`（只看尾部窗口，Pod 一重启日志即丢）；全量检索 `ssh k8s-master` 后逐 Pod grep 容器内日志文件。
- 改端口的唯一正确姿势：只改 `targetPort`，**NEVER** 改 `port` / Service selector（`docs/ops/流量切换Runbook.md`）。

## 三、后端 → 红岛生产（CloudOS ns `itpb`）

> **生产红线（缺一不可）**：二次确认 + 低峰 + 灰度 / 回滚预案（单副本模块按服务逐个滚更，不做金丝雀分流）；命令统一 `--env hongdao`，脚本写命令缺 `--yes` 一律拒绝。环境事实见 `docs/ops/environments/红岛.md`；CloudOS 认证与平台坑见 `docs/ops/environments/scripts/README.md` §三「CloudOS 知识沉淀」。

标准流程（2026-10-29 按「发布一个红岛应用」的真实动作序列重排，登录是第 1 步；每一步标了命令落点与是否已脚本化）：

1. **登录 CloudOS**：`POST /api/sys/oapi/v1/double_factor/login`，body `{username, rsa:true, password:<RSA-1024 密文>, domain:"default"}` → 后续请求头 `X-Auth-Token`。脚本侧一句 `./itp-ops.sh --env hongdao cloudos health` 即「登录 + 缓存 token + 连通性自检」（网卡 `en9` active、TCP 443、登录、业务四测；红岛 USB 网卡一掉线，所有请求都以 502/超时形式失败，看着像平台故障，实际是本机链路断了）。✅ `lib/cloudos-auth.sh`
   - **JDK 兼容前置**：红岛公共基础镜像实测 `itpb/jdk21:1.0.0`（Harbor `itpb` 项目唯一的 JDK 镜像，现查），模块 `<java.version>` 高于它 MUST 先降级并跑全量测试（先例：route-sentinel 1.0.0 → 1.0.1，Java 25 → 21，22 个测试全过）。
2. **现查发版对象**（定「谁、什么镜像名、回滚点」）：`GET /api/cloud/app-mgmt/v1.0/apps` → `metadata.container_image`（镜像名权威，`fep-app` ≠ 目录名）、`version`（平台自生成 `x.y.z.N`）、当前 `metadata.version_id` / `package_version_id` = 回滚点、`package_type`、副本数。✅ `cloudos apps` / `cloudos app <应用>`
3. **本机 bump + 出 jar**（§一；字节码架构无关，x86 由平台产出）：pom 末位 `+0.0.1`，产物 mtime / 内嵌版本号自证是本批。
4. **查目标 tag 未占用**：`itp-ops.sh buildx <镜像名> <版本> --check`。**镜像名 MUST 现查 `GET /apps` 的 `metadata.container_image`，NEVER 拿模块目录名推断**（`fep-app` ← `fep-app-server`、`web-admin` ← `web-server/web-admin`）。**响应形态注意**：`data.images[]` 是**每个 tag 一行**、`versions` 单值，判「tag 是否已存在」MUST 对所有行的 `versions` 按逗号切开求并集（循环里直接赋值会被最后一行覆盖，得出「全 free」的假结论——2026-10-28 实测踩过）。
5. **buildx 出镜像**（当前唯一实测可用 = 平台 x86 buildx，2026-10-26 实测；2026-10-28 已批量跑通 23 个服务）：
   - **入口脚本**：`itp-ops.sh buildx <镜像名> <版本> --jar <绝对路径> --dockerfile <共享模板绝对路径>`。
   - **Dockerfile 统一用共享模板** `docs/ops/environments/scripts/buildx.Dockerfile`（`FROM os-harbor-svc.default.svc.cloudos:443/itpb/jdk21:1.0.0` + `ENV JAVA_TOOL_OPTIONS` + `COPY app.jar /app.jar`，平台上传的文件名固定 `app.jar`，NEVER 写 `target/` 路径）。**NEVER 写 `ENTRYPOINT` / `CMD`**——基础镜像的运行期契约（`-Xmx5900m`、GC 日志、heapdump、`MaxDirectMemorySize`、`max_memory` 三件套 env）全在镜像自带的 `/startapp.sh` 里，自写 `ENTRYPOINT` 会整段旁路，实测堆退回 2 GiB（现例：`fep-dev-server` / `route-sentinel`，见 [IT-031](../tracking/IT-031-红岛镜像ENTRYPOINT绕过startapp致JVM日志契约失效.md)）。
   - 机制：本机 jar + Dockerfile 经 `POST /api/cloud/hcr/v1.0/images/file/upload`（**fileFlag = 客户端自生成 uuid，走请求头**）上传构建上下文 → `POST /api/cloud/hcr/v1.0/images/buildx`（`platform` 可指定 `linux/amd64`）由平台 x86 构建节点构建并推 Harbor `itpb`。端点 / body / fileFlag 语义详见 [IT-024](../tracking/IT-024-红岛流水线构建缺口.md) §1「背景 / 现象」（Web SPA JS 反解所得，**非平台官方文档**，平台升级后 MUST 重验，失效即回 Web 控制台「镜像构建」页手工构建）。
   - **脚本化缺口（MUST 知道）**：`./itp-ops.sh --env hongdao cloudos image plan <模块> <版本> --jar <绝对路径> --dockerfile <绝对路径>` 可作 dry-run（路径 MUST 绝对路径），但其 `image build` 走旧端点 `/images/build`，**红岛实测不可用**（404 / `img.5`）；`k8s` 域 **NEVER** 用于红岛（跳板 `hd-linux` 无 `/home/java`、无 docker 只有 podman）。flowLine 流水线现查 0 条，立项建成后入口改回流水线（IT-024 方案 A）。
6. **镜像三验**：`GET /api/cloud/hcr/v1.0/image/versions?name=<镜像名>&harborProjectName=itpb` 里目标 tag 那一行的 `osAndArch=linux/amd64`、`digest` 与构建日志一致、`imgStatus=unused`。**digest MUST 在这一步记下**，第 9 步拿它比对。
7. **应用切到新镜像**：`PATCH /api/cloud/app-mgmt/v1.0/apps/{uuid}/advanced-config`——**已脚本化**：

   ```
   ./itp-ops.sh --env hongdao cloudos deploy <应用> <裸tag|镜像名:tag|完整引用> [--app-version <v>]   # 只读预演
   ./itp-ops.sh --env hongdao cloudos deploy <应用> <裸tag> --yes                                    # 真发（生产写）
   ```

   脚本干的活：读 `GET /apps/{uuid}` 现状 → 校目标 tag 在 Harbor 真存在且 `linux/amd64`（不存在 / arch 不对即停，**不发写请求**）→ 拒同 tag 覆盖 → 拼 body（`version` 默认把当前值末段 +1，平台校验不能等于当前值；`container_name` / `service_name` / `strategy` 原样；**`env` 从现网全量原样回传**——平台是整份覆盖，漏一条 = 删一条）→ PATCH → 轮询实例容器切到新镜像且 ready。不带 `--yes` 就是预演，MUST 先跑一遍核对打印出来的 body 再执行。
   - **`version_id` 的真相（2026-10-29 反解 SPA + 现网实测，更正本文档旧说法）**：厂商文档把 `version_id` 标成必选，但控制台「升级」页对**镜像应用**（`package_type=image` 且 `metadata.container_image` 非空）走的分支**根本不带 `version_id`**——`enterprise-apps/static/js/apply/app/detail/upgrade.*.js` 的 `createParams()` 只发 `{version, strategy, container_name, container_image, env}`。`version_id` 只在「包类型应用」分支取 `selectedPackage.selectedVersion.uuid`，来源是**软件包仓库** `GET /cloud/deploy/v1.0/packages/version/<app.package_version_id>`；而镜像仓库 `GET /cloud/hcr/v1.0/image/versions` 每行**没有 `uuid` 字段**（实测，`data.uuid` 恒为空串）——所以「到 `images/versions` 里取 `uuid` 当 `version_id`」这条路径在红岛**不存在**，照旧文档执行必然取不到。脚本按更稳的一档走：**回传 `metadata.version_id` 现值**（两次生产实测过的 image 型 PATCH 都带它且成功；MUST 传现值，传镜像引用会撑爆 `pkg_version_id varchar(36)` → 500，见 [IT-020](../tracking/IT-020-JVM参数被平台回滚.md) §2 隐藏契约）。
   - 缺 `container_image` 必 500（文档未标必填）。**改 env 也 MUST 走这条**（`kubectl set env` / patch 会被平台数分钟内回收）。env 三条硬纪律：
     - `SERVICE_*_URL` MUST 显式注入 `http://<目标>-internal-svc.itpb.svc:8080`——不注入则保留测试默认值指向 ns `itp`，跨模块 RPC 全失败、入口接口只返 UUID `retCode`（见 [IT-016](../tracking/IT-016-红岛服务地址指向测试命名空间.md)）；
     - `VLOGS_URL` / `VLOGS_QUERY_URL` 指红岛 `http://victoria-be7vr-internal-svc.itpb.svc:9428`，NEVER 沿用测试值；
     - 新建应用 / 给应用追加访问方式走 Web 端 API（`docs/ops/environments/红岛.md`「云管台 Web 端」表）。
8. **env 与副本核对**：`./itp-ops.sh cloudos env <应用>` 一次打全（第 7 步是整份覆盖，MUST 复验没被覆盖坏）；副本 `web-admin` 恒 **1**（会话是进程内 `LocalCache`，2 副本 = 验证码失效 + 约 50% 接口 401；平台重部署可能重置成 2），`recon-server` / `face-pay-server` / `collect-pay-server` 定时任务无分布式锁 MUST 单副本（名单与判据见 `docs/ops/environments/跨环境共性.md`）。
9. **上线验证**：实例容器镜像的 digest 与第 6 步记下的推送 digest 前缀一致（`cloudos pods <应用>`）；探活注意红岛 **Service `port` = NodePort = `319xx`、`targetPort` 统一 8080**，Service 名带平台随机后缀、NEVER 照抄测试环境服务名（现查命令见 IT-016 §4.3）；日志查 VictoriaLogs 红岛址（CloudOS `logs` 接口恒空）。
   - **红岛 MUST 追加一条启动形态复验（[IT-031](../tracking/IT-031-红岛镜像ENTRYPOINT绕过startapp致JVM日志契约失效.md)）**：`kubectl -n itpb exec <pod> -- tr '\0' ' ' < /proc/1/cmdline` 打出的 MUST 是 `sh /startapp.sh`；若打出 `java -jar /app.jar`，说明该镜像自写了 `ENTRYPOINT`、第 5 步的约束被绕过，堆 / GC 日志 / heapdump 一并失效（实测堆退回 2 GiB）。随后核 `-XX:MaxHeapSize=6186598400`（= 5900 m）：`kubectl -n itpb exec <pod> -- /home/javaapp/soft/jdk-21.0.1/bin/jcmd <javaPid> VM.flags`。**已列入计划**：现网 `fep-dev-server:2.0.72`、`route-sentinel:1.0.1` 正是失效形态，这两个服务下次发版（改用共享模板出的 `:2.0.74` / `:1.0.3`）时 MUST 做本条复验——**动在跑应用 MUST 先经用户二次确认**。
10. **报告 + 回滚**：向用户报告新版本号、镜像 digest、一键回滚命令。回滚 = 同一命令指回旧 tag：`cloudos deploy <应用> <旧 tag> --app-version <旧 version> --yes`（Harbor 旧 tag 未删）；镜像删错 tag 用 `POST /api/cloud/hcr/v1.0/images/deleteOneImage`。未切流（`fep-app-vr` 5 条 exact 未指向红岛实际 Service）时无流量风险；**流量切换 NEVER 在发版流程里顺手做**，走 `docs/ops/流量切换Runbook.md`。
11. **回写**：新坑回填本文与 `docs/ops/environments/红岛.md`；新缺口先进 `docs/tracking/问题清单.md`（§5.0）。

## 四、前端 `web/` → CloudOS（应用包，不打镜像）
