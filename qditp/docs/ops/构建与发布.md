## 〇、三条发布路径总览

| 路径 | 产物链 | 目标环境 | 构建入口 | 上线入口 |
|---|---|---|---|---|
| 后端 → 测试 | jar → x86 镜像（远端产出） | k8s ns `itp`，Harbor 项目 `itp` | 本机出 jar（§一） | `itp-ops.sh k8s deploy` + 手工滚更（§二） |
| 后端 → 红岛生产 | jar → x86 镜像（平台 buildx） | CloudOS 应用，ns `itpb`，Harbor 项目 `itpb` | 本机出 jar（§一）+ Dockerfile | 平台 buildx + `advanced-config`（§三） |
| 前端 `web/` | zip（**不打镜像**） | CloudOS 应用包（脚本默认红岛云管台） | `npm run build:zip` | `web_frontend_release.py`（§四） |

- 辽阳东与红岛同为生产、部署方式相同，**未实测**，操作前 MUST 现查（`docs/ops/environments/辽阳东.md`）。
- 两条全局前置（任何路径动手前先确认）：**① 发布任务 MUST 显式确认目标是测试还是生产**（`AGENTS.md` §5「AI Workflow (AI 执行工作流)」前置判据）；**② 生产 MUST 二次确认 + 低峰 + 灰度 / 回滚预案**，NEVER 自动执行。

**为什么本机只出 jar**：本机连不上集群 docker 守护进程（`tcp://172.20.211.21:2375` 超时），且本机是 Apple Silicon——本地 buildx 模拟构建 x86 慢、单层与缓存产物动辄数 GB（`AGENTS.md` §5.C 明令 NEVER 本机 buildx）。**一切镜像由远端产出**：测试 = `k8s-master` 上的 `build-push.sh`（podman）；红岛 = 云平台 x86 构建节点 buildx。

## 一、本机构建（后端两条路径共用的前置）

### 1.1 工具链

- MUST `mise exec -- mvn ...`：Maven 3.8.7 / JDK 21 由 `qd/mise.toml` 钉死；裸 `mvn` 落 mise 全局 3.9.10、裸 `java` 落 25.0.1，均非项目版本。
- SVN 服务器不可达 ⇒ 源码提交换有公司网络的环境（本机构建不受影响）。

### 1.2 构建顺序（NEVER 颠倒）

① `resource/micro`（仅当改了自研持久层或 `micro` / `web` 公共构件；**不在根 pom 聚合列表**，需单独 `install`）→ ② `model` + `rpc`（有改动时 `mise exec -- mvn -o clean install -pl model,rpc -DskipTests`；**版本号恒定、NEVER 升**——被全部业务模块 pom 的 `<model.version>` / `<rpc.version>` 引用）→ ③ 目标模块。

判据：输出里找 `model` / `rpc` 各自的 `Installing ... .jar`（NEVER 只看整体退出码）。没先 install 就打包，会拿到 `~/.m2` 里的旧 class——编译通过但打进镜像的是旧代码，新增字段被 Fastjson2 静默丢弃。

### 1.3 验证改动 vs 出 jar（两条命令，别混用）

| 用途 | 命令 | 要点 |
|---|---|---|
| 验证可编译 | `mise exec -- mvn -o clean test-compile -pl <模块>` | 增量会被 target 缓存骗过，MUST `clean`；跑测试且依赖已改 model/rpc 时加 `-am`（新字段在旧 jar 里不可见，典型如 ticket-server） |
| 出 jar | `mise exec -- mvn -o -pl <模块> -am package -Dmaven.test.skip=true` | `-am` 把 model/rpc 一并重编进 jar——给 model 的 DTO 加字段后 MUST 重建链路上每一个经手该 DTO 的模块镜像；MUST `maven.test.skip` 而非 `skipTests`（后者仍跑 test-compile，删过 target 会报「主类找不到」假错）；默认只出 jar 不推镜像（jkube `remote` profile 已无 `activeByDefault`） |

共同红线：NEVER 无 `-pl` 全量跑（`employee-card-acc-simulator` 全量编译必假失败，缺 spring-web 依赖，既存缺陷）、NEVER 靠全量 `mvn compile` 判断改动可编译；`mvn clean` 会失败（`gate-txn-pay-server/target/docker/...` 删不掉）⇒ 手动 `rm -rf <模块>/target/classes` 且**只删目标模块**（连带删了 model/rpc 的 classes 会让 reactor 用半成品目录而不是 `~/.m2` 的 jar；误删后全量 `mvn -o compile` 约 9 秒补回）。

### 1.4 版本号规则

- 目标模块 `pom.xml` 的 `<version>` 末位 **+0.0.1**；**NEVER 同 tag 覆盖**——`rollout restart` 与同 tag `set image` 都不会重新拉取（节点已缓存该 tag 的镜像层）。
- `web-admin` 例外：tag 取聚合 pom `web-server/pom.xml` 的 `<project.version>`，只改那一处。
- 镜像名取模块 pom 的 **`<image.prefix>`**，≠ 模块目录名（`fep-app-server` 的镜像是 `itp/fep-app`），NEVER 用目录名拼。

## 二、后端 → 测试环境（k8s ns `itp`）

> 环境事实（NodePort / Service 随机后缀 / 探活地址）MUST 现查，见 `docs/ops/environments/测试环境.md`；跳板 `ssh k8s-master`，`kubectl` 只在远端可用。

标准六步（1~3 步命令见 §一）：

1. **bump 版本号**（§1.4）。
2. **出 jar**（§1.3）。
3. **构建推送（自动化，不含滚更）**：

   ```
   cd docs/ops/environments/scripts
   ./itp-ops.sh k8s deploy <模块目录名> --yes     # 单/多服务，失败继续，末尾汇总
   ./itp-ops.sh k8s deploy-all --yes              # 有序全量，失败即断
   ```

   行为边界：取 `<模块>/target/` 最新可执行 jar（排除 original/sources/javadoc）→ scp 到 `k8s-master:/home/java` → 远端 `HARBOR_PROJECT=itp ./build-push.sh <服务> <版本>`（podman 构建推送）。**镜像 tag = jar 文件名里的版本号 = bump 后的 pom 版本**，第 4 步滚更用同一字符串。**命令跑完 ≠ 上线完成**——滚更与验证是第 4~6 步。
   - `ALL_SERVICES`（24 个，`domains/k8s.sh` 单一真源）是「可构建推送的模块全集」**不是生产部署清单**，NEVER 擅自对齐任何一边；`web-admin` 不在清单——bump 聚合 pom 后按本节步骤手工执行（出 jar → scp → `build-push.sh` → 滚更）。
   - **一次只传一个 jar**：远端 `build-push.sh` 会 `find ... ! -name 目标jar -delete` 删掉 `/home/java` 下其他 jar；两个服务分批。
   - 推送成功判据 = 输出有 **`digest:` 或 `Pushed`**（两种措辞：`Pushed itp/<name>:<tag>` 与 `Pushed os-harbor-svc...:443/itp/<name>:<tag>`，只按 `Pushed itp/` 过滤会漏后者），NEVER 只看退出码。
4. **滚更**：改前 MUST 先记下原 tag 作为回滚命令：

   ```
   ssh k8s-master "kubectl -n itp set image deployment/<d> <容器>=<镜像>:<新版本> && kubectl -n itp rollout status deployment/<d>"
   ```

   Deployment 名 / 容器名 ≠ 模块名（账户域两者都叫 `account`，不是 `account-server`）。
5. **验证三件（缺一不可）**：
   - `rollout status` 成功 + 新 Pod `1/1 Running`、重启次数 0。**`rollout status` 成功 ≠ 应用起来了**。
   - 探活：`curl -s -w '\nhttp=%{http_code}\n' http://172.20.211.23:<NodePort>/actuator/health`——MUST 从 k8s-master 用 `172.20.211.23:<NodePort>`，打 `<svc>.itp.svc` 一律 `http=000`（宿主节点不在 Pod 网络、无 CoreDNS）。刚滚完可能 503，**间隔约 40 秒复探，单次 503 NEVER 当部署失败**；有 DB 的服务 Oracle 亦须 UP。
   - **digest 比对**：Pod `containerStatuses[].imageID` 与刚推送的 digest 一致——「跑着的真是这一版」的硬证据（多容器时 `containers[0]` 与 `containerStatuses[0]` 索引可能错位，istio sidecar `proxyv2` 常混进来）。
6. **报告与回滚**：向用户报告新版本号、digest、一键回滚命令。回滚 = `set image` 指回原 tag（Harbor 旧 tag 未删）。**若已发生同 tag 覆盖**，MUST digest 强制替换 `kubectl -n itp set image deployment/<d> <容器>=<镜像仓>@sha256:<digest>`（digest 引用必触发重拉；代价是 Harbor 上没有旧镜像可快速回滚、只能重构建旧代码——正是 MUST 升版本号的原因）。

冒烟与排障注意：

- 外部直连 NodePort / Pod 会被 **istio mTLS 拒绝**，不是服务挂了。
- **Pod 内没有 curl**，用 `/dev/tcp`：`kubectl -n itp exec <pod> -- bash -c 'exec 3<>/dev/tcp/127.0.0.1:<容器端口>; printf "GET /actuator/health HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n" >&3; cat <&3'`。容器端口 ≠ Service `port` ≠ `server.port`（`gate-txn-pay` 容器端口 9106 非 8080；`pay-sign-server-hsa9w-svc` 是 8080 非 9096）。
- 「确认 Pod 里到底是哪版代码」的终极手段：容器内 `javap` 反查字节码——jar 在 `/app.jar`，容器无 unzip / strings，用镜像自带完整 JDK（红岛 jdk21 镜像在 `/home/javaapp/soft/jdk-21.0.1/bin`；测试环境现查），**用完 MUST `rm -rf /tmp/BOOT-INF`**。
- 日志：`./itp-ops.sh log tail <服务> -f`（只看尾部窗口，Pod 一重启日志即丢）；全量检索 `ssh k8s-master` 后逐 Pod grep 容器内日志文件。
- 改端口的唯一正确姿势：只改 `targetPort`，**NEVER** 改 `port` / Service selector（`docs/ops/流量切换Runbook.md`）。

## 三、后端 → 红岛生产（CloudOS ns `itpb`）

> **生产红线（缺一不可）**：二次确认 + 低峰 + 灰度 / 回滚预案（单副本模块按服务逐个滚更，不做金丝雀分流）；命令统一 `--env hongdao`，脚本写命令缺 `--yes` 一律拒绝。环境事实见 `docs/ops/environments/红岛.md`；CloudOS 认证与平台坑见 `docs/ops/environments/scripts/README.md` §三「CloudOS 知识沉淀」。

标准流程：

1. **前置核对**：本机可达（USB 网卡 `en9` + `172.120.0.0/16` 网段路由；`./itp-ops.sh cloudos health` + `diag reach` 自检）；**JDK 兼容**——红岛公共基础镜像实测 `itpb/jdk21:1.0.0`（Harbor `itpb` 项目唯一的 JDK 镜像，现查），模块 `<java.version>` 高于它 MUST 先降级并跑全量测试（先例：route-sentinel 1.0.0 → 1.0.1，Java 25 → 21，22 个测试全过）。
2. **bump + 出 jar**（§一；字节码架构无关，x86 由平台产出）。
3. **Dockerfile**（模块根目录）：`FROM os-harbor-svc.default.svc.cloudos:443/itpb/jdk21:1.0.0` + `COPY app.jar /app.jar`（平台上传的文件名固定 `app.jar`，NEVER 写 `target/` 路径）+ 保留 `JAVA_TOOL_OPTIONS`。
4. **镜像构建（当前唯一实测可用 = 平台 x86 buildx，2026-10-26 实测）**：
   - 机制：本机 jar + Dockerfile 经 `POST /api/cloud/hcr/v1.0/images/file/upload`（**fileFlag = 客户端自生成 uuid，走请求头**）上传构建上下文 → `POST /api/cloud/hcr/v1.0/images/buildx`（`platform` 可指定 `linux/amd64`）由平台 x86 构建节点构建并推 Harbor `itpb`。端点 / body / fileFlag 语义详见 [IT-024](../tracking/IT-024-红岛流水线构建缺口.md) §1「背景 / 现象」（Web SPA JS 反解所得，**非平台官方文档**，平台升级后 MUST 重验，失效即回 Web 控制台「镜像构建」页手工构建）。
   - **脚本化缺口（MUST 知道）**：`./itp-ops.sh --env hongdao cloudos image plan <模块> <版本> --jar <绝对路径> --dockerfile <绝对路径>` 可作 dry-run（路径 MUST 绝对路径），但其 `image build` 走旧端点 `/images/build`，**红岛实测不可用**（404 / `img.5`）；`k8s` 域 **NEVER** 用于红岛（跳板 `hd-linux` 无 `/home/java`、无 docker 只有 podman）。flowLine 流水线现查 0 条，立项建成后入口改回流水线（IT-024 方案 A）。
   - 构建后核对：`GET /api/cloud/hcr/v1.0/image/versions?name=<模块>&harborProjectName=itpb` 的 `osAndArch=linux/amd64` + 记下 `digest`。
5. **应用上线 / 升级**：走 `PATCH /api/cloud/app-mgmt/v1.0/apps/{uuid}/advanced-config`——body 由 `GET /apps/{uuid}` 的 `metadata` 读现状后只改目标字段；`version_id` 取 hcr 包记录的短 uuid（`GET /images/versions` 的 `uuid` 字段，**传镜像引用会 500**，`pkg_version_id varchar(36)` 溢出）；缺 `container_image` 必 500（文档未标必填）。**改 env 也 MUST 走这条**（`kubectl set env` / patch 会被平台数分钟内回收）。env 三条硬纪律：
   - `SERVICE_*_URL` MUST 显式注入 `http://<目标>-internal-svc.itpb.svc:8080`——不注入则保留测试默认值指向 ns `itp`，跨模块 RPC 全失败、入口接口只返 UUID `retCode`（见 [IT-016](../tracking/IT-016-红岛服务地址指向测试命名空间.md)，`./itp-ops.sh cloudos env <应用>` 一次打全核对）；
   - `VLOGS_URL` / `VLOGS_QUERY_URL` 指红岛 `http://victoria-be7vr-internal-svc.itpb.svc:9428`，NEVER 沿用测试值；
   - 新建应用 / 给应用追加访问方式走 Web 端 API（`docs/ops/environments/红岛.md`「云管台 Web 端」表）。
6. **副本纪律**：`web-admin` 恒 **1** 副本（会话是进程内 `LocalCache`，2 副本 = 验证码失效 + 约 50% 接口 401；平台重部署可能重置成 2，上线核验 MUST 查 `kubectl get deploy web-admin -n itpb` 的 READY 是 `1/1`）；`recon-server` / `face-pay-server` / `collect-pay-server` 定时任务无分布式锁，MUST 单副本（名单与判据见 `docs/ops/environments/跨环境共性.md`）。
7. **验证**：Pod imageID digest 与推送 digest 前缀一致；探活注意红岛 **Service `port` = NodePort = `319xx`、`targetPort` 统一 8080**，Service 名带平台随机后缀、NEVER 照抄测试环境服务名（现查命令见 IT-016 §4.3）；日志查 VictoriaLogs 红岛址（CloudOS `logs` 接口恒空）。
8. **回滚**：应用侧 = `advanced-config` 的 `version_id` 指回上一版本（Harbor 旧 tag 未删）；镜像删错 tag 用 `POST /api/cloud/hcr/v1.0/images/deleteOneImage`。未切流（`fep-app-vr` 7 条 exact 未指向红岛实际 Service）时无流量风险；**流量切换 NEVER 在发版流程里顺手做**，走 `docs/ops/流量切换Runbook.md`。

## 四、前端 `web/` → CloudOS（应用包，不打镜像）

- **一条命令**：`python3 docs/ops/environments/scripts/web_frontend_release.py <版本> [--yes]`——缺省 dry-run（本地出 zip + 打印将发的请求，不碰生产）；`--yes` 真发（上传 + 升级 + 轮询到满员）。变体 `--skip-build`（复用已出 zip，**回滚常配**）/ `--skip-upgrade`（只上传）/ `--app` / `--pkg` / `--app-uuid`。
- **回滚**：重跑旧版本 `--yes --skip-build`（旧版本已在软件中心，自动跳过上传）。**回滚点 = 线上当前版本（脚本打印 `ROLLBACK_POINT`），MUST 现查，NEVER 照文档抄版本号**。
- **NEVER 套用后端那套**（jar / 镜像 / k8s 滚更）——前端走 CloudOS 应用包 + 应用升级（`advanced-config`），`pkgType=web` 不是 jar。
- 前提：本机直连云管台（USB 网卡 active；`./itp-ops.sh cloudos health` 自检）；脚本默认红岛云管台，测试环境用 `CLOUDOS_ENV=test` 覆盖（测试 RSA 公钥未抓到前不可脚本化，见 scripts/README.md §三「CloudOS 知识沉淀」）。
- 细节真源：UI 流程 / 坑位（包仓库「部署」≠ 升级、双版本字段、低峰执行）→ `docs/ops/web前端云平台发版流程.md`；脚本参数 → `docs/ops/environments/scripts/web-frontend-release.README.md`；本地出 zip 判据 → `docs/architecture/web-admin-development-workflow.md` §5「验收、打包与发版闭环」。

## 五、完成判据（所有路径通用，全部满足才算完成）

1. 版本号末位 +0.0.1、NEVER 同 tag 覆盖；
2. **digest 硬证据**：Pod `imageID` = 本次推送 digest（NEVER 只看 tag 名相同）；
3. 探活 `http=200` / `status=UP`（有 DB 的服务 Oracle 亦 UP）；
4. 单副本名单（`web-admin` / `recon-server` / `face-pay-server` / `collect-pay-server`）副本数核过为 1；
5. 已向用户报告：新版本号、digest、一键回滚命令；
6. 回写：新踩的坑按 §六分工回填对应文档；新缺口先在 `docs/tracking/问题清单.md` 登记（判据见 `AGENTS.md` §5.0「问题跟踪」）。
