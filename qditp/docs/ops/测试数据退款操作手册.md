# 测试数据退款操作手册

清退测试环境「已支付未退款」订单的标准流程。**2026-09-10 全量执行并逐笔核验通过**（140 笔 / 25.84 元），本文的入口、参数、判定条件均为实测结论，非推断。

> ⚠️ 退款是**真实资金流动且不可逆**。测试环境的服务对接的是**支付中心生产网关**（`dtcustomer.bestonepay.com`）与支付宝真实商户，「测试环境」不等于「沙箱」。执行前 **MUST** 与用户确认清退范围。

## 一、八条业务线的退款入口

服务地址取 `172.20.211.23` + NodePort（`kubectl get svc -n itp` 查；本机 `kubectl` 无集群凭据，**MUST** 走 `ssh k8s-master`）。

| 业务线 | 订单主表 | 端点 | 报文格式 |
|---|---|---|---|
| TVM 扫码购票 | `TBL_TVM_ORDER_PAY` | `POST :30024/itptvm/ci/tvm/requestRefund` | form-urlencoded |
| APP 扫码取票 | `TBL_TVM_APP_ORDER` | `POST :30024/ci/app/requestRefundTicket` | form-urlencoded |
| BOM 非现金 | `TBL_BOM_ORDER_PAY` | `POST :30024/itpbom/ci/bom/requestTicketRefund` | form-urlencoded |
| 免密扣款 | `PAY_TXN_DETAIL` | `POST :30016/ci/app/requestRefund` | application/json |
| 支付宝渠道 | `ALIPAY_PAY_LOG` | `POST :30022/api/payment/requestRefund` | application/json |
| **TVM 扫码充值** | `TBL_TVM_ORDER_TOPUP` | 同 TVM 购票端点（**按前置订单类型自动分派**） | form-urlencoded |
| **日票 / 计次票** | `DAILY_TICKET_ORDER` | `POST :30027/page/daily-ticket/refund/request`；重提交 `POST :30027/page/daily-ticket/refund/resubmit` | application/json |
| **当面付（face-pay）** | `F2F_ORDER` / `F2F_PAYMENT` / `F2F_REFUND` | `POST :30025/page/face-pay/orders/{orderNo}/refund` | application/json |

**日票线为什么补进本表（2026-09-15）**：这条线是 2026-09-14 第五轮才发现的（见 §七），当时只把细节写在那一节，**三张速查表都没补行**。结果就是「标题说八条、表里只有七行」，而历次复扫都是照着 §一 的表逐线跑的 —— 少一行等于这条线继续被漏掉，正是 §七 第五轮记录的那个原始失效（「日票线此前根本不在本手册里，所以历次复扫从来没覆盖过它」）。本次把它补进 §一 / §二 / §三 三张表，**NEVER 再只在正文补细节而不补表**。

**第八条线：当面付 face-pay（2026-09-15 纳入）。** 此前本手册不含该线，理由是「face-pay 不承载真实流量」；**ADR-D85 已把设备与 APP 流量切到 `face-pay-server`，那个前提作废，NEVER 回退成「face-pay 不用扫」**。模块 `face-pay-server`（当前线上 `itp/face-pay-server:1.0.32`，`<image.prefix>face-pay-server`），Service `face-pay-server-svc`，**NodePort 30025**（注意不是 collect-pay 的 30024，两者都自称 58101）。旧的 `collect-pay-server`（30024）已退居后台，只留对账源、补款内部端点与**旧表**退款入口 —— **两条线的表完全不同，NEVER 用 30024 的端点去退 `F2F_*` 的单，也 NEVER 反之**。

**充值线不是第六个端点**：`/itptvm/ci/tvm/requestRefund` 的分派依据是 `TBL_TVM_ORDER_PAY_PRE.TRANS_TYPE`（`TvmOrderPreServiceImpl.requestRefund:86`），`01`→购票、`02`→充值（`tvmTopupService.requestRefund`）、`03`→取票。因此**充值订单用与购票完全相同的报文即可**（`orderNo` + `refundAmt`），2026-09-14 实测通过。本文档此前称「充值线入口未确认」是错的，**NEVER 回退**。

form-urlencoded 三个入口的业务字段都放在 `bizData`（JSON 字符串），另带 `charset=UTF-8&format=JSON&signType=00`（`collect-pay-server` 无验签，`signType=00` 即可）。

### 必填参数

- TVM 购票：`{"orderNo":"...","refundAmt":"<分>"}`
- APP 取票：`{"orderNo":"..."}` — 金额由服务端取 `PAY_AMOUNT`，勿自行传
- BOM 非现金：`{"orderNo":"...","ticketLogicNum":"...","transAmount":"<分>","transType":"04","transDate":"YYYYMMDD","ticketRefundDate":"YYYYMMDD","TakeTicketNum":"1"}`
- 免密扣款：`{"orderNo":"...","refundAmount":<分,整数>,"refundReason":"..."}`
- 支付宝：`{"orderNo":"..."}` — **不要传 `refundAmount`**，让服务端按 `PAY_AMOUNT - REFUND_AMOUNT` 自算，历史上手工传值踩过元/分混用
- 日票 / 计次票：`{"orderNo":"0E..."}` —— `orderType` **由服务端固定为 `1`，前端传值不被信任**，不必传；金额不接受入参
- 当面付：`POST :30025/page/face-pay/orders/<orderNo>/refund`，body 全部可选、可直接传 `{}`；**金额不接受入参**，服务端取订单总额整单退（`FacePayOrderPageController.java:151`）。给了 `refundReason` 会入库，不给则落「运营人工退款」。⚠️ **该页面端点无鉴权**（类注释自陈），却能发真实退款。

金额单位统一是**分**。

## 二、待退判定条件（逐线不同，勿套用）

| 业务线 | 判定条件 |
|---|---|
| TVM 购票 | `STATUS='1' AND RSV2 IS NULL` |
| APP 取票 | `PAY_STATUS='1' AND NOT EXISTS (SELECT 1 FROM TBL_APP_ORDER_REFUND R WHERE R.PAY_ORDER_NO = ORDER_NO)` |
| BOM 非现金 | `STATUS='1' AND RSV2 IS NULL` |
| 免密扣款 | `PAY_STATUS='SUCCESS' AND REFUND_STATUS='NONE'` |
| 支付宝渠道 | `PAY_STATUS='SUCCESS' AND REFUND_STATUS='NONE'` 且 `ALIPAY_REFUND_LOG` 无**成功**记录 |
| TVM 扫码充值 | `STATUS='1' AND RSV2 IS NULL` |
| 日票 / 计次票 | `PAY_STATUS='PAID'` 且 `DAILY_TICKET_REFUND` 无 `REFUND_STATUS='REFUNDED'` 的行。**成功值是 `REFUNDED` 不是 `SUCCESS`**，照抄会把全部订单误判成「一次都没退成」 |
| 当面付 | `F2F_PAYMENT.PAY_STATUS='SUCCESS'` 的金额之和 > `F2F_REFUND` 中 `REFUND_STATUS='SUCCESS'` 的金额之和（按 `F2F_REFUND.ORIG_ORDER_NO` 关联）。**`MANUAL` 行 NEVER 计入已退**，见 §二末「MANUAL」段 |

⚠️ **上表只是快速筛，会漏单；判「账面是否还欠钱」MUST 用聚合口径**（主表金额 − SUM(退款表 `REFUND_STATUS='1'` 的金额)，见第七节第三轮）。上表三条基于「行存在 / 字段非空」的条件（APP 的 `NOT EXISTS`、TVM/BOM 的 `RSV2 IS NULL`）都会把**尝试过但失败的订单**排除在外，而那些单钱一分没退。2026-09-14 第四轮实测漏了 43 笔 / 106.12 元。

**APP 取票线的坑**：`AppOrderServiceImpl.doRefund`（`collect-pay-server/.../service/impl/AppOrderServiceImpl.java:520`）全程不碰 `TBL_TVM_APP_ORDER`，**不回填 `RSV2`**。用 `RSV2 IS NULL` 筛这条线会把已退订单全部算成待退——2026-09-10 实测 31 笔已支付里 28 笔早有退款记录，误用条件会对 23 笔重复退款。

**支付宝线的坑**：`ALIPAY_REFUND_LOG` 里「有记录」不等于「已退成功」。同一笔失败会反复重试落多行（实测 16 行只对应 4 个订单号，其中一单 5 行全 `FAIL`）。判定 **MUST** 看有没有 `REFUND_STATUS='SUCCESS'` 的行。

## 三、五条铁律

**1. 接口响应不可信，必须查退款记录表核验。**

`TvmOrderServiceImpl.requestRefund`（`:752`）无论退款成败都返回 `retCode 0000`；BOM 的 `requestTicketTRefund` 同理。逐笔核验用：

| 业务线 | 核验表 | 成功值 |
|---|---|---|
| TVM 购票 | `TBL_TVM_ORDER_REFUND.REFUND_STATUS` | `1`（`2`=失败） |
| APP 取票 | `TBL_APP_ORDER_REFUND.REFUND_STATUS` | `1`（`0`=退款中、`2`=失败） |
| BOM 非现金 | `TBL_BOM_ORDER_REFUND.REFUND_STATUS` | `1` |
| 免密扣款 | `PAY_REFUND_DETAIL.REFUND_STATUS` | `SUCCESS`（`RETRY`/`PROCESSING`=未终态） |
| 支付宝渠道 | `ALIPAY_REFUND_LOG.REFUND_STATUS` | `SUCCESS` |
| 日票 / 计次票 | `DAILY_TICKET_REFUND.REFUND_STATUS` | **`REFUNDED`**（`REFUNDING`=退款中、`WAIT_VERIFY`=等核销，两者都是未终态） |
| 当面付 | `F2F_REFUND.REFUND_STATUS` | `SUCCESS`（`INIT`/`PROCESSING`=未终态，`FAILED`=失败，**`MANUAL`=悬挂，见下**） |

### 当面付的 `MANUAL`：不是失败，是「本系统放弃判定」

`F2F_REFUND.REFUND_STATUS` 值域 `INIT`/`PROCESSING`/`SUCCESS`/`FAILED`/`MANUAL`（`f2f-schema.sql:228` 的 `CK_F2F_REFUND_STATUS`）。**`MANUAL` 的语义是「钱到底退没退未知」**，由 `F2fRefundService.giveUpToManual`（`F2fRefundService.java:280~298`）唯一写入，触发判据二者取先到：`RETRY_TIMES >= f2f.refund.maxQueryTimes`（默认 30）或 `REQUEST_TMS` 距今超过 `f2f.refund.giveUpAfterHours`（默认 24 小时）。

**写成 `MANUAL` 之后这条单就永久悬挂，NEVER 指望它自愈**：
- 回查任务 `F2fRefundReconcileJob` 只扫 `PENDING_STATUSES = [INIT, PROCESSING]`（`F2fRefundService.java:103`、`F2fRefundMapper.xml:140~143`），**不再碰 `MANUAL`**。
- `giveUpToManual` 只改状态，**不落工单、不发通知**（该模块没有异常工单表），唯一产出是一条 ERROR 日志。
- 运营页面重点一次也推不动：`F2fPageRefundService.refundWholeOrder` 先按 `SOURCE_PAGE_MANUAL` 查重（`F2fPageRefundService.java:88~91`、`:129~140`），命中即返回「该订单已发起退款」。其他来源（TVM / BOM / APP / TOPUP）的 `MANUAL` 单**根本没有任何 HTTP 入口**能推进。
- APP 侧 `queryRefundResult` 把 `MANUAL` 归到 `else`、对外恒回 `PROCESSING / 退款中`（`F2fAppOrderService.java:444~453`）。
- **唯一的复活入口是支付中心退款回调** `POST /ci/app/receiveRefundResult` —— 它的前置状态白名单里显式带了 `MANUAL`（`F2fAppOrderService.java:488~493`），但要求报文带 `refundNo`。

因此测试环境清理 `MANUAL` 单只有两条路：让支付中心补发一次带 `refundNo` 的回调，或手工核对支付中心侧真实结果后 UPDATE 该行（**MUST 先记原值与还原 SQL**）。**NEVER 直接重发退款** —— 钱可能已经退过了。

另注意 `giveUpToManual` 走的是 `updateStatus`、**不写 `FAIL_REASON`**，所以 `MANUAL` 行里留的是转人工前最后一次的失败原因，不是转人工的原因。

**2. 全部入口无幂等，禁止整批重跑。**

没有任何一条链路对同一 `orderNo` 做「已退则短路」，退款单号每次新生成。实测事故：`GT20260728095950844542741` 在 2026-07-28 16:39:42 与 16:40:06 各退 100 分，两笔都成功。中断后 **MUST** 先按第二节条件重查待退清单再续跑，**NEVER** 重放原列表。

**3. 逐笔调用 + 间隔 1~2 秒，不要并发。**

`PaymentRefundService.requestRefund`（`alipay-pay-sign-server`，`:46` + `:109`）带 `@Transactional` 且事务内调支付中心，违反 AGENTS.md「事务内不得发起网络调用」，密集并发会触发行锁堆积。

**4. 先试最小金额一笔，核验通过再批量。**

**5. 编写 shell 循环时用单行空格分隔的列表。**

2026-09-10 用多行变量 `for item in $LIST` 只执行了 1 次迭代就静默退出（exit code 仍是 0），靠查库才发现。发现后按第二节条件重查、改单行列表重跑，未产生重复退款。

## 四、TVM / APP / BOM 三线的其他实测结论

`refundReason` 传了会被忽略，服务端硬编码「出票数量不足」并以 `\u51FA\u7968...` 转义字面量入库（未做 unicode 解码）。

`RSV2` 被无条件回填：`doRefund` 返回 true 只表示「退款流程结束」，成败都算（`TvmOrderServiceImpl.java:742`）。因此退款失败的订单也会被打上 `RSV2` 而从待退清单消失，这个条件对失败重试不可靠。

BOM 的 `ticketLogicNum` **不参与退款**：`bomRefund`（`BomOrderServiceImpl.java:1589`）只用 `orderNo` + `transAmount`；该字段唯一用途是成功后回写 `TBL_BOM_SUB_TICKET.RSV2`。Controller 却强制校验非空（`BomOrderController.java:308`）。取值来源是 `TBL_BOM_ORDER_PAY.CARD_ID`；`CARD_ID` 为 null 时填 `0000000000000000`，实测 `TBL_BOM_SUB_TICKET` 无此卡号、`updateByTicketLogicNum` 命中 0 行纯空转，不会脏写（该表只有 6 列、**无 `ORDER_NO` 列**，本来也无法按订单反查真实卡号）。

BOM 的分派依据是 `TBL_TVM_ORDER_PAY_PRE.TRANS_TYPE`（`BomOrderServiceImpl.java:1481`），**不是**请求里的 `transType`、也不是 `TBL_BOM_ORDER_PAY.TRANS_TYPE`。取值 `04` = `BOM_SCANED_PAY` 才会走 `bomRefund`。

## 五、支付中心侧状态怎么查

`alipay-pay-sign-server` 只暴露了 `payQuery`，**没有暴露 `refundQuery`**（`PayCenterClient.refundQuery` 和 `pay.center.refund-query-url` 都在，但 `AlipayTripPaymentController` 没有对应端点）。查支付状态：

```
POST :30022/api/payment/payQuery   {"orderNo":"..."}
```

返回 `tradeStatus` / `totalAmount` / `tradeNo` / `tradeDesc`。

⚠️ **`payQuery` 不是只读操作**（本文此前称「可放心调」是错的，**NEVER 回退**）。2026-09-14 实测：`PaymentQueryService.payQuery` 拿到支付中心应答后**无条件回写本地** `ALIPAY_PAY_LOG`（`PAY_STATUS` / `RESULT_CODE` / `RESULT_MSG` / `TRADE_NO` / `TRANS_TIME`）。而这条链路用的是**另一个商户与另一个网关**（`ngopenplatform`，`merchantNo=UIQ2N4F0Q2`，且 `PayCenterClient.signRequest` 打印「测试阶段使用测试签名」、`sign` 固定为 `test`），`channelAgreementNo` 解析不出时支付中心返 `code=604 渠道协议号不能为空`——**这是请求被拒，不是订单状态结论**，却照样把 `PAY_STATUS` 改成 `FAIL`、`RESULT_CODE` 改成 `9999`。实测把 `GT20260814121142985542741` 的 `SUCCESS/INIT/支付处理中` 打成 `FAIL/9999/渠道协议号不能为空`，靠 `SELECT ... AS OF TIMESTAMP` 闪回取回原值后还原。**用它探测网关健康度前 MUST 想清楚会脏写哪一行**。

另注意：外层 `retCode=0000 查询成功` **只表示我方封装成功**，与支付中心的 `code` 无关。判断网关是否可用 **MUST** 看日志里 `支付中心响应, response=` 那一行的 `code`。

**判断「钱是否真的扣走」以支付中心的 `tradeStatus` 为准。** 实测 `GT20260724145837541541710` 本地与支付中心均为 `FAIL`（`tradeDesc=渠道协议号不能为空`，对应卡 `SIGN_STATUS=TERMINATED`），这类单不需要退款；而它在 `ALIPAY_REFUND_LOG` 里有两行 `{"code":200,"msg":"操作成功"}`——那只是**网关受理了报文**，不代表有资金退回，勿据此判定已退款。

支付中心常见拒绝措辞：`该订单已全部退款`（历史已退）、`该订单不能退款`（无实付，多为手工造的单）。这两种都属于「本来就不该退」，不是执行失败。

### 第三轮 10:13~10:24：补退「部分退款的剩余部分」

**前提是换了口径**：TVM / BOM / APP 三线主表**没有 `REFUND_AMOUNT` 列**，只查 `PAY_TXN_DETAIL` 与 `ALIPAY_PAY_LOG` 的金额列会得出「无部分退款残留」的错误结论（本文档作者当天犯过）。**判定部分退款 MUST 用「主表金额 − SUM(退款表 `REFUND_STATUS='1'` 的金额)」**：

- TVM：`TBL_TVM_ORDER_PAY.TOTAL_PRICE` − `TBL_TVM_ORDER_REFUND`
- BOM：`TBL_BOM_ORDER_PAY.TRANS_AOUNT`（**注意列名少个 M**）− `TBL_BOM_ORDER_REFUND`
- APP：`TBL_TVM_APP_ORDER.PAY_AMOUNT` − `TBL_APP_ORDER_REFUND`

三张退款表的 `REFUND_AMOUNT` 都是 `VARCHAR2` 且有脏值，聚合 **MUST** 带 `REGEXP_LIKE(REFUND_AMOUNT,'^[0-9]+$')`，否则 `TO_NUMBER` 抛 `ORA-01722`。

### 新增：日票线的退款重提交端点（daily-ticket-server 1.0.24）


**存在的原因**：`/retry` 是「先查再重发」，前提是支付平台已建过退款单、查得到结论；对端**从未受理**时 `refundQuery` 永远查不到东西，那条链路会一直卡在「支付平台退款单号缺失」，那笔退款能力永久丧失。本端点补的就是这个分支。

## 八、待修复的代码缺陷（历次执行暴露）

- 🔴 **face-pay 运营页面退款端点把「支付中心当场拒绝」也返成 `0000 成功`**（2026-09-15 实测 3 笔）。`POST :30025/page/face-pay/orders/{orderNo}/refund` 一律返 `{"code":"200","data":{"retCode":"0000","retMsg":"成功"}}`，而库里落的是 `REFUND_STATUS='INIT'` + `FAIL_REASON='错误的订单号'` / `'该订单不能退款'` + `PAY_CENTER_REFUND_NO IS NULL`。**因此 NEVER 拿 HTTP 应答判断退款结果，MUST 回查 `F2F_REFUND`**（这与 §五那条「外层 `retCode` 只表示我方封装成功」是同一类陷阱，但这里连「已受理」都不成立）。更糟的是被当场拒绝的单仍会落一行 `INIT`，随后被 `F2fRefundReconcileJob` 反复 `refundQuery`（对端压根没建单，必然查不出结论）直到 30 次 / 24 小时用尽转 `MANUAL` —— **等于每次「不该退」的尝试都会制造一条悬挂垃圾**。修的方向是把支付中心的**业务性拒绝**（`错误的订单号` / `该订单不能退款` / `该订单已全部退款`）与**网络不可达**区分开，前者一次即终态、NEVER 进重试队列（判据形态即 AGENTS.md §5.2 的 `RpcOutcome.BizRejected` vs `Unreachable`）。
