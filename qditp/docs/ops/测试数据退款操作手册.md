# 测试数据退款操作手册

清退测试环境「已支付未退款」订单的标准流程。

> ⚠️ 退款是**真实资金流动且不可逆**。测试环境的服务对接的是**支付中心生产网关**（`dtcustomer.bestonepay.com`）与支付宝真实商户，「测试环境」不等于「沙箱」。执行前 **MUST** 与用户确认清退范围。

## 一、八条业务线的退款入口

服务地址取 `172.20.211.23` + NodePort（`kubectl get svc -n itp` 查；本机 `kubectl` 无集群凭据，**MUST** 走 `ssh k8s-master`）。

| 业务线 | 订单主表 | 端点 | 报文格式 |
|---|---|---|---|
| TVM 扫码购票 | `TBL_TVM_ORDER_PAY` | `POST /itptvm/ci/tvm/requestRefund` | form-urlencoded |
| APP 扫码取票 | `TBL_TVM_APP_ORDER` | `POST /ci/app/requestRefundTicket` | form-urlencoded |
| BOM 非现金 | `TBL_BOM_ORDER_PAY` | `POST /itpbom/ci/bom/requestTicketRefund` | form-urlencoded |
| 免密扣款 | `PAY_TXN_DETAIL` | `POST /ci/app/requestRefund` | application/json |
| 支付宝渠道 | `ALIPAY_PAY_LOG` | `POST /api/payment/requestRefund` | application/json |
| **TVM 扫码充值** | `TBL_TVM_ORDER_TOPUP` | 同 TVM 购票端点（**按前置订单类型自动分派**） | form-urlencoded |
| **日票 / 计次票** | `DAILY_TICKET_ORDER` | `POST /page/daily-ticket/refund/request`；重提交 `POST /page/daily-ticket/refund/resubmit` | application/json |
| **当面付（face-pay）** | `F2F_ORDER` / `F2F_PAYMENT` / `F2F_REFUND` | `POST /page/face-pay/orders/{orderNo}/refund` | application/json |

**充值线分派依据**：`/itptvm/ci/tvm/requestRefund` 的分派依据是 `TBL_TVM_ORDER_PAY_PRE.TRANS_TYPE`（`01`→购票、`02`→充值、`03`→取票）。**充值订单用与购票完全相同的报文即可**（`orderNo` + `refundAmt`）。

form-urlencoded 三个入口的业务字段都放在 `bizData`（JSON 字符串），另带 `charset=UTF-8&format=JSON&signType=00`（`collect-pay-server` 无验签，`signType=00` 即可）。

### 必填参数

- TVM 购票：`{"orderNo":"...","refundAmt":"<分>"}`
- APP 取票：`{"orderNo":"..."}` — 金额由服务端取 `PAY_AMOUNT`，勿自行传
- BOM 非现金：`{"orderNo":"...","ticketLogicNum":"...","transAmount":"<分>","transType":"04","transDate":"YYYYMMDD","ticketRefundDate":"YYYYMMDD","TakeTicketNum":"1"}`
- 免密扣款：`{"orderNo":"...","refundAmount":<分,整数>,"refundReason":"..."}`
- 支付宝：`{"orderNo":"..."}` — **不要传 `refundAmount`**，让服务端按 `PAY_AMOUNT - REFUND_AMOUNT` 自算
- 日票 / 计次票：`{"orderNo":"0E..."}` — `orderType` **由服务端固定为 `1`，前端传值不被信任**，不必传；金额不接受入参
- 当面付：`POST /page/face-pay/orders/<orderNo>/refund`，body 全部可选、可直接传 `{}`；**金额不接受入参**，服务端取订单总额整单退。⚠️ **该端点无鉴权**，却能发真实退款。

**指定金额退款端点**（日票 / APP 部分退款残留场景）：

| 端点 | 说明 |
|---|---|
| `POST :30024/page/app/orders/{orderNo}/refund`，body `{"refundAmount": <分>}` | collect-pay-server，自带超退闸门（可退余额 = `PAY_AMOUNT` − SUM(成功退款)，超额直接拒），**无鉴权、不做幂等** |
| `POST :30027/page/daily-ticket/refund/resubmit`，body `{"orderNo":"0E..."}` | daily-ticket-server，**仅对支付平台从未受理的单**（`PLATFORM_REFUND_NO IS NULL`）重发，沿用原退款单号做外部幂等，**无鉴权** |

金额单位统一是**分**。

## 二、待退判定条件（逐线不同，勿套用）

| 业务线 | 判定条件 |
|---|---|
| TVM 购票 | `STATUS='1' AND RSV2 IS NULL` |
| APP 取票 | `PAY_STATUS='1' AND NOT EXISTS (SELECT 1 FROM TBL_APP_ORDER_REFUND R WHERE R.PAY_ORDER_NO = ORDER_NO)` |
| BOM 非现金 | `STATUS='1' AND RSV2 IS NULL` |
| 免密扣款 | `PAY_STATUS='SUCCESS' AND REFUND_STATUS='NONE'` |
| 支付宝渠道 | `PAY_STATUS='SUCCESS' AND REFUND_STATUS='NONE'` 且 `ALIPAY_REFUND_LOG` 无**成功**记录 |
| TVM 扫码充值 | `STATUS='1' AND RSV2 IS NULL` |
| 日票 / 计次票 | `PAY_STATUS='PAID'` 且 `DAILY_TICKET_REFUND` 无 `REFUND_STATUS='REFUNDED'` 的行 |
| 当面付 | `F2F_PAYMENT.PAY_STATUS='SUCCESS'` 金额之和 > `F2F_REFUND` 中 `REFUND_STATUS='SUCCESS'` 金额之和（按 `ORIG_ORDER_NO` 关联）；**`MANUAL` 行 NEVER 计入已退** |

**已知陷阱**（用上表快速筛前 MUST 先评估）：

- **TVM / BOM 的 `RSV2 IS NULL` 不可靠**：`doRefund` 返回 true 只表示「退款流程结束」，**失败也填 `RSV2`**。凡重试过但失败的订单会从待退清单消失，钱一分没退。
- **APP 的 `NOT EXISTS(TBL_APP_ORDER_REFUND)` 不可靠**：「有退款记录」不等于「退成功了」，失败行（`REFUND_STATUS='2'`）也会让该行「存在」。
- **日票线成功值是 `REFUNDED`，不是 `SUCCESS`**。照抄会把全部订单误判成「一次都没退成」。
- **支付宝线「有记录」不等于「已退成功」**：同一笔失败会反复重试落多行。判定 **MUST** 看有没有 `REFUND_STATUS='SUCCESS'` 的行。

**账面聚合口径**（「钱到底欠没欠」的最终判据，**MUST 优先于上表的快速筛**）：

```
主表金额  −  SUM(退款表 REFUND_STATUS='1' 的金额)
```

| 线 | 主表金额列 | 退款表 |
|---|---|---|
| TVM | `TBL_TVM_ORDER_PAY.TOTAL_PRICE` | `TBL_TVM_ORDER_REFUND` |
| BOM | `TBL_BOM_ORDER_PAY.TRANS_AOUNT`（**列名少个 M**） | `TBL_BOM_ORDER_REFUND` |
| APP | `TBL_TVM_APP_ORDER.PAY_AMOUNT` | `TBL_APP_ORDER_REFUND` |

⚠️ 三张退款表的 `REFUND_AMOUNT` 都是 `VARCHAR2` 且有脏值，聚合 **MUST** 带 `REGEXP_LIKE(REFUND_AMOUNT,'^[0-9]+$')`，否则 `TO_NUMBER` 抛 `ORA-01722`。

## 三、操作铁律

### 1. 接口响应不可信，必须查退款记录表核验

TVM / BOM / face-pay 各入口无论退款成败都返回 `retCode 0000`。逐笔核验用：

| 业务线 | 核验表 | 成功值 |
|---|---|---|
| TVM 购票 | `TBL_TVM_ORDER_REFUND.REFUND_STATUS` | `1`（`2`=失败） |
| APP 取票 | `TBL_APP_ORDER_REFUND.REFUND_STATUS` | `1`（`0`=退款中、`2`=失败） |
| BOM 非现金 | `TBL_BOM_ORDER_REFUND.REFUND_STATUS` | `1` |
| 免密扣款 | `PAY_REFUND_DETAIL.REFUND_STATUS` | `SUCCESS`（`RETRY`/`PROCESSING`=未终态） |
| 支付宝渠道 | `ALIPAY_REFUND_LOG.REFUND_STATUS` | `SUCCESS` |
| 日票 / 计次票 | `DAILY_TICKET_REFUND.REFUND_STATUS` | **`REFUNDED`**（`REFUNDING`/`WAIT_VERIFY`=未终态） |
| 当面付 | `F2F_REFUND.REFUND_STATUS` | `SUCCESS`（`INIT`/`PROCESSING`=未终态，`FAILED`=失败，**`MANUAL`=悬挂**） |

### 2. 全部入口无幂等，禁止整批重跑

没有任何一条链路对同一 `orderNo` 做「已退则短路」。中断后 **MUST** 按第二节条件重查待退清单再续跑，**NEVER** 重放原列表。

### 3. 逐笔调用 + 间隔 1~2 秒，不要并发

`alipay-pay-sign-server` 退款事务内调支付中心，密集并发会触发行锁堆积。

### 4. 先试最小金额一笔，核验通过再批量

### 5. 编写 shell 循环时用单行空格分隔的列表

多行变量 `for item in $LIST` 可能静默退出（exit code 0），靠查库才发现。

### 6. 网关 `code=600` 单次不可信，NEVER 直接判故障中止

单次 600 可能偶发，**MUST 间隔几分钟复打一次**再决定是否中止。若已中止并打了最小一笔，该笔的 `RSV2` 已被失败退款回填——**MUST 还原 `RSV2` 为 `NULL`**（先记录原值与还原 SQL）再继续。

## 四、操作细节（影响判断，MUST 知道）

- **`refundReason` 被忽略**：TVM / BOM 入口的 `refundReason` 传了会被服务端硬编码「出票数量不足」覆盖，以转义字面量入库，未做 unicode 解码。
- **BOM `ticketLogicNum` 不参与退款**：只用于成功后回写 `TBL_BOM_SUB_TICKET.RSV2`。`CARD_ID` 为 null 时填 `0000000000000000`，该占位卡号在 `TBL_BOM_SUB_TICKET` 里不存在，`updateByTicketLogicNum` 命中 0 行纯空转，不会脏写。
- **BOM 分派依据**：`TBL_TVM_ORDER_PAY_PRE.TRANS_TYPE`（**不是**请求里的 `transType`、也不是 `TBL_BOM_ORDER_PAY.TRANS_TYPE`）。取值 `04` = `BOM_SCANED_PAY` 才走 `bomRefund`。

## 五、支付中心侧状态查法

`alipay-pay-sign-server` 只暴露 `payQuery`，**没有暴露 `refundQuery`**：

```
POST :30022/internal/alipay/payment/payQuery   {"orderNo":"..."}
```

返回 `tradeStatus` / `totalAmount` / `tradeNo` / `tradeDesc`。

⚠️ **`payQuery` 不是只读**：拿到支付中心应答后**无条件回写** `ALIPAY_PAY_LOG` 的 `PAY_STATUS` / `RESULT_CODE` 等字段。`channelAgreementNo` 解析不出时支付中心返 `code=604`，却照样把 `PAY_STATUS` 改成 `FAIL`。**用它探测网关前 MUST 想清楚会脏写哪一行，MUST 先存原值与还原 SQL**。

外层 `retCode=0000` 只表示我方封装成功，与支付中心 `code` 无关；判断网关是否可用 **MUST** 看日志里 `支付中心响应, response=` 那一行的 `code`。

**判断「钱是否真的扣走」以支付中心的 `tradeStatus` 为准。** `ALIPAY_REFUND_LOG` 里网关受理报文的记录（`code=200 操作成功`）**不代表有资金退回**，勿据此判定已退款。

支付中心常见拒绝措辞：`该订单已全部退款`（历史已退）、`该订单不能退款`（无实付，多为手工造的单）——均属「本来就不该退」，不是执行失败。

### 定位「查不到的订单号」

支付中心侧的订单号（如 `287985340479602688`）落在我方 `DAILY_TICKET_ORDER.TRADE_NO` / `PAYMENT_ORDER_NO`，**MUST 全库扫列定位，NEVER 只猜表**：

```sql
select TABLE_NAME, COLUMN_NAME, CNT from (
  select t.TABLE_NAME, t.COLUMN_NAME,
         to_number(extractvalue(xmltype(dbms_xmlgen.getxml(
           'select count(*) c from "'||t.TABLE_NAME||'" where "'||t.COLUMN_NAME||'" = ''<待查号>'''
         )),'/ROWSET/ROW/C')) as CNT
  from USER_TAB_COLUMNS t
  where t.DATA_TYPE = 'VARCHAR2' and t.CHAR_LENGTH >= 18
    and (t.COLUMN_NAME like '%ORDER%' or t.COLUMN_NAME like '%SEQ%'
         or t.COLUMN_NAME like '%TRADE%' or t.COLUMN_NAME like '%RSV%')
) where CNT > 0
```

**MUST 带上列名过滤**：不加时会撞到某张表的隐式日期转换、报 `ORA-01843`，且错误信息看不出是哪一列。

## 六、face-pay `MANUAL` 悬挂单的处理

`F2F_REFUND.REFUND_STATUS` 值域 `INIT`/`PROCESSING`/`SUCCESS`/`FAILED`/`MANUAL`。

**`MANUAL` 的语义是「钱到底退没退未知」**，由 `F2fRefundService.giveUpToManual` 唯一写入（`RETRY_TIMES >= 30` 或 `REQUEST_TMS` 距今超过 24 小时）。

**写成 `MANUAL` 之后该单永久悬挂，NEVER 指望自愈**：
- `F2fRefundReconcileJob` 只扫 `[INIT, PROCESSING]`，**不碰 `MANUAL`**；
- 无 HTTP 入口可推进；
- **唯一复活入口是支付中心退款回调** `POST /ci/app/receiveRefundResult`（要求报文带 `refundNo`）。

**测试环境清理 `MANUAL` 单只有两条路**：
1. 让支付中心补发一次带 `refundNo` 的回调；
2. 手工核对支付中心侧真实结果后 UPDATE 该行（**MUST 先记原值与还原 SQL**）。

**NEVER 直接重发退款** —— 钱可能已经退过了。另注意 `MANUAL` 行里 `FAIL_REASON` 留的是转人工前最后一次的失败原因，不是转人工的原因。
