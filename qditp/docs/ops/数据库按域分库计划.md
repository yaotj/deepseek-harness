# 青岛地铁 ITP 数据库按域分库计划

**撰写依据**：仓库 108+ 份 DDL 实测（130 张表）、`docs/ops/生产数据库容量规划.md`、项目工作记忆（P0 缺陷与部署约束）。
**状态**：草案 v2（**已定：方案 A 逻辑分库 + 4 个用户库**），待与甲方 DBA / 业务方校准口径。
**前置结论**：comate 历史会话中未检索到一份标题/内容明确为"按域分库计划"的会话；本文案以**当前代码库真实表清单**为基准重建，并沿用容量规划 §2.1 的"分域"口径与 `docs/business/README.md` 的模块↔域映射。如手头有具体 comate 会话 ID，可贴出由我对齐。

## 0. 现状（实测，非推断）

| 项 | 事实 |
|---|---|
| 物理位置 | 单实例 `172.20.222.3:1521 / AFCITPDB`，唯一 schema `QDITP`（用户 `qditp`） |
| 表规模 | **162 张业务表**（另 3 张 `BAK_RECON_*` CTAS 快照；2026-10-14 查库实测 `all_tables WHERE owner='QDITP'`），全部落在同一 schema，无物理/逻辑隔离。**本文 §3 清单当前只覆盖 127 张，34 张漏统待补（见 §3 勘误）** |
| 模块形态 | ~20 个微服务，硬编码 `application.properties` 的 `service.*.url` 与 `datasource` 指向同一个 `QDITP`（见 `docs/architecture/overview.md` §一：无注册中心、无 Feign/Dubbo、无 Redis/MQ） |
| 已知 P0（见容量规划 + 工作记忆） | ① **8 张手工 RANGE 分区**只建到 `P202612`，**2027-01-01 起分区管理失效**（另 3 张 `F2F_*` 为 INTERVAL 分区自动扩展、无悬崖，但带 GLOBAL 唯一索引；库内分区表共 15 张 = 13 RANGE + 2 LIST）；② 全库**零归档零清理**（除 2026-10-13 的 3 张 `BAK_RECON_*` 快照）；③ `F2F_ORDER/F2F_PAYMENT/F2F_RESULT_REPORT` 用 **GLOBAL 唯一索引**，DROP/TRUNCATE PARTITION 会让全局索引 UNUSABLE；④ `RACDG` 已用 **89.60%**，仅剩 624 GB |
| 环境约束 | **唯一目标业务库**，无第二套环境（decisions.md「唯一目标库」裁决）；`mcp_database_qd` 无只读保护、删除不可回滚，兜底只能用库内 `CREATE TABLE BAK_<表> AS SELECT` |
| 双跑风险 | recon / web-admin / face-pay / collect-pay 定时任务**无分布式锁**，两套同跑一库会重复扣费与重复投对账文件 |

> ⚠️ 容量问题（④）是**磁盘组层面**的，逻辑分库（同实例多 schema）**不增加任何容量**；只有物理分库（独立表空间/磁盘组/实例）才解决。本计划按**方案 A 逻辑分库**推进，容量 P0-4 须配合磁盘均衡另行处理。

## 1. 选型结论（已定）

- **方案 A：逻辑分库（同实例多 schema）** —— 在 `AFCITPDB` 内新建 **4 个用户库（schema）**，把 130 张表按业务聚类迁入；各微服务 `datasource` 指向自己的库。
- **4 个用户库**：`QDITP_USER`（用户中心）、`QDITP_TXN`（交易支付）、`QDITP_RIDE`（乘运）、`QDITP_PLAT`（平台公共）。
- **分组核心原则**：强耦合表尽量同库，减少跨库读。特别是**对账源表 `GATE_TXN_PAY` / `DAILY_TICKET_ORDER` / `F2F_*` 与 `RECON_*` 全部归入 `QDITP_TXN`**，对账不再跨库读源；`USER_ITP_REG_INFO` 留在 `QDITP_USER`，由分流网关 qdscg 用 `itp_ro` 只读账号跨库访问。
- **逻辑分库不解决容量**：热点表（PAY_CALLBACK_LOG / GATE_TXN_PAY / ALIPAY_PAY_CENTER_MSG_LOG / ALIPAY_PAY_CALLBACK_LOG / QRCODE_TXN_DETAIL）仍在同一磁盘组；分库把它们逐库隔离后，分区维护/归档/压缩可**逐库独立**做，把 P0-1/P0-2 从"全库单点"降维成"每库自治"。
- **实施顺序前置**：先 M0 修 P0（补 2027 分区 / 定归档 / F2F GLOBAL→LOCAL / 磁盘均衡），再做分库迁移。

## 4. 跨库共享策略（垂直拆分的真正难点）

`QDITP_PLAT` 是**全域只读引用层**：黑名单、参数/票价/线路/站点、密钥都在此，USER/TXN/RIDE 通过 **同义词 + 只读授权** 访问，禁止跨库写。

| 表 | 拥有库 | 谁跨库用 | 处理策略 |
|---|---|---|---|
| `USER_ITP_REG_INFO`(+LOG) | USER | 分流网关 qdscg（只读路由） | 归 USER；网关用 **`itp_ro` 只读账号**跨库授权 + 同义词，绝不写 |
| `APP_USER_PAY_CHANNEL` | USER | 支付域读 | USER 拥有，TXN 只读引用（同义词） |
| `TBL_STATION_INFO`(para) / `STATION_INFO`(ticket) | PLAT / RIDE | 多域读站线 | **两处并存是技术债**：统一收敛到 PLAT 的 `TBL_STATION_INFO`，RIDE 的 `STATION_INFO` 下线、改同义词 |
| `BLACKLIST*` | PLAT | 各交易服务黑名单校验 | PLAT 拥有，各库只读授权 + 同义词 |
| `METRO_CA_KEYSTORE`/`METRO_MEMBER_STATIC_KEY` | PLAT | AGM/fep-dev 密钥同步 | PLAT 拥有，设备域只读 |
| `TBL_*` 参数/票价/风险 | PLAT | 计费、闸机、风控多域读 | PLAT 拥有，各库只读授权 + 同义词 |
| `SYS_JOB`/`QRTZ_*` | PLAT | web-admin 内存 JobStore | 留 PLAT；其它模块 `@Scheduled` 属内存任务，不依赖这些表 |
| `RECON_*` 读源表 | TXN 内 | recon 读 GATE/DAILY/F2F | **已同库（TXN），零跨库读** |

> 原则：**引用数据只读共享 → PLAT + 同义词**；**交易数据绝不跨库 JOIN**，跨域需要数据走服务调用或文件，不在 DB 层做跨库事务。

## 5. 迁移方案（无第二环境前提下）

1. **兜底快照**：每批迁移前对源表 `CREATE TABLE BAK_<表>_<日期> AS SELECT * FROM <表>`（库内 CTAS，符合工作记忆兜底约束；`mcp_database_qd` 无回滚，绝不直接 DROP）。
2. **建库**：`CREATE USER QDITP_USER/QDITP_TXN/QDITP_RIDE/QDITP_PLAT IDENTIFIED BY ... DEFAULT TABLESPACE ...;` 并赋权；PLAT 对全域授只读。
3. **迁表**：同实例内 `DBMS_METADATA.GET_DDL` 取结构 + `INSERT /*+ APPEND */ INTO 目标 SELECT * FROM QDITP.<表>`（或 `expdp/impdp` `REMAP_SCHEMA`）。分区表连带分区定义迁。
4. **共享暴露**：PLAT 对象在 USER/TXN/RIDE 各库 `CREATE SYNONYM` + `GRANT SELECT`；USER 的 `USER_ITP_REG_INFO` 对网关 `itp_ro` 授权。
5. **切 datasource**：改各模块 `application.properties` 指向新库；同实例内可秒级回滚（`rename` 表或切回连接串）。
6. **双跑锁**：迁移窗口内对该库定时任务**停跑或加 `@SchedulerLock`**（呼应 P0 双跑硬约束），避免旧库+新库双写。
7. **GLOBAL 索引**：`F2F_*` 迁移或归档，`DROP/TRUNCATE PARTITION` 必须 `UPDATE GLOBAL INDEXES`（等效全索引重建），建议先改 LOCAL（见 M0）。

## 7. 风险与回滚

- **无第二环境**：一切靠库内 CTAS 快照 + 同实例可逆（rename / 切连接串回滚），严禁跨环境假想。
- **双跑重复扣费**：迁移期停该库定时任务或加分布式锁；recon 对账文件重复投递风险同理。
- **GLOBAL 索引陷阱**：F2F_* 归档/迁移务必 `UPDATE GLOBAL INDEXES`，否则索引 UNUSABLE 致查询/写入全挂。
- **容量不增**：逻辑分库**不扩容**，须配合 M0 磁盘均衡与表空间规划；若热点库需真扩容，须升级到物理分库（独立表空间/磁盘组）。
- **分区 2027 失效**：M0 必须在 **2026-12-15** 前完成（留 2 周观察），分库不能替代。

## 附：容量热点与分库的协同（来自容量规划 §0）
5 张占 81% 年增量的表分属：`PAY_CALLBACK_LOG`(TXN)、`GATE_TXN_PAY`(TXN)、`ALIPAY_PAY_CENTER_MSG_LOG`(TXN)、`QRCODE_TXN_DETAIL`(RIDE)、`ALIPAY_PAY_CALLBACK_LOG`(TXN)。**垂直分库后每张热点表独占其库**，分区维护、归档、压缩可逐库独立实施——这是分库最实在的运维收益。其中 4 张在 `QDITP_TXN`、`QRCODE_TXN_DETAIL` 在 `QDITP_RIDE`，两库需优先排分区与归档。
