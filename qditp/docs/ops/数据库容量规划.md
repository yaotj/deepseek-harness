## 0. 结论摘要

**一句话（已按实测校准，2026-09-23）**：老 ITP 环境实测**日增不到 3 GB**（≈ **1.07 TB/年**）。据此反推，§2 原设的「互联网票务日行程 60 万」**高估约 7.7 倍**，实际约 **7.8 万**。修正后：新平台 1 年增量 **1.07 ~ 3.21 TB**（视业务量相对老环境为 1~3 倍而定），**现有 10 TB 盘子够用 0.8 ~ 2.5 年，无需立即申请 20 TB**（原「20 TB」建议作废）。

**但容量不是本报告的头号问题 —— 结构性缺陷才是，且它们与数据量大小无关**：

- **P0-1**：7 张手工 RANGE 分区只建到 `P202612`，**2027-01-01 起分区管理直接失效** —— 这是**日期问题，不是容量问题**；
- **P0-2**：全库零归档、零清理；
- **P0-4**：老环境 `RACDG` 已用 **89.60%**，按实测增速也只够 **208 天** —— 而均衡是唯一「零成本、立即可做」的动作。

> **「容量集中度」不随口径缩放而改变** —— 各表占比是相对值，所以下面这张表在修正口径后依然成立。

### 四条必须先处理的结论（P0-4 于 2026-09-23 依老 ITP 实测容量补入）

| 优先级 | 结论 | 后果 | 最迟处理时间 |
|---|---|---|---|
| **P0-1** | 所有手工 RANGE 分区表只建到 `P202612`，靠 `P_MAX (MAXVALUE)` 兜底，且**43 个定时任务里零个「加分区」任务** | 2027-01-01 起新数据全部涌入 `P_MAX` 单分区，**月度分区形同虚设**：无法 DROP 归档、单分区无界增长、统计信息失效、查询退化 | 2026-12-15（留 2 周观察期） |
| **P0-2** | 全库**零归档、零清理**：43 个定时任务全是业务补偿/退款/对账，无任何数据生命周期管理 | 表只增不减。按基准量，交易流水 3 年将累积 ≈ 25 TB，且**无法回收** | 上线前定稿保留策略 |
| **P0-3** | `F2F_ORDER` / `F2F_PAYMENT` / `F2F_RESULT_REPORT` 用了 **GLOBAL 唯一索引**（其余分区表全是 LOCAL） | 这三张表 **DROP/TRUNCATE PARTITION 会让全局索引 UNUSABLE**，必须 `UPDATE GLOBAL INDEXES`（等于全索引重建）或事后重建，**归档窗口不可控** | 归档方案落地前 |
| **P0-4** | **老 ITP 环境 `RACDG` 已用 89.60%、仅剩 624 GB**，且两个 RAC 磁盘组严重不均衡（89.60% vs 47.68%，偏差 **1,006 GB**） | 按老环境实测增速（< 3 GB/日）也只够 **208 天**；**均衡后可达 543 天**。若为 ASM 磁盘组，满 = **实例全线停写** | **立即** —— 均衡是本报告**唯一「零成本、立即可做」**的动作（§5.1 ②） |

**三个结构性观察**：

1. **只有 `F2F_*`（face-pay 新表）用了 INTERVAL 自动分区**——即「写入时自动建下月分区」，是唯一面向未来正确的做法。其余 7 张 RANGE 表全是**手工枚举分区**，需人工维护。
2. **两张 LIST 分区表的分区键是「分片键」而非「时间键」**（`CARD_ID_TAIL` / `THIRD_USER_ID_SUFFIX`）——它们解决的是并发争用与批量维护，**天然无法承载时间维度的归档**。`QRCODE_STATUS` 与 `USER_ITP_REG_INFO` 属于「只增不减但只能整表管理」的形态。
3. **`ALIPAY_PAY_CALLBACK_LOG`（1 年 0.68 TB，全库第 5 大表）竟然未分区**——同域的另外两张表（`ALIPAY_PAY_TXN_DETAIL` / `ALIPAY_REFUND_TXN_DETAIL`）都分区了，只有它漏了。这是最显眼的一处不一致。

### 3.3 索引现状

- 13 张分区表中，**10 张全 LOCAL 索引**（DROP PARTITION 友好）；`F2F_*` 三张表混入 **5 个 GLOBAL 唯一索引**（见 §6 P0-3）。
- `USER_ITP_REG_INFO` 的 3 个索引在 DDL 中**未声明 LOCAL/GLOBAL**，Oracle 对分区表的默认行为取决于分区键是否包含在索引列中——**MUST 连库查 `USER_INDEXES.PARTITIONED` 确认**，不能在归档方案里想当然。

### 4.3 复算公式（口径变更时自行重算）

```
单表年容量 = 数据段 + 索引段
  数据段 = ceil(年增行数 / floor(7206 / 行宽)) × 8192 × 1.08
  索引段 = ceil(年增行数 / floor(7206 / (Σ索引列宽+11))) × 8192 × 1.15

年增行数 = 日交易笔数 × 每笔落行数 × 365
```

**行宽敏感度**：§1.2 的填充率是推算值。若实际行宽比推算值低 30%（报文普遍偏短），总容量降至约 **5.8 TB**；若高 30%（报文接近声明上限），升至约 **10.8 TB**。**MUST 按附录 A 在首次真实压测后校准一次**，并把实测行宽写回本表。

## 6. 风险清单

### P0-1 ｜ 分区表在 2027-01-01 集体失效

**事实**：7 张手工 RANGE 分区表的最后一个显式分区均为 `P202612 VALUES LESS THAN ('20270101')`，其后是 `PARTITION P_MAX VALUES LESS THAN (MAXVALUE)`。

```sql
-- 全部 7 张表同构（pay-sign / gate-txn-pay / ticket / alipay-pay-sign 四份 DDL）
PARTITION P202612 VALUES LESS THAN ('20270101'),
PARTITION P_MAX VALUES LESS THAN (MAXVALUE)
```

**后果**（不是「可能」，是「必然」）：

1. **2027-01-01 起，所有新数据落入 `P_MAX` 单分区**——分区表退化成普通表。按基准量，`PAY_CALLBACK_LOG` 与 `GATE_TXN_PAY` 各自 219 万行/月涌入同一分区。
2. **归档手段归零**：无法 `DROP PARTITION` 释放历史月份，只能 `DELETE`（产生海量 UNDO/REDO、且不释放高水位下空间）。
3. **统计信息与执行计划劣化**：`P_MAX` 无界增长，分区裁剪对「近 30 天」查询不再有效——所有时间范围查询都会扫到 `P_MAX` 的**全部分区内容**。
4. **`P_MAX` 有 MAXVALUE 兜底，不会报 ORA-14400**——这反而是坏事：**故障静默发生**，没有报警，没有报错，只有性能缓慢下滑。

**为什么没人发现**：43 个定时任务（`docs/ops/定时任务清单.csv`）中**没有一个是加分区任务**；`@Scheduled` 清单里也没有。这是一个**纯人工、无提示、无告警**的到期事件。

**处置**（见 §7.1）。

### P0-2 ｜ 全库零归档、零清理

**事实**：43 个定时任务逐条核对，**全部**是业务补偿（签约/解约通知补发、退款回查、黑名单通知）、对账、退款批量处理，**没有任何一条是数据归档或清理**。

**后果**：表只增不减。按基准量，3 年后交易流水类表累积约 25 TB，且**没有回收路径**（分区失效后连 DROP PARTITION 都用不了）。

**这是设计缺失，不是配置遗漏**——需要业务方先定义保留期，MUST 见 §8 待确认第 1 项。

### P0-3 ｜ GLOBAL 唯一索引阻断分区归档

**事实**：`F2F_ORDER`（2 个）、`F2F_PAYMENT`（2 个）、`F2F_RESULT_REPORT`（1 个）使用 `GLOBAL` 唯一索引：

```sql
-- face-pay-server/src/main/resources/sql/f2f-schema.sql
CREATE UNIQUE INDEX UK_F2F_ORDER_NO ON F2F_ORDER (ORDER_NO) GLOBAL;
CREATE UNIQUE INDEX UK_F2F_PAY_ATTEMPT ON F2F_PAYMENT (ORDER_NO, ATTEMPT_NO) GLOBAL;
CREATE UNIQUE INDEX UK_F2F_RESULT_REPORT_IDEM ON F2F_RESULT_REPORT (REPORT_TYPE, ORDER_NO) GLOBAL;
```

**后果**：对这三张表执行 `ALTER TABLE ... DROP PARTITION` 时，若不指定 `UPDATE GLOBAL INDEXES`，**全局索引整体变为 UNUSABLE**（对所有分区都不可用，不只是被删的分区）。带上该子句则**每次归档都触发全索引重建**。

**对比**：其余 10 张分区表全是 LOCAL 索引，`DROP PARTITION` 只影响被删分区，**归档可在线完成、秒级**。这三张表是**唯一需要特殊处理的**。

**处置建议**：归档方案里对 `F2F_*` 单独走一条路径（低峰期 + `UPDATE GLOBAL INDEXES`，或先重建为 LOCAL 索引——但需评估 `ORDER_NO` 的全局唯一性是否依赖 GLOBAL 索引，**MUST 先确认业务是否要求跨分区唯一**）。

### P1-1 ｜ 4 张表的 VARCHAR2 声明长度超出数据块，存在行链接

| 表 | 列 | 声明 | AL32UTF8 下最大字节 | 8K 块可用 |
|---|---|---|---|---|
| `APP_PAY_SIGN_LOG` | `REQUEST_BODY` / `RESPONSE_BODY` | VARCHAR2(8000 CHAR) | 24,000 B | 7,206 B |
| `APP_PAY_SIGN_REQUEST` | `REQUEST_BODY` / `RESPONSE_BODY` | VARCHAR2(8000 CHAR) | 24,000 B | 7,206 B |
| `GATE_TXN_PAY` | `INDUSTRY_DETAIL` | VARCHAR2(4000 CHAR) | 12,000 B | 7,206 B |
| `ALIPAY_PAY_CALLBACK_LOG` | `RAW_BODY` | VARCHAR2(4000) | 12,000 B | 7,206 B |

**后果**：单行超过块大小时 Oracle 使用**行链接（row chaining）**——一行跨 2 个以上块存储。代价是：① 空间浪费（每块尾部填充率骤降）；② **任何按 rowid 的单行读取都要多跳一次 I/O**。

`GATE_TXN_PAY` 是 219 万行/月的大表，`INDUSTRY_DETAIL` 一旦接近声明长度就会大面积行链接。**当前联调数据量小、报文短，完全看不出来**。

**处置**：① 确认这 4 列的**实际最大长度**（`SELECT MAX(LENGTH(...))`）；② 若确实需要存长报文，MUST 改用 `CLOB` + 行外存储（这些问题列都**不是**分区键，可以改）；③ 若实际远小于声明，MUST 收窄声明长度（同时防住「超长直接 ORA-12899」）。

### P1-2 ｜ 21 张表的 LOB 未做任何存储优化

**事实**：全库 108 份 DDL 中，**`STORE AS` / `LOB(` 关键字零命中**——所有 CLOB/BLOB 均使用默认参数。

**三个后果**：
1. **默认 `ENABLE STORAGE IN ROW`**：CLOB 在 4,000 字节以内的部分**内联在行里**，把本已 4~5 KB 的行宽进一步推高、加剧 §6.2 讨论的块填充浪费。
2. **无独立 LOB 表空间**：LOB 与普通数据混存，无法对 LOB 单独做压缩、单独扩容、单独迁移到低成本存储。
3. **LOB 默认不压缩**：而表数据可通过 `COMPRESS FOR OLTP` 压缩 2~3 倍（见 §7.3）。

**处置**：为 LOB 建独立表空间，对 `PAY_CALLBACK_LOG` / `ALIPAY_PAY_CENTER_MSG_LOG` / `F2F_PAYMENT` / `PAY_REFUND_DETAIL` 的报文列考虑启用压缩。

### P1-3 ｜ `ALIPAY_PAY_CALLBACK_LOG` 未分区（本可避免）

1 年 0.68 TB、全库第 5 大表，**同域另外两张表都分了区**。属 DDL 一致性缺口。

**处置**：按 `CREATE_TIME` 做 INTERVAL 月分区，与 `F2F_*` 形态对齐。⚠️ 对已有数据的表改分区需 `DBMS_REDEFINITION` 在线重定义。

### P1-4 ｜ 49 张表含时间列但未分区

其中**真正会持续增长**的约 25 张（`ALIPAY_PAY_CALLBACK_LOG`、`APP_PAY_SIGN_*`、`DAILY_TICKET_*` 8 张、`F2F_NOTIFY_TASK` / `F2F_TICKET` / `F2F_REFUND`、`SUPPLEMENT_ORDER` / `_ITEM`、`USER_ACC_EMPLOYEE_CARD*`、`USER_PHONE_CHANGE_LOG`、`SYS_OPER_LOG` / `SYS_LOGININFOR` / `SYS_JOB_LOG`、`TBL_RISK_CONTROL_LOG`、`TBL_NOTICE_APP_FAILURE_RECORD`、`LOGIC_CARD_POOL_CARD` 等）。其余是配置/主数据类（`SYS_*`、`TBL_PARA*`、`TBL_STATION*`、`TBL_FARE*`、`QRTZ_*`），不增长、无需处理。

**处置**：按 §7.2 分层，**优先处理年容量 > 10 GB 的**（`ALIPAY_PAY_CALLBACK_LOG` 0.68 TB、`F2F_NOTIFY_TASK` 0.14 TB、`DAILY_TICKET_PAY_LOG` 69 GB、`DAILY_TICKET_INSTANCE` 35 GB、`DAILY_TICKET_PAY_NOTIFY` 35 GB、`APP_PAY_SIGN_REQUEST` / `_LOG` 各 11 GB）。

### P1-5 ｜ 行宽导致块填充率仅 55%~59%

**这是容量测算里最容易被忽略、但数值最大的浪费项。**

| 表 | 行宽 | 8K 块可放行数 | 块填充率 |
|---|---|---|---|
| `PAY_CALLBACK_LOG` | 4,496 B | 1 行 | **55%** |
| `ALIPAY_PAY_CENTER_MSG_LOG` | 4,814 B | 1 行 | **59%** |
| `F2F_PAYMENT` | 4,830 B | 1 行 | **59%** |
| `PAY_REFUND_DETAIL` | 5,897 B | 1 行 | **72%** |
| `GATE_TXN_PAY` | 3,487 B | 2 行 | **85%** |

前四张表**每块只能放 1 行、块内 40%+ 空间被浪费**。这三张表 1 年合计 3.77 TB，**其中约 1.5 TB 是块内碎片**。

**处置**：
- 短期：**16K 块**（前提下表已按 16K 块建，或整库重建）——`PAY_CALLBACK_LOG` 在 16K 块下可放 3 行、填充率升至 82%。
- 中期：把报文列下沉为行外 LOB + 压缩（见 §7.3），行宽降到 1 KB 级后填充率自然改善。
- **注意**：把报文列改成「行外」需要重建表（`DBMS_REDEFINITION`），**MUST 在业务窗口内做**。

### P2 ｜ 其他已登记的容量相关事项

- **时间列类型与时区基准不统一**（`docs/ops/排障手册.md` §1.6、项目记忆）：`QRCODE_STATUS.CREATE_TIME/UPDATE_TIME`、`QRCODE_TXN_DETAIL.CREATE_TIME` 是 `TIMESTAMP(6)` 无时区列、由 Java `LocalDateTime.now()` 直写，**TZ 修复（2026-09-23 12:00）之前写入的历史行是 UTC、之后是北京时间**。做时间窗 / 分片 / 对账判断 MUST 先分清基准。**这与容量规划的关系**：任何「按时间归档」的脚本若用这两列做分区或删除条件，**MUST 先做时区归一**，否则会归档错数据。
- **`TXN_DATE` 是 `VARCHAR2(8)`（`YYYYMMDD` 字符串）**，分区靠字典序比较。**格式一旦写错（如出现 `2026-09-23`），该行会静默落入 `P_MAX`**。归档脚本 MUST 加格式校验。
- **序列逼近上限**：`LOGIC_CARD_POOL_BATCH_SEQ` 区间 100000~999999 且 **无 `CYCLE`**，90 万个批次号（`docs/business/card-pool.md`）。当前用量未知，**MUST 连库查 `LAST_NUMBER`**。
- **`USER_ITP_REG_INFO_BAK20260909`** 等库内备份表的存在会额外占容量，**MUST 连库盘点并清理**。

### 7.1 立即（2026-12-15 前必须完成）

**① 解决分区到期（P0-1）——两个方案，任选其一**

## 附录 A ｜ 实测校准 SQL

**首次连库时 MUST 执行下列语句，把实际值换回 §1.2 / §4.3 的公式。**（本次未连库、以下均为待执行）

```sql
-- A1. 确认库与块大小
SELECT name, log_mode, block_size FROM v$database;
SHOW PARAMETER db_block_size;
SHOW PARAMETER db_recovery_file_dest_size;

-- A2. 表空间与可用空间
SELECT tablespace_name, status,
       ROUND(SUM(bytes)/1024/1024/1024, 2) AS total_gb
  FROM dba_data_files GROUP BY tablespace_name, status ORDER BY 3 DESC;

-- A3. 每张表的真实段大小（容量基线；当前量小，仅作对照）
SELECT segment_name, segment_type,
       ROUND(SUM(bytes)/1024/1024, 1) AS mb, SUM(blocks) AS blocks
  FROM user_segments
 GROUP BY segment_name, segment_type
 ORDER BY SUM(bytes) DESC FETCH FIRST 40 ROWS ONLY;

-- A4. ★ 真实行宽（校准本报告全部数字的关键）
SELECT table_name, num_rows, blocks, avg_row_len
  FROM user_tables WHERE num_rows IS NOT NULL
 ORDER BY avg_row_len DESC FETCH FIRST 40 ROWS ONLY;

-- A5. 实际最大报文长度（判 P1-1 行链接是否真的发生）
SELECT MAX(LENGTH(INDUSTRY_DETAIL)) AS max_industry_detail FROM GATE_TXN_PAY;
SELECT MAX(LENGTH(RAW_BODY))        AS max_raw_body        FROM ALIPAY_PAY_CALLBACK_LOG;
SELECT MAX(LENGTH(REQUEST_BODY))    AS max_request_body    FROM APP_PAY_SIGN_LOG;

-- A6. 分区实际情况（含 P_MAX 当前行数，P0-1 的探针）
SELECT table_name, partition_name, num_rows, blocks,
       ROUND(bytes/1024/1024, 1) AS mb, high_value
  FROM user_tab_partitions
 WHERE table_name IN ('PAY_TXN_DETAIL','PAY_REFUND_DETAIL','PAY_CALLBACK_LOG',
                      'GATE_TXN_PAY','QRCODE_TXN_DETAIL','ALIPAY_PAY_TXN_DETAIL',
                      'ALIPAY_REFUND_TXN_DETAIL','ALIPAY_PAY_CENTER_MSG_LOG',
                      'F2F_ORDER','F2F_PAYMENT','F2F_RESULT_REPORT')
 ORDER BY table_name, partition_position;

-- A7. 索引 LOCAL/GLOBAL 与可用性（P0-3 与 §3.3）
SELECT index_name, table_name, partitioned, status, locality
  FROM user_part_indexes WHERE table_name IN ('F2F_ORDER','F2F_PAYMENT','F2F_RESULT_REPORT',
       'USER_ITP_REG_INFO');

-- A8. 序列余量（P2）
SELECT sequence_name, last_number, max_value FROM user_sequences WHERE cycle_flag='N';

-- A9. 库内备份表盘点（P2）
SELECT table_name, num_rows FROM user_tables
 WHERE table_name LIKE '%BAK%' OR table_name LIKE 'BAK_%';

-- A10. UNDO 使用与 ORA-01555 历史（§5）
SELECT MAX(maxquerylen) AS max_query_sec, MAX(undoblks) AS max_undo_blocks FROM v$undostat;
```
