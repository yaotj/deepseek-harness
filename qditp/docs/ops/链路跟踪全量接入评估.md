# 链路跟踪（Tracing）全量接入评估

> 状态：**评估稿 v1.0**（2026-10-14）
> 范围：`itp` 命名空间全部业务模块是否应开启 Micrometer Tracing + VictoriaLogs 日志链路
> 结论速览：**不建议简单「全量三行成组」**；应按模块重要度分三档接入，先补齐当前已开模块的配置缺口，再分批扩展，并同步治理日志上报量与存储容量。

---

## 一、现状盘点（2026-10-14 仓库基线 + deploy/k8s 2026-09-22 导出）

### 1.1 链路跟踪的机制回顾

当前实现是**轻量级自建方案**，不依赖 Zipkin/Jaeger/SkyWalking/OTel Collector：

- **traceId 产生**：Spring Boot `management.tracing`（Micrometer Tracing）在 HTTP 入向/出向自动生成或续接；Quartz 侧由 `AbstractQuartzJob.before()` 生成 32 位 hex traceId 写入 MDC 与 `sys_job_log.job_message`。
- **传递**：入向请求头 `traceparent`/`b3`（`FirstFilter` 小写后塞 MDC）；服务间由 Boot 托管的 `WebClient.Builder` 自动带 W3C `traceparent`；Quartz 出向由 `QuartzTraceUtils.traceHeaders()` 显式组装 `traceparent` + `X-Vlogs-Capture: 1`。
- **落点**：log4j2 `%X{traceId}` 写文件；`VictoriaLogsAppender` 推送 JSON 结构化日志到 VictoriaLogs（`VLOGS_URL`），按 `traceId` 检索还原链路。

### 1.2 当前开启面

| 维度 | 现状 |
|---|---|
| **tracing 已开模块（文档实测 9 个）** | `pay-sign-server`、`card-pool-server`、`recon-server`、`gate-txn-pay-server`、`daily-ticket-server`、`collect-pay-server`、`face-pay-server`、`alipay-pay-sign-server`、`para-server`（后两者经 K8s Deployment env 注入） |
| **VLOGS_URL 注入面（deploy/k8s 基线）** | **21 个业务 Deployment 全部注入**（唯一例外 `trans-query` 未注入；`web` 前端 nginx 无需注入） |
| **tracing 配置三行成组完整度** | ✅ 完整：`collect-pay`（yml 三行）；`pay-sign`、`card-pool`、`recon`、`gate-txn-pay`、`daily-ticket`（properties 三行）<br>⚠️ **缺口**：`para-server`（deploy/k8s 只有 `enabled=true` + `sampling.probability=0`，**无** `OtlpAutoConfiguration` 排除）；`blacklist-server`（deploy/k8s 只有 `enabled=true`，**既无** sampling=0 **也无** 排除）；`face-pay-server`/`alipay-pay-sign-server` 的 deploy/k8s 基线中未捕获到 tracing env（但文档称已开，**需现查线上 Deployment**） |

### 1.3 用户描述与实际的偏差

> 「当前只是定时任务链路启用了链路跟踪」

**不准确**。实际上：

1. **HTTP 入向链路也已在 9 个模块开启**——不是只有 Quartz 任务链路。`FirstFilter` + Micrometer 对 HTTP 请求自动生成/续接 traceId，`WebClient` 自动传播 `traceparent`。
2. **Quartz 只是「显式传头」做得最完整**（`QuartzTraceUtils` 9 个任务类全接入），所以给人「只有定时任务在跟踪」的印象；实际上普通 HTTP 服务间调用在已开模块间也已透传 traceId。
3. **日志上报（VictoriaLogs）已全量部署**——21 个模块都注入了 `VLOGS_URL`，只是未开 tracing 的模块上报的是**无 traceId 的 WARN+** 日志。

## 二、全量接入的影响面与风险分析

### 2.1 直接收益

| 收益 | 说明 |
|---|---|
| **端到端排障** | 请求从 `fep-app` → 业务服务 → DB/RPC/支付渠道，全程一个 traceId，VictoriaLogs 一条 LogsQL 串起全链路 |
| **对账/退款链路可追踪** | 当前对账链路已实测续接通过（face-pay 补齐动因）；全量后覆盖所有跨服务链路 |
| **性能观测** | `MapperAspectToTrace` / `ServiceAspectToTrace` 自动记录 mapper/service 耗时与成功/失败状态，可做慢调用分析 |
| **Quartz 调度日志闭环** | 前台「执行日志」按 `job_message` 的 traceId 检索下游日志，目前依赖下游模块开启 tracing |

### 2.2 成本与风险

| # | 风险 | 等级 | 说明 |
|---|---|---|---|
| 1 | **VictoriaLogs 存储容量** | 🔴 **高** | 当前 PVC 仅 **15Gi** RWO（`apigateway2`，**不支持扩容**）。当前只有 WARN+ 与 `x-vlogs-capture=1` 链路全量上报，若全量开启 tracing 且把上报阈值降到 INFO，日志量将暴涨（collect-pay 心跳日志曾占 79%，face-pay 设备心跳同样高频），**15Gi 很快写满** |
| 2 | **OTLP exporter 空转** | 🔴 **高** | 集群**不存在** `collector-istio-traces-service.opentelemetry`。任何模块若只加 `management.tracing.enabled=true` 而**漏掉** `OtlpAutoConfiguration` 排除，Deployment 一旦注入 `MANAGEMENT_OTLP_TRACING_ENDPOINT` 就会起 exporter，每批抛 `UnknownHostException` 刷日志。**当前 `para-server` / `blacklist-server` 已存在此缺口** |
| 3 | **ADR-D53 异常包装陷阱放大** | 🟠 **中** | `MapperAspectToTrace` / `ServiceAspectToTrace` 的 `observe(Supplier)` 陷阱（会把受检异常包成 `RuntimeException`，使幂等兜底 `catch (DuplicateKeyException)` 失效）**只在打开 tracing 的模块出现**。全量开启 = 所有模块的幂等逻辑都要经受切面考验；当前代码已修复，但**线上镜像若未全部重建**，旧切面仍会触发 |
| 4 | **日志敏感信息泄漏面扩大** | 🟠 **中** | `FirstFilter` 把**全部请求头**（含 `authorization`）塞进 MDC。VictoriaLogs 模板只白名单 `traceId/spanId`，但若全量开启后有人把模板改成全量输出 MDC，或日志级别下调，报文日志（含令牌）会被整体搬进日志后端 |
| 5 | **`InternalMicroHttp` 请求头明文** | 🟠 **中** | `recon-server` 与三个源服务已把该 logger 压到 WARN（含 `X-Recon-Token` 明文）。全量接入若动日志级别，可能把内部令牌重新暴露 |
| 6 | **虚拟线程 pinning** | 🟡 **低** | `VictoriaLogsAppender` 已用平台线程发送、有界队列，业务线程只做序列化入队；开启 tracing 本身不新增阻塞 IO，风险可控 |
| 7 | **部署与镜像重建面** | 🟠 **中** | 每个模块开启 tracing = 改 properties/yml + 重建镜像 + 滚动发布（`replicas=1` 需逐个）；且 `mvn install` 只更新本机 `~/.m2`，**公共构件改动需逐个重建所有模块镜像**（ADR-D53 曾只重建 1 个、其余 6 个线上仍是旧切面） |
| 8 | **判断依据不可靠** | 🟠 **中** | deploy/k8s 只是模板，**线上 Deployment 与仓库不同源**（`para-server` 即活样例）。全量接入前 MUST 先 `kubectl -n itp get deploy <d> -o yaml` 逐模块核对实际 env，否则会漏/错配 |

## 三、评估结论与推荐方案

### 3.1 总体结论

**不建议「一把梭」全量三行成组**。理由：

1. **存储是硬约束**：VictoriaLogs 15Gi 不可扩容，全量 INFO 上报会快速写满，且无容量治理方案前置；
2. **当前架构下 tracing 的边际收益递减**：链路的关键路径（对账、退款、Quartz 调度）已开；剩余模块大多是**无状态接入层/公共能力层**，单跳链路价值有限；
3. **存在未闭合的配置缺口**（para / blacklist 的 OTLP 排除），全量接入会把这些缺口放大到所有模块。

### 3.2 推荐：分三档接入

#### 档位 A：必须补齐（当前已开但配置不完整）

| 模块 | 动作 |
|---|---|
| `para-server` | 在 deploy/k8s 与线上 Deployment 补 `spring.autoconfigure.exclude=...OtlpAutoConfiguration`（已有 enabled+sampling=0） |
| `blacklist-server` | 补 `sampling.probability=0` + `OtlpAutoConfiguration` 排除（当前只有 enabled=true） |
| `face-pay-server` / `alipay-pay-sign-server` | 核对线上 Deployment 是否三行完整；deploy/k8s 基线未捕获，需现查 |
| 全部 9 个已开模块 | 逐个核对线上 env 是否三行成组，防止历史漏配 |

#### 档位 B：建议新增接入（业务链路关键节点）

| 模块 | 理由 |
|---|---|
| `fep-app-server` | **APP 统一接入层**，所有 APP 流量入口；不开则 APP 请求的 traceId 在入口断链 |
| `fep-dev-server` | 闸机/设备域入口（IF1A） |
| `fep-acc-server` | ACC 员工卡通知链路 |
| `fep-alipay-server` | 支付宝渠道网关入口 |
| `ticket-server` | 乘车码状态机核心，被 face-pay/trans-query 依赖 |
| `account-server` | 账户开户核心 |
| `alipay-account-server` | 支付宝账户链路 |
| `trans-query-server` | 已承接真实流量（APP 交易查询），且当前**未注入 VLOGS_URL**，需一并补 |

#### 档位 C：暂不接入（低价值/高成本）

| 模块 | 理由 |
|---|---|
| `key-server` | 密钥管理，调用极低频，无跨服务追踪价值；且涉及安全密钥，日志面越小越好 |
| `blacklist-server`（若已完成档位A则按需） | 黑名单通知低频，单跳 |
| `industry-data-server` | 行业数据上报，低频 |
| `acc-es-server` / `security-server` | ACC/安全内部链路，低频且敏感 |
| `web-admin` | 管理后台，使用 logback 非 log4j2，且依赖 RuoYi 框架，接入成本高、收益低（其 Quartz 出向链路已通过显式头传递闭环，不需要自身开启 tracing） |
| `web`（nginx 前端） | 静态资源，无需 |

### 3.3 前置条件（在扩展接入之前 MUST 完成）

1. **存储容量治理**：
   - 评估 VictoriaLogs 日志量（`* | stats by (app) count()` 看各 app 上报量）；
   - 扩容 PVC 或建立日志保留/归档策略（当前 15Gi 不可扩容，需甲方协调）；
   - 维持「默认只上报 WARN+，`x-vlogs-capture=1` 链路全量 INFO」的两级过滤策略，**NEVER 把 Root 的 VictoriaLogs 引用放到 INFO**。
2. **配置治理**：
   - 把「三行成组」固化为可复用片段（建议在 deploy/k8s 的 Deployment 模板统一加，而非散落各 properties）；
   - 利用 `deploy/k8s` 基线 + 线上核对脚本，建立「哪些模块开了 tracing」的**可执行核对清单**（避免再次出现 para-server 式「仓库无配置、线上已开」）。
3. **安全边界**：
   - 维持 VictoriaLogs 模板白名单只有 `traceId/spanId`；
   - 确保 `InternalMicroHttp` logger 保持 WARN；
   - 全量开启前 MUST 复核所有模块的 `other.web.enableLogRequestInFilter` 与 `logResponseMaxSize`，控制报文日志体量。
4. **镜像基线**：
   - 确认所有目标模块的镜像都包含 ADR-D53 修复后的切面（`MapperAspectToTrace` / `ServiceAspectToTrace` 手工 start/openScope/error/stop 版本），否则幂等兜底会失效。

### 3.4 实施顺序建议

```
Phase 0：核对线上现状
  kubectl -n itp get deploy <d> -o yaml 逐模块核对 tracing env / VLOGS_URL / 三行成组
  → 输出《线上 tracing 实际开启清单》

Phase 1：补齐档位 A 缺口（低风险，纯配置）
  给 para-server / blacklist-server 补三行成组；核对 face-pay / alipay-pay-sign 线上配置
  → 验证：日志出现 traceId，且无 vlogs-sender 异常、无 UnknownHostException

Phase 2：VictoriaLogs 容量评估与扩容
  统计当前日志量 → 申请容量 / 建立保留策略
  → 前置条件：容量满足后再扩展接入面

Phase 3：档位 B 模块分批接入（每批 2~3 个）
  每批：改配置 → 重建镜像 → 滚动发布 → 用 trace-selfcheck-<yyyyMMdd> 路径自检验证续接
  → 验证：入向 traceparent 能续成下游 MDC traceId；按 traceId 检索 VictoriaLogs 全链路可查

Phase 4：回归验证
  对账链路、退款链路、Quartz 调度日志（前台「执行日志」按钮）全链路可检索
  → 观察 vlogs-sender 线程数、日志量增长、无 OTLP 异常日志
```

### 3.5 替代方案（如果目标是「全链路可观测」而非「全模块开 tracing」）

1. **Istio 分布式追踪**：集群已装 istio 1.24.6（含 jaeger/kiali/grafana），每个 Pod 已有 envoy sidecar。**启用 istio 的 mesh 内追踪**（`meshConfig.enableTracing` + 把 trace 上报到 Jaeger）即可获得**无代码侵入**的全链路拓扑，覆盖所有模块（含 fep-*、web-admin），且不产生应用日志量。**这是性价比最高的替代路径**。
   - 注意：istio 追踪需要 Jaeger collector 地址可达、需要为它分配存储；与应用侧 Micrometer traceId 是**两套体系**，但可以通过 W3C `traceparent` 传播头**互通**（istio 也支持 W3C）。
2. **保持现状 + 按需开启**：只保留档位 A/B，其余模块不开。排障时对关键链路已足够。

## 四、验证方法（每个模块开启后）

| 验证项 | 方法 |
|---|---|
| traceId 是否写入 | `kubectl -n itp logs deploy/<d> | grep traceId` 看 `%X{traceId}` 列是否有值 |
| 入向续接 | 用带 `traceparent` 的请求打一个不存在的路径（如 `/trace-selfcheck-20261014`），看目标模块日志 MDC traceId 是否等于入向 traceId |
| 服务间续接 | 从已开模块调用下游，看下游日志 traceId 是否一致 |
| VictoriaLogs 上报 | 容器内 `cat /proc/$(pgrep -f app.jar)/task/*/comm | grep vlogs-sender` 看线程在；VictoriaLogs `* | stats by (app) count()` 看 app 出现 |
| 无 OTLP 空转 | `kubectl -n itp logs deploy/<d> | grep -i unknownhost` 应无 `collector-istio-traces-service` 相关异常 |
