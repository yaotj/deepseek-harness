### Gateway / VirtualService 现状（2026-10-23 14:5x 实测，ns `itpb`）

| 对象 | 类型 | 关键配置 |
|---|---|---|
| `accountserver-gw` | Gateway | selector `istio: ingressgateway`、**port 8082**、hosts `*` |
| `manage-gw` | Gateway | 同 selector、**port 8081**、hosts `*` |
| `fep-app-vr` | VirtualService | → `accountserver-gw`，15 条（7 exact SCG + 8 prefix） |
| `manage-vr` | VirtualService | → `manage-gw`，2 条（`/web-server/`→`web-admin-gfbh6-svc:31943`；`/`→`web-frontend-twcm6-svc:31919`） |

**四条硬事实（踩过才知道）**：

1. **8081 / 8082 靠 `hostPort` 对外，不靠 Service**。`istio-ingressgateway` 容器的 `http8080/http8081/http8082` 三个端口都声明了**同名 hostPort**，所以直连「跑着 ingressgateway 的节点 IP + 端口」即可访问（实测 `http://172.120.2.28:8081/login` → 200）。但该 Service 只有 `80→80 (nodePort 32493)` / `443→443 (31291)`，**没有 8081/8082 的 Service 端口映射**（`istioctl analyze` 报 IST0162）⇒ 走 Service / NodePort / 集群内 `<svc>:8081` 反而**不通**。
   - **推论（排障时别踩）**：8081/8082 只在那两个部署了 ingressgateway Pod 的节点上监听。2026-10-23 快照为 `172.120.2.28`(`worker-ec8c3`) 与 `172.120.2.29`(`worker-c4051`)；任一 Pod 重建换节点，对应节点 IP 立即失效。现查：`kubectl get vs` 无用，用 `kubectl get pod -n istio-ingress -o wide` 取 NODE 再对 `kubectl get node -o wide` 取 INTERNAL-IP。
2. **destination 的 `port.number` 填 Service port（319xx），不是 targetPort 8080**。填 targetPort 会让 `istioctl analyze` 报 IST0101 `Referenced host:port not found`，且运行时 503。唯一例外是 `fep-app-eyrx5-svc`（port 就是 8080）。
3. 两个 Gateway 同 selector、不同端口 ⇒ Envoy 内 `http.8081` / `http.8082` 两个 listener 并存、互不影响（8081 `/` → 200 与 8082 `/fep-app/` → 403 同时成立）。但 `istioctl analyze` 会报 **IST0145 冲突告警**（因 hosts 同为 `*`），**实测无影响**，属已知噪声。
4. `fep-app-vr` 现有 4 个 destination 指向**测试环境服务名**（`fep-alipay-rec8g-svc`、`fep-dev-server-748lq-svc`、`para-server-pufrl-svc`、`route-sentinel-svc`），红岛无此 Service ⇒ `/para-server/` 实测 503，与 IT-016 同源，MUST 换成 `itpb` 实际 Service 名（对照表见该 IT）。

**探活口径**（不要 `kubectl port-forward`、不必起临时 Pod）：

```bash
kubectl exec -n istio-ingress deploy/istio-ingressgateway -c istio-proxy -- \
  curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/
```

> 判定：`200/403` = 网关与后端都通（403 是后端鉴权正常拒绝）；`404` = VS 未命中（前缀写错或未生效）；`503` = 路由通但后端无实例或 Service 名不存在。

### 综管台 `web-admin` MUST 单实例（会话层是进程内缓存）

> 2026-10-23 实测事故：`web-admin` 被平台默认部署成 **2 副本**，登录页报「验证码已失效」。已用 `docs/ops/environments/scripts/itp-ops.sh cloudos scale web-admin 1 --yes` 降为单实例，10/10 验证通过。

- **根因**：`web-admin` 不用 Redis（项目纪律），会话全部走 `LocalCache` —— 其类注释原文即 **“JVM local cache for single-instance deployments”**，底层 `ConcurrentHashMap`。两处受影响的键：
  - `SysLoginService.validateCaptcha` → 验证码 `uuid → code`；
  - `TokenService`（第 78 / 158 行）→ 登录态 `uuid → LoginUser`。
  **两者都只存在于生成它的那个 Pod 内存**。2 副本时：取码落 A、提交落 B ⇒ 验证码失效（实测 7/10）；侥幸登录成功后每个接口仍有约 50% 概率 401（表现为「登录进去马上弹回登录页」）。
- **约束**：`web-admin` **NEVER 多副本**，`replicas` 恒为 `1`。平台重新部署若把副本数重置为 2，登录会再次间歇性失效 —— 上线核验 MUST 检查 `kubectl get deploy web-admin -n itpb` 的 READY 是 `1/1`。
- **代价与替代**：单副本 = 综管台无高可用、发布时秒级中断（内部管理后台，可接受）。要恢复多副本 MUST 先把 `LocalCache` 外部化（落 Oracle 表或改 JWT 自包含），属架构改造，需业主裁决，**NEVER 只调副本数了事**。
- **关验证码不解决**：`sys.account.captchaEnabled=false` 只绕过第一层，登录态照样跨 Pod 丢。

**PDB 连接要点**：
- MUST 用 Service name `hditpdb` 连接；**NEVER 用 SID**（`itpcdb1`/`itpcdb2` 或 CDB 服务名）—— 能连上但看不到业务表

- RAC VIP 已由集群维护故障切换，**NEVER 直连单节点 IP**

RAC 三库（`hdmlcdb` / `hdaccdb` / `hditpdb`）均为 CDB+PDB 架构，业务对象在 PDB 里。
