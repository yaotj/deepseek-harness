# 推荐部署顺序（qd-itp）

> **用途**：全新集群全量部署、整批滚动更新、异网迁移时，按业务依赖关系排「先起谁后起谁」。
> 单模块日常发版不需要本文；多模块同批发版 MUST 按本文波次走。
>
> **依赖依据**：各模块 `application.properties` 的 `service.*.url`（2026-10-17 实读）+ 启动类 `@EnableRpcXxx` 注入点 + `docs/architecture/overview.md` 分层 + `docs/ops/environments/跨环境共性.md` 外部依赖。
> **快照口径**：端口 / NodePort / 版本以 [`K8S迁移清单.md`](../K8S迁移清单.md) + 各环境文档（[测试环境.md](测试环境.md) / [红岛.md](红岛.md)）现查为准，**MUST 现查集群实况**，NEVER 把本文数字当现状。
> 粗粒度顺序（迁移视角）见 `K8S迁移清单.md` 建议顺序，本文是其按模块的细化。

## 一、结论：六波部署顺序

| 波次 | 内容 | 模块（按序） |
|---|---|---|
| W0 前置（非部署） | 网络策略 / Secret / 时区 / 日志底座 | Oracle、HSM 加密机、支付中心、支付宝、ACC、FTP 网络策略；VictoriaLogs；`database`（database-server） |
| W1 安全与公共能力 | 被广泛调用、出向依赖最少 | `security-server`（acc-security-server）→ `para-server` → `key-server` → `card-pool-server` → `blacklist-server` → `industry-data-server` |
| W2 业务核心 | 事务与落库，互调成环 | `account` → `ticket-server` → `pay-sign-server` → `gate-txn-pay-server` → `daily-ticket-server` → `alipay-account-server` → `alipay-pay-sign-server` → `face-pay-server` → `trans-query` |
| W3 接入层（FEP） | 对外流量入口，依赖已就绪 | `fep-app` → `fep-alipay` → `fep-dev-server` → `fep-acc` → `es-server`（acc-es-server） |
| W4 对账 | 数据生产方就绪后才起 | `recon-server` |
| W5 管理旁路 | 最后起，反代全部后端 | `web-admin` → `web`（nginx 前端） |

**不纳入**：`collect-pay-server`（2026-10-13 起退居后台、判断 MUST 现查 Deployment）、`acc-secure-server` / `collect-ticket-server`（目录在、集群无 Deployment）、`employee-card-acc-simulator`（模拟器，未部署且编译失败，NEVER 进部署清单）。

## 二、依赖依据

### 2.1 分层与调用关系（按 `service.*.url` 实测）

```
外部：APP / 闸机AGM / TVM / BOM / ACC清分中心 / 支付中心 / 支付宝
                    │
  接入层(FEP)   fep-app  fep-alipay  fep-dev  fep-acc     ← W3
                    │  （薄网关：解析报文 → RPC 转发，多数无数据库）
  业务服务层    account ticket pay-sign gate-txn-pay       ← W2
               daily-ticket alipay-account alipay-pay-sign
               face-pay trans-query
  公共能力层    para key blacklist industry-data card-pool ← W1
  ACC/安全层    security-server(HSM) acc-es                ← W1 / W3
  旁路          web-admin + web(nginx)                     ← W5
```

**被调用次数（决定同波次内的先后）**：ticket-server（8 个调用方）、pay-sign-server（8）、gate-txn-pay-server（8）、account（7）、para-server（7）、security-server（8，含配置键未注入的按实际注入点计 5）、blacklist-server（5）、alipay-pay-sign-server（5）、industry-data-server（5）、daily-ticket-server（4）、alipay-account-server（3）、trans-query-server（3）、key-server（3）、card-pool-server（4）、face-pay-server（2 + 设备直推）、fep-acc-server（1，ACC 主动推）。

### 2.2 外部依赖（W0 必须就绪，否则对应业务起不来或不可用）

| 外部系统 | 使用方 | 不通的后果 |
|---|---|---|
| Oracle 业务库 | 全部业务模块 | 起不来 |
| HSM 加密机（TCP 长连） | `security-server` | 签名 / 密码运算全失败，W1 首个就受阻 |
| 支付中心（bestonepay） | pay-sign / daily-ticket / alipay-pay-sign（collect-pay 已退居后台） | 下单 / 支付 / 退款不可用 |
| 支付宝 openapi | fep-alipay / alipay-account / alipay-pay-sign | 支付宝域全不可用 |
| ACC 清分中心 | fep-acc（入向员工卡通知）、acc-es（FTP + Netty） | 员工卡域不可用 |
| 公网入口 + 回调地址 | daily-ticket / collect-pay 支付回调、fep-app 签约/解约回调 | 支付结果收不到 |

地址与端口见 `docs/ops/environments/跨环境共性.md`（MUST 现查，迁移场景全部会换）。

## 三、分批明细

### W0 前置（部署动作之前）

1. 网络策略：新集群 → Oracle / HSM / ACC / FTP / 支付中心 / 支付宝（这是整个部署里最长的前置项，MUST 最早启动）。
2. 密钥进 Secret（`deploy/k8s/05-secret-template.yaml` 是模板，NEVER 把真实值写进仓库）。
3. 节点时区 `Asia/Shanghai`——挂宿主 `/etc/localtime` 或 Deployment 注入 `TZ`，否则对账账期与乘车码时效全线错 8 小时。
4. 日志底座 VictoriaLogs 先起（后续每批排查都靠它）。
5. `database`（database-server）按集群现状确认是否需要在业务之前就绪。

### W1 安全与公共能力

| 顺序 | 模块 | 放此波的理由 |
|---|---|---|
| 1 | `security-server` | HSM 封装，被 account / ticket / key / industry-data / para / alipay-pay-sign / web-admin 调用；它不起，后面全部签名类操作失败 |
| 2 | `para-server` | 参数服务，被 ticket / gate-txn-pay / alipay-pay-sign / fep-app / fep-alipay / trans-query / web-admin 调用；仅弱依赖 security |
| 3 | `key-server` | 密钥版本，被 fep-app / fep-dev / web-admin 调用；仅弱依赖 security |
| 4 | `card-pool-server` | 逻辑卡号池，被 account / alipay-account / daily-ticket / web-admin 调用；无出向业务依赖、无 `@Scheduled` |
| 5 | `blacklist-server` | 黑名单，被 pay-sign / fep-app / fep-alipay / alipay-pay-sign / web-admin 调用；与 alipay-pay-sign 运行期互调（见 §四） |
| 6 | `industry-data-server` | 行业数据上报，被 ticket / fep-app / fep-alipay / alipay-pay-sign / web-admin 调用；仅弱依赖 security |

### W2 业务核心（事务与落库层）

同波次内部顺序的意义：**缩短「已被调用的服务先就绪」的窗口**。这一层四个模块（account / ticket / pay-sign / gate-txn-pay）存在运行时互调环（见 §四），无启动强依赖，按被调用次数降序排列：

| 顺序 | 模块 | 关键出向依赖（就绪状态） |
|---|---|---|
| 1 | `account` | ticket（本波 2）、security（W1）、paySign（本波 3）、cardPool（W1）、gateTxnPay（本波 4） |
| 2 | `ticket-server` | security / industryData / para（W1）、account（1）、alipayAccount（6）、gateTxnPay（4）、dailyTicket（5）、paySign（3） |
| 3 | `pay-sign-server` | account（1）、blacklist（W1）、gateTxnPay（4）+ 支付中心（W0） |
| 4 | `gate-txn-pay-server` | paySign（3）、account（1）、para（W1） |
| 5 | `daily-ticket-server` | cardPool（W1）、recon（W4，见 §四）+ 支付中心（W0） |
| 6 | `alipay-account-server` | ticket（2）、cardPool（W1） |
| 7 | `alipay-pay-sign-server` | alipay-account（6）、blacklist（W1）、para（W1）+ 支付中心（W0） |
| 8 | `face-pay-server` | 设备（TVM/BOM/APP）直推 + fep-app / web-admin 调用；7 个 `@Scheduled` 无分布式锁，**MUST 单副本** |
| 9 | `trans-query` | 只读聚合：alipay-pay-sign（7）、dailyTicket（5）、gateTxnPay（4）、paySign（3）、para（W1）——全部就绪后才起，查询不返空 |

### W3 接入层（FEP）

| 顺序 | 模块 | 理由 |
|---|---|---|
| 1 | `fep-app` | APP 统一入口，出向依赖横跨 W1+W2 全部；放最后意味着「入口通了，后端都通了」 |
| 2 | `fep-alipay` | 支付宝渠道入口；依赖 alipay-account / alipay-pay-sign / blacklist / ticket / transQuery |
| 3 | `fep-dev-server` | 闸机 / 设备域入口（AGM 心跳落库）；依赖 key / ticket |
| 4 | `fep-acc` | ACC 员工卡入向（ACC 主动推）；依赖 account |
| 5 | `es-server`（acc-es-server） | ACC 编码设备（FTP + Netty），独立通道；web-admin 查询用它 |

### W4 对账

- `recon-server`：被 ticket / gate-txn-pay / daily-ticket 在运行期调用（推送对账数据），又通过 web-admin 的 `sys_job` 触发日终对账（读上述模块的交易数据）——**双向依赖，放在 W2 全部就绪之后**。
- **MUST 单副本**（无分布式锁）；双跑场景（新旧集群并行）MUST 保持 0 副本或关掉 Quartz，否则重复投对账文件。

### W5 管理旁路

| 顺序 | 模块 | 理由 |
|---|---|---|
| 1 | `web-admin` | 综管台后端，`/page/**` 查询横跨全部业务模块，且其 `sys_job` 触发 recon——recon（W4）就绪后才起它 |
| 2 | `web`（nginx） | 前端静态 + 反代全部后端（`nginx.conf` 逐条 `location` 指向各服务）；最后起，用户才见得到完整功能 |

## 四、互依赖环的处理（顺序无法完全线性化的部分）

| 环 | 成员 | 处理 |
|---|---|---|
| 账户-票务-支付环 | account ↔ ticket ↔ pay-sign ↔ gate-txn-pay | 运行期 RPC 互调，**无启动强依赖**（WebClient 不建立即连）；按被调用次数降序起，把探活窗口内不可用的调用降到最少 |
| 黑名单-支付宝签约环 | blacklist ↔ alipay-pay-sign | 同上；blacklist 放 W1、alipay-pay-sign 放 W2 后段，环上后起动者用先起者的服务 |
| 对账双向依赖 | recon ↔ ticket / gate-txn-pay / daily-ticket | recon 单独 W4：调用方（W2）先就绪，recon 后起；W2 期间指向 recon 的调用失败按各模块既有重试 / 补偿逻辑消化 |
| 入口-后台环 | web-admin → 全部；fep-app → collectPay（已下线） | web-admin 放 W5；fep-app 的 collectPay 指向已下线服务，属已知缺口，见 overview.md 配置现状问题 |

## 五、每批验证门（缺一不可）

1. **探活用 `/actuator/health`**（`http://172.20.211.23:<NodePort>/actuator/health`）：`http=200` 且 body 里 `db` UP 才算起来。
2. **`rollout status` 成功 ≠ 应用起来了**：刚返成功时探活可能 503，单次 503 NEVER 当失败，间隔约 30 秒复探、带 body 看是 envoy 无健康上游还是 Boot 自己 DOWN。
3. **日志确认**：VictoriaLogs 按 `app` 名（≠ Deployment 名）检索，确认无 `APPLICATION FAILED` / `Failed to parse mapping resource`；`Tomcat started` 搜不到 NEVER 当失败（重载时机问题）。
4. **digest 比对**：Pod imageID = 推送 digest（判据见 `AGENTS.md §7`）。
5. **单副本保持**：face-pay / recon / web-admin（及 collect-pay 若在跑）NEVER 扩到 >1 副本。
6. 每批完成后记录原 image tag 作回滚命令；NEVER 同 tag 覆盖。

## 六、日常批量发版怎么用

- **单模块发版**：不需要本文，按 `qditp-deploy-release` 技能六步走。
- **多模块同批发版**：按 W1→W5 波次分组，波内可并行、波间 MUST 等上一波探活通过；改了 `model` / `rpc` / `resource/micro` 时，MUST 先 install 再重建链路上每一个经手模块（详见 `AGENTS.md §7`）。
- **给 `model` 的 DTO 加字段**：MUST 重建链路上每一个经手该 DTO 的模块，NEVER 只重建终点服务（旧 class 被 Fastjson2 静默丢字段）。
