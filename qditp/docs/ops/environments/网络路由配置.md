# 本机到各环境的内网路由配置（USB 网卡 AX88179B）

> **定位**：开发者本机（macOS）通过 USB 有线网卡 `AX88179B`（接口 `en9`）接入 qd-itp 各环境内网时，
> 如何配置「网卡地址 + 网段路由」，以及踩过的坑。
> **各环境网段 / 网关 / 插口完全不同，MUST 现查、NEVER 跨环境抄值**——照抄别的环境只会得到一个"看似配好了但什么都连不上"的状态。
> **红岛的网段分区、各段网关与端点可达性实测见本文档 §七**（源：ACLC 红岛数据中心设备管理表 2026-10-15）。

## 一、核心原理：只配网卡地址不够，MUST 补网段路由

macOS 把网卡地址配上后只会自动生成**直连网段**（如 `172.120.249.0/24` → `en9`）。
访问**其他网段**（如 `172.120.110.25` 业务库）时，内核会走**默认路由**（办公网 `en0`）→ 出口防火墙直接丢弃 → 表现为"连接超时"。

所以 MUST 显式加一条**覆盖目标环境整段的三层路由**，把跨区流量交给该环境的接入网关：

```
目标网段（如 172.120.0.0/16）──► 接入网关（如 172.120.249.254）──► en9
```

未加路由时的典型误判：`ping` 本网段网关通、`ping`/`nc` 其他区全不通，容易得出"防火墙隔离、跨区本来就不通"的错误结论
（`红岛.md` 2026-10-19 的旧结论即源于此，2026-10-23 已实测修正，见 §六）。

## 三、操作步骤（macOS，需管理员权限）

### ① 确认接口名与链路状态

```bash
networksetup -listallhardwareports | grep -A2 AX88179B   # 应输出 Device: en9
ifconfig en9 | grep -E "inet |status"                     # status: active 才算插好
```

> 接口名 `en9` 是本机当前值，**换机器 / 增减外设会漂移**，MUST 每次现查，NEVER 硬记。

### ② 下发网卡地址

```bash
sudo ifconfig en9 inet 172.120.249.163 netmask 255.255.255.0
```

> 掩码 MUST 与网段一致（出口区为 `/24`）。掩码写错会导致网关不在直连网段、路由直接加不上。

### ③ 加网段路由

```bash
sudo route -n add -net 172.120.0.0/16 172.120.249.254
```

### ④ 验证（三项全过再算通）

```bash
route -n get 172.120.110.25            # gateway 应为 172.120.249.254，interface 应为 en9
route -n get 8.8.8.8                   # 默认路由 MUST 仍是办公网 en0，未被抢占
nc -z -G 5 172.120.110.25 1521         # 目标服务端口可达
```

**绝对不可省的对照项**：`172.120.x.x` 与 `8.8.8.8` 两条 `route get` 必须分别指向 `en9` 和 `en0`。
只测前者会漏掉"整段路由把默认路由一起顶掉、外网全断"的情况。

## 四、五个已踩过的坑（2026-10-23 实测）

| # | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 1 | `netstat` 里路由挂在 `en9`，`route get` 却返回默认路由 `en0` | 用了 `-ifscope en9`，作用域路由只对同作用域 socket 生效，普通程序匹配不到 | **NEVER 加 `-ifscope`**，用普通路由 |
| 2 | `networksetup -setmanual` 返回 0，但 `ifconfig en9` 没有 IPv4 | 手动配置存在 `preferences.plist` 里但未下发到网卡（重启 / 插拔后高发） | 用 `ifconfig en9 inet ...` 直接下发；MUST 复查 `ifconfig` 而非只看返回码 |
| 3 | `ping` 100% 丢包，误判服务挂了 | 红岛两侧主机对 ICMP 静默（防火墙只放行管理探测） | 判定可用性 MUST 用 **TCP 端口探测**（`nc -z` / `openssl s_client`），NEVER 用 ping 定论 |
| 4 | `curl` 超时，但 `nc` 显示端口通 | `172.120.209.151` 是**自签证书**（`C=CN, O=Default Company Ltd`），且 80 → 443 强制 308 跳转 | 加 `-k` 跟随跳转：`curl -sSk -L` |
| 5 | 重启后路由神秘消失 | `route add` 只改运行时表，不持久 | 每次接入后重跑 §三；或见 §五 的持久化选项 |

> 补充：`nc -z` 的超时给太短（`-w 2`）会把首次 ARP 解析/慢握手误判为失败。探测统一用 `nc -z -G 5`。

## 五、切换环境 / 断开时的清理

换插口或换环境前 MUST 清掉旧环境的路由，避免旧路由把新环境流量带偏：

```bash
sudo route -n delete -net 172.120.0.0/16     # 删上一环境网段路由
sudo ifconfig en9 inet <新环境地址> netmask <新掩码>   # 覆盖为新环境地址
```

- **NEVER 用 `route flush`**——会连办公网默认路由一起清掉，本机直接断网。
- 路由 **不持久**：如需开机自动生效，需自建 LaunchDaemon（当前未做，按需再加）。

## 六、2026-10-23 实测记录（红岛，出口区 `.249` 插口）

本机 `172.120.249.163/24` + 路由 `172.120.0.0/16 → 172.120.249.254`：

| 目标 | 结果 | 证据 |
|---|---|---|
| `172.120.249.254`（网关） | ✅ 0.7 ms | `ping` 通、ARP 已解析 |
| `172.120.110.25`（ITP 生产库 RAC VIP / `HDTPDB`） | ✅ 可达 | `:22` OpenSSH_8.0；`:1521` TCP 通且静默等待客户端（Oracle 监听器特征）；`:80/:8080` refused |
| `172.120.209.151`（云管 VIP / 云管理平台控制台） | ✅ 可达 | `:22` OpenSSH_9.8；`:80` → 308 → `:443` TLSv1.2 自签证书，`/platform/` 返回 200；`:1521/:3389/:8080` refused |
| 两台主机 ICMP | ❌ 静默 | ping 全丢、traceroute 全星号——**属正常，非故障** |
| 办公网默认路由 | ✅ 未受影响 | `route get 8.8.8.8` → `192.168.29.19`/`en0`，外网正常 |

**与旧结论的差异（重要）**：
`红岛.md` 2026-10-19 记「`.249` 出口区插口只能 ping 本网段、全其他区不通」。
2026-10-23 实测：**补上 `172.120.0.0/16` 路由后，业务区 `.110` 与其他区均可达**。
差异原因是旧结论**未加网段路由**，跨区流量回落办公网默认路由被入口防火墙丢弃。
若在新环境复现"只有本网段通"，先按 §一 检查路由，**NEVER 直接断定网络侧隔离、更 NEVER 反复重试触发告警**。

### 7.4 结论：三层全通、四层按分区 ACL 放行

1. **七个网段的 `.254` 网关全部可达** ⇒ 三层路由没有问题，一条 `/16` 路由足够覆盖全红岛。
2. **能否访问某个服务，取决于分区防火墙 ACL，与路由无关**。同一网段内会出现"网关通、业务端口不通"（如 `3.x` 网关通但 FTP / EM 全超时）。
3. 已实测放行的分区：**`209`（云管/安全）全通、`110`（业务网）数据库 1521 全通、`2.x` 控制节点 22 通**。
   未放行：`3.x` / `4.x` 业务端口、`250.x` 堡垒机、各集群 K8s API。
4. **判定顺序 MUST 是**：`route -n get <目标>` 确认走 en9 → `nc -z -G 5 <网关> 22` 确认三层通 → 再 `nc -z -G 5 <目标> <端口>`。
   前两步通而第三步超时 = **ACL 未放行，找网络侧开通**，**NEVER 改路由、NEVER 反复重试**。
5. 表里有 ≠ 现在能通：网段与端点会随二期新增 / ACL 调整变化，**MUST 以实测为准**，本表仅作起点。
