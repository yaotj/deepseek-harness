5. **日终对账（recon-server）未端到端实跑** — 三个源 + recon-server 链路此前从未跑通过；四张 `RECON_*` 表生产库仍待执行、对账 FTP / PVC / 鉴权令牌均待闭合。
6. **旅游票 `TRAVEL_TICKET_ORDER.PAY_STATUS` 无代码回写** — `TravelTicketOrderMapper` 无任何 UPDATE，`PAY_STATUS` 恒 `INIT`，`ITP.PAY` 旅游票两段恒为 0 行。
7. **`GATE_TXN_PAY.TXN_DATE` 实际列类型与仓库 DDL 不一致**（P1，但影响对账/分区，建议上线前闭合）。
8. **分区表 2027-01-01 集体失效（数据层 P0）** — 7 张手工 RANGE 分区表只建到 `P202612`，靠 `P_MAX(MAXVALUE)` 兜底，2027 起全落单分区，裁剪与 DROP PARTITION 归档双失效且静默。**MUST 在 2026-12-15 前处理**（详见 `docs/ops/数据库容量规划.md`）。
9. **容器时区 TZ 未设（P0，隐蔽）** — 上线 MUST `kubectl -n itp set env deployment/<d> TZ=Asia/Shanghai`；否则对账账期/乘车码时效全线错 8 小时。

> 其余历史 P0（支付回调死循环、网关路径缺 `/v1`、地址指错目标、localhost 死配置等）文档已标注「已修复」，但不等于当前线上一定正确 —— **改 env 后 MUST 探活 + 字节码反查确认**。

### 0.4 已知 P1 风险（上线前评估，非硬阻塞）

- 虚拟线程 pinning（ojdbc8 大量 synchronized，慢 SQL 会 pin 载体线程；Dockerfile 已抬高 parallelism 缓解，未取证）。
- 服务间地址错配 / 键缺失（改 env 易遗漏，MUST 逐 `*Client` 对键）。
- 容器内不可用本地路径（Windows `d://`、`/Users/zhoucong/logs` 残留）。
- 明文 FTP 穿越防火墙可能被阻断；被动模式端口段须单独开。
- `DISCOUNT_LEVEL` 档位非单调（满 300 元反而更贵）。
- `PAY_REFUND_DETAIL` 有 6 条 `RETRY` 无人补偿、2 行畸形 `TXN_DATE`、渠道退款号三列全 NULL（与支付中心对账做不到）。

### 0.5 决定部署形态的关键约束

- **单副本硬约束**（NEVER 扩副本）：`recon-server`（进程内锁）、`web-admin`（Quartz 内存 JobStore）、`face-pay-server`（7 个 `@Scheduled`）、`collect-pay-server`（`SingleTicketRefundTask` 4 处）、`acc-security-server`（逻辑卡号内存自增）。
- **无 Redis / 无 MQ**：异步统一为「落库 + 扫表补偿」，幂等靠唯一索引 + `DuplicateKeyException`。
- **双跑禁止**：新旧集群同时连同一库时，上述 4 个服务的定时任务 MUST 保持 0 副本或关 Quartz，否则重复扣费/重复推通知/重复投对账文件。
- **入向路由唯一开关**是 `fep-app-vr` 这条 VirtualService（8 条前缀），NEVER 改 K8s Service selector 切流量。

## 2. 构建流程

> 镜像 tag = pom `<version>`。**重复构建会覆盖同 tag，节点 `IfNotPresent` 不重拉 ⇒ MUST 升版本号（+0.0.1）重建**，否则改动不生效。判成功 MUST 在输出里找 `Pushed` / `digest:`，**NEVER 看退出码**（管道会吃掉 Maven 退出码）。

### 2.1 标准构建（多数模块 `package` 即 build+push 镜像）

```bash
mise exec -- mvn -o clean package -pl <module> -DskipTests
```

- **`package` 就会推镜像**的模块（含 `pay-sign` / `gate-txn-pay` / `acc-es` / `collect-ticket` / `fep-dev` / `recon` / `para` / `web-admin` / `fep-app` / `account` / `key` / `blacklist` / `industry-data` / `acc-security` / `fep-alipay` 等，MUST 逐模块 `grep -A6 kubernetes-maven-plugin <module>/pom.xml` 确认）。
- **只出 jar 不推镜像**的模块：`fep-acc-server`（goals 被注释，须显式 `mvn k8s:build k8s:push`）、`face-pay-server`（jkube 在 `remote` profile 且**无** `activeByDefault`，须加 `-Premote`）。
- 镜像名来自 `<image.prefix>`，**≠ 模块名**：`fep-app-server` 的镜像是 `itp/fep-app`。

### 2.2 改动 `model` / `rpc` / `resource/micro` 后的标准三步序列（铁律）

> 这三个公共构件版本号恒定（`model` 2.0.0 / `rpc` 2.0.1，NEVER 升），旧 class 已打进旧镜像；Fastjson2 宽松模式**静默丢字段不报错** ⇒ 只 `mvn install` 对线上零影响，**MUST 逐个重建受影响模块镜像**。

```bash
mise exec -- mvn -o clean install -pl model,rpc -DskipTests -Djkube.skip=true
mise exec -- mvn -o clean package -pl <业务模块1>,<业务模块2> -DskipTests   # 这步会 build+push
ssh k8s-master "kubectl set image deploy/<名> <容器名>=<镜像>:<tag> -n itp"   # 逐个滚更
```

- 第一步 MUST 带 `-Djkube.skip=true`；第二步 **NEVER 加 `-am`**（否则掩盖「到底 install 过没有」）。
- 给 `model` 的 DTO 加字段 ⇒ 重建链路上**每一个**经手该 DTO 的模块（APP 类接口至少 `fep-app-server` + 目标业务服务两个）。

### 2.3 本机无法直连集群 docker 时的离线构建（常态）

```bash
# 本机只出 jar（MUST -Dmaven.test.skip=true，否则删过 target 报假错）
mise exec -- mvn -o -pl <module> -am package -Djkube.skip=true -Dmaven.test.skip=true
# 逐个 scp（build-push.sh 会删目录下其他 jar，两 jar 不能同时传）
scp <module>/target/<module>-<ver>.jar k8s-master:/home/java/
ssh k8s-master "cd /home/java && ./build-push.sh <svc> <ver>"
```

### 2.4 版本号铁律

- 每次部署 MUST 升 pom `<version>` 末位 +1，**NEVER 同 tag 覆盖**（AGENTS.md §7）。
- `web-admin` 的 tag 来自聚合 pom 的 `<project.version>`，改一处带动 6 子模块。
- 判断线上实际版本 **MUST 查 Deployment image tag**，NEVER 拿仓库 pom 推断。

## 3. 部署流程

### 3.1 部署顺序（依赖方向：安全/公共 → 业务核心 → 接入层 → 后台）

```
1. acc-security-server            # 无依赖，密码运算前提
2. para-server, blacklist-server, key-server, industry-data-server
3. account-server
4. ticket-server, pay-sign-server, gate-txn-pay-server
5. daily-ticket-server, collect-pay-server, collect-ticket-server
6. alipay-account-server, alipay-pay-sign-server
7. fep-app-server, fep-dev-server, fep-acc-server, fep-alipay-server
8. acc-es-server
9. web-server(web-admin) + web
```

> ⚠️ **`pay-sign-server` MUST 排在 `web-admin` 之前**：web-admin 的 `sys_job` 305/310 调 pay-sign 的 `/internal/payment/compensateRefundQuery` 与 `/compensateRefundSummary`，这两个端点在 pay-sign < 2.0.87 不存在，反序上线会每轮 404 且被误判成补偿 bug。

### 3.2 单服务部署

```bash
./scripts/deploy-to-harbor.sh <module>      # 自动 scp + ssh build-push.sh
```

脚本从自身位置推导仓库根（`LOCAL_BASE_DIR`），会找 `target/<module>-*.jar`（排除 `*-original`/`*-sources`/`*-javadoc`），提取版本号，上传并远程构建推送。

### 3.3 批量串行部署

```bash
./scripts/batch-deploy.sh                    # 按 ALL_SERVICES 全量
./scripts/batch-deploy.sh <m1> <m2>         # 指定
```

- 失败即 `break`、终止后续。**`ALL_SERVICES` MUST 与 `deploy-to-harbor.sh` 保持一致**，且须按 §3.1 顺序；`web-admin` 不适用本脚本。
- ⚠️ 脚本目录在根 `svn:ignore` 内，**仅本机生效、不进版本库**。

### 3.4 基于 `kubectl set image` 的灰度 / 回滚

```bash
kubectl get deploy -n itp -o custom-columns='NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image'   # 看现版
kubectl set image deploy/<名> <容器名>=<镜像>:<tag> -n itp
kubectl rollout status deploy/<名> -n itp
```

- Deployment / 容器名 ≠ 模块名（账户域叫 `account` 不是 `account-server`）；Service 端口 ≠ `server.port`（pay-sign svc 是 8080 非 9096）。

### 3.5 单副本约束

`recon-server` / `web-admin` / `face-pay-server` / `collect-pay-server` / `acc-security-server` 的 Deployment **replicas MUST 恒为 1**。双跑/扩副本会导致重复扣费、重复推通知、重复投对账文件。

## 4. 部署后验证

### 4.1 探活（NEVER 只看 rollout status）

```bash
# 从 k8s-master 压测 MUST 用 NodePort，NEVER 用 <svc>.itp.svc
curl -s -w '\nhttp=%{http_code}\n' http://172.20.211.23:<NodePort>/actuator/health
```

- `rollout status` 成功 ≠ 应用起来了（Pod `2/2` 但端口不监听）。
- 探活单次 `503` **NEVER 当失败**（预热期），间隔约 40 秒复探；`200` 即端口在监听、上下文起完。
- `web-admin` 探活返 `200` 带 `401` body 是它自己鉴权拦了 `/actuator/health`，**属正常**。

### 4.2 字节码反查（确认上线的是哪版代码）

`image tag` / `pom 版本` 都可能被同名覆盖欺骗，**确认「改动真的上线」MUST 容器内反查**：

```bash
kubectl exec -n itp <pod> -c <容器> -- sh -c \
 "cd /tmp && J=/home/javaapp/soft/jdk-21.0.1/bin; \$J/jar xf /app.jar BOOT-INF/classes/<pkg>/<Class>.class && \$J/javap -p -c BOOT-INF/classes/<pkg>/<Class>.class; rm -rf /tmp/BOOT-INF"
```

### 4.3 日志查看

```bash
./scripts/klog.sh <服务名> [关键字] [-f] [行数]   # 例：./scripts/klog.sh para-server ERROR 200
```

- 404 伪装成 `200 + UUID retCode` 时 MUST 逐 Pod grep 容器内完整日志的 `No static resource`，NEVER 只靠 klog 带关键字（尾部窗口 + Pod 重启丢日志会漏）。

### 4.4 定时任务验证

Quartz 用**内存 JobStore**，`QRTZ_*` 表恒为 0 行 ≠ 没跑。**判断任务在跑 MUST 查 `SYS_JOB_LOG`**，NEVER 看 `QRTZ_*`。运行中改 `sys_job` 不会生效，须重启 web-admin 或在后台界面对该任务改一次保存。

## 6. 回滚方案

- **单服务回滚**：`kubectl set image deploy/<名> <容器>=<上一版镜像>:<上一 tag> -n itp` + `rollout status`。**改前 MUST 先记下原 tag**。
- **回滚位三件套**（迁移/大版本）：旧集群 YAML + 原 image tag + 公网入口指回旧地址，缺一不可。
- **双跑期间**：旧集群业务 Deployment 缩到 0（NEVER 直接删），保留至少 T+2 一个对账周期作回滚位。
- 注意：同 tag `set image` / `rollout restart` **不会**重拉已缓存镜像层；回滚 MUST 用**升过号的原 tag**，或临时 `imagePullPolicy: Always` / 删节点缓存。

## 7. 关键约束与禁令（NEVER 清单）

- **NEVER 扩那 5 个单副本服务**（recon / web-admin / face-pay / collect-pay / acc-security）。
- **NEVER 双跑期间让两套集群定时任务同时对同一库生效**。
- **NEVER 把 Service 端口「统一规整」** —— 一堆 `service.*.url` 写死了现有端口号，改端口 = 同时改几十条 env。
- **NEVER 照搬旧密钥/旧地址到新环境**；也 NEVER 在文档/提交信息/对话里回显这些值。
- **NEVER 漏 `/etc/localtime` 与 `TZ`** —— 新节点非 CST 会让对账账期与乘车码时效错 8 小时。
- **NEVER 切流量改 K8s Service selector** —— 唯一开关是 `fep-app-vr` VirtualService（带 `test` op 的 `kubectl patch`）；`/itptvm/` `/itpbom/` 的 rewrite 带前缀、不是 `/`。
- **NEVER 用 git 判断改动**（本项目是 SVN；上层旁挂 git 是陈旧快照）。
- **NEVER 只看退出码/rollout status/image tag 判成功** —— 找 `Pushed`/`digest:`、探活 `200`、必要时字节码反查。
- **NEVER 认为「`mvn install` 过了 / env 改过了」就等于生效** —— 公共构件改动 MUST 重建受影响模块镜像 + `kubectl set image`。
- **NEVER 认为「改完 env 就生效」适用于公共构件** —— 涉及 `model`/`rpc`/`resource/micro` 的改动必须重建镜像。
