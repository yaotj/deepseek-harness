# IT-054 乱序迟到的 IF1A-01 进站通知覆盖更新的出站结果，状态倒退致 IF8D-03 不发进站码

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-054` 一行。

## 1. 背景 / 现象
- 发现时间：2026-11-03 15:18（测试环境）
- 发现渠道：测试反馈「15:18 推码没有成功」，排障发现
- 影响范围：`ticket-server` IF1A-01 状态机（`QRCODE_STATUS` 更新链路）；受影响卡 `0426090949000058`
- 现象描述：15:18:12 / 15:19:21 两次 IF8D-03（`/ci/app/requestNoSignalData`，无信号取离线码）均返回 `retCode=0000` 但 **`entryData=null`、只发 `exitData`**；按当时"已进站"状态这是设计行为，但按业务时间线卡应处于"已出站"、应发 entry+exit 双码。测试侧表现为"推码没有成功"（拿不到进站码）。

## 2. 根因分析
- 排查过程（关键日志，traceId 见括号）：
  1. 14:59:53 出站通知到达（设备 02430504，`handleDateTime=20261103145953`，traceId `9193582a...`）→ 状态 05 已出站，`lastTxnTime=20261103145953`。
  2. 15:00:01 进站通知到达（设备 0622040D，`handleDateTime=20261103145917`，traceId `2739754c...`）——**业务时间比上一笔出站早 36 秒、却晚 8 秒到达**（闸机侧排队/重发导致乱序）。ticket-server 日志显示当前库内状态已是 `lastTxnTime='20261103145953'`，但状态机照常受理（`isDuplicate=false, updateCount=1`），落库后 **`lastTxnTime` 从 145953 倒退为 145917**，`codeStatus` 05→04。
  3. 15:18 IF8D-03 查到状态 04 → 按 `IndustryDataOrchestrator#requestNoSignalData` 设计"已在站内只发出站码"→ `entryData=null`。
  4. 代码核查：`GateTicketHandler` / `GateTxnAssembler` 全文无 `handleDateTime`/`lastTxnTime` 单调性比较（grep 0 命中）；防护只有幂等（`isDuplicate`）与状态迁移白名单（05→04 是合法进站迁移，拦不住"旧进站覆盖新出站"）。
  5. 反向验证：15:24:56 补送一笔出站通知（设备 02450604，trxType=02）状态回 05 后，15:24:57 起 IF8D-03 立即返回双码（`entryData` 非空）——根因闭环。
- 根因结论：**IF1A-01 状态机按到达顺序应用通知、不校验 `handleDateTime` 与库内 `lastTxnTime` 的先后**，乱序迟到的旧进站通知可覆盖更新的出站结果并让时间字段倒退，状态错卡 04 导致 IF8D-03 只发出站码。

### 触发概率辨析（2026-11-03 与用户对齐）
- **本例触发是测试模拟器产物**：36 秒内跨 0622 / 0243 两站，真实乘客不可能——用户判断正确，不能拿本例当"生产会复现"的证据。
- **但防护对象是「送达乱序」而非「业务乱序」**：进出站物理距离只约束 `handleDateTime` 的先后（业务序天然正确），不约束**两台设备通知到达平台的先后**。状态机消费的是到达序，两者之间的缺口才是缺陷面。
- 真实场景可命中的向量（均不需要物理瞬移，只需「进站通知送达晚于出站通知送达」）：
  1. **同站进出**：同站 20 分钟窗是真实业务流（`08`/`09` 状态即为此设计），进出闸机是同一站点的两台设备，无跨设备送达序保证，行程仅几分钟，进站通知延迟几分钟即命中；
  2. **闸机离线缓存补传**：AFC 设备标准行为（本项目 IF8D-03 离线码链路本身就是为闸机离线场景设计的），离线闸机恢复后补传旧进站，期间乘客已从联网闸机出站；
  3. **通知重发沿用原 `handleDateTime`**：进站通知丢失后重发，重发到达时乘客已完成短途行程。
- 结论：概率低于"常规时序错误"，但非零；且一旦命中即码体错误、乘客过闸失败，属静默状态污染。

## 3. 方案对比
| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| 方案A（倾向） | `GateTicketHandler` 受理前加时序守卫：入参 `handleDateTime` < 库内 `lastTxnTime` 时判为 stale，记 WARN、落明细但**不推进 `QRCODE_STATUS`**，仍回 0000（对闸机幂等友好） | 改动小、只动受理入口；不动状态机白名单；对乱序/重发天然免疫 | 需定义 stale 通知的明细落库口径（建议照落、标记不推进）；同 `handleDateTime` 边界需定义（建议相等走原幂等判定） | 若闸机时钟漂移导致 `handleDateTime` 偏小，合法通知会被拒推进——需与设备侧确认时钟同步口径 |
| 方案B | 不改受理逻辑，闸机侧保证通知有序（发送端排队/序列号） | 平台零改动 | 依赖全部闸机厂商改造；现有设备已实测乱序（本例 44s 延迟）；无法防御重发旧报文 | 跨团队契约变更，落地周期长、漏一台设备就复发 |
| 方案C | 事后自愈：`@Scheduled` 扫 `QRCODE_TXN_DETAIL` 与 `QRCODE_STATUS` 不一致时按 `handleDateTime` 最大者重放状态 | 不拦任何通知 | 引入扫表任务与重放复杂度；窗口期内码仍错；违反"状态机在受理口收口"的既有约定 | 架构债扩大，与 outbox 语义纠缠 |

## 4. 决策与结论
- 选定方案：**只加 stale 观测告警日志（2026-11-03 用户裁决）**——`GateTicketHandler#warnIfStaleNotify`：`handleDateTime` < 库内 `lastTxnTime` 时记 WARN（带新旧值与卡号/设备），**不改受理行为**；生产若命中该 WARN 再回到 §3 评估方案A。
- 决策理由：用户判断本类乱序在实际场景概率低（进出站物理距离约束业务序）；§3 触发概率辨析表明送达乱序向量仍存在但无生产实证，先零行为风险地收集证据，避免为未证实场景引入时序守卫的设备时钟漂移误拒风险。
- 影响范围 / 关联模块：`ticket-server`（`GateTicketHandler.handleNotifyVerifyResult` 入口新增观测方法，纯日志）；不改对外契约、不改状态机行为。
