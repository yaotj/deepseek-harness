# IT-081 扣费单已 FAIL 终态时拒收成功回调，导致支付成功而扣费域永久停 PROCESSING

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-081` 一行。

## 1. 背景 / 现象

- 发现时间：2026-11-19（复核 IT-077 存量单时发现）
- 发现渠道：测试环境自查（支付域回调凭据与扣费域状态对账）
- 影响范围：`pay-sign-server` + `gate-txn-pay-server` 的「重试扣费」链路；测试环境现存 3 笔已处置，另有 2 笔存在重复收款风险的单待支付中心确认
- 现象描述：
  1. 3 笔单（`GT20261117144435890000081` / `GT20261117164231697000126` / `GT20261118143303624000081`）支付中心与 `PAY_TXN_DETAIL` 均为 `SUCCESS`，而 `GATE_TXN_PAY` 长期停在 `PROCESSING`，`PAY_CALLBACK_LOG.HANDLE_STATUS='MANUAL'`（原因「扣费订单状态同步失败」）。
  2. 后台日志实证（`GT20261117144435890000081`）：14:44:52 首次扣费被 pay-sign 拒 `9001 操作失败` → 扣费单置 `FAIL` 终态（日志「已置 FAIL 终态待人工核对（NEVER 重推）」）；14:45:53 支付中心推 `SUCCESS` 回调 → 同步扣费域返回 `8003 订单状态不允许收敛：FAIL`；14:47:01 周期重试把 `FAIL` 拉回 `RETRY` → 再次请求支付 → 支付域已 `SUCCESS` 返回幂等 → 扣费单被置 `PROCESSING` 后再无回调。

## 2. 根因分析

- 排查过程：`PAY_CALLBACK_LOG` 取 3 笔 `HANDLE_STATUS='MANUAL'` 行 → 按 `MERCHANT_ORDER_NO` 拉 VictoriaLogs（`app:"gate-txn-pay"`）→ 命中 `syncDebitStatus` 的 `8003` 应答与随后的周期重试 UPDATE 语句。
- 根因结论：**两条白名单互斥造成死结**。
  - `GATE_TXN_PAY.convergeDebitStatus`（回调收敛）白名单为 `INIT / PROCESSING / RETRY`，**不含 `FAIL`**，设计意图是「`FAIL` 为终态、拒绝被回调改写」；
  - 而 `FAIL` 同时又在周期重试的**可重入**白名单里（`INIT / RETRY / FAIL`），重试一发起就把它改回 `RETRY → PROCESSING`。
  - 于是「回调想改 `FAIL` 被拒」+「重试把 `FAIL` 改回 `PROCESSING` 后又没有回调」= 扣费域永久 `PROCESSING`，钱已收、状态不收口。
  - 触发前提：首次扣费请求在支付中心侧实际受理（或稍后成功），但 pay-sign 当时返回 `9001`，扣费域据此落了 `FAIL` 终态。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A 重放回调 | 从 `PAY_CALLBACK_LOG.RAW_BODY` 取原始成功报文重放，走正规幂等出口 | 零改代码、走同一链路、证据可查 | 只解决已发生的单 | 无（单已终态，重复收敛幂等） |
| B 调补款收敛接口 | 直接调 `/internal/gate-txn-pay/debit/converge` | 单点生效 | 语义是「补款收口」，用在普通扣费上语义不符 | 中（审计口径混淆） |
| C 人工 UPDATE | SQL 直接改 `DEBIT_STATUS` | 最快 | 绕过状态机、无审计 | 高（NEVER 采用） |
| **D 方向敏感白名单（选定）** | `convergeDebitStatus` 按入参分支：`SUCCESS` 方向允许 `INIT/PROCESSING/RETRY/FAIL`，`FAIL` 方向仍只允许三个中间态 | 从状态机根上解开死结；`SUCCESS` 仍不可被失败通知改写；改动集中在一条 SQL | 需同步两条守卫测试与契约文档 | 低（`SUCCESS` 保护不变，`FAIL→SUCCESS` 是资金事实前移） |
| E 把 `FAIL` 从周期重试白名单移除 | 让 `FAIL` 真成为不可重入终态 | 结构最简单 | 会关掉「补扣重试」能力（批量重试正靠 `FAIL → RETRY` 归一），业务不可接受 | 高 |

## 4. 决策与结论

- 选定方案：**A（重放回调，处置存量 3 笔）+ D（方向敏感白名单，根治）**。方案 E 明确否决。
- 决策理由：
  1. `FAIL` 的语义是「本次扣费请求被判失败」，不是「资金一定没动」。支付中心可能已受理并随后回调成功，此时 `FAIL → SUCCESS` 是资金事实前移，必须允许；
  2. 当年立「终态不可被回调改写」的判据，防的是 **`SUCCESS` 被迟到/乱序通知改写**，这一点在 D 中保持不变（`SUCCESS` 不在任何方向的前置白名单）；
  3. 周期重试的 `FAIL → RETRY` 归一（`prepareRecentRetry` / `prepareBatchRetry`）是补扣能力的底座，不能动。
- 落地细节：成功方向收敛时一并清空 `DEBIT_FAIL_CODE` / `DEBIT_FAIL_MSG`（成功单不应带失败归因）；补款收敛语句同步清空，两条语句仍**不合并**。
- 影响范围 / 关联模块：`gate-txn-pay-server`（`GateTxnPayMapper.xml` 一条 SQL + 两条守卫测试）；`pay-sign-server` 无需改动（`8003` 只在 `SUCCESS` 终态出现，该路径本就幂等返回 `0000`）。

### 5.3 端到端回归（2026-11-19 13:56，测试环境，2.1.14）

链路：`fep-app:30010 /ci/app/receivePayResult` → `pay-sign` → `gate-txn-pay`，真实落库三表；测试单 `QAIT081E2E20261119`（两表各造 1 行，验后已删，残留 0）。

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 造 `GATE_TXN_PAY=INIT`、`PAY_TXN_DETAIL=PROCESSING` | 起点就位 |
| 2 | 调 `syncDebitStatus(FAIL)` 模拟「首次扣费被判失败」 | GATE 落 `FAIL`，复现死结前提 |
| 3 | 走 fep-app 真实入口推 **SUCCESS** 回调 | 返回 `0000`；`PAY_TXN_DETAIL` → `SUCCESS/SUCCESS` 并回写支付中心单号与渠道单号；`GATE_TXN_PAY` → `SUCCESS`、`DEBIT_FAIL_CODE` 为 `NULL`；`PAY_CALLBACK_LOG` 1 行 `SUCCESS` —— **同一场景在修复前会返 8003 并卡住** |
| 4 | 再推**迟到 FAIL** 回调 | 返回 `0000`；`PAY_TXN_DETAIL` 与 `GATE_TXN_PAY` 均保持 `SUCCESS`；该条回调 `HANDLE_STATUS=MANUAL`（「支付订单不存在或状态不允许更新」）—— 成功态未被改写，按设计转人工 |

结论：修复在真实链路（三服务 + 三表）上闭环；成功方向可解开 `FAIL` 死结，失败方向仍不能覆盖 `SUCCESS`。

### 5.4 最佳实践改造（P1–P3，2026-11-19）

按「回调是快速路径、查询才是真相」的原则补齐三条链路，代码已落地、待发测试环境启用。

**P1 支付状态主动回查（双通道收敛）**
- 端点 `POST /internal/payment/compensatePayStatus` → `PaymentDomainServiceImpl.compensatePayStatus`；
- 扫 `PAY_TXN_DETAIL` 中 `PAY_STATUS IN ('INIT','PROCESSING','RETRY')` 且 `NVL(UPDATE_TIME,CREATE_TIME)` 早于 10 分钟的单（近 7 天分区、单轮最多 20 笔），逐笔调支付中心 `payQuery`：
  - `SUCCESS` / `FAIL` → 复用 `updatePayCallback`（白名单天然幂等，与在途回调并发安全）后再 `syncGateTxnPayStatus`；
  - `PROCESSING` / 查询失败 → 不动，等下一轮；
  - `9999 查无此交易` → 置 `FAIL`（中心从未建单）。
- **单轮 45 秒时间预算**：支付中心对钱包单 / 未知单的查询会跑到 10 秒超时（实测 9 笔耗时 42 秒），不设预算会让 web-admin 的 RPC 超时并记失败。预算用尽即停，剩余留待下一轮（cron 每 5 分钟 + 禁止并发，不会堆叠）。对应 `PaySignClient` 响应超时由 30 秒放宽到 60 秒（仅上限，其余接口毫秒级不受影响）。
- 调度：`paymentCompensateQuartzTask.compensatePayStatus()`，`0 */5 * * * ?`。

**P2 MANUAL 可运维**
- 人工重放端点 `POST /internal/payment/replayCallback?merchantOrderNo=<单号>`：取该单最近一条 `PAY_CALLBACK_LOG`，把 `RAW_BODY` 还原成 `ReceivePayResultReqDTO` 后重走 `receivePayResult`（兼容原始通知与内部 DTO 两种报文形态）；
- 每轮回查顺带巡检：近 2 天「该单最新一条回调是 MANUAL」的数量 > 0 时打 ERROR 并给出重放命令（**按单取最新**，否则已重放的单会因老 `MANUAL` 行长期误报）；
- 巡检 SQL（可直接给运维）：
  ```sql
  select *
    from (select MERCHANT_ORDER_NO, CALLBACK_STATUS, HANDLE_MSG, CREATE_TIME,
                 row_number() over (partition by MERCHANT_ORDER_NO order by CREATE_TIME desc, ID desc) rn
            from PAY_CALLBACK_LOG
           where TXN_DATE >= to_char(sysdate - 2, 'YYYYMMDD') and CALLBACK_TYPE = 'PAY')
   where rn = 1 and HANDLE_STATUS = 'MANUAL'
   order by CREATE_TIME desc;
  ```

**P3 跨域分叉核对**
- 端点 `POST /internal/gate-txn-pay/divergenceCheck` → `CrossDomainDivergenceService.check`；
- 扫本域近 48 小时收口的 `SUCCESS` 单，用 `PaySignClient.queryPayTxnBatch` 反查支付域：
  - 支付域非 `SUCCESS` 且 `REMARK` 含「补款」→ WARN（补款收口的口径差异，原单支付本未发生）；
  - 其余 → ERROR「跨域分叉，MUST 人工核对」。
- 只发现 + 告警，**NEVER 自动改支付域**：补款场景下擅自置 `SUCCESS` 会污染支付事实；直扣漏回调的单由 P1 自行收口。
- 调度：`gateTxnPayQuartzTask.checkDivergence()`，`0 15 * * * ?`。

**启用顺序（MUST）**：发 `pay-sign-server` → 发 `gate-txn-pay-server` → 发 `web-admin` → 执行 `web-server/web-quartz/src/main/resources/sql/web-quartz-payment-divergence-jobs-migration.sql` → **重启 web-admin**（Quartz 内存 JobStore）→ 在「监控管理 → 定时任务」先「执行一次」确认成功 → 再把 `status` 切 `1 → 0`。种子 SQL 刻意以 `status='1'`（暂停）插入。
