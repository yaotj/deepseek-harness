# IT-072 IF8A-35 未支付数未含「已进站未出站」行程

## 一、背景

2026-11-16 14:03 测试环境，调用方（`com.bestone.metro.service.ITP_Service`）请求 `POST /fep-app/ci/app/requestUserAccInfo`，对 thirdUserId `00523018`（卡 `0426090949000508`）返回：

```json
{"retCode":"0000","retMsg":"成功","unpaidCount":0,"failureCount":0}
```

但该卡 13:38:06 已在灵山卫（1325）进站、尚未出站（同日 IT-069 已核过这张卡的状态）。业主口径：**已进站未出站算一次未支付**，`unpaidCount` 应为 1。

库核对（测试库 QDITP thin 本机直连）：

| 表 | 事实 |
|---|---|
| `USER_ITP_REG_INFO` | `00523018` → 卡 `0426090949000508`，`DEL_YN=1` 有效 |
| `QRCODE_STATUS` | `CODE_STATUS=04`，`GATE_IN_STATION=1325`，`GATE_IN_TIME=20261116133806` |
| `QRCODE_TXN_DETAIL` | 仅 1 条进站明细（`ID=3088143`） |
| `GATE_TXN_PAY` | 该用户/卡近 3 个月 **0 条订单** |

## 二、根因

IF8A-35 `countUserAccInfo` 的数据源**只有 `GATE_TXN_PAY`**，`unpaidCount` 只数 `DEBIT_STATUS IN ('INIT','PROCESSING')` 的扣费订单。而**进站（IF1A-01）不产生扣费订单，出站才落 `GATE_TXN_PAY`**——所以「已进站未出站」这种有行程、无订单的状态，在旧口径下必然返回 0。这不是 SQL 写错，是统计口径缺了一路数据源。

连带暴露一处既有裁决的假设漏洞：ADR-D172（2026-10-16，业主明确要求「未完成行程不允许注销」）写「口径 1/2 已由 IF8A-35 覆盖，只需保留」，但 IF8A-35 实际没覆盖「未完成行程」——新卡首次进站时 `GATE_TXN_PAY` 无单，销户 8023 校验放行。本次修复**落实 D172 的本意**，不推翻它；D20「销户不校验进行中行程」的前提（"进站未出站通常已留下未结清订单"）在本场景不成立，见 ADR-D175。

## 三、方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| A（否决） | 进站时预插一条 `GATE_TXN_PAY` 占位单，出站再收敛 | 改动闸机主链路 + 影响扣费/重试/对账全链路，风险远超一个查询接口，否决 |
| B（否决） | gate-txn-pay-server 直连 `QRCODE_STATUS` JOIN 查询 | 分库后 `GATE_TXN_PAY` 在 QDITP_TXN、`QRCODE_STATUS` 在 QDITP_RIDE，`docs/domain/README.md` 禁止跨域直读对方表，否决 |
| C（本次采用） | IF8A-35 服务端聚合：account-server 查有效卡 → ticket-server 逐卡查状态 → 白名单命中则 +1 | 聚合收口在 IF8A-35 的 owner 服务，两次只读 RPC 符合域边界；fail-closed 保证查询失败不误放行销户 |

关键设计点：

1. **状态白名单与 owner 同源**：只认「已进站未出站」——开环 `04` / `81` + 入站码更新 `10`，复用 `QRCodeStatusEnum.isOpenLoop()` + `UPDATE_ENTRY`，与 ticket-server `SupplementStateRules.hasEnteredWithoutExit` 完全一致。**NEVER 写成「非闭环即可」黑名单**（`01` 无交易 / `03` 初始化 / `05` 已出站 都不算）。
2. **thirdUserId → CARD_ID 走账户域只读 RPC**：新增内部端点 `POST /queryActiveCards`（account-server `CardDataInternalController`），只返回 `DEL_YN` 有效的卡；调用方 `AccountClient.queryActiveCards`，返回空列表按 0 处理。
3. **失败 fail-closed**：任一 RPC 异常 / `retCode != 0000`（除 ticket `8004` 未注册用户视为「不在行程中」）→ IF8A-35 返 `9002`、两个计数归 0。理由：`primitive int` 在失败分支照样是 0，唯一能区分「无欠费」与「查询失败」的是 retCode；若把聚合失败当 0，销户会放行有进行中行程的用户（与 D172 冲突）。
4. **对外契约零改动**：`RequestUserAccInfoResult` 字段不变（无新字段），fep-app 与 APP 侧无需改报文映射；新增 DTO 均为 internal，不经 `parseBizData`。

## 四、决策

采用方案 C，改动清单：

- `model`：`QueryActiveCardsReqDTO` / `QueryActiveCardsResult`（内部 DTO）
- `account-server`：`AccountProfileService.queryActiveCards` + impl（`selectActiveListByThirdUserId`）+ internal controller 端点
- `rpc`：`AccountClient.queryActiveCards`
- `gate-txn-pay-server`：`GateTxnPayQueryServiceImpl` 构造器增 `AccountClient` / `TicketClient`（仍只做只读），`requestUserAccInfo` 内新增 `countInProgressTrips` 聚合
