# IT-088 行程订单通知 orderPayNotice 首推返 7004（站时间传了 8 位，APP 要求 14 位）

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-088` 一行。

## 1. 背景 / 现象

- 发现时间：2026-11-20 11:22（用户报「测试环境订单 `GT20261120110545409000081` 没接收到通知」）
- 发现渠道：用户反馈 + R6 §3.62 接口规范截图
- 影响范围：测试环境全部过闸行程订单的 APP 出向通知；红岛未发
- 现象描述：
  1. 订单 `GT20261120110545409000081` 支付链路正常：11:05:45 建单（双珠路→仙家寨，800 分），11:05:58 `INIT→PROCESSING→SUCCESS`；同笔 R6「卡片行程通知」`receiveCardTran` 已推成功（`retCode=0000`）。
  2. §3.62「行程订单通知」`/app/orderPayNotice` 全仓 0 命中——**该接口此前从未实现**（2026-08-25《全量接口实现进度报告》把它标成「✅ 已实现（路径匹配）」属脚本误报，该报告已判废删除）。
  3. 按 R6 表127 实现并部署测试后，**首推一律返 `7004 处理过程出现错误!`**；同一笔订单隔 5 秒重推即返 `0000 成功`。

## 2. 根因分析

### 2.1 真实根因（2026-11-20 13:49 由 APP 侧确认）

**`entryStationDate` / `exitStationDate` 传的是 8 位 `yyyyMMdd`，APP 侧要求 14 位 `yyyyMMddHHmmss`。** 解析异常被 APP 的对端兜底 `catch` 捕获，落通用错误码 `7004 处理过程出现错误!`。

- 取值源头没有错：闸机上送的 `handleDateTime` / `lastHandleDateTime` 本就是 14 位紧凑格式（实测值 `20261120124300`），落库 `GATE_TXN_PAY.IN_TIME` / `OUT_TIME`（VARCHAR2）仍是 14 位。
- 错在通知侧的格式化：旧实现按「字段名带 Date」把值截成前 8 位（`substring(0, 8)`），把 `20261120124300` 削成 `20261120`。
- 该错误与订单内容、金额、`orderStatus`、卡号、`deviceId` 全都无关——这正是下文变体探测「怎么改都还是 7004」的原因。

### 2.2 一次被推翻的误判（MUST 留档，避免后人重犯）

首版结论曾定为「APP 侧同一时刻也在处理支付中心推的支付结果，我方收敛后立刻首推撞进并发窗口」，依据是「首推 7004、隔 5 秒重推即 `0000`」这一稳定规律。**该结论已被推翻**，关键理由是**两次投递的 `bizData` 逐字相同**：同一份报文不可能靠时间自愈，所以差异只能来自对端状态机，不能来自我方报文。

纠正后的机制是：**APP 首次收到该 `tradeOrderNo` 时完整处理、在日期解析处抛异常返回 `7004`，但订单已被登记；第二次投递命中「重复通知」分支直接返回 `0000`（幂等短路），并不重新解析日期。**

⚠️ **由此带来一个必须核实的后果**：此前那批「重试成功」的订单（`GT20261120124208458000081`、`GT20261120124241865000508`、`GT20261120132558955000542`、`GT20261120134857598000081` 等）**很可能并未被 APP 正确处理**，`0000` 只是幂等短路的回执。已请 APP 侧核对这些单据是否真的落地。

### 2.3 排除项（2026-11-20 11:52~13:26 逐项取证）

| 怀疑点 | 取证 | 结论 |
|---|---|---|
| 端点不存在 | `OPTIONS .../ci/app/v2/orderPayNotice` → 200；伪造路径 → 404 | 端点存在 |
| 验签被拦 | 同款公共参数（`providerId=01` / `signType=00` / 空 `sign`）打同网关 `receiveCardTran` → `0000` | 验签不是原因 |
| 报文信封 / 字段缺失 | 表127 16 字段全带；变体探测（`orderStatus`=0/SUCCESS、金额 0/800、假单号/真单号、换用户卡号、`deviceId` 留空）**全部 7004** | 与字段有无无关（但与字段**格式**有关，见 §2.1） |
| 订单内容相关 | 同一笔订单首推 7004、重推 `0000` | 与订单内容无关 |
| 偶发 / 对端已修 | 11:56 起重推全部 `0000`，但新单首推仍 7004 | 稳定可复现 |
| 并发窗口 | 两次投递报文逐字相同 → 不成立 | 已推翻，见 §2.2 |

## 3. 方案对比

| 方案 | 思路 | 结论 |
|---|---|---|
| A. 首次推送前固定 sleep 3~5s | 简单 | ❌ 白等 5s，且对格式错误毫无作用（报文还是错的） |
| B. 失败只 WARN（同族现状） | 不动 | ❌ 通知直接丢，正是本次用户报障的形态 |
| C. 本地消息表 + 扫表补偿 | 建 outbox 表 | 最稳，但需建表 + 定时任务外移 + 生产 DDL，本轮成本过高 |
| **D. 修正站时间为 14 位（选用：真正的修复）** | 去掉 `substring(0,8)`，统一输出 `yyyyMMddHHmmss` | ✅ 打在根因上，首推即应收 `0000` |
| **E. 首推失败后按退避延迟重投 + 保留补偿入口（选用：兜底）** | `appNotifyScheduler` 调度 `5000/15000/30000` 三次 | ✅ 覆盖对端临时故障，不占通知线程池、不改表、不影响主链路 |

## 4. 决策与结论

- 主修是 D，兜底是 E，两者**不互相替代**：D 决定「正常情况首推就成功」，E 只保证「对端偶发失败时不丢通知」。
- **验收判据是「首推即 `0000`」**，NEVER 再用「重试成功」当修复证据——那恰恰是本轮误判的入口。
- 7004 **不加入成功码**（`isAccepted` 仍只认 `0000`）：它是兜底码，把它当成功就等于把「对端根本没正确处理」永久记成投递完成；`pay-sign` 那条链路配 `0000,7004` 是独立结论，**口径 NEVER 跨链统一**。
- 补偿入口 `POST /internal/gate-txn-pay/order-pay-notice/push` 保留，用于历史单与重试耗尽后的补推。
- `payTradeOrderNo` / `requestDebitNo` 暂按订单号兜底（gate 侧无支付域单号；本仓「不存在跨域 JOIN」是不变式，不读 `PAY_TXN_DETAIL`），待甲方明确语义后再定。

## 5. 实施

### 5.1 gate-txn-pay-server 2.1.22（2026-11-20，首版）

- `model/app/AppOrderPayNoticeReqDTO`：表127 16 字段逐字对齐。
- `gatetxnpay/notify/OrderPayNoticeNotifier`：`ProxyWebClient` + multipart 表单，受理判据 2xx 且 `retCode=0000`。
- `gatetxnpay/notify/GateTxnPayNoticeService`：仅终态推送 + 延迟重试（`appNotifyScheduler`）+ `repush(orderNo)` 补偿。
- 触发点四处：`requestPay` 默认成功分支 / `syncDebitStatus` / `convergeDebitStatusForSupplement` / `PaySignInitiator.converge` 落 FAIL（`updateOrderStatusFromPending` 返回 >0 才推）。
- 线程池：`appNotifyExecutor`（core 2 / max 8 / queue 500）、`appNotifyScheduler`（2 线程、守护）。
- 配置：`app.notify.order-pay-notice-url` / `-enabled` / `-timeout-ms` / `-retry-delays-ms`（默认 `5000,15000,30000`）；测试环境已注入大写下划线键 `APP_NOTIFY_ORDER_PAY_NOTICE_URL/_ENABLED`。

### 5.2 gate-txn-pay-server 2.1.23（2026-11-20，修根因）

- `OrderPayNoticeNotifier.resolveDate` 重写：14 位纯数字原样返回；8 位纯数字补 `000000`；`yyyy-MM-dd HH:mm:ss` 转紧格；无法识别时按原值上报并打 WARN（不臆造时间，也不静默丢）。
- 站时间格式抽成常量 `STATION_DATE_TIME_PATTERN`，类注释写明「MUST 14 位」与误判留档。
- 清掉两处过期日志文案「本次不补偿」（上层早已有退避重试，该文案会误导运维）；`GateTxnPayNoticeService` 类注释同步更正根因。
- 单测：`OrderPayNoticeNotifierTest` 5 → 7（新增「8 位补零点成 14 位」「带横线时间转紧格」「空值留空」），gate 模块 139 例全绿。
