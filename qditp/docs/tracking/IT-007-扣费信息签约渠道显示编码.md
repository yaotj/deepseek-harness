# IT-007 用户查询-扣费信息：列表「签约渠道」直接显示编码，未翻中文

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-007` 一行。
> 流程：先在索引表加一行 → 再建本处理文档 → 处理完回填索引「状态 / 处理情况 / 更新」。

## 1. 背景 / 现象

- 发现时间：2026-10-15
- 发现渠道：用户反馈 —— 「用户查询的扣费信息显示，列表的签约渠道要显示为中文」
- 影响范围：综管台（`web`）**用户查询 - 扣费信息**页（`views/trans/user/debit-detail/index.vue`）列表的「签约渠道」列；
  纯展示问题，不影响查询、退款等任何功能。
- 现象描述：该列直接渲染 `SIGN_CHANNEL_CODE` 原值（`03` / `04` / `07` …），看不出是什么渠道。

## 2. 根因分析

- 数据源链路：页面调 `GET /gate-txn-pay-server/page/gate-txn-pay`（`web/src/api/trans/userSearch.js` `listGateTxnPays`）
  → `gate-txn-pay-server` 的 `GateTxnPayPageController` → `GateTxnPayMapper.xml` 查 `GATE_TXN_PAY`，
  渠道字段是 `GATE_TXN_PAY.SIGN_CHANNEL_CODE`。
- 前端该列为 `<el-table-column label="签约渠道" prop="signChannelCode" />` —— **直接用 `prop` 展示原值**，没有接任何翻译器。
- 码表其实**已经存在**，只是散落在另外两个页面里各自定义了一份**完全相同的**副本：
  `views/trans/user/itp/index.vue`（「默认渠道」列）与 `views/trans/user/pay-channel/index.vue`（「支付渠道」列表）。
  扣费信息页没有接入 ⇒ 同一个渠道概念在同一套综管台里出现三种呈现（两页中文、一页编码）。
- 该码表在后端有权威对应物：`pay-sign-server` 的 **`PaymentVendorEnum`**（12 项，逐条一致）。
- 展示格式在仓库里也有统一约定：`utils/codeLabel.js` —— 「能翻译就显示 `编码-翻译`，翻译不到就只显示 `编码`，空值 `-`」。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| 方案A | 把码表抽成**共享唯一真源** `utils/payChannel.js`，扣费信息页接入，同时把 itp / pay-channel 两页的副本改为引用它 | 一份定义、三页一致；顺带消掉两份已有副本 | 需改 4 个文件 | 低 |
| 方案B | 只在扣费信息页再抄一份码表 | 改动面最小 | 变成**第 3 份**副本，日后必然漂移（本仓已有此教训） | 中 |
| 方案C | 后端 `gate-txn-pay-server` 在返回里带上中文名 | 前端零改动 | 要动一个与本次需求无关的服务并重新发布；且会与前端既有码表形成第二事实源 | 中 |

## 4. 决策与结论

- 选定方案：**方案A**。
- 业主裁定（2026-10-15，两项）：
  1. **显示格式 = 「编码-中文」**（如 `03-支付宝`），理由是「用户查询-ITP」「签约渠道管理」两页已是该格式，
     且保留编码便于对照报文排查；该格式也正是 `utils/codeLabel.js` 写死的统一约定。
  2. **只翻有权威码表的编码**；本仓查不到权威中文名的编码**原样显示编码**，不臆造名称（见 §5）。
- 落地改动：
  1. **新增 `web/src/utils/payChannel.js`**（唯一真源）：导出 `PAY_CHANNEL_LABELS`（12 项，与后端 `PaymentVendorEnum` 一一对应）
     与 `payChannelLabel(code)`（内部走 `formatCodeLabel`，固定 `编码-中文`）。
     文件头写明 **NEVER 与「发卡渠道」混用** —— `trans/user/alipay` 页的 `issueChannelLabels`（`01 正常渠道` / `07 支付宝`）
     取自后端 `IssueChannelCodeEnum`，码值空间不同。
  2. **`views/trans/user/debit-detail/index.vue`**：`签约渠道` 列由 `prop="signChannelCode"` 改为模板
     <code v-pre>{{ payChannelLabel(row.signChannelCode) }}</code>（列宽 110 → 130，容纳「编码-中文」）。
  3. **`views/trans/user/itp/index.vue`**：删掉本地 `channelLabels` 与 `channelLabel()`，改 import 共享表
     （模板 `channelLabel(row.channel)` → `payChannelLabel(row.channel)`）。
  4. **`views/trans/user/pay-channel/index.vue`**：同上（模板 3 处调用 + 1 处函数 + 1 处常量）。
  5. **`views/trans/user/alipay/index.vue`**：仅更新注释里对旧副本的引用路径（`trans/user/itp 页的 channelLabels`
     → `@/utils/payChannel` 的 `PAY_CHANNEL_LABELS`），避免注释指向已不存在的位置。
- **追加改动（同日 16:40，业主追加要求「12/15 分别精确对应卡种 0445 一日票 / 0448 多日计次票，也要处理」）**：
  1. **新增 `web/src/utils/cardType.js`**（卡种码表**唯一真源**）：`CARD_TYPE_LABELS`（16 项）+ `cardTypeLabel()`。
     该表由 `trans/user/itp`、`trans/user/alipay`、`trans/user/pay-channel` 三页**逐字节相同的副本**收敛而来
     （收敛时保持内容不变，是纯搬迁）。两套键的出处：2 位键取自后端 `CardTypeMapping.ISSUE_CARD_TYPES`
     （`12→0445`、`15→0448` …），4 位键取自后端 `CardTypeCodeEnum`。
  2. **`utils/payChannel.js` 新增 `signChannelLabel()`**（**仅供「签约渠道」这一列**）：
     先查支付渠道表、查不到再查卡种表、都查不到原样显示编码。**两张表保持独立、不合并** ——
     码值空间不同（`04` 在支付渠道是「微信」，卡种表里没有这个码），合并会造出错误译名。
  3. **`views/trans/user/debit-detail/index.vue`**：列改为 `signChannelLabel(row.signChannelCode)`。
  4. **itp / alipay / pay-channel 三页**：删掉各自的 `cardTypeLabels` 与 `cardTypeLabel()`，改 import 共享表
     （`pay-channel` 因此不再需要 `formatCodeLabel` 的 import，一并移除）。
- 影响范围 / 关联模块：仅 `web`（综管台前端）；**后端零改动**。

## 5. 数据实证与「未覆盖编码」的处置

对测试环境 `GATE_TXN_PAY.SIGN_CHANNEL_CODE` 做了全量分组统计（2026-10-15）：

| 编码 | 行数 | 是否有权威中文名 | 说明 |
|------|------|------------------|------|
| `03` | 33 | ✅ 支付宝 | `PaymentVendorEnum.ALIPAY("03")` |
| `04` | 11 | ✅ 微信 | `PaymentVendorEnum.WECHAT("04")` |
| `07` | 5 | ❌ | 5 笔**全部是支付宝出行单**（`ISSUE_CHANNEL_CODE=07`、第三方用户号为支付宝 10 位定长） |
| `NULL` | 4 | — | 空值，按约定显示 `-` |
| `17` | 4 | ⚠️ 代码里有定义但**不在支付渠道码表内** | `ticket-server` `GateResponseAssembler.SIGN_CHANNEL_OFFLINE = "17"`，注释「离线码的签约渠道代码（0x17）」 |
| `12` | 3 | ✅ **一日票**（16:40 已补） | 后端 `CardTypeMapping.ISSUE_CARD_TYPES`：`12 → 0445`；实测 3 笔的 `CARD_TYPE` 全为 `0445` |
| `15` | 1 | ✅ **多日计次票**（16:40 已补） | 后端同上：`15 → 0448`；实测该笔 `CARD_TYPE` 为 `0448` |

- **12 / 15 已处理（业主 16:40 追加要求）**：其精确对应卡种 `0445 一日票` / `0448 多日计次票` 在**后端有权威依据**
  （`CardTypeMapping.ISSUE_CARD_TYPES`，不是从界面标签反推的），故在「签约渠道」列**按卡种译名显示**
  （`12-一日票` / `15-多日计次票`）。实现为「支付渠道表 → 卡种表」两级兜底，**两张表不合并**（见 §4 追加改动第 2 点）。
- **仍未覆盖的只剩 2 个编码（`07` / `17`）**，本仓找不到权威中文名（已查：`docs/接口规范文档/*.docx` 全部提取正文、
  `docs/` 全量、`model/.../enums` 与各服务 `constant` 枚举）。
  - `07` 疑似支付宝出行渠道，`IssueChannelCodeEnum` 里 `07 = 支付宝`，但那是**发行渠道**空间，不能直接嫁接到签约渠道；
  - `17` 是「离线码」语义（非某家支付渠道），且不在支付渠道码表内。
- 按业主裁定 **只翻有权威依据的编码**：`07` / `17` 在界面上**原样显示编码**（`formatCodeLabel` 的既有兜底行为），
  **不臆造名称**；等业务侧给出正式中文名后再补。**后续 AI 不要凭猜测补名。**
- 代码空间边界的**反面教训**：`12` / `15` 与 `07` / `17` 看起来都是「本仓没定义的乱码」，
  但前者在后端 `CardTypeMapping` 里有权威对应、后者没有 —— 所以**不能因为「同列出现」就合并码表**，
  只能各自查各自的权威源。这也是本轮坚持两张表独立的原因。
