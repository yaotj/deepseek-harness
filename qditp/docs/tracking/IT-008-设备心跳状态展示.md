# IT-008 `F2F_DEVICE_STATUS` 只写不读：BOM/TVM 设备心跳在线状态无展示入口

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-008` 一行。
> 流程：先在索引表加一行 → 再建本处理文档 → 处理完回填索引「状态 / 处理情况 / 更新」。

## 1. 背景 / 现象

- 发现时间：2026-10-15
- 发现渠道：**用户（业主）需求**，并附带一条流程约束 —— 「用户要求在前端能做展示，**请先进行设计问询，我们设计好再执行**」。
- 影响范围：综管台（`web`）新增页面 + `face-pay-server` 新增只读接口 + 心跳写路径补算站码。**不改动任何既有对外契约**。
- 现象描述：`F2F_DEVICE_STATUS` 表记录 BOM/TVM 设备的心跳与在线状态，是判断「某台设备是否掉线」的唯一依据，
  但**整表没有任何读取出口** —— 既无接口、也无页面，运维只能连库查。
- 本问题**不是本轮才发现的**：历史设计文档 face-pay-refactor.md（已删除）曾登记这条待办
  （原文「`F2F_DEVICE_STATUS` 当前只写不读……补一个 `/page/face-pay/` 设备状态列表接口即可兑现价值」），
  原始裁决为 2026-09-09「暂不处理」。本条 IT 单是**解禁并兑现**，不是新开需求。

## 2. 根因分析

### 2.1 为什么只写不读

- 写侧：`TvmOrderController.notiDeviceHeard` / `BomOrderController.notiDeviceHeard`
  （`@PostMapping({"/notiDeviceHeard","/deviceHeartbeat"})`）→ `F2fDeviceHeartbeatService.recordHeartbeat`
  → `F2fDeviceStatusMapper.mergeHeartbeat`（`MERGE INTO` 上插下更），**心跳链路本身是通的**。
- 离线翻转：`F2fDeviceOfflineJob` 按 `offlineScanIntervalMs=60000` 扫表，把超时设备 `ONLINE_FLAG` 置 `0`。
- 读侧：`F2fDeviceStatusMapper` 里**已有三个查询方法** `selectByChannelAndDevice` / `selectHeartbeatTimeout` /
  `selectByChannel`，但**至今零调用方**；`F2fDeviceHeartbeatService` 之下没有任何 Controller 暴露它们。
- 结论：**不是数据缺失、也不是链路故障，纯粹是缺出口**。

### 2.2 库实测（`172.20.222.3:1521/AFCITPDB`，2026-10-15 17:00，读码 + 直连库双向确认）

| 事实 | 实测值 | 对设计的影响 |
|------|--------|--------------|
| 行数 | **21 行** | 数据量小、只存最新状态 ⇒ **不设「必须给检索范围」**（与订单分页接口的要求相反） |
| 渠道分布 | `02`(TVM) 3 台 / `03`(BOM) 18 台 | 页面筛选只需 `01/02/03` 三值；`01` APP 无设备 |
| 在线情况 | 在线 16 / 离线 5 | 统计卡有必要，且「离线优先」排序有实际价值 |
| `STATION_CODE` | **21 行全为 NULL** | 这是本次最大的缺口，见 §2.3 |
| 时钟 | `sessiontimezone=+08:00`；`LAST_HEARTBEAT_TMS` 由 Java `LocalDateTime.now()` 写入，与 `SYSTIMESTAMP` 相差个位数秒 | **无** `QRCODE_STATUS` 那种「前期 UTC、后期北京时间」的混用问题 ⇒ 不需要任何时区兜底 |

### 2.3 站码缺失的根因与可解性

- 两个心跳控制器历史上都传 `null` 给 `stationCode` 参数，落库 SQL 的 `STATION_CODE = NVL(SRC.STATION_CODE, 原值)`
  因此永远保留初始 NULL ⇒ **该列自建表起从未被写过**。
- **设备号 = 站码(前 4 位) + 站内序号**，该口径**不是本次新定**：ADR-D157（票卡分析站点感知）已裁定并核验过。
  实测 `06220701`→`0622` 辛屯、`03520801`→`0352` 双山、`11280801`→`1128` 世博园、`02200101`→`0220` 国际邮轮港；
  与 `COM_DEVICE_SYN_KEY` 对照 **19/21 台可对上**（`0243`、`0821` 两个前缀查不到站名，因 `STATION_INFO` 只有 196 个站）。
  ⚠️ **但此对照是「循环印证」、不构成独立验证** —— `COM_DEVICE_SYN_KEY.STATION_CODE` 由
  `KeySyncServiceImpl.saveDeviceKeyVersion` 用**同一条前缀规则**（`deviceId.trim().substring(0,4)`）写入，
  不是独立源。这行是**动手前**的初判，结论已由 §5.7 的真独立证据（`TBL_STATION_INFO` + `GATE_TXN_PAY`）取代。
- 关键机会点：**既有 MERGE 已经是 `NVL(SRC.STATION_CODE, 原值)`** ⇒ 只要服务层把推导值当参数传进去，
  **落库 SQL 一行都不用改**，21 行存量数据在各自下一次心跳（实测 BOM 20~30 秒、TVM 约 60 秒一次）后**自动自愈**，
  **不需要数据迁移**。

### 2.4 一个必须先排掉的码值陷阱

`02` / `03` 在不同码值空间里含义完全不同：

| 码值 | F2F 渠道空间（受理渠道 / 设备类型，同域两口） | 卡种空间 | 支付渠道空间 |
|------|------------------|----------|--------------|
| `02` | **TVM 自动售票机** | 后付费二维码 | — |
| `03` | **BOM 车站客服中心终端** | HCE 卡 | 支付宝 |

⇒ 页面用的渠道码表 **MUST 独立成文件**，NEVER 并进 `payChannel.js` / `cardType.js`。
（同类陷阱见 IT-007：`12`/`15` 同列混落两个码值空间。）这条是**动手前就判定的**，不是事后补的。

## 3. 方案对比

业主指令是「先设计问询」，故本节列的是**问询时给出的候选**与其后确认的裁决。

| 议题 | 候选 | 裁决 | 理由 |
|------|------|------|------|
| 菜单落位 | ① 系统监控下 ② 独立一级菜单 | **① 系统监控下** | 同目录已有 `2088` 服务状态监控、`2078` 卡池管理两个先例 |
| 车站列来源 | ① 心跳侧预处理并落库 ② 展示层按设备号现算 ③ 关联 `COM_DEVICE_SYN_KEY` | **① 心跳侧预处理** | 站码是**设备自身属性**、不是查询期派生量；落库后所有消费方（含日后对账、报表）共享同一口径；且既有 MERGE 天然支持、零 SQL 改动 |
| 在线判定 | ① 直读落库 `ONLINE_FLAG` ② 按 `LAST_HEARTBEAT_TMS + 300s` 现算 | **① 直读落库** | 页面口径与扫表口径完全一致，不会出现「库里 1、页面显示离线」的自相矛盾。代价是页面最多滞后一个扫描周期（60s），可接受 |

| 后端接口落位 | ① `face-pay-server` 新接口 ② `web-server`（web-admin） ③ `gate-txn-pay-server` | **① face-pay-server** | 业务查询接口 MUST 落业务模块的 `/page/**`；综管台只拥有 `sys_*`；数据表本就在 face-pay 域 |
| 车站列格式 | ① `站名(站码)` ② 只站名 ③ 只站码 | **① `站名(站码)`** | 已知部分站码在 `STATION_INFO` 无对应站名，带站码可保证「任何情况下都能定位到设备所属站点」 |
| 菜单名 | ① 设备心跳状态 ② 设备在线状态 | **① 设备心跳状态** | 与表名 `F2F_DEVICE_STATUS` 的心跳语义对齐，且避免与「设备状态」这类更宽的词混淆 |

**实现路径上还否决了一个自研方案**：本可再写一个 `substring(0,4)` 的私有方法，但读 ADR-D157 时发现
`F2fHceService.deriveStationCode` 已存在同规则实现 ⇒ 改为**抽出唯一真源** `F2fDeviceId.stationCode()`，让两处都指向它。

## 4. 决策与结论

- 选定方案：**按上表 7 项裁决全部落地；站码解析抽出唯一真源；只读接口；独立码表。**
- 落地改动：

  **后端 `face-pay-server`（新增）**
  1. `support/F2fDeviceId.java` —— 站码解析**唯一真源**：`stationCode(deviceId)` 取前 4 位、不足 4 位回 `null`，
     **刻意不 trim、不归一大小写**（设备号自身是复合主键的一部分，站码 MUST 与同一个原值同源；
     在此规整会出现「行键是补空格的、站码是规整后的」这种自相矛盾）。
  2. `api/page/F2fDeviceStatusPageVO.java`、`api/page/F2fDeviceStatusSummaryVO.java` —— 出参 VO。
  3. `service/F2fDeviceQueryService.java` —— 校验 + 分页参数夹取（默认 10 / 上限 100）+ `LIKE` 转义，
     用 `sealed interface PageOutcome` 表达「受理 / 拒绝」。
  4. `controller/page/F2fDeviceStatusPageController.java` —— `GET /page/face-pay/devices`，返回 `ResultVO`（管理后台形态）。
  5. Mapper 新增 `selectDevicePage` / `countDevicePage` / `selectDeviceSummary` 三方法及对应 XML。

  **后端（修改）**
  6. `support/F2fChannel.java` —— 抽出 `isSupported(String)`，`fromProviderId` 改为委托（消除重复判断）。
  7. `service/F2fDeviceHeartbeatService.java` —— 站码补算：调用方传空时用 `F2fDeviceId.stationCode(deviceId)` 兜底。
  8. `service/F2fHceService.java` —— 私有 `deriveStationCode` 收敛为**委托** `F2fDeviceId`，
     只保留「推不出来 → 空串」这一层本字段语义。

  **前端 `web`（新增）**
  9. `src/utils/f2fChannel.js` —— `CHANNEL` 码表**唯一真源**（**独立文件**，见 §2.4）。同一码值域两个展示口：
     **受理渠道**（`F2F_CHANNEL_LABELS` 三值齐全 + `f2fChannelLabel`，输出 `编码-字典值` 如 `02-TVM`）与
     **设备类型**（`F2F_DEVICE_TYPE_LABELS` 只收 `02`/`03` + `f2fDeviceTypeLabel`，输出**纯字典值** `TVM`/`BOM`）。
  10. `src/api/monitor/deviceHeartbeat.js` —— `GET /face-pay-server/page/face-pay/devices`。
  11. `src/views/monitor/device-heartbeat/index.vue`（`<script setup name="DeviceHeartbeat">`）——
      统计卡（总数/在线/离线/最近心跳）+ 筛选（设备类型/在线状态/设备编号模糊）+ 表格
      （序号/设备类型/设备编号/车站/在线状态/最近心跳/距上次心跳/累计心跳次数/最后更新）+ 分页 + 30 秒自动刷新；
      离线行整行淡红底（`:deep(.row-offline) td`）。

  **数据库**
  12. `web-server/sql/device-heartbeat-menu.sql` —— 已在 AFCITPDB 执行，落到 `menu_id=2091`。

- **MUST NEVER 回退的实现约束**（同 ADR-D171 §三，改代码前先看）：
  - 站码唯一真源是 `F2fDeviceId`；**`TvmResponses.topupOrderDetail` 的 `length() <= 4` 刻意不动** ——
    其 javadoc 自陈「照搬旧判据」，是对外应答契约的兼容，改成 `< 4` 会变更 TVM 充值单详情的 `singlePickupStationCode`。
  - 心跳写路径 **零 SQL 改动**，靠既有 `NVL` 实现（别再往 MERGE 里加推导逻辑）。
  - `LIKE` 关键字 MUST 由服务层转义 `% _ \`（反斜杠**先于**通配符），XML 侧配 `ESCAPE '\'`。
  - **排序与分页 MUST 放最外层**：单层 `FROM F2F_DEVICE_STATUS D LEFT JOIN STATION_INFO S`，
    不用「子查询内排序 + 外层 JOIN」—— 后者被优化器改走 hash join 会打乱顺序、分页错位，**单测看不出来**。
  - 汇总 `SUM` MUST 裹 `NVL`（空表 `SUM` 返回 `NULL` 而非 0）。
  - `resultType` 用「别名即属性名」，Oracle 折大写靠 MyBatis 大小写不敏感匹配，**这是既有可用形态、不是笔误**。
  - `utils/f2fChannel.js` **独立**，NEVER 并入 `payChannel.js` / `cardType.js`；两个展示口（受理渠道 / 设备类型）也 **NEVER 互换** —— 订单行可能是 `01`（APP 下单，不是设备）。

- 影响范围 / 关联模块：`face-pay-server`（新增 4 类 + 改 3 类 + Mapper）、`web`（新增 3 文件 + 菜单 SQL）。
  **既有对外契约零变更**（TVM/BOM 心跳应答、HCE 上报字段均未动）。

### 5.7 站码取值的独立佐证（重要：先排除了一个循环印证）

- **必须排除的伪证据**：`COM_DEVICE_SYN_KEY.STATION_CODE` 看似是「设备→站」的权威台账，实测 19/21 与设备号前 4 位逐字相同。
