# IT-013 琴岛通对账需求对齐评估

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-013` 一行。
> **需求解读、逐表对齐明细、差距清单、九项确认清单全部写在 `docs/business/recon-qdt.md`，本文不复制**，只记处理过程与决策。

## 1. 背景 / 现象

- 发现时间：2026-10-20（需求文件 2026-10-15 由琴岛通发出）
- 发现渠道：用户提供《对账.xls》要求评估对齐性
- 影响范围：recon-server 及全部对账相关域（gate-txn-pay / face-pay / daily-ticket / ticket-server / pay-sign）
- 现象描述：琴岛通要求按「消费 / 充值 / 互联互通（含 APPLY PAY）/ 互联网支付」四张日对账表与地铁对账，ITP 侧义务为「打包上传琴岛通」。现状：ITP 只向 ACC 传四类文件，与第三方渠道账单的 TXNDIFF 链路已设计落地；**无琴岛通上传通道、无反馈接收、无结算 / 可疑 / 调整 / 挂账台账、无互联互通与 Apple Pay 产品数据**。

## 2. 根因分析

- 排查过程：通读《对账.xls》五表 → 盘点 `docs/business/recon.md`、`recon-thirdparty.md` 及 recon-server / face-pay / pay-sign / ticket-server 源码与 schema → 全仓 grep `琴岛通|互联互通|Apple|微信|龙支付|qdt` 核实产品与渠道零命中 → 尝试直连业务库实查 `RECON_*` 表（本机网络不可达，未能实查，已在文档标注 MUST 现查）。
- 根因结论：不是代码缺陷，是**契约缺口**——①现有对账契约的对手方只有 ACC 与第三方支付渠道，从未包含琴岛通；②四张表所需的「结算 / 可疑 / 调整 / 挂账 / 补账 / 拒付」状态语义在全对账域不存在；③表 1 / 表 3 所需产品（实体卡消费、互联互通卡、Apple Pay）ITP 未接入。另有两个执行级不确定项：`RECON_THIRD_BILL` / `RECON_TXN_DIFF` 是否已在库内建好（文档记载「待 DBA 执行」）；`recon-thirdparty.md` §五 7 个外部契约项中 4 个仍是默认假设。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| 方案A：先做表 4，横切台账同步设计 | 复用 TXNDIFF + 渠道账单链路，补三个特殊交易维度导出与账单投递通道；同步设计可疑 / 调整 / 结算统一台账 | 投入产出比最高；台账一次设计覆盖四表 | 表 1/3 仍阻塞，整体闭环晚 | 口径会开完后表 1/3 结论可能推翻台账的部分字段设计 |
| 方案B：四表同时开工 | 按工作簿逐表实现上传 + 台账 + 反馈接收 | 一次性闭环 | 表 1/3 口径未定即动手，返工风险极高；违反「增量需求先问要不要做」 | 大概率白做 |
| 方案C：只做文件上传，台账用人工 Excel | ITP 仅产出「打包上传琴岛通」文件，差异 / 状态全人工 | 改动最小、最快上线 | 未结算上报、可疑调整跟踪不可自动化；与需求「有数据必须上报」的时效要求有差距 | 人工漏报风险 |

## 4. 决策与结论

- 选定方案：**待定（推荐 A）**——须先完成 §六口径确认再立项。本文不代为决策。
- 决策理由：表 4 是四表中唯一 ITP 侧数据基本齐全的，且已落地链路可复用；表 1/3 的产品口径未确认前任何实现都是猜测。
- 影响范围 / 关联模块：recon-server（编排 / FTP / 新增文件类型与台账表）、gate-txn-pay / ticket-server / face-pay（新增导出维度）、pay-sign（渠道映射）、web 综管台（若需对账结果呈现）。

## 5. 验证与回滚

- 验证方式 / 结果：未立项无实施；评估结论的证据链（源码 / schema / grep / 文档）已在 `recon-qdt.md` 逐条落明。后续实施验证 MUST 包含：库内实查 `RECON_*` 表存在性、上传琴岛通文件的回查日志判据（复用 `recon.ftp.verify-after-upload` 口径）、与 ACC 现有四类文件的账期一致性。
- 回滚预案：新增文件类型与 FTP 目标 MUST 配置驱动、默认关闭（参照 `recon.thirdparty.enabled` 先例），确保上线失败可一键回退到「只传 ACC」现状。
