# IT-014 补扣（含补款）支付方式留痕：原支付方式与实际支付方式

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-014` 一行。
> **登记轮（2026-10-20）**：用户明示「先记录问题，后续再实现」——本文档只登记需求、现状事实与约束，方案未裁决、代码零改动。

## 1. 背景 / 现象
- 发现时间：2026-10-20（用户两轮提出）
- 发现渠道：用户反馈（需求登记，非故障）
- 影响范围：后付费乘车码出站扣费全链路；本轮需求明确要求覆盖 **超时交易** 与 **单边交易**
- 需求原文（两轮）：
  1. 「补扣的支付方式需要记录。如果用户使用某个签约渠道支付未成功，补扣的时候可能使用另外的支付方式，需要记录原支付方式和实际支付方式」
  2. 「记录超时交易、单边交易，记录这部分的需求」＋「先记录问题，后续再实现」
- 现状事实（2026-10-20 读码 + DDL 实测；本文只引文件路径、不引行号，数字类以括注来源为准、引用前 MUST 现查）：
  - **原订单侧（`GATE_TXN_PAY`，owner `gate-txn-pay-server`，月分区表）**：落单时写的渠道类列只有 `ISSUE_CHANNEL_CODE`（发行渠道代码，兼作免密出账口分派键：`07` → alipay-pay-sign，其余 → pay-sign）、`SIGN_CHANNEL_CODE`（签约通道代码）、`PAYMENT_VENDOR`（支付厂商编码，钱包为 `0B`）、`CHANNEL_TYPE`（交易渠道类型，`01` 蓝牙）、`PAY_USER_ID`（钱包支付用户标识）——见 `gate-txn-pay-server/src/main/resources/sql/gate-txn-pay-schema.sql` 列注释。
  - **所有状态收敛语句只写状态与备注**：`gate-txn-pay-server/src/main/resources/mapper/GateTxnPayMapper.xml` 的 `updateStatusFromPending` / `updateStatusIfProcessing` / `convergeDebitStatus` / `convergeDebitStatusForSupplement`（补款收敛）/ `updateStatus` 均只 SET `DEBIT_STATUS` / `REMARK` / `UPDATE_TIME`；重试记账语句 `prepareBatchRetry` / `prepareRecentRetry` / `prepareUserRetry` / `updateDebitFailInfo` 只写次数、退避时刻与失败原因。**全表没有任何列表达「某次补扣实际使用的支付方式」。**
  - **免密代扣重试入口共用唯一出账口 `PaySignInitiator`**：运营 `retryPay`、定时补偿（`sys_job` 220 / 255 / 345，ADR-D149 / D154）、用户主动重试（`requestPayFailOrder` + `GATE_RETRY_QUEUE`，ADR-D169）、离线码金额补偿后重扣（`OfflineFareRecovery`，`DISCOUNT_CALC_STATUS='OFFLINE_FARE_PENDING'`），全部按 `ISSUE_CHANNEL_CODE` 分派 ⇒ **当前重试必然复用原签约渠道，「换渠道重扣」在代码里没有表达位**（`docs/business/gate-txn-pay.md`、`docs/domain/decisions.md` ADR-D169）。
  - **补款单侧（`SUPPLEMENT_ORDER`，owner 已迁 `face-pay-server`）**：`SIGN_CHANNEL_CODE` / `PAYMENT_VENDOR` 承自原订单；`PAY_CHANNEL_CODE` = 乘客在 APP 收银台选定的支付渠道（PayCenter 预下单时传入，下单时为空）；另有 `MERCHANT_ORDER_NO` / `PAYMENT_INFO` / `PAY_TIME`（`face-pay-server/src/main/java/com/chinasofti/huateng/facepay/entity/SupplementOrder.java`、`gate-txn-pay-server/src/main/resources/sql/supplement-order-schema.sql`）。**收敛回写原订单只写状态**：face-pay 经 `POST /internal/gate-txn-pay/debit/converge` 调 `convergeDebitStatusForSupplement`，SET 仅 `DEBIT_STATUS='SUCCESS'` + `REMARK` ⇒ 补款实际支付方式**不回写** `GATE_TXN_PAY`。
  - **支付侧明细表 `PAY_TXN_DETAIL`（owner `pay-sign-server` / `alipay-pay-sign-server`）只覆盖免密代扣路径**：按 `ORDER_NO` 记 `PAY_CHANNEL_CODE` / `PAYMENT_VENDOR` / `REQUEST_SIGN_SEQ` / `REQUEST_COUNT` 等（`pay-sign-server/src/main/resources/sql/pay-txn-schema.sql`）；补款走收银台 + collect-pay，`face-pay-server` 与 `collect-pay-server` 全仓无该表写入（2026-10-20 grep 实测）⇒ 换方式补扣成功在支付侧同样无统一留痕。
  - **对账影响面**：`ReconExportService`（gate-txn-pay-server）的 ITP.PAY 支付渠道段取 `SIGN_CHANNEL_CODE`；原订单若最终以另一渠道补扣成功，对账文件用哪个口径需与本需求一并定义。
- 需求范围内的两类交易（现状与普通出站同链路，无特殊分支）：
  - **超时交易**：`TRX_TYPE='03'`（超时出站），`OVERTIME_AMOUNT` 计入 `TOTAL_AMOUNT`；出站扣费 / 补扣 / 补款路径与 `TRX_TYPE='02'` 完全相同。
  - **单边交易**：`ORDER_EXP_TYPE` ∈ `1` 单边账(入) / `2` 单边账(出) / `3` 单边入站人工 / `4` 单边出站人工 / `5` 双段计费超时（`0` 为正常）；同样生成 `GATE_TXN_PAY` 扣费单并走同一套补扣 / 补款链路（IF8A-26 覆盖 `INIT` / `RETRY` / `FAIL` 原订单）。

## 2. 根因分析
- 排查过程：读 `gate-txn-pay-schema.sql` 列注释与 `GateTxnPayMapper.xml` 全部 UPDATE 语句 → 读 `SupplementOrder.java` 与 `supplement-order-schema.sql` → grep 确认 `PAY_TXN_DETAIL` 写入方只有 pay-sign 两模块 → 读 `docs/business/gate-txn-pay.md` 与 ADR-D169 确认重试入口共用出账口。
- 根因结论：**需求缺口而非代码缺陷**。原设计假定「一笔扣费订单自始至终只有一个签约渠道」：补扣 = 同渠道重试，无需另记；补款的渠道信息只落在补款单自身，不回写原订单。用户场景（签约渠道扣失败 → 换支付方式补扣成功）打破该假定后，系统没有任何位置能回答「这笔欠费最终用什么方式收的钱」。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| 方案A：原订单加列 | `GATE_TXN_PAY` 新增「实际支付方式」列（「原支付方式」是否另立列、还是从既有 `ISSUE_CHANNEL_CODE` / `SIGN_CHANNEL_CODE` 派生，待裁决）；免密重试发起时与补款收敛时按当次渠道回写 | 原订单一屏可见；运营查询 / APP 查询 / 对账直接可用；与现有收敛语句同点位修改 | 月分区表加列需 DDL 与生产二次确认；多个写入方（重试入口 + 补款收敛）都要改 | 漏改某个写入方即静默丢留痕；与既有两列语义重复易歧义 |
| 方案B：只落补款单 + 关联 | 不改 `GATE_TXN_PAY`；以 `SUPPLEMENT_ORDER.PAY_CHANNEL_CODE` 为「实际支付方式」，查询 / 对账时关联补款单 | 零 DDL、不动生产表结构 | 免密重试路径没有记录位（重试无补款单）；回答「最终用什么付的」要跨表 JOIN；对账抽取复杂化 | 口径分裂：两条补扣路径一个有一个无 |
| 方案C：补扣流水表 | 新建 `GATE_DEBIT_ATTEMPT`（每次扣费尝试一行：渠道 / 结果 / 时间 / 入口） | 完整按次留痕，支持审计与「第 N 次用什么渠道」 | 新表 + 分区 + 五个以上写入方，改动面最大；查询 / 对账要重新聚合 | 与现有「收敛只写终态」的心智模型冲突，回归面大 |

倾向（未裁决，NEVER 擅自实施）：先做 **A 的最小版**（只加「实际支付方式」一列 + 补款收敛回写）覆盖「换方式补扣」主场景；C 留作审计增强。

## 4. 决策与结论
- 选定方案：**待定（登记轮无决策）**。
- 决策理由：—
- 影响范围 / 关联模块：`gate-txn-pay-server`（表 + 收敛 / 重试写入方 + 对账导出）、`face-pay-server`（补款单 owner，补款收敛回写）、`pay-sign-server` / `alipay-pay-sign-server`（免密代扣明细）、`recon-server`（ITP.PAY 渠道口径）、综管台查询页（若要展示）。
- 待裁决问题（实施前 MUST 逐条有结论）：
  1. **「补扣」口径**：是否同时覆盖免密代扣重试与补款单两条路径（本文按两条都覆盖登记）。
  2. **「原支付方式」表达**：单列还是从既有 `ISSUE_CHANNEL_CODE` / `SIGN_CHANNEL_CODE` 派生。
  3. **回写时机**：免密重试「发起时」记还是「成功收敛时」记（与 `DEBIT_STATUS` 收敛同点位还是独立语句）。
  4. **对账口径**：ITP.PAY 支付渠道段继续用 `SIGN_CHANNEL_CODE` 还是改实际渠道（涉及 `ReconExportService`，MUST 与业主确认）。
  5. **码表口径**：`SUPPLEMENT_ORDER.PAY_CHANNEL_CODE`（收银台选定）与免密 `SIGN_CHANNEL_CODE` 不同源，落到同一列前 MUST 先定码表（码表唯一真源、各码值空间独立，NEVER 混用）。
- 已定约束（实施轮 MUST 遵守）：
  - 涉及扣款金额与免密代扣的改动 **MUST 提示人工复核资金安全**（`docs/business/gate-txn-pay.md` 编码约束）。
  - 改支付 / 订单 / 扣款链路 **MUST** 先读 `docs/architecture/transaction-and-consistency.md`；改 MyBatis XML **MUST** 先读 `docs/architecture/mybatis-oracle-runtime-traps.md`（`AGENTS.md` §5.1 路由表）。
  - `GATE_TXN_PAY` 是月分区表：新增唯一索引 **MUST** 含分区键 `TXN_DATE`；生产 DDL **MUST** 二次确认 + 先备份（`BAK_<表>_<日期>`），NEVER 直接在生产库执行（`AGENTS.md` §5.D）。
  - `convergeDebitStatusForSupplement` 白名单含 `FAIL`、回调侧 `convergeDebitStatus` 不含——差异是**有意的**（有守卫测试），改一侧会打挂另一侧。
  - SQL 正文禁写注释（Druid WallFilter `commentAllow=false`，`GateTxnPayMapper.xml` 文件头说明）；`TXN_DATE` 是 `VARCHAR2(8)`，NEVER 当日期类型用。
