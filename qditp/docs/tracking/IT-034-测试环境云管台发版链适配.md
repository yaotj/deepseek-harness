# IT-034 测试环境云管台发版链适配（含应用记录与实跑镜像脱节）

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-034` 一行。

## 1. 背景 / 现象

- 发现时间：2026-11-02
- 发现渠道：适配「红岛部署脚本 → 测试环境」时的现查（用户需求：同一套脚本适配测试环境，且走 CloudOS）
- 影响范围：测试环境 `k8s ns itp` 全部 27 个应用的发布动作、回滚点判定、版本号推进；`itp-ops.sh --env test` 整条云管台链
- 现象（三条，均 2026-11-02 现查）：

  1. **云管台链在测试环境完全不可用**：`lib/cloudos-auth.sh` 的 test profile 里 `CLOUDOS_RSA_PUBKEY_B64` 恒为空，`cloudos_env_init` 直接拒跑，所有 `--env test cloudos *` 命令停在认证前。文档当时的口径是「本机到 172.20.217.210 长期不可达，公钥一直没抓到」。
  2. **平台应用记录与实际运行镜像大面积脱节**：27 个应用里 **25 个** `metadata.container_image` 落后于 Pod 实跑。典型值：

     | 应用 | 平台 app.version | 平台 metadata tag | Pod 实跑 tag |
     |---|---|---|---|
     | fep-app | 2.0.66 | 2.0.66 | **2.0.105** |
     | ticket-server | 2.1.46 | 2.1.46 | **2.1.112** |
     | face-pay-server | 1.0.0 | 1.0.0 | **1.0.83** |
     | daily-ticket-server | 1.0.10 | 1.0.10 | **1.0.69** |
     | pay-sign-server | 2.0.69 | 2.0.69 | **2.1.15** |

  3. **测试平台无 `/images/build` 旧端点，但有 buildx 端点**：`POST /api/cloud/hcr/v1.0/images/build` 不可用；`POST /api/cloud/hcr/v1.0/images/buildx` 空体返回 `img.5`（参数错，说明路由存在）；前端 `/apps-image/static/js/mirror/build.<hash>.js` 的 `createImage` 确实 POST `/cloud/hcr/v1.0/images/buildx`。即红岛那套 buildx 通道在测试同样成立。

## 2. 根因分析

- **现象 1 的根因**：把「本机不可达」当成了「公钥不可得」，于是把公钥留空当护栏。实际 2026-11-02 本机到 172.20.217.210 已可达（办公网 en0），且测试平台登录页 `/platform/static/js/login/login.<hash>.js` 里 `encryptRSA` 内联的公钥与红岛**逐字符相同**（216 字符 / 1024 bit）——两套环境本就是同一把平台密钥，无需分别抓取。
- **现象 2 的根因**：测试环境的滚更一直是 `ssh k8s-master "kubectl set image ..."`（`hosts/k8s-master/k8s-deploy.sh` 就是这么写的），**完全绕开云管台**。云管台只在应用创建时写过一次镜像，之后 `metadata.container_image` 再没被更新；而 `app.version` 也只在平台侧发版时才会递增。于是平台记录停在「被绕开的那天」。
  这条根因对工具的影响是**破坏性的**，因为 `cloudos deploy` 的三个判断全部以 `metadata.container_image` 为基线：

  | 判断项 | 拿旧基线的后果 |
  |---|---|
  | 当前镜像 / 回滚点 | 显示成 2.0.66，回滚会指到半个月前的镜像 |
  | 「NEVER 同 tag 覆盖」 | 拦的是 2.0.66；真正在跑的 2.0.105 反而放行（重复滚一个同镜像） |
  | 版本末位 +1 | 从 2.0.66 起算，永远追不上 tag |
- **现象 3 的根因**：测试平台版本为 `E7501-V500R001B03D019-RC31`，镜像构建走的是较新的 buildx 通道；旧 `/images/build`（软件中心 fileFlag 路线）是更早版本的形态，测试环境已不再提供。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A 只在测试环境另写一套 cloudos 脚本 | 复制红岛脚本改常量 | 不动现有文件 | 立刻产生第二份实现，「改一处忘另一处」必然发生；与 §4.1「NEVER 引入冗余」冲突 | 高（长期） |
| B 现有脚本参数化 `--env`（本次采用） | 认证/项目/基础镜像按环境取；deploy 的基线改取实例实跑镜像 | 单一实现，红岛行为不变；测试一开即用 | 需改 4 个文件 + 文档回写 | 低 |
| C 先修数据：逐个用云管台重发一次把记录补齐 | 不改进脚本，只做数据修复 | 平台记录一次性变真 | 25 个应用逐个发版 = 25 次生产级写操作，且下次仍会漂移；不解决工具问题 | 高 |

## 4. 决策与结论

**选定方案 B**（2026-11-02 用户裁定，三点口径）：

1. **范围**：只打通「buildx 打镜像 + `cloudos deploy` 切 tag」这条云管台发版链；`k8s` 域保留为兜底，不删不改语义。
2. **版本口径**：`cloudos deploy` 默认把**目标镜像 tag 作为应用 version**（两套号从此对齐），不再从旧 version 末位 +1；需要另行指定用 `--app-version`。
3. **本轮只改脚本 + 只读预演**，真实写操作（推镜像 / 滚应用）等另行确认。

落地改动：

| 文件 | 改动 |
|---|---|
| `lib/cloudos-auth.sh` | 新增 `CLOUDOS_RSA_PUBKEY_SHARED`（两环境共用），test profile 不再留空；错误提示与账号口径按环境区分；`HONGDAO_RSA_PUBKEY_B64` 保留为兼容别名 |
| `itp-ops.sh buildx` | 新增 `--env hongdao|test`、`--base-image`；Harbor 项目 / 基础镜像按环境取（红岛 `itpb/jdk21:1.0.0`、测试 `itp/jdk:25`）；描述串带环境 |
| `domains/cloudos.sh` | 新增 `_app_running_image`（取实例实跑镜像，排除 istio sidecar）；`_deploy_plan` 以实跑为基线、version 默认对齐 tag、`version_id` 做 uuid 形态校验后按需省略；`health` 的 en9 检查限定红岛；usage / 已知缺口同步 |
| `docs/ops/构建与发布.md` | §〇 路径表拆出「测试·云管台链」；新增 §二·1 四步法 |
| `docs/ops/environments/测试环境.md` | 「构建与部署规则」补云管台链与脱节告警 |
| `docs/ops/environments/scripts/README.md` | §3.1 公钥结论更正；新增 §3.1.1 两环境 Δ 速查表 |
| `AGENTS.md` §5.C | 测试环境镜像构建位置由单一路径改为「云管台链首选 / k8s 链兜底」 |

附带修掉的隐藏坑（预演时暴露）：`_deploy_plan` 原 fallback 是 `metadata.version_id or app.package_version_id`，而**测试环境的 `package_version_id` 存的是镜像引用字符串**（`os-harbor-svc.default.svc.cloudos:443/itp/fep-app:2.0.66`）而非 uuid —— 直接塞进 `version_id`（varchar(36)）会 500。现改为只认 `metadata.version_id` 且必须是 32/36 位 hex 或 uuid 形态，否则省略该键（控制台镜像应用分支本就不发）。
