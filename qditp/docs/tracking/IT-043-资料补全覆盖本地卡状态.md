# IT-043 员工卡资料补全会覆盖本地卡状态

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-043` 一行。

## 1. 背景 / 现象

- 发现时间：2026-11-02 17:29
- 发现渠道：联调测试（修完 IT-045 后验证 ACC 资料补全，副作用暴露）
- 影响范围：`POST /employeeCard/query`（APP 查详情）触发的资料补全；`USER_ACC_EMPLOYEE_CARD.CARD_STATUS`
- 现象描述：卡 `13045027231` 在 ITP 本地为 `CARD_STATUS=1`（17:12 由 ACC 启用通知置位）。17:29 调查询接口后回读变成 `cardStatus=2`，而期间没有任何状态类通知或激活调用。

## 2. 根因分析

- 代码走查（`EmployeeCardPersistenceServiceImpl`）：
  - `refreshProfileFromAcc(target, source)`：`applyAccInfo(target, source)` 之后，仅当 `target.getCardStatus() == null` 才回退原值；
  - `applyAccInfo` 中 `target.setCardStatus(source.getCardStatus())` —— **无条件覆盖**。
- 触发条件：`queryEmployeeCard` 在 `employeeName` 为空时才调 `queryFromAcc`；IT-045 修复后该分支首次真正生效，于是把 ACC 侧状态一并写回。
- 为什么 ACC 侧是 `2`：17:06 走 APP 禁用（`actionFlag=0`）时状态**同步到了 ACC**；17:12 的「启用」走的是 ACC→ITP 的 `notify`，**只改 ITP、不回写 ACC**。两侧本就已漂移，资料补全把漂移结果反向灌回本地。
- 根因结论：资料补全没有区分「资料字段」与「状态字段」，把 ACC 的陈旧状态当权威回写了。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A. 补全只回填资料字段 | `applyAccInfo` 去掉 `setCardStatus`（或单列一个 profile-only 方法） | 状态真源唯一（仅 notify / activate 两条显式链路）；改动小 | 若 ACC 才是权威状态源，则本地可能落后 | 低 |
| B. 状态以 ACC 为准 | 保留覆盖，并把所有状态变更都同步 ACC | 两侧强一致 | 需要 `notify` 也回写 ACC（新增出向调用），改动大 | 中高 |
| C. 冲突时按时间戳裁决 | 比较 `UPDATE_TMS` 与 ACC 返回的时间 | 理论最严谨 | ACC 侧未必给时间戳，实现复杂 | 中 |

## 4. 决策与结论

- 选定方案：**A（已实施并已发布验证）**——资料补全只回填资料字段，`CARD_STATUS` 交回两条显式状态链路。
- 决策理由：当前 ITP 的状态变更有两条显式入口（ACC `notify`、APP `activate`），查询接口只是读操作，**读操作不应改状态**是基本原则。
- 代码改动（`EmployeeCardPersistenceServiceImpl`）：
  - 抽出私有 `applyProfileInfo(target, source)`：只 set `cardNo/employeeName/idCardNo/company/center/department/position/photoUrl`；
  - `applyAccInfo` = `applyProfileInfo` + `setCardStatus`，**仅供 `saveFromStatusNotify` 使用**（notify 是状态真源之一）；
  - `refreshProfileFromAcc` 改调 `applyProfileInfo`，删除原「状态为 null 才回退」的兜底（不再需要），并就地注释指向 IT-043 防回退。
- 影响范围：`account-server` 单类；无接口契约变化、无数据迁移。
- 需确认（未闭合）：ACC 与 ITP 谁是员工卡状态真源；若 ACC 为真源，需另行统一 `notify` 不回写 ACC 造成的漂移（本单只解决「读操作改状态」）。
- 测试说明：`account-server` **当前没有测试基建**（无 `src/test`、pom 无 test 依赖；`docs/business/account-employee-card.md` 「2 个测试类」的记载与工作树不符），本单未新增单测，验证靠编译 + 发布后实测；如需补，须先引入 test-scope 依赖（属独立决定）。

## 5. 验证与回滚

- 验证方式 / 结果：
  - 改动前复现（2026-11-02 17:12→17:29）：`notify` 置 `CARD_STATUS=1` 后，调查询接口（触发 ACC 补全）回读变 `2`，资料同时补全（`employeeName="一三零"`）。
  - 改动后判据（发布后执行）：查询前后 `CARD_STATUS` 不变；`employeeName/idCardNo/company/...` 正常补全；日志无新增 WARN。
  - 编译门：`mise exec -- mvn -o clean test-compile -pl account-server` → **BUILD SUCCESS**（2026-11-02 17:23）。
  - 发布：`account` 2.0.87 → **2.0.88**（镜像 digest `sha256:ccefe4e8e936484d8a5c446569c8bc2aa1e5a02362a677599693a28481ee76ef`，2 实例 imageID 与 digest 一致）。
  - 实测（17:33）：把 `13111111111` 造数为 `CARD_STATUS=3` + `EMPLOYEE_NAME=NULL`（刻意与 ACC 侧状态不同）→ 查询 2.09s 返回 `cardStatus=3`、`employeeName="一一一"`、photo 88020；库内 `CARD_STATUS` **仍为 3 未被覆盖**，资料正常补全 → **修复生效**。
- 回滚预案：代码改动无数据迁移，`git revert` 即可；已被改状态的卡用 `notify` 重推目标状态修正。
