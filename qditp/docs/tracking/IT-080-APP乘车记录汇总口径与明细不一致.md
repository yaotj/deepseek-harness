# IT-080 APP 乘车记录月度汇总口径与明细不一致

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-080` 一行。
> 状态：**已定位（只读排查，未改代码）**。2026-11-19 15:16 用户截图再次复现（同用户同卡，7 笔）。

## 1. 背景 / 现象
- 发现时间：2026-11-19 10:31（首现）；2026-11-19 15:16（本次截图，7 笔样本）
- 发现渠道：用户反馈（测试环境 APP「青岛地铁乘车记录」→「扫码过闸」）
- 影响范围：APP 月度汇总的 `totalPrice` / `count` / `totalDebit` / `totalDiscount` 四个展示值
- 现象描述：
  - 首现样本：总票价 14 / 次数 3 / 总实付 38.04 / 节省 3.96，明细只显示现金 1 + 17 + 0.04 = 18.04。
  - 本次样本：总票价 37 / 次数 7 / 总实付 54.11 / 节省 10.89（页面未展示超时费 24），
    「总实付」明显高于「总票价」；所有明细均标「已补款」，同时页面仍提示「存在未扣费订单」。

## 2. 根因分析
- 排查过程：
  - 用 VictoriaLogs 按金额反查到截图对应的请求：`traceId=6be738427f21d38c2f6c7f782441832b`，
    15:16:19 `fep-app → trans-query-server → gate-txn-pay`，用户 00523018 / 卡 0426090949000508 / 0441，
    窗口 20261101~20261130，响应与截图逐字一致。
  - 聚合 SQL 落在 `gate-txn-pay-server` 的 `selectTransStatistics`：
    `totalPrice = SUM(NVL(ORIGINAL_FARE, NVL(TRX_AMOUNT,0)))/100`；
    `totalDebit = SUM(NVL(TOTAL_AMOUNT,0))/100`；
    `totalDiscount = SUM(GREATEST(NVL(ORIGINAL_FARE,NVL(TRX_AMOUNT,0)) - NVL(TRX_AMOUNT,0), 0))/100`；
    `totalOvertime = SUM(NVL(OVERTIME_AMOUNT,0))/100`。
  - 只读查测试库 7 笔原行（单位分）：

    | 交易类型 / 扣费状态 | 笔数 | ΣORIGINAL_FARE | ΣTRX_AMOUNT | ΣOVERTIME_AMOUNT | ΣTOTAL_AMOUNT |
    |---|---|---|---|---|---|
    | 二维码后付费（TRX_TYPE=02，DEBIT_STATUS=FAIL） | 5 | 2700 | 1611 | 0 | 1611 |
    | 超时补款单（TRX_TYPE=03，DEBIT_STATUS=SUCCESS） | 2 | 1000 | 1400 | 2400 | 3800 |
    | 合计 | 7 | 3700 | 3011 | 2400 | 5411 |

  - 与响应勾稽：3700→37（总票价）、5411→54.11（总实付）、1089→10.89（节省）、2400→24（超时费）、count=7，全部吻合。
- 根因结论：
  1. `TOTAL_AMOUNT` 在扣费单组装处固定为 `TRX_AMOUNT + OVERTIME_AMOUNT`，是**应收金额**而非实收金额；
     统计时不按 `DEBIT_STATUS` 过滤，5 笔 FAIL 单的 16.11 元被计入「总实付」。
     真实扣款成功只有 2 笔超时补款单，合计 38 元。
  2. `totalPrice` 只累计 `ORIGINAL_FARE`，不含超时费；两笔超时单原价 3+7=10 元，实收 14+24=38 元。
  3. `totalDiscount` 用 `GREATEST(原价-交易额, 0)`，只反映正向折让 10.89；超时单中
     `TRX_AMOUNT > ORIGINAL_FARE` 的一笔 4 元差额被截断为 0，未进任何汇总项。
     因此 `54.11 - 37 = 24（超时费）- 10.89（折让）+ 4.00（被截断差额）= 17.11`，不能只靠「超时费 - 节省」配平。
  4. 展示层把应收额标成「实付」、把 FAIL 单标成「已补款」，与「存在未扣费订单」横幅并存，
     同源问题是汇总与明细不是同一口径，并非重复扣款或金额算错入账。5 笔 FAIL 的成因见 IT-079 / IT-081（云闪付协议分叉）。

## 3. 方案对比
| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A 修正统计 SQL | 按业务定义重算「实付」：只算 SUCCESS 的实收额，超时费单列；补齐被 `GREATEST` 截断的差额 | 汇总与资金口径一致 | 必须先裁定「实付」是否含超时费/补款单，涉及 4 个展示值与 APP 既有习惯 | 口径未定就改会引发新旧版本展示跳变 |
| B 仅修展示文案与标签 | 汇总标注「含超时费/未扣款应收」；FAIL 单不标「已补款」 | 改动小、无需改 DB 口径 | 数字仍与明细不相加，用户疑惑仍在 | APP 端改动，需与后端对齐字段语义 |
| C 仅记录不改 | 写入本档，保持现状 | 零风险 | 汇总继续误导用户 | 业务持续误解 |

## 4. 决策与结论
- 选定方案：**本次只定位，未改代码**；「总实付」的业务定义（是否含超时费、是否只算 SUCCESS）
  需用户 / 业务裁定后，再在 A 与 B 之间选择。
- 影响范围 / 关联模块：聚合口径唯一落点是 `gate-txn-pay-server` 的 `selectTransStatistics`；
  `trans-query-server` / `ticket-server` / `fep-app` 只做透传，APP 为最终展示方。
- 关联：IT-079（云闪付签约分叉）、IT-081（扣费终态与回调冲突）；差额定性依赖这两条背景，不由汇总 SQL 单独产生。

## 5. 验证与回滚
- 验证方式 / 结果：VL traceId 串联 4 跳响应一致；只读 SQL 七行分项求和与响应四个数值逐项相等；本次未改任何代码或数据。
- 回滚预案：无代码 / 数据改动，无需回滚；后续若按方案 A 修改 SQL，须保留旧口径 SQL 以便回滚并用同一 traceId 重放比对。
