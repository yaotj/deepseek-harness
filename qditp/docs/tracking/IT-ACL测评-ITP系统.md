### 一、身份鉴别

#### 序号 1｜部分符合（0.5 分）｜重要
**控制项 a）** 应对登录的用户进行身份标识和鉴别，身份标识具有唯一性，身份鉴别信息具有复杂度要求并定期更换

**现场核查情况**  
使用用户名及口令鉴别；未发现空口令、弱口令账户；已开启密码复杂度策略（长度8-20位，含大小写字母、数字、特殊字符）；**未开启口令定期更换策略**。

**整改方案**

| 步骤 | 操作 |
|---|---|
| 1 | 在 `web-server/web-admin/src/main/resources/application.properties` 新增配置项 `user.password.expireDays=90` |
| 2 | 修改 `SysPasswordService.validate()`，在密码校验通过后增加有效期检查：从 `sys_user` 表读取 `pwd_update_time`，若距今天数 > `expireDays` 则抛出 `PasswordExpireException`，前端引导重置密码 |
| 3 | 首次发版后，对现有用户批量执行 `UPDATE sys_user SET pwd_update_time = SYSDATE - 90 WHERE user_id > 0`，使所有存量用户立即触发首次到期 |
| 4 | 在 `SysLoginService.login()` 中捕获 `PasswordExpireException`，返回特殊状态码（如 `PWD_EXPIRED`），前端展示"密码已过期，请修改密码" |
| 验证 | 用旧密码登录验证是否提示过期；修改密码后确认 `pwd_update_time` 更新为当前时间 |

**现场核查情况**

#### 序号 4｜不符合（0 分）｜关键
**控制项 d）** 应采用口令、密码技术、生物技术等两种或两种以上组合的鉴别技术对用户进行身份鉴别，且其中一种鉴别技术至少应使用密码技术来实现

**现场核查情况**  
被测系统**仅使用用户名及口令**进行登录，未使用两种以上方式进行登录。

**整改方案**

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1 | **方案选型**：推荐采用「JWT 签名密钥（密码技术）+ 口令」作为双因子方案。具体做法：在现有 JWT 签名基础上，引入动态 OTP（一次性密码），登录时除用户名/口令外还需输入动态口令 | OTP 可对接企业微信消息推送或短信，降低开发成本 |
| 2 | 在 `SysLoginService.login()` 中增加 OTP 校验步骤：登录成功后、签发 Token 前，校验 OTP 是否匹配；OTP 验证通过后清除 OTP 记录（一次性使用） | 位于 `login()` 方法的最后一步 |
| 3 | 新增 `SysOtpRecord` 表（或复用 `sys_user` 扩展字段），存储 OTP 值、生成时间、有效期（建议 5 分钟） | Oracle 建表语句附在方案文档中 |
| 4 | 前端 login 页增加 OTP 输入框；管理后台运维入口（如跳板机）可选配白名单豁免 | 前端在 `web/` 目录下 |
| 5 | **替代方案**（如业主不接受 OTP）：接入堡垒机作为统一运维入口，堡垒机本身已实现双因子，ITP 侧仅需收敛访问源 IP | 运维习惯变更，需业主决策 |
| 验证 | 用正确用户名/口令但无 OTP 登录，确认被拒绝；用正确 OTP 登录，确认正常签发 Token |

### 二、访问控制

#### 序号 5｜不符合（0 分）｜重要

**现场核查情况**  
**未对登录的每一个用户分配账户和权限**，仅存在账户 admin，管理员权限。

**整改方案**

| 步骤 | 操作 |
|---|---|
| 1 | 梳理 ITP 系统实际使用角色（运维管理员、审计员、普通操作员等），在 `sys_role` 表中为每种角色创建独立记录 |
| 2 | 在 `sys_user` 表中为每位实际操作人员创建唯一账号，关联对应角色（`sys_user_role` 中间表） |
| 3 | 在 `sys_menu` 表中按角色划分菜单权限，确保各角色只能访问其职责范围内的功能 |
| 4 | admin 超级管理员账户保留但不使用（不登录操作），日常运维使用专用账号 |
| 5 | 在 `docs/ops/environments/scripts/itp-ops.sh` 中记录各角色账号清单，纳入配置基线 |
| 验证 | 用不同角色账号登录，确认各自只能访问授权菜单；admin 账号确认无日常登录记录 |

**现场核查情况**

| 4 | 安全标记功能作为中长期建设目标，本期可先建立标记体系框架，标记赋值分步完成 | 中长期 |

### 三、安全审计

#### 序号 14｜不符合（0 分）｜一般
**控制项 c）** 应对审计记录进行保护，定期备份，避免受到未预期的删除、修改或覆盖等

**现场核查情况**  
审计日志本地保存，未作备份保存。

**整改方案**

| 步骤 | 操作 |
|---|---|
| 1 | 在 `logback.xml` 中将 `maxHistory` 从 60 天增加到 **180 天**（满足等保三级审计记录留存不少于 6 个月的要求） |
| 2 | 新增定时任务（Quartz Job），每日凌晨将前一日日志文件打包压缩并上传至第二中心 NFS 存储（与数据异地备份同链路） |
| 3 | 上传完成后在本地标记已备份，防止重复上传；上传失败时记录错误并告警 |
| 4 | 对日志文件增加不可变属性（如 `chattr +a` 或在 Oracle 中创建只读视图），防止被意外删除或修改 |
| 5 | 审计日志的访问增加权限控制：只有安全审计员角色可查看/下载 |
| 验证 | 手动触发日志备份任务，确认文件已上传至第二中心；尝试删除日志文件，确认被拒绝 |

**现场核查情况**
