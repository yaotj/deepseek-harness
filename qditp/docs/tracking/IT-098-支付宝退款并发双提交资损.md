# IT-098 支付宝退款并发双提交（唯一索引建在随机单号上，同单并发可双退款）

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-098` 一行。
> 重档判据：资金一致性风险（并发双退款 = 直接资损）+ 库表索引口径变更。
> 关联：[全库 10 轮 Review 报告 §三 P0-1](../reviews/代码全面Review-2026-11-22/全库10轮代码Review报告.md)。

## 1. 背景 / 现象
- 发现时间：2026-11-22（全库 10 维度代码 Review 第 2 轮「事务与数据一致性」）
- 发现渠道：只读代码审查 + 逐行核验
- 影响范围：`alipay-pay-sign-server` 两条退款链路——旧表 `ALIPAY_REFUND_LOG`（`AlipayPayRefundServiceImpl`）与新表 `ALIPAY_REFUND_TXN_DETAIL`（`AlipayTxnRefundService`）
- 现象描述：退款幂等只靠「同一 ORDER_NO 存在在途明细即拒绝」的 `count` 状态短路（先查后插、无库层互斥），而唯一索引 `UK_ARL_REFUND_ORDER_NO` / `UK_ARTD_REFUND_ORDER` 建在**每次随机生成**的退款单号上。两条并发请求各生成不同单号 → 都能插入 → 都出网调支付中心 → **同一原订单两笔真实退款，直接资损**。
- 重要核定：Review 报告原指 `PaymentRefundService.java:88`，但该类业务文档已明确为「零调用方的回滚位、NEVER 在其上加能力」（`docs/business/alipay-channel.md` §退款）。经全库 grep 核实——真实在跑的是上面两条链路，故本项修复针对现行链路，**未改回滚位**（与 §5.0「NEVER 只修不记录」及最小改动原则一致）。

## 2. 根因分析
- 排查过程：
  - `grep PaymentRefundService` → 唯一注入方 `AlipayTripPaymentServiceImpl`（回滚位），`requestRefund` 现行入口是 `AlipayPaymentInternalController` 的 `AlipayPayRefundService` / `AlipayTxnRefundService`。
  - 读 `AlipayPayRefundServiceImpl:62` / `AlipayTxnRefundService:73` → 均为 `rejectIfProcessingRefundExists`（count 查询）后 `insert`。
  - 读 `alipay-refund-order-no-unique-migration.sql:52` / `alipay-pay-txn-schema.sql:239` → 唯一索引前导列都是随机单号；存量归一脚本注释自认「挡不住同一 ORDER_NO 并发双提交」。
  - `docs/domain/decisions.md` 退款条目亦明确记录该缺口「尚未做」。
- 根因结论：**先查后插的幂等短路在 READ COMMITTED 下存在竞态窗口；缺少「在途态按业务键（ORDER_NO）唯一」的数据库层互斥。** 随机单号上的唯一索引只防「同一退款单号重复落库」，防不住「同一原订单并发发起两笔不同单号的退款」。

## 3. 方案对比
| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A：只靠应用层加锁 | service 内 `synchronized` / 进程锁 | 零 DDL | 多实例部署无效（生产多副本），仍双退款 | 高——不解决根因 |
| B：唯一索引建在 ORDER_NO 全列 | `UK(ORDER_NO, ...)` | 简单 | 终态后无法再次部分退款（同单合法二次退款被拦） | 中——误伤业务 |
| C：虚拟列部分唯一索引（选定） | `CASE WHEN 在途 THEN ORDER_NO ELSE NULL` + 朴素唯一索引 | 只约束在途态、终态释放；多实例有效；ADR-D135 已验证可行 | 需执行 DDL；存量若已有同单多笔在途会 ORA-01452 需人工核 | 低——前置检查 0 行即可建 |
| D：号段/序列单号改确定性 | 由 orderNo 派生 refundOrderNo | 让现有索引生效 | 破坏对外单号语义、跨渠道对账口径 | 中——契约变更 |

## 4. 决策与结论
- 选定方案：**方案 C**（虚拟列两步法，ADR-D135）+ 代码层 fail-closed 兜底。
- 决策理由：
  - 只有数据库唯一索引能在多实例下真正互斥；应用层锁无效。
  - 部分唯一（终态 NULL）保留合法的部分退款语义，不误伤业务。
  - ADR-D135 已实测：MCP 校验器拒裸 `CASE` 索引，但接受 `ALTER TABLE` 里加虚拟列 + 对虚拟列建朴素唯一索引。
  - 两条链路在途态口径不同，刻意分开处理：旧表插入即 `PROCESSING`（只约束 PROCESSING + DELETE_FLAG='0'）；新表插入是 `INIT`、随后 `markRequesting` 转 PROCESSING，故覆盖 `INIT/PROCESSING/RETRY` 三态。
- 影响范围 / 关联模块：
  - `alipay-pay-sign-server`：两 Service + `RefundLogRepository` + 两个 Mapper + 两份迁移 SQL + 单测。
  - 不发布、不执行 DDL（用户裁决：先出方案+代码，人工复核后再发版）。
  - 新表唯一索引刻意建为 GLOBAL（不带 `TXN_DATE` 分区键），保证跨分区同单在途唯一；NEVER 改 LOCAL。
