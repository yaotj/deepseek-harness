# IT-044 员工卡停用后 APP 无法启用（状态机不闭环）

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-044` 一行。

## 1. 背景 / 现象

- 发现时间：2026-11-02 16:47
- 发现渠道：联调测试（员工卡 Test_012 停用 / 启用连测）
- 影响范围：电子员工卡的 **APP 自助停用 → 再启用**路径；ACC 通知路径不受影响
- 现象描述：
  - 16:44:20 ACC 推 `cardStatus=2`（停用）→ `0000`，库内 `CARD_STATUS` 由 `1` 变 `2`（traceId `485737f4c303cdba2c0fc0b54a2df2df`）
  - 16:47 模拟 APP 调 `POST /ci/app/employeeCard/activate`，`{"cardNo":"13111111111","actionFlag":1}` → **`2002 电子卡当前状态不允许激活操作`**
  - 即用户一旦停用，就再也无法在 APP 内自助启用

## 2. 根因分析

- 代码事实（`EmployeeCardServiceImpl`）：
  - 激活（`actionFlag=1`）前置白名单只收 `CARD_STATUS=3`，目标态 `1`
  - 禁用（`actionFlag=0`）前置白名单只收 `CARD_STATUS=1`，目标态 **`2`**
  - `CARD_STATUS` 语义（DDL 列注释 `account-server-schema.sql`）：`1`-启用 / `2`-禁用 / `3`-未启用 / `4`-注销
- 根因结论：**迁移图缺边**。`1 → 2`（停用）合法、`3 → 1`（激活）合法，但停用后的 `2` 不在激活白名单里，`2 → 1` 这条边不存在，状态机不闭环。
- 对照：ACC 通知路径（`saveFromStatusNotify`）**无前置状态校验**，实测两次均可行——16:38 ACC 直接推 `1` 把 `3` 改 `1`；**16:56 ACC 推 `1` 把已停用的 `2` 改回 `1`（`0000`，查询回读 `cardStatus=1`，traceId `7a82d2b940c1a8c57762d22ed0081a55`）**。说明「启用」在系统里有两条互不校验的入口，**只有 APP 侧那条断了**。
- **2026-11-02 17:31 追加实测（双锁死）**：停在 `2` 的卡想走「重新开卡」也不行——`notify` 推 `3` 时 APP 侧返 `已有电子员工卡`，整批失败（fail-fast，ITP 不落库）；随后 APP `activate` 仍 `2002`。即**停用后 APP 侧两条路（启用 / 重新开卡）都被堵死**，只能等 ACC 下发 `1`。此事实加重了本单优先级。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A. 激活白名单加 `2` | 允许 `2 → 1`，语义区分「首次激活」与「重新启用」 | 改动小（白名单 + 单测），APP 自助闭环 | 需明确 `2` 与 `3` 在展码/闸机侧语义是否等价 | 中；需与甲方对齐状态机 |
| B. 停用目标态改 `3` | 停用即回「未启用」 | 复用现有激活白名单 | 与「未启用」语义冲突（用户已开通过，不是未启用）；且与 ACC 下发的 `2` 不一致，会造成两侧状态发散 | 高，倾向否 |
| C. APP 不提供启用 | 明确「启用只能由 ACC 下发」，APP 侧去掉启用入口或提示联系管理员 | 零代码改动、语义最保守 | 产品体验差；需改 APP 契约与话术 | 低（技术）/ 中（产品） |

## 4. 决策与结论

- 选定方案：**A（启用白名单加 `2`，允许 `2 → 1` 重新启用）** —— 2026-11-02 用户裁定；同一裁决确认「补一条状态机单测」。
- 决策理由：状态机校验用白名单是既定规范（`AGENTS.md` §4.2），修法应在迁移图上补边，而不是绕过白名单。`EmployeeCardStatus.DISABLED` 的枚举注释本就写着「ACC 侧停用，**可再激活**」，缺的只是白名单这一条边。
- 实施内容（2026-11-02）：
  - `EmployeeCardStatus` 新增 `activatableFrom(Integer)`：白名单只放 `3`（首次激活）与 `2`（重新启用），`1`/`4`/`null` 一律拒绝，注释标注 NEVER 改成「非终态即可」；
  - `EmployeeCardServiceImpl.activateEmployeeCard` 的激活前置改用该方法；
  - 新增单测 `EmployeeCardActivateWhitelistTest`（**account-server 首个测试类**，此前无 `src/test`）：7 条用例覆盖 `3→1`、`2→1`、`1→1`、`4→1`、禁用 `2→2`、禁用 `1→2` 与白名单枚举，`mvn -o test -pl account-server` → **Tests run: 7, Failures: 0**。
- 影响范围 / 关联模块：account-server（`EmployeeCardServiceImpl` 激活分支 + `*StatusMachineTest`）；`04-电子员工卡.md` Test_012 断言。
- 需甲方/ACC 确认：① 停用（`2`）与未启用（`3`）在展码、过闸、优惠政策上是否同样「不可用」；② ACC 侧是否会在 APP 之外自行下发 `1`（16:38 已实测发生一次），若会，则「用户手动激活」的产品预期本身需要复核。

## 5. 验证与回滚

- **2026-11-02 17:41 发布并实测通过**：`account` 2.0.88 → **2.0.89**（镜像 digest `sha256:dfa3218770b2b49b8e4a424e3b5e74650df9e83bea0c41c07d0c6db7d00324cc`，2 实例 imageID 与 digest 一致）。真实链路连测（卡 `13111111111`）：
  1. `actionFlag=0` 停用 → `0000`，库内 `1→2`，日志 `STATUS`/`2`/`APP请求禁用员工码成功`（17:42:11）；
  2. `actionFlag=1` 启用（修复前必返 `2002`）→ **`0000`**，库内 `2→1`，日志 `STATUS`/`1`/`APP请求激活员工码成功`（17:42:13）。
  → **「停用 → 启用」闭环成立**；单测侧 `EmployeeCardActivateWhitelistTest` 7 条全绿。
- 回滚：`cloudos deploy account .../itp/account:2.0.88 --app-version 2.0.88 --yes`。

- 验证方式 / 结果（现状复现，2026-11-02）：
  - 停用：ACC 推 `2` → `0000`，`update USER_ACC_EMPLOYEE_CARD set CARD_STATUS='2' ...` 1 行，日志 `STATUS`/`2`
  - 启用：APP `actionFlag=1` → `2002`；查询接口回读 `cardStatus=2`（未被改动）
- 修复后判据：`2 → 1` 返 `0000`；主表 `CARD_STATUS=1`；日志表新增 `STATUS`/`1`；且 `4`（注销）仍 MUST 拒绝激活（终态不可复活）。
- 回滚预案：白名单改动无数据迁移，`git revert` 即可；已在 `2` 态的卡无需回滚（本就是合法态）。
