# IT-104 综管台三级等保合规扫描（5 轮）差距清单

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-104` 一行。
> 重档判据：安全风险（身份鉴别 / 访问控制 / 审计留存 / 个人信息）+ 跨模块（web-server + web + deploy）整改，且涉及合规结论。
> 详细取证与逐条证据见 [综管台三级等保 5 轮合规扫描](../reviews/2026-11-23-综管台等保三级5轮合规扫描.md)。

## 1. 背景 / 现象
- 发现时间：2026-11-23
- 发现渠道：业主提出「综管台需通过三级等保测评」，按 GB/T 22239-2019 第三级做 5 轮只读合规扫描
- 影响范围：`web-server`（web-admin / web-framework / web-common / web-system / web-quartz）+ `web/` 前端 + `deploy/k8s` web 部署件 + 综管台 nginx 反代链路
- 现象描述：5 轮共 60 个检查项，**不符合 31 项 / 部分符合 16 项 / 符合 13 项**。按现状直接送测，8.1.3.2（通信传输）与 8.1.4.1 a/c/d（口令复杂度、传输防窃听、双因子）、8.1.4.2 b（默认口令）、8.1.4.3 c（审计保护）必然判不符合。
- 一票否决点：全链路 HTTP 明文、`admin/ry` 默认口令 `admin123`、Druid `admin/123456`、`token.secret` 26 位弱口令、Swagger 与 `/profile/**` 匿名可读、审计日志 60 天自动删除且可一键清空、`/page/**` 无鉴权。

## 2. 根因分析
- 排查过程：只读逐行取证（`SecurityConfig`、`TokenService`、`SysLoginService`、`SysPasswordService`、`LogAspect`、`logback.xml`、`CommonController`/`FileUploadUtils`/`XssFilter`、`ResourcesConfig`、`application.properties`、`deploy/k8s/*.yaml`、`web/nginx.conf`）；复用了 admin-web 测试库 `06`（A9/B15/B16/B17）与 IT-096/IT-097 的既有结论，未重复登记。
- 根因结论：
  1. **框架默认值直接上生产**：RuoYi 默认的弱口令策略（5~20 位）、Swagger、Druid 控制台、`/profile/**` 匿名、`TestController`、devtools 全部未按等保要求裁剪。
  2. **部署面缺 TLS 与边界收敛**：ingress `tls: {}`、nginx `listen 80`、内部 `service.*.url` 全 http；`05-secret-template.yaml` 存在但 Deployment 用明文 env，未 `secretKeyRef`。
  3. **审计按「可用」而非「可取证」设计**：`maxHistory=60`、清理接口直开、IP 取 sidecar 回环、异步写无补偿。
  4. **个人信息未做脱敏分层**：`password` 哈希随 `LoginUser` 返回、列表/导出明文手机号，XSS/上传链可放大到批量导出。
  5. **管理要求无载体**：制度、机构、人员、建设、运维五类材料在仓库内无任何落点。

## 3. 方案对比
| 方案 | 思路 | 优点 | 缺点 | 风险 |
|---|---|---|---|---|
| A 全量整改后送测 | 8 项 P0 + 16 项部分符合全部收口，再请测评机构进场 | 一次通过概率最高；不留「整改中」扣分 | 周期长（含双因子选型与开发） | 双因子方案需业主定（短信/OTP/证书/堡垒机） |
| B 技术 P0 先改 + 制度材料并行 | 6 类纯配置/代码项先落地，双因子与 `/page/**` 等业主裁决项挂账，同步准备 14 类制度材料 | 复用现有发版链，2~3 个迭代可完成技术面；材料与技改不互相阻塞 | 首测可能带 2~3 个不符合项，需复测 | 复测次数增加；`/page/**` 若仍缓则属明确不符合 |
| C 仅出差距报告，不改 | 本次扫描即交付，整改另立项目 | 零风险、零成本 | 不具备送测条件 | 与「通过测评」目标直接冲突 |

## 4. 决策与结论
- 选定方案：**待业主裁决**。建议 B（技术 P0 先改 + 制度并行），并将双因子与 `/page/**` 作为两个必须由业主拍板的决策点。
- 决策理由：P0 中 6 项属既有代码/配置，改动面清晰、可随常规发版灰度；双因子涉及账号体系与运维习惯，`/page/**` 已有 2026-11-09「暂缓」裁决，二者不宜由技术侧自行推进。
- 影响范围 / 关联模块：`web-server`（SecurityConfig / TokenService / SysPasswordService / logback / CommonController / MimeTypeUtils / ResourcesConfig）、`web`（token 存储、构建）、`deploy/k8s`（ingress TLS、Deployment env→Secret、探针、容器加固）、业务模块 `/page/**`（若裁决整改）。
- 红线提示：涉及 `token.secret`、数据库口令的改动 MUST 同步 `docs/ops/environments/跨环境共性.md` §三「敏感值真源」表；本项目 2026-10-26 裁定「仓库明文即唯一真源」，与等保 8.1.9 密钥管理要求冲突，**须业主重新裁决后再动**。

## 5. 验证与回滚
- 验证方式 / 结果：本轮为只读扫描，未做任何修改，无验证结论。整改后按项验证：TLS/安全头用 `curl -I` 抓响应头；默认口令与权限用 admin-web 测试库回归；审计留存查滚动文件与库表归档；上传/XSS 用靶场页面复测；`/page/**` 用不带 token 的 curl 断言 401。前端改动 MUST 走 `web-admin-development-workflow.md` §5.1 验证四件套。
- 回滚预案：配置类（TLS、env、探针、日志）按发版回滚点回退；代码类（SecurityConfig、TokenService、脱敏）随镜像 tag 回滚。改 `token.secret` 会使全部已签发 JWT 失效，须低峰期执行并提前通知运营。
