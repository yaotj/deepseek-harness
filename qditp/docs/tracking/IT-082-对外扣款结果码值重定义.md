# IT-082 对外扣款结果码值重定义（0/1/2 三值）

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-082` 一行。
> 状态：**阶段一已发测试环境并业务验证通过；阶段二（线下补款「1」的产出）用户裁定暂缓**。
> 发版记录（2026-11-19）：SVN r1333（源码）、git 0ee3cfaf（docs+pom）；
> ticket-server 2.2.15 / trans-query 1.0.31 / alipay-pay-sign 1.1.69，仅测试环境（itp ns），红岛未发。
> 用户裁定码值：`0`=线上支付成功、`1`=线下补款人工成功、`2`=失败（0 和 1 都是成功态）；
> 当前「不产出 1」——出口只发 `0`/`2`。

## 1. 背景 / 现象
- 发现时间：2026-11-19
- 发现渠道：用户口径澄清（旧 ITP 二维码后付费订单状态码）
- 影响范围：对外 APP 的 `debitRequestResult` 字段（扣款结果），涉及 3 个服务 + 1 处 SQL 过滤 + 对外接口清单文档
- 现象描述：
  - 旧 ITP 二维码后付费订单状态码：`0`=支付成功（自动扣费成功 / 重试扣费成功 / 主动补款成功，三种都归 0），
    `1`=线下补款人工通过综管台处理成功。**0 和 1 都是成功态**。
  - 新仓现状：对外 `debitRequestResult` 只有两值——`"SUCCESS".equals(authoritative) ? "0" : "1"`，
    即 `0`=成功、**`1`=失败/在途/未知的全部兜底**。支付失败响应给 APP 的就是 `1`。
  - 冲突：`1` 在旧 ITP 是成功态（线下补款人工成功），新仓却拿它表示失败，语义相反。
  - 用户裁定：失败专用 `2`；旧 `1`（失败兜底）从响应值域里退出，留给「线下补款人工成功」。
  - 新仓 DB 侧 `GATE_TXN_PAY.DEBIT_STATUS` 是字符串枚举 `INIT/PROCESSING/RETRY/SUCCESS/FAIL`，
    **没有数字码值，也没有「线下补款人工成功」独立状态**；补款结清成功也落 `SUCCESS`，
    唯一来源是 `GATE_TXN_PAY.REMARK` 里的 `补款单号:<SP...>` 痕迹。

## 2. 根因分析
- 排查过程：
  - 全仓 grep `? "0" : "1"` + `debitRequestResult` 定位全部映射出口（见 §4 影响面）。
  - 对齐 DB DDL 注释与对外接口清单，确认新仓从未实现「1=线下补款人工成功」这一语义。
  - 确认补款结清在 `GATE_TXN_PAY.REMARK` 写 `补款单号:<SP...>`
    （`SupplementPayCenterFlow.setRemark("补款单号:" + orderNo)` → `convergeDebitStatusForSupplement`），
    而直扣成功的 REMARK 是 `支付结果回调收敛：SUCCESS` / `扣费已被…受理` 等，二者可区分。
  - `GateTxnPayListDTO` 已带 `remark` 字段，两个 `TransRecordAssembler` 都能拿到该信号，无需改 model。
- 根因结论：新仓把旧 ITP 的双成功态（0/1）压成了单成功态（0），再用 `1` 兜住一切非成功，
  导致「1」的语义与旧系统相反；要恢复旧语义必须引入第三值并给出「线下补款」的判定信号。

## 3. 方案对比
| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A 最小改动（推荐） | 只把失败/在途的兜底从 `1` 改成 `2`，`0` 仍=所有成功（含补款结清）；`1` 先不在响应里产出，作为旧语义保留位 | 改动面小；不动解约口径（APP 页签 `1` 的原筛选语义需单独确认）；无需新字段 | `1=线下补款人工成功` 暂时无法对外产出，旧系统该状态在新侧仍不可见 | 若 APP 侧已按 `1`=失败做展示，会漏判；须 APP 同步 |
| B 完整三值 | `0`=直扣成功、`1`=补款结清成功（按 REMARK 判定）、`2`=失败；同步改请求侧过滤 | 完整对齐旧 ITP 语义 | 需判定信号（REMARK 字符串）稳定可靠；跨 3 服务 + SQL + 文档 + 测试；牵动解约页签筛选 | REMARK 文案变更即口径漂移；补款结清与直扣的边界要 CA 复核 |
| C 不改代码只记档 | 把口径写入文档/记忆，代码保持 | 零风险 | 失败对外仍是 `1`，与旧语义相反的问题未解决 | 业务继续误解 |

## 4. 决策与结论
- 选定方案：**方案 B（完整三值），分两阶段落地**（阶段一先解决「失败不能是 1」，阶段二补 `1` 的产出）。
- 决策理由：用户明确裁定三值语义并给出失败码 `2`；只做 A 会把「1=线下补款人工成功」永久悬空。
- **2026-11-19 15:43 用户追加裁定**：「线下补款这个可以先不做，先把出口做了」「当前不再产出 1 的状态」。
  即**只实施阶段一**，且出口只发 `0`/`2`，`1` 暂不产出；阶段二（线下补款人工成功的数据来源）整体暂缓。
- **阶段一实施结果（已落地，未发版）**：
  - **4 个**出口的映射由 `SUCCESS ? "0" : "1"` 改为 `SUCCESS ? "0" : "2"`：
    ① `ticket-server/src/main/java/com/chinasofti/huateng/ticket/query/TransRecordAssembler.java`
    ② `trans-query-server/src/main/java/com/chinasofti/huateng/transquery/query/TransRecordAssembler.java`
    ③ `alipay-pay-sign-server/src/main/java/com/chinasofti/huateng/alipay/paysign/service/impl/payment/PaymentQueryService.java`
    ④ `trans-query-server/src/main/java/com/chinasofti/huateng/transquery/query/AlipayTravelQueryHandler.java`
       `mapDebitStatusToResult` —— **支付宝出行真实活链路**（`AlipayTravelQueryController.findTravelDetail`
       → `TransQueryServiceImpl` → `AlipayTravelQueryHandler`，列表 181 行 + 详情 280 行共用）；
       ③ 那个 `PaymentQueryService` 端点全仓零调用方，但既然是对外映射也一并改，避免死代码复活时口径回退。
       全仓 grep 确认生产代码已无残留 `? "0" : "1"`。
  - 测试同步：`trans-query-server/.../TransRecordAssemblerTest`（FAIL/PROCESSING/null→2 + 新增「永不产出 1」守卫）、
    `alipay-pay-sign-server/.../TravelDetailDebitResultTest`（同上，7 例）、
    `trans-query-server/.../AlipayTravelDetailFromGateTxnPayTest`（活链路详情 FAIL→2，8 例）。
  - 验证：trans-query-server 25 例、ticket-server 248 例、alipay-pay-sign-server 155 例全部 0 失败（合计 428 例）；
    改 model 后需先 `mvn -o install -pl model` 才编得过 alipay 模块（本地 model jar 未含最新坐标的既有环境问题）。
- **请求/响应同源收口（2026-11-19 16:00，用户追加，与出口改造同批发版）**：
  - 背景：阶段一后响应侧发 0/2，而请求侧筛选只有 0/1，`2` 传回会因 `<choose>` 无 `2` 分支而**静默不过滤返全量**。
  - 查证：解约「未结清」校验走 `countFailedOrder`（硬编码 `DEBIT_STATUS != 'SUCCESS'` 的独立 SQL），
    **与 `Debit_Result_Filter` 不是同一条 SQL**——历史守卫注释「与解约口径一致」只是语义对齐，不是代码共享，
    故给筛选加 2 分支不会破坏解约/APP 页签。
  - 改动：`gate-txn-pay-server/src/main/resources/mapper/GateTxnPayMapper.xml` 的 `Debit_Result_Filter`
    把分支改为 `debitRequestResult == "1" or == "2"` → 都筛 `DEBIT_STATUS != SUCCESS`；
    `1` 保留兼容存量 APP（请求侧 `1` 从来是筛选入参、不是响应值，无语义冲突）。
  - 测试：`GateTxnPayMapperSqlTest` 新增 `debitResultFilterAcceptsTwoAsFailureCodeForResponseRoundTrip`
    （selectTransList/countTransList 两条语句分别验 `2`/`1` 都渲染出非成功过滤、`0` 仍只筛成功）。
  - 验证：gate-txn-pay-server 122 例全绿（SQL 守卫 16 例）。
  - 发版：gate-txn-pay-server 2.1.18→**2.1.19**，SVN r1334 + git 3e5f823e，仅测试环境；
    buildx amd64 + cloudos deploy 切流。红岛未发。
  - 验证：gate 单测 122 例全绿（SQL 守卫 16 例）；Pod 级 deploy updated=3/ready=3 全为 2.1.19
    （k8s 里 2 个旧 2.1.18 是 RS desired=0 的孤儿 Pod、无 Endpoint 引用、不接流量）；
    **业务实测**（NodePort 30019 `/ci/gateTxnPay/app/requestTransList`，thirdUserId=0700001448）：
    传 `debitRequestResult=2` 返 4 条全 FAIL、`=0` 返 1 条 SUCCESS、`=1` 返同样 4 条 FAIL（存量兼容）——
    响应回显的 2 已可直接当筛选入参，同源收口完成。
- 码值定义（对外 `debitRequestResult`，三值）：
  | 值 | 语义 | 新仓判定 |
  |---|---|---|
  | `0` | 支付成功（自动扣费 / 重试扣费 / 主动补款） | `DEBIT_STATUS=SUCCESS` 且 REMARK 不含 `补款单号:` |
  | `1` | 线下补款人工通过综管台处理成功 | **新仓暂无此状态**：需新增「线下补款」标记（见 §5 阶段二前置） |
  | `2` | 失败（或未收口） | 非 `SUCCESS` 一律 `2`（含 FAIL/INIT/RETRY/PROCESSING/null） |

**当前实际产出（阶段一后）**：只有 `0` 和 `2`；`1` 永不产出。

## 5. 验证与回滚
### 阶段一（失败从 1 改 2，先解语义相反）
- 改 §4 清单中 1~4、6、7 的失败返回值与过滤；`1` 暂不产出（保留位）。
- 验证：单测覆盖 `SUCCESS→0`、`FAIL/INIT/RETRY/PROCESSING→2`；
  集成验证一个真实 FAIL 订单对外返回 `2`、一个 SUCCESS 订单返回 `0`；
  解约页签按旧 `1` 查询的订单不消失（或确认 APP 已同步改传 `2`）。
- 回滚：3 个服务按版本回退 + XML 还原；对外字段值域变更需 APP 侧联合发布，回滚须双侧同步。

### 阶段二（补 1 的产出，需前置条件）
- 前置：产品或甲方定义「线下补款人工通过综管台处理成功」在新仓的**数据来源**。
  当前新仓补款单 `SUPPLEMENT_ORDER` 由 APP 发起（在线补款）、状态 `PENDING/SUCCESS/FAILED`，
  综管台只有只读页，**没有人工线下补款写状态入口**（见 `docs/testing/admin-web/旧ITP交易管理功能分析-2026-11-18.md` §对标结论）。
  可选做法：① 在 `GATE_TXN_PAY` 增独立的结清来源列（DDL，另立项）；
  ② 复用 `REMARK` 标记但须约定固定前缀并加单测守卫（文案漂移即失败）。
- 落地：判定信号确定后，在三个出口统一加「补款结清 → `1`」分支，并同步 SQL 过滤与文档。
