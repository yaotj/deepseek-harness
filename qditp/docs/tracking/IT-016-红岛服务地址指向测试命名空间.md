# IT-016 红岛各模块 `service.*.url` 仍指向测试环境 `itp` 命名空间，全链路 RPC DNS 解析失败

## 1. 背景 / 现象

- **发现时间**：2026-10-23 13:06（联调侧 Apifox 手工调用）
- **发现渠道**：用户反馈（红岛环境联调）
- **影响范围**：红岛生产集群命名空间 **`itpb`** 全部有跨模块调用的业务模块（17 个 Deployment，明细见 §4）；当前实际被触发的是 `fep-app` 的 APP 入口链路
- **现象描述**：`POST http://172.120.2.11:31936/ci/app/requestApplication` 返回 HTTP 200，响应体为

```json
{"retCode":"b3b1dc9f-fb5a-49b2-8f18-934c56ddd1df","retMsg":null,"data":null}
```

`retCode` 呈 UUID 形态 = 踩了 `resource/micro/web` 的全局异常处理器 `ApiErrorResponse`（其构造函数只做一件事：`retCode` 置为 `UUID.randomUUID()`，`retMsg` / `data` 留 null）。**它不是业务错误码，不能按错误码表解读。**
当天同一现象复现 3 次（12:53:02 / 12:57:07 / 13:06:12），三次请求的 `content-length` 分别为 1147 / 1220 / 1220，**body 不同但失败点完全相同**，说明与报文内容（`bizData` / `sign` / `timestamp`）无关。

## 2. 根因分析

- **排查过程**（工具：`kubectl -n itpb logs`；VictoriaLogs 侧无数据，原因见 §4 末「连带发现」）：

  1. 按 `requestApplication` 检索入口 Pod 日志，命中当次请求原文（`content-length=1220`、boundary `825201597684061372852562` 与联调侧完全一致）：

     ```
     2026-10-23 13:06:12  f1b0b9bf93d7eb36cf56a0cce73e5f65  FirstFilter          receive request url=/ci/app/requestApplication method=POST
     2026-10-23 13:06:14  f1b0b9bf93d7eb36cf56a0cce73e5f65  ApiErrorResponse     http://172.120.2.11/ci/app/requestApplication
             java.lang.RuntimeException: org.springframework.web.reactive.function.client.WebClientRequestException:
             Failed to resolve 'account-n4ba6-svc.itp.svc' [A(1)]
     2026-10-23 13:06:14  f1b0b9bf93d7eb36cf56a0cce73e5f65  BodyCacheFilter      response body:{"retCode":"b3b1dc9f-...","retMsg":null,"data":null}
     ```

     调用栈自 `ProxyWebClient.handleResponse` → `AccountClient.requestApplication` → `AccountAppServiceImpl.requestApplication` → `AppAccountController.requestApplication`，即 **`fep-app` 把请求转发给 `account-server` 时 DNS 就失败了**，从未到达下游。
  2. 48 小时内全命名空间 Pod 日志中 `Failed to resolve` 共 30 行，**全部是 `'account-n4ba6-svc.itp.svc'`**，分布在同一 Pod，与其余模块无关（其他模块尚无入向流量）。
  3. Pod 内实测 DNS 对照：`account-server-xpz7t-svc.itpb.svc` → 解析到 `10.100.226.110`；`account-n4ba6-svc.itp.svc` → 失败。
  4. 集群命名空间实况：**只有 `itpb`，不存在 `itp`**（`kubectl get ns` 已确认）。
  5. 逐 Deployment 导出 env 后确认：`service.*.url` 全部是 `application.properties` 的原样默认值 `${SERVICE_*_URL:http://<测试环境服务名>.itp.svc:<测试环境端口>}`，**17 个 Deployment 上一个 `SERVICE_*_URL` 覆盖都没配**（K8s 只注入了 `SERVICE_NAME`）。

- **根因结论**：红岛部署时是按 `application.properties` 生成环境变量的，占位符的**默认值来自测试环境**（命名空间 `itp`、平台生成的 `<模块>-<5位随机>-svc` 服务名、测试环境端口 9098/9100/9101/300xx）。红岛的命名空间是 `itpb`、服务名是另一套随机后缀、**Service 端口 = NodePort = 319xx（targetPort 统一 8080）**。由于没有任何 `SERVICE_*_URL` 覆盖，所有 RPC baseUrl 都落在不存在的 `itp` 命名空间上 → DNS 必然失败 → 异常冒到全局处理器 → UUID `retCode`。

  三个环境维度**同时错位**（命名空间 / 服务名 / 端口），只改其中一项仍不通。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| 方案A：按模块注入 `SERVICE_*_URL` 环境变量覆盖 | 利用 `application.properties` 已内置的占位符机制，逐 Deployment `kubectl set env` 注入红岛真实地址 | 不动代码、不重建镜像；占位符是设计好的覆盖点；可单模块灰度 | 环境变量数量多（web-admin 单模块 22 条）；Service 名含平台随机后缀，**重部署后若后缀变化需重配** | 低：只改 env，滚动重启单模块，`rollout undo` 即回滚 |
| 方案B：在 `itpb` 建稳定命名的别名 Service（ClusterIP）指向各 Deployment | 创建 `account-server` 等固定名 Service，代码侧只改默认值的命名空间/端口 | 服务名稳定，不受随机后缀影响 | 需要改代码默认值 + 重建镜像；手工 Service 不在 CloudOS 平台管理范围内，易被视为配置漂移 | 中：需发版，且引入平台外资源 |
| 方案C：改 `application.properties` 默认值为同命名空间短名 | 默认值改成不带命名空间的 `<svc>:<port>` | 语义更健壮（天然跟随所在命名空间） | 服务名随机后缀问题仍未解决；仍需重建镜像；影响测试环境现值 | 中：改动面横跨全部模块配置，回归成本高 |

## 4. 决策与结论

- **选定方案**：**方案A**（本文件只出清单与可执行命令，**生产改动待红岛运维窗口执行 / 人工复核后再落地**，本次未对集群做任何变更）。
- **决策理由**：占位符机制是代码里就设计好的覆盖点，零代码改动、零发版、可按模块灰度；方案B/C 都需要重建镜像并改代码默认值，在联调窗口内不划算，留作后续架构改进项。
- **影响范围 / 关联模块**：`itpb` 下 17 个 Deployment。映射规则与明细如下（**Service 名与端口 MUST 现查**，见文末命令）。

### 4.4 连带发现（本单不处理，另行立项）

- **`VLOGS_URL` 在 `itpb` 全部 Deployment 上未配置**：`victoria-be7vr-svc`（`31920` → targetPort `9428`）里 24h/7d/30d 查询均为 0 条，日志只落 Pod stdout。红岛排障目前只能 `kubectl logs`；综管台日志查询页同样取不到数据（`web-admin` 的 `vlogs.query-url` 默认值为空）。
- **`collect-pay-server` / `collect-ticket-server` / `acc-secure-server` 在 `itpb` 未部署**：`fep-app` 的 `service.collectPay.url` 即使按本单修好其余 12 条，缴费链路仍无下游。
- **`acc-security-server` 与测试环境 `security-server` 的对应关系**按名称推定（测试环境无同名服务），落地前 MUST 由运维确认二者是同一职责。
- **`fep-app-vr` 的 4 个 destination 仍指测试环境服务名**（2026-10-23 14:5x 现查）：`fep-alipay-rec8g-svc`、`fep-dev-server-748lq-svc`、`para-server-pufrl-svc`、`route-sentinel-svc` 在 `itpb` 均不存在（`istioctl analyze` 报 4 条 IST0101）⇒ 对应 prefix（`/fep-alipay/` `/fep-dev/` `/itpagm/` `/para-server/` 与 7 条 SCG exact）经网关必然 503。**与本单同源**（配置沿用测试环境的服务名/端口），但落点是网关层而非 `service.*.url`，处置时两处 MUST 一起改，否则服务间 RPC 修好、入向仍不通。

## 5. 验证与回滚

- **实际执行（2026-10-26，改走云平台 REST，而非 §4 方案A 的 `kubectl set env`）**：用 CloudOS `PATCH /api/cloud/app-mgmt/v1.0/apps/{uuid}/advanced-config` 就地改 env，值写成 `${SERVICE_*_URL:http://<svc>.itpb.svc:<319xx>}`（与 `fep-app` 既有已修好的写法一致，不改 `application.properties`、不重建镜像、可单应用灰度）。踩坑实测出的契约（MUST 记住）：
  - `version_id` 写入 `pkg_version_id varchar(36)`，必须 ≤36 字符 → 用应用的 `upgrade_id`（32 位十六进制），**不能**用 `package_version_id`（是镜像 URL，会 500 `value too long for type character varying(36)`）；
  - `version` 不能等于当前版本（否则 500 `application.5000077 current status is not allowed to be upgraded`）→ 用「镜像 tag 追加/递增第 4 段」：如 `2.0.83.1→2.0.83.2`、`2.0.83→2.0.83.1`、`1.0.11→1.0.11.1`；
  - `service_name` 以 `GET /apps/{uuid}/service` 现查为准（8 个应用详情里 `metadata.service_name` 为 null）；
  - `affinity` / `pvcResource` / `resources` 从 `metadata.image_metadata.metadata` 原样回传，其余不动。
- **验证结果（2026-10-26，逐个 `GET /apps/{uuid}` 复核）**：14 个应用、78 条 `service.*.url` 全部改为 `itpb`；滚动完成后**全部 `status=OK`、实例就绪（各 2/2，`web-admin` 按设计 1/1）、`service.*.url` 无任何 `.itp.svc` 残留**。`fep-app` / `key-server` / `industry-data-server` 此前已正确（默认值已是 itpb），本次未动。
- **回滚预案**：对目标应用再发一次 `advanced-config` PATCH，把 `env` 中对应 `service.*.url` 改回原 `${SERVICE_*_URL:http://<测试服务名>.itp.svc:<port>}`（原值见本单 §4.1），`version` 继续递增即可；回滚后即回到「指向 itp」的旧状态，不引入新故障。
- **未覆盖（连带项，另行处理）**：`VLOGS_URL` 在 `itpb` 全未配置；`collect-pay-server` / `collect-ticket-server` / `acc-secure-server` 在 `itpb` 未部署；`fep-app-vr` 网关 destination 仍指测试服务名（见 §4.4）。
