# IT-035 平台端口变量与应用监听口径错配致服务批量 503

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-035` 一行。

## 1. 背景 / 现象

- 发现时间：2026-11-02 11:05（ACC 侧报警），同日 12:05–13:05 完成治理
- 发现渠道：第三方（青岛地铁 ACC）联调反馈
- 影响范围：测试环境 `ns itp` 全部 23 个 Java 业务服务（对外入口 `/fep-app`、`/fep-acc`、`/fep-dev` 三个前缀先后全量 503）
- 现象描述：
  - ACC 调 `http://58.56.166.170:48000/fep-app/ci/app/requestApplication` 报 HTTP error，用户 `522992` 开卡失败。
  - 首轮取证：VictoriaLogs 在 `11:03–11:08` 全平台**无一条**含 `requestApplication` / `ci/app` 的日志，fep-app 该时段 0 条；而 account-server 正常在跑 → 请求未进应用层。
  - 内网入口 `172.20.211.200:48000` 复现返回 `upstream connect error or disconnect/reset before headers`，`latest reset reason: remote connection failure`（istio 到上游连接被拒），非 404。
  - 故障面不止 fep-app：`/fep-app`、`/fep-acc`、`/fep-dev` 同时 503，`/fep-alipay`、`/itptvm`、`/itpbom` 正常 200。

## 2. 根因分析

- 排查过程：
  1. 逐 Pod 读 `/proc/net/tcp6` 实测应用容器**真实监听端口**（不依赖配置与探针——fep-app 的 app 容器**没有** readinessProbe，Pod `2/2 Ready` 不代表业务端口在听）。
  2. 比对 `kubectl -n itp get svc` 的 `targetPort`：**全部服务恒为 8080**。
  3. 读 Deployment env，定位到平台按应用分配端口并注入：`account=9098`、`ticket-server=9100`、`fep-app=9101`、`blacklist-server=9102`、`fep-dev-server=9104`、`para-server=9107`、`daily-ticket-server=9108`、`fep-acc=9110`、`card-pool-server=9111`、`recon-server=9112`、`trans-query=9113`，键名分别为 `server.port` / `SERVER_PORT` / `CARD_POOL_PORT`。
  4. 时间对照：`02:42:05Z`（10:42）旧 Pod 仍正常返回 200（同一 `thirdUserId=00522992` 的 `/app/ticket/realName`），11:05 起失败；旧 Pod 镜像与新 Pod **同为** `fep-app:2.0.105`、env 一致 → 变的不是应用，而是 Service 的 `targetPort` 侧（Service 的 `managedFields` 已被清空，取不到改动人与时间，据此无法再往下钉）。
- 根因结论：
  - **平台对每个应用分配一个 9xxx 端口并通过 env 注入，应用据此监听 9xxx；而平台生成的 NodePort Service 的 `targetPort` 恒为 8080** → 网关/NodePort 侧连接被 RST，表现为 503，ACC 侧只能看到「HTTP error」。
  - 该错配是**系统性**的：只要某应用被重新滚更（平台重新渲染 env），端口就会按平台分配值生效，因此故障会随每次发版在不同服务上反复冒出来（12:2x 滚更后 `card-pool-server` / `recon-server` / `trans-query` 又跑到 9111/9112/9113）。
  - 叠加 IT-034 的事实（测试环境滚更长期用 `kubectl set image` 绕开云管台，平台 `metadata.container_image` 落后于实跑），平台「端口分配」这一层与运行态早已脱节。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| 方案A 逐个改 Service `targetPort` 跟随实际端口 | 谁的端口是 9xxx 就把该 Service 指过去 | 改动最小、立即止血 | 每滚更一次端口可能又变，需持续追；23 个服务口径各不相同，无法沉淀约定 | 追不上即再次 503；新人无法判断该填哪个值 |
| 方案B 统一应用监听 8080 + 新增内网 Service + 服务间走内网 | 把端口口径压回 8080；每个服务加一个 ClusterIP `<app>-internal`；调用地址统一 `http://<app>-internal.itp.svc:8080` | 与 Service `targetPort` 天然对齐，滚更不再反复；服务间不走 NodePort 绕节点；两个网络服务并存，外部对接零改动 | 需逐个应用改 env 触发滚更 | 滚更期间单副本服务有秒级中断；env 全量替换语义（IT-020） |
| 方案C 平台侧改端口分配 | 让平台按 8080 统一分配 | 一处改、全局生效，最彻底 | 需平台厂商支持，周期不可控 | 与现网大量既有配置冲突，本次无法验证 |

## 4. 决策与结论

- 选定方案：**方案 B**（2026-11-02 用户裁定「所有 java 服务都改为监听 8080，所有服务都要绑定两个网络服务，需要添加集群内网服务，然后服务间集群内调用要走内网」）。
- 决策理由：A 是「跟着故障跑」，与平台机制对抗；C 依赖厂商且周期不可控；B 让代码/配置/Service 三者口径一致，是唯一能把问题**收敛**掉的做法。
- 落地明细（全部走云管台 `PATCH /apps/{uuid}/advanced-config`，不用 kubectl 改 env——会被平台数分钟内回收，见 IT-020）：
  1. **统一监听 8080**：把上表 11 个应用的端口变量全部压回 8080；实测 31 个业务 Pod 统一监听 8080（`es-server` 另监听 5000，属 ES 自身端口）。
  2. **代码层固化**：改 `acc-secure-server(9099)`、`acc-security-server(9012)`、`collect-pay-server(58101)`、`collect-ticket-server(9098)`、`face-pay-server(58101)`、`employee-card-acc-simulator(9114)` 六个模块的 `server.port` 为 8080，避免「哪个镜像没带 env 就复发」。
  3. **双网络服务**：新增 23 个 ClusterIP `<app>-internal`（`port 8080 → targetPort 8080`，selector `app: <应用名>`），与原 NodePort Service 并存；**原 NodePort 号一概未动**，外部/联调/istio 路由不受影响。清单入仓 `deploy/k8s/20-services.yaml`。
  4. **服务间走内网**：72 条 env（`service.*.url` / `*_URL`）由 NodePort 或 `*-svc.itp.svc:9xxx` 改为 `http://<app>-internal.itp.svc:8080`；顺带修掉 3 处指向 Pod 自身回环的错误配置（`fep-alipay`、`alipay-pay-sign-server` 的 `127.0.0.1:9012/9103/9107`）。
- 影响范围 / 关联模块：19 个应用 env + 23 个 Service + 6 个模块配置文件。外部回调类 url（`58.56.166.170:48000`、`dtcustomer.bestonepay.com`、ACC 安全服务、VictoriaLogs）**刻意不动**。

## 5. 验证与回滚

- 验证方式 / 结果（2026-11-02 13:0x 实测）：
  - 公网入口 6 个前缀 `fep-app`/`fep-acc`/`fep-dev`/`fep-alipay`/`itptvm`/`itpbom` 全部 `http=200`；
  - 11 个核心服务 NodePort 全部 `403`（应用级拒绝，链路通；`403` 不等于故障，`503` 才是）；
  - 23 个 `<app>-internal` 的 endpoints 全部有后端（`fep-dev-server`/`gate-txn-pay-server`/`pay-sign-server`/`ticket-server` 各 3 个、`account` 2 个）；
  - VictoriaLogs 命中 fep-app 收到 `/ci/app/requestApplication`（`x-envoy-original-path` 正确、`response.status=200`）。
- 回滚预案：
  - 单个应用：`cloudos deploy <app> <原镜像:tag> --app-version <原 version> --yes`，或把刚才被改的 env 键改回原值（每个应用的原值在同一次 PATCH 前的 `GET /apps/{uuid}` 快照里）；
  - 单个 Service：`kubectl -n itp patch svc <app>-<后缀>-svc --type=json -p '[{"op":"replace","path":"/spec/ports/0/targetPort","value":<原值>}]'`；
  - internal Service 回滚 = `kubectl -n itp delete svc <app>-internal`（不影响现有 NodePort 访问）。
- 已知遗留（MUST 跟进，勿当已解决）：
  1. **9 条 `SERVICE_*` 大写变量改不动**：由平台注入、不在 `metadata.env` 内（如 fep-app 的 `SERVICE_TRANS_QUERY_URL`、`SERVICE_COLLECT_PAY_URL`，web-admin 的 `RECON_SERVICE_URL`/`F2F_SERVICE_URL`），仍指 `*-svc.itp.svc:300xx`——功能通，但未走 8080，需在云管台「服务绑定」侧调整。
  2. **端口变量命名口径（重要）**：`face-pay-server` 对**点号形式** `server.port` 不生效、对**下划线** `SERVER_PORT` 生效（fep-app 等应用点号形式却生效，差异原因未定位）。这与项目既有约定「K8s env var MUST 下划线命名」一致 → **新增端口类 env MUST 用 `SERVER_PORT`**。该服务已用 `SERVER_PORT=8080` 纠正，`face-pay-server-svc` 的 targetPort 同步改为 8080，NodePort 30025 实测 `403`。存量仍用点号 `server.port` 的应用（account / ticket-server / blacklist-server / fep-* 等）值已统一 8080、功能正常，建议下次发版时随手改名为 `SERVER_PORT`。
  3. 平台「按应用分配 9xxx 端口」的机制本身未变，下次若有人在平台侧改端口分配，仍可能把 env 写成 9xxx；建议与厂商确认该字段能否固定 8080。
