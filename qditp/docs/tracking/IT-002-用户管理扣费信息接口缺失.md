# IT-002 用户管理「扣费信息」前端有调用、web-admin 无对应端点

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-002` 一行。

## 1. 背景 / 现象

- 发现时间：2026-10-15
- 发现渠道：把前端包 `1.2.30` 更新到测试环境后的连带核查（该功能随本包**首次真正上线**）
- 影响范围：综管台「系统管理 → 用户管理」列表的扣费信息列（未缴费笔数 / 扣费失败笔数）
- 现象描述：前端调用 `GET /web-server/system/user/userAccInfo`，但 web-admin 侧没有该端点。

## 2. 根因分析

- 前端：`web/src/api/system/user.js` 中 `requestUserAccInfo` → `/web-server/system/user/userAccInfo`；`web/src/views/system/user/index.vue` 的 `getList()` 对列表中每行调用 `loadUserAccInfo()`，失败时 `.catch(() => ({ unpaidCount: 0, failCount: 0 }))` 兜底。
- 后端：全仓搜 `userAccInfo`，`web-server/**/*.java`（web-admin）**0 命中**；`SysUserController`（`@RequestMapping("/system/user")`）仅暴露 `/list`、`/{userId}`、`/authRole/{userId}`、`/deptTree`。真正的数据侧实现位于 `gate-txn-pay-server`（`GateTxnPayQueryService.userAccInfo`，带白名单桶、按配置月份反推 startDate 的单测）。
- 根因结论：前端功能已随包上线，**web-admin 侧端点从未实现** ⇒ 该列恒为 0/空；因前端有 `catch` 兜底，**不报错、无前端报错提示**，属静默失效。
- 探活无判别力（记录以免后续误用）：未登录访问 `172.20.211.23:30028/system/user/userAccInfo` 返回 **200 空响应**，与随机不存在路径 `/system/user/zzzDefinitelyNotExist` 的响应完全一致，故只能用代码侧证据定界，不能靠裸探活。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| 方案A | web-admin 新增 `GET /system/user/userAccInfo`，经 `rpc` 模块调下游 | 功能闭环、与前端现状零改动 | 需定清下游归属（gate-txn-pay / account）与鉴权；逐行单调用有 N+1 | 中 |
| 方案B | 改为批量端点 `POST /system/user/userAccInfo/batch`，一次传 userId 列表 | 消除 N+1，用户列表页更稳 | 前后端都要改 | 中 |
| 方案C | 前端摘掉该列与 `loadUserAccInfo()` | 改动最小、立即消除「永远为 0」的误导 | 丢掉业主要的信息 | 低 |

## 4. 决策与结论

- 选定方案：**挂起（待业主确认该信息是否必须）**
- 决策理由：该功能源自 2026-10-10 的前端优化提交，仓库内没有对应的后端需求记录；先确认需求与数据口径（白名单桶定义、统计起止月份），再在 A/B/C 中决策，避免凭猜测实现接口。
- 影响范围 / 关联模块：仅综管台用户管理页的展示列；**不影响登录、用户增删改、分配角色等主流程**。

## 5. 验证与回滚

- 验证方式 / 结果：代码侧证据（前端调用点 + web-admin 无该 mapping + 全仓 `userAccInfo` 在 web-admin 侧 0 命中）；接口探活无判别力，见 §2。
- 回滚预案：若该列造成困惑，前端删除该列与 `loadUserAccInfo()` 即可，无需动后端。
