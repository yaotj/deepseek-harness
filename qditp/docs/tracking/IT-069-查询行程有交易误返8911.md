# IT-069 查询行程有交易却误返 8911（`lastStation=FFFF` 被当零交易）

## 一、背景

2026-11-16 13:38 测试环境，调用方日志（`com.bestone.metro.service.ITP_Service` 调 `/fep-app/c/ian/app/queryUserItinerary`）显示：卡 `0426090949000508` 刚在灵山卫（1325）进站，明细已落库，但接口返回：

```json
{"retCode":"8911","retMsg":"上次行程为空","memberItinerary":{
  "thisStationName":"灵山卫","thisStationCode":"1325","thisTransTime":"20261116133806",
  "lastStationName":"FFFF","lastStationCode":"FFFF","lastTransTime":"20261116133345","ticketStatus":"04"}}
```

本次行程字段有效，`8911` 却把整趟判成「上次行程为空」。

数据侧核对（测试库 `QDITP`）：
- `QRCODE_STATUS`：建卡 `13:33:41`，进站后 `GATE_IN_STATION=1325`、`LAST_TXN_STATION=1325`、`TXN_SEQ=1`；
- `QRCODE_TXN_DETAIL`：该卡仅 1 条（`ID=3088143`，`TRX_TYPE=01`，`HANDLE_STATION_CODE=1325`，`LAST_HANDLE_STATION_CODE=FFFF`，`HANDLE_DATE_TIME=20261116133806`）；13:33:xx 全表 0 条过闸。

即：**这是新卡首次进站，有真实交易，`lastHandleStationCode=FFFF` 是建行哨兵被 `GateTicketHandler` 原样带入明细**，不是脏数据、不是漏写。

## 二、根因

D166（2026-09-22）为规避「新卡首次进站时 `lastStationName=FFFF` 被 APP 当站名渲染报查询失败」，把**「上次站点是哨兵 FFFF」判成 8911**。该判据混淆了两个概念：

- 「上次站点未知」——首次进站的正常形态；
- 「没有任何交易」——才是 8911 的语义。

原判据 `TicketRideStatusServiceImpl.isLastItineraryEmpty()`：`!hasText(lastStationCode) || lastStationCode.equals(defaultLastTxnStation)`。首次进站 `lastStationCode=FFFF` → 命中 → 误返 8911。

业务方（业主 2026-11-16）明确口径：查上次行程 = 查这个号上一次产生的交易，进出站各算一笔；刚进完查进站、刚出完查出站；**只有进出都没有才算 8911**。

## 三、方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| A（沿用 D166） | 保持哨兵即 8911，APP 改渲染逻辑忽略 FFFF | 需 APP 配合；明明有交易还返错误码，语义持续错，否决 |
| B（本次采用） | 8911 收窄为零交易 + 站点哨兵归一空串 | 后端单点闭环，APP 无需改映射；空串是 APP 友好的「无站点」表达 |
| C（改数据） | 把明细 `lastHandleStationCode` 的 FFFF 回填真实站 | 哨兵是建行初值、无真实上一站可填，不成立 |

## 四、决策

采用方案 B，三点联动（详见 [ADR-D174](../domain/decisions.md)）：

1. `queryUserItinerary` 的 8911 唯一条件改为 `latestDetail == null`（无任何过闸明细）；有交易一律 0000。删除 `isLastItineraryEmpty()`。
2. `MemberItineraryAssembler` 装配 `this`/`last` 的 code+name 四字段时，未知站哨兵归一为 `""`。
3. 判据统一走 `SupplementCodec.isUnknownStation`（同时识别字面量 `FFFF` 与配置 `ticket.default-last-txn-station`），该类提升为 public；禁止裸 `"FFFF".equalsIgnoreCase(x)`（审查项 C004）。

错误码 `8911` 的 code 与文案不变，APP 无需改映射。
