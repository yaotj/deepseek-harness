# IT-086 风控命中无生产者（规则链路输入缺口）

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-086` 一行。

## 1. 背景 / 现象
- 发现时间：2026-11-19 17:10（与用户对账风控链路时确认）
- 发现渠道：自查（全仓代码检索 + 用户确认）
- 影响范围：para-server 风控域整条「规则命中 → 自动加黑」链路（IT-083）
- 现象描述：`TBL_RISK_CONTROL_LOG`（风控命中台账）在全仓**没有任何生产写入方**。
  唯一写入路径是 `POST /page/risk/control-logs`（`RiskManagementServiceImpl.createControlLog`），
  但该端点无任何业务模块调用。IT-083 的 E2E 验证靠**手工造数 6 条命中**为前提通过，
  造数已清理；定时任务（job_id=425）现为恒 `candidates=0` 空转，
  规则阈值/绑定配置不产生任何实际效果，风控记录页恒空。

## 2. 根因分析
- 排查过程：全仓 grep `TBL_RISK_CONTROL_LOG` 仅命中 para-server 自身 mapper；
  `riskControlLogMapper.insert` 唯一调用方是 `createControlLog`；
  全仓无任何模块 POST `risk/control-logs`。初始化 SQL（`docs/sql/02_qditp_data.sql`）
  对该表只有 DDL、无造数 INSERT。
- 根因结论：**需求级缺口，非代码缺陷**。实时规则引擎按需求文档 §35 另案、不在本仓；
  本仓只交付了链路的「配置层」（组/规则/阈值/绑定/综管台页面）与「处置层」
  （IT-083 定时聚合加黑），中间的「命中判定/生产层」没有落地组件。
  旧 ITP 的命中由旧系统引擎产生，新系统切换后该输入断供。

## 3. 方案对比
| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A 交易链路实时判定 | 进站/出站/扣费等主链路内嵌规则匹配，命中即落 `TBL_RISK_CONTROL_LOG` | 真·实时引擎；命中带完整交易上下文 | 侵入交易主链路（性能/稳定性敏感）；工作量大；正是需求 §35「另案」的原方案 | 主链路抖动直接放大到乘客出行；需压测与安全合规复核 |
| B 批量扫描派生（定时任务升级） | 新 job 直接读交易表（乘车/订单域），按规则条件 SQL 派生命中行写入台账（或直写 `BREACH` 事件） | 不侵入主链路；与现有 sync job 同构、最易落地；规则条件可 SQL 表达 | 准实时（批间隔）；引擎规则表达能力受 SQL 限制；需新造「规则→SQL 模板」映射 | 派生口径与真实交易语义偏移；高频表全扫的性能需评估 |
| C 维持开放接口上报 | 保留 `POST /page/risk/control-logs`，由外部/ACC/对账系统按契约上报 | 本仓零改动 | 依赖第三方配合；`/page/**` 现无鉴权（P0-1 安全债）暴露面扩大 | 无 producer 则链永远空转；接口被滥刷污染台账 |

## 4. 决策与结论
- 选定方案：**方案 B 批量扫描派生**（2026-11-19 用户裁定，IT-083 实时引擎 §35 另案前先落地）
- 决策理由：不侵入交易主链路、与既有 sync job 同构最易落地；规则仅 2 条、条件可 SQL 表达。
- **口径裁定（2026-11-19 用户裁定）**：
  - 000003 最大允许单边交易数：**超时出站（出站明细 OVERTIME_AMOUNT 大于 0）与滞留进站（04 超 24h 未出站）两种都算**，各写一行命中；
  - 000002 出站规则：**同一自然日出站明细（TRX_TYPE 02/03）≥ 阈值记一次命中**（独立 1 天窗口，
    NEVER 沿用全局 7 天——正常乘客 7 天出站十余次会全量误伤；旧系统阈值 300 实为永不触发）。
- **实现（本日完成）**：para-server `POST /internal/risk/hit-derive` + 每规则一个 Handler Bean
  （000003 `OnesideHitDeriveHandler` / 000002 `RepeatExitHitDeriveHandler`，新增规则=新增 Bean）；
  web-admin `riskHitDeriveQuartzTask.derive()` + `sys_job` 426（`0 2/10 * * * ?`，早于 425 加黑 3 分钟）；
  迁移 `migration/20261119_risk_hit_derive_job.sql`（幂等）。去重在派生 SQL 反连接完成，重复扫描不重复落行。
- 影响范围 / 关联模块：para-server、web-admin、model/rpc（纯增量，按 §3 豁免仅重打包这两服务）、
  读模型直读 ticket 域表（QRCODE_TXN_DETAIL / QRCODE_STATUS，同库跨域读，读模型先例同 recon）。

## 5. 验证与回滚
- 验证方式 / 结果：
  - 单测 8/8 全绿（`RiskHitDeriveServiceImplTest` 5 例 + `RiskHitDeriveHandlersTest` 3 例）；
  - `mvn -o clean test-compile` para-server / web-admin 均过；mapper XML 过 xmllint；
  - **E2E（测试环境 2026-11-19 19:26）**：
    1. 造数 5 行（QRCODE_TXN_DETAIL 超时出站 1 + 自然日出站 3 + QRCODE_STATUS 滞留 1）；
    2. 手动触发 430（`PUT /monitor/job/run`）→ para-server 日志 `candidates=60, inserted=60`（000003=54 超时出站+滞留 / 000002=6 自然日重复出站）；
    3. E2E 卡 3 行命中落 `TBL_RISK_CONTROL_LOG`（`RISK_STATUS=0`、快照齐、`RISK_HIT_TIME` 正确）；
    4. 二次触发 430 → `inserted=0`（去重反连接生效，E2E 行数不变）；
    5. 手动触发 425 → `candidates=9, skipped=9`（E2E_STUCK_001 已在黑名单，SKIPPED_EXISTING）；
    6. `BLACKLIST` 核验：`E2E_STUCK_001` 行 `BLACK_SOURCE=01 / BLACK_CAUSE=03 / CREATE_BY=riskRuleBlacklistSync / REASON=规则[000003]「最大允许单边交易数」窗口期命中 3 次（黑名单直拉规则组自动加黑）`；
    7. E2E 造数已清理（5 表 × 11 行）。
  - **发现并修复**：`RiskRuleMapper.selectAll` 的 `<sql id="columns">` 含 `R.` 前缀但无别名 → ORA-00904，
    改为内联列名（para-server 2.0.50）。
- 回滚预案：`UPDATE sys_job SET status='1' WHERE job_id=430` 停派生（425 加黑不受影响）；
  已写入命中行为审计数据只增不改不删（`RISK_HANDLE_*` 除外）。
