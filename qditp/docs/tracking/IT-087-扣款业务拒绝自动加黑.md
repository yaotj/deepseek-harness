# IT-087 扣款业务拒绝自动加黑（签约分叉/9001 类失败纳入欠费黑名单）

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-087` 一行。

## 1. 背景 / 现象
- 发现时间：2026-11-20 08:40（复核旧 ITP 请求新系统 `queryBlackList` 日志时连带发现）
- 发现渠道：用户反馈（测试环境，卡 `0426090949000508`）
- 影响范围：测试环境；出站扣费经 pay-sign 支付、被支付平台明确业务拒绝而落 `DEBIT_STATUS=FAIL` 的订单。重档依据＝**自动化敏感动作（加黑）+ 跨模块契约变更**（gate-txn-pay 首次引入黑名单写入）。
- 现象描述：
  1. 旧 ITP 请求新系统 `/fep-app/app/ticket/queryBlackList` 查卡 `0426090949000508`，返回 `{"inBlack":"0","failedCount":0}`——新系统黑名单查不到该卡。
  2. 测试库实证：该卡 `GATE_TXN_PAY` 有 5 笔 `DEBIT_STATUS=FAIL`（11-18 一笔 4 分、11-19 四笔 7/500/700/400 分），`PAY_TXN_DETAIL.PAY_STATUS=FAIL`，失败原因 `BIZ_REJECTED`，REMARK=`重试扣费被pay-sign业务拒绝: 9001/未查到相关信息[3910014]`；`BLACKLIST` 表 0 行。
  3. 该卡确为**真欠费**：乘车出站交易成立、扣款未成功、支付平台侧查无签约（IT-079 已取证，协议 `status=UNSIGNED`），但当前系统无任何加黑链路覆盖，导致欠费用户仍可通行。
  4. 用户口径裁定（2026-11-20）：**这类扣款业务拒绝也必须加黑**，且字段口径 `BLACK_CAUSE=01`（欠费类，可被自动解除覆盖）+ `CHANNEL_CODE=01`（走闸机欠费源，补扣成功后可自动解黑）。

## 2. 根因分析
- 排查过程：
  - 日志侧：`com.bestone.metro.service.ITP_Service` 是旧 ITP 系统客户端，日志中的 `inBlack=0` 是新系统黑名单查询的真实结果；`failedCount` 在新系统 `BlacklistServiceImpl:85` 硬编码为 0，无失败累计语义（误导项）。
  - 数据侧：直连测试库 `qditp/AFCITPDB` 核 `BLACKLIST` / `GATE_TXN_PAY` / `PAY_TXN_DETAIL` / `ALIPAY_PAY_LOG` / `TBL_RISK_CONTROL_LOG` / `TBL_RISK_RULE` / `TBL_RISK_GROUP_RULE` / `sys_job`。
  - 链路侧：三条既有加黑路径逐条排除——
    ① pay-sign 免密失败加黑（`PaymentDomainServiceImpl:150-154`）门槛 `paymentVendor ∈ {03,05}` + `queryGatewayPayStatus` 二次确认 FAIL；本批 vendor=07 被挡，且平台 payQuery 返"未找到数据"致二次确认恒为 null；
    ② 风控命中加黑（job 425 / 直拉组 65）：该卡 `000002` 命中 1 次、`000003` 命中 2 次，均未达阈值 3，非候选；
    ③ 规则 `000009`「扣费失败5次加入黑名单」：是空配置，不在直拉组 65（组描述明确"扣款失败类属灰名单"），job 430 命中派生也无对应 handler。
  - 时序侧：9001/3910014 产生在**支付平台应答阶段**（`PaymentGatewayAdapter:46` → `PaymentReply.Rejected` → `fillError(SYSTEM_ERROR=9001, 平台原文字段)`），不是支付前本地校验拒绝（本地校验失败码是 8001/8011，见 `PayTxnRules:23-44`）。详见 IT-079。
- 根因结论：**系统缺少"出站扣费被业务拒绝（确定失败、终态 FAIL）→ 加黑"的自动化链路**；既有三条路径各有准入门槛/空配置，均不覆盖此类。属需求缺口，非偶发 bug。

## 3. 方案对比
| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A. 改 pay-sign 加黑方法 | 放宽 `addBlacklistForPaymentFailure` 的 vendor 白名单到含 07，并改二次确认判据 | 贴近支付失败源头 | ① 本场景 payQuery 返"未找到数据"，二次确认恒 null，放宽白名单也拉不黑，必须改闸门；② `queryGatewayPayStatus` 是防误拉黑的关键闸门，改动是支付安全红线 | 高：放宽闸门可能把幂等拒答当欠费拉黑（§70 历史缺陷复现） |
| B. gate-txn-pay converge 的 BizRejected→FAIL 落点（推荐） | 在 `PaySignInitiator.converge` 收敛处，对 `BizRejected` 落 FAIL 终态时加黑；afterCommit 查重后调 `BlacklistClient.addBlackList` | ① 统一收敛点，覆盖首次/批量重试/用户主动重试三条路径；② 欠费事实源（GATE_TXN_PAY）就在本模块，判据可本地判定；③ 不碰 pay-sign 的支付安全闸门 | gate-txn-pay 首次引入黑名单写入依赖；BizRejected 是粗粒度分类，需判据防误伤 | 中：判据设计不当会误拉黑已付费用户，需白名单 + 人工复核 |
| C. 风控规则 000009 补链路 | 给 000009 补命中派生 handler + 纳入直拉组 65 | 复用现有风控三表框架 | ① 000009 被明确划为灰名单、阈值 10 与"5次"文案矛盾；② 新增 handler + 派生 SQL + 改组绑定，工作量最大；③ 派生是批量、非实时，欠费通行窗口更长 | 中：规则语义（灰名单 vs 黑名单、阈值 5 vs 10）未定，易做错 |

> **收敛结论（2026-11-20 评审后）**：B（gate 侧新链路）撤销——加黑决策已散在 6 模块，再新开一处违反「加黑逻辑放一处」原则。最终按方案 A 的**方向**收口到 pay-sign 一处，但比原 A 多修两点：②二次确认语义改为「仅 SUCCESS 免黑」（原 A 的闸门是"必须 FAIL 才加黑"，正是 07 场景拉不黑的根因）+ channelCode 99→01（否则 job 230 解不掉）。

## 4. 决策与结论
- 选定方案：**收口到 pay-sign 一处**（用户 2026-11-20 裁定「加黑逻辑应放在一个地方，不四处维护」）。
  曾一度在 gate-txn-pay 新增 `DebitFailureBlacklistService`，评审后撤销——加黑决策逻辑已散在 6 个模块（pay-sign / alipay-pay-sign / fep-alipay / para / gate-txn-pay / …），再加一处是「四处维护」反例。
- **渠道边界（用户 2026-11-20 裁定）**：pay-sign（地铁/云闪付 07 等）与 alipay-pay-sign（支付宝出行）是**不同渠道，各保留自己的加黑路径，不合并**。本次只收口 pay-sign 这一路，不碰 alipay-pay-sign 的 `BlacklistRpcAdapter` 及其 3 个 service。
- 决策理由：`addBlacklistForPaymentFailure` 本就在 pay-sign 的 `PaymentReply.Rejected` 分支上、且已有二次确认防误伤机制，把 vendor 门槛与二次确认语义修正后即覆盖全渠道；改 gate 侧等于新开并行链路，与"收口一处"相悖。

### 4.1 实施（pay-sign 一处，改动点）
1. **vendor 门槛**：`PaymentDomainServiceImpl` Rejected 分支原 `paymentVendor ∈ {03,05}` 白名单 → 改为「vendor 非空即触发」。「平台明确业务拒绝」对所有渠道语义一致，真正区分"该不该拉黑"的是方法内二次确认，MUST 保留。
2. **加黑判据重构为三态（用户 2026-11-20 两次裁定，以支付中心真实订单状态为准）**：原「确认 FAIL 才加黑 / 非 SUCCESS 就加黑」都错——前者挡住 IT-079 签约分叉，后者误伤「已支付、再次请求被拒」。重构 `queryGatewayPayStatus` → `confirmPayStatus` 三态 sealed：
   - `SUCCESS`（payQuery 明确已成功/已结清）→ 幂等/重复扣款，**免黑**；
   - `FAIL`（payQuery 明确失败，或「查无数据/查无签约」业务应答 raw 非空）→ 真欠费，**加黑**（含 IT-079）；
   - `UNKNOWN`（payQuery 未配置 / 异常 / 无业务应答 raw=null，即技术故障问不出结果）→ **保守不加黑**（宁可漏拉、不误拉已付费用户）。
   关键实现：`GatewayReply.Rejected` 的 `raw` 是否非空区分「业务查无（FAIL）」与「技术故障（UNKNOWN）」。
3. **channelCode**：`"99"` → `"01"`（欠费落 GATE_TXN_PAY，走闸机欠费源，使 job 230「自动解除」能覆盖；99 会永解不掉，见 common-services.md §99 覆盖缺口）。
4. **REASON**：统一带 `code=msg`（原只带 msg），便于人工到支付中心核对。
- 安全红线复核：加黑含出网、属自动化敏感动作，本次判据经用户逐项裁定（收口层级 / 渠道边界 / 存量处置 / 三态判据），非 AI 擅自定稿。

### 4.2 加黑字段口径（已定）
- `CHANNEL_CODE=01` / `BLACK_SOURCE=01`（系统自动）/ `BLACK_CAUSE=01`（欠费）/ `CREATE_BY=pay-sign-server` / `BIZ_NO=orderNo`

## 4.3 拦截效果边界（MUST 告知业务方）
- 加黑后本地 `inBlack=1` 可被旧 ITP 的 `queryBlackList` 查到；但新系统 `queryBlackList` 是纯查询，过闸/开码/开户都不调它（common-services.md §107）。
- 实际"过不了闸"依赖出向渠道通知，而通知唯一出口是**内部支付宝**（`BlacklistChannelSyncService:105`），云闪付 07 侧收不到 → **加黑 ≠ 必然拦截 07 通道**。
- 实测补加黑后 `CHANNEL_SYNC_STATUS=FAILED`（通知发内部支付宝失败），印证此边界。07 侧是否需另建拦截通道（如平台侧拉黑）为**后续独立议题**，不在本次范围。

## 5. 验证与回滚
- 验证方式 / 结果（2026-11-20 测试环境）：
  - 单测 `PaymentFailureBlacklistDecisionTest` 5/5 全绿：① 查无签约（payQuery 9999 未找到数据）→ 加黑 channel=01 ② 二次确认 SUCCESS → 免黑 ③ 二次确认 FAIL → 加黑 ④ 技术故障（payQuery 无应答）→ 保守不加黑 ⑤ vendor 空 → 不加黑。
  - pay-sign 全量 350 用例全绿（`mvn -o -pl pay-sign-server test`，Java 21）。
  - 存量补加黑：卡 `0426090949000508` 经 `/addBlackList` 端点补加（cause=01/channel=01/source=01，bizNo=GT20261118115843625000508）→ `BLACKLIST` 落 1 行 ACTIVE + `BLACKLIST_OPERATE_LOG` 1 条 ADD，`queryBlackList` 由 inBlack=0 变 1；`CHANNEL_SYNC_STATUS=FAILED`（渠道通知边界，见 §4.3）。该卡 5 笔为"查无签约"（真欠费），三态判据归 FAIL，加黑成立、维持。
- 回滚预案：三处改动均为 pay-sign 单点，`git revert` 该提交即可；已补加的欠费黑名单按现有人工/自动解除路径处置，NEVER 直接删审计数据。
