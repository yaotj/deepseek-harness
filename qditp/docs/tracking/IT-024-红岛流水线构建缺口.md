# IT-024 红岛持续交付流水线缺口（镜像构建走 buildx 兜底）

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-024` 一行。

## 1. 背景 / 现象

- 发现时间：2026-10-26（route-sentinel 红岛首发）
- 影响范围：红岛 CloudOS 的镜像构建路线（未来所有模块的 x86 镜像产出方式）
- 现象：
  1. 平台持续交付（flowLine）`GET /api/cicd/fluxes/v1.0/pipelines` 现查 **0 条**（无任何已建流水线）；
     预置 BUILD 任务模板全部以 **Git CHECK_OUT 起步**，平台取不到源码即跑不起来（2026-10-23 已结论）；
  2. CloudOS `/api/cloud/hcr/v1.0/images/build`（旧脚本走的端点）在红岛 11443/443 均不可用
     （404 或 `img.5`），且「软件中心 jar 包上传（`POST /deploy/v1.0/packages` 的 fileFlag）」
     **不是**构建上下文文件（构建报 `COPY failed: file not found`）；
  3. 真正可用的构建通道是 Web 控制台「镜像构建」页背后的两个端点（2026-10-26 从
     `/apps-image` SPA JS 反解确认）：
     - `POST /api/cloud/hcr/v1.0/images/file/upload`：multipart 上传构建上下文文件，
       **`fileFlag` 走请求头（客户端自生成 uuid），响应 `data.id`**；
     - `POST /api/cloud/hcr/v1.0/images/buildx`：body 为
       `{dockerfile, imgName, version, imgType, type:"private", fileFlag, project, platform?, description}`，
       平台 x86 节点 buildx 构建并推 Harbor；`platform` 可指定 `linux/amd64`（**可指定架构，
       推翻 AGENTS.md §5.C「架构不可指定」的旧口径**）。

## 2. 根因分析

- 红岛 CloudOS 容器云模块只部署了 hcr（镜像仓库）与 app-mgmt（应用管理），持续交付模块
  的流水线引擎存在（`/api/cicd/fluxes` 有路由）但**从未建过流水线**；且 BUILD 模板依赖
  平台可达的 Git 源，而本仓 SVN/Git 服务器从平台侧不可达（AGENTS.md §6 前置判据同源）。
- 旧脚本 `itp-ops.sh sentinel` 走 `/images/build` + 软件中心 fileFlag 是
  **端点误用**（两个不同文件存储：`/deploy/v1.0/packages` 是软件中心应用包，
  `/hcr/v1.0/images/file` 才是构建上下文）。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|---|---|---|---|---|
| A 建 flowLine 流水线（Git 源） | 平台检出 → 构建 jar → 打镜像 → 推 Harbor | 全自动、代码不出内网、符合「流水线构建」既定计划 | 需平台可达 Git 仓 + 建 pipeline/trigger，平台侧 `/pipelines` 现为 0，工作量大；红岛网络出口限制未核实 | 中 |
| B hcr buildx 兜底（本次采用） | 本机出 jar（字节码架构无关）→ `images/file/upload`（fileFlag 头）→ `images/buildx`（platform=linux/amd64）→ Harbor | 单镜像 20s 级、可指定架构、与 `AGENTS.md` §5.C「本机只出 jar」纪律兼容 | 非流水线、每模块手动一步；fileFlag 机制靠 Web JS 反解（非官方文档），平台升级可能变 | 低 |
| C 本地 docker buildx | 本机打 x86 镜像 | — | Apple Silicon QEMU 模拟，AGENTS.md §5.C 明令 NEVER | 高 |

## 4. 决策与结论

- 本次决策（2026-10-26 用户裁定）：**先放行 B**（route-sentinel `itpb/route-sentinel:1.0.1`
  已按 B 产出并入 Harbor，digest `sha256:d4c6bd67…`、amd64 已核），应用创建 / 双 Service /
  `SERVER_PORT` env 均已完成（现状见 [IT-021](IT-021-红岛网关路由表缺失.md)「现场实测」节）。
- 后续 MUST：立项建 **A（flowLine 流水线）**——先裁决源码源（平台可达 Git or 软件中心
  产物），建成后把 `AGENTS.md` §5.C「镜像构建位置」入口从 buildx 兜底改回流水线，
  并在 `docs/ops/environments/红岛.md`「构建与部署规则」节回填端点。

### 4.1 决策翻转（2026-10-28 用户裁定：还是要用流水线）

- **A（flowLine 流水线）现为选定默认路线，取代 B（buildx 兜底）作为红岛后续镜像构建入口**；
  B 仅保留为「route-sentinel 首发已放行」的历史事实与紧急兜底，不再作为常态路径。
- **绕开 Git 源不可达的缺口**：流水线不再以「平台可达的 Git 源 CHECK_OUT」为第一步，
  而是以**软件中心应用包**为构建输入——先 `POST /deploy/v1.0/packages` 上传 jar
  （`itp-ops.sh cloudos pkg-upload`），流水线取该应用包出镜像。这正对应 §3 方案 A
  「软件中心产物」这一备选源码源，落地为「上传应用包」这一步。
- **第一步（本 IT 推进）**：上传应用包到软件中心 `itpb` 项目（jar 型）。
  具体包/模块（route-sentinel 1.0.2？还是先拿某通用模块验证流水线）与是否先本地出 jar，
  属生产写操作，MUST 二次确认后执行；未定前本行只记录入口与命令形态。

## 10. 用应用仓库同源 jar 批量出镜像（2026-10-28 第三批动作）

## 11. 流水线能力探测：「应用仓库 jar + 自定义基础镜像 → 可部署镜像」（2026-10-28）

### 11.2 可行性裁决（答用户问）

- **自定义基础镜像：直接支持**（BUILD_IMAGE `baseImage` 字段；`itpb/jdk21:1.0.0` 平台内可拉
