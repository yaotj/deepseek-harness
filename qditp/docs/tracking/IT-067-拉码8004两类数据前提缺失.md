# IT-067 IF8A-03 拉码连续 8004：两类数据前提缺失，且同一 retCode 承载两种语义

> 本处理文档对应 `docs/tracking/问题清单.md` 索引表中 `IT-067` 一行。

## 1. 背景 / 现象

- 发现时间：2026-09-22（排查时集群日志原文时间）；归档回写 2026-11-09。**两者不一致，本文按日志原文记录时间，差异待复核**。
- 发现渠道：用户反馈（「互联互通卡数据请求失败」）。
- 影响范围：测试环境 APP 真实入向流量（`x-real-ip` 为公网客户端，经网关 `58.56.166.170:48000` → `itp-gateway` → `fep-app`），**不是全量故障**。
- 现象：`POST /ci/app/requestIndustryData`（IF8A-03）稳定失败，但 `retCode` 同为 `8004`、`retMsg` 分两类：

| 类别 | retMsg | 报文字段（`bizData`） | 出现时段 |
|---|---|---|---|
| ① 账户无卡 | `没有账号卡片数据` | `thirdUserId=00522959` / `cardId=0426090942000062` / `cardType=02`；另一例 `00522950` / `0426090942000095` | 15:07~16:30 |
| ② 日票不可用 | `无可用日票` | `thirdUserId=00522968` / `cardId=0426090944000008` / `cardType=12` | 15:25~16:13 |

- 反证（排除「生码链路故障」）：
  - 同窗口 16:31 离线码 IF8D-03（`0426090949000058`）返回 `{"retCode":"0000",...,"exitData":"0007FAD7...310264"}`（80 位），链路正常；
  - `industry-data-server` 与 `acc-security-server` 容器日志按 `ERROR|WARN|失败|非法|不能为空` 检索 **0 条**。

**2026-11-16 实时复现（同一根因第二例：日票卡仅开户未购票）**：14:31:07 测试环境 `thirdUserId=00522980` 用日票卡 `0426090951000196`（cardType=12）拉码，返回 `8004 无可用日票`（traceId `4bce75c05caf1c1a4ee81c1bba72224f`）。证据链完整：`fep-app → ticket-server → daily-ticket-server`，SQL `CARD_NUM='0426090951000196' and TICKET_STATUS in ('ACTIVATED','USED')` 命中 `Total: 0`。库内该卡 14:26:14 刚写 `USER_ITP_REG_INFO`（CARD_TYPE=0445 / ITP_CARD_TYPE=12）与 `QRCODE_STATUS`（`CODE_STATUS=03` 未进站），但 `DAILY_TICKET_INSTANCE` / `DAILY_TICKET_ORDER` / `PAY_TXN_DETAIL` 均 0 行、全库当日无任何新增日票实例——**仅完成开户、未走完购买→支付→激活→生成实例**，与 §2.3 根因二一致。附带发现（进出站记录核查）：**全库今日（11-16）日票族（0445/0446/0447/0448）进出站记录 0 条**（`QRCODE_TXN_DETAIL` 按 `CARD_TYPE in (...)` + `HANDLE_DATE_TIME>='20261116000000'` 实查）；新日票卡 `0426090951000196` 作为 `CARD_ID` 或 `ITP_USER_ID` 均 0 条，`GATE_TXN_PAY` 亦 0 条。该用户当日唯一进站是 14:26:55 用另一张普通后付费卡 `0426090949000081`（CARD_TYPE=0441）在 0223 站（TRX_TYPE=01，`LAST_HANDLE_STATION_CODE=1125`），即这张日票卡从未实际过闸。旁证：老日票卡 `0426090951000219` 虽有 2 万+ 条进出站交易，但 `HANDLE_DATE_TIME` 均为 2026-10-21/22、`ITP_USER_ID` 混乱（含 `00900441`），属历史批量造数，与本次联调无关。**用户后续于 14:39:02 用同一入参（bizData `thirdUserId=00522980`/`cardId=0426090951000196`/`cardType=12`，timestamp `20261116143902`）再次拉码，仍返回 `8004 无可用日票`**（traceId `3b71d808424fa54d55c54aa9c22ea3fb`，SQL 同样 `Total: 0`）；复验库状态未变：日票实例 / 订单 0 行、`QRCODE_STATUS.CODE_STATUS=03`/`GATE_IN_STATION=FFFF`/`TXN_SEQ=0`（`UPDATE_TIME` 仍为 14:26:14），今日全库日票族进出站仍 0 条。证明两次是同一根因的重复触发，非「进站后状态变化」。

## 2. 根因分析

### 2.1 排查过程

调用链（代码走查确认，行号为 2026-11-09 现查）：

```
APP → fep-app /ci/app/requestIndustryData（IndustryDataController:28）
    → ticket-server /internal/ticket/industry/online（IndustryDataInternalController）
        ├ account /queryUserInfo            → AccountProfileServiceImpl:55-56（NO_ACCOUNT_CARD）
        ├ daily-ticket /rideAvailability    → DailyTicketInstanceLifecycleService:228-232
        └ industry-data /ci/industry/buildCardData → acc-security /ci/itp/requestSignInsData（HSM）
```

判定顺序在 `IndustryDataOrchestrator`：先查账户（`:92-103`），通过后才做日票可用性校验（`:134-140`）。因此两类失败是**互斥的两道前置闸**，都不会走到生码。

### 2.2 根因一：卡从未开户（账户闸，retMsg = 没有账号卡片数据）

- 出处：`IndustryDataOrchestrator.java:99-103` 原样透传 account 的返回；源头 `AccountProfileServiceImpl.java:55-56`。
- 查询是**三键全等 + 软删过滤**（`UserItpRegInfoMapper.xml:75-85`）：
  `THIRD_USER_ID = ? AND CARD_ID = ? AND CARD_TYPE = ? AND DEL_YN = 1`，
  且 `cardType` 先经 `CardTypeMapping.toIssueCardType` 映射（APP 送 `02` → 库里比 `0441`）。
- 库内实查（测试库 `AFCITPDB`）：
  - 卡 `0426090942000062`、`0426090942000095` 在 `USER_ITP_REG_INFO` **零行**（不分 `DEL_YN`），在 `QRCODE_STATUS` 也**零行**；
  - `thirdUserId=00522959`、`00522950` 名下同样零行。
- 结论：**这两张卡从未开户**（或 APP 侧取的卡号不来自本环境开户结果），任意一个键不匹配都会得到同一个 8004。

### 2.3 根因二：日票无实例（日票闸，retMsg = 无可用日票）

- 账户侧这次**通过**：`USER_ITP_REG_INFO` 有行（`CARD_TYPE=0445` / `ITP_CARD_TYPE=12` / `DEL_YN=1` / `REG_TMS=15:24:50`），`QRCODE_STATUS` 有档（`CODE_STATUS=03`）。
- 卡在 `DailyTicketInstanceLifecycleService.java:228-232`：`selectForEntryCheck(cardNum)` 返 `null` → `无可用日票`。
- 库内实查：`DAILY_TICKET_INSTANCE WHERE CARD_NUM='0426090944000008'` = **0 行**。该用户名下只有两张实例：
  `0426090954000021`（`EXPIRED`）、`0426090951000040`（`REFUND_LOCKED`）。
- 结论：**一日票开户完成但没有对应日票实例**（未购买/未支付到实例生成），拉码被日票可用性校验拦下。

### 2.4 附带缺陷：`8004` 同时承载两种语义

`IndustryDataOrchestrator.java:134-140` 把 daily-ticket 的业务拒绝**统一硬编码为 `8004`**，只透传 `retMsg`。而 `8004` 在账户侧本义是「没有账号卡片数据」。因此：

- **按 retCode 无法区分「未开户」与「未买到日票」**，只能看 `retMsg`；
- 上游若按 `8004` 做「去开户」引导，日票场景会被误导到错误分支。

## 3. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 风险 |
|------|------|------|------|------|
| A. 只治数据（本次采用） | APP 侧核对卡号来源；未开户的补开户，日票的补购买至生成 `ACTIVATED` 实例 | 零代码风险；与「两类失败都是数据前提缺失」的根因一致 | 不防复发，下一个用户仍会踩同一报错 | 低 |
| B. 拆分 `8004` 语义 | 日票不可用改用独立 retCode（或增加 `failReason` 字段） | 上游可定向引导；排障成本下降 | **对外契约变更**，APP/甲方可能按 `8004` 写死分支 | 中高，须先与 APP 侧确认 |
| C. 仅补结构化日志 | 编排层在返回前记录 `thirdUserId` / `cardId` / 卡类型 / 拦截闸位 | 改动小、不影响契约 | 只改善排障，不改善 APP 体验 | 低 |

## 4. 决策与结论

- 选定方案：**A（数据侧处置，无代码改动、无数据写操作）**；B / C 暂不做。
- 决策理由：
  - 两类失败的成因都在数据，改代码既修不好、还会掩盖问题（与 IT-046「不把数据错变成代码猜」同一口径）；
  - B 属对外契约变更，IF8A-03 的 DTO 是可被 `parseBizData` 解析的对外契约，**必须先取得 APP 侧/甲方确认**，不在排障中顺手改；
  - C 可在下次动该编排类时顺带做，不单独立项。
- 影响范围 / 关联模块：`fep-app-server`（透传，无判断）、`ticket-server`（编排）、`account-server`（账户查询）、`daily-ticket-server`（日票可用性）。
- 后续若决定拆语义，**MUST** 同批更新 `docs/business/ride-code.md` 的接口清单与 Apifox。

## 5. 验证与回滚

- 验证方式 / 结果（本次未做写操作，均为只读核对）：
  1. 账户闸：库内实查两卡两用户在 `USER_ITP_REG_INFO` 全零行，复现 8004 的必要条件成立；
  2. 日票闸：`DAILY_TICKET_INSTANCE` 按 `CARD_NUM` 查为 0 行，且该用户另两张实例状态分别为 `EXPIRED` / `REFUND_LOCKED`（拿它们重试会得到「日票已过期」/「车票已申请退款，不允许使用」，同样不通）；
  3. 正向对照：同窗口离线码请求返回 `0000` + 80 位码体，证明生码与 HSM 签名链路可用。
- 回滚预案：本次无代码、无数据变更，**无需回滚**。
- 遗留 / 待确认：
  - APP 侧卡 `0426090942000062` / `0426090942000095` 的来源（本环境无任何开户痕迹，疑为旧环境或手工造号）；
  - 日票开户后未生成实例的链路归因（购买/支付环节），需按 `DAILY_TICKET_ORDER` 反查该卡是否有已支付未激活订单；
  - `8004` 语义合并是否拆分（方案 B），待 APP 侧确认。
