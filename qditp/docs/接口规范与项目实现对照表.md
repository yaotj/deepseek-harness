## 一、总体架构对比

| 维度 | 接口规范 | 项目实现 |
|------|---------|---------|
| 部署形态 | 单体 ITP 平台，路径前缀 `/[project]/ci/app` | 微服务拆分：fep-app-server、account-server、key-server、pay-sign-server、wallet-server、collect-ticket-server、industry-data-server 等 |
| 调用方式 | APP → ITP 直连 | APP → APP_SERVER → fep-app-server → 各业务 server（RPC） |
| 报文格式 | HTTP POST，公共参数平铺 + `bizData` JSON | fep-app 入口用 `application/x-www-form-urlencoded`（`CommonFormRequest`），内部 RPC 用 JSON |
| 签名 | signType 01 sha1withrsa / 02 MD5，所有非空参数按 ASCII 排序后拼接 | 当前 signType 固定为 `"00"`（不签名），sign 为空串 |

### 3.1 卡类型编码映射

规范表 4 定义：

| 规范定义 | 含义 | 项目映射 |

| 02 | 二维码后付费单程票 | `"02" -> "0441"` |
| 03 | HCE 后付费单程票 | `"03" -> "0442"` |
| 其他 | 预留 | — |

| `"04"` | `"0443"` | 新版 HCE 后付费单程票 |
| `"11"` | `"0444"` | 员工票 |
| `"12"` | `"0445"` | 一日票 |
| `"13"` | `"0446"` | 三日票 |
| `"14"` | `"0447"` | 七日票 |
| `"15"` | `"0448"` | 月票 |

**结论**：项目实现比规范表 4 更丰富，规范表 4 可能已过时。

### 3.4 签名机制

| 维度 | 规范要求 | 项目实现 |
|------|---------|---------|
| signType | `01` sha1withrsa / `02` MD5 | 固定返回 `"00"`（不签名） |

## 六、微服务拆分推荐方案

> 本章节基于当前项目实现（15+ 服务）进行领域驱动分析，提供保守合并和领域重构两条路线。

---

### 6.1 当前问题诊断

| 问题 | 表现 | 风险 |
|------|------|------|
| **服务粒度不均** | wallet-server 只有 2 个接口，pay-sign-server 却承担支付/签约/解约/退款/回调全链路 | 小服务运维成本高，大服务变更风险集中 |
| **职责边界交叉** | pay-sign-server（签约/解约）与 account-server（开户/支付通道）都存在签约状态管理；wallet-server 又是独立签约入口 | 数据一致性难保障，排查问题链路长 |
| **ACC 模块分裂** | acc-secure-server、acc-security-server、acc-es-server 三个都与 ACC 相关，名称相近易混淆 | 部署、运维、问题定位成本高 |
| **命名误导** | collect-ticket-server 实际是"票务订单+取票+票价"聚合，不是单纯的"取票" | 新人理解成本高 |
| **基础设施混杂** | gate-txn-pay-server、fep-dev-server、collect-pay-server 都与支付网关/代收付相关，边界不清 | 支付链路排查困难 |

---

### 6.2 推荐架构（6+3 模型）

#### 一、业务域服务（6 个）

| 服务名 | 原服务合并来源 | 核心职责 | 理由 |
|--------|---------------|---------|------|
| **member-service** | account-server + wallet-server | 用户开户、卡管理、账户信息、支付通道绑定、钱包签约 | 都是"用户-卡-支付渠道"关系管理，强数据关联 |
| **ticket-order-service** | collect-ticket-server + ticket-server | 订单全生命周期（下单/支付/退款/取消）、取票、票价、二维码状态、行程注册 | 订单、支付、取票、二维码状态强耦合，跨服务会导致分布式事务 |
| **payment-service** | pay-sign-server + gate-txn-pay-server | 支付、签约、解约、退款、支付回调、与第三方支付平台对接 | 支付全链路闭环，避免回调跨服务调用 |
| **industry-service** | industry-data-server + key-server | 行业数据生码、密钥同步、离线码、CA 管理 | 生码依赖密钥，密钥依赖 CA，强关联 |
| **ride-service** | （新建或从 ticket-server 拆分） | 行程管理、补站、交易记录、账单统计、黑名单 | 行程是独立领域，与订单、账户解耦 |
| **app-gateway** | fep-app-server | APP 接入网关、公共参数解析、路由转发、BFF | 保持现有角色，只做接入和编排 |

#### 二、基础设施服务（3 个）

| 服务名 | 原服务合并来源 | 核心职责 | 理由 |
|--------|---------------|---------|------|
| **acc-service** | acc-secure-server + acc-security-server + acc-es-server | ACC 安全通信、密钥安全、对账、ES 任务 | 都是 ACC 相关，统一入口降低联调成本 |
| **device-service** | online-server | AGM/TVM/BOM 设备在线状态、心跳、设备管理 | 设备管理是独立能力 |
| **blacklist-service** | blacklist-server | 黑名单管理 | 保持独立，但可考虑合并到 member-service（如果业务强相关） |

#### 三、开发/辅助服务

| 服务名 | 原服务 | 说明 |
|--------|--------|------|
| **fep-dev-server** | fep-dev-server | 开发环境支付网关，保留 |
| **collect-pay-server** | collect-pay-server | 代收付，可考虑合并到 payment-service |

---

### 6.3 合并路线图（建议分两步）

#### 第一步：保守合并（1-2 周，低风险）

1. **wallet-server → pay-sign-server**
   - wallet-server 只有 2 个接口（`requestTermination`、`requestContractResult`），直接迁入 pay-sign-server
   - 风险：低，接口独立，无数据耦合

2. **acc-secure-server + acc-security-server → acc-service**
   - 两个服务都依赖 ACC 安全通信，合并为一个
   - 风险：低，职责相近

3. **collect-pay-server → payment-service**
   - 代收付是支付的一部分，合并到 payment-service
   - 风险：低

4. **命名修正**
   - `collect-ticket-server` → `ticket-order-service`
   - 更新 pom 和文档

#### 第二步：领域重构（1-2 个月，中风险）

1. **建立 ride-service**
   - 从 ticket-server 拆出行程相关接口（补站、交易记录、账单统计）
   - 与 account-server、ticket-order-service 通过事件或 RPC 交互

2. **统一支付网关**
   - gate-txn-pay-server + fep-dev-server → pay-gateway
   - 支持多环境（prod/dev）通过配置区分

3. **DDD 限界上下文对齐**
   - Member：用户、卡、账户、支付通道
   - TicketOrder：订单、取票、票价
   - Payment：支付、签约、退款
   - Ride：行程、交易记录、补站
   - Industry：生码、密钥
   - Blacklist：黑名单（可归属 Member 或独立）

---

### 6.4 为什么不推荐继续拆分更多？

当前项目处于**业务快速迭代期**（大量 if8a_26~if8a_77 接口待实现），过度拆分会导致：

- 分布式事务复杂度飙升（开户→订单→支付→生码 跨 4+ 服务）
- 联调成本指数级增长
- 小团队维护困难（当前看起来是 2-5 人团队）

**建议**：先完成第一步保守合并，把 15 个服务精简到 10 个左右，再根据业务增长逐步演进。

---

### 6.5 当前架构 vs 推荐架构对比

```
当前（15+ 服务）：
  fep-app → account / wallet / pay-sign / collect-ticket / ticket / industry / key / ...

推荐（9 服务）：
  app-gateway → member / ticket-order / payment / industry / ride / acc / device / blacklist
```

**核心改进点：**
- 减少跨服务调用深度（从 4-5 层降到 3 层）
- 消除 account-server ↔ pay-sign-server 的签约状态竞争
- 统一支付网关，回调链路不再跨 2 个服务
- ACC 相关能力统一，联调只需对接一个服务
