## 1 总则

### 1.1 目的与适用范围

1. 【强制】本规范用于统一青岛地铁互联网票务平台（qd-itp）的编码产出，保证**金融级安全、可追溯、可评审、可持续改进**，并为同行评审、验证确认、过程度量提供可核查的判据。
2. 【强制】适用范围：仓根全部 `*-server` 业务模块、`model` / `rpc` / `resource` 公共构件、`web-server` 综管台后端、`web/` 前端、`deploy/` 下的配置与 SQL 脚本，以及新增模块。
3. 【参考】不适用范围：甲方原始规格（只读）、外部系统接口规格原文、`cmmi5/` 评估过程材料、`docs/` 下提示词与业务文档（另按 `docs/提示词/工程与文档规范.md`）、第三方依赖源码。
4. 【强制】判断「某个接口是否存在 / 是否已实现」MUST 直接看 Controller 的 `@RequestMapping` / `@PostMapping` 注解，NEVER 依据提示词或汇总清单推断。

### 1.2 术语与缩略语

| 术语 | 含义 |
|---|---|
| MUST / NEVER | 本仓现行硬约束语气；MUST 为强制，NEVER 为禁止且必须配正向替代 |
| 【强制】/【推荐】/【参考】 | 借自阿里手册的三级约束力；【强制】违反即打回 |
| 真源 | 某类事实的唯一权威文档；同一事实 NEVER 在多处各写一份 |
| JIT 文档 | 按需加载的下沉文档（如各 traps 篇），不进常驻上下文 |
| 自研 adaptor | `resource/micro/mybatis-adaptor` 与 `sql-datasource` 两个基础构件 |
| rpc Client | `rpc/` 模块下 20 个 `*Client`，经 `ProxyWebClient` + `service.*.url` 直连 |
| 白名单状态机 | 枚举 + 迁移表 + `canTransitTo` / `isTerminal` 的状态迁移范式 |
| 客观证据 | CMMI 评估认可的、能证明过程被执行的记录（评审记录、提交记录、度量数据等） |
| PR / VV / MPM / CAR | 同行评审 / 验证与确认 / 管理绩效与度量 / 原因分析与解决 |
| SRS / SDD | 需求规格说明书 / 软件设计文档 |

### 1.3 约束级别与执行策略

1. 【强制】三级定义：【强制】违反即打回，不得合入；【推荐】默认遵守，偏离须在评审记录写明理由并经审核人确认；【参考】建议采纳，不影响合入。
2. 【强制】**存量 / 增量三级执行策略**：① 新写模块、新写类 MUST 全量合规；② 改动存量代码只修「被触碰的那部分」，NEVER 借规范之名做无关格式化 / 重命名 / 大范围重构；③ 【强制】条目在被触碰的代码内仍然生效，不因「保持行为不变」而豁免。
3. 【强制】存量已知不合规形态（`web-server` 的 `I*Service` / `AjaxResult`、`acc-secure-server` 与 `model` 的重复 DTO、多数模块用 String 字面量表达状态）按所在模块既有风格续写，NEVER 造第三种，也 NEVER 模仿这些技术债。
4. 【强制】**金融级适配原则**：支付 / 订单 / 扣款 / 签名链路上，安全与一致性优先级高于风格统一。所有风格类【推荐】条目让位于幂等、状态机白名单、事务边界等【强制】条目。
5. 【推荐】性能极敏感的高频并发代码，方法行数、圈复杂度等【推荐】条目可酌情豁免，但 MUST 在代码注释与评审记录里说明理由；安全与一致性【强制】条目 ANY 情况下不得豁免。

### 1.4 裁剪指南

1. 【强制】项目级裁剪 MUST 在评审记录中登记「裁剪了哪条 / 为什么 / 谁批准 / 有效期」，NEVER 默认全裁或口头约定。
2. 【强制】以下章节 ANY 项目不得裁剪：6 安全规约、第 7.5 节 mapper 六陷阱、10 评审与证据链。
3. 【推荐】仅做静态页面或纯文档改动时可裁剪3  Java 条目、7 持久层条目；仅改后端接口时可裁剪9 前端条目。
4. 【参考】原型 / 一次性验证代码（`employee-card-acc-simulator` 等）可裁剪发布与评审相关条目，但 NEVER 合并进生产模块，NEVER 引用业务模块内部实现。

### 1.5 生效、维护与豁免

1. 【强制】本规范经审核 / 批准后生效；生效前的在途改动按评审记录逐项确认，NEVER 追溯处罚已有提交。
2. 【强制】豁免流程：申请人提出条目号 + 理由 + 影响范围 + 补偿措施 → 技术负责人审核 → 记入评审记录 → 到期复核。NEVER 以「历史代码都这样」为理由豁免。
3. 【强制】每半年复审一次；发生下列情形 MUST 提前复审：生产事故、CAR 结论要求修订、框架大版本升级、跨模块契约变更、甲方规格变更。
4. 【参考】复审结论 MUST 写进修订记录，并同步检查第 10.5 节度量指标是否仍能反映过程性能。

## 2 组织与过程治理

### 2.1 角色与职责

| 角色 | 职责 | 客观证据 |
|---|---|---|
| 开发工程师 | 按本规范编码、自测、填提交说明、发起评审 | 提交记录、自测记录 |
| 评审人（同行） | 按第 10.2 节清单逐项核对、记录问题与结论 | 评审记录 |
| 技术负责人 | 裁决【推荐】条目偏离、批准豁免、审核规范修订 | 审核签字、豁免单 |
| 项目负责人 | 批准规范发布、批准重大裁剪与过程改进项 | 批准签字 |

1. 【强制】评审人 MUST 与作者不同，NEVER 自评自审；涉及支付 / 密钥 / 签名的改动 MUST 追加一名熟悉该链路的评审人。
2. 【推荐】角色可一人多岗，但「编制 / 审核 / 批准」三个签字位 NEVER 由同一人填满。

### 2.2 文档受控与版本

1. 【强制】受控文档四要素齐全：文件编号、版本号、状态（受控 / 作废）、生效日期；缺一即视为不受控，NEVER 作为评估证据。
2. 【强制】版本号采用 `V<主版本>.<次版本>`：条目级修订升次版本，结构性重排或适用范围变更升主版本；修改日期、修订内容、修订人、审核、批准 MUST 同步写进修订记录。
3. 【强制】**单一真源**：本规范的唯一内容源是 `docs/architecture/编码规范.md`（Markdown，受 lint 门禁）；Word 发布版由它生成，NEVER 两份手写内容并行维护。
4. 【推荐】作废版本保留在配置库但明确标注「作废」，NEVER 删除历史版本，NEVER 让作废版本继续被引用。

### 2.3 同行评审（PR）

1. 【强制】以下改动 MUST 走同行评审：新增 / 修改对外接口、支付与订单链路、状态机与事务边界、mapper XML 与 SQL、密钥与签名相关配置、`model` / `rpc` / `resource` 公共构件、菜单与权限 SQL。
2. 【强制】评审记录 MUST 含：评审对象（模块 / 提交标识）、评审人、日期、逐项结论、问题清单与处置、最终结论（通过 / 有条件通过 / 打回）。
3. 【强制】评审发现的问题 MUST 按 `AGENTS.md` 第 5.0 节两档判据登记到 `docs/tracking/问题清单.md`：一次性小缺陷只加索引行；阻塞 / 架构债 / 跨模块契约变更 / 数据一致性或安全风险另建 `IT-<编号>-<简述>.md` 六节文档。NEVER 只修不记录、NEVER 升级凑流程。
4. 【强制】评审记录按链路 + 日期归档到 `docs/reviews/`，**只增不改**；NEVER 事后重写结论。
5. 【推荐】评审前作者先跑完第 10.2 节自查清单，把命令输出贴进评审记录，减少往返。

### 2.4 验证与确认（VV）

1. 【强制】验证门四件套（缺一不可）：后端 `mise exec -- mvn -o clean test-compile -pl <module>`；文档 `python3 docs/提示词/lint-prompts.py` ERROR 0；改 `application*.yml` 后 `itp-ops.sh lint yaml`；前端按 `docs/architecture/web-admin-development-workflow.md` 验证四件套。
2. 【强制】线上改动追加 NodePort 探活 + 服务端日志确认；判定接口异常 MUST 落在日志原文，NEVER 只看 HTTP 200 + UUID `retCode`。
3. 【推荐】把「编译发现不了」的规则写成断言测试（见第 5.6 节），让验证可重复、可机检。
4. 【参考】确认（Validation）关注「做的是不是对的东西」：涉及业务规则的改动 MUST 对照 `docs/business/<业务域>.md` 与甲方规格原文，NEVER 只凭代码自洽判断。

### 2.5 度量与过程性能（MPM）

1. 【强制】可机检的三项过程指标作为基线候选，NEVER 用主观打分代替：

| 指标 | 采集方式 | 目标 |
|---|---|---|
| 文档门禁 ERROR 数 | `lint-prompts.py` 输出 | 恒为 0 |
| 模块 `test-compile` 通过率 | 构建记录 | 100% |
| 状态机白名单单测数 | `*WhitelistTest` / `*StatusMachineTest` 计数 | 随状态机数量只增不减 |

2. 【推荐】可补充：评审缺陷按章节分布（用于定位规范哪一条最常被违反）、线上问题按根因分类、CAR 改进项的效果验证数据。
3. 【强制】度量数据 MUST 真实采集、与项目执行一致，NEVER 为评估造数据、NEVER 补写历史记录。
4. 【参考】ML4 / ML5 关注的是「用统计与量化手段管理过程性能并证明改进有效」，因此度量项 MUST 与改进动作关联，孤立数字不构成高成熟实践证据。

### 2.6 原因分析与解决（CAR）

1. 【强制】触发条件：生产事故、同类缺陷重复出现两次以上、评审缺陷率显著上升、线上变更导致回滚。触发后 MUST 做根因分析，NEVER 只修表象。
2. 【强制】CAR 闭环四步：① 选定问题与数据；② 分析原因（区分直接原因与过程原因）；③ 制定并实施改进动作（常见为「补一条规范条目 + 补一个断言测试 / lint 规则」）；④ 用第 2.5 节度量数据验证有效性。
3. 【强制】根因、方案对比、决策、验证与回滚、流程符合度自评 MUST 写进 IT 文档六节模板（见 `docs/tracking/IT-模板.md`），NEVER 只写在会议纪要里。
4. 【推荐】改进动作落到本规范时，MUST 同步写修订记录并说明触发的 IT 编号，形成「问题 → 根因 → 规范条目 → 度量验证」可追溯链。

### 2.7 培训与宣贯（OT）

1. 【推荐】新成员开工前 MUST 读本文第 1、3、7、9、11 章，并在评审记录里留一次「结对评审」记录。
2. 【推荐】规范升主版本后 MUST 做一次宣贯，保留签到 / 会议纪要 / 材料版本。
3. 【参考】把高频违反条目做成第 10.2 节自查清单，比长篇培训材料更有效。

### 2.8 配置管理与证据链（CM）

1. 【强制】提交按功能点分批，关联任务 / IT 编号；NEVER 一次提交混入无关格式化与多个不相关功能点。
2. 【强制】类名、方法名、URL、端口、状态取值、数据表 owner、菜单变动 MUST 同步回写 `docs/business/<业务域>.md`、`docs/domain/README.md` 与 `docs/architecture/*.md`，细则见 `docs/提示词/工程与文档规范.md` 的回写义务。
3. 【强制】改名 MUST 保留旧名做交叉引用；ADR 正文与撤回记录 NEVER 删改，只在原文旁补注现名。
4. 【强制】证据链示例（评估抽查路径）：需求条目 → 业务提示词 → 提交记录 → 评审记录 → 单测 → 验证门输出 → 上线核验 → 问题清单 / IT 文档 → CAR 改进 → 规范修订记录。任一环缺失即视为不可追溯。

### 2.9 安全与合规

1. 【强制】敏感配置口径以 `docs/ops/environments/跨环境共性.md` 为真源：仓库内明文配置即唯一真源，NEVER 改成「问 DBA / 必填 ENV / 空默认」形态；但密钥不外传、截图打码、日志不打印密钥明文、库表只存加密态。

3. 【推荐】安全类评审结论单独留痕，NEVER 与普通风格问题混在同一条结论里。

## 3 编程规约

### 3.1 命名风格

1. 【强制】代码中的命名 NEVER 以下划线或美元符号开始 / 结束；NEVER 使用拼音与英文混合，NEVER 直接使用中文。项目里 `F2F`、`AGM`、`TVM`、`BOM`、`ACC`、`VL` 属行业通用缩写，视同英文。
2. 【强制】根包 `com.chinasofti.huateng.<模块短名>`，如 `account`、`paysign`、`gatetxnpay`、`acc.es.server`；包名全小写、点分隔、无下划线。NEVER 在业务模块另起根包。
3. 【强制】类名 UpperCamelCase，方法名 / 参数名 / 成员变量 / 局部变量 lowerCamelCase，常量 UPPER_SNAKE_CASE；泛型类型参数用单个大写字母（`T`、`E`）或 `RequestT` 形式。
4. 【强制】新增类沿用所在模块既然后缀，NEVER 自创缩写：

| 对象 | 项目后缀 / 位置 | 备注 |
|---|---|---|
| 接口入口 | `*Controller`；`controller/` 下按 `page` / `app` / `ci` / `internal` / `task` / `notify` 分目录 | 综管台用 RuoYi 原生 controller 布局 |
| 业务层 | `*Service` + `*ServiceImpl` | 综管台例外：`I*Service` |
| 持久层 | `*Mapper` 接口 + 同名 XML | `src/main/resources/mapper/` |
| 请求 / 响应 | `*ReqDTO` / `*RespDTO`；`model/request`、`model/response` | 跨模块对象 MUST 放 `model` 模块 |
| 视图对象 | `*VO`（如 `face-pay-server` 的 `api/page/`） | 运营端返回封装 `ResultVO` |
| 查询 / 分页 | `*Query`、`*SearchQuery`、`page/*View` | 与请求 DTO 分开 |
| 码值 / 常量 | `*ErrorCodeEnum`、`*Enum`、`*Constants`；放 `constant/` | 枚举取值落库即契约，只增不改 |
| 状态迁移 | `*StatusTransition`（如 `SignStatusTransition`） | 不引状态机框架 |
| 异常 | `*Exception`（如 `ServiceException`、`PayGatewayException`） | 按模块全局异常处理器转译 |
| 测试 | `*Test`；专题 `*WhitelistTest` / `*StatusMachineTest` / `*ArchTest` / `*MapperSqlTest` | 见5  |

5. 【强制】跨模块传输对象 MUST 定义在 `model`，NEVER 在业务模块复制一份。已知技术债：`acc-secure-server` 的 `accsecure.model.*` 与 `model/model/security/*` 存在重复 DTO，勿模仿。
6. 【强制】公共请求报文骨架只有 `model/app/ItpCommonRequest` 与 `ItpCommonFormRequest` 两个类，NEVER 再建副本；这两个类只承载报文骨架，不承载签名语义。
7. 【推荐】方法命名用动宾结构；查询用 `get` / `find` / `query` / `list` / `page`，写操作用 `create` / `update` / `delete` / `handle`；布尔返回用 `is` / `has` / `can` 开头。
8. 【推荐】命名体现业务语义而非技术实现：`PaySignInfoDTO` 优于 `DataDTO2`；`GATE_RETRY_QUEUE`（落库重试队列）优于 `TempTable`。
9. 【推荐】常量与状态值集中到 `*Constants` / `*Enum`，放 `constant` 包。注意现状：多数模块用 String 字面量表达状态，**改动状态值 MUST 全局 grep 确认调用方**；新增代码 NEVER 再散落字面量比对。
10. 【强制】NEVER 使用「魔法值」直接出现在业务判断里；已落库的码值 MUST 查 `docs/business/dictionary-detail.md` 核对中文含义与落库列。
11. 【推荐】包名 / 类名避免使用 `Util` / `Helper` / `Manager` 这类无边界后缀；确需工具方法时先查 `docs/architecture/common-components.md` 的复用清单。
12. 【强制】代码与注释中 NEVER 出现侮辱性、歧视性词语（阿里、Google 共同强制）。

### 3.2 常量定义

1. 【强制】NEVER 在代码中直接出现未经定义的字符串常量参与状态判断；状态白名单 MUST 用枚举 + 迁移表表达。
2. 【强制】常量类按业务域划分，NEVER 建一个全模块共享的 `AllConstants` 大杂烩；跨模块共用的码值 MUST 放 `model` 的 `enums` 包。
3. 【推荐】`long` / `Long` 初始赋值用大写 `L`（`0L`），NEVER 小写 `l`，避免与数字 1 混淆。
4. 【强制】枚举取值一旦落库即为数据契约，NEVER 修改已有取值，只能新增；新增后 MUST 同步码值字典与调用方。
5. 【推荐】常量命名带业务前缀，避免 `STATUS_1` 这类无语义命名；`CHANNEL_01_APP` 优于 `TYPE_A`。
6. 【强制】`F2F CHANNEL` 取值 `01` APP / `02` TVM / `03` BOM；设备号规则为「站码前 4 位 + 站内序号」，MUST 复用现有常量，NEVER 重新推导。
7. 【参考】配置项里的常量（如 `service.*.url`）以 `application.properties` 为准，NEVER 在 Java 里再写一份默认值兜底；线上真实地址 MUST 查 K8s Deployment env，NEVER 照抄仓库配置。
8. 【推荐】用一个字符 / 数字表达的码值，MUST 在常量旁写中文注释说明含义与出处规格。
9. 【强制】NEVER 把可变对象声明为 `static final` 常量使用（如 `static final Map` 后到处 put），需要共享配置走 Spring 配置类。
10. 【参考】常量复用优先级：`model/common/constant` → `model/*/enums` → 本模块 `constant` → 新增（须评审）。

### 3.3 代码格式

1. 【强制】源文件 UTF-8、换行 LF、4 空格缩进（前端 `web/` 按 `.editorconfig` 用 2 空格，两者各自遵守），NEVER 用 Tab 缩进。
2. 【强制】单文件一个 top-level class；文件名与 public 类名完全一致；`import` 禁通配符、禁未使用导入；单行一条语句。
3. 【强制】大括号用 K&R 风格；`if` / `else` / `for` / `while` 即使只有一条语句也 MUST 加大括号，NEVER 省略。
4. 【强制】覆盖方法 MUST 加 `@Override`；NEVER 通过实例访问静态成员（用类名限定）。
5. 【推荐】新增代码行宽 ≤ 120；NEVER 用空格做视觉对齐；长参数列表换行后缩进 4 空格。
6. 【强制】`if` / `for` 等关键字与左括号之间加一个空格，二元运算符两侧加空格，逗号后加空格；方法名与左括号之间不加空格。
7. 【推荐】方法体内用空行分隔「参数校验 / 主逻辑 / 结果封装」三段；NEVER 用多行连续空行。
8. 【强制】注释与代码同缩进；NEVER 在行尾堆长注释；NEVER 用注释掉的代码块（墓碑代码）留在仓库，删除并由版本控制追溯。
9. 【强制】`switch` 每个 case MUST 有 `break` / `return` 或注释说明穿透，`default` MUST 存在；优先用枚举 + `switch` 表达式替代多层 `if`。
10. 【参考】仓库最长行约 159 字符、无硬行宽门禁，因此**不设全仓格式化任务**；新增代码按本条执行即可。
11. 【推荐】Lombok 可用（实测 161 个文件使用 `@Data` / `@Builder` / `@Slf4j`），但对外 DTO MUST 显式无参构造 + getter/setter 可预期；NEVER 用 `@Data` 承载带签名语义的公共请求类（其 `toString` 已定制脱敏）。
12. 【强制】构造器注入优先：新 Controller 用 `private final` + 显式构造器（实测新模块已如此），NEVER 在字段上用 `@Autowired` 混用两种风格。

### 3.4 OOP 规约

1. 【强制】`controller` 仅参数校验与路由，NEVER 写业务逻辑；`service` 承载业务逻辑与事务；`entity` / `model` 为 DB 映射，`dto` / `vo` 为传输 / 视图对象。
2. 【强制】方法参数超过 3 个 MUST 封装成对象；NEVER 用 `Map` 作跨层入参 / 返回值；NEVER 用 `Object` 作业务方法返回类型。
3. 【强制】对外接口 DTO MUST 放 `model` 并在对应 rpc Client 补方法；NEVER 把 `entity` 直接作为对外响应返回。
4. 【推荐】所有覆写方法、`equals` / `hashCode` / `toString` 保持契约一致；`toString` NEVER 打印敏感字段。
5. 【强制】NEVER 在构造器中调用可覆写方法，NEVER 在 `@PostConstruct` 里发起远程调用。
6. 【推荐】优先用不可变对象与 `final` 字段；集合类字段在构造时初始化，NEVER 暴露可变内部集合引用。
7. 【强制】工具类若确需新增（默认禁止），MUST 先查 `docs/architecture/common-components.md` 复用清单并在评审记录写明「无可复用」的结论；NEVER 新建 `DateUtils` / `StringUtils`。
8. 【推荐】业务判断用「卫语句 + 早返回」，NEVER 深层嵌套 `if`；圈复杂度高的分支优先抽成状态迁移表 / 策略枚举。
9. 【强制】NEVER 使用 `BigDecimal(double)` 构造金额，MUST 用 `BigDecimal(String)` 或 `BigDecimal.valueOf`；金额比较用 `compareTo`，NEVER 用 `equals`。
10. 【强制】所有涉及金额、票卡数量、费率的字段 MUST 明确单位与精度，NEVER 用 `float` / `double` 承载金额。
11. 【推荐】接口方法声明抛出的受检异常 MUST 有业务语义，NEVER 用 `throws Exception` 一把梭。
12. 【强制】NEVER 在业务模块复制 `model/common/response/CommonResult`、`ResultVO` 等公共封装；统一返回码的 `retCode` / `retMsg` 字段语义 NEVER 擅改。

### 3.5 日期时间

1. 【强制】使用 Java 21 `java.time`（`LocalDateTime` / `LocalDate` / `Instant` / `Duration`），NEVER 使用 `SimpleDateFormat` / `java.util.Date` 的新代码。
2. 【强制】日期格式化模式 MUST 用 `yyyy-MM-dd HH:mm:ss`（`yyyy` 而非 `YYYY`），带时区的场景用 `OffsetDateTime` 明确时区。
3. 【强制】容器默认 UTC：部署侧 MUST 设 `TZ=Asia/Shanghai`；NEVER 在代码里用「+8 小时」硬编码补偿时区。
4. 【强制】`PAY_TXN_DETAIL.PAY_TIME`、`DAILY_TICKET_INSTANCE.COUNTING_*` 是 VARCHAR2，NEVER 当 DATE 类型参与比较或排序；MUST 按既有格式字符串处理，改动前查对应 mapper。
5. 【强制】「运营日期」与「自然日」不是同一概念，跨日场景 MUST 按业务提示词的运营日口径，NEVER 用 `LocalDate.now()` 代替。
6. 【推荐】获取当前时间统一走注入的 `Clock` 或现有时间构件，便于单测固定时间；NEVER 在状态机判断里散落 `System.currentTimeMillis()`。
7. 【强制】定时任务 cron MUST 与 `sys_job` 实际配置一致；Quartz 用内存 JobStore，`QRTZ_*` 表恒 0 行 ≠ 任务没跑，MUST 查 `SYS_JOB_LOG`。
8. 【推荐】时间范围查询两端语义（含 / 不含）MUST 在方法 Javadoc 写清；前端传空白时间范围时后端 NEVER 拼出全表扫描。
9. 【强制】跨模块的日期字符串格式 MUST 与甲方规格一致，NEVER 自行加毫秒 / 改分隔符。
10. 【参考】历史遗留的 `Date` 字段按所在模块既有风格处理，NEVER 在同一次改动里混用新旧 API。

### 3.6 集合处理

1. 【强制】返回集合 / 数组的方法 NEVER 返回 `null`，MUST 返回空集合或空数组；调用方因此不需要到处判空。
2. 【强制】`Arrays.asList()` 返回的是固定长度列表，NEVER 对其做 `add` / `remove`；需要可变列表用 `new ArrayList<>(...)`。
3. 【强制】NEVER 在增强 `for` 循环里直接 `remove` / `add` 元素，MUST 用 `Iterator` 或 `removeIf`。
4. 【推荐】`Map` 遍历用 `entrySet()`；需要按 key 查找时建 `Map` 而非在 `List` 里循环比对。
5. 【强制】`HashMap` 作返回类型时 MUST 明确是否允许 `null` 值；跨层传递 NEVER 用 `Map<String, Object>` 承载业务实体。
6. 【强制】`Collections.emptyList()` / `List.of()` 返回不可变集合，NEVER 传给可能修改它的方法；需要修改先拷贝。
7. 【推荐】集合判空用 `CollectionUtils`（若已有构件）或 `isEmpty()`，NEVER 写 `size() == 0` 与 `== null` 两套散落判断；NEVER 为此新建工具类。
8. 【强制】`subList` 结果是原列表视图，NEVER 长期持有或在原列表修改后继续使用；MUST 拷贝成新列表。
9. 【强制】对账 / 报表类大结果集 MUST 用流式或分片处理，NEVER 一次性把全量数据装入 `List` 再聚合（参见 `docs/business/recon.md` 的分片抽取）。
10. 【推荐】排序 / 去重 MUST 明确比较器与稳定性；涉及金额或交易时间的排序 NEVER 依赖数据库默认顺序。
11. 【强制】`equals` 比较的对象 NEVER 为 `null` 字面量调用，用 `Objects.equals(a, b)` 或常量在前。
12. 【参考】集合转 JSON 统一走 Fastjson2；NEVER 用 `toString()` 拼接当 JSON 返回。

### 3.7 并发处理

1. 【强制】NEVER 引入 Redis / RabbitMQ / Kafka 等中间件；本项目不使用缓存与消息队列，`resource/micro/rabbitmq-adaptor` 是历史遗留基础构件，业务模块 NEVER 引用。
2. 【强制】需要异步或重试时 MUST 用「落库状态 + `@Scheduled` 扫表重试」；需要并发控制时 MUST 用「数据库唯一索引 + `DuplicateKeyException` 兜底」。
3. 【强制】NEVER 在应用内用 `synchronized` / `ReentrantLock` 做跨实例分布式互斥；单副本部署也不能依赖 JVM 锁保证幂等。
4. 【强制】线程池 NEVER 用 `Executors` 快捷工厂创建（无界队列风险），MUST 显式 `ThreadPoolExecutor` 参数并命名线程；NEVER 在请求线程里无超时地等待异步结果。
5. 【强制】`SimpleDateFormat` 非线程安全（见第 3.5 节），NEVER 声明为 `static` 共享；`java.time` 的 formatter 可共享。
6. 【推荐】`ThreadLocal` MUST 在 `finally` 中 `remove()`；tracing 的 `traceId` 传递按 `docs/architecture/runtime-observability-traps.md` 的三行成组开关，NEVER 自建 MDC 方案。
7. 【强制】定时任务无分布式锁的模块 MUST 单副本运行；名单与判据见 `docs/ops/environments/跨环境共性.md`，NEVER 为提速擅自扩副本。
8. 【强制】判断「某个补偿有没有跑」MUST 查 `SYS_JOB_LOG` + 集群 Deployment 实况（是否 0 副本），NEVER 只在模块里找 `@Scheduled`、NEVER 只凭仓库有代码就当线上在跑。
9. 【推荐】并发写同一业务键时，MUST 用 `MERGE INTO` + 状态终态短路，NEVER 先查后写不加唯一约束。
10. 【强制】`CompletableFuture` 等异步编排 NEVER 吞掉异常，MUST 有 `exceptionally` / `whenComplete` 记录日志并落库状态。
11. 【参考】虚拟线程相关 pin / 慢 SQL 拖垮全 JVM 的排查见 `docs/architecture/runtime-observability-traps.md`。
12. 【强制】涉及支付、扣款的重试 MUST 有最大次数与退避策略，NEVER 无限重试；重试键 MUST 与幂等键一致。

### 3.8 控制语句

1. 【强制】`switch` MUST 有 `default`；每个 `case` MUST 显式终止或注释穿透；优先用枚举 `switch` 表达式。
2. 【强制】`if` / `else if` / `else` 链超过 3 层 MUST 改成卫语句、策略枚举或状态迁移表，NEVER 继续堆叠。
3. 【强制】状态判断 NEVER 写成「非终态即可处理」（黑名单式），MUST 用白名单。
4. 【强制】NEVER 在条件表达式里做赋值、NEVER 用 `==` 比较字符串内容；布尔变量 NEVER 与 `true` / `false` 显式比较。
5. 【推荐】复杂条件 MUST 抽成语义化私有方法（如 `canRetry()`），NEVER 用一长串 `&&` / `||` 且不换行。
6. 【强制】三目运算符内 NEVER 嵌套三目；表达式 MUST 保证类型一致，避免 NPE 拆箱。
7. 【强制】`try` 块 MUST 尽量小，只包住真正可能抛异常的代码；NEVER 把整个方法体塞进 `try`。
8. 【强制】循环内 NEVER 做远程调用 / 数据库逐条查询 / 拼装大对象；MUST 批量化或走既有批量接口。
9. 【推荐】`return` 早返回优于多层缩进；但资源释放 MUST 用 try-with-resources，NEVER 因早返回漏关。
10. 【强制】`Optional` 只用于返回值表达「可能为空」，NEVER 用作 DTO 字段 / 方法参数 / 集合元素，NEVER 直接 `get()` 不判空。
11. 【参考】高频分支的性能优化 MUST 有实测依据，NEVER 为「看起来更快」牺牲状态机白名单。
12. 【强制】`assert` NEVER 用于生产参数校验（默认关闭），MUST 用显式校验并抛业务异常。

### 3.9 注释规约

1. 【强制】public 类、对外方法、状态迁移方法 MUST 有中文 Javadoc，写清「做什么 / 前置条件 / 异常语义」，NEVER 复述方法名。
2. 【强制】Javadoc 标签顺序 `@param` → `@return` → `@throws` → `@deprecated`，描述 NEVER 留空。
3. 【强制】注释与代码同缩进、同语言（中文为主）；NEVER 写「已经不存在 / 已被推翻」的墓碑注释，改为断言测试。
4. 【强制】注释和文档里 NEVER 写 `Xxx.java:NNN` 式行号引用，MUST 按类名 / 方法名定位（行号会漂，且 lint 门禁拦截）。
5. 【推荐】「为什么这么写」比「这行做什么」更值得注释：尤其是 WallFilter 绕过、Oracle 别名折叠、时区补偿这类反直觉处理。
6. 【强制】待办注释 MUST 带责任人与问题的 IT 编号（`TODO(姓名, IT-编号)`），NEVER 留无主 `TODO`；完成即删除。
7. 【强制】注释掉的旧代码 MUST 删除，由版本控制追溯；NEVER 以「以后可能要用」为由保留。
8. 【推荐】枚举每个取值 MUST 有中文注释；已落库码值注释 MUST 与 `docs/business/dictionary-detail.md` 一致。
9. 【强制】SQL 正文 NEVER 写注释（见第 7.5 节），说明 MUST 写在 mapper XML 的 `<!-- -->` 或 Java 注释里，且 XML 注释里 NEVER 出现两个连续减号。
10. 【参考】DDL 的 `COMMENT ON` 是数据字典的一部分，NEVER 当普通注释删除。

### 3.10 前后端规约

1. 【强制】前后端交互字段命名 MUST 与甲方规格原文一致（下划线 / 驼峰按各链路既有约定），NEVER 前端擅自改名再在后端兼容两套。
2. 【强制】统一返回封装 `CommonResult`（`retCode` / `retMsg`) 与运营端 `ResultVO` / `ResultMapper` 的语义 NEVER 擅改；错误码 MUST 取自 `*ErrorCodeEnum`。
3. 【强制】HTTP 200 + UUID `retCode` 是本仓常见「业务失败」形态，前端 NEVER 只看 HTTP 状态码判断成功；排查 MUST 落服务端日志原文。
4. 【推荐】分页参数与返回结构 MUST 沿用既有 `page/*View` / `PageHelper` 约定，NEVER 新增第二套分页协议。
5. 【强制】时间字段前后端 MUST 约定格式与时区（见第 3.5 节），NEVER 传时间戳与字符串混用。
6. 【强制】金额字段 MUST 以「分」为单位的整数或明确精度的字符串传递，NEVER 用浮点数 JSON 承载金额。
7. 【推荐】接口版本号 / 路径前缀变动 MUST 同步 `docs/business/` 与前端 `web/src/api/`，NEVER 只改一侧。
8. 【强制】生产错误响应 NEVER 回显堆栈、SQL、密钥、内部 IP；对外只给业务错误码与可展示文案。

### 3.11 其它

1. 【强制】NEVER 使用 `System.out` / `printStackTrace` 输出诊断信息，MUST 走 slf4j（见4 ）。
2. 【强制】NEVER 硬编码环境地址、端口、密钥；`service.*.url` 等 MUST 从配置读取，线上真实值 MUST 查 Deployment env。
3. 【推荐】正则表达式 MUST 预编译为 `static final Pattern`，NEVER 在高频循环里 `String.matches()`。
4. 【强制】`BigDecimal` 除法 MUST 指定精度与舍入模式，NEVER 依赖默认（可能抛 `ArithmeticException`）。
5. 【强制】日志与异常信息里 NEVER 拼接用户输入构造新字符串用于再解析，防止注入与信息泄露。
6. 【推荐】反射 / 动态代理仅在基础构件中使用，业务模块 NEVER 新增；Fastjson2 反序列化 MUST 指定明确类型，NEVER 用 `Object` 接收后再强转。
7. 【强制】外部输入（APP / 设备 / 第三方渠道）MUST 先校验再使用，NEVER 假定字段齐全；`bizData` 解析失败 MUST 走明确兜底分支，且兜底决策 MUST 打 INFO 日志（如 `LEGACY|NEW`）。
8. 【参考】代码生成器的模板是 RuoYi 风格，NEVER 用它生成业务模块代码（见 `docs/architecture/web-server.md`）。

## 4 异常与日志规约

### 4.1 错误码

1. 【强制】错误码统一放 `*ErrorCodeEnum`（`constant` 包），NEVER 在业务代码里散落字符串错误码。
2. 【强制】新增错误码 MUST 先查 `docs/business/dictionary-inventory.md` 与 `dictionary-detail.md`，确认不与既有码值冲突；落库码值 NEVER 修改已有取值。
3. 【强制】错误码与用户可见文案分离：后端返回 `retCode` / `retMsg`，文案 NEVER 含堆栈 / SQL / 内部 IP。
4. 【推荐】错误码按链路分段（APP 域 / 设备域 / 支付域 / 对账域），新增码值在注释里写明来源规格章节。
5. 【强制】第三方渠道返回码 MUST 在接入层转译成本项目错误码，NEVER 把渠道原始码透传给前端。
6. 【参考】排查「返回 Spring 原生 500」时先看异常 message 是否为 `null`（见第 7.5 节第 6 条），NEVER 一律归因于业务错误码。

### 4.2 异常处理

1. 【强制】NEVER 捕获异常后不做任何处理（Google Java Style 6.2）：要么按模块全局异常处理器转译，要么记日志并保留 cause，要么写明为何忽略。
2. 【强制】NEVER `e.printStackTrace()`；NEVER 只 `log.error(e.getMessage())` 丢掉堆栈，MUST `log.error("...", e)` 或等价地把异常对象作为最后一个参数。
3. 【强制】`throw` 业务异常时 MUST 保留 cause 与业务上下文（订单号 / 业务键），NEVER 只抛「处理失败」。
4. 【强制】`finally` 中 NEVER `return`；资源关闭 MUST 用 try-with-resources。
5. 【强制】NEVER 用异常做流程控制（如靠捕获 `DuplicateKeyException` 之外的异常判断分支）；`DuplicateKeyException` 作幂等兜底是项目明确允许的唯一形态。
6. 【强制】`@Transactional` 方法内 NEVER 吞掉异常导致事务静默提交；捕获后 MUST 重新抛出或显式标记回滚。
7. 【强制】全局异常处理器按模块各一份（`GlobalExceptionHandler` / `PaySignExceptionHandler` / `TicketExceptionHandler` 等），新增模块 MUST 复用 `resource/micro/web` 的公共处理器，NEVER 另造第三套返回形态。
8. 【推荐】自定义异常继承 `BaseException` 家族（web-common）或模块内既有基类，NEVER 直接裸抛 `RuntimeException`。
9. 【强制】RPC 调用失败 MUST 按 `RpcOutcome` 表达结果与错误分类，NEVER 用 `boolean` 或 `null` 表达；细则见 `docs/architecture/transaction-and-consistency.md`。
10. 【强制】排查「明明有全局异常处理器却返 Spring 原生 500」时 MUST 先看异常自身 `getMessage()` 是否为 `null`：`resource/micro/web` 的 `ApiErrorResponse` 会执行 `ex.getMessage().length()`，`MyBatisSystemException` 的 message 恒为 `null`，会导致 `@RestControllerAdvice` 自身抛 NPE。
11. 【推荐】可预期的业务拒绝（如「风险组名称已存在」）返回带 `code:"500"` 的业务报文；Spring 原生 500 报文（body 无 `retCode`）是处理器自身失败，两者 NEVER 混淆。
12. 【强制】异常日志 MUST 带业务键与 traceId 可关联的上下文，NEVER 只打「系统异常」。
13. 【参考】`TerminationException` 等特定语义异常按所在链路既有用法续写，NEVER 扩大其捕获范围掩盖状态机错误。

### 4.3 日志规约

1. 【强制】统一 slf4j：`private static final Logger log = LoggerFactory.getLogger(Xxx.class)` 或 `@Slf4j`，同一模块内 NEVER 混用两种声明风格。
2. 【强制】日志用 `{}` 占位符，NEVER 字符串拼接；实测仓库中 `{}` 占位符 2729 处、拼接 93 处，新代码 NEVER 增加后者。

3. 【强制】日志级别：ERROR 为需要人工介入的失败；WARN 为可自愈的降级 / 兜底；INFO 为关键业务节点与决策；DEBUG 为排障明细。NEVER 用 ERROR 打正常业务拒绝。
4. 【强制】NEVER 打印密钥、签名明文、完整卡号、口令；`ItpCommonRequest.toString` 已对 `sign` 恒定脱敏，NEVER 改成打印真实签名值。
5. 【强制】注意 `bizData` 会完整进日志：打印请求对象前 MUST 确认无敏感字段；`fep-alipay-server` 的 controller 有多处 `log.info(... request)`，新增同类日志前先核对。
6. 【强制】关键链路 MUST 打可关联的业务键（订单号 / 逻辑卡号 / `thirdUserId`），NEVER 只打「开始处理 / 处理完成」。
7. 【推荐】用户分流决策处 MUST 打 INFO 日志标明 `LEGACY|NEW` 与判据，便于核查旧 / 新 ITP 分发是否正确。
8. 【强制】日志落盘：21 个 Java 应用挂 PVC `app-logs-v2` → `/home/javaapp/app/logs`，统一 `log4j2-linux.xml` 含 VictoriaLogs appender；NEVER 自定义第二套日志文件名。
9. 【强制】进程未到 Ready 时 `log4j2-linux.xml` 不加载、不产 `*.log`、不发 VL；排查启动期问题 MUST 看 Pod 控制台输出，NEVER 断言「没有日志 = 没启动」。
10. 【推荐】VL 的 app 名 ≠ Deployment 名（如 `face-pay-server` → `itpagm`、`fep-dev-server` → `fep-dev`），查日志 MUST 现查映射表，NEVER 按 Deployment 名直接搜。
11. 【强制】NEVER 在循环里打 INFO / ERROR 日志；批量任务按批次汇总打点。
12. 【参考】tracing 开关「三行成组」与 `%X{traceId}` 恒空的排查见 `docs/architecture/runtime-observability-traps.md` 与 `docs/architecture/common-components.md`。

### 4.4 可观测性与链路

1. 【强制】新增接口 MUST 保证 traceId 能贯穿入口到下游，NEVER 在异步 / 线程池边界丢失；改 env 开 tracing MUST 走 CloudOS `advanced-config`，NEVER 用 kubectl patch（会被平台回收）。
2. 【强制】排查入口链路按 `docs/ops/入口服务链路排查规范.md`：确认现象 + traceId + 报错原文 → 追 traceId → 查 `docs/ops/定位排查手册.md` 对应症状。
3. 【推荐】关键业务指标沿用 `resource/micro/web` 已有的 prometheus 自定义指标（`web.running` / `web.mvc.timeout.cnt` / `log.error.cnt` 等），NEVER 另造同名指标。
4. 【强制】判定「接口是否正常」NEVER 只看 HTTP 状态码，MUST 结合服务端日志原文与业务返回码。

### 4.5 敏感信息与脱敏

1. 【强制】日志、异常、接口响应、截图 NEVER 出现数据库口令、`token.secret`、私钥、signKey 明文；对外材料 MUST 打码。
2. 【强制】库表只存加密态；NEVER 为了排障临时把明文密钥落库或写入临时文件。
3. 【推荐】手机号 / 证件号 / 卡号在日志与运营页面按既有脱敏规则展示，NEVER 新增未脱敏字段。
4. 【强制】涉及敏感配置的改动 MUST 提示人工复核，NEVER 在评审记录里回显口令值。

## 5 单元测试规约

### 5.1 基本原则（AIR / BCDE）

1. 【强制】AIR：Automatic（自动化，可 CI 复跑）、Independent（用例间无顺序依赖）、Repeatable（不依赖真实环境数据与真实时间）。
2. 【强制】测试 NEVER 依赖测试环境数据库、真实支付网关、真实集群；外部依赖 MUST 用 Mockito mock 或 Fixture。
3. 【推荐】BCDE：Border（边界值）、Correct（正确输入）、Design（按设计文档构造）、Error（错误输入与异常分支）。
4. 【强制】断言 MUST 明确，NEVER 用「不抛异常即通过」代替断言；每个用例至少一个业务语义断言。
5. 【参考】NEVER 为覆盖率数字而写无意义测试；状态迁移、边界判据、事务边界优先。

### 5.2 命名与目录

1. 【强制】测试类统一 `*Test`；实测 132 个测试 `.java` 中 129 个如此，辅助类可用 `*Fixture` / `*Results`。
2. 【强制】专题命名沿用：`*WhitelistTest`（状态白名单）、`*StatusMachineTest`、`*TransitionTest`、`*ArchTest`（架构约束）、`*MapperSqlTest`、`*CharacterizationTest`、`*GuardTest`。
3. 【强制】测试包路径与主代码包路径一致；新增状态机 MUST 同时新增对应 `*WhitelistTest`。
4. 【推荐】测试方法名用 `shouldXxxWhenYyy` 或中文语义化命名，NEVER `test1` / `test2`。
5. 【强制】NEVER 使用 `*Tests` / `*IT` / `*TestCase` 命名（实测仓库无此形态），避免构建插件扫描口径不一致。

### 5.3 框架与断言

1. 【强制】JUnit 5 Jupiter（`org.junit.jupiter.api.Test`）+ Mockito（`@ExtendWith(MockitoExtension.class)`、`@Mock`、`ArgumentCaptor`）；NEVER 引入 JUnit4 / TestNG / Spock 新用例。
2. 【强制】断言用 `org.junit.jupiter.api.Assertions` 静态导入（`assertEquals` / `assertTrue` / `assertNull` / `assertThrows`），个别已有 AssertJ 用例按原文件风格续写，NEVER 在同一文件混用两套断言风格。
3. 【强制】`@SpringBootTest` 极少（实测 3 处），新增前 MUST 说明为何需要起容器；绝大多数单测 MUST 是纯 JVM 测试。
4. 【推荐】验证交互用 `verify` + `ArgumentCaptor`，NEVER 依赖 mock 调用顺序推断业务正确性。
5. 【强制】异常分支 MUST 用 `assertThrows` 断言异常类型与关键上下文，NEVER 用 `try-catch + fail()` 手写。

### 5.4 状态机与白名单测试

1. 【强制】状态机改动 MUST 配 `*WhitelistTest` 覆盖：允许的前置状态、禁止的前置状态、终态、未知状态、重复事件。
2. 【强制】测试 MUST 断言「除白名单外的所有状态一律拒绝」，NEVER 只测几个允许分支就结束。
3. 【推荐】用参数化测试遍历枚举所有取值，新增状态值时测试自动覆盖，NEVER 手工补几个用例。
4. 【强制】状态迁移表与测试 MUST 同源：新增迁移 MUST 同步改枚举、迁移表与白名单单测三处。

### 5.5 架构约束测试（ArchTest）

1. 【推荐】把「编译发现不了」的规范写成断言测试：`PaySignTransactionBoundaryArchTest` 已示范事务边界检查，新增同类约束时优先沿用该形态。
2. 【强制】架构测试 NEVER 依赖反射扫描全仓源码树导致构建极慢，MUST 限定目标包。
3. 【参考】可机检的规范条目优先沉淀为 lint 规则或 ArchTest，而不是写在文档里靠人记。

### 5.6 Mapper / SQL 测试

1. 【推荐】mapper XML 改动 MUST 跑 `xmllint --noout <file>`；新增含可空列的写语句 MUST 有对应参数 `jdbcType` 检查（可写 `*MapperSqlTest` 断言 XML 结构）。
2. 【强制】NEVER 用 H2 / 内存库「等价替代」Oracle 验证运行时陷阱（WallFilter、别名折叠、`JdbcType.OTHER` 都只在 Oracle 暴露），判据 MUST 落在 Oracle 实库或已有事故结论。

### 5.7 覆盖率与度量

1. 【推荐】新增业务逻辑的分支覆盖率目标由模块自定并在评审记录说明；状态机 / 幂等 / 事务边界 MUST 100% 分支覆盖。
2. 【强制】度量数据 MUST 真实采集，NEVER 为评估虚报覆盖率。
3. 【参考】第 2.5 节的过程指标包含状态机白名单单测数，删测试 MUST 在评审记录说明原因。

### 5.8 测试禁令

1. 【强制】NEVER 在单测里 `Thread.sleep` 等待异步结果；MUST 用可注入的 `Clock` / 显式状态轮询或同步化被测逻辑。
2. 【强制】NEVER 修改 `sys_config` / `sys_job` 等带 LocalCache 的运行期数据来「造测试条件」；直接改库不生效且污染环境。
3. 【强制】NEVER 在测试里硬编码线上地址 / 口令；测试配置与生产配置 MUST 分离。
4. 【强制】`@Transactional` 单测 NEVER 依赖真实事务回滚验证业务幂等，MUST 用唯一索引 + `DuplicateKeyException` 的真实形态验证。

## 6 安全规约

> 本项目是支付 / 票务金融级系统，本章条目优先级高于所有风格类条目。对应 CMMI V3.0 的 Enabling Security 与 Managing Security Threats & Vulnerabilities 实践域思路。

### 6.1 敏感配置与密钥

1. 【强制】仓库内明文密码 / 配置即唯一真源（口径见 `docs/ops/environments/跨环境共性.md`）：直列不掩码，NEVER 改成「问 DBA / 运维 / 必填 ENV / `${ENV:}` 空默认」形态。改密 MUST 同步真源表、模块 properties、运维脚本中的配置档与迁移 SQL。
2. 【强制】密钥 / 口令 NEVER 外传、NEVER 出现在截图与对外材料、NEVER 在日志中打印明文；库表只存加密态。
3. 【强制】涉及口令 / 私钥 / `signKey` / 3DES / `token.secret` 的改动 MUST 读 `AGENTS.md` 第 4 节安全红线与 `docs/ops/environments/跨环境共性.md` 对应章节，并触发人工复核。
4. 【强制】NEVER 擅自修改现有加密 / 签名逻辑。四条链路的加签 / 验签算法互不相同（摘要式 SHA1/MD5 + signKey、`AccSecureSignUtils`、fastjson2 摘要、`signType=00` 不签），共用 `ItpCommonRequest` 不等于共用签名语义，NEVER「顺手统一」。
5. 【推荐】涉及密钥审批端点等关键路径的改动，MUST 对照 `docs/tracking/IT-061-key-server密钥审批端点安全红线门控.md` 的门控结论。
6. 【强制】线上真实地址 / 口令 / 版本 MUST 查 K8s Deployment env 与 image tag，NEVER 只看仓库 properties 或 pom（集群 env 会覆盖 jar 内配置）。

### 6.2 加密与签名

1. 【强制】签名 / 验签 MUST 复用既有构件与算法，NEVER 自行实现摘要拼接；改动 MUST 由熟悉该链路的评审人复核。
2. 【强制】`SHA256WithRSA` / JJWT / SM2 等既有用法按所在模块续写，NEVER 在同一次改动里更换算法或密钥长度。
3. 【强制】签名失败 MUST 明确拒绝并留日志，NEVER 降级为「验签失败也放行」。
4. 【推荐】随机数 MUST 用 `SecureRandom`，NEVER 用 `Math.random()` 或时间戳构造令牌 / 设备随机因子。
5. 【强制】`sign` 字段在 `toString` / 日志 / 响应中 NEVER 出现真实值；脱敏逻辑 NEVER 被「方便排障」为由关闭。
6. 【参考】JBDC 连接串、HSM 交互、AGM 密钥同步等链路的约束见 `docs/business/security-hsm.md` 与 `docs/business/common-services.md`。

### 6.3 参数校验

1. 【强制】外部输入（APP / 闸机 / TVM / BOM / 第三方渠道）MUST 在 `controller` 层做参数校验，NEVER 假定字段齐全后直接进 service。
2. 【强制】校验失败 MUST 返回明确错误码，NEVER 抛 NPE 后被全局异常处理器包成 UUID `retCode`。
3. 【强制】`bizData` 解析失败 MUST 走明确兜底分支，且分发决策 MUST 打 INFO 日志（`thirdUserId` / `LEGACY|NEW`），NEVER 静默走默认链路。
4. 【推荐】长度、枚举范围、金额上下界、时间区间 MUST 在服务端独立校验，NEVER 只依赖前端校验。
5. 【强制】分页参数 MUST 有上限，NEVER 允许前端传超大 `pageSize` 拖垮 Oracle。

### 6.4 SQL 注入与 WallFilter

1. 【强制】SQL 参数 MUST 用 `#{}` 绑定，NEVER 用 `${}` 拼接用户输入；确需动态列名 / 排序 MUST 用白名单枚举映射，NEVER 直接拼接。
2. 【强制】NEVER 通过放宽 `wall.config.comment-allow` 等全局配置绕过 Druid WallFilter，那等于降低整体注入防护等级。
3. 【强制】mapper 六陷阱（第 7.5 节）中「SQL 正文写注释」「`where 1 = 1`」两条既是运行时缺陷也是注入防护相关约束，NEVER 违反。
4. 【推荐】拼接 `order by` 时 MUST 用 `<choose>` 白名单，NEVER 把前端字段名原样透传。

### 6.5 XSS / CSRF / 重放

1. 【强制】运营端输出到页面的用户可控内容 MUST 转义；`web-common` 已有 XSS 与 Referer 过滤，NEVER 绕过。
2. 【强制】涉及支付 / 扣款 / 签约的请求 MUST 有幂等键与时间戳校验，NEVER 允许同一报文无限重放。
3. 【推荐】回调接口 MUST 校验来源签名与业务键，NEVER 只凭「收到就处理」。
4. 【强制】`token.secret` 等鉴权配置 NEVER 使用弱口令 / 默认值上线；更换后所有已签发 JWT 失效，需低峰期执行。

### 6.6 权限与鉴权（综管台）

1. 【强制】综管台鉴权走 Spring Security + JJWT，新增后台接口 MUST 配权限标识并补菜单 SQL，NEVER 只加路由不加权限。
2. 【强制】`web-admin` 的 controller NEVER 直调业务服务（会滑向聚合层），运营查询接口后端 MUST 落在业务模块的 `/page/**`。
3. 【强制】菜单 / 用户 / 角色 / 权限 / 定时任务相关表（`sys_*`）的变更 MUST 走 `web-server` 既有 SQL 组织方式，NEVER 手工改运行期 `sys_job` 期望生效（Quartz 内存 JobStore，须重启 web-admin）。
4. 【推荐】数据权限切面按 `web-framework` 既有实现复用，NEVER 在业务方法里手写角色判断。

### 6.7 文件上传与导出

1. 【强制】上传文件 MUST 校验类型、大小、文件名，NEVER 用原始文件名直接落盘；导出 MUST 走 `docs/architecture/excel-import-export-framework.md` 的既有框架。
2. 【强制】ACC 文件摆渡 / 对账文件投递 MUST 校验文件命名与内容行数，NEVER 覆盖同批文件；命名见 `docs/ops/对账文件上传命名与替换说明.md`。
3. 【推荐】导入失败 MUST 给出行级错误定位，NEVER 只报「导入失败」。

### 6.8 审计与留痕

1. 【强制】关键业务操作（支付、退款、密钥审批、参数下发、菜单权限变更）MUST 有操作日志与业务键，NEVER 只靠应用日志推断。
2. 【强制】生产数据变更 MUST 先存原值并给还原 SQL，测试库演练后走审批，NEVER 直接执行 DDL/DML。
3. 【推荐】安全类问题的评审结论单独留痕，并与 IT 文档关联，形成可追溯证据链。

## 7 Oracle 数据库规约

### 7.1 建表规约

1. 【强制】表名 / 字段名沿用现有大写下划线风格；新增表 MUST 明确所属域与 owner（见 `docs/domain/README.md` 与 `docs/ops/域表owner归属字典.md`）。
2. 【强制】每张表 MUST 有主键；支付 / 订单 / 扣款相关表 MUST 有业务唯一键（幂等键），NEVER 只靠应用判重。
3. 【强制】字段类型 MUST 与甲方规格一致：注意 `PAY_TXN_DETAIL.PAY_TIME`、`DAILY_TICKET_INSTANCE.COUNTING_*` 是 VARCHAR2，NEVER 当 DATE / NUMBER 处理。
4. 【推荐】建表脚本放 `*-schema.sql`，变更脚本放 `*-migration.sql`，两者 NEVER 混写。
5. 【强制】`COMMENT ON` 注释是数据字典的一部分，NEVER 当普通注释删；改字段语义 MUST 同步注释。
6. 【强制】NEVER 在生产库直接执行 DDL；按 `docs/提示词/任务路由表.md` 的「按域分库 / 迁移」行：备份（`BAK_<表>_<日期>` CTAS）+ 还原 SQL + 测试库演练 + 审批。
7. 【推荐】新增列 MUST 明确是否可空；可空列在 mapper 写语句里 MUST 有 `jdbcType`（见第 7.5 节）。

### 7.2 索引规约

1. 【强制】幂等唯一索引是并发控制的第一道闸门，NEVER 用 JVM 锁替代；冲突时以 `DuplicateKeyException` 兜底。
2. 【推荐】组合索引字段顺序 MUST 按实际查询谓词与选择性设计，NEVER 照抄其它表。
3. 【强制】NEVER 在低基数字段上单独建索引指望提升查询；NEVER 为「以后可能用」预留大量索引。
4. 【推荐】分区表的本地 / 全局索引选择 MUST 结合分区维护策略，改动前查 `docs/ops/生产数据库容量规划.md`。

### 7.3 SQL 语句

1. 【强制】NEVER 用 `SELECT *` 作为业务查询返回列，MUST 显式列出字段；`resultMap` 与列名 MUST 对应。
2. 【强制】`count(*)` / `sum()` 的 NULL 语义 MUST 明确；金额聚合 NEVER 用 `float`。
3. 【强制】分页 MUST 用 PageHelper 或既有 Oracle 分页范式，NEVER 用 MySQL 的 `LIMIT`。
4. 【强制】`order by` MUST 有确定性排序键（建议追加主键），NEVER 依赖默认顺序；分页查询尤其重要。
5. 【推荐】`IN` 列表 MUST 有上限并分批，NEVER 拼出超长 `IN` 触发 Oracle 上限。
6. 【强制】NEVER 在 SQL 中隐式转换类型：`VARCHAR2` 时间列与日期比较 MUST 按既有格式处理，NEVER 依赖 `TO_DATE` 隐式转换。
7. 【强制】排查「编译单测全过、只在生产 Oracle 才炸」MUST 先读 `docs/architecture/mybatis-oracle-runtime-traps.md`，NEVER 只看 HTTP 状态码。

### 7.4 ORM 映射（自研 adaptor）

1. 【强制】持久层统一走 `resource/micro/mybatis-adaptor` 与 `sql-datasource`，NEVER 直接写原生 JDBC 或标准 MyBatis 注解；唯一遗留是 `collect-pay-server` 的 `OrderSeqMapper`（取序列），NEVER 再新增同类写法。
2. 【强制】mapper XML 与接口同名、`namespace` = 接口全限定名，放 `src/main/resources/mapper/`；统一 `mybatis.mapper-locations=classpath*:mapper/*.xml`。
3. 【强制】统一返回封装与公共 DTO MUST 复用 `model`，NEVER 在业务模块复制。
4. 【强制】`resultType` 依赖列别名的字段映射，NEVER 改动子查询里的驼峰别名（见第 7.5 节第 4 条）。
5. 【推荐】改动 mapper XML 后 MUST 跑 `xmllint --noout <file>` 逐个校验。
6. 【强制】PageHelper 与自研 adaptor 的装配约定按 `docs/architecture/common-components.md` 执行，NEVER 混用两套分页写法。

### 7.5 mapper 六条运行时陷阱（提交前逐项核对）

> 这六条同族：编译、单测、`xmllint` 全部发现不了，**只在 Oracle 运行时炸**，且常被全局异常处理器包成 HTTP 200 + UUID `retCode`。写 mapper 前 MUST 读 `docs/architecture/mybatis-oracle-runtime-traps.md` 全文。

| # | 规则 | 触发条件 | 典型后果 |
|---|---|---|---|
| 1 | SQL 正文 NEVER 写注释（`--` / `/* */`），说明写进 XML 注释或 Java 注释 | Druid WallFilter `commentAllow=false` | UPDATE 静默失效，支付状态卡 `PROCESSING` |
| 2 | NEVER 用 `where 1 = 1` 打头 + 全可选 `<if>`，MUST 用 `<where>` | 筛选条件全空 | `select alway true condition not allow`，默认加载必失败 |
| 3 | XML 注释里 NEVER 出现两个连续减号 | XML 解析失败 | 服务启动即挂，Pod Running 但端口不监听 |
| 4 | 子查询起了驼峰别名，外层 MUST 引用别名，NEVER 引用物理列名 | Oracle 折叠别名为大写 | `ORA-00904`，页面 100% 报错 |
| 5 | 写语句参数 MUST 显式写 `jdbcType` | 前端传 `null` | `无效的列类型: 1111`，被包成 message 为 null 的异常 |
| 6 | 排查「全局异常处理器却返 Spring 原生 500」MUST 先看异常 message 是否为 `null` | `ApiErrorResponse` 对 null message 调 `length()` | `@RestControllerAdvice` 自身抛 NPE，回落 BasicErrorController |

1. 【强制】第 1、2、3 条 NEVER 通过放宽 WallFilter 或全局 `mybatis.configuration.jdbc-type-for-null` 绕过，前者降低注入防护，后者改所有模块公共行为。
2. 【强制】第 5 条 NEVER 用「把 null 归一成空串」绕过，那会改变列语义。
3. 【强制】第 4 条 NEVER 去动子查询里的别名，`resultType` 字段映射依赖它；MUST 改外层引用。
4. 【强制】第 6 条判据：HTTP 200 + UUID `retCode` 是业务拒绝；Spring 原生 500（body 无 `retCode`）是处理器自身失败，两者 NEVER 混淆。
5. 【推荐】六条核对结果写进评审记录，作为 VV 证据。

### 7.6 分区表

1. 【强制】写入分区表前 MUST 现查分区上限；历史上 8 张 RANGE 分区表只建到 `P202612`，NEVER 凭文档清单判断覆盖范围。
2. 【推荐】跨分区查询 MUST 评估是否需要按分区键裁剪，NEVER 无条件全分区扫描。
3. 【强制】分区维护脚本 MUST 按 `*-migration.sql` 组织并走审批，NEVER 运行期手工 `ADD PARTITION`。

### 7.7 幂等与一致性

1. 【强制】支付、订单、扣款相关表 MUST 有幂等设计（唯一索引 / 防重表）与分布式一致性方案。
2. 【强制】统一形态为「唯一索引 + `DuplicateKeyException` 兜底 + `MERGE INTO` + 状态终态短路」，NEVER 自行换一套。
3. 【强制】「按业务键幂等」的远端资源 NEVER 在事务失败分支回滚；细则见 `docs/architecture/transaction-and-consistency.md`。
4. 【推荐】乱序通知覆盖状态的问题 MUST 用终态短路 + 版本号 / 时间戳判据，NEVER 靠「后到的覆盖先到的」。

### 7.8 迁移脚本与变更

1. 【强制】`*-schema.sql` 与 `*-migration.sql` 分界 NEVER 打破；迁移脚本 NEVER 直接在生产库执行。
2. 【强制】真 DML 通道走本机 `oracledb` thin 直连：变更前建 `BAK_<表>_<日期>` CTAS、给还原 SQL、测试库演练、审批后执行。
3. 【推荐】迁移脚本 MUST 幂等可重跑，NEVER 依赖「只执行一次」的假设。
4. 【强制】表 owner / 字段语义变动 MUST 回写 `docs/domain/README.md` 与业务域文档。

### 7.9 统计与报表

1. 【推荐】统计类查询按 `docs/business/recon.md` 的分片抽取 / 流式聚合范式，NEVER 一次性装载全量结果。
2. 【强制】综管台 `/page/**` 统计接口的时间范围为空时 MUST 有默认边界，NEVER 拼出全表扫描。
3. 【参考】`count` / `sum` 结果在 Java 侧 MUST 处理 `null`（无行时 `sum` 返回 null）。

## 8 工程结构与构建规约

### 8.1 模块分层

1. 【强制】仓库为平铺多模块（无注册中心、无网关），每个 `*-server` 独立 Spring Boot 应用；`model` / `rpc` / `resource` 为公共构件。
2. 【强制】分层职责与落点对照：

| 落点 | MUST | NEVER |
|---|---|---|
| `controller` | 参数校验、路由、调用 service | 业务逻辑、直接调 mapper、事务注解 |
| `service` / `service/impl` | 业务逻辑、`@Transactional`、编排 | 直接拼 SQL、硬编码地址 |
| `entity` / `model` | DB 映射、传输对象 | 承载签名语义、打印敏感字段 |
| `mapper` 接口 + XML | SQL、参数绑定 | 标准 MyBatis 注解（唯一遗留除外） |
| `rpc` Client | 服务间调用封装 | 返回 boolean、在事务内发起调用 |
| `config` / `constant` | 配置装配、码值 | 业务判断、状态字面量 |

3. 【强制】依赖方向 `resource/micro → model + rpc → 业务模块`，NEVER 反向；`model` / `rpc` 版本号恒定、NEVER 升级，改动后只 `mvn install`。
4. 【强制】改 `model` 的 DTO 加字段后 MUST 重建链路上每一个经手该 DTO 的模块镜像，NEVER 只重建终点服务（否则 Fastjson2 静默丢字段）。
5. 【强制】综管台另成一套：`web-admin` → `web-quartz` / `web-generator` / `web-system` → `web-framework` → `web-common`，NEVER 让 `web-common` 反向依赖上层（见 `docs/architecture/web-server.md`）。

### 8.2 二方库与依赖

1. 【强制】NEVER 引入 Jackson / Gson 处理核心业务报文、Feign / Dubbo、Redis / MQ、新工具类；统一 Fastjson2。
2. 【强制】新增第三方依赖 MUST 在评审记录写明用途、版本、许可证与「无可复用构件」的结论，NEVER 为单个小功能引入框架。
3. 【强制】子模块各自以 `spring-boot-starter-parent` 为 parent，JDK / Maven 版本由 mise 管；NEVER 裸跑 `mvn` / `java`。
4. 【推荐】依赖升级 MUST 单独提交，NEVER 与业务改动混在一起；框架大版本升级按 `docs/提示词/任务路由表.md` 的对应行评估。

### 8.3 配置管理

1. 【强制】主配置以 `application.properties` 为主（实测 27 个模块中 24 个），仅 `face-pay-server` / `collect-pay-server` 用 `application.yml`；新增模块 NEVER 无理由换格式。
2. 【强制】改 `application*.yml` 后 MUST 跑 `itp-ops.sh lint yaml`（语法 + 重复键门禁）。
3. 【强制】服务间地址读 `service.*.url`；RPC 地址 MUST 现查并注入 `SERVICE_*_URL`，NEVER 全指向同一命名空间（历史事故见 `docs/tracking/IT-016-红岛服务地址指向测试命名空间.md`）。
4. 【强制】改应用 env MUST 走 CloudOS `PATCH /apps/{uuid}/advanced-config`：`env` 全量替换且 MUST 取 `metadata.env`，NEVER 用 kubectl patch（会被平台回收）。
5. 【强制】线上真实配置 MUST 查 Deployment env，`deploy/k8s/` 的 manifest 只作模板，NEVER 当现状。
6. 【推荐】`sys_config` 有 LocalCache，直接改库不生效；运行期配置变更 MUST 走既有刷新入口。

### 8.4 构建与验证命令

1. 【强制】所有 Maven 命令 MUST 用 `mise exec -- mvn ...`（裸 `mvn` 落到 mise 全局默认版本，非项目指定）。
2. 【强制】构建顺序 NEVER 颠倒：`resource/micro`（仅改了自研持久层或公共构件时）→ `model` + `rpc` → 目标模块。
3. 【强制】验证改动 MUST `mise exec -- mvn -o clean test-compile -pl <module>`；跑依赖已改 `model` / `rpc` 的模块测试 MUST 带 `-am`。
4. 【强制】NEVER 从根 pom 跑全量（会带进 `employee-card-acc-simulator` 假失败），NEVER 靠全量 `mvn compile` 判断。
5. 【强制】出 jar：`mise exec -- mvn -o -pl <module> -am package -Dmaven.test.skip=true`；用 `maven.test.skip` 而非 `skipTests`。
6. 【强制】NEVER 在本机跑 `docker buildx` 构建 x86/amd64 镜像（Apple Silicon 模拟构建会迅速吃满磁盘）；本机只出 jar，镜像由远端产出。
7. 【推荐】发版前按 `docs/ops/构建与发布.md` 与技能 `qditp-deploy-release` 执行；起始版本 MUST 取线上实际，NEVER 照 pom / 文档抄。

### 8.5 版本与发布

1. 【强制】发版必升版本末位 +1，段上限 99 进位；NEVER 覆盖同 tag。算法真源是 `docs/ops/environments/scripts/itpops/core/version.py`。
2. 【强制】测试环境发布首选云管台链（`itp-ops.sh buildx --env test` 出镜像 + `cloudos deploy` 切镜像），k8s 链仅云管台不可达时兜底。
3. 【强制】测试 / 红岛生产环境 NEVER 混用；生产发布 MUST 二次确认 + 回滚预案。
4. 【强制】就绪判据看 **Pod 级**（image tag == 目标且 Ready、Pod 数 == 副本数），`updatedReplicas` 会误判。
5. 【强制】推镜像看 `digest:` / `Pushed`，NEVER 只看退出码；rollout 后 MUST 比对 Pod imageID 与推送 digest。
6. 【强制】前端本仓只出 zip，发版 MUST 走云平台；回滚点 = 线上当前版本，NEVER 照文档抄版本号。

### 8.6 环境与平台差异

1. 【强制】测试（`itp`）与红岛生产（`itpb`）的命名空间、入口、基础镜像、跳板机路径全部不同，NEVER 复制粘贴配置。
2. 【强制】红岛跳板 `hd-linux` 只有 podman、无 `/home/java`，`k8s` 域 NEVER 用于红岛；发版走 `cloudos image build --env hongdao`。
3. 【推荐】容器 UTC 坑：部署侧 MUST 设 `TZ=Asia/Shanghai`（见第 3.5 节）。
4. 【强制】VL app 名 ≠ Deployment 名，查日志 MUST 现查映射表（见第 4.3 节）。

### 8.7 目录与文件命名

1. 【强制】Java 包目录按分层（第 8.1 节）；资源目录：`mapper/*.xml`、`sql/*.sql`、`application*.properties`。
2. 【强制】SQL 脚本用连字符命名，按 `*-schema.sql` / `*-migration.sql` 分界；NEVER 用中文 / 空格命名资源文件。
3. 【推荐】前端文件命名见9 ；工作汇报类文档命名见 `docs/reports/README.md`。
4. 【强制】NEVER 在仓库内新增「需求接口清单 / 实现进度报告 / 接口提取结果」这类汇总文件（`docs/提示词/工程与文档规范.md` 已明令删除且 NEVER 重建）。

## 9 前端规约（`web/`）

### 9.1 技术栈与版本

1. 【强制】Vue 3.5 Composition API（`<script setup>`）+ Element Plus；版本以 `web/package.json` 为准。
2. 【强制】Vite 6 / Pinia 3 / vue-router 4，`src` 下 0 个 `.ts`（152 个 `.vue` 全为 JS）；NEVER 在没有工程化支撑时单独引入 TypeScript。
3. 【推荐】新增依赖前 MUST 核对 `package.json` 现有版本，NEVER 为单个组件引入整套 UI 库。

### 9.2 目录结构

1. 【强制】目录按既有分域，NEVER 新建平行结构：

| 目录 | 用途 |
|---|---|
| `src/views/<业务域>/` | 页面，多为 `index.vue`，少量 camelCase |
| `src/api/<业务域>/*.js` | 接口封装，文件小驼峰（如 `serviceStatus.js`） |
| `src/components/` | 公共组件，大驼峰目录（如 `QueryTimeRange`、`DictTag`） |
| `src/utils/request.js` | axios 统一封装 |
| `src/router/index.js` | 路由（`createWebHistory`） |
| `src/store/` + `modules/` | Pinia 状态（`app` / `user` / `permission` / `dict` / `settings` / `tagsView`） |
| `src/layout/`、`directive/`、`plugins/` | 布局、指令、插件 |

2. 【强制】`api/system|monitor|tool` 对应 web-admin 的 RuoYi 原生接口；`api/para`、`api/trans` 的后端在 `para-server` / `ticket-server` 等业务模块的 `/page/**`，经反代转发，NEVER 把业务查询搬进 web-server。
3. 【强制】页面组件里 NEVER 直接裸调 axios，MUST 走 `utils/request.js` 与 `api/` 封装。

### 9.3 组件与命名

1. 【强制】组件文件名与组件名一致，公共组件用大驼峰；页面内局部组件 NEVER 与公共组件重名。
2. 【推荐】`<script setup>` 中 props / emit MUST 显式声明与类型，NEVER 用 `$attrs` 隐式传参。
3. 【强制】组件 NEVER 直接修改父级传入的 prop；MUST 通过 emit 通知。
4. 【推荐】公共查询条件组件（时间范围、字典标签）MUST 复用既有组件，NEVER 复制粘贴后改样式。

### 9.4 API 与请求封装

1. 【强制】接口封装 MUST 与方法名、URL 一致，NEVER 在页面里硬编码 URL 字符串。
2. 【强制】错误处理统一在 `utils/request.js`，NEVER 每个页面各写一套 `retCode` 判断。
3. 【强制】超时 / 取消 / 重复提交 MUST 有统一处理；列表查询 NEVER 因快速切换条件产生竞态覆盖。
4. 【推荐】分页参数命名沿用既有约定，NEVER 新增第二套分页协议（见第 3.10 节）。

### 9.5 路由与权限

1. 【强制】新增页面 MUST 同步补菜单 SQL（写法参考 `web-server/sql/*-menu.sql`）与权限标识，NEVER 只加路由。
2. 【强制】路由名 / 组件路径 MUST 与菜单 SQL 一致，NEVER 靠通配符兜底。
3. 【推荐】按钮级权限沿用 `permission` store 与既有指令，NEVER 手写角色字符串判断。

### 9.6 状态管理

1. 【强制】全局状态只放跨页面共享数据（用户、权限、字典、设置），页面局部状态放组件内，NEVER 全塞进 Pinia。
2. 【强制】`sys_config` 有 LocalCache，前端 NEVER 假定「改库立即生效」。
3. 【推荐】状态变更 MUST 通过 action，NEVER 在组件里直接改 store 内部对象。

### 9.7 样式与 UI 一致性

1. 【强制】`web/.editorconfig` 是 2 空格 / LF / UTF-8（与后端 Java 的 4 空格不同，各按各的）。
2. 【强制】改样式前 MUST 先确认「编译出的选择器能否命中真实 DOM」，NEVER 凭源码选择器推断（见 `docs/architecture/web-admin-development-workflow.md`）。
3. 【推荐】颜色 / 间距 / 字号沿用 Element Plus 变量与既有页面，NEVER 引入第二套主题变量。
4. 【强制】涉及金额 / 状态展示 MUST 按既有字典与脱敏规则，NEVER 前端硬编码中文标签替代后端码值。

### 9.8 构建与检查

1. 【强制】`web/` **无 ESLint / Prettier 配置与依赖**，NEVER 声称「已过 lint」。
2. 【强制】改动后 MUST 跑 `web/` 下自研检查脚本（`syntax-check.mjs` / `ui-consistency-audit.mjs` / `query-ui-check.mjs`）+ 构建（`build:prod` / `build:stage`）。
3. 【强制】本地只出 zip，发版 MUST 走云平台；NEVER 在本机构建 x86 镜像。
4. 【参考】环境配置 `.env.development` / `.env.staging` / `.env.production` 的差异按 `docs/architecture/web-server.md` 与发版流程执行。

### 9.9 验收四件套

1. 【强制】前端改动 MUST 走 `docs/architecture/web-admin-development-workflow.md` 的验证四件套 + 打包 + 上线后核验 + 回写义务，缺一不可。
2. 【强制】线上核验 MUST 包含 NodePort 探活与页面实际渲染，NEVER 只看构建成功。
3. 【参考】问题定位先判层：前端渲染 / 后端接口 / 菜单 SQL / nginx 反代，层判错后面全白做。

### 9.10 前端禁令

1. 【强制】NEVER 把运营查询接口后端放进 web-server（菜单在 web-server，但接口在业务模块 `/page/**`）。
2. 【强制】NEVER 用代码生成器（RuoYi 模板）生成业务模块代码。
3. 【强制】NEVER 在前端硬编码密钥、内部地址、测试账号。
4. 【强制】NEVER 提交构建产物（`dist/` 等）到仓库。

## 附录 F 常见误判速查

| 现象 | 常见误判 | 正确判据 |
|---|---|---|
| 接口返 HTTP 200 但业务失败 | 以为成功 | 看 `retCode` + 服务端日志原文 |
| 返 Spring 原生 500 | 以为业务拒绝 | 全局异常处理器自身失败（异常 message 为 null） |
| `QRTZ_*` 表恒 0 行 | 以为任务没跑 | Quartz 内存 JobStore，查 `SYS_JOB_LOG` |
| 直接改 `sys_job` / `sys_config` | 以为立即生效 | 须重启 web-admin / LocalCache 不刷新 |
| 容器里时间差 8 小时 | 代码里 +8 | 部署侧设 `TZ=Asia/Shanghai` |
| Pod `Running` 但端口不监听 | 以为依赖没注入 | 往下翻到 `Failed to parse mapping resource` 看 mapper 文件名 |
| 编译单测全过、生产才炸 | 以为代码没问题 | 先查 mapper 六陷阱 |
| 按 Deployment 名搜 VL 无结果 | 以为没接日志 | VL app 名 ≠ Deployment 名，现查映射表 |
| 仓库里有 `@Scheduled` | 以为补偿在跑 | 查 `SYS_JOB_LOG` + Deployment 副本数 |
