## 1 总则

### 1.1 目的与适用范围

本规范规定青岛地铁互联网票务系统（ITP）所有 Java 后端模块、Oracle 持久层、配置与 SQL 脚本、以及 `web/` 前端中**单元与组件级测试**的策略、设计方法、用例规范、执行与度量、角色职责与证据链要求，是 CMMI V3.0 过程域 VER（验证）、MPM（管理绩效与度量）、CAR（原因分析与解决）、CM（配置管理）、PR（同行评审）在本项目的落地标准类过程资产。

适用范围不含端到端联调、性能压测与渗透测试（分别由联调测试、性能测试、安全测试相关过程覆盖）。凡涉及支付、订单、扣款、签约、开户、卡池、对账链路的代码，单元测试 MUST 覆盖其幂等与状态机边界（见第 6 章）。

### 1.2 术语与缩略语

| 术语 | 含义 |

## 2 单元测试策略

### 2.1 测试金字塔与定位

本项目测试以**单元 / 组件级**为底座，原则上不依赖集成环境：

1. 【强制】单元测试 MUST 在纯 JVM 内运行，NEVER 拉起完整 Spring 容器即可验证业务逻辑。
2. 【强制】外部依赖（数据库、支付网关、RPC 服务、消息组件）MUST 以 Mockito mock 或 Fixture 隔离；测试 NEVER 连接测试环境数据库、真实支付网关或真实集群。
3. 【推荐】集成 / 联调测试仅覆盖跨模块契约，不作为单元质量证据；单元层解决不了的边界，才上推到集成层。

### 2.2 AIR 原则

1. 【强制】**Automatic**：用例 MUST 可经 CI 自动复跑，NEVER 手工触发才生效。
2. 【强制】**Independent**：用例之间 MUST 无顺序依赖、无共享可变状态；NEVER 用 `@FixMethodOrder` 或隐式执行序依赖。
3. 【强制】**Repeatable**：用例 MUST 不依赖真实环境数据（库里既有行）与真实时间（`new Date()`）；时间 MUST 通过可注入的 `Clock` / 测试桩提供。

### 2.3 BCDE 设计原则

1. 【推荐】**Border**：优先覆盖边界值——空集合、单元素、最大长度、枚举首末值、金额 0 / 负 / 精度边界。
2. 【推荐】**Correct**：正确输入路径 MUST 有断言明确的用例，验证「正常也能对」。
3. 【推荐】**Design**：用例 MUST 依据设计文档 / 接口契约构造，NEVER 凭直觉凑输入输出。
4. 【强制】**Error**：错误输入与异常分支 MUST 有专门用例，且用 `assertThrows` 断言异常类型与关键上下文。

### 2.4 测试范围与豁免

1. 【强制】以下 MUST 有单元测试：状态机与白名单、幂等与事务边界、错误码与异常处理、金额 / 精度计算、编解码与签名校验、对外 RPC Client 的参数装配。
2. 【推荐】纯 getter/setter、Spring 配置类、DTO 简单映射可豁免，但 MUST 在评审记录登记豁免条目与理由。
3. 【强制】项目级豁免 MUST 在评审记录中登记「豁免了哪条 / 为什么 / 谁批准 / 有效期」，NEVER 默认全裁或口头约定。

### 2.5 入口与出口准则

- **入口准则**：代码完成自测、静态检查（含 lint 门禁）通过、关联需求 / 设计明确。
- **出口准则**：目标分支覆盖率达标（见 7.2）、新增 / 修改逻辑均有对应断言用例、CI 全绿、评审通过。

## 3 技术栈与测试环境

### 3.1 测试框架

1. 【强制】使用 **JUnit 5（Jupiter）**，`org.junit.jupiter.api.Test`；NEVER 在新用例中引入 JUnit 4 / TestNG / Spock。
2. 【强制】Mock 使用 **Mockito**，配合 `@ExtendWith(MockitoExtension.class)`、`@Mock`、`ArgumentCaptor`；验证交互用 `verify` + `ArgumentCaptor`。
3. 【强制】架构约束测试使用 **ArchUnit**；NEVER 用反射扫描全仓源码树导致构建极慢，MUST 限定目标包。
4. 【参考】既有 AssertJ 用例按原文件风格续写，NEVER 在同一文件混用 JUnit Jupiter 断言与 AssertJ 两套风格。

### 3.2 Spring Boot Test 的最小化

1. 【强制】`@SpringBootTest` MUST 极少使用（实仓当前仅约 3 处）；新增前 MUST 在评审记录说明为何必须起容器。
2. 【推荐】绝大多数单测 MUST 是纯 JVM 测试：直接 `new` 被测类、用 Mockito 注入依赖，或仅加载相关 slice（如 `@MybatisTest` 风格的自研等价物）隔离验证。

### 3.3 外部依赖隔离

1. 【强制】数据库、支付网关、RPC 服务、消息组件 MUST 以 Mockito mock 或 Fixture 替代，测试 NEVER 依赖测试环境数据库、真实支付网关、真实集群。
2. 【强制】测试配置与生产配置 MUST 分离；NEVER 在测试里硬编码线上地址 / 口令。
3. 【推荐】验证交互用 `verify` + `ArgumentCaptor` 捕获实参，NEVER 依赖 mock 调用顺序推断业务正确性。

### 3.4 数据库与 Oracle 陷阱

1. 【强制】NEVER 用 H2 / 内存库「等价替代」Oracle 验证运行时陷阱——别名折叠、`JdbcType.OTHER`、WallFilter 拦截只 Oracle 暴露。
2. 【强制】幂等与事务边界 MUST 用「数据库唯一索引 + `DuplicateKeyException` 真实形态」验证，NEVER 用 `@Transactional` 单测的事务回滚来证明业务幂等。
3. 【推荐】Oracle 相关陷阱的判据 MUST 落在 Oracle 实库或已有事故结论，Maper/SQL 测试见 6.3。

### 3.5 测试配置隔离

1. 【强制】测试配置 MUST 独立，NEVER 复用生产 `application*.yml` 的线上地址 / 口令。
2. 【强制】NEVER 修改 `sys_config` / `sys_job` 等带 LocalCache 的运行期数据来「造测试条件」——直接改库不生效且污染环境。

## 4 测试设计方法

### 4.1 等价类与边界值

1. 【推荐】按输入域划分有效 / 无效等价类，边界值 MUST 单独立例（含空、单元素、极值、精度边界）。
2. 【推荐】金额类 MUST 覆盖 0、负数、最大精度、超长精度截断等边界。

### 4.2 状态机白名单设计

1. 【强制】状态迁移 MUST 用「枚举 + 迁移表 + `canTransitTo` / `isTerminal`」白名单范式，测试 MUST 同源：新增迁移 MUST 同步改枚举、迁移表与白名单单测三处。
2. 【强制】状态机改动 MUST 配 `*WhitelistTest` 覆盖：允许的前置状态、禁止的前置状态、终态、未知状态、重复事件。
3. 【强制】测试 MUST 断言「除白名单外的所有状态一律拒绝」，NEVER 只测几个允许分支就结束。
4. 【推荐】用参数化测试遍历枚举所有取值，新增状态值时测试自动覆盖，NEVER 手工补几个用例。

### 4.3 幂等与事务边界设计

1. 【强制】涉及支付、订单、扣款的关键逻辑 MUST 有幂等测试：同一请求重复提交 MUST 经唯一索引 + `DuplicateKeyException` 拦截为一次生效。
2. 【强制】事务边界 MUST 有 ArchTest 或单测断言「该在该事务内的逻辑确实在同一事务内」（参考 `PaySignTransactionBoundaryArchTest`）。

### 4.4 异常与错误分支设计

1. 【强制】异常分支 MUST 用 `assertThrows` 断言异常类型与关键上下文，NEVER 用 `try-catch + fail()` 手写。
2. 【强制】每个用例至少一个业务语义断言，NEVER 用「不抛异常即通过」代替断言。

### 4.5 参数化与数据驱动

1. 【推荐】多组相似输入优先用 JUnit 5 `@ParameterizedTest` + `@ValueSource` / `@MethodSource`，减少复制粘贴、提升边界可读性。
2. 【推荐】状态机 / 编解码等枚举密集型逻辑 MUST 优先参数化遍历全取值。

## 5 测试用例规范

### 5.1 类与方法命名

1. 【强制】测试类统一 `*Test`；实仓 132 个测试 `.java` 中 129 个如此，辅助类可用 `*Fixture` / `*Results`。
2. 【强制】专题命名沿用：`*WhitelistTest`（状态白名单）、`*StatusMachineTest`、`*TransitionTest`、`*ArchTest`（架构约束）、`*MapperSqlTest`、`*CharacterizationTest`、`*GuardTest`。
3. 【强制】NEVER 使用 `*Tests` / `*IT` / `*TestCase` 命名（实仓无此形态），避免构建插件扫描口径不一致导致用例不被执行。

### 5.2 包路径一致性

1. 【强制】测试包路径 MUST 与主代码包路径一致；新增状态机 MUST 同时新增对应 `*WhitelistTest`，删除测试 MUST 在评审记录说明原因。

### 5.3 测试方法命名

1. 【强制】方法名用 `shouldXxxWhenYyy` 或中文语义化命名，NEVER `test1` / `test2` 之类无意义名。
2. 【推荐】命名应表达「预期行为 + 触发条件」，使失败时能直接定位场景。

### 5.4 测试结构（AAA）

1. 【推荐】单测结构 MUST 遵循 Arrange-Act-Assert：准备输入与桩 → 执行被测逻辑 → 断言结果，三者界限清晰。
2. 【强制】NEVER 在一个用例里暗藏多个互不相关的断言场景；一个行为一个用例。

### 5.5 断言规范

1. 【强制】断言用 `org.junit.jupiter.api.Assertions` 静态导入（`assertEquals` / `assertTrue` / `assertNull` / `assertThrows`）。
2. 【强制】异常 MUST 用 `assertThrows` 断言类型与关键上下文；标量比较 MUST 用明确语义的断言而非笼统 `assertTrue`。

### 5.6 禁止形态

1. 【强制】NEVER 在单测里 `Thread.sleep` 等待异步结果；MUST 用可注入 `Clock` / 显式状态轮询 / 同步化被测逻辑。
2. 【强制】NEVER 在同一文件混用两套断言风格；NEVER 写无断言的「伪测试」。

## 6 专项测试要求

### 6.1 状态机与白名单测试

1. 【强制】状态机 MUST 有 `*WhitelistTest`，覆盖：允许前置 → 允许迁移、禁止前置 → 拒绝、终态 → 不可再迁移、未知状态 → 拒绝、重复事件 → 幂等或拒绝（依设计）。
2. 【强制】断言 MUST 包含「除白名单外的所有状态一律拒绝」，且用参数化遍历全枚举。
3. 【参考】实仓示例：`key-server` 的 `AgmKeyApprovalStatusWhitelistTest`。

### 6.2 架构约束测试（ArchTest）

1. 【强制】「编译发现不了」的规范 MUST 沉淀为 ArchTest 断言，如事务边界、包依赖方向、禁止直接 JDBC。
2. 【推荐】新增同类约束优先沿用 `PaySignTransactionBoundaryArchTest` 形态，限定目标包避免全仓慢扫描。
3. 【参考】实仓示例：`pay-sign-server` 的 `TerminationStatusArchTest`、`WalletChannelGuardTest`、`SignStatusArchTest`、`PaySignTransactionBoundaryArchTest`。

### 6.3 Mapper / SQL 测试

1. 【推荐】Mapper XML 改动 MUST 跑 `xmllint --noout <file>` 校验结构；新增含可空列的写语句 MUST 有对应参数 `jdbcType` 检查。
2. 【强制】可写 `*MapperSqlTest` 断言 XML 结构与参数绑定；NEVER 用 H2 替代 Oracle 验证运行时陷阱。
3. 【参考】实仓示例：`pay-sign-server` 的 `PayRefundDetailMapperSqlTest`、`AppTerminationRequestMapperSqlTest`。

### 6.4 幂等与事务边界

1. 【强制】幂等 MUST 用唯一索引 + `DuplicateKeyException` 真实形态验证，NEVER 用 `@Transactional` 回滚证明。
2. 【强制】事务边界 MUST 有断言（ArchTest 或单测）证明关键逻辑落在同一事务内。

### 6.5 敏感信息与脱敏

1. 【强制】测试数据 MUST 使用脱敏 / 虚构数据，NEVER 在用例或 Fixture 中写入真实乘客 PII、真实密钥、真实支付凭证。

## 7 测试执行与度量

### 7.1 自动化执行

1. 【强制】单元测试 MUST 纳入 CI 自动执行，每次提交 / 合并 MUST 复跑，NEVER 靠本地手动验证代替。
2. 【强制】CI MUST 以非零退出码暴露失败用例，NEVER 静默通过。

### 7.2 覆盖率目标与门禁

1. 【强制】状态机 / 幂等 / 事务边界 MUST **100% 分支覆盖**。
2. 【推荐】新增业务逻辑的分支覆盖率目标由模块自定，MUST 在评审记录说明；其余代码以「关键路径有断言、异常分支有覆盖」为基本门槛。
3. 【强制】覆盖率由构建流水线中配置的覆盖率工具真实采集；当前若未集成覆盖率插件（如 JaCoCo），MUST 在评审记录登记补齐项与责任人与期限，NEVER 以「口头达标」代替度量。

### 7.3 度量真实性与证据

1. 【强制】度量数据 MUST 真实采集，NEVER 为评估虚报覆盖率或编造通过率。
2. 【强制】单元测试报告、覆盖率报告、CI 执行记录 MUST 作为 VER / MPM 的**客观证据**留存，可追溯。

### 7.4 过程指标

1. 【推荐】过程指标纳入：状态机白名单单测数、关键链路分支覆盖率、CI 失败修复时长；删测试 MUST 在评审记录说明原因，指标变动可解释。

## 8 缺陷管理与回归

### 8.1 缺陷登记与定位

1. 【强制】失败用例 MUST 登记缺陷，含复现条件、预期 / 实际、关联提交与 traceId（若涉运行期）。
2. 【推荐】缺陷修复前 MUST 先复现（红），修复后转绿，禁止「盲目改到绿」。

### 8.2 回归测试

1. 【强制】缺陷修复 MUST 配套回归用例，防止同类问题复发。
2. 【强制】NEVER 为通过 CI 而删除 / 注释掉失败用例；删除测试 MUST 经评审并在记录说明。

### 8.3 测试禁令（重申）

1. 【强制】NEVER 在单测里 `Thread.sleep` 等待异步结果。
2. 【强制】NEVER 修改 `sys_config` / `sys_job` 等带 LocalCache 的运行期数据造测试条件。
3. 【强制】NEVER 硬编码线上地址 / 口令；NEVER 依赖真实环境数据。

## 9 角色职责与过程改进

### 9.1 角色与职责

| 角色 | 职责 | 产出 |
| --- | --- | --- |
| 编制（开发） | 编写 / 维护单元测试，保证 AIR 与断言充分 | 测试用例、覆盖率数据 |
| 审核（技术负责人） | 裁决【推荐】条目偏离、批准豁免、审核规范修订 | 审核签字、豁免单 |
| 批准（项目负责人） | 批准规范发布、批准重大裁剪 | 批准签字 |
| 配置管理员 | 维护受控版本、修订记录、测试资产基线 | 配置库记录、基线清单 |

1. 【强制】「编制 / 审核 / 批准」三个签字位 NEVER 由同一人填满。
2. 【强制】本规范经审核 / 批准后生效；生效前在途改动按评审记录逐项确认。

### 9.2 同行评审（PR）

1. 【强制】测试代码随业务代码一并进入 PR 评审，NEVER 「只评业务不评测试」。
2. 【推荐】评审检查单见附录 B；评审 MUST 确认：命名合规、断言充分、无禁止形态、覆盖率达标。

### 9.3 培训与宣贯（OT）

1. 【推荐】新成员开工前 MUST 阅读本规范与 `编码规范.md` 第 5 章；关键链路改动前组织短时宣贯。
2. 【参考】宣贯记录 MUST 留存作为过程证据。

### 9.4 原因分析与解决（CAR）

1. 【强制】删除既有测试 MUST 在评审记录说明原因（为何不再需要 / 被何替代），NEVER 静默删除。
2. 【强制】同一类测试缺陷重复出现（如反复出现「无断言伪测试」「H2 替 Oracle」），MUST 触发 CAR：根因分析 → 规范增补 / lint 规则固化 → 度量验证。
3. 【推荐】改进动作落到本规范时，MUST 同步写修订记录并说明触发的 IT 编号，形成「问题 → 根因 → 规范条目 → 度量验证」可追溯链。

## 附录 B 单元测试评审检查单

- [ ] 类 / 方法命名符合第 5 章（无 `test1`、`*Tests`、`*IT`）
