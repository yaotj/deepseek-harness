# 提示词工程与文档规范

> **何时读**：写 / 改任何 `.md` 提示词、`docs/` 业务文档、`qditp-*` 技能，或提交前做文档层门禁时 **MUST 先读**。
> 本文件承载「文档维护 + 提示词体系治理」的细则，**不再固化进 `AGENTS.md`**（2026-10-15 抽离，遵循「常驻上下文只放高海拔规则、细节按需 JIT 加载」）。

## 一、提交前跑提示词自检（可机检门禁）

**MUST** 提交前跑 `python3 docs/提示词/lint-prompts.py`，**ERROR 必须清零**。它把文档层纪律变成机械检查（历史补丁句 / 旧任务编号被当现状引用 / `.md` 间断链 / 常驻预算 / 单行长度 / **新增源码行号引用**）。`--fix` 自动删纯历史补丁句，`-v` 看全部 WARN，仍报 ERROR 的 **MUST** 手工处理。**NEVER** 用「我记得改过了」代替它。

**源码行号引用走基线机制**：`docs/提示词/lint-baseline.json` 存量按文件汇总成 WARN、**基线外的新增报 ERROR**；基线已为空 ⇒ 现存任何行号引用即新增、直接 ERROR。日后再有存量，清一批后 **MUST** `--update-baseline`；`--deep` 把每条引用与源码树核对（诊断用、不进提交门禁）。

**第三层（技能）默认同查、不设存量基线**：`~/.workbuddy/skills/qditp-*/SKILL.md` 默认同一套检查（补丁句 / 旧编号 / 断链 / 行号引用 / 单行长度），**不设存量基线**——任何行号引用都算新增；`--no-skills` 可跳过。

### 跨文件 `§` 引用 MUST 带锚点（2026-10-20 新增）

**规则本体被搬走、引用没跟着改，是本仓库最贵的一类腐烂**：规则下沉到 `docs/architecture/*` 后，几十处「`AGENTS.md` 第 4.2 节 + 规则名」形式的引用仍指着旧位置，读者按引用找不到规则（2026-10-20 实测 52 处）。

因此：**跨文件引用 MUST 写成 `文件名 §N「锚点」`**，锚点必须是目标章节标题或该章节正文里的原话（例：`docs/architecture/transaction-and-consistency.md` §6「`@Transactional` 方法内 NEVER 发起任何 RPC / 网络调用」）。机检按**字符二元组重叠率 ≥ 0.5**判定（允许简写，如「NEVER 新建工具类」对「NEVER 主动创建新的工具类」），重叠不足即 ERROR。

- **裸引用**（形如 `AGENTS.md` 第 4.2 节那样后面不跟锚点）⇒ WARN：它无法机检，章节号一重排就静默漂移。**MUST** 补锚点。
- **只查约束层文档**（`docs/business/` `docs/domain/` `docs/ops/` `docs/architecture/` `docs/提示词/`）；`docs/testing/` `docs/reviews/` `docs/history/` 是归档记录，不拦门禁。
- **规则下沉时 MUST 同批改引用**——这是 §六 回写义务的一部分，不是可选项。

### 路由表单一真源 + 受机检投影（2026-10-20 新增）

「任务 → 读哪篇」的真源是 `docs/提示词/任务路由表.md`（2026-10-20 从 `docs/ops/workflow-routes.md` 迁来——原位置与 `docs/ops/` 的目录语义不符，且它不在 `docs/ops/README.md` 的文档清单里）。`AGENTS.md` §5.1「任务 → 必读路由」是它的**高频投影**，两表的「先读」路径集合由 lint 校验，**不一致即 ERROR**。

**这解决了「快路径 vs 单一真源」的两难**：常驻层不可能不放高频入口，而放了两份就会漂移——所以让副本变成**可机检的派生视图**（`★` 标记 = 高频项），漂移由机器拦。**MUST NOT** 恢复成「两份表 + 靠人记得同步」。

## 二、仓库内不再维护「需求接口清单 / 实现进度报告 / 接口提取结果」这类汇总文件

2026-08-25 全部删除（4 份进度报告曾给出四个互相矛盾的实现率、「实现位置」列大面积误指）。

**判断「某接口是否存在 / 是否已实现」** **MUST** 直接看 Controller 的 `@RequestMapping` / `@PostMapping` 注解，**NEVER** 重新生成这类汇总报告。

## 三、前端技术栈

前端代码 **MUST** 遵循 Vue 3.5 Composition API（`<script setup>`）及 Element Plus 规范；版本以 `web/package.json` 为准，不自此处查。

## 四、提示词体系治理（写 / 改文档、技能、提示词时的 meta-rule）

### 4.1 模型升级后 MUST 重新评估常驻规则

规则多是为当年模型短板写的，新模型已能自行处理的条目留着只是上下文成本与枷锁，该删就删。**判据**：这条规则改变的是模型行为，还是只是提醒一个真实陷阱——只有后者才留。

### 4.2 技能（`~/.workbuddy/skills/qditp-*/SKILL.md`）编写规范

依据 Anthropic Skills 最佳实践（2025-12）：
1. 目录名用**动名词**（`refund-execution` / `deploy-release`），`description` 用**陈述句**写明「做什么 + 何时用（适用场景）」，**NEVER** 写「I can help you…」式空话。
2. 主体 **MUST ≤ 500 行**，超出 MUST 拆引用文件做**渐进式披露**（SKILL.md 只放入口与决策，细节放 `reference.md` 等按需读），引用深度 **MUST 控制在一层内**。
3. 每篇 MUST 含**至少一个具体输入/输出样例**（命令、SQL、报文），样例与要鼓励的行为一致，**NEVER** 只堆规则不示范。
4. 技能之间 **MUST 无功能重叠**，重叠即合并。
5. 改动技能后 **MUST** 跑 `lint-prompts.py`（技能层默认同查、不设存量基线）复验。

### 4.3 上下文占用即冗余（常驻 vs JIT 判据）

**写 / 改 `AGENTS.md` 或其他常驻提示词时 MUST 应用此判据**：「窄场景细节堆进常驻上下文」本身就是冗余，应下沉到 JIT 文档。判据：这条规则是**日常 90% 场景都要遵守**，还是**只在特定任务触发**？前者留 AGENTS，后者下沉到 `docs/architecture/` 或 `docs/提示词/` 对应子文档。

### 4.4 否定约束 MUST 配对正向替代

写 `NEVER` / 「禁止」/ 「不得」时，**MUST** 同时给出可执行的替代做法（形如 `NEVER X → 改用 Y`）；纯禁止无替代项易让模型卡在禁项上或自作主张绕开。依据 Google Prompt Engineering / Claude Code 最佳实践（2025）。`AGENTS.md` §4.1「代码生成与修改 (Do's and Don'ts)」各条即此范式。

## 五、文档维护元规则

三条**高海拔元规则**（每条 ≤ 2 行）：
- 事实快照 MUST 让位于实况（代码/集群实况 > 文档）；
- 事实过期 MUST 直接改旧值、NEVER 追加补丁；
- 版本号 / 端口 / 任务编号 / 名单口径 **MUST 现查**，NEVER 引用文档里的数字当现状，NEVER 新增 `Xxx.java:NNN` 行号引用。

本文件其余条款是本节的实施细则。

## 六、回写义务（`AGENTS.md` §5.2「通用步骤骨架」第 5 步的实施细则）

改代码后 **NEVER 只改代码不回写**——本仓库提示词是全项目唯一的架构事实源，过期表述仍以 `MUST` / `NEVER` 的语气继续指挥后续改动，而编译与单测都发现不了。改动涉及**类名 / 方法名 / URL / 端口 / 状态取值 / 数据表 owner** 时 MUST 同步回写：

- **回写到哪**：业务域事实 → `docs/business/<业务域>.md`；跨域归属 / 边界变化 → `docs/domain/README.md`。**同一事实常散落在三处**（`docs/business/README.md` 全局事实 + `docs/business/<域>.md` + `docs/architecture/*.md`），MUST 三处一起改，否则必然分叉。
- **每条 MUST 标注改动日期与 ADR 号**；改 `docs/business/README.md` 全局事实时 MUST 同步检查 `docs/business/<域>.md` 与 `docs/architecture/*.md`。
- **改名 MUST 保留旧名做交叉引用**，否则后续按旧名检索会误判成文档自相矛盾；**ADR 正文与撤回记录 NEVER 删改**，只在原文旁补注现名。
- **行号会漂、NEVER 依赖行号**，MUST 按类名 / 方法名定位。

## 七、任务分解原则（写文档 / 拆任务时读）

复杂任务优先「规划 → 单 agent 分步执行 → 每步自检」闭环，**NEVER 盲目并行拆子 agent**。编码类任务子任务间依赖重、共享上下文多，多 agent 往往不划算且易分叉；仅当子任务真正独立、需隔离不同上下文（如并行检索互不相通的信息）时才拆。拆分后每个子 agent 的 prompt **MUST** 含明确目标、输出格式与边界，并只回传 1–2k token 的压缩结论，而非完整上下文。
