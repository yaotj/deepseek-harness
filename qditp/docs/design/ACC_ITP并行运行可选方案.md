## 二、决策点一：用户数据切分策略

**背景**：一期上线后注册用户归属新 ITP 平台。若全量切换，存在回滚风险与压测困难，故需在「按时间段切分」与「挑部分内部用户试水」间决策。

**可选方案**：

| 方案 | 说明 | 优点 | 风险 / 代价 |
|---|---|---|---|
| A | 按时间段切分：以某一时间点为界，此前注册用户归属老系统，此后归属新系统。建议使用电子员工票作为第一批用户进行业务测试；待完成测试后，向新用户注册的乘客开放 | 规则清晰、可自动化、回滚边界明确；不存在钱票损失风险；逐步增加乘客用户接入；风险可控 | 边界时间点之后注册的用户如需访问旧账户 / 历史数据，存在跨系统查询；边界用户的业务连续性需设计 |
| B | 先内部用户试水：选取部分内部用户先行迁移至新系统试运营 | 影响面小、压测与回滚压力低；可端到端验证新链路（开卡、支付、查询） | 内部用户样本有限，与真实乘客场景有偏差；仍需最终的全量切分决策 |

**推荐建议**：一期采用 B（内部用户试水）控制风险、验证链路；试水稳定后，结合 A（按时间段切分）作为全量切分的落地规则。两者并非互斥，而是「先试点、后定型」的递进关系。

**待确认**：① 试水内部用户的范围与量级；② 时间段切分的基准时间点定义；③ 历史账户在新系统不可查时的跨系统查询 / 迁移策略。

## 三、决策点二：BOM/TVM 业务切分与设备接入

**背景**：现场设备只能接入一方系统，全线改配风险过大、且存在兼容性差异与回滚风险，无法像实验室随意切换地址。BOM 兼具「购票」与「用户业务」两类特性，需决定其并行期归属与接入方式。若与过闸业务同期上线，需 ITP 配置分发服务。

**可选方案**：

| 方案 | 说明 | 优点 | 风险 / 代价 |
|---|---|---|---|
| A | BOM/TVM 直接切分至新 ITP：购票、单程票、支付等走新 ITP，用户业务走新 ITP | 架构清晰、彻底迁移，长期演进成本最低 | 现场设备改配兼容性差异大、回滚风险高；一旦异常影响面大 |
| B | 旧用户查询转发（AB 测试分流）：BOM/TVM 接新系统；查不到旧用户时，请求转发至老 ITP 取结果后返回 | 新旧平滑共存、可按业务分流；回滚容易（关闭转发即回老系统） | 转发链路增加时延与故障点；需新老系统接口结构对齐 |
| C | 网络代理备选：除接口结构对接外，做网络代理直接将请求转给老系统 | 降低适配复杂度，无需改业务接口即可接通老系统 | 代理层成为单点、运维复杂；不利于长期架构演进 |

**推荐建议**：并行验证期以 B（查询转发 / AB 分流）为主，实现新旧共存与可控回滚；C（网络代理）作为降级 / 过渡手段；待 B 验证稳定、接口对齐完成，再实施 A（直切新 ITP）作为稳态目标。

**待确认**：

1. 转发触发条件（何种情况判定「查不到旧用户」；城交大数据需给出完整分发接口列表，ITP 侧进行分发 BOM 业务）；
2. 转发超时与降级策略；
3. 网络代理覆盖范围与是否仅作临时方案。

## 四、决策点三：并行范围组织（ACC 独立先行 vs 合并大方案）

**背景**：纪要指出，ACC 的并行测试（交易与客流比对）相对独立、可先期开展；但受限于 ITP 并行需求的复杂性，最终可能需与 ITP 并行合并执行。下一步计划亦提出：待华腾输出 ITP 并行方案后，拉通田老师及相关人员评估「新旧 ACC/ITP 并行能否合并为一个整体大方案」。

**可选方案**：

| 方案 | 说明 | 优点 | 风险 / 代价 |
|---|---|---|---|
| A | ACC 并行先期独立开展：先完成 ACC 交易文件提取、导入新系统与比对验证 | 先易后难、快速出阶段性结论；降低整体耦合风险 | 若最终需合并，存在重复设计与后期集成成本 |
| B | ACC + ITP 合并为整体大方案：统一规划新旧 ACC/ITP 并行 | 一次性解决、避免重复、整体视角最优 | 范围大、复杂度超预期、排期与多方协调成本高（需田老师及相关人员联合评审） |

**推荐建议**：采取「小步快跑 + 视情况合并」：先 A 快速验证 ACC 比对能力；同时梳理 ITP 并行的受影响项与改造内容，待方案输出后评估是否升级为 B。判定标准建议设为「ITP 并行是否复用 ACC 并行的基础设施与数据通道」。

**待确认**：

- 合并与否的判定标准；
- 联合专项评审的参会范围（田老师、相关人员）。

## 五、决策点四：NFC 卡黑名单生成与交接机制

**背景**：ITP 产生的 NFC 卡黑名单需由 ACC 参数下发至设备拦截；纪要指出该流程在测试初期影响较小，但上线后需保证数据实时互通。

**解决方法**：ACC 与 ITP 新增文件类型：NFC 卡黑名单文件，按照业务需求，定时推送黑名单文件。

**待确认**：① 二维码与 NFC 黑名单的「双端产生范围」边界划分；② ACC 侧 NFC 黑名单文件格式约定；③ 上线后实时互通的技术机制（消息 / 文件 / 接口）。

## 六、决策点五：参数下发机制

**背景**：参数变更主要涉及票价与线路。纪要明确：前期可通过 FTP 获取或手工放置，后期以新系统为主生成，参数文件版本校验机制：版本号 + MD5 文件校验。

**推荐建议**：并行验证期采用 A 作为过渡；明确「切换时点」——新系统参数生成能力就绪后切 B。全程建立参数版本校验，避免手工 / 自动混用导致的不一致。

**待确认**：① 新系统参数生成就绪时点；② FTP 目录、权限与操作责任人。

## 七、决策点六：ACC 与 ITP 接口支撑与对接方式

**背景**：ITP 需与生产环境加密机打通，前置服务由华腾负责，涉及逻辑卡号获取及签名等。新系统上线前需提供多项支撑与对接：卡池与加密机交互、对账与文件传输、参数下发、实时客流上传等。

**支撑需求清单（需在新系统上线前提供）**：

| 支撑项 | 内容 / 接口 | 对接方式选项 |
|---|---|---|
| 加密机交互（测试环境已验证） | 加密机前置服务完成交互 | 实时接口直连 |
| 对账与文件传输（测试环境已验证） | 第三方对账文件 + 新老系统 ACC 对账文件 | 文件摆渡（FTP）/ 接口 |
| 参数下发（ACC 测试环境手动放置参数后，ITP 参数自动下载与解析已验证） | 票价、线路等参数变更下发接口 | 并行期 FTP/手工 → 后期接口 |
| 实时客流上传（可以靠后完成） | 实时客流上传接口 | 实时接口直连 |
| 卡池文件处理（测试环境已验证） | 逻辑卡号获取，用户开卡、卡池管理均验证完成 | 前置服务（当前团队） |

**推荐建议**：并行验证期以「文件摆渡（FTP/手工）+ 接口并行开发」并行推进，先用文件方式跑通比对与对账，同步开发实时接口；上线前将关键链路（客流、ACC 对账、参数）切换为实时接口，降低对手工的依赖。

**待确认**：

1. 加密机生产环境打通的前置条件与责任人；加密机是否使用新加密机或者旧加密机添加白名单？
2. 实时交易文件生成。

## 八、关键风险与依赖汇总

- **设备接入唯一性**：设备只能接一方系统，需分发服务上线方案；
- **网络与业务双重复杂**：需田老师等专业人员参与评估，专项会议须补齐人员；
- **加密机依赖**：ITP 打通生产加密机、获取逻辑卡号属前置业务，需前置完成；
- **合并范围不确定性**：ACC 与 ITP 是否合并大方案；
- **上线后实时互通**：黑名单文件生效、参数下发在上线后需实时，上线前须闭环。
