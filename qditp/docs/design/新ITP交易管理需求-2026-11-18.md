## 2. 范围与边界

**本需求包含**：6 页查询字段/列口径对齐、详情下钻、存疑单人工处置（写）、单边退款按钮接入、导出、异常类型字典映射、补款单动作定义、必要的存量数据迁移。

**本需求不包含（明确划线）**：
- 6 个查询页本身的重建（已存在于 IT-062）。
- 乘客侧 APP / BOM / TVM 的交易链路改造——本需求只做**运营端管理台**。
- 日票订单退款 / 当面付订单退款（Test_036~038，属用户管理/交易管理的另一组页，已有实现）。
- 服务器重试策略管理（gb 报告 #6，另案待裁决）。
- 对账 / 清分 / 日统计报表（12 页已补建，另案）。
- `GATE_TXN_PAY` 的支付退款底层链路（pay-sign 的 `requestRefund` 已存在，只调用不改造）。

## 3. 功能需求（FR）

### FR-1 六页查询能力对齐

**FR-1.1 字段补齐**（沿用现有 GET 端点，不改路径）

| 页 | 新增/调整查询参数 | 来源 |
|---|---|---|
| BOM 非现金 | 增 `payChannel`（支付通道）、`payStatus`、`operator`/`managerId`；`userId` 与 `cardId` 并存 | 旧查询条件 §1.1 |
| 单程票购票 | 增 `thirdUserId`（旧 `userId` 用户标识）与 `ticketType`；区分 `orderChannel` / `payChannel` | 旧 §2.1 |
| TVM 充值订单 | 增 `lineName`（线路）；`ticketLogicNum` 与 `cardId` 并存 | 旧 §3.1 |
| 单边查询 | `orderExpType` 支持 1~5 全值（现默认圈 1/2）；日期参数兼容 `yyyyMMdd` 与 `yyyy-MM-dd` | 旧 §4.1~4.2 |
| 在线补款 | 现 4 项已覆盖旧查询，保持不变 | 旧 §5.1 |

**FR-1.2 列表列补齐**：按旧侧全字段表补齐（尤其 TVM 的线路名称/支付方式、单程票的下单渠道/票卡种类、BOM 的行政交易类型、补款单的支付状态与覆盖笔数）；金额统一按分转元展示，格式沿用现有 `formatAmount`。

**FR-1.3 约束**：新增参数一律可空；MyBatis 可空参数 MUST 显式 `jdbcType`（ORA-1111 教训，见 `docs/architecture/mybatis-oracle-runtime-traps.md`）；NEVER 用 `WHERE 1=1`（Druid 注入检测）；日期区间必填的负例保持现有 `code=400` 文案。

### FR-2 详情下钻（P1，先于写操作）

**FR-2.1 三页共性详情抽屉**：BOM 非现金、单程票购票、TVM 充值订单三页，点击订单号弹「订单信息 / 支付信息」双页签，字段按旧侧全集对应（BOM 16+支付、单程票 24+支付、TVM 16+6）。

**FR-2.2 操作历史子表**：每个详情内嵌「订单操作历史」，列至少含事件、操作结果码、结果描述、操作员、操作日期、入库时间；单程票另有「TVM出票记录」页签。
- 旧侧单程票操作历史达 **425,048 条**（21,253 页），历史子表 MUST 服务端分页 + 按订单号索引查询，**NEVER 前端一次拉全量**。
- 数据来源：优先现有业务表（`TBL_BOM_ORDER_PAY` / `TBL_TVM_ORDER_TOPUP` / `GATE_TXN_PAY`）中已有的操作字段；如确需新表，则属 D2 裁定范围。

**FR-2.3 单边详情**：`one-side-query` 页点击订单号展示旧侧 30 字段（进出站线路/车站/设备/时间、请求扣款结果与描述、实际扣款时间、入库日期等），数据来自 `GATE_TXN_PAY` 现有列；缺列时按 D2 补列，不从旧库直读。

### FR-3 TVM 充值存疑订单处置（🔴 核心缺口）

**FR-3.1 数据视角（先裁定 D1）**：旧「存疑」挂在**充值订单**上（含写卡时间/充值金额/余额/操作历史）；新页挂在 `F2F_RESULT_REPORT` **设备回执**上（含故障单号/错误码/处理结论）。默认方案：保留回执页为「待处置队列」，新建**订单视角详情**按 `orderNo` 关联 `TBL_TVM_ORDER_TOPUP`，两视角互为链接，不以一侧覆盖另一侧。

**FR-3.2 写端点契约**（face-pay-server 新增）
- `POST /page/face-pay/topup-suspicious/{id}/resolve`，body `{decision: "SUCCESS"|"FAIL", operatorId, reason?}`。
- 状态机白名单：`PENDING` → `SUCCESS` / `FAIL`；终态再处置一律拒绝（**NEVER 写成「非终态即可」**，见 AGENTS.md §4.2）；配 `TopupSuspiciousResolveWhitelistTest` 单测。
- 并发：DB `UPDATE ... WHERE STATUS='PENDING'` CAS + 影响行数判重（幂等）；失败不生成退款单，只落处置结论与操作留痕。
- 写操作**不触碰密钥/签名逻辑**；涉及金额与写卡态，属资金相关变更，实施前 MUST 提示人工安全合规复核（AGENTS.md §4.2 安全红线）。
- ⚠️ `/page/**` 当前无鉴权（P0-1 业主裁决现阶段不做），本端点 MUST 至少校验 `operatorId` 非空并写审计日志；是否补鉴权沿用 P0-1 裁决，NEVER 在本需求里单方面推翻。

**FR-3.3 前端**：`tvm-topup-suspicious` 页增加操作列「判定成功 / 判定失败」，按钮带 `v-hasPermi=['trans:topup-suspicious:resolve']`（菜单需补 F 型按钮权限）；点开详情展示旧侧 16+6 字段与操作历史；写入后刷新列表与处理状态。

**FR-3.4 留痕**：新增处置流水（建议 `F2F_TOPUP_SUSPICIOUS_OP_LOG`），记录订单号、回执 ID、处置结论、原因、操作人、时间，供详情内嵌展示。若 D2 选「不加表」，则复用回执表已有 `OPT_RESULT` / `OPT_RESULT_DESC` / 处理人字段，但只能记最后一次（明确降级）。

### FR-4 单边查询「申请退款」接入

**FR-4.1 复用现有写端点**：`POST /page/gate-txn-pay/{orderNo}/refund`，body `{refundAmount(int, 分), refundReason?}`；已实现 `GateTxnPayManualOpsService.requestRefund` 的校验（金额 >0 且 ≤ 订单扣费金额、`DebitStatus.isRefundable` 白名单、日票订单拒绝、支付宝/微信分渠道退款）——**NEVER 新造退款链路**。

**FR-4.2 前端**：单边详情页底部增「申请退款」按钮（旧侧有此动作）；点击弹确认框，显示订单号、订单金额、实际扣款金额、可退金额；提交复用 `web/src/api/trans/oneSideQuery.js` 新增 `requestRefund` 方法。

**FR-4.3 约束**：退款按钮可用条件用**白名单**（`debitStatus` 属可退集 + `refundAmount` 未退满 + 非日票），其余一律灰显；金额默认取订单扣费金额可改但不得超限（服务端二次校验）；按钮带 `v-hasPermi=['trans:one-side:refund']`。

> ⚠️ 旧侧「申请退款」是否等于新侧「过闸扣费退款」**需业主确认**（D3）：旧页属人工处理单语义，新端点是扣费订单退款，二者数据源都是 `GATE_TXN_PAY` 但业务前提可能不同。D3 未裁定前只做前端接入设计，不实际开放按钮。

### FR-5 导出能力

- 旧 TVM 充值订单、单边查询有导出；新 6 页均无导出按钮。
- 走 IT-056 已启用的**异步导出任务框架**（`SYS_JOB` + 导出执行器），新增两个导出执行器与 `EXPORT_TYPE` 枚举值，不新造同步下载链路。
- 导出字段按 §FR-1.2 列口径；上限 20000 行，超出提示缩小范围；导出文件存既有 `async_export_task` 路径，前端从「异步导出任务」监控页下载。

## 4. 非功能需求（NFR）

- **NFR-1 兼容性**：现有 6 个 GET 端点路径不变，新增参数向后兼容（可空）；新增写端点独立于既有退款端点。
- **NFR-2 权限**：新增 F 型按钮权限 `trans:{topup-suspicious:resolve,one-side:refund}` + `SYS_MENU` F 行；`superadmin` 走 `*:*:*` 无需绑定，其它角色需勾 `SYS_ROLE_MENU`。
- **NFR-3 审计**：所有写操作（存疑处置/单边退款）记录操作人、时间、前后状态、原因；审计 IP 恒 `127.0.0.6` 问题（IT-064）属基础设施层，本需求不处理但验收时标注。
- **NFR-4 状态机**：一律枚举 + 迁移表 + `canTransitTo`，配 `*WhitelistTest`；NEVER 散落 `if` 比状态字符串。
- **NFR-5 性能**：425,048 条操作历史服务端分页 + 索引；导出走异步框架限量 20000 行；八张 RANGE 分区表只到 P202612，超范围日期查询要有明确提示。
- **NFR-6 序列化**：新增 DTO 一律放 `model`，用 Fastjson2；NEVER 引入 Jackson/Gson。
- **NFR-7 事务**：退款/处置写操作 `@Transactional` 边界在 service 层；跨服务调用走 `rpc` 模块直连；幂等靠 DB 唯一约束 + `DuplicateKeyException` 兜底，不引入 Redis/MQ。
- **NFR-8 安全复核**：FR-3 / FR-4 均涉及资金与状态变更，实施前 MUST 提示人工复核；NEVER 修改现有加密/签名逻辑。

| D3 | 旧「申请退款」是否等于新过闸退款 | A 复用 `POST /{orderNo}/refund`（推荐） / B 另起端点 / C 不做 | A，但裁定前不开放按钮 |
| D4 | 异常类型 3/4/5 映射 | 现查新库分布后定；人工处理单是否单列状态 | 待现查 |
| D5 | 在线补款「操作」语义 | ① 只读保留现状 ② 补人工动作页 ③ 取消该页 | ① |
| D6 | 2 条存疑老单是否迁移 | A 只读历史展示 / B 按 orderNo 补关联回执 / C 不迁 | A |

> D1 的前提：旧侧存疑判定依据是「订单 + 写卡 + 支付 + 操作历史」四态，新回执页只有故障/错误码/处理结论。若不补订单视角，运营无法判断「钱付了没写卡」——这是 §1 判 🔴 的根因，不是页面字段多少的问题。
> D3 特别说明：新端点 `GateTxnPayManualOpsService.requestRefund` 已校验 `DebitStatus.isRefundable`、日票拒绝、金额上限，且已支持支付宝/微信分渠道；旧侧「人工处理单」的业务前提若不同，强行复用会产生错误退款——必须先由业主确认语义。
