# 设计文档：APP 流量接入层「新老用户」渐进迁移分流

## 0. 背景与目标

本项目是老项目改造，存量用户正在**渐进式迁移**到本套新链路。
流量接入到 `fep-app-server`（端口 9101，薄接入层）后，需要：

1. **判定该请求是否「存量旧用户」**；
2. **旧用户 → 分发到旧系统**（原报文原样透传，含 `sign`）；
3. **新用户 → 走现有路由**（`service.*.url` 指向的本套新服务）。

本设计把分流落在 **`fep-app-server` 接入层**，先只覆盖**订单支付主链路**（`CollectPayController` 8 个端点），控制改动面。

## 2. 总体链路

```
APP 请求 (ItpCommonFormRequest: providerId ... sign ... bizData)
   │
   ▼
fep-app-server / CollectPayController (8 端点)
   │
   │  ① 取用户键：thirdUserId = parseBizData(request, 兜底 DTO).getThirdUserId()
   │  ② UserRouteService.route(thirdUserId)
   │       ├── 查本地缓存 (Caffeine, key=thirdUserId)
   │       └── 未命中 → rpc → account-server 查名单
   │
   ├── 命中旧系统名单 (LEGACY)
   │      → LegacyCollectPayClient (base = service.legacy.url, 占位键)
   │      → 原报文 toFormDataMap(request) 原样透传，含 sign
   │
   └── 未命中 (NEW)
          → 现有 CollectPayClient (base = service.collectPay.url)
          → 走本套新链路
```

## 3. 数据层：分流名单

### 3.1 定案（2026-10-14：不建独立表，用 `USER_ITP_REG_INFO` 存在性判定）

落在 `account-server`（它本来就持有 `USER_ITP_REG_INFO`，路由判定数据同源最自然）。

**分流口径（2026-10-14 定案）**：不另建独立名单表，直接用既有账号注册表 `USER_ITP_REG_INFO` 判定。
网关/分流器只读查 `third_user_id` 在 `USER_ITP_REG_INFO` 里**是否存在任意记录**（不看 `DEL_YN`）：

- **存在（含已注销行 `DEL_YN=0`）** ⇒ 该用户已在新系统开过户 ⇒ 打**新 ITP**（fep-app）；
- **不存在** ⇒ 尚未开户的旧用户 ⇒ 打**旧 ITP**（LEGACY 承接）；
- `thirdUserId` 缺失 / DB 故障 ⇒ fail-safe 打**旧 ITP**（承接兜底）。

```sql
-- 网关/分流器只读点查（QDITP schema，只读账号 itp_ro，不写库）
SELECT CASE WHEN COUNT(*) > 0 THEN 1 ELSE 0 END
FROM qditp.user_itp_reg_info
WHERE third_user_id = ?;
-- 返回 1 ⇒ 走新 ITP；返回 0 ⇒ 走旧 ITP
```

> 与旧「方案 B 独立名单表 `USER_MIGRATE_ROUTE`」的差别：不新增表、不维护 `STATUS`/`ROUTE_TARGET` 状态机，
> 判定完全由注册表的存在性天然驱动——**已开过户的用户自然走新，没开过户的自然走旧**，无需人工逐批改状态。
> `THIRD_USER_ID` 点查 MUST 有 B 树索引（表按 `THIRD_USER_ID_SUFFIX` LIST 分区，见 `account-server-schema.sql`），
> 否则每请求扫全分区。

### 3.2 查询端点（account-server）

```
POST /internal/user-route/{thirdUserId}
```
- 仅内网 `/internal/**`（与 `USER_ITP_REG_INFO` 同模块（account-server）的既有 `/internal/**` 风格一致，**综管台 `/page/**` 无鉴权、MUST 不挂到 `/page/**`**，见 `AGENTS.md` 排障第一怀疑对象）。
- 返回 `CommonResult`：`retCode=0000` + `retMsg` + 业务体 `{ "routeTarget": "LEGACY" | "NEW" }`。
- 查法：`thirdUserId` 在 `USER_ITP_REG_INFO` 有任意记录（不看 `DEL_YN`）⇒ `NEW`；无记录 ⇒ `LEGACY`；DB 故障/缺失 ⇒ fail-safe `LEGACY`。

## 4. fep-app-server 侧改动（核心）

> 遵守 F1：**不在 fep-app 写查表/事务/直连 DB**；只加"取用户键 + 选下游 + 透传"的编排。

### 4.1 新增 `UserRouteService`（fep-app 内，纯编排）

```java
@Service
public class UserRouteService {
    // 注入：UserRouteClient (rpc) + Caffeine 本地缓存
    // 缓存 key=thirdUserId, value=RouteDecision(LEGACY/NEW), TTL 可配 (user-route.cache.ttl)

    public boolean isLegacy(String thirdUserId) {
        // 1) 缓存命中直接返
        // 2) 未命中 → 查 USER_ITP_REG_INFO 存在性（有记录=NEW/无记录=LEGACY）→ 落缓存 → 返
        // 3) DB 查询失败/超时/uid 缺失 → 兜底返 LEGACY（fail-safe 走旧 ITP 承接，避免把活流量挡死；见 §7 D2）
    }
}
```

**缓存必要性**：注册表存在性是**低频变更、命中率极高**，本地 Caffeine（TTL 分钟级）能避免每个请求都打一次 DB。
**fail-safe 原则（默认，2026-10-14 定案）**：路由查询本身挂了/超时/uid 缺失 ⇒ 按"未开户"走**旧 ITP 承接**，**不把故障放大成整条链路 404**；同时落日志告警。（区别于早期"fail-open 走新"——定案取 fail-safe 走旧，理由：旧 ITP 是存量承接方，流量误投旧系统可被业务兜住，误投新系统则可能撞上"新链路尚未接管"的空洞。）

### 4.2 取用户键

`thirdUserId` 在 `bizData` 里（F5），公共字段上没有。两种取法：
- **推荐**：`CollectPayController` 各端点先 `parseBizData(request, <对应请求 DTO>)` 取 `getThirdUserId()`；该 DTO 已存在（`model` 模块）。
- **轻量兜底**：单独解析 `bizData` 里 `thirdUserId` 字段（`JSON.parseObject(bizData).getString("thirdUserId")`），不依赖具体业务 DTO。
- **若 `thirdUserId` 缺失** ⇒ 无法分流 ⇒ fail-safe 走旧 ITP 承接 + 告警日志（§7 D2 定案）。

### 4.3 双下游选择

在 `CollectPayController` 里按 `userRouteService.isLegacy(thirdUserId)` 选 client：

```java
@PostMapping("/ci/app/requestOrder")
public JSONObject requestOrder(@ModelAttribute ItpCommonFormRequest request) {
    log.info("IF8A-20 请求下单, request={}", request);
    String thirdUserId = /* §4.2 取键 */;
    Map<String,String> form = toFormDataMap(request);   // 原报文原样，含 sign（F6）
    if (userRouteService.isLegacy(thirdUserId)) {
        return legacyCollectPayClient.requestOrder(form);   // 旧系统
    }
    return collectPayClient.requestOrder(form);             // 新链路
}
```

8 个端点同型改造。`toFormDataMap(request)` 复用现有方法，**保证 sign 原值透传**。

### 4.4 新增 `LegacyCollectPayClient`（rpc 模块）

与 `CollectPayClient` 同型（`ProxyWebClient` 子类），构造 base = `service.legacy.url`，方法集合与 8 端点对应：

```java
@Service
public class LegacyCollectPayClient extends ProxyWebClient {
    public LegacyCollectPayClient(@Value("${service.legacy.url:}") String base, ...) { super(base, ...); }
    // requestOrder / requestPaymentInfo / ... 8 个，path 与旧系统侧对齐（旧系统的真实路径需甲方给）
}
```

## 6. 回滚与安全

- **回滚**：把 `user-route.fail-policy` 改回 `NEW` 或 `service.legacy.url` 置空 + 重启 fep-app ⇒ 全部流量回新链路（旧用户也暂时走新链路，需业务评估是否可接受）；更稳妥的灰度是**逐批把旧 ITP 存量用户在新系统开户**（写 `USER_ITP_REG_INFO` 注册记录）——开过即"在表"自动走新 ITP，无需改任何客户端。
- **安全**：`/internal/user-route/**` MUST 限内网；分流透传 **MUST 原样带 sign**（F6），不得在 fep-app 加验签（本模块不验签，下游负责，`AGENTS.md` §2.2.1 红线）。
- **可审计**：每次分流决策（`thirdUserId → LEGACY/NEW`）MUST 落日志，含 `thirdUserId`（脱敏按现有 `toString` 口径，`sign` 已脱敏、`bizData` 注意敏感字段）。

### 15.2 档 1 的关键论据（互联网资料，逐条标注出处）

### 15.3 档 1 的最小完整改动清单（如果走这条路）

```
1. 新增 1 个内网名单查询接口
   account-server /internal/user-route/{thirdUserId} → { "routeTarget": "LEGACY"|"NEW" }
   （查 `USER_ITP_REG_INFO` 存在性，复用档 2 的接口，不建独立表）

2. 新增 1 个 Wasm 插件（Rust/Go，proxy-wasm SDK）
   - 只匹配 /fep-app/ 前缀
   - 解析 form body 取 thirdUserId（buffer 必须，§15.2 L5）
   - 查注册表存在性接口（插件侧 C 缓存，TTL 可配；DB 故障 → FAIL_SAFE 走旧 ITP 承接，§15.2 L4）
   - 命中旧 → 改写 :authority / :path 指旧系统 ServiceEntry；未命中 → 不动

3. 新增 1 个 ServiceEntry（EXTERNAL_NAME）指旧系统
   hosts: <旧系统域名/IP>, resolutionMode: EXTERNAL_NAME, port 对齐（§15.2 L10）

4. fep-app-vr（itp ns）加第二条 match：
   - headers: { X-User-Route: exact: LEGACY } → destination <ServiceEntry host>
   - 缺省 → 仍走 fep-app-hr32k-svc:9101

5. 给网关 ingressgateway 挂 WasmPlugin（matchLabels: istio=ingressgateway）

6. EnvoyFilter：给 ingressgateway 加 request buffer（max_request_bytes 按 bizData 最大 size 设）
```

### 15.6 一个容易踩的坑（Internet 资料反证）

**EnvoyFilter 写 header 不能动态影响 VS 路由**：swill.fun "VirtualService Routing Fails After EnvoyFilter Injects a Header" 坐实了 Envoy 路由匹配在 HTTP filter chain 之前完成，Lua 写 header 不会重算路由。所以"EnvoyFilter 写 `X-User-Route` 让 VS 按 header 切"这条看似最轻的路线**走不通**——这就是档 1 必须上 Wasm 插件（Wasm 可以 `clear_route_cache` 或改 `:authority` 让路由重算，且可解析 body）的根因。

### 15.7 Wasm 插件耗时评估（2025/2026 互联网 benchmark，带数字）

> 本条专门回答"档 1 的 Wasm 插件大概耗时多久、是不是最佳实践"。数据来自 4 篇 2025/2026 公开 benchmark，**不是本项目实测**（测试环境无底座，还没法压测）。

#### 通用 Wasm 插件开销区间（与业务逻辑无关的纯开销）

| 场景 | 耗时增量 | 出处 |
|---|---|---|
| 简单 header 注入（telemetry 类） | **p99 +0.3 ms** | johal.in 2025 Istio 1.22 vs Linkerd 2.15 |
| 一般 L7 逻辑（含 body 解析） | **p99 +0.5~2 ms** | servicemeshblog.com "Native C++ ~0.1ms vs WASM ~0.5–2ms" |
| Rust Wasm（推理型策略） | **p99 8.2 ms**（10k RPS，m5.4xlarge） | johal.in 2025 Istio Benchmark Suite |
| Python Wasm（Pyodide 0.26） | **p99 12.5 ms** | 同上 |
| Lua 对照 | p99 35 ms | 同上 |
| C++ 原生对照 | p99 9.1 ms | 同上 |
| 冷启动（每个新 proxy） | **+22 ms / proxy**（VM 初始化）+ 8% 内存 | johal.in "Wasm plugin system adds 22ms cold-start latency per proxy" |

#### 本场景（旧用户命中路径）单请求增量拆解

```
请求进入网关 ingressgateway
  → Envoy 加 request buffer（+0~0.2 ms，看 body 大小）
  → Wasm 插件 on_http_request_body
      → 解析 form body 取 thirdUserId（+0.1~0.3 ms，JSON 字符串定位）
      → 查本地 C 缓存
          ├── 命中：+0.05 ms
          └── 未命中：发 async proxy_http_call 到 account-server
                     /internal/user-route/{thirdUserId}
                     → 名单查询服务 RT（+2~10 ms，看网络+服务处理）
  → 改写 :authority / :path 指旧系统 ServiceEntry（+0.05 ms）
  → 路由重算 / clear_route_cache（+0.05 ms）
```

| 情形 | 单请求增量 | 说明 |
|---|---|---|
| 旧/新用户 + 名单 C 缓存**命中** | **~0.5~1 ms** | 纯 Wasm 开销，接近"一般 L7 逻辑"区间（15.7 通用表） |
| 旧/新用户 + 名单 C 缓存**未命中** | **~3~15 ms**（取决于名单查询服务 RT） | **大头是名单查询服务的 RT，不是 Wasm 本身** |
| 新 ingressgateway pod 冷启动 | **+22 ms**（一次性） | 不影响稳态每请求 |

**对照本项目量级**（`docs/` ADR-D122 支付宝开户热态 273ms / 冷态 2785ms，调用方只给 2500ms 超时）：
- **+3~15 ms 的 Wasm 开销对这个量级不敏感**；
- 但**DB 查询挂 + 缓存未命中 → FAIL_SAFE 走旧 ITP 承接，这 2~10 ms 已经耗掉**，不能"零代价回退"。

#### Wasm 的 4 条硬约束（影响设计，必须遵守）

| 约束 | 影响 | 出处 |
|---|---|---|
| **不能同步阻塞 HTTP 调用** | 查名单 MUST 走 `async proxy_http_call`；名单查询 RT 直接叠加到请求上 | servicemeshblog "Blocking calls are not allowed — WASM runs in Envoy's event loop. Never make synchronous HTTP calls. Use DispatchHttpCall for async external calls" |
| **默认 Wasm heap 100MB** | body 大时（form 含长 bizData）要扩 `vm_config.runtime` 的 heap size | servicemeshblog "Default WASM module heap is 100MB. Set vm_config.runtime: envoy.wasm.runtime.v8 and configure heap size if needed" |
| **共享状态是 per-worker 的** | Envoy 多 worker，跨 worker 共享名单 C 缓存 MUST 用 `proxy_set_shared_data` | servicemeshblog "Shared state is per-worker... Use the shared KV store API for cross-worker state" |
| **无文件系统 / 无 raw socket** | 名单 / 配置 MUST 从 `pluginConfig` JSON 或外呼接口取，不能读文件 / 开 socket | oneuptime "Plugins run in a sandbox and cannot access the host filesystem... no raw socket access" |

#### 是否最佳实践（分场景）

| 场景 | 最佳实践？ | 理由 |
|---|---|---|
| **测试环境、少量用户、灰度期** | ❌ **不是**。档 2（fep-app 内部分流）更合适 | 改动小、风险面小、不用维护 Wasm 模块管线、不用挂 ServiceEntry、不用压测 |
| **生产、大流量、多用户、长期** | ✅ **是**。档 1 网关 Wasm 插件更合适 | 把"分流"从业务代码剥离到网关侧，fep-app 不用为"分流"反复发版；网关侧缓存摊薄名单查询成本；**业务零感知**（客户端完全不动） |
| **纯按百分比灰度（不按人）** | ❌ **档 0（VS weight）更轻**，用不着 Wasm | 改 1 个 VS 即生效 |
| **按用户但客户端能带 header** | ⚠️ **档 0 + header 比 Wasm 更简单** | 客户端加 `X-User-Route: LEGACY` header → VS 直接按 header 切，**不需要 Wasm**（但客户端要改，不满足"业务无感知"） |

#### 档 1 上线前的 4 个 MUST（§15.4 的 3 个 + 本条新增 1 个）

1. 确认生产 Istio 版本 ≥1.12（`kubectl -n istio-system get pod -o wide`）；
2. 压测 Wasm 插件 p99 开销（**<5% 是 Istio 1.23 官方 benchmark 口径**）；
3. 给 Wasm 插件挂 `failStrategy: FAIL_OPEN` + 健康告警；
4. **名单查询服务加 C 缓存 + 多 worker 用 `proxy_set_shared_data` 共享**（否则每个 worker 各自缓存、命中率骤降，且未命中 RT 叠加到请求上）。

## 17. 档 3：SCG 透明网关（Spring Cloud Gateway，新增默认推荐）

> 本章节专门回答"能不能再添加一个服务做透明网关，比如 Spring Cloud Gateway"。结论：**能，且对你这个场景"比 Istio Wasm 插件更适合"——代价是新增 1 个服务 + 一次入口流量改造，但 fep-app 完全不动。**

> **选型更新（2026-10-13）**：本档 3 默认采用 **SCG Web MVC 版**（`spring-cloud-starter-gateway-server-webmvc`，同步编程模型 + Tomcat/Jetty 运行时 + 内置 `FormFilter` 原生处理 form 报文），**不再默认 WebFlux 版**。理由：
> 1. 理论峰值 **< 5k QPS**，Web MVC 版线程池在中等流量下足够（配合线程池调优 + 下游硬超时）；
> 2. qd-itp 报文为 `application/x-www-form-urlencoded`，Web MVC 版 `FormFilter` 原生支持，无需 WebFlux 版的 `AdaptCachedBody` 兜底；
> 3. 同步编程模型 + Servlet 日常，团队理解成本低、交付快、调试友好（栈完整）；
> 4. WebFlux 版作为**流量 > 5k QPS 时的升级路径保留**（路由 DSL 几乎 1:1 迁移）。
>
> **名单查询方式更新（2026-10-14 定案：查 `USER_ITP_REG_INFO` 存在性）**：默认**网关直连业务库查注册表**（`spring-boot-starter-jdbc` + `JdbcTemplate`/`HikariCP` + `Caffeine` 本地缓存），**不再依赖外部 Redis / HTTP 名单查询服务，也不再建独立名单表 `USER_MIGRATE_ROUTE`**。判定口径：`thirdUserId` 在 `USER_ITP_REG_INFO` **有任意记录（不看 `DEL_YN`）** ⇒ 走新 ITP；**无记录** ⇒ 走旧 ITP；uid 缺失 / DB 故障 ⇒ fail-safe 走旧 ITP。要点：
> - 用**专用只读账号**连 `172.20.222.3:1521/AFCITPDB`（schema `QDITP`），网关只查不写；
> - `USER_ITP_REG_INFO.THIRD_USER_ID` MUST 带 B 树索引（表按 `THIRD_USER_ID_SUFFIX` LIST 分区，每请求一次点查）；
> - `JdbcTemplate` 设 `queryTimeout=2s`，DB 抖动快速 fail-safe 走旧 ITP；
> - `HikariCP` 池设小（20 级），避免网关池跑满业务库（DB 故障放大成网关雪崩）；
> - `Caffeine` TTL 30s 挡 90%+ 查询，DB 查询失败仍可命中旧值。
>
> **动态维护 URL 更新（2026-10-13，Actuator 直接维护版，去 `@Scheduled` 扫表，去 Nacos/Redis，零新第三方服务）**：来源路径 + 旧系统出口 + 新系统出口全由**两条路由**（`legacy-route`/`new-route`）承载，DBA/运维**直接调 Actuator API** 改/删/增路由即生效，**不扫表、不落库、不接 Nacos**。依赖只用**HikariCP（Spring Boot 默认连接池，查名单）+ ojdbc11 + Caffeine 本地缓存 + Spring Boot 内置 Actuator**（零新第三方服务，不引 Druid/Nacos/Redis）。要点：
> - **改出口 URL**：DBA/运维 `POST /actuator/gateway/routes/{legacy-route|new-route}`（改 `uri`）+ `POST /actuator/gateway/refresh`，**立即生效**（不用等 30s、不用改库、不用改 Nacos）；
> - **改来源路径**：两条路由的 `predicates`（`Path=...`）**一起 POST 改** + `refresh`（漏改一条 = 名单命中/不命中某一方新路径进不来）；
> - **紧急全切新系统**：`DELETE /actuator/gateway/routes/legacy-route` + `refresh`（LEGACY 路由没了，名单命中也全落 `new-route`）；恢复时 `POST` 重建 legacy-route；
> - **名单查询仍走 DB**（`USER_ITP_REG_INFO`，Caffeine 挡）：`legacy-route` 带名单断言（`thirdUserId` 不在注册表才匹配 → 走旧 ITP），`new-route` 兜底全量；出口 URL 维护权完全交给 Actuator，名单断言只负责"判断走 legacy 还是 new"；
> - **DB 熔断 + 自动回切（M8）**：连续 3 次 DB 查询失败/超时 → 熔断短路 30s（不打 DB，用 Caffeine 旧值、无缓存 fail-safe 走旧 ITP）；到期半开试探，DB 恢复自动回切；防"库挂 = 网关雪崩"，也防"库恢复但永远走旧"；
> - **Caffeine 冷启动预热（M9）**：`@PostConstruct` 把 `USER_ITP_REG_INFO` 全量 `third_user_id` load 进 Caffeine（分批 5000，DB 失败降级空启动），避免启动后"冷穿透"打爆连接池；上线前实测 uid 基数配 `maximumSize`（10w→100w 按量级）；
> - **traceId 全链路透传（采纳）**：网关入向补/透传 `X-Request-Id`（缺省 UUID），下游 MDC 接进日志，全链路排障；
> - **防"改不生效" 4 条 MUST（D1-D4，见最佳实践文档 §7.9）**：改路由后 MUST `refresh`、出口 URL 兜底默认值、紧急全切用 DELETE 路由（不改空 uri）、来源路径两条路由一起改；
> - **审计**（可选）：DBA/运维在 `gateway_route_change_log` 纯记录表手工 INSERT 留痕（网关不查它，不参与刷新链路），或靠 K8s/堡垒机操作日志。
>
> 下文 §17.1~§17.10 的 WebFlux 版 + 外部名单服务描述（GlobalFilter/ReadBody/响应式 API/`account-server /internal/user-route` 接口）作为**升级路径与回退参考**保留；**实际落码按 Web MVC 版 + 直连 DB 查名单 + Actuator 直接维护路由 URL（两条路由 + 名单断言，不扫表不落库）+ DB 熔断 + Caffeine 预热 + traceId 透传**，详见 `docs/spring-cloud-gateway/SCG网关功能与最佳实践.md` §七（含依赖、两条路由 DSL、`UserRouteResolver` 名单断言 + 熔断 + 预热、连接池配置、traceId、上线前 M1~M9 + D1~D4 + §7.9 Actuator 维护操作手册 + §7.12 明确不做的事）。

### 17.5 4 条硬约束（设计时必守）

| # | 约束 | 出处 | 影响 |
|---|---|---|---|
| C1 | **响应式 API**：GlobalFilter 里查名单 MUST 用 `WebClient` / `ReactiveRedisTemplate`，**不能阻塞** | CSDN "Reactive 编程模型要求不能随便调用阻塞式 API。在 GlobalFilter 里直接查 Redis、调远程接口，Gateway 的吞吐量会直线下滑" | 阻塞 = QPS 直降 |

| C4 | **线程安全**：GlobalFilter 是单例，避免非线程安全成员变量 | juejin "GlobalFilter 是单例的,避免使用非线程安全的成员变量" | 用 Caffeine / ConcurrentHashMap 兜底 |

## 23. fep-app 能否被 SCG 完全替代？（代码实测结论）

> 本章节回答"加了 SCG 后 fep-app 是不是多余的"。结论：**fep-app 不能被 SCG 完全替代——两者是分工关系，不是替代关系。SCG 做"选哪条路"，fep-app 做"怎么把请求送下去"。**

### 23.1 fep-app 的真实职责（10 个 Controller / 几十端点，代码实测）

| 职责 | 代码证据 | SCG 能做？ |
|---|---|---|
| **双别名路由**（同一端点 2~4 个 URL） | `@PostMapping({"/ci/app/requestApplication", "/app/requestApplication"})`；日票 `@PostMapping({"/ci/app/dailyTicket/requestOrder", "/app/dailyTicket/requestOrder", "/app/requestCountingOrder"})` | ⚠️ 能做但要维护几十组别名规则，**契约漂移风险**（下游改 URL 时 SCG 规则不跟） |
| **DTO 解析 + 按类透传** | `BaseAppController.parseBizData(request, TargetDTO.class)` 按端点选 DTO；`AccountAppServiceImpl.requestApplication` 收 `RequestApplicationReqDTO` 转 `AccountClient.requestApplication` | ⚠️ SCG 读原始 form body（String），**不做 DTO 解析**；要透传给下游得重新组 form，**契约对不上** |
| **多 client 编排**（一个端点调多个下游） | `GateTxnPayController` 同时注入 `GateTxnPayClient` + `FacePayClient`；`AccountAppServiceImpl` 同时用 `AccountClient` + `KeyClient` | ❌ SCG 是**单路由单目标**，编排逻辑要写成 filter 调 N 个 client，**等于把 fep-app 的 service 层重写在网关里** |
| **回调接收**（`@RequestBody String` 而非 form） | `PaySignController.receivePayResult(@RequestBody String requestBody)`、`DailyTicketAppServiceImpl.receivePayNotify/receiveRefundNotify` | ⚠️ SCG 能转发回调，但**回调解析逻辑仍在下游**，fep-app 这层只是"接住 + 透传"，去掉后下游要自己接回调 |
| **日志 + 脱敏** | `log.info("IF8A-xx 请求..., request={}", request)`，`ItpCommonFormRequest.toString()` 对 `sign` 脱敏 | ⚠️ SCG 能记访问日志，但**不解析业务字段、不做 sign 脱敏**，审计能力降级 |

### 23.2 为什么不能"完全替代"——3 个硬理由

1. **契约耦合**：fep-app 的 13 组下游 `service.*.url` 都**依赖 fep-app 透传的是"解析后的 DTO + 原 form"**。SCG 读原始 form body，要么不解析直接透传（下游要自己解析，行为变了），要么 SCG 自己组 form（**契约在网关里复制一份，下游改字段时 SCG 规则不跟 = 契约漂移**）。
2. **编排逻辑**：`GateTxnPayController` 一个端点调 2 个 client、`AccountAppServiceImpl` 一个端点调 2 个 client——**这不是"路由"，是"编排"**。SCG 的模型是"一个请求 → 一个目标"，编排要写成 GlobalFilter 串 N 个 client，**等于把 fep-app 的 service 层重写到网关里**，维护面更大。
3. **双别名路由**：几十个端点每个 2~4 个别名，SCG 要维护几十组 `predicates: [Path=/ci/app/x, Path=/app/x]`，**下游改 URL 时 SCG 规则不跟**（fep-app 里是注解，编译期检查；SCG 里是配置，运行期 404）。

### 23.3 SCG 与 fep-app 的合理分工（档 3 的核心认知）

```
APP 请求 (form 报文)
   │
   ▼
SCG 透明网关 (user-route-gateway)  ← 只做"选哪条路"
   │  ① 读 body 取 thirdUserId
   │  ② 查名单
   │     ├── 旧用户 → 旧系统（原报文原样透传，含 sign）
   │     └── 新用户 → fep-app-svc:9101（原报文原样透传）
   ▼
fep-app (保留，做"解析 + 编排 + 双别名 + 回调 + 日志")
   │  ① parseBizData → DTO
   │  ② 按端点选 client（account / collect-pay / pay-sign / ...）
   │  ③ 双别名路由（/ci/app/x + /app/x）
   │  ④ 多 client 编排（GateTxnPay 调 2 个 client）
   │  ⑤ 回调接收（receivePayResult 等）
   ▼
下游服务（account-server / collect-pay / ...）
```

**关键认知**：
- **fep-app 不能删**——新用户（占大多数）还要走它；
- **fep-app 不用改**（档 3 的核心优势）——SCG 在 fep-app 前面做分流，fep-app 代码/配置/发布全都不动；
- **未来退场路径**：等所有用户都已在 `USER_ITP_REG_INFO` 里开过户（表中存在 ⇒ 全走新 ITP）后，**SCG 也可以退场**（入口直接指 fep-app），fep-app 继续做"解析 + 编排 + 路由"。

### 23.4 什么时候 fep-app 才能被替代（远期）

| 条件 | 现状 |
|---|---|
| 所有端点的 DTO 解析下沉到下游（下游自己解析 form body） | ❌ 下游目前依赖 fep-app 透传的 DTO |
| 多 client 编排下沉到下游（每个下游自己调兄弟服务） | ❌ 目前 fep-app 做编排 |
| 双别名路由收敛为单别名 | ❌ 目前几十组别名 |
| 回调接收下沉到下游 | ❌ 目前 fep-app 接住后透传 |

**结论**：在"渐进迁移"的过渡期，**fep-app 必须保留**；SCG 只做"分流"，**不替代 fep-app 的解析/编排/别名/回调职责**。等迁移完成 + 下游能力下沉后，fep-app 才可逐步瘦身，最终退场。

### 23.5 退场路线图（从"SCG + fep-app 并存"到"只剩 fep-app + 下游"）

> 本章节给一张 4 阶段的退场路线图，回答"什么时候 SCG 可以退场、fep-app 能瘦到多薄"。**前提事实（改动前 MUST 复核）**：
> - fep-app 现有 10 个 Controller / 几十端点 / 13 组 `service.*.url` 下游（§23.1 代码实测）；
> - SCG 在 fep-app 前做"分流"（不在表的用户打旧系统、在表的用户打 fep-app）；
> - 注册表 `USER_ITP_REG_INFO` 的**存在性**记录哪些 `thirdUserId` 已在新系统开过户（方案 A，§3）——在表⇒走新，不在表⇒走旧。

#### 阶段 0：分流上线（P0，本设计落地目标）

**形态**：`入口 → SCG（分流）→ {旧用户 → 旧系统 / 新用户 → fep-app → 13 组下游}`

| 项 | 状态 |
|---|---|
| SCG | 新增 `user-route-gateway/` 模块（§17.6） |
| fep-app | **不动**（代码/配置/发布全都不变） |
| 名单 | 不建表——直接用既有 `USER_ITP_REG_INFO`（存在→新 ITP，不存在→旧 ITP） |
| 旧系统 | 原报文原样透传（含 sign） |
| 回滚 | 入口 Service 指回 fep-app（1 行 yaml） |

**退出条件**：无（这是过渡期常态形态，旧用户在、SCG 就在）。

#### 阶段 1：旧用户全量迁到新链路（P1）

**目标**：所有用户都已在 `USER_ITP_REG_INFO` 里开过户（表中存在 ⇒ 全走新 ITP），旧 ITP 不再有流量。

| 项 | 动作 |
|---|---|
| 名单 | 旧 ITP 存量用户逐批在新系统开户（注册流程写 `USER_ITP_REG_INFO`），开过即"在表" ⇒ 自动走新 ITP |
| 监控 | 观察"旧系统调用量"归零（SCG 日志里 `thirdUserId → LEGACY` 的条数） |
| 旧系统 | 不再有新流量；保留冷备（出问题可临时把某批用户注册记录删除 ⇒ 点查无记录 ⇒ 打回旧 ITP） |
| fep-app / SCG | **都不动**（SCG 仍在，只是全量在表 = 所有流量走 fep-app） |

**退出条件**：`SELECT COUNT(*) FROM user_itp_reg_info` 覆盖全部目标用户（即旧 ITP 侧已无"不在表"用户），且旧系统调用量连续 N 天（建议 30 天）归零。

#### 阶段 2：SCG 退场（P2，分流层移除）

**目标**：旧系统正式下线，入口不再需要"按用户分流"，SCG 退场。

| 项 | 动作 |
|---|---|
| 入口 | Service 从 `scg-gateway:8080` 改回 `fep-app-svc:9101`（1 行 yaml + apply） |
| SCG | 下线 `user-route-gateway/` Deployment（保留镜像 + 代码，回滚用） |
| 名单 | `USER_ITP_REG_INFO` 保留（注册表常驻，审计用） |
| 旧系统 | 正式下线（或保留只读 90 天） |
| fep-app | **仍不动**（继续做解析 + 编排 + 双别名 + 回调 + 日志） |

**风险**：旧系统一旦下线，"临时打回旧系统"的回滚能力消失——**P2 启动前 MUST 确认旧用户全部迁完且无回退诉求**。

#### 阶段 3：fep-app 瘦身（P3，远期，条件成熟才做）

**目标**：fep-app 的 5 类职责（§23.1）逐步下沉到下游，fep-app 退化为"纯路由"或彻底移除。

| 下沉项 | 下沉到 | 前置条件 |
|---|---|---|
| DTO 解析（`parseBizData`） | 各下游（account-server / collect-pay / ...） | 下游接自己解析 form body，不再依赖 fep-app 透传的 DTO |
| 多 client 编排（`GateTxnPay` 调 2 个 client） | 下游自己调兄弟服务（或走 rpc 直连） | 下游具备跨服务调用能力 |
| 双别名路由（几十组） | 收敛为单别名（下游改 URL，客户端改调用） | 客户端 / 设备侧配合改 URL |
| 回调接收（`receivePayResult`） | 下游直接接回调（支付中心 / 支付宝 直连下游） | 回调地址改到下游 |
| sign 脱敏日志 | 下游 / 集中日志 | 审计能力下沉 |

**退出条件**：fep-app 的 5 类职责全部下沉后，**fep-app 可彻底移除**，入口直接指各下游（或保留一个"纯路由"网关）。

> ⚠️ **P3 不在本设计范围内**——它是"渐进迁移完成 + 下游能力下沉"后的远期动作，需要下游逐个改造（工作量 >> 本设计），建议单独立项。

#### 路线图总览

```
P0 分流上线          P1 旧用户全迁          P2 SCG 退场           P3 fep-app 瘦身
   │                    │                    │                    │
   ▼                    ▼                    ▼                    ▼
入口→SCG→{旧/新}    名单全 OFFLINE       入口→fep-app          fep-app 5 类职责下沉
fep-app 不动         旧系统冷备            SCG 下线              下游接 DTO/编排/别名/回调
旧系统原样透传       监控旧调用量归零       旧系统正式下线         fep-app 可彻底移除
   │                    │                    │                    │
   └── 本设计目标 ────┘                    └── 远期（单独立项）──┘
```

| 阶段 | SCG | fep-app | 旧系统 | 名单 | 回滚能力 |
|---|---|---|---|---|---|
| **P0** | 新增（分流） | 不动 | 原样透传 | `USER_ITP_REG_INFO` 存量（在表→新/不在表→旧） | 入口指回 fep-app |
| **P1** | 保留（全量在表） | 不动 | 冷备 | 全量在表（旧 ITP 用户全部已开户） | 临时删除某批用户注册记录打回旧 |
| **P2** | 退场 | 不动 | 下线 | 归档（`USER_ITP_REG_INFO` 保留审计） | ❌（旧系统没了） |

**关键判断**：
- **P0→P1 是"数据迁完"，SCG / fep-app 都不动**（只改名单状态）；
- **P1→P2 是"分流层退场"，入口 1 行 yaml 改回 fep-app**（SCG 下线）；
- **P2→P3 是"接入层瘦身"，需要下游逐个改造**（工作量最大，远期单独立项）。

## 24. SCG 请求耗时增加的处理方案（档 3 专项）

> 本章节专门回答"加了 SCG 后请求耗时增加怎么处理"。**核心认知：耗时增量里真正能优化的只有"名单查询"一项，且旧用户是静态存量（变更极低、占比随迁移变小），本地 Caffeine 缓存（含否定缓存）能把它几乎消灭。**

### 24.1 耗时增量的真实构成

| 增量来源 | 大小 | 能否省 |
|---|---|---|
| SCG 多一跳转发（Netty 读写 + 路由匹配） | p99 +2~5ms | ❌ 省不掉（架构代价） |
| 读 form body 取 `thirdUserId` | +0.1~0.3ms | ❌ 省不掉（要分流必须读） |
| **名单查询** | 命中 +0.5~1ms / 未命中 +3~15ms | ✅ **重点优化对象** |

### 24.2 4 层处理方案（按性价比排序）

| 层 | 手段 | 效果 | 要点 |
|---|---|---|---|
| **L1 本地 Caffeine 缓存（最关键）** | 注册表存在性结果（含**否定缓存**）缓存在 SCG 进程内，TTL 300s | 命中 +0.05ms（内存读），未命中 +3~15ms（仅首次） | **否定缓存必须做**（"不在注册表"也要缓存，否则未开户用户每次查）；已开户占比越高命中率越高，增量自然趋近 0 |
| **L2 响应式查询（不阻塞）** | GlobalFilter 里查注册表 MUST 用 `ReactiveJdbcTemplate` / `WebClient` | 不占 Netty 工作线程，QPS 不降 | 阻塞 = QPS 直降（CSDN 实测 QPS 4200→3200）；C1 约束 |
| **L3 body 只读一次 + 设上限** | ReadBody 断言缓存 body 到 exchange 属性；`max_body_size_bytes` ≤10KB；`thirdUserId` 用字符串定位不整段反序列化 | 省 0.1~0.3ms 解析开销 + 防内存膨胀 | 超大 body 直接跳过判定（fail-safe 走旧 ITP + 告警）；C2 约束 |
| **L4 只对需要的请求跑判定** | predicate 用 `Path=/ci/app/**` 限定，只订单支付主链路 8 端点触发存在性判定 | 其它路径 0 额外耗时 | 查询/参数类请求直接透传 fep-app，不查注册表 |

### 24.3 压测对照（落地前必做）

```bash
# 基线（不带 SCG，直连 fep-app）
hey -n 10000 -c 100 -q 1000 http://fep-app:9101/ci/app/requestOrder

# 带 SCG（走 user-route-gateway）
hey -n 10000 -c 100 -q 1000 http://scg-gateway:8080/ci/app/requestOrder

# 对比 p99 / QPS / CPU / 内存，算增量百分比
```

**验收口径**：
- p99 增量 < 5ms（对应互联网 L6"一般 L7 逻辑"区间）；
- QPS 降幅 < 5%（缓存命中后应接近 0）；
- 若超标，先查"否定缓存做没做 + 名单查询是不是阻塞的"——99% 的超标都是这两个。

### 24.4 压测仍超标的兜底手段（按代价从低到高）

| # | 手段 | 代价 | 适用 |
|---|---|---|---|
| 1 | Caffeine 调参：`maximumSize` 调大 + `refreshAfterWrite` 缩短 | 低 | 命中率不够 / 名单变更生效慢 |
| 2 | 名单下沉到 Redis（`/internal/user-route` 背后查 Redis 而非 Oracle） | 中 | 未命中 RT 从 3~15ms 降到 ~1ms |
| 3 | SCG 扩 pod（横向扩） | 中 | 单实例 QPS 1~3w 超了；多 worker + 多 pod 分摊 |
| **4** | **切档 1（Istio Wasm 插件）** | 高 | **SCG 这跳本身压不住时的退路**——Wasm 跑在网关进程内、**不新增一跳**，转发开销≈0，只有 Wasm 本身 +0.5~2ms |

### 24.5 关键结论

- **耗时增量主要矛盾是"名单查询"，不是"网关转发"**——L1（Caffeine + 否定缓存）解决后，绝大多数请求增量 < 1ms；
- **随迁移推进，增量自然下降**——旧用户占比越小，"未命中"越少，Caffeine 命中率越高；
- **压测是验收硬门槛**——互联网数字只是参考，你项目实际多少必须 `hey` 对照实测（§24.3）；
- **压不住的最后退路是档 1**——如果 SCG 多一跳的 +2~5ms 本身就不达标，说明延迟极敏感，**该用 Wasm 插件（不新增一跳）**，回到 §15。

## 25. 选型修正：分流面窄时档 2 优于档 3（2026-10-13）

> 本章节修正 §11/§17 的"默认推荐档 3"。新增关键事实：**分流只覆盖订单支付主链路（`CollectPayController` 8 端点），不是全接口**。分流面窄改变了档 2/档 3 的性价比结论。

### 25.1 关键事实：分流面窄

- 只有订单支付主链路（8 端点）需要按 `thirdUserId` 分流（旧用户打旧系统）；
- 查询/参数/黑名单/签约/日票等其它接口**不需要分流**，直接走新链路（fep-app → 13 组下游）。

### 25.2 为什么"分流面窄"让档 3 性价比下降

**档 3 的代价是固定的**（新增 1 服务 + 入口改造 + 名单查询 + 压测 + 一条发布线 + 监控告警），**不随分流面大小而变**；而**档 2 的代价随分流面走**（只改 `CollectPayController` 8 端点 + 1 个 `UserRouteService` + 1 个 `LegacyCollectPayClient`）。

分流面窄（就 8 端点）时：
- 档 3 的固定成本（新服务 + 入口改造）为这么点流量不值回票价；
- 档 2 搭在 fep-app 现成载体上，边际成本最低；
- 名单查询搭在 fep-app JVM 里（Caffeine），比档 3 的"响应式 Redis/WebClient"还**少一跳网络**。

### 25.3 重新对比（在"分流面窄"事实下）

| 维度 | 档 3（SCG） | 档 2（fep-app 内部） | 谁赢 |
|---|---|---|---|
| 改动面 | 新增 1 服务 + 入口改 | 改 8 端点 + 1 Service + 1 Client | **档 2** |
| 故障域 | SCG 单 pod | fep-app 单模块 | 平 |
| 业务零感知 | ✅ | ✅ | 平 |
| 名单查询 | 响应式 Redis/WebClient（多一跳网络） | Caffeine（JVM 内，更直接） | **档 2** |
| 配置动态生效 | Nacos 秒级 | 要发版 | 档 3 |
| 维护面 | 多 1 条发布线 + 监控 | 搭在 fep-app 现成发布上 | **档 2** |
| 适用 | 分流面大 / 全接口 / 长期 / 秒级灰度 | **分流面窄 / 就 8 端点 / 过渡期** | **档 2** |

### 25.4 修正后的默认推荐

| 场景 | 推荐 | 理由 |
|---|---|---|
| **分流面窄（就订单支付 8 端点）+ 过渡期** | **档 2（fep-app 内部分流）** ← **修正后默认** | 固定成本低、搭现成载体、名单查询少一跳网络、业务零感知照样做到 |
| 分流面扩到全接口 | 档 3（SCG） | 分流逻辑够重，值得独立网关收敛 |
| 要求配置秒级灰度 / 分流规则频繁变 | 档 3（SCG） | fep-app 发版扛不住，需 Nacos 热更 |
| 生产大流量（>10w QPS） | 档 1（Wasm） | 网关侧收敛、fep-app 不用为分流发版 |

### 25.5 档 2 的退路（将来上档 3/档 1 不浪费）

- 档 2 的 `UserRouteService`（查名单 + 选下游）+ `LegacyCollectPayClient`（透传旧系统）**逻辑可平移到 SCG / Wasm 插件**；
- 将来分流面扩到全接口 / 要秒级灰度 / 生产大流量 ⇒ 把 `UserRouteService` 的逻辑搬进 `user-route-gateway`（档 3）或 Wasm 插件（档 1），fep-app 里那 8 端点的 `isLegacy` 分支删掉即可；
- **档 2 不是"死路"，是过渡期最优 + 可平移**。

### 25.6 档 2 落地顺序（修正后默认执行路径，§12 细化）

1. `account-server`：`UserItpRegInfoMapper` 加 `countByThirdUserId` + `POST /internal/user-route/{thirdUserId}`（查 `USER_ITP_REG_INFO` 存在性，无记录⇒LEGACY，有记录⇒NEW，响应式无关，fep-app 用同步 rpc 调，JVM 内 Caffeine 缓存兜住）；
2. `rpc`：`UserRouteClient`（fep-app → account-server）+ `LegacyCollectPayClient`（fep-app → 旧系统，8 端点）+ `EnableRpcUserRoute`；
3. `fep-app-server`：`UserRouteService`（Caffeine + fail-open）+ 改造 `CollectPayController` 8 端点 + `FepAppServer` 加 `@EnableRpcUserRoute`；
4. `fep-app-server` 配置：`service.legacy.url`（占位，甲方回填 D4）+ `user-route.cache.ttl=300` + `user-route.fail-policy=LEGACY`（定案 fail-safe 走旧承接）；
5. 测试环境 `fep-app` Deployment：env `SERVICE_LEGACY_URL` + 重启验证；
6. 按 §9 用例 T1~T8 回归 + 观察分流日志。

> **与档 3 的边界**：档 2 只做"8 端点 + Caffeine + 发版生效"；如果将来要"全接口 + Nacos 秒级 + fep-app 不再发版"，再切档 3，把 `UserRouteService` 逻辑平移到 SCG。

## 26. 结构性事实修正：设备域不经 fep-app，分流必须上网关（2026-10-13）

> 本章节修正 §25 的"分流面窄 ⇒ 档 2 胜出"结论。新增关键事实：① **face-pay(`F2F_*`) 与 collect-pay(旧表) 都算"旧应用"，要迁走**（最终新系统是第三套）；② **设备域请求（`/itptvm/`、`/itpbom/`）不经 fep-app，网关 VS 直接打 face-pay**；③ 设备域 + 订单域都要按 `thirdUserId` 分。这三条让"分流逻辑"必须收敛到**网关层**，档 2（fep-app 内部）做不到设备域。

### 26.1 迁移结构（修正后）

```
最终形态 = 新系统（第三套，非 face-pay 非 collect-pay）

旧用户按业务域分两组打旧应用：
  ├── 设备域 TVM/BOM（/itptvm/ /itpbom/）→ face-pay（F2F_*，旧，要迁走）
  └── APP 域订单支付（/fep-app/ → collect-pay 旧表）→ collect-pay（旧，要迁走）

新用户 → 最终新系统（第三套）
```

| 角色 | 系统 | 表 | 现状（测试环境实测） | 迁移定位 |
|---|---|---|---|---|
| **旧应用 ①** | face-pay-server | `F2F_*` | `/itptvm/`、`/itpbom/` 已打它 | **旧，要迁走** |
| **旧应用 ②** | collect-pay-server | 旧表 `*_ORDER` | `/fep-app/` → fep-app → collect-pay | **旧，要迁走** |
| **新系统** | （第三套，你方提供） | — | 占位 | 最终形态 |

> ⚠️ P0 记忆"face-pay=新应用（F2F_* 相对 collect-pay 旧表是新的）"是**改造前的相对口径**；本次迁移语境下 face-pay 也归"旧、要迁走"，以甲方口径为准。

### 26.2 为什么分流必须上网关（设备域不经 fep-app）

| 业务域 | 请求前缀 | 经过谁 | 旧用户打哪 | 新用户打哪 | 分流逻辑落点 |
|---|---|---|---|---|---|
| 设备域 TVM/BOM | `/itptvm/`、`/itpbom/` | **网关 VS → face-pay（不经 fep-app）** | face-pay（旧） | 新系统（设备域新入口） | **只能网关层** |
| APP 域订单支付 | `/fep-app/` | 网关 → fep-app → collect-pay | collect-pay/旧系统 | 新系统 | fep-app 内部（档 2）或网关 |

**结论**：设备域分流 fep-app 接不到（不经 fep-app），**必须在网关层做**；订单域跟着放网关最一致。⇒ **档 2 单干做不到设备域，档 3（SCG）/ 档 1（Wasm）成为主选。**

### 26.3 名单不用加"业务域"字段

"打哪个旧应用"由**请求路径前缀天然决定**（`/itptvm/`→face-pay、`/fep-app/` 订单支付→collect-pay），名单只记 `LEGACY/NEW`。分流器按"路径前缀 + 名单结果"选目标：

```
网关分流器：
  isLegacy = 查名单(thirdUserId)
  ├── /itptvm/ 或 /itpbom/：isLegacy → face-pay（旧）；新用户 → 新系统（设备域新入口）
  └── /fep-app/ 订单支付端点：isLegacy → collect-pay/旧系统（旧）；新用户 → fep-app→collect-pay（现状）/ 新系统
```

### 26.4 修正后的选型（§25 的"档 2 胜出"作废）

| 诉求 | 推荐 |
|---|---|
| **设备域 + 订单域都按 thirdUserId 分（当前诉求）** | **档 3（SCG）/ 档 1（Wasm）**——分流收敛到网关 |
| 档 2（fep-app 内部） | **做不到设备域**（不经 fep-app），只够分订单域 ⇒ 全量诉求下不够 |
| 档 3 vs 档 1 | 测试环境 + 过渡期 + Java 栈 ⇒ **档 3**；生产大流量 + 愿意维护 Wasm ⇒ 档 1 |

### 26.5 设备域 face-pay 入向已核实（代码实测）

- face-pay 入向 Controller：`TvmOrderController`（`/ci/tvm/**`）、`BomOrderController`（`/ci/bom/**`）、`AppOrderController`（`/ci/app/**`）；
- 都带 `thirdUserId`、有 form 解析基类（`ItpCommonFormRequest`）⇒ **设备域请求确实带 `thirdUserId`，能按用户分**。

## 27. 事实修正：collect-pay 废弃，旧目标塌缩为单一 face-pay（2026-10-13）

## 29. 档 2 变体：仅 5 端点时，直接在 face-pay 里改（不上 SCG/Wasm）

> 本章节回答"就这几个接口，是不是直接在应用里改"。结论：**是——分流面窄（5 端点 / 7 处方法体）时，直接在 face-pay 里改最省，不上 SCG/Wasm 网关。**

### 29.1 为什么不上网关

| 理由 | 说明 |
|---|---|
| 分流面极窄 | 就 5 个端点（7 条 URL），网关那套固定成本（新服务 + 入口改造 + 名单查询接口 + 压测 + 发布线）不值回票价 |
| 全在 face-pay | `TvmOrderController` + `BomOrderController`，改 5 个方法体即可，**零新服务** |
| 名单查询更直接 | face-pay JVM 内 Caffeine + 同步调 account-server 内网接口，比 SCG 的响应式 Redis/WebClient 少一跳网络 |
| 故障域小 | face-pay 单模块重启即可回滚，不碰数据面热路径 |

### 29.2 改动落点（face-pay 内部分流，档 2 变体）

| `rpc` | 新增 `UserRouteClient`（face-pay → account-server）+ `LegacyClient`（face-pay → 旧/新系统 5 端点透传） |
| `account-server` | 新增 `UserItpRegInfoMapper.countByThirdUserId` + `POST /internal/user-route/{thirdUserId}`（查 `USER_ITP_REG_INFO` 存在性，复用 §3 档 2 的） |

### 29.5 D16 的逻辑澄清（关键）

"face-pay + collect-pay 都算旧、最终新系统是第三套" ⇒ 旧用户打"旧"：
- 若"旧目标"= face-pay 本身 ⇒ face-pay 里做分流、旧用户"回 face-pay" = **自己转给自己，等于没分流**；
- 若"旧目标"= 另一个旧系统（第三套之外的） ⇒ `service.legacy.url` 填那个；
- 若"旧目标"= 第三套新系统（即旧用户也打新，只是灰度阶段先放一批） ⇒ `service.newsyst.url` 就是旧用户目标。

**D16 不定，"旧/新"两个分支各打哪写不出来。** 这是档 2 变体落码前的**唯一硬卡点**。
