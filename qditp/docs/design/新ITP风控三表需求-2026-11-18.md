## 2. 范围与边界

**本需求包含**：风险规则、风险组、风险记录三张表的字段补齐、数据迁移、CRUD/查询/导出接口、页面、三者关联。

**本需求不包含（明确划线，避免范围蔓延）**：
- 灰名单自动累计逻辑（另案：`GRAYLIST_RISK` 只读台账，1821 条已迁，筛选空壳待修）。
- 黑名单的加入/解除/审批状态机（属 blacklist-server，已有完整实现）。
- "什么条件灰名单自动升黑名单"（旧系统未证实，见 §7 决策 D4）。
- 风控**规则引擎**本身（命中交易怎么写记录）——本需求只定义"记录写入接口"契约，引擎调用方由业务侧确认后另案。

## 2.5 风险组的定位与引擎加载模型（重要设计结论）

> 结论级别：**高置信度推断**（基于甲方需求原文 + 旧系统数据结构 + 通用风控引擎最佳实践）；旧后端代码不在本仓，非代码实证。业主若确认旧系统另有机制，须推翻重来。

### 2.5.1 结论

**风险组是"管理分类容器"，不是引擎的加载/执行单元。**

- **规则**＝执行单元：全部启用的规则一起加载进规则引擎，每条按自身的风险等级、阈值、优先级参与交易监控与命中判定。
- **风险组**＝运营端的查看/筛选/统计维度：给规则贴的分类标签，只在管理台用；引擎执行时不读组。
- 类比：组是文件夹，规则是文件。系统加载的是文件，文件夹只帮人整理。

### 2.5.2 证据

1. **甲方需求原文**（`cmmi5/青岛地铁互联票务系统需求分析v2.1.doc` §风险管理，两处重复）：
   > 每条规则可设置风险等级和优先级，**根据风险等级、优先级决定交易报警优先处理顺序**，生成任务并按照优先处理顺序进行任务分配。
   
   调度单位是"规则"——优先级挂规则上、排序按规则算、任务按规则分配。需求通篇未把"组"与加载/执行/生效/优先级关联。
2. **组缺少作为执行单元的一切机制**：旧组字段仅名称/描述/管理编码/入库时间；无启用状态、无版本、无生效时间、无场景/渠道选择入口。按组加载的引擎必须有"哪组生效"的选择机制——全都没有。
3. **组间规则大量重叠**：旧实证中 000008/000001/000002 同时属于组1和组2。若按组加载会重复执行、命中记录翻倍——正常设计不会这样，反证组不是规则包。
4. **通用最佳实践**：规则引擎的加载单元是"规则"或"规则集（按场景/租户/版本切分）"；若真要"多套规则互斥切换"，那叫规则集/版本发布，必须具备版本号、生效状态、灰度范围——与风险组是两回事。

### 2.5.3 对新 ITP 实现的约束

- **规则引擎按"全部启用规则"加载，按规则自身等级/优先级排序执行**；本需求不实现引擎，但 §FR-3.3 的写入接口契约按此假设设计。
- **风险组不加启用状态字段、不进引擎调度路径**；仅用于管理台筛选、统计、权限归类。
- 若未来需按场景隔离规则，给**规则**加场景标签（支付/充值/退款），引擎按交易类型过滤——而不是让组承担此职责。
- 这是 §7 决策 D1 的前提：无论选多对多中间表还是单值外键，组都不进引擎。

### FR-2 风险组管理

**FR-2.1 数据字段（目标表 `TBL_RISK_GROUP`）**

|---|---|---|---|---|

**FR-2.2 关联模型：规则 ↔ 组（决策 D1，见 §7）**

- **推荐方案 A（对齐旧系统多对多）**：新建中间表 `TBL_RISK_GROUP_RULE(GROUP_ID NUMBER(10), RULE_ID VARCHAR2(16), PRIMARY KEY(GROUP_ID,RULE_ID))`；风险组表单提供规则 checkbox 勾选；风险规则页面显示"所属风险组"多选。删除组时删中间表行、不删规则；删除规则时删中间表行（或拒绝删除，见 D2）。
- **保守方案 B（保留现有单值外键）**：不加中间表，规则表单单选组。接受与旧系统模型不一致，仅在需求文档记录差异。

**FR-2.3 接口**

**FR-2.4 页面**（`views/para/risk/group/index.vue`）
- 新增/修改弹窗增加「包含规则」checkbox 列表（数据源 `listRiskRules` 全量）。
- 列表增加「规则数」列（可选）。

> ⚠️ 旧系统字段拼写是 `rsikRuleId` / `riskHanleDate`（拼写错误），新系统列名用正确拼写 `RULE_ID` / `RISK_HANDLE_TIME`，实体里的死字段 `rsikStatus`/`riskHanleDate` 应删除或改映射，NEVER 把错误拼写带进 DDL。

**FR-3.2 快照 vs 现查（决策 D3）**：旧记录里规则名/描述/等级是**冗余快照**；新系统当前 LEFT JOIN 现查。推荐：保留 JOIN 现查作为主显示，同时新增快照列存旧迁移数据；页面优先显示快照，快照为空时回退 JOIN 值。理由：历史记录不应因规则改名/删除而丢失当时的语义。

**FR-3.3 写入接口（契约，供规则引擎调用）**
- `POST /page/risk/control-logs` body：`{cardId, userOrderNo, ruleId, riskHitTime, riskStatus?, riskHandleDesc?, riskDeviceId?}`。
- 服务端校验：cardId/ruleId/riskHitTime 必填；ruleId 不存在时**拒绝写入**（避免脏规则ID）还是**允许写入**（保留历史，旧系统无 FK）——默认允许，D3 裁定。
- 幂等：同一 `(cardId, userOrderNo, ruleId, riskHitTime)` 重复写入应去重（旧系统无证据，属新增设计，待 D3 裁定）。
- **写入调用方**：本需求不实现规则引擎，只暴露接口；实际由哪个服务在命中时调用，属 D4 待裁定。

**FR-3.4 查询与导出**
- 现有 `GET /control-logs` 的 5 个筛选条件保留；新增按 `riskStatus`、`riskDeviceId` 筛选（可选）。
- 🔴 **新增后端导出端点** `GET /page/risk/control-logs/export`，返回 xlsx（或 CSV），支持当前筛选条件、上限 20000 行。当前页面"导出 Excel"是前端逐页拉取本地生成（`views/para/risk/control-log/index.vue:88-130` 注释写明"para 侧没有导出端点"）——需求要求改为后端导出，解决大数据量导出超时/内存问题。
- 保持左关联兜底：规则删除后历史记录仍可查（现有 XML 注释的设计正确）。

**FR-3.5 页面**（`views/para/risk/control-log/index.vue`）
- 表格列补齐：规则描述、风险等级、风险状态、处理时间、处理描述、处理人、设备ID（按 D3 结果决定显示快照还是 JOIN 值）。
- 导出按钮改调后端导出端点。
- 保持只读（无增删改按钮）——风险记录是审计日志，页面不提供人工写入。

## 4. 非功能需求（NFR）

- **NFR-1 兼容性**：现有 5 个风险规则端点 + 5 个风险组端点路径不变；新增字段向后兼容（可空）。
- **NFR-2 性能**：风险记录分页查询走现有索引 `IDX_RISK_LOG_CARD_ID` / `IDX_RISK_LOG_ORDER_NO` / `IDX_RISK_LOG_RULE_TIME`；新增 `RISK_STATUS` 筛选时补索引。导出限制 20000 行，超出提示缩小范围。
- **NFR-3 审计**：风险记录只增不改不删（页面无写按钮，接口仅 POST + GET）；规则/组的增删改保留 CREATE_TIME/UPDATE_TIME。
- **NFR-4 Oracle 陷阱**：所有可空 MyBatis 参数 MUST 显式 `jdbcType`（历史 ORA-1111，见 `docs/architecture/mybatis-oracle-runtime-traps.md`）；禁 `WHERE 1=1`（Druid 注入检测拦截，见 `docs/tracking/问题清单.md` IT-060）；八张 RANGE 分区表只到 P202612，迁移时间超范围会失败。
- **NFR-5 权限**：沿用 `para:risk-rule:*` / `para:risk-group:*` / `para:risk-control-log:query`；`SYS_MENU` 2024 的 perms 与 `sys_role_menu` 绑定沿用现状（灰名单 2123 缺角色绑定是另案）。

## 7. 待业主裁定（决策点）

| 编号 | 决策 | 选项 | 默认 |
|---|---|---|---|
| D1 | 规则↔组关联模型 | A 多对多中间表（对齐旧系统） / B 单值外键（保留现状） | A |
| D2 | 删除被规则引用的风险组 | 拒绝（现状） / 级联解绑 / 允许删成孤儿 | 拒绝 |
| D3 | 风险记录字段策略 | A 快照列+JOIN回退（推荐） / B 只JOIN现查 / C 只快照 | A |
| D4 | 风险记录写入方与自动联动 | ① 仅提供接口，人工/外部系统调用 ② 接入规则引擎自动写 ③ 灰名单自动累计+升黑（旧系统未证实，见 `风险三表关系与导出说明.md`） | ① |

> D4 的 ③ 特别说明：旧系统"灰名单达阈值自动升黑名单"**没有确凿证据**——需求文档只写"根据风控灰名单，升级为黑名单"（管理台人工动作），规则描述里 000009 名称（5次入黑）与描述（10次入灰）矛盾，旧后端代码不在本仓。若业主选 ③，必须先向旧系统维护方确认真实阈值与触发条件，NEVER 依据推断实现。

> D4 的 ② 与 §2.5 的关系：按高置信度推断，引擎加载**全部启用规则**（组不参与加载）。因此 ② 的"接入规则引擎自动写记录"应按规则维度触发，NEVER 设计成"按组加载再写记录"。若业主确认旧系统确有"按组切换加载"，则 §2.5 结论与 FR-3.3 契约须一并推翻重做——这是一处需要先向旧系统维护方核实的假设点。
