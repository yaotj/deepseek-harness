# 设计定稿：APP 流量「新老用户」渐进迁移分流（仅 5 端点，face-pay 内部分流）

> **本定稿收口**：旧稿一路讨论中有多次事实修正与结论反转（旧稿 §25/§26/§27）。本定稿**只保留当前最新、自洽的结论**，把矛盾拍平、编号理顺。**设计边界：只做设计，不改代码。** 历史修正留痕见 §14。

## 0. 背景与目标

本项目是老项目改造，存量用户**渐进式迁移**到新系统。流量接入后需：
1. 判定该请求是否「存量旧用户」（按 `thirdUserId` 查名单）；
2. **旧用户 → 打旧应用**；**新用户 → 打新系统（第三套）**。

**本次分流范围（甲方指定）**：仅 **5 个设备域端点**（TVM 3 个 + BOM 票卡分析/更新 2 个，见 §8）。**不是全接口**——分流面窄是本设计选型的核心约束。

## 4. 决策树

```
你要按 thirdUserId 分流吗？
├── 否（按百分比灰度） → 档 0
└── 是 → 客户端能带 header（X-User-Route）吗？

        └── 不能（必须业务零感知） → 分流面大还是窄？
```

## 5. 最终选型：档 2 变体（仅 5 端点，直接在 face-pay 里改，不上网关）

**结论**：本次分流面窄（仅 5 端点 / 7 处方法体）+ 设备域不经 fep-app（§F3）+ 坚持 Java 栈 ⇒ **档 2 变体：直接在 face-pay 的 5 个端点方法体里加 `isLegacy` 分支，不上 SCG/Wasm 网关。**

### 5.1 为什么不上网关（档 3 / 档 1）

| 理由 | 说明 |
|---|---|
| 分流面极窄 | 就 5 端点（7 条 URL），网关那套固定成本（新服务 + 入口改造 + 名单查询接口 + 压测 + 发布线）不值回票价 |
| 全在 face-pay | `TvmOrderController` + `BomOrderController`，改 5 个方法体即可，**零新服务** |
| 名单查询更直接 | face-pay JVM 内 Caffeine + 同步调 account-server 内网接口，比 SCG 的响应式 Redis/WebClient 少一跳网络 |
| 故障域小 | face-pay 单模块重启即可回滚，不碰数据面热路径 |

### 5.2 为什么档 2 变体落在 face-pay 而不是 fep-app

- 本次 5 端点全在 **face-pay**（§F4），不在 fep-app（fep-app 是 APP 域，本次订单支付也走 face-pay 30025，§F2）；
- 设备域请求**不经 fep-app**（§F3），fep-app 接不到 ⇒ 分流只能落在 face-pay（唯一能同时接住设备域 + 订单域旧用户的应用）。

### 5.3 档 2 变体不是"死路"（可平移到档 3 / 档 1）

- `UserRouteService`（查名单 + 选下游）+ `LegacyClient`（透传旧/新系统）逻辑**可平移到 SCG / Wasm**；
- 将来分流面扩到全接口 / 要 Nacos 秒级灰度 / 生产大流量 ⇒ 把逻辑搬进 `user-route-gateway`（档 3）或 Wasm 插件（档 1），face-pay 里那 5 端点的 `isLegacy` 分支删掉即可。

## 6. 数据层：分流名单

### 6.1 分流判定表（定案 2026-10-14：方案 A，直接用 `USER_ITP_REG_INFO`，不建独立表）

落在 `account-server`（它持 `USER_ITP_REG_INFO`，路由判定数据同源最自然）。

**判定口径**：不新增名单表、不维护 `STATUS`/`ROUTE_TARGET` 状态机，直接用既有账号注册表
`USER_ITP_REG_INFO` 的存在性分流——查 `third_user_id` 是否有**任意记录**（不看 `DEL_YN`）：

```sql
-- 网关/分流器只读点查（QDITP schema，只读账号 itp_ro，不写库）
SELECT CASE WHEN COUNT(*) > 0 THEN 1 ELSE 0 END
FROM qditp.user_itp_reg_info
WHERE third_user_id = ?;
-- 返回 1（在表，含已注销行）⇒ 走新 ITP；返回 0（不在表）⇒ 走旧 ITP（LEGACY 承接）
```

- **判定**：`thirdUserId` 在 `USER_ITP_REG_INFO` 有记录 ⇒ 打新系统（fep-app）；无记录 ⇒ 打旧目标（§D16 待定）；
- **DB 故障 / uid 缺失**：fail-safe 打旧 ITP（承接兜底）；
- **灰度**：旧 ITP 存量用户在新系统逐批开户（写注册表）后自动转走新 ITP；临时删除某批用户注册记录可打回旧 ITP；
- **索引**：`THIRD_USER_ID` MUST 带 B 树索引（表按 `THIRD_USER_ID_SUFFIX` LIST 分区，建议局部索引 LOCAL，防点查扫全分区）。

> 旧「方案 B 独立名单表 `USER_MIGRATE_ROUTE`」已作废（不建表、不导入存量、不维护状态机）。

### 6.2 查询端点（account-server）

```
POST /internal/user-route/{thirdUserId}   （仅内网，MUST 不挂 /page/**）
```
- 返回 `CommonResult`：`retCode=0000` + 业务体 `{ "routeTarget": "LEGACY"|"NEW" }`；
- 查法：`thirdUserId` 在 `USER_ITP_REG_INFO` 有任意记录 ⇒ `NEW`；无记录 ⇒ `LEGACY`；DB 故障/缺失 ⇒ fail-safe `LEGACY`；
- 兜底（方案 A）：名单未建时退化为查 `selectActiveByThirdUserId`。

## 7. 分流器逻辑（face-pay 内，档 2 变体）

```
每个目标端点方法体（§8 的 7 处）：
  thirdUserId = JSON.parseObject(form.bizData).getString("thirdUserId")   // §F5
  if (thirdUserId == null) { fail-safe 走旧 ITP 承接 + 告警 }   // 2026-10-14 定案：缺失=无法判定→走旧承接
  isLegacy = userRouteService.isLegacy(thirdUserId)
              // 语义：thirdUserId 在 USER_ITP_REG_INFO 无记录 ⇒ true（走旧 ITP）
              //      有记录（含 DEL_YN=0）⇒ false（走新 ITP）；DB 故障 fail-safe 走旧
              // face-pay JVM 内 Caffeine（含否定缓存）+ 未命中同步调
              // account-server /internal/user-route/{thirdUserId}
  if (isLegacy) {
      return legacyClient.<对应方法>(form);   // §D16 旧目标
  }
  return newsysClient.<对应方法>(form);       // §D11 新系统（占位）
```

**关键约束**：
- `thirdUserId` 在 **bizData 里**（§F5），不在 `BaseDeviceRequest` 公共字段上——分流器要解析 bizData 取键，**不能整段反序列化**（字符串定位即可，省 0.1~0.3ms）；
- **fail-safe（2026-10-14 定案）**：注册表查询失败/超时/`thirdUserId` 缺失 ⇒ 按 `user-route.fail-policy`（默认 LEGACY）走**旧 ITP 承接** + 告警日志，**不把故障放大成 404**；
- **Caffeine 含否定缓存**："`thirdUserId` 不在注册表"也缓存（TTL 300s），否则未开户用户每次查；已开户占比越高命中率越高，增量自然趋近 0。

## 10. 回滚

| 场景 | 回滚动作 |
|---|---|
| face-pay 分流灰度出问题 | face-pay env `service.legacy.url` 置空 + `user-route.fail-policy=LEGACY`（定案默认 fail-safe 走旧）+ 重启 face-pay ⇒ 全回新链路；或逐批将用户注册记录 `DEL_YN` 置 0（点查无记录 ⇒ 走旧 ITP）控制分流方向 |

## 12. 请求耗时处理（档 2 变体）

| 增量来源 | 大小 | 能否省 |
|---|---|---|
| 名单查询（Caffeine 命中） | +0.05~0.1ms | ✅ L1 本地缓存 |
| 名单查询（未命中，同步调 account-server） | +3~15ms | 仅首次（否定缓存兜住） |
| 读 bizData 取 thirdUserId | +0.1~0.3ms | 字符串定位（不整段反序列化） |
| 多一跳转发 | 0 | **档 2 变体无额外一跳**（在 face-pay 进程内判定，不像 SCG 多一跳） |

**关键**：档 2 变体**没有"多一跳网关"的 +2~5ms**（那是 SCG 的代价）；增量主要矛盾是"名单查询"，L1（Caffeine + 否定缓存）解决后绝大多数请求 < 1ms。随迁移推进旧用户占比变小、命中率趋近 100%，增量自然趋近 0。

**压测对照**（落地前必做）：

```bash
# 基线（face-pay 现状）vs 加分流后，对照 p99 / QPS / CPU / 内存
hey -n 10000 -c 100 -q 1000 http://face-pay:30025/itptvm/ci/tvm/notiTakeTicketResult
```

**验收口径**：p99 增量 < 1ms（Caffeine 命中）；QPS 降幅 < 5%。超标先查"否定缓存做没做 + 名单查询是不是阻塞的"。

```
                       旧系统冷备

   └── 本设计目标 ────┘                    └── 远期（单独立项）──┘
```

| 阶段 | 名单 | face-pay 5 端点 | 旧系统 | 回滚能力 |
|---|---|---|---|---|
