# 旧 ITP 灰名单及风控链路功能梳理（2026-11-17 实扫）

> 事实来源：旧 ITP `http://58.56.166.170:9080/qd-omp` 登录实扫（`FuTianTest001`），抓取页面 HTML + 各模块 `listData` JSON。
> 证据目录：`docs/testing/admin-web/graylist-export-2026-11-17/old-side-evidence/`（9 个文件）。
> 本篇只梳理**旧系统现状事实**，不做新系统设计——目标形态与实施见同目录 `新灰名单功能对标计划.md`。

## 1. 风控域全貌（旧系统）

旧系统「风险控制」是一组相互关联的菜单，灰名单只是其中一环：

| 菜单 | URL | 记录数 | 作用 |
|---|---|---|---|
| 风险规则管理 | `risk/riskRule/list` | **8** | 定义规则（ID/名称/等级/最大值） |
| 风险组管理 | `risk/riskRuleGroup/list` | — | 规则分组（名称/描述） |
| 风险记录管理 | `risk/riskRecord/list` | **5709** | 每次规则命中的明细流水（含描述/状态/处理） |
| **灰名单管理** | `risk/riskGrayList/list` | **1821** | 按卡+规则累计的名单台账 |
| 黑名单管理 | `risk/riskBlackList/list` | 339（11-03） | 带审批状态（待审批/已审批/已停用）的拦截名单 |

**数据链路（据页面字段推断，标注推断）**：风险引擎命中规则 → 写「风险记录」一条明细 → 按 (卡号+规则) 聚合累计到「灰名单」（发生次数 + 最后发生时间）→ 达阈值/人工审批后进「黑名单」拦截。
> ⚠️ 入灰是**系统自动**的（灰名单无新增按钮、有"风险发生次数"累计字段）；具体阈值触发逻辑在旧后端，本次只读页面无法看到代码，属**推断**，需业主/旧系统维护方确认。

## 2. 灰名单管理（核心，对标主体）

### 2.1 页面形态
- 面包屑：风险控制 / 灰名单管理；**只读台账**——工具栏仅「查询」「重置」，表格**无操作列**，详情 form 仅「关闭」按钮。
- 无进灰/移出/审批/导出/编辑/删除任何写操作。

### 2.2 查询条件
| 字段 | 控件 | 说明 |
|---|---|---|
| 逻辑卡号 | 文本框 `userId`，maxlength=16 | — |
| 风险规则编码 | 下拉 `riskRuleId` | 7 个选项（见 2.4） |
| 更新时间 | `startDate`~`endDate` 日期（yyyy-MM-dd） | 按日期范围 |

### 2.3 表格列（7 列，jqGrid colModel 原文）
| 列头 | 字段名 | DB 列 | 样例 |
|---|---|---|---|
| 逻辑卡号 | userId | a.user_id | 0418061109611480 |
| 风险规则 | riskRuleId | a.risk_rule_id | 扣款失败 / 最大允许进入黑名单次数 |
| 风险发生次数 | riskRuleIdTimes | a.risk_rule_id_times | 0 / 1 / 17 |
| 风险发生最后时间 | riskOccursLastDate | a.risk_occurs_last_date | 2026-11-16 11:22:42 |

- 详情 form 只读字段：userId / riskRuleId / riskRuleIdTimes / managerId / hanleDesc / operatingDate。

## 3. 关联页面字段（用于判断新系统是否需补页）

**风险规则管理**（8 条，可新增/编辑/删除）：规则ID / 风险规则名称 / 风险等级 / 风险规则最大值 / 管理编码 / 更新时间 / 入库时间。
**风险组管理**（可增删改）：风险组名称 / 风险组描述 / 管理编码 / 入库时间。
**风险记录管理**（5709 条，只读）：逻辑卡号 / 用户订单 / 风险规则编码 / 名称 / 描述 / 风险等级 / 风险发生最后时间 / 风险状态(0…) / 风险处理时间 / 风险处理描述 / 处理人编码 / 设备ID / 最近修改时间 / 入库时间。
**黑名单管理**（20:14 实扫，3 条）：逻辑卡号 / 审批状态(0 待审批·1 已审批·2 已停用) / 管理编码 / 更新时间 + 操作列（编辑/删除注释掉）。详情页有"加入黑名单 / 移除 / 保存 / 关闭"四个按钮，JS 调 `/risk/riskBlackList/updateStatus` 接口（返回 0 成功/1 失败/2 移除失败/3 已达拉黑上限永久禁用/99 已存在），详情下方嵌入**黑名单操作记录**子表（`riskBlackListOptHist/listData`，按 userId 查询）。

## 4. 关键结论（对标输入）

1. **灰名单 ≠ 运维观察名单**：旧灰名单是风控规则命中自动累积的只读台账，新系统的 `GRAYLIST`（运维手工进灰/移出）语义错位——这是本次对标要纠正的核心。
2. **数据模型主键不同**：旧 = (卡号, 规则名) 复合；新 `GRAYLIST` = CARD_ID 唯一。不能直接灌 1821 行。
3. **新系统已有可复用的上游**：`TBL_RISK_RULE` / `TBL_RISK_GROUP` / `TBL_RISK_CONTROL_LOG`（para-server，`/page/risk/control-logs`），前端 `views/para/risk/**` 三页已在——**风险规则/组/记录已对齐**，缺的只是灰名单台账本体。
4. **入灰机制是推断**：自动触发规则/阈值未知；新系统若要"实时自动入灰"需确认旧引擎逻辑，否则只能先做"台账展示 + 存量导入"。
5. **旧黑名单机制**：详情页有"加入黑名单 / 移除"按钮，调用 `/riskBlackList/updateStatus`（传 `rStatus=1` 加入 / `rStatus=2` 移除），返回码含"已达拉黑上限/永久禁用"业务语义；状态机为 0 待审批→1 已审批 / 2 已停用。新系统 `BLACKLIST` 表已有两阶段解除机制，但缺少"加入/移除"的操作动作页与操作记录流水页。
