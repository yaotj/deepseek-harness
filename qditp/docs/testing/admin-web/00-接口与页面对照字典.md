## 二、响应结构（断言基础）

- **业务模块 `/page/**`**：`model/src/main/java/com/chinasofti/huateng/common/response/ResultVO.java:8~23` —— 字段是 `code` / `msg` / `data`，成功为 `code="200"` / `msg="SUCCESS"`，参数非法 `400`「非法参数」，内部异常 `500`「内部异常」。**注意不是 `retCode`**（`retCode` 属对外 IF 接口族）。
- **web-admin**：RuoYi 风格。列表接口返 `{"total":N,"rows":[...],"code":200,"msg":"查询成功"}`，写操作返 `{"code":200,"msg":"操作成功"}`。
- **失败形态有两种，判断时别只看一种**：①业务层显式 `ResultMapper.error/illegalParams` → `code=500/400` + 可读 msg；②SQL 在运行时被 Oracle / Druid 拒掉 → 被公共 web 组件的全局异常处理器包成 **HTTP 200 + 一个 UUID 形态的错误码**，前台只显示「查询失败」（`AGENTS.md` §5.1 / §8 记的三类陷阱都是这个形态）。**出现第二种 MUST 去服务端日志取原文，NEVER 按上次结论套用。**
- **2026-09-22 实测补两种成因**（`AGENTS.md` §8 现列 5 种）：**第 6 种 = 缺必填 `@RequestParam`**（日志原文 `Required request parameter 'cardId' for method parameter type String is not present`）；**第 7 种 = POST 空 body**。两者都不是「端点不存在」，见 `06` B12。
- **2026-09-22 实测的参数契约**：`queryType` 只认大写下划线常量 **`THIRD_USER_ID` / `MSISDN` / `CARD_ID`**（account 与 alipay-account 两侧同），送 `cardId` 返 `code=400 不支持的查询类型`；`/page/user/itp/pay-channels` 是 **`thirdUserId` + `cardId` + `cardType` 三参必填**。
- **2026-09-22 实测第三种失败形态**：**筛选条件不足** → `code=400` + 明确中文文案（`/page/gate-txn-pay`、`/page/qrcode-txn-detail`、`/page/face-pay/orders`、`/page/user/itp/search` 四处），属业务前置校验、没走到 SQL，**不要与上面第二种混判**。

## 三、取 JWT（web-admin 侧接口必须）

```bash
# 1) 拿验证码开关 / 验证码（若 captchaEnabled=true，登录需带 uuid + code）
curl -s 'http://172.20.211.23:30028/captchaImage'

# 2) 登录取 token（账号口令向环境负责人索取，NEVER 写进文档）
TOKEN=$(curl -s -X POST 'http://172.20.211.23:30028/login' \
  -H 'Content-Type: application/json' \
  -d '{"username":"<账号>","password":"<口令>","code":"<验证码>","uuid":"<captcha uuid>"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

# 3) 之后所有 web-admin 接口都带
curl -s 'http://172.20.211.23:30028/getInfo' -H "Authorization: Bearer $TOKEN"
```

入口代码：`web-server/web-admin/src/main/java/com/chinasofti/huateng/web/controller/system/SysLoginController.java:56`（`POST /login`）。permitAll 白名单：`web-server/web-framework/src/main/java/com/chinasofti/huateng/framework/config/SecurityConfig.java:113~118`。

业务模块 `/page/**` **不需要任何头**（见 `INDEX.md` §鉴权说明与 `06` A8）。

## 七、日志通道

- 看日志 **MUST 走 `scripts/klog.sh <服务名> [关键字] [行数]`**，NEVER 用本机 `kubectl logs`（`AGENTS.md` §8）。
- 三类只在运行时炸、且被包成 HTTP 200 的错误，关键字如下（这三条正是综管台查询页 100% 报错的常见成因）：
  - `ORA-00904` —— 列 / 别名不存在。若报的表别名是**子查询自己的别名**，就是「子查询驼峰别名、外层却引物理列名」那条（`AGENTS.md` §5.1，`daily-ticket-server` 1.0.35 修过 Test_036 那个页面）。
  - `sql injection violation ... comment not allow` —— SQL 正文里写了 `--` 或 `/* */` 注释。
  - `sql injection violation ... select alway true condition not allow` —— `where 1 = 1` + 全部谓词都是可选 `<if>`，**只在「筛选条件全空」那一支踩**（`account-server` 2.0.73 修过 Test_032）。
- `No static resource` —— 路径没有 handler（404 被伪装成 200）。巡检 **MUST 逐 Pod grep 容器内 `/home/javaapp/app/logs/*/*.log`**，klog 只看尾部窗口且 Pod 重启即丢（`AGENTS.md` §8）。
- `%X{traceId}` 只有 8 个模块有值（名单见 `AGENTS.md` §2.2.1）。本目录涉及的模块里 **para / account / alipay-account / ticket / key / blacklist / web-admin 那一列是空的**，按 traceId 搜 0 条不代表没请求。
