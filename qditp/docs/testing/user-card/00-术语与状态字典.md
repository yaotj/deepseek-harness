# 用户卡管理 · 术语与状态字典

来源：仓库代码实测（2026-09-07）。本页只记录代码中确实存在的字面量，未在代码中出现的含义标 `⚠️ 待验证`。

## 乘车码状态 `QRCODE_STATUS.CODE_STATUS`

枚举定义：`ticket-server/src/main/java/com/chinasofti/huateng/ticket/enums/QRCodeStatusEnum.java:9`

- `02` 结束行程
- `03` 初始化（开卡后的默认值）
- `04` 已进站
- `05` 已出站
- `06` 超时出站
- `08` 20 分钟内免费更新
- `09` 20 分钟内付费更新
- `10` 入站码更新
- `80` APP 自助补出站
- `81` APP 自助补进站

默认值来源：`ticket.default-code-status=03`（`ticket-server/src/main/resources/application.properties:14`），读取点 `TicketRideStatusServiceImpl.java:47`。

> ⚠️ 矛盾：`GateTicketHandler.java:53` 同名配置的兜底默认值写成 `01`，与 `TicketRideStatusServiceImpl` / `CardDataHandler` 的 `03` 不一致。当前被 `application.properties` 覆盖，测试环境若漏配该项两处行为会分叉。

## 开户记录有效标志 `USER_ITP_REG_INFO.DEL_YN`

`DEL_YN = 1` 表示**有效**（反直觉），`DEL_YN = 0` 表示**已注销**。
写入点：开户 `AccountApplicationServiceImpl.java:1351` / `:1463`（`setDelYn(1)`）；销户 `updateCancelByThirdUserId`（`:884` 调用，置 `0` 并写 `UN_REG_TMS`）。业务判断写作 `getDelYn() != 1` 即无效。

核对数据库时 **不要**按「1=已删除」理解。已销户且已归档的用户在该表**没有行**（归档时物理删除）。

## 操作日志类型 `USER_ITP_REG_LOG.OPER_TYPE`

常量定义 `AccountApplicationServiceImpl.java:82-91`：

- `0` — 开户
- `1` — 删除支付通道（写入点 `:664`；⚠️ 只在解绑的是默认通道时才写，见 `05` 的 B8）
- `2` — 销户（IF8A-42，写入点 `:892`，每张有效票卡一条）
- `3` — 销户归档（写入点 `:749`，与物理删除同一事务）

同一次操作的多行共用一个 `OPER_DATE_TIME`，可据此聚合出「这批属于同一次动作」。

## 同行码标识 `USER_ITP_REG_INFO.COMPANION_FLAG`

`VARCHAR2(1)`，取值 `Y`=同行票、`C`=第三方票，空=主码。
建表脚本：`account-server/src/main/resources/sql/account-server-companion-flag-migration.sql:2`

## 电子员工卡状态 `cardStatus`

代码只约束取值范围为 `1|2|3|4`（`EmployeeCardServiceImpl.java:405`），并有两条前置约束：

- 激活（`actionFlag=1`）要求当前 `cardStatus == 3`，否则返回 `2002 电子卡当前状态不允许激活操作`（`:208`）
- 禁用（`actionFlag=0`）要求当前 `cardStatus == 1`，否则返回 `2002 电子卡当前状态不允许禁用操作`（`:211`）

> ⚠️ 待验证：`1/2/3/4` 各自的业务名称（正常 / 停用 / 待激活 / 已注销？）代码与注释中均无定义，需向 ACC 侧确认后补齐。据激活前置可推断 `3` 为「待激活」、`1` 为「正常」，但**未在代码中得到确认**。

## 黑名单命中标记

`inBlack = "1"` 命中、`"0"` 未命中；两种情况 `retCode` 均为 `0000`（`BlacklistServiceImpl.java:98`）。
错误码枚举仅 4 个值：`0000` / `9999` / `9001` / `8001`（`BlacklistErrorCodeEnum.java:7`）。
