### A1a 销户不校验「进行中行程」 —— ✅ 2026-09-11 用户裁决：不加该校验，条目关闭

裁决（用户原话「确认销户不校验进行中行程」）：**销户不做进行中行程校验，保持现状**。因此本条由「需求确认项」转为**已确认的设计决定**，Test_004 不再算阻塞。详见 `docs/domain/decisions.md` ADR-D20。

## B. 安全与实现风险（建议开发确认，非测试阻塞）

### B1 `GET /updatePhone` 无验签、无二次验证

`RequestApplicationController.java:105` 是 `GET` + `@RequestParam`；该类注入了 `AccountRequestVerifier`（:37）但本方法**未调用**。
结合 A4（无验证码），任何网络可达方只要知道 `thirdUserId` 即可改绑手机号。对照 `AGENTS.md` §5.2「新增状态变更型接口 MUST 有鉴权与归属校验」。
建议：由开发按现有验签实现（`AccountRequestVerifier`）补齐，不要自造签名。

### B2 `companionFlag=Y|C` 整段跳过重复开户查重

`AccountApplicationServiceImpl.java:107` + `isMultiCardCompanionFlag`（:900）。重复提交是否会开出多张同行卡需实测（见 [[02-同行码]] Test_005 补充观察点）。

### B3 员工卡状态机可能不闭环

停用要求 `cardStatus==1`、启用要求 `cardStatus==3`（`EmployeeCardServiceImpl.java:208`、:211），但停用后写入的目标值未确认。若停用后不落到 `3`，启用会被拒。见 [[04-电子员工卡]] Test_012。

### B4 乘车码默认状态两处不一致

`GateTicketHandler.java:53` 兜底默认 `01`，`TicketRideStatusServiceImpl.java:47` 兜底默认 `03`。当前被 `application.properties:14` 的 `03` 覆盖，配置缺失时行为分叉。

### B5 换绑路由全异常吞成 `false`

`PhoneChangeAppServiceImpl.java:55` 整段 `catch Exception → return false`，APP 侧只能拿到 `9999`，无法区分「用户不存在」「下游超时」「参数错误」。排查线上问题需依赖服务端日志。

### B6 `paySignClient.updatePaySignDisplayAccount` 失败只 warn

`AccountApplicationServiceImpl.java:1050`。ITP 手机号已改、签约展示账号仍是旧号，无补偿任务收敛该不一致。

### B7 IF8A-42 销户无验签、无归属校验

`/app/cancelAccount`（`AppAccountController.java:112`）在 `fep-app-server` 不验签、`sign` 原样透传；account-server 侧 `userCancel` 只校验 `thirdUserId` 非空（`AccountApplicationServiceImpl.java:774`）。
规格要求上送 `phone`，但 **`USER_ITP_REG_INFO` 无手机号列，无法据此做归属校验**，`phone` 现仅登记在日志（已做前 3 后 4 掩码）。
后果：任何网络可达方只要知道 `thirdUserId` 即可注销他人账户，且归档会**物理删除** `USER_ITP_REG_INFO` 记录。对照 `AGENTS.md` §5.2「新增状态变更型接口 MUST 有鉴权与归属校验」。
与 B1 同类，建议一并按现有验签实现补齐。

### B8 `OPER_TYPE=1`（删除支付通道）只记默认通道

`requestRemovePayChannel` 仅在解绑的是 `USER_ITP_REG_INFO.CHANNEL` 记录的默认通道时才写 `OPER_TYPE=1`，因此 `USER_ITP_REG_LOG` **无法完整追溯每个通道的解绑时间**（2026-09-09 实测 `00522947` 的渠道 04 在该表无痕迹，只有渠道 03 有）。
已向用户说明属既有设计、非缺陷。待用户决定是否改成「每次解绑都写日志」。

### B9 归档依赖物理删除，销户后无法回溯用户信息

归档成功即 `deleteCanceledByThirdUserId`（`AccountApplicationServiceImpl.java:752`）物理删除 `USER_ITP_REG_INFO` 行，历史只留在 `USER_ITP_REG_LOG`（`OPER_TYPE=2` / `3`）。
连带影响：`DEL_THIRD_USER_ID` 列**仍无写值调用点**；销户后按 `thirdUserId` 查开户信息一律返 `8004`。
待确认：是否需要保留软删除行以支持事后审计 / 重新开户判重。

### B10 开卡：卡池预占已确认，本地插入失败无补偿（2026-09-09 追加）

现状：`account-server` 开卡时先向 `card-pool-server` 预占卡号（`/internal/card-pools/reservations`，`expireTime` 10 分钟）→ 再 `/confirm` → 之后才写本地 `USER_ITP_REG_INFO`。
风险：`/confirm` 成功后本地插入失败，卡池那条已置 `STATUS=ASSIGNED` 且 `EXPIRE_TIME=null`（不再被回收），本地却无该用户记录——**卡号永久泄漏**，无对账也无补偿任务。
判据见 `01` Test_001b。待确认：是否补「已确认但无归属」的巡检 / 释放接口。

### B11 乘车码先建、本地库后落，失败留孤儿档（2026-09-09 追加）

现状：`registerRideStatus` 用 `MERGE INTO` 写 `QRCODE_STATUS`（幂等、不会重复插），但发生在本地 `USER_ITP_REG_INFO` 插入之前。
风险：本地插入失败时 `QRCODE_STATUS` 留下 `CODE_STATUS=03` 的孤儿档，无清理机制。
判据见 `01` Test_001c。

### B12 `APP_PAY_SIGN_INFO.CARD_ID` / `CARD_TYPE` 签约后为 NULL（2026-09-09 实测）

实测：`00522949` 完成支付宝签约 + 通道绑定后，`APP_PAY_SIGN_INFO` 该行 `SIGN_STATUS=SIGNED`，但 `CARD_ID` 与 `CARD_TYPE` 均为 **NULL**。
连带影响：任何按卡维度查签约 / 解约的逻辑取不到值；已知 `Test_002d` 的「解约回调 `cardType` 为 null 兜底」正是同一根因的下游表现。
待确认：签约是账户维度（字段冗余、应删）还是卡维度（漏回写、应补）。

### B13 被放弃的签约请求悬挂无清理（2026-09-09 实测）

实测：`00522949` 除成功的 `APP_PAY_SIGN_REQUEST` ID 989（`NOTIFY_STATUS=SUCCESS`）外，还有 987 / 988 未走到终态，其中 `requestSignSeq=0052294901523912` 属重复发起后被放弃的请求。
风险：重复点击签约会不断堆积悬挂请求行，无超时关单也无清理任务，影响后续按 `thirdUserId` 查「最新签约请求」的判定。
待确认：是否需要给 `APP_PAY_SIGN_REQUEST` 加超时置终态的补偿。

### B14 码体 `issueChannelCode` 被静默截断（2026-09-09 实测，**确认为缺陷，已定位根因并给出修复**）

`IndustryCardDataServiceImpl.buildUnsignedIndustryData` 用 `normalizeHex(issueChannelCode, 2, "01")` 填发行渠道位，而 `normalizeHex` 在**超长时取右侧 2 位**（`substring(len-length)`），**不告警、不报错**。
实测：account `queryUserInfo` 返回 `cardIssueCode=5412`（4 字符），码体发行渠道位落成 **`12`** —— 既不是 `5412`，也不是兜底 `01`。

**根因链（已逐环节核实）**：APP 开户上送的是**发卡机构编码**（4 位） → `AccountApplicationServiceImpl.validateRequest` 只校验非空 → 原值写入 `USER_ITP_REG_INFO.CARD_ISSUE_CODE`（`VARCHAR2(64 CHAR)`，宽度不设防） → `queryUserInfo` 原样返回 → industry-data 按 2 位截断落码体。
两个域被混用了：`IssueChannelCodeEnum` 只有 `01`(正常渠道) / `07`(支付宝) **两个合法发行渠道值**；而发卡机构编码字典是 `0004` 海上巴士 / `0007` 支付宝出行 / `0008` 成都地铁 / `0020` 青岛地铁(早期) / `5412` 青岛地铁 / `5413` 畅行U惠小程序（用户 2026-09-09 提供）。**只有 `0007`→`07` 恰好正确，其余 5 个全错。**

**生产影响（已量化）**：`QRCODE_TXN_DETAIL.ISSUE_CHANNEL_CODE` 分布 `01`×80 / `12`×76 / `07`×50 / `08`×6 / null×1，即 **82/213 = 38% 落了非法渠道值**。`12` 最早出现在 **2026-08-07**，提示当日引入回归（该模块 git 历史只有 3 条提交、message 分别是 `1` / `commit` / `current file`，无法据此定位改动）。对照组：`ALIPAY_USER_INFO.CARD_ISSUE_CODE` 4 行全为 `0007`，说明「4 位归一化值」本就是既有正确口径。
**尚未核实**：那 76 笔 `12` 的交易是否真的在闸机被拒。

**修复设计（用户 2026-09-09 决定，已实现待部署）**：
- `CARD_ISSUE_CODE` 收窄为**发行渠道编码**，只落 `0001` / `0007`（选 4 位而非 2 位，为与 `ALIPAY_USER_INFO` 既有口径一致，且不必改动 `normalizeHex` 的截断行为）。
- 新增列 `USER_ITP_REG_INFO.ISSUE_ORG_CODE VARCHAR2(16 CHAR)` 保留 APP 上送的 4 位机构码原值，仅作留痕与统计，**不参与码体拼装**。
- 新增 `model/.../enums/CardIssueOrgEnum`：机构码字典 + `toIssueChannelCode4()` 映射（未知机构码 → `0001`，并在 account 侧打 ERROR 暴露字典缺口，但**不拒绝开户**——用可用性故障换数据问题不值当）。
- `0008` 成都地铁那 11 行（注册于 2026-08-12~13）**一并归一为 `0001`**。
- `QRCODE_TXN_DETAIL` 已落的 82 条 `12` / `08` **不改**：那是历史交易的客观记录，改了就丢掉「当时确实下发过错误码体」的证据，对账时反而说不清。受影响区间 **2026-08-07 ~ 修复日**，仅在此处记明。
- `warnIfTruncated` 收口为「截断后**不在** `{01,07}` 才告警」——否则修复后每次生码都刷一条 WARN（`0001`/`0007` 也是 4 字符），真正的异常会被淹掉。

**变更清单**：`model/.../enums/CardIssueOrgEnum.java`（新建）、`UserItpRegInfo.java` + `UserItpRegInfoMapper.xml`（新字段）、`AccountApplicationServiceImpl`（归一化 + 原值留痕）、`IndustryCardDataServiceImpl`（WARN 条件收口）、`account-server-schema.sql`（加列 + 两处注释）、`scripts/20260909_issue_org_code_migration.sql`（备份 + DDL + 存量迁移 + 还原 SQL）。

### B15 码体 `handleDate` 位在无交易时落「当前时间」（2026-09-09 实测，**机制系设计，语义待确认**）

⚠️ **本条 2026-09-09 二次核对后修正**：初版写「`"00000000000000"` 非空字符串，走不到兜底」——**该描述错误，已作废**。实际 `toFourByteHexByBizTime`（`:153-165`）显式判 `trimmed.length() != 14 || isAllZeros(trimmed)`，同文件 `firstNonBlank:204-211` 也排除全 0。即**兜底分支确实被走到了，只是兜底值本身就是 `LocalDateTime.now()`**。

因此这不是「判空写漏」，而是一个明确的设计选择：**「无上次交易」→ 用当前时间填该位**。
实测：`handleDate=0x3234588A`、`timeStamp=0x323490CA`，差值恒 `0x3840`（14400s = `industry.timestamp-expire-hours=4`），确认 `handleDate` 基准就是 now。
剩余问题只有语义一条：闸机若把该位读作「上次交易时间」，未过闸的新卡会被读成「刚刚交易过」。若闸机只用它做码体防篡改填充，则当前实现无害。

**2026-09-09 19:37 升级为「已确认有实际影响」**：闸机确实按「上次交易时间」读该位并原样上报。
证据：19:37:47 首次进站，AGM 上报 `lastHandleDateTime=20260909192654`、`lastHandleStationCode=FFFF`、`tikcetTransSeq=0`、`lastTicketStatus=03`。**`19:26:54` 正是那一轮拉码的时刻**，而该卡在此之前从未过闸（`QRCODE_TXN_DETAIL` 当时 0 行）。所以闸机读到的「上次交易时间」= 我方填的生码时刻 `now()`。
后果（已落库、可复现）：`QRCODE_TXN_DETAIL` 首程那一行的 `LAST_HANDLE_DATE_TIME=20260909192654` 指向一个**不存在的交易**。这一列在首程记录上不可用于对账，也不能用来判断「上次出站时间」。
仍未确认：甲方码体规格对该位的定义。**改动前仍需规格** —— 填全 0 可能触发闸机「非法时间」校验，这条风险没变。判据见 Test_001k。
待确认：该位在甲方码体规格里的定义与闸机用法。判据见 Test_001k。**不建议在拿到规格前改动**——改成全 0 同样可能触发闸机的「非法时间」校验。

### B16 离线码 `txnSeq` 用「库值 +1」且不回写（2026-09-09 实测，**确认为设计正确，非缺陷**）

⚠️ **本条 2026-09-09 二次核对后由「缺陷候选」降级为「设计说明」**：初版推测「防重放防不住」，读完 `IndustryDataServiceImpl:184-212` 后该推测不成立。

真实分支逻辑：
- **已进站**（`isInStation`，`CODE_STATUS=04`）→ 只出 `exitData`，用**库中原 `txnSeq`**（本次行程已占用该序号）
- **未进站** → `nextTxnSeq(txnSeq)`（`:342-350`，`BigInteger + 1`），`entryData` 与 `exitData` **共用同一个 seq**（同一趟行程的进出两码）

「不回写」是**必要的**：`QRCODE_STATUS.TXN_SEQ` 只应由真实过闸交易推进（`GateTicketHandler.buildNextStatus`）。若拉码就回写，用户每点开一次二维码都会白耗一个序号，与闸机上报的序号错位。
因此「5 次拉码 `transSeq` 恒为 `00000001`」是**预期行为**——期间没有任何过闸交易，库中 `TXN_SEQ` 就该停在 `0`。
唯一残留待确认：闸机侧是否用 `transSeq` 做防重放。若做，则「同序号多码」是规格层面的取舍（离线码本就要预生成），需甲方确认容忍度；若不做，本条完全无需处理。判据见 Test_001j。

### B21 IF1A-01 扣费链路的 `discountFee` / `discountInfo` 是死链（2026-09-09 定位，**已收口日志，字段本身不动**）

⚠️ **本条修正了同日一次误判**：我先前说「`GateTransactionHandler` 漏了 `payRequest.setDiscountFee(...)`，补上即可」——**该结论错误**。补 setter 是无意义的。

真实情况（三层都已核实）：
- `GateTxnPayReqDTO`（`model/pay/`）**有** `discountFee` / `discountInfo` 字段与 setter
- `gate-txn-pay-server` **确实消费入参**：`GateTxnPayServiceImpl:451-452` `payRequest.setDiscountFee(request.getDiscountFee())` 转发给 pay-sign
- 但 **ticket-server 的 IF1A-01 响应从不给这两个字段赋值**。全仓 grep `setDiscountFee|setDiscountInfo` 在 ticket-server 只有 3 处命中，全在**查询路径**（`TransQueryHandler:400-401`、`TransRecordAssembler:43-44`、`TicketRideStatusServiceImpl:232`），都是从 `PAY_TXN_DETAIL` **反读**后填 APP 查询响应

结论：折扣数据在本项目里的流向是**反向**的 —— gate-txn-pay 自算 → 落 `GATE_TXN_PAY` → pay-sign 落 `PAY_TXN_DETAIL` → 查询时 ticket-server 读出来给 APP。**扣费方向上这两个字段是整条死链**，`fep-dev` 补 setter 只会永远传 null。

已做（2026-09-09）：删掉 `GateTransactionHandler` 透传日志里那两个恒 null 的字段，并就地注释说明流向，避免后人再次误读成「漏透传」。**字段本身、DTO、gate-txn-pay 的转发逻辑一律不动** —— 那是给未来上游真的能给出折扣时预留的入口。
- `account` 的 `queryUserInfo` 应答**明文返回 `msisdn`**，且被 fep-app 与 account 双方日志完整打印（与 B7 处 `UserCancelReqDTO` 已做掩码的口径不一致）。
