# 04 · 电子员工卡（Test_010~013）

对应原手册「四、电子员工卡模块」。链路：ACLC（ACC 侧）→ fep-acc-server → account-server；APP 侧走 fep-app-server。

## 链路事实

**account-server**（`controller/ci/employee/EmployeeCardController.java`，类上无 `@RequestMapping`）

- `POST /employeeCard/notify`（:29）→ `notifyEmployeeCardStatus` 员工码状态通知（ACC 推送）
- `POST /employeeCard/query`（:37）→ `queryEmployeeCard` 资料查询
- `POST /employeeCard/activate`（:45）→ `activateEmployeeCard` 激活 / 禁用（`actionFlag` 1=激活、0=禁用）
- `POST /employeeCard/updateNotify`（:53）→ `updateEmployeeInfo` 员工信息变更通知

接口定义 `EmployeeCardService.java:15-21`，实现 `EmployeeCardServiceImpl.java`，落库拆到 `EmployeeCardPersistenceServiceImpl.java`。

**fep-acc-server 转发**（`controller/EmployeeCardController.java`）

- `POST /employee_card/notify`（`multipart/form-data`，:37）→ `accountClient.notifyEmployeeCardStatus`（:41）
- `POST /employee_card/update_notify`（`multipart/form-data`，:47）→ `accountClient.updateEmployeeInfo`（:51）

注意两侧路径风格不同：ACC 面向 `employee_card/*`（下划线），ITP 内部 `employeeCard/*`（驼峰）。测试时按调用方向选对路径。

**状态通知是批量接口**，返回三态（`EmployeeCardServiceImpl.java:124-133`）：

- 全成功 `0000 员工码状态通知处理成功`
- 全失败 `9999 员工码状态通知处理失败`
- 部分失败 `0001 员工码状态通知部分处理失败`，明细在 `failList`

单条落库失败会写日志表 `USER_ACC_EMPLOYEE_CARD_LOG`（`eventType="STATUS"`，`insertLog` 在 `:449`）并计入 `failList`（`:151-156`）。

**校验与状态前置**

- 入参校验：`phone` 必填（`:403`）、`cardStatus` 必须为 `1|2|3|4`（`:405`）
- 激活要求当前 `cardStatus == 3`，否则 `2002 电子卡当前状态不允许激活操作`（`:208`）
- 禁用要求当前 `cardStatus == 1`，否则 `2002 电子卡当前状态不允许禁用操作`（`:211`）
- 卡不存在：`8004 员工码信息不存在`（`:206`）
- ⚠️ `1/2/3/4` 的业务名称代码内无定义，见 [[00-术语与状态字典]]

## 用例

### Test_010 电子员工卡开卡

ITP 侧接口已存在（`/employee_card/notify` + `/employeeCard/activate`），原手册「暂不支持」的备注**已过期**，需按当前代码重测。
步骤：ACLC 推送开卡通知 → APP 侧激活。
预期（可验证）：
- `notify` 返回 `0000`，员工卡记录落库，`cardStatus=3`（待激活）
- `activate`（`actionFlag=1`）返回成功，`cardStatus` 变为 `1`
- `USER_ACC_EMPLOYEE_CARD_LOG` 有对应事件流水
- APP 可展员工码并过闸
- ⚠️ 「享有对应乘车权限和优惠政策」——票价 / 优惠归属 `para-server`，本页未验证员工卡是否接入优惠计算，需单独确认

结果：☐ 通过 ☐ 失败 ☐ 阻塞

### Test_011 电子员工卡销户

⚠️ **无独立销户接口**。销户只能通过 `POST /employeeCard/notify` 推送目标 `cardStatus` 实现，具体哪个值代表「已注销」未在代码中定义（见 [[00-术语与状态字典]]）。
可验证：`notify` 推送销户状态后，`queryEmployeeCard` 返回该状态；日志表有流水（「操作记录可追溯」成立）。
不可直接验证：「无法再生成有效二维码」——需确认展码链路是否读取 `cardStatus` 做拦截，本页未验证。

结果：☐ 阻塞（原因：状态取值待确认）

### Test_012 停用 / 启用 / 信息同步

- 停用：`POST /employeeCard/activate`，`actionFlag=0`，要求当前 `cardStatus==1`
- 启用：`actionFlag=1`，要求当前 `cardStatus==3`
- ⚠️ **状态机不闭环**：停用会把状态从 `1` 改成什么值未确认；若停用后不是 `3`，则「启用」会被 `:208` 的前置校验拒绝，出现「停得下、启不动」。**这是本页优先级最高的验证点**，请务必按「停用 → 立即启用」顺序连测并记录两次返回码与库内状态值。
- 信息同步：`POST /employee_card/update_notify` → `updateEmployeeInfo`
- 「可在 ITP 查询页面查看」：用 `POST /employeeCard/query` 或后台页面核对

预期（可验证）：三个动作各自返回 `0000`，`USER_ACC_EMPLOYEE_CARD_LOG` 流水完整，`query` 返回值与 ACLC 侧一致。
⚠️ 「停用成功，员工卡无法乘车」同 Test_011，展码侧拦截未验证。

结果：☐ 通过 ☐ 失败 ☐ 阻塞

### Test_013 员工手机号变更后重新开卡

步骤（按原手册）：ACLC 改手机号 → 同步至 ITP → APP 解约 → 重新开卡。
可验证：
- `update_notify` 返回码与落库后的 `phone` 字段
- 解约走 [[01-二维码电子票]] 的 `requestTermination` / `requestRemovePayChannel` 链路
- 重新开卡后 `queryEmployeeCard` 可查到新手机号且可展码

⚠️ 注意与普通用户换绑手机（[[03-用户信息与状态]] `updatePhone`）是**两条独立链路**：员工卡走 ACC 通知，普通用户走 APP 自助，不要混测。`USER_ITP_REG_INFO.MSISDN` 与员工卡表的 `phone` 是不同字段，需分别核对。

结果：☐ 通过 ☐ 失败 ☐ 阻塞

## 矛盾/待验证

- `cardStatus` 1/2/3/4 语义缺定义 —— 阻塞 Test_011 / 012 的精确断言。
- 停用后的目标状态值未确认 —— 可能导致停用后无法启用。
- 展码 / 过闸链路是否读取员工卡状态做拦截 —— 未验证，影响 Test_011、012 的「无法乘车」预期。
- 原手册 Test_010 备注「预计 8 月 25 日完成调试」已过期，接口现已存在。
