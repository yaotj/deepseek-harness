实测拆解（在线 `0007FAC503FFFF3234588A323490CA0426090942000017000200000000120301` + 签名）：
`0007FAC5`（00522949→0x7FAC5）· `03` · `FFFF` · `3234588A` · `323490CA` · `0426090942000017` · `0002` · `00000000` · `12` · `03` · `01`

**三处与既有文档不一致的实测事实**：

- ⚠️ **`issueChannelCode` 被静默截断（缺陷）**：account 给的是 `5412`，但 `normalizeHex(issueChannelCode, 2, "01")`（`:96`）在超长时取**右侧 2 位**（`:185-187`），码体发行渠道位实际落 **`12`**。既不是 `5412` 也不是兜底 `01`，且截断不留任何日志（2026-09-09 已补 WARN）。见 [[05-阻塞项与缺陷候选]] B14。
- ℹ️ **`handleDate` 位在无交易时落「当前时间」（设计如此，语义待确认）**：`toFourByteHexByBizTime`（`:153-165`）显式判 `length != 14 || isAllZeros`，`firstNonBlank`（`:204-211`）也排除全 0 —— 兜底分支**确实被走到**，只是兜底值本身就是 `LocalDateTime.now()`。`timeStamp` = `handleDate` + 4h（`industry.timestamp-expire-hours=4`），实测 `0x323490CA - 0x3234588A = 0x3840 = 14400s`。见 B15。
- ⚠️ **ticket-server 实际服务端口是 9100**（istio decorator `ticket-server-bsyju-svc.itp.svc.cluster.local:9100`），仓库 `ticket-server/application.properties:1` 写的是 `server.port=9103` —— 说明**线上被 Deployment env 覆盖了**，`AGENTS.md` 与 `docs/business/ride-code.md` 记的 9103 只是仓库值。

**离线码 `txnSeq` 的两个分支（设计正确，勿当缺陷）**：`IndustryDataServiceImpl:184-212`
- 已进站（`CODE_STATUS=04`）→ 只出 `exitData`，用库中**原** `txnSeq`（本趟已占用该序号）
- 未进站 → `nextTxnSeq`（`:342-350`）后 `entryData` / `exitData` **共用同一 seq**（同一趟行程的进出两码）
- **不回写库**是必要的：`TXN_SEQ` 只应由真实过闸推进（`GateTicketHandler.buildNextStatus`），否则用户每点开一次码就白耗一个序号。见 B16。

**生码「零落库」验证 SQL**（拉码前后各跑一次，四个值必须完全一致）：

```sql
select CODE_STATUS, USE_COUNT, TXN_SEQ, UPDATE_TIME
  from QRCODE_STATUS where CARD_ID = :cardId;
```

2026-09-09 17:56 复核 `0426090942000017`：`CODE_STATUS=03 / USE_COUNT=0 / TXN_SEQ=0`，与 17:10:27 建档时一致 —— 7 次拉码**未产生任何写入**。

### Test_001m 冷启动首次拉码耗时（性能观察点）

**现象**：pod 重启后第一次拉码 **4850ms**，热态同一接口 36~67ms，相差约 100 倍。

拆解（2026-09-09 17:54:45~51 实测）：
- fep-app `Initializing Spring DispatcherServlet` 17:54:45.280 —— 懒初始化在**首个请求**上完成
- ticket-server pod 17:52:24 启动，`DispatcherServlet` 初始化 17:54:48.481
- 各段耗时：IF8A-73 1409ms · `queryUserInfo` 1349ms · `queryQrCodeStatus` 1395ms（其中 SQL 仅 17ms）· 第一次 `buildCardData` 1952ms · 第二次 `buildCardData` **24ms**
- 结论：慢的是**每条链路的首次连接 + servlet/连接池懒加载**，不是业务逻辑；同一请求内第二次 `buildCardData` 已降到 24ms

判据：重启任一链路服务后立即拉码，确认首次耗时可复现且第二次即恢复；若热态也持续 >1s 才属真实缺陷。
⚠️ 影响：APP 侧若拉码超时阈值 < 5s，部署窗口内首个用户会看到失败。建议确认 APP 超时配置与预热策略。

结果：☑ 已观察到（2026-09-09），**是否需要预热 / 调大超时待确认**

### Test_001n 日志 ERROR 级别 ≠ 业务失败（排查约定）

`MoreInterceptor.afterCompletion`（`resource/micro/web/.../MoreInterceptor.java:71-76`）：
```
boolean timeOut = time >= webconfig.getSlowRequestOfMillis();
if (timeOut || response.getStatus() > 300) { log.error(logs); } else { log.info(logs); }
```

因此 Test_001m 那次 4850ms 的请求在日志里是 **ERROR 级别，但 `retCode=0000`、`response.status=200`、码体正常返回**。
