# 02 · 同行码（Test_005~006）

对应原手册「二、同行码」。

## 定义

同一 APP 用户在主码之外再开一张可独立展码过闸的卡，ITP 侧通过 `USER_ITP_REG_INFO.COMPANION_FLAG` 区分。

## 链路事实

**没有独立的「开通同行码 / 关闭同行码」接口。** 同行码复用开户接口，靠入参 `companionFlag` 分流：

- 入参落库：`AccountApplicationServiceImpl.java:889`
- 分流作用点：重复开户查重仅在 `companionFlag` 不是 `Y`/`C` 时执行（`:107`），判定方法 `isMultiCardCompanionFlag`（`:900-902`，只认 `Y` 与 `C`，做了 `trim`）
- 即：`companionFlag=Y` 的作用是**跳过一人一卡限制**，允许同一 `thirdUserId` 再开一张卡
- 定位查询：`selectByThirdUserIdAndCardIssueCodeAndCompanionFlag`（`UserItpRegInfoMapper.java:34`，调用点 `AccountApplicationServiceImpl.java:424`）
- 回传：`queryUserInfo` 与 `queryCardTypeByCardId` 都会带出 `companionFlag`（`:572`、`:613`）
- 后台可见：`ItpUserPageController.java:59` → `ItpUserSearchView.companionFlag`
- 字段定义与取值见 [[00-术语与状态字典]]

**关闭同行码：ITP 后端无实现。** 与 [[01-二维码电子票]] 的注销同因——`UserItpRegInfoMapper` 没有任何置无效的 UPDATE 语句，无法把某张同行卡改成不可用。

## 用例

### Test_005 同行码-开卡

前置：主码已开通。
步骤：APP 添加同行码 → 拉码 → 展码进出站 → BOM 补站 / APP 自助补站。
预期（可验证）：
- `USER_ITP_REG_INFO` 新增一行，`THIRD_USER_ID` 与主码相同、`CARD_ID` 不同、`COMPANION_FLAG='Y'`、`DEL_YN=1`
- 该卡在 `QRCODE_STATUS` 有独立记录，初始 `03`
- 正常进出站与扣费（同 Test_001 的验证点）
- 自助补站后 `CODE_STATUS` 为 `80`（补出站）或 `81`（补进站）
- ⚠️ BOM 补站入口未在本仓库验证，执行时以实际 BOM 页面为准

补充观察点（值得单独确认）：`companionFlag=Y` 会**整段跳过**查重，因此重复提交同一次「添加同行码」请求理论上可开出多张卡。执行时请重复提交一次，记录是否产生重复卡——若产生，转 [[05-阻塞项与缺陷候选]]。

结果：☐ 通过 ☐ 失败 ☐ 阻塞

### Test_006 同行码-关闭

⚠️ **部分阻塞**。ITP 后端无关闭实现，本用例只能验证 APP 前端表现（列表不再展示、无法展码），**无法验证后端状态生效**。
可验证：关闭后再次调用 `queryUserInfo` / 后台用户页面，确认同行卡记录是否仍为 `DEL_YN=1`（按现状预期为「仍然有效」）。
若确认后端未失效，则「关闭立即生效」不成立——属功能缺失，转 [[05-阻塞项与缺陷候选]]。

结果：☐ 阻塞（原因：后端无关闭实现）

## 矛盾/待验证

- 原手册预期「关闭立即生效」与代码现状冲突（无关闭实现），⚠️ 矛盾未裁决，需产品确认关闭语义是「后端置无效」还是「仅前端隐藏」。
- `COMPANION_FLAG='C'`（第三方票）与同行票走同一条免查重分支，两者在测试数据上需要区分，避免互相污染。
