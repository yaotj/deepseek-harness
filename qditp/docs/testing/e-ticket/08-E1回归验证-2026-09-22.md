### 代码现状

`GateDailyTicketCoordinator.java:129`（当前仓库）：
```java
if (!TrxTypeCodeEnum.EXIT.getCode().equals(request.getTrxType())
        || !CardTypeCodeEnum.isDailyTicket(resolvedCardType)) {

```

`TrxTypeCodeEnum.EXIT.getCode()` = `"02"`（`TrxTypeCodeEnum.java:12`）。
`isExitTxn()` = `EXIT.code.equals(trxType) || EXIT_OVERTIME.code.equals(trxType)`（`:43-44`），即 `02` 或 `03` 都是出站。

**精确等值仍在（`:129` 只认 `02`）。** 本轮未打 `trxType=03` 的请求，原因：E1 修复后 `resolvedCardType` 首次正确（`0445`），`isDailyTicket` 首次返 true，`:129` 那个精确等值**才第一次成为真正的瓶颈** -- 上一轮 E1 未修时它根本轮不到生效。本轮 `02` 已证明整条链路从头到尾打通，`03` 的对照唯一能额外证明的就是「`:129` 是否放行 `03`」，答案从代码上已确定是否。

## 七之二、本轮踩到的取证陷阱（MCP 查询缓存）

**`mcp_database_qd` 的 `executeQuery` 有查询结果缓存，逐字重复同一条 SQL 会拿到缓存里的旧值。**

本轮实测：出站请求打完后，用与出站前**逐字相同**的那条 `SELECT ... FROM DAILY_TICKET_INSTANCE WHERE CARD_NUM='...'` 回查，连查两次都返回 `ACTIVATED` / `FIRST_USE_TIME=null` / `UPDATE_TIME=2026-09-20 16:40:00` -- 与 daily-ticket-server 日志里那条 `update ... set TICKET_STATUS='USED' ... fetchRowCount:1` **直接矛盾**。把 SQL 换个写法（改成按 `ID` 过滤 + 多取两列 + 时间格式带毫秒）后立刻返回真实值 `USED` / `2026-09-22 13:56:42.994`。

**判据与规避**：
- 「服务日志显示 UPDATE 影响 1 行，MCP 回查却是旧值」= 极可能是查询缓存，**NEVER 先怀疑事务回滚**。
- 写操作前后的两次回查 **MUST 用不同的 SQL 文本**（换列、换谓词、换格式化都行），或调 `clearCache`。
- 这个陷阱与 `AGENTS.md` §8 已记的六条 MCP 坑同族，但**成因完全不同**：那六条都是「语句本身报错被包装」，本条是「语句成功执行、返回的是过期数据」-- **静默、无任何报错**，也是本轮最容易得出错误结论的一处。
