## Test_001 二维码生成-正常生码（青岛地铁乘车码 + 同行码）

原表步骤：打开 APP 乘车码页面 → 检查二维码能否正常展示（①青岛地铁乘车码 ②同行码）。
原表结果：两种码都生码成功、可过闸、BOM 可识别。✅ 通过。

**分类：需人工**（APP 点按展码）。等价可 curl 入口：模板 T2（`IF8A-03` + `IF8D-03`）。

预期（可验证断言）：

1. `POST /ci/app/requestIndustryData` 返 `retCode=0000` 且 `cardData` 非空（`fep-app-server/.../controller/IndustryDataController.java:28`）。
2. `POST /ci/app/requestNoSignalData` 返 `retCode=0000` 且 **`entryData` + `exitData` 两个码都非空**（同文件 `:34`）——离线码是双码，在线码只有一个 `cardData`。
3. **生码零落库**：拉码前后 `QRCODE_STATUS` 的 `CODE_STATUS` / `USE_COUNT` / `TXN_SEQ` / `UPDATE_TIME` 四个值必须完全一致（判据与 SQL 见 `docs/testing/user-card/01-二维码电子票.md:119-126`，已于 2026-09-09 实测 7 次拉码无写入）。
4. ⚠️ **「同行码」在生码侧没有独立接口**：`fep-app-server` 的 `IndustryDataController` 只有上面两个端点；同行卡与主卡的区别落在**开户侧**（`TICKET_LIMIT` / `COMPANION_FLAG`，见 `AGENTS.md` §2.2.1），生码时两者走同一条 `requestIndustryData`、只是 `cardId` 不同。因此本条实际是「用同行卡的 cardId 再跑一次第 1~3 步」。→ `05` B1
5. ⚠️ **「BOM 可识别」在 ITP 侧无法直接验证**：ITP 能提供的查询入口是 `POST /ci/agm/queryCardStatus`（`ticket-server/.../controller/ci/agm/TicketAgmController.java:69`）与 `POST /ci/agm/requestQrCodeStatus`（`fep-dev-server/.../controller/FepAgmController.java:92`）。**BOM 客户端是否在调这两条，本仓库无从核实** → 写「未找到」，不当通过判据。

执行方式：

① curl：模板 T2 两条（在线 + 离线），`bizData` = `{"thirdUserId","cardId","cardType"}`。
② DB：
```sql
select CODE_STATUS, USE_COUNT, TXN_SEQ, UPDATE_TIME
  from QRCODE_STATUS where CARD_ID = :cardId;
```
拉码前后各跑一次、四值比对。
③ 日志：`ticket-server` 搜 `queryQrCodeStatus`（纯读、无写）；`industry-data-server` 搜 `buildCardData`。
**两个服务都没开 tracing**（`AGENTS.md` §2.2.1 那 8 个名单里没有它们），按 traceId 检索恒 0 条，MUST 按时间窗 + `cardId` 检索。

## Test_002 二维码生成-密钥同步

原表步骤：打开乘车码页面 → 看生码结果。原表结论「生码成功且可过闸 ⇒ 密钥同步成功」。✅ 通过。

**分类：可 curl 自动跑**。

预期（可验证断言）：

1. 生码成功本身**不是**密钥同步的直接证据。真正的密钥同步接口是 **IF1A-02 `POST /ci/agm/requestSynKeyList`**（`fep-dev-server/.../controller/FepAgmController.java:70`），归属 `key-server`（`AGENTS.md` §3.2）。因此本条 MUST 拆成两步验：
   - 直接打 IF1A-02，`retCode=0000` 且返回的密钥列表非空；
   - 再跑 Test_001 的生码 + Test_008 的进站，闸机侧校验通过。
2. ⚠️ **`fep-dev-server` 曾缺 `service.key.url` 键**，2026-09-14 已补齐（`AGENTS.md` §8 该条明确「NEVER 再列」）。若 IF1A-02 打不通，**MUST 先查 Deployment env 的实际值**，NEVER 先怀疑 key-server。
3. 生码链路**不经过 key-server**：三次 RPC 是 account → ticket → industry-data（`docs/testing/user-card/01-二维码电子票.md:93-100`）。所以「生码成功」只能证明码体签名服务可用，不能证明 AGM 侧密钥池已同步。→ `05` C1（手册推理链与代码链路不一致）

执行方式：

① curl：
```bash
curl -s -X POST 'http://172.20.211.23:<NodePort:fep-dev-server 待现查>/ci/agm/requestSynKeyList' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'charset=UTF-8' --data-urlencode 'format=JSON' \
  --data-urlencode 'signType=00' --data-urlencode 'sign=' \
  --data-urlencode 'timestamp=20260922120000' --data-urlencode 'deviceId=02450604' \
  --data-urlencode 'bizData={}'
```
⚠️ `bizData` 字段本页未核对，MUST 先读 `FepAgmController.java:70` 那个方法的入参 DTO。
② DB：本条**不产生业务落库**（`fep-dev-server` 无 DB，`AGENTS.md` §3.2）。密钥池表归 `key-server`，表名本页未核对 → 写「未找到」。
③ 日志：`fep-dev-server` 搜 `requestSynKeyList`；`key-server` 搜同名。

## Test_003 NFC 虚拟电子票生成-开卡

原表步骤：APP 选 NFC 乘车 → 验证手机 NFC 能力 → APP 向 ITP 申请开卡 → 写入手机。
原表结果：开卡成功、NFC 过闸成功、BOM 可更新。✅ 通过。

**分类：需人工**（真机 NFC 写卡）。ITP 侧可 curl 的只有开卡与 HCE 数据两段。

预期（可验证断言）：

1. 开卡走的是**同一条 IF8A-01**（`POST /ci/app/requestApplication`，`fep-app-server/.../controller/AppAccountController.java:44`）——**代码里没有「NFC 专用开卡接口」**。开卡数量由必填 `ticketLimit` 控制（`AGENTS.md` §2.2.1 首条）。
2. HCE（写卡数据）链路**不完整**：全仓只有 `requestCardDataAnalyse` / `requestUpdateCardData` / `notiUpdateHceData` 三个入口（`AGENTS.md` §2.2.2 「IF5A HCE 链路」条）。**「写入手机 NFC 模块」这一步在 ITP 侧没有可断言的落点** → 写「未找到」。
3. 因此本条真正可验证的只有：`USER_ITP_REG_INFO` 新增一行 `DEL_YN=1`、`QRCODE_STATUS` 新增一行 `CODE_STATUS=03`（依据 `docs/testing/user-card/01-二维码电子票.md:176-179` 的实测断言集）。
4. ⚠️ 「NFC 过闸」与「二维码过闸」在 IF1A-01 报文上**如何区分，本页未找到判据** —— `GateCodeStatusResolver` 只看 `trxType` / `excessFareType` / `adviceOpt` 三个字段（`ticket-server/.../gate/GateCodeStatusResolver.java:71`），没有介质字段分支。→ `05` B2（与 Test_029 / 030 的状态值疑问同源）

执行方式：

① curl：开卡用 `POST /ci/app/requestApplication`（报文骨架同模板 T2 的公共参数，`bizData` 字段集 MUST 看 `AppAccountController.java:44` → account-server `RequestApplicationController`）；过闸用模板 T1。
② DB：
```sql
select CARD_ID, ITP_CARD_TYPE, CARD_TYPE, DEL_YN, REG_TMS
  from USER_ITP_REG_INFO where THIRD_USER_ID = :thirdUserId;
select CODE_STATUS, USE_COUNT, TXN_SEQ from QRCODE_STATUS where CARD_ID = :cardId;
```
③ 日志：`account` 服务（Deployment 名是 `account`、不是 `account-server`，`AGENTS.md` §7）搜 `requestApplication`；`ticket-server` 搜 `registerRideStatus`。
