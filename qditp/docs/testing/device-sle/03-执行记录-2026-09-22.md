## D7 · 对照：不存在的端点（**方法论更正**）

**请求**
```
POST http://172.20.211.23:30009/ci/agm/deviceHeartbeatXX
```

**响应**
```json
{"retCode":"3e7299a4-a982-4b80-83f2-5ecf1f5621ea","retMsg":null,"data":null}
```
**`http=200`**

**结论（本轮最重要的一条）**：
- `fep-dev-server` 对「路径无 handler」返 **HTTP 200 + UUID `retCode`**，**不是 404**。成因是全局异常处理器兜底（`AGENTS.md` §8 记载的 UUID retCode 五种成因之一：路径无 handler）。
- 因此 **判 fep-dev 端点是否存在 MUST 看 `retCode` 是不是 UUID，NEVER 用 HTTP 404**。
- `01` / `02` 引用的「404 = 端点不存在、HTTP 200 + 业务码 = 存在」那条判据，**原始语境是 APP（第三方）侧的 `/app/receiveXxx` 出向通知端点**（`AGENTS.md` §2.2.2 §3.63 实测事实），**与 fep-dev 入向不是同一套**。已在 `02` 新增 **C12** 记录该区分。
- 连带：`retMsg=null` + 多一个 `data` 字段，是全局兜底响应体的形状特征 —— 可作为「这不是业务应答」的辅助判据。

## D11 · 直连下游对照 · ticket-server（**新观察点：字段裁剪**）

**请求**
```
POST http://172.20.211.23:30014/ci/app/queryQrCodeStatus
Content-Type: application/json
{"cardId":"0426090951000129"}
```

**响应**（原样，**9 个业务字段**）
```json
{"retCode":"0000","retMsg":"成功","thirdUserId":null,"cardId":"0426090951000129",
 "status":"05","gateInStation":"0622","gateInTime":"20260920180004",
 "lastTxnStation":"0245","lastTxnTime":"20260920180021","txnSeq":"4"}
```
`http=200`，耗时 **8ms**

**与 D8 的差分**：`fep-dev-server` 只把其中 **2 个**透传出去（`status` → `lastTicketStatus`、`lastTxnTime` → `lastHandleDateTime`）。被丢弃的是：

| ticket-server 返回 | 本次值 | fep-dev 是否透传 |
|---|---|---|
| `gateInStation` | `0622`（辛屯） | ❌ 丢弃 |
| `gateInTime` | `20260920180004` | ❌ 丢弃 |
| `lastTxnStation` | `0245`（合川路） | ❌ 丢弃 |
| `txnSeq` | `4` | ❌ 丢弃 |
| `thirdUserId` | `null` | ❌ 丢弃 |

**代码定位**：`fep-dev-server/.../qrcode/QrCodeStatusHandler.java:57`~`:62` —— 只 `set` 了 6 个字段（含 2 个回显）。

**结论**：这是**信息裁剪，不是缺陷判定**，但直接影响「闸机能否本地判断进出站次序」——闸机拿不到进站站点、进站时刻与交易流水号。已记入 `02` 的 **C11**，待与闸机侧确认它是否需要这几个字段。

**附带事实**：直连下游 8ms vs 经 fep-dev 冷态 1152ms ⇒ **1152ms 里绝大部分不是业务耗时**，而是接入层冷启动（`ticket-server` 的 `DispatcherServlet` 懒初始化 + RPC 首次建连）。这是 `02` 的 C6「冷热不可混用」的又一组证据。
