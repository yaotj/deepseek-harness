## C1 · 「ITP 校验后 AGM 再开闸」与代码现状不符（IF1A-01 是事后通知）

- **原表描述**：`ACLC_Device_Test_001` 步骤 2「AGM 发起检票请求」→ 3「ITP 校验」→ 4「AGM 开闸/拒绝」→ 5「AGM 发送结果给 ITP」，读起来是**两次交互 + ITP 在环内授权**。
- **代码现状**：`FepAgmController` 只有 4 个方法（`:46` / `:70` / `:92` / `:112`），检票相关**只有一个** `POST /ci/agm/notiVerifyResult`，方法名与 Javadoc 都是「闸机检票**通知**」（`:45`）。**未找到**任何「ITP 返回放行/拒绝、闸机据此开门」的同步授权接口。
- **可推断的真实形态**：闸机**先本地判定并开闸、再把结果通知 ITP**；IF1A-04 `requestQrCodeStatus` 是闸机在扫码时**自己去查状态**用的（见 C4），也不是授权接口。
- **影响**：`ACLC_Device_Test_001` 的步骤 3 与 4 无法在 ITP 侧验证；ITP 的 `retCode=0000` **只表示「通知我收到了」，不表示「该放行」**。
- **待澄清**：原表步骤描述是按甲方规格写的还是按理解写的？若甲方确实要求 ITP 在环内授权，那是**未落地需求**。

## C2 · P0：`trxType=03` 出站时多日计次票不扣次 + 金额被清零

- **代码定位**：`GateDailyTicketCoordinator.java:125` 用 `TrxTypeCodeEnum.EXIT.getCode()` **精确等值只认 `"02"`**；同枚举 `TrxTypeCodeEnum:43` 的 `isExitTxn()` 把 `02`/`03` **都当出站**。
- **后果**：送 `03` 时扣次逻辑整段 `return`（不扣次、不推进 `TICKET_STATUS`、不发 §3.63 通知），而扣费链路照常触发（`GateFarePaymentOrchestrator.shouldPay` 用的是 `isExitTxn`）、金额又已被 `GateCardTypeEnricher.java:158` 连同车费清零 ⇒ **两头落空，等于免费乘车一次**。
- **来源**：`AGENTS.md` §2.2.2「超时处理」P0 条；唯一入口文档 `docs/business/overtime-handling.md`。
- **影响**：`ACLC_Device_Test_001` 若用 `trxType=03` 造超时出站，**必然撞上**。
- **处置**：未修复。修它会连带推翻 §3.63「`times` 恒传 1」口径（宿主需从 `GateDailyTicketCoordinator` 迁到 daily-ticket 侧）。**同一条也记在** `docs/testing/app/0X-阻塞项与缺陷候选.md` A2。

## C6 · 「查询响应时间 < 200ms」当前无性能基线，属需另立压测口径的断言

- **原表**：`ACLC_Device_Test_002` 预期 3。
- **为什么单次 curl 不能验**（4 条，逐条都有依据）：
  1. **链路跨 2 个服务 + 1 次 DB 查询**：`curl → fep-dev-server → RPC(ProxyWebClient/WebClient) → ticket-server → Oracle`。单次耗时里混着网络、RPC、SQL 三段，无法归因。
  2. **冷启动差 2 个数量级**：`ticket-server` 的 `DispatcherServlet` 是懒初始化的，冷启动后首次拉码已实测 **4850ms**，同一接口热态 **36~67ms**（`docs/testing/user-card/INDEX.md:80`，该条明确写「两组数据不可混用」）。不定预热轮次，结果没有意义。
  3. **尾延迟不是正态分布**：全服务默认 `spring.threads.virtual.enabled=true`（`resource/micro/web/src/main/resources/web.properties:6`），而 ojdbc8 的 `PhysicalConnection` / `OracleStatement` 大量方法是 `synchronized` —— 虚拟线程在其中阻塞会 **pin 住载体线程**，载体池 `parallelism` 默认等于容器可见 CPU 数，**一两条慢 SQL 就能让全 JVM 虚拟线程停止调度**。因此 P99 可能远离 P50，**只测均值会得出乐观的假结论**。
  4. **口径四要素全缺**：没有约定 **P50/P95/P99 中的哪一个**、**并发度**、**样本量与预热轮次**、**是否含入向网关那一跳**（经网关要多走 `itp-gateway` 一层 envoy）。
- **处置建议（不裁决）**：若甲方确实要求这条 SLA，MUST 单独立一条压测用例并先定上面四要素；取证手段用 `jcmd <pid> Thread.dump_to_file -format=json`（**`jstack` 看不到虚拟线程**）、`-Djdk.tracePinnedThreads=full` 或 JFR 事件 `jdk.VirtualThreadPinned`。
- **本库做法**：用例里 curl 带 `-w 'time_total=%{time_total}'` **只作观察记录**，**明确写出它不是通过判据**。

## C8 · IF1A-03 设备心跳：不解析 `bizData`、不落库、不 RPC、恒返成功

- **代码定位**：`FepAgmController.java:112`~`:119`，方法体 **8 行**（含日志 1 行 + 构造响应 3 行 + return）。
- **四条事实**（全部可从那 8 行直接读出）：
  1. **不解析 `bizData`** —— 没调 `hasBizData`、没调 `parseBizData`。原表步骤 2 里的「IP、状态、时间戳」**一个都不读**。
  2. **不落库** —— `fep-dev-server` 无 DB、无 mapper（`AGENTS.md` §3.2），该方法也不调任何 Handler / Client。
  3. **不做任何 RPC**。
  4. **恒返 `SUCCESS`**（`:116`~`:117`）—— 无论上送什么、包括空 `bizData` 与不存在的 `deviceId`。
- **影响（`ACLC_Device_Test_004`）**：
  - 预期 1「设备状态更新为在线」—— **未找到实现**，ITP 侧没有任何 AGM 在线状态表或字段。
  - 预期 2「心跳时间记录正确」—— **未找到实现**，唯一「记录」是日志行 `IF1A-03 设备心跳, deviceId=<X>`（`:114`），**只含 `deviceId`**，时间靠日志自身前缀。
  - 预期 3「日志完整」—— 只能退化成「日志里有这一行」。
  - **原表这条的 ✅ 很可能只验证了「接口返回成功」—— 而这个接口恒返成功。**
- **易误判的对照物**：`face-pay-server` 有一个「设备离线」`@Scheduled`（7 个之一），但那是 **TVM/BOM 域**的设备离线判定、**与 AGM 心跳不是同一套，NEVER 混用**。`key-server` 的 `COM_DEVICE_SYN_KEY` 会被 `%DEVICE%` 模糊匹配命中，但它是**密钥同步记录**、不是心跳状态表。

## C10 · `fep-dev-server` 不在 tracing 名单，设备域链路会断 traceId

- **事实**：`%X{traceId}` 只在 8 个模块里有值（`pay-sign` / `card-pool` / `recon` / `gate-txn-pay` / `daily-ticket` / `collect-pay` / `face-pay` / `alipay-pay-sign`）。**`fep-dev-server`、`ticket-server`、`key-server`、`blacklist-server` 都不在名单里**，那一列**恒为空、不报错**。
- **影响**：一笔过闸从 `fep-dev-server` 进来、到 `ticket-server` 处理、再到 `gate-txn-pay-server` 扣费 —— **只有最后一段能按 traceId 串**。
- **排查约束**：「按 traceId 检索 0 条」**MUST 先确认目标模块在不在名单里，NEVER 先怀疑上游没发头**。
- **NEVER 自造 `traceId` 请求头** —— `FirstFilter`（`resource/micro/web/.../filter/FirstFilter.java:88`）把请求头小写后塞 MDC，自定义头会落到 `traceid` 键、与 pattern 的 `%X{traceId}` 对不上、永远不显示。
- 要开某个模块 MUST **三行成组**（`management.tracing.enabled=true` + `management.tracing.sampling.probability=0` + `spring.autoconfigure.exclude=...OtlpAutoConfiguration`），**NEVER 只加第一行**。

## C12 · 判据更正：`fep-dev-server` 侧「端点不存在」是 HTTP 200 + UUID `retCode`，NEVER 用 404

- **实测**（D7）：故意打错端点名 `POST http://172.20.211.23:30015/ci/agm/deviceHeartbeatXX`，应答
  ```
  http=200
  {"retCode":"3e7299a4-a982-4b80-83f2-5ecf1f5621ea","retMsg":null,"data":null}
  ```
  **不是 404、不是 400**，而是全局异常处理器把「路径无 handler」兜成 UUID。
- **与已有那条 404 判据的关系（MUST 分清，NEVER 混用）**：
  - `AGENTS.md` §2.2.2 §3.63 那条「**404 = 端点不存在、HTTP 200 + 业务码 = 存在**」说的是**我方出网打 APP（第三方）侧** `/app/receiveXxx` 通知端点 —— 对端是 APP 的 web 容器，没有我方这套全局异常处理器。
  - **我方入向的 `/ci/**` 端点走的是另一套**：`resource/micro/web` 的全局异常处理器一律返 HTTP 200，`retCode` 位置放 UUID。
- **连带**：APP 域同样如此（`docs/testing/app/0X-阻塞项与缺陷候选.md` 同批新增；实测 `POST /ci/app/requestTransListXX` → `{"retCode":"b75d6159-ddb6-4945-a424-f086de5a8f18","retMsg":null,"data":null}` http=200）。**因此「打不通的接口是不是没实现」在我方任何 `/ci/**` 端点上都 NEVER 用 HTTP 状态码判断。**
- **正确判法（三步，MUST 按序）**：① grep Controller 的 `@PostMapping` 确认 URL 是否存在；② 拿到 UUID 后 **MUST 去服务端日志取那行原文**（`scripts/klog.sh <服务名> <UUID或关键字> 300`），`No static resource` 才是「路径无 handler」；③ **NEVER 套用上次结论** —— UUID 至少有 5 种成因（事务内 RPC 超时 / `service.*.url` 指向自身 / 路径无 handler / SQL 被 Druid WallFilter 拒 / 入参反序列化失败，见 `AGENTS.md` §8）。
- **巡检口径不变**：查历史 UUID **MUST 逐 Pod grep 容器内完整日志文件的 `No static resource`，NEVER 用 `scripts/klog.sh` 带关键字**（klog 只看尾部窗口，Pod 一重启日志目录就消失）。

## C13 · 字典补漏：`8004` 在设备域读作「未注册用户」，同一码值在 APP 域读作「员工码信息不存在」

- **设备域实测**（D10）：`POST :30015/ci/agm/requestQrCodeStatus`，`bizData={"cardId":"9999999999999999"}`（库中不存在的卡）→ `{"retCode":"8004","retMsg":"未注册用户",...}`。
- **APP 域实测**（同批，见 `docs/testing/app/04-执行记录-2026-09-22.md`）：员工卡查询 `cardNo=9999999999999999` → `{"retCode":"8004","retMsg":"员工码信息不存在"}`。
- **结论（事实，不裁决）**：`8004` 是**「目标主体查不到」这一类**的共用码，`retMsg` 才承载具体语义。因此：
  - **NEVER 按 `retCode` 反推业务含义**，断言 MUST 同时钉 `retCode` + `retMsg`。
  - 这两个 `retMsg` 出自不同模块的错误码枚举（`FepDevErrorCodeEnum` / 账户域枚举），**不是同一个枚举项**，改一处 NEVER 假定另一处同步。
- **同批还实测到的两个码值，一并补进字典**：
  - `1001` = 参数缺失/格式错，`retMsg` 直接给出缺哪个键（`bizData不能为空` / `bizData格式错误` / `keyCurVerList不能为空` / `cardId不能为空`）—— **`1001` 的 `retMsg` 是可断言的，MUST 按原文钉**。
  - APP 域 `8002` = 无数据（查不存在的订单号）、`8001` = 无效的参数（`retMsg` 会带具体原因，如 `日期格式非法: 20260901，期望格式 yyyy-MM-dd` / `卡类型非法: 0445`）。
- **去处**：本条 MUST 同步补进 `docs/testing/app/00-报文与接口字典.md` 的码值表（同批已补）。
