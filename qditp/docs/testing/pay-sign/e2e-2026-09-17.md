## 四、本次暴露的问题（按优先级）

① **`receiveSignResult` 重复推 SUCCESS 返 `9001` 而非幂等 `0000`** —— **已修（pay-sign-server 2.0.108，ADR-D123）**。成因：`SignResultCallbackHandler` 直插 `APP_PAY_SIGN_INFO`，撞 `UK_APPSI_REQUEST_SIGN_SEQ` 后整事务回滚，而支付中心/渠道的回调普遍会重推，上游持续收到失败码并继续重推。现改为沿 cause 链判定（`domain/PaySignDuplicateKey.isConflict`）后回查库内状态，已是 `SIGNED` 即返 `0000`，且**不再发 `SignResultCommittedEvent`、不再插 `NOTIFY_STATUS='PENDING'` 流水**（否则会重复通知 APP / 被 `compensateNotify` 再推一遍）。**本模块已开 tracing，裸 `catch (DuplicateKeyException)` 会被切面换类型（ADR-D53），必须用 cause 链判定**；同批把 `PaymentDomainServiceImpl.ensurePayTxn` 与 `TerminationExecutor` 两处原有的裸 catch 一并改掉。

② **`requestPay.scene` 只校验非空、不校验枚举** —— **已修（pay-sign-server 2.0.109 + gate-txn-pay-server 2.0.89，ADR-D125）**。非法取值（如 `SIGN_PAY`）本地放行、到网关才报 `1001「支付类型不能为空」`，最终对上游表现为 `9001` + 网关文案，排查时极易误判成签约或金额问题。网关合法值只有 `scan` / `app` / `withholding` / `wap` / `qrcode`（文档 §1.1）。**本条原先「在 `PaySignValidators.validateRequestPay` 加白名单」的建议已作废、NEVER 采纳**：上游 `fep-app-server` 在 `scene` 为空时会把 `channelType` 透传进来，而 `gate-txn-pay-server` 的仓库默认值长期是非法的 `AGM_GATE`（线上靠 env 覆盖成 `withholding`），硬拒绝会直接打挂在跑的免密扣款。实际落地的是两处：`PaymentDomainServiceImpl.warnIfSceneOutsideGatewayEnum` **只打 WARN、不拒绝**；`GatePayRequestFactory` 的 `${gate.pay.scene:withholding}` 把仓库默认值订正为合法值（线上 env 本已是 `withholding`，故属潜伏风险清除、非行为变更）。

③ **`requestAgreeRelease` 只改本地状态、不通知支付中心** —— **口径已写入文档（`docs/business/pay-sign.md`，ADR-D125）**，代码未改（属既有设计，IF8A-36「移除签约信息」）。调用后本地 `UNSIGNED`、支付中心仍 `SIGNED`（**仍可被扣款**），与 `requestTermination` 语义容易混淆。对外沟通 MUST 原样引用 `docs/business/pay-sign.md` 里那句「它只翻本地状态，不是解约」，**NEVER 把它当成 IF8A-06 的同义词或「快捷解约」**；真要在支付渠道解掉协议只有 `requestTermination`（IF8A-06）或 `unbindAgreement`（IF8A-75）两条路。

④ **同一异常映射出两个错误码**：解约执行失败经 `/internal/termination/execute` 返 `9999`、经 `/ci/app/unbindAgreement` 返 `8007`。上游若按码分支处理需要各自适配。

⑤ **异步通知回写可能落在「复活」之后** —— **已修（pay-sign-server 2.0.109，ADR-D125）**。`notifyFailed` 的异步 APP 通知在 `reactivateFailed` 清空 `NOTIFY_*` 之后才回写 `NOTIFY_STATUS=SUCCESS`，导致新一轮 `PENDING` 申请带着上一轮的通知成功标记；本次实测到（11:11:42 复活、随后 `NOTIFY_STATUS=SUCCESS`）。不影响解约主流程，但会让 `compensateNotify` 漏掉这一轮的通知（`selectCompensableNotify` 只捞 `FAILED` 与超时 `PENDING`，一个假 `SUCCESS` 就让这轮**永久**不可见）。修法是给 `updateNotifyStatus` 与 `increaseNotifyRetryCount` 两条 UPDATE 都加**轮次闸门** `TERMINATION_STATUS = #{expectedTerminationStatus}`：回写只在「库内终态 == 本次通知所描述的终态」时生效，影响 0 行只打 WARN 不抛异常（本轮已被取代不是错误）。三条 NEVER 见 ADR-D125：闸门值 NEVER 取实体快照的 `getTerminationStatus()`（传进异步方法的是 `markSuccess` / `rejectScanning` 之前的快照、仍是 `SCANNING`，会恒命中 0 行）；0 行 NEVER 抛异常；NEVER 改用 `NOTIFY_STATUS='PENDING'` 当闸门。**证据只到单测 + SQL 渲染层（`AppTerminationRequestMapperSqlTest.notifyWritebacksAreScopedToTheirOwnRound`，全量 300 项绿）；竞态窗口只有几十毫秒，未做线上端到端复现，NEVER 写成「已线上验证」。**

⑥ **`SqlAudit` 的日志渲染会串位**：响应体里含 `?` 时，`?` 占位符按序替换会把后续绑定值插进字符串，`/requestSignInfo` 那条审计 INSERT 在日志里显示成 `startapp'0000'appId=` 且结尾多一个 `?`。**这是日志渲染假象，库里 `RESULT_CODE='0000'` 是对的**（已回查）。排查时 NEVER 拿 SqlAudit 的日志文本当作真实 SQL。

### 本轮新暴露的问题（均为**可观测性 / 契约一致性**类，不影响资金正确性）

⑦ **`APP_PAY_SIGN_REQUEST.OPERATION_TYPE` 存在两套词表，`RECEIVE_SIGN_RESULT_REPLAY` 永远进不了库。**
`PaySignAuditLogger.convertOperationType`（`audit/PaySignAuditLogger.java:100`）把一切操作名归并成只有
`SIGN` / `UNSIGN` 两个值（含 `TERMINATION`/`UNSIGN` 字样归 `UNSIGN`，其余全归 `SIGN`），而
`SignResultCallbackHandler:141` 与 `TerminationResultCallbackHandler:165` 是**绕开该 logger、直接 mapper insert**
细分值 `RECEIVE_SIGN_RESULT` / `RECEIVE_TERMINATION_RESULT`。后果：`replaySignResult` 明明写的是
`auditLogger.write("RECEIVE_SIGN_RESULT_REPLAY", ...)`（`SignResultCallbackHandler:187`），**库里落的是 `SIGN`**，
与一次普通 `requestSignInfo` 无法区分。本轮实测：3 次调用留下 1 行 `RECEIVE_SIGN_RESULT` + 2 行 `SIGN`。
**排查「回调被重推过几次」MUST 看 `REQUEST_BODY`/`RESPONSE_BODY` 或日志的「签约结果回调幂等重放」WARN，
NEVER 靠 `OPERATION_TYPE`**；`EXECUTE_TERMINATION` 同样被归成 `UNSIGN`。

⑧ **解约成功那行审计流水的 `NOTIFY_STATUS='PENDING'` 永远没人收口。**
`receiveTerminationResult` 会在 `APP_PAY_SIGN_REQUEST` 插一行 `RECEIVE_TERMINATION_RESULT` +
`NOTIFY_STATUS='PENDING'`，但签约侧补偿扫表 `PaySignRequestMapper.selectCompensableNotify`
（`mapper/PaySignRequestMapper.xml:91`）硬过滤 `OPERATION_TYPE = 'RECEIVE_SIGN_RESULT'`，解约侧补偿又只看
`APP_TERMINATION_REQUEST`。因此该行**永久停在 PENDING**（本轮实测 ID 1060 即如此）。真实通知状态记在
`APP_TERMINATION_REQUEST.NOTIFY_STATUS`（已 `SUCCESS`），所以**不丢通知**，但「按 `NOTIFY_STATUS='PENDING'`
统计待补偿量」会恒偏大。**若将来放宽那条 `OPERATION_TYPE` 过滤，会把解约行当签约通知再推一遍 —— NEVER 直接去掉它。**

⑨ **`/internal/termination/execute` 在 `SCANNING`/`SUCCESS`/`FAILED` 三态上静默返 `0000`、不留任何日志。**
`TerminationExecutor.executeTermination:95~98` 直接 `fillSuccess` 返回，既不打 INFO 也不打 WARN（对比同方法
:105 的并发未命中分支是有日志的）。于是 web-admin Quartz 侧只看到一片绿，**无法区分「真的发起了解约」与
「状态不符、什么都没干」**。同一端点的入口日志还是 `request=...ExecuteTerminationReqDTO@318ce150`
（该 DTO 没有 `toString`），排查时连流水号都看不到。建议补一行 INFO + 给 DTO 加 `toString`。

⑩ **两处「缺参」的表现与其余端点不一致。**
- `POST /ci/app/updateDisplayAccount` 是 `@RequestParam` 端点，漏传 `thirdUserId` 时由框架抛
  `MissingServletRequestParameterException`，全局处理器返 **HTTP 200 + UUID `retCode`**（本轮实测
  `52708ee2-...`，服务端日志原文 `Required request parameter 'thirdUserId' ... is not present`），
  而所有 `@RequestBody` 端点缺字段都是规整的 `8001`。这就是 AGENTS.md「UUID retCode 五种成因」里
  **入参解析失败**那一支，**排查时 MUST 先确认是不是自己少传了参数，NEVER 直接当服务故障**。
- `POST /internal/termination/checkFailedOrders` 的三个字段（`thirdUserId`/`paymentVendor`/`requestTime`）
  缺任意一个都返同一句 `8001「请求报文不能为空」`（`TerminationInternalServiceImpl:87~91`），报文其实不空，
  文案会把调用方带偏；补上 `requestTime`（`yyyy-MM-dd'T'HH:mm:ss`）后即 `0000 hasFailedOrder=false`。
- `GET /querySignInfoBySeq` 查不到时返 **HTTP 200 + 零长度 body**（无 `retCode` 信封），存在时返
  `{"requestSignSeq":...,"payAccountId":...}`。调用方只能拿「body 为空」当未找到。
