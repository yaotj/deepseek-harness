# 02 · 阻塞项与缺陷候选（BOM 单边处理）

冲突汇总，按影响排序。均来自 2026-09-08 代码实测（`main` @ `8e8b7bd`），矛盾不在本页裁决。

## A. 功能缺失 / 用例无法执行

### A1 ITP 侧不计算超时费 —— 影响 Test_022

- 状态 `06`（超时出站）**只由闸机上送 `trxType=03` 触发**（`GateTicketHandler.java:445-449`），ITP 无任何按时长自行判定超时的代码
- 超时费由闸机 / AGM 算好后经 `overtimeAmount` 上送，ITP 原样落 `QRCODE_TXN_DETAIL.OVERTIME_AMOUNT`（`GateTicketHandler.java:320`）
- **ITP 的两条补站链路都把 `overtimeAmount` 硬编码为 `"0"`**：`CardDataHandler.java:540`、`ExcessFareHandler.java:107` 与 `:132`

结论：BOM 上做的任何补站操作，下发给闸机的超时金额永远是 0。待确认「超时补票」的收费责任方是闸机还是 ITP。

### A2 无独立的「未进/出站补票」实现 —— 影响 Test_023

`transType=04`「未出站更新处理」只是 `RequestGenNoCashOrderReqDTO.java:15` / `BomNoCashOrder.java:23` 的收款单字典值，**全仓库无对该值的任何分支**。实际仍落到 `018` 补进站或 `006` 补出站。
待确认：甲方规格里该场景是否有独立计费规则（如按全程最高票价）。若有，属功能缺失；若无，本用例应与 020/021 合并。

### A3 「验证身份」无 ITP 侧实现 —— 影响 Test_021 步骤 3

IF5A-03 只校验 `cardId` / `adviceOpt` / `updateStationCode` / `optDate` 非空（`BomOrderController.java:246-270`），无鉴权、无归属校验。身份核实是 BOM 操作员的线下动作。
关联安全问题见 B1。

## B. 实现风险（建议开发确认）

### B1 IF5A-03 无鉴权，可按 `cardId` 操作任意用户行程

`collect-pay-server` 与 `ticket-server` 两侧的补站接口都没有验签、没有操作员权限校验、没有归属校验。任何网络可达方只要知道 `cardId`，就能提交补进站/补出站并推动行程状态、触发扣费。
对照 `AGENTS.md` §5.2「新增状态变更型接口 MUST 有鉴权与归属校验」。这是**状态变更 + 涉及资金**的接口，优先级高于普通查询接口。
鉴权应对齐现有实现（`AccountRequestVerifier` / `ItpRequestSignVerifier`），不要自造。

### B2 `handleCardDataUpdate` 在事务内发起 RPC

`CardDataHandler.java:151` 标注 `@Transactional(rollbackFor = Exception.class)`，而 `:265` 在事务内调 `fepDevClient.notifyVerifyResult`。
这正是 `AGENTS.md` §5.2 明令禁止的模式，与 2026-08-26 生产事故（`PaySignWorkflow.receivePayResult`，订单循环重推 8 分钟、`PAY_CALLBACK_LOG` 零条落库）**同一形态**：行锁持有时长等于闸机侧响应时长，同一张卡的重复提交会全部堆在同一行上串行等待。
补站是操作员手工触发、频率不高，但 BOM 侧超时重试会放大风险。建议改 `afterCommit` 或让该方法不带事务。

同一模块内还有 `TicketCollectServiceImpl.java:440`（`collect-ticket-server`）是同类问题，见 `../face-pay/04-阻塞项与缺陷候选.md` B6。

### B3 BOM 链路不上送 `excessFareType`

`buildGateRequest`（`CardDataHandler.java:525-550`）不设 `excessFareType`，也不设 `channelType`。而该字段语义是「空 = 真实检票，`01` = 补进站，`02` = 补出站」（`NotifyVerifyResultReqDTO.java:24-27`）。
后果：BOM 补站产生的交易明细在闸机侧与真实检票**可能无法区分**，影响对账与客诉排查取证。
`ExcessFareHandler`（APP 自助补站）会设 `excessFareType`（`:113`），两条链路不一致。

### B4 `channelType` 定义了但从不赋值

`NotifyVerifyResultReqDTO.java:45` 注释 `03 自助补站`，但 `ExcessFareHandler` 与 `CardDataHandler` **都不调 `setChannelType`**。字段形同虚设。

### B5 `03`（初始化）状态下补进站无条件放行

`isUpdateAllowed`（`CardDataHandler.java:365-404`）对 `adviceOpt=018` + `codeStatus=03` 的组合**不校验 `updateType`**。即对一张从未进站的新码，无论乘客在付费区还是非付费区，都能直接补进站。
需业务确认是否合规——按 `AGENTS.md` §5.2「状态机校验用白名单不用黑名单」的精神，这里虽是白名单，但条件被放宽到了无条件。

### B6 存在两份 `QRCodeStatusEnum`，取值数量不同

- `ticket-server/.../ticket/enums/QRCodeStatusEnum.java` — 10 个值（`02/03/04/05/06/08/09/10/80/81`）
- `model/.../model/ticket/enums/QRCodeStatusEnum.java:9-46` — 13 个值，多出 `01 无交易`、`70 异常`、`FF 进站失败`

`ExcessFareHandler` import 的是 **model 版**，所以 `fromCode("01"/"70"/"FF")` 不为 null，会落到 `default` 分支被拒绝（提示「当前票卡状态不支持补站」），而不是走「状态未知」分支。
改状态取值时若只改一份，两处行为会分叉。按 `AGENTS.md` §2.2.1，改状态值 **MUST 全局 grep 所有比较点**——这里的坑是同名类有两份。

### B7 `ExcessFareHandler` 用 `String.contains` 判白名单

`ExcessFareHandler.java:90` 是 `allowedTypes.contains(upgradeAreaType)`，而 `allowedTypes` 是字符串 `"02,03,04"`。传入 `","`、`"2,0"`、`"3,0"` 等子串同样会通过校验。
这条属 **APP 自助补站链路**（不影响 BOM 的 `CardDataHandler`），但既然发现就一并记录。应改为按 `,` split 后精确比较。

### B8 `upgradeAreaType` 的 `03` / `04` 含义未定义

`RequestExcessFareReqDTO.java:10-11` 只注释了 `01 补进站 / 02 补出站`。`03`、`04` 仅以字面量出现在白名单字符串 `"02,03,04"` 里（`ExcessFareHandler.java:158-176`），**全仓库无任何注释、枚举或常量定义其含义**。
即代码允许了两个没人知道含义的取值。需向甲方或原作者确认。

## C. 文档一致性

`docs/business/ride-code.md` 需补一条：**BOM 单边处理走 IF5A-01/IF5A-03（`CardDataHandler`），与 APP 自助补站的 `requestExcessFare`（`ExcessFareHandler`）是两条独立链路，白名单规则与上送字段均不同。** 目前该文档未明确区分，容易被误读成同一条。

`AGENTS.md` §2.2.2 记「IF5A HCE 链路：仅有 `requestCardDataAnalyse` / `requestUpdateCardData` / `notiUpdateHceData` 三个入口，链路不完整」——按本次探索，这三个入口在 **BOM 补进出站** 方向上链路是完整可跑的（BOM → collect-pay-server → ticket-server → fep-dev-server → 改状态 → 扣费）。「链路不完整」应指 HCE 卡数据下发方向，建议在 AGENTS.md 里把两者分开表述，避免误判成「BOM 补站没做」。

## D. 规格逐条核对结果（2026-09-08 补）

依据《技术规范-第9部分-互联网业务规范》§7.3「青岛地铁ITP与BOM对接设计」与 §5.3「BOM乘客事物处理」逐条比对。

### D1 ⚠️ 本页白名单规则没有规格依据

**BOM 章节没有规定「允许的前置状态」**。规格只写「ITP收到票卡分析请求后，根据卡号，及付费区标分析该乘车码可做哪些操作」（§5.3.1），把状态判定责任整个交给 ITP，**未列举任何状态白名单**。

因此 [[00-链路事实与状态机]] 里那两张表（`resolveAdviceOpt` 规则表、`isUpdateAllowed` 白名单）是**实现方自定义的**，甲方无对应条文。

**测试口径由此确定**：这些规则只能验「代码行为与代码设计一致」，**不能得出「符合需求」的结论**。若要把它们作为验收标准，需先让甲方或产品把白名单书面确认下来。

### D2 ⚠️ `adviceOpt` 在同一份规格里有两套编码

- §5.3.1 流程正文：`00` 无需更新 / `01` 补进站 / `02` 补出站 / `03` 20分免费更新 / `04` 20分付费更新
- IF5A-01 应答参数表：`000` 无需更新 / `018` 补进站 无法出站 / `006` 补出站（最低票价）无法进站 / `005` 20分免费进站更新无法进站

代码用的是后一套（`CardDataHandler.resolveAdviceOpt:290-360` 产出 `000/005/006/018`），与接口表一致。
但接口表的取值里**没有「20分付费更新」**，而同一张表的 `transAmount` 字段说明写的却是「20分付费更新 金额」——规格自相矛盾。需向甲方确认「20分付费更新」是否应有独立 `adviceOpt` 值。

### D3 ⚠️ `adviceOpt` 的数据类型前后不一致

- IF5A-01 **应答**：类型原文写「json数据组」，示例报文 `"adviceOpt":["006"]`（数组）
- IF5A-03 **请求**：类型原文是 String，取值只三个 `018`/`006`/`005`（**不含 `000`**）

同一字段跨接口传递时形态要转换。联调时需核对 ITP 侧 IF5A-01 是否按数组返回、BOM 侧能否正确解析。

### D4 `transType` 里的 `05` 无入站更新处理 —— 规格有、代码无分支

IF8A-04 的 `transType` 规格共九个取值：
`02` 超时更新 · `03` 超程更新/一卡通余额不足更新 · `04` 未出站更新处理 · `05` 无入站更新处理 · `06` 储值票即时退卡/单程票退票 · `22` 充值 · `2A` 黑名单卡锁定 · `2B` 卡锁定解除 · `42` 行政处理（须带 `adminTransType`，10 个取值 `01`~`0A`）

代码只对 `42` 做了校验（`collect-pay-server/.../BomOrderController.java:101-103`），其余八个值无任何分支，仅作字典值落库。

**由此更正 [[01-用例]] Test_023 的结论**：规格给了 `04 未出站更新处理` 与 `05 无入站更新处理` 两个独立交易类型，属「规格有、代码无分支」，不是「等价于 020/021 的换名」。是否需要独立的计费与状态处理规则，需产品确认。

注意 `02` 原文是「**超时**更新」而非「超程更新」——「超程更新」是 `03`。此前文档若按「02=超程」理解需一并更正。

### D5 §5.3.1 要求把行业数据推送给 APP_SERVER —— 待核实

§5.3.1 原文两步：「ITP 组织生成最新的行业数据，分别推送给APP_SERVER及BOM」「BOM 收到后台推送的行业数据后，通过蓝牙回传给用户地铁APP，地铁APP更新行业数据」。

IF5A-03 应答只有 `retCode` / `retMsg` / `cardData`（行业数据，示例是 40 字节 HEX），`BomOrderServiceImpl.requestCardDataUpdate:1026-1051` 只回 `cardData`——**回 BOM 这一路一致**。
**推送 APP_SERVER 这一路本次未核实**，需单独确认是否实现。

### D6 规格未提及的三项（原用例预期应删除或转设备侧）

BOM 章节全章检索结论：

- **无凭证打印要求**：全章唯一含「打印」的句子是「用户在TVM充值，TVM充值结果存疑，打印故障单」，描述 TVM 行为且属输入条件
- **无「充值失败要退款」条文**：该要求只在 §7.5 TVM 章节（「充值失败，后台直接调用支付通道退款」）
- **无「对账」「冲正」「单边账」「差错」任一字样**

### D7 心跳与超时数值（规格侧已提取，代码侧待核）

- 心跳：每 1 分钟一次；**「心跳异常，设备暂停非现金支付」是对设备的要求**，ITP 只需返回 `0000`。代码 `BomOrderController.java:44` 记日志后返回成功，符合
- 下单接口：超时 5 秒、最多重试 3 次
- **扫码支付：超时 15 秒，且原文明确「不要重试」**；超时后 BOM 改调查询支付结果
- 查询支付结果：超时 5 秒、最多重试 3 次
- 业务操作结果通知 / 充值结果通知：超时 5 秒、最多 3 次，且要求 BOM 本地留存待补传

代码侧 `bom.payTimeOut`（`application.yml:61`）、`bom.payTimeInterval`（`:62`）的实际值与上述是否一致，**本次未核对**，需单独一轮。



## E. 已修复

### E1 `005` 免费更新此前永不可用（2026-09-09 修复，`ticket-server` 2.1.46）

**现象**：BOM 侧「20 分钟内免费更新」自上线起没有一次成功。

**根因**：`005` 的唯一前置状态是 `10`（入站码更新），而 `10` **没有任何代码写入路径**。写 `CODE_STATUS` 的只有 `TicketRideStatusServiceImpl:91`（`03`）、`ExcessFareHandler:71`（`03`）、`GateTicketHandler:348`（产出 `04/05/06/08/09/FF/01`，其中 `08`/`09` 还要求入参 `adviceOpt` 已是 `005`/`006`，构成循环依赖）与运营端人工改状态（`QRCodeRideStatusPageController`，`ALLOWED_CODE_STATUS` 含 `10`）。生产库实测（`AFCITPDB.QRCODE_STATUS`）：`03`=48、`05`=13、`04`=6、`06`=3、`80`=1，**`10` / `08` / `09` 均 0 行**。
因此 IF5A-01 永远不会建议 `005`，BOM 强行传 `005` 也必被 `isUpdateAllowed` 拒绝（`INVALID_PARAM` +「票卡状态不允许此操作」）。

**修复**（用户 2026-09-09 裁决按此意图，依据 §5.3.1 把「20分免费更新 / 20分付费更新」并列成一对）：
- `resolveAdviceOpt` 开环分支先按 `isWithin20Minutes(gateInTime)` 分流出 `005`，超 20 分钟才落 `006`
- `isUpdateAllowed` 的 `005` 白名单放开开环 `04/81` 且 `updateType=00`，原 `10` 通路保留

**尚未闭合**：`10` 依然是孤岛状态。若甲方确认「入站码更新」是独立业务态，还缺「闸机上送哪个 `trxType` 置 `10`」的定义——规格里没有。

**回归口径**：把某张 `CODE_STATUS='04'` 的码的 `GATE_IN_TIME` 置为当前时间前 5 分钟，IF5A-01 传 `updateType=00` 应回 `adviceOpt=["005"]` + `transAmount=0`；置为 30 分钟前应回 `006` 且带票价。改库前记录原值。
