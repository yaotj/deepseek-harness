# 01 · 用例（ITP_ETicket_Test_020~023）

链路事实、`adviceOpt` 规则表、白名单见 [[00-链路事实与状态机]]。所有用例的证据都在 `ticket-server` 的 `QRCODE_STATUS` 与 `QRCODE_TXN_DETAIL`，**collect-pay-server 不落库**。

## Test_020 BOM 补进出站-补出站

对应 `adviceOpt=006`。

前置条件（比原用例严格，白名单决定的）：
- 乘车码 `CODE_STATUS` 必须是开环态 `04`（已进站）或 `81`（APP 自助补进站），或 `10`（入站码更新）
- `updateType` 必须传 `00`（非付费区）——`04`/`81` 且 `updateType=01` 会得到 `adviceOpt=000`「无需操作」
- 例外：`81` 状态下 `updateType` 不限（`isUpdateAllowed` 对 `81` 是无条件放行）

步骤与预期（可验证）：

1. BOM 调 IF5A-01 `requestCardDataAnalyse`（`cardId` + `updateType=00`）→ 返回 `adviceOpt=006`，并带回 `transAmount`（票价）、`cardStatus`、`lastStationCode`
2. 票价来源是 `paraClient.requestTicketPriceByStation`，入参为 `QRCodeStatus` 里的进站站与本次 `updateStationCode`。**断言金额时要用这两个站点去 para-server 单独查一次比对**，而不是只看 BOM 界面
3. BOM 调 IF5A-03 `requestUpdateCardData`（`cardId` + `adviceOpt=006` + `updateStationCode` + `optDate`）
4. `QRCODE_STATUS.CODE_STATUS` 变为出站态（`trxType` 被解析成 `02`），`QRCODE_TXN_DETAIL` 新增一笔，金额与第 2 步一致
5. 扣费：满足条件时触发 `gate-txn-pay`（后付费）或 alipay-trip

值得专门测的两点：
- **`lastTxn=FFFF` 的分支**：`resolveAdviceOpt` 在开环态遇到 `lastTxn=FFFF` 会打 `WARN_STATION_FFFF` 并**按最低票价**计算。这是兜底逻辑，正常流程测不到，需要造数据
- **`excessFareType` 未上送**：BOM 链路的 `buildGateRequest` 不设该字段（见 [[00-链路事实与状态机]]），请核对 `QRCODE_TXN_DETAIL` 里这一笔能否与真实检票区分

结果：☐ 通过 ☐ 失败 ☐ 阻塞

## Test_021 BOM 补进出站-补进站

对应 `adviceOpt=018`。

前置条件：
- `CODE_STATUS` 是闭环态 `02`（结束行程）/ `05`（已出站）/ `06`（超时出站）/ `80`（自助补出站），且 `updateType=01`
- 或 `08`/`09`（20 分钟内更新）且 `updateType=01`
- 或 `03`（初始化）——**无条件放行**，`updateType` 不限
- 或 `10`（入站码更新）且 `updateType=01`（IF5A-01 侧还要求 `gateInStation=FFFF` 才给 `018`）

步骤与预期：

1. IF5A-01 返回 `adviceOpt=018`
2. IF5A-03 执行后 `trxType` 解析为 `01`（进站），`QRCODE_STATUS` 进入进站态
3. **补进站不算钱**：只有 `adviceOpt=006` 才调票价接口，`018` 分支 `trxType=01`，`transAmount` 不参与计算
4. 「可正常出站」：补进站后再走一次正常出站或 IF5A-03 `006`，验证行程能闭环

⚠️ 原用例步骤 3 写「验证身份并选择站点」——**ITP 侧没有身份验证代码**。IF5A-03 只校验 `cardId`/`adviceOpt`/`updateStationCode`/`optDate` 非空，身份核实是 BOM 操作员的线下动作。这条不可测，建议改为「BOM 界面显示的用户信息与 `queryUserInfo` 返回一致」——`handleCardDataAnalyse` 确实会查用户信息（`CardDataHandler.java:452-486`，`providerId=07` 走支付宝侧）。

结果：☐ 通过 ☐ 失败 ☐ 阻塞

## Test_022 BOM 补进出站-超时补票

⚠️ **「超时费用计算正确」在 ITP 侧无实现，本用例的核心断言无法验证。**

代码事实（详见 [[00-链路事实与状态机]] 超时一节）：

- 状态 `06`（超时出站）**只由闸机上送 `trxType=03` 触发**，ITP 不自行判定超时
- 超时费由闸机 / AGM 算好后通过 `overtimeAmount` 上送，ITP 原样落 `QRCODE_TXN_DETAIL.OVERTIME_AMOUNT`
- **走 BOM 补站链路时 `overtimeAmount` 恒为 `"0"`**（`CardDataHandler.java:540` 硬编码）

也就是说：如果「超时补票」指的是在 BOM 上为一笔超时行程补费，那么 ITP 下发给闸机的报文里超时金额永远是 0。真正带超时费的路径只有闸机自己上送 `trxType=03`。

重写后的可测形态（二选一，需产品确认走哪个）：

- **形态 A**（验现状）：造一笔 `CODE_STATUS=06` 的行程 → BOM 走 `updateType=01` + `adviceOpt=018` 补进站（`06` 在 `018` 白名单里）→ 断言操作成功、`OVERTIME_AMOUNT` 为 0。这只验「超时态可被补站」，不验超时费
- **形态 B**（验闸机侧）：由闸机上送 `trxType=03` 带 `overtimeAmount` → 断言 ITP 原样落库。这是超时费的唯一真实路径，但不经 BOM

结果：☐ 阻塞（原因：超时费计算不在 ITP 侧）

## Test_023 BOM 补进出站-未进/出站补票

⚠️ **代码里没有独立的「未进/出站补票」分支。**

唯一相关的线索是收款单业务类型注释：`RequestGenNoCashOrderReqDTO.java:15` 与 `BomNoCashOrder.java:23` 的 `transType` 含 `04:未出站更新处理`（`03` 是超程更新/一卡通余额不足更新）。但**全仓库没有对 `transType=04` 的任何特殊分支**——它只是收款单上的一个字典值。

实际执行时，「未进站」和「未出站」两种情况仍然落到已有的两个 `adviceOpt`：

- 未进站（乘客在付费区但码是闭环态）→ `018` 补进站，等价于 Test_021
- 未出站（乘客已出站但码是开环态）→ `006` 补出站，等价于 Test_020

所以本用例在 ITP 侧**不是新场景**，是 020/021 的换名。可测形态：

1. 按 020/021 执行补站
2. 若涉及收款，BOM 另发 `requestGenNoCashOrder` 带 `transType=04`，断言 `BomNoCashOrder` 落库的类型值正确
3. 「扣费金额按规则计算」——同 020，金额由 `006` 分支的票价接口决定；若走 `018` 则不算钱

⚠️ 需产品确认：本用例与 020/021 是否应合并。若甲方规格里「未进/出站补票」有独立的计费规则（例如按全程最高票价），那 ITP 侧**没有实现**，属缺失而非换名。

结果：☐ 通过（按 020/021 口径） ☐ 阻塞（若需独立计费规则）

## 矛盾/待验证

- ⚠️ Test_022「超时费用计算正确」ITP 无实现，BOM 链路 `overtimeAmount` 恒 0
- ⚠️ Test_023 无独立实现，需确认是否等价于 020/021
- ⚠️ Test_021「验证身份」ITP 无鉴权代码，属 BOM 线下动作
- ⚠️ BOM 链路不上送 `excessFareType`，补站笔可能与真实检票无法区分
- ⚠️ `03`（初始化）状态下 `018` 补进站**无条件放行**，`updateType` 不校验——对一张从未进站的新码直接补进站是否合规，需业务确认
