# BOM 单边处理 · 链路事实与状态机

来源：仓库代码 + 集群实测（2026-09-10 修复并复测；原始版本 2026-09-08 @ `8e8b7bd`）。只记录代码中确实存在的事实。

## 先定位：BOM 补站走的不是 `requestExcessFare`

本项目有**两条互不相同的补站链路**，测试时极易混淆：

- **APP 自助补站**：`POST /ci/app/requestExcessFare` → `ticket-server/.../ExcessFareHandler.java`，参数是 `upgradeAreaType`，`deviceId` 拼 `站点码 + "36" + "01"`（`36` = 自助补站手机）
- **BOM 单边处理**（本页对象）：IF5A-01 + IF5A-03 → `ticket-server/.../CardDataHandler.java`，参数是 `updateType` + `adviceOpt`，`deviceId = operaterId`（操作员号）

Test_020~023 全部走**第二条**。写用例、配 Apifox、提缺陷单时不要引用 `requestExcessFare` 的字段名与状态白名单——两条链路的白名单规则不同。

⚠️ **入口模块与 URL 已于 2026-09-10 纠正**（原文档记为 collect-pay-server + `/ci/agm/**`，两处都错）：

- **BOM 侧入口是 `face-pay-server`（58101），不是 `collect-pay-server`**。2026-09-10 实测：BOM 补站期间 `collect-pay-server` 日志对 `CardData` 零命中，全部命中 face-pay-server 的 `BomOrderController`。两个模块都有同名接口，**定位实现 MUST 看 face-pay-server**。
- **ticket-server 侧命中的是 `/ci/app/**`**（`rpc/TicketClient.java:147,156` 硬编码），不是 `/ci/agm/**`。连带结论：`TicketAgmController:105-150` 那套入参校验（cardId / adviceOpt / updateStationCode / optDate 非空 + `buildCardDataAnalyseError`）**在真实链路上不执行**，校验只剩 face-pay-server 那一层。

`TicketAgmController.java` 的类注释仍准确描述了业务语义：`:28`「IF5A-03 票卡更新（BOM 补进站/补出站）」、`:103`「BOM 终端在补进站/补出站前调用」、`:122`「BOM 终端执行补进站/补出站操作」——但那个 Controller 只是同名旁路。

**关键点**：`face-pay-server` 两个方法都是**纯透传、本地不落库**。所以在 face-pay / collect-pay 的表里找不到补站记录，证据全在 `ticket-server` 的 `QRCODE_STATUS` 与 `QRCODE_TXN_DETAIL`。

## 请求参数

**IF5A-01 `requestCardDataAnalyse`**：必填 `cardId`、`updateType`（`face-pay-server/.../BomOrderController.java:212-223` 校验）
**IF5A-03 `requestUpdateCardData`**：必填 `cardId`、`adviceOpt`、`updateStationCode`、`optDate`（14 位 `yyyyMMddHHmmss`）、`updateType`（`:231-253` 校验）

> `optDate` 的**格式校验**是 2026-09-10 新增（原先只校验非空）。长度不足 8 时会一路透到 ticket-server 的 `buildTxnDetail` 在 `substring(0,8)` 处抛 `StringIndexOutOfBoundsException`、表现为 500。现返回 `8003 optDate格式错误，应为14位yyyyMMddHHmmss`；ticket-server 侧也加了兜底（`resolveTxnDate`，格式异常时用当天日期并打 WARN）。

`updateType` 语义（`CardDataHandler.resolveAdviceOpt`）：`01` = 付费区（乘客在闸机内侧），`00` 或其他 = 非付费区（闸机外侧）。

## `adviceOpt` 取值

`CardDataHandler.java:290-360`：

- `000` 无需操作
- `005` 免费更新
- `006` 补出站 / 付费更新
- `018` 补进站

| `adviceOpt` | 允许的前置状态 |
|---|---|
| `018` 补进站 | 闭环 `02/05/06/80` 且 `updateType=01`；`08`/`09` 且 `updateType=01`；`03` 无条件；`10` 且 `updateType=01` |

> ⚠️ **2026-09-23 / ADR-D157 站码维度**：上表 `006` 行——**跨站（BOM 站码 ≠ 进站站）无论窗内窗外一律放行收费**（用户「窗内不同站也收费」裁决）；同站且仍在窗内则拒绝（应走 005）；站码未知沿用旧兜底「证明不了超窗就 NEVER 收费」。`005` 行——**跨站 MUST 拒绝**（`CROSS_STATION_NOT_FREE`，提示改走 006）。站码比较任一侧未知（含 `FFFF`/空）即判未知，NEVER 误判跨站而错收费。

> **`005` 的 20 分钟窗口现在在执行侧复核**（2026-09-10 修复）。原先时间判定只在 IF5A-01，`isUpdateAllowed` 只看 `codeStatus`/`updateType`，于是「先拿到 005、隔 40 分钟再提交 IF5A-03」照样免费出站——纯收入损失口子。

`resolveTrxType`：`018` → `trxType=01`（进站）；`005`/`006` → `trxType=02`（出站）；其他拒绝。

## 扣费边界：补站不触发 gate-txn-pay（2026-09-10 修复）

`fep-dev-server` 的 `shouldPay` 原先只判 `TrxTypeCodeEnum.isExitTxn(trxType)`，而 `005`/`006` 都被 `resolveTrxType` 映射成 `trxType=02`，于是**每笔 BOM 补出站都会发起一次免密扣款**。

实测证据（修复前，2026-09-10 17:21）：一次 `005` 免费更新落出 `GATE_TXN_PAY` 订单 `GT20260910172129730135717`，`ORIGINAL_FARE=700`、`TRX_AMOUNT=0`、`ORDER_EXP_TYPE=0`（正常）、`DEBIT_STATUS=SUCCESS`。在扣费表里与一笔正常出站完全同形，直接污染对账。根因还包括 `adviceOpt` 在 `requestGateTxnPay` 新建 `GateTxnPayReqDTO` 时没被拷贝，下游看到的是 `null`。

**现行规则（2026-09-23 实测校正，见下方「落单口径」）**：判据在 `ticket-server/.../gate/GateFarePaymentOrchestrator`，白名单是 **`AdviceOptEnum.SUPPLEMENT_EXIT_CODES`（`005` / `006` / `020` 三者都在内）**，不是本文原先写的 `Set.of("005","006")`。`adviceOpt` 只有 IF5A-03 链路上送，真实闸机报文里恒 `null`，APP 自助补站用 `excessFareType`，所以这个判据精确命中 BOM 补站。业务口径（用户 2026-09-10 裁决）：**006 补出站的钱由 BOM 现场向乘客收取，ITP 不再扣款**。

> **NEVER 退回「`adviceOpt` 非空即跳过扣费」**（2026-09-10 第一版曾这样写，代码审查拦下）。那是黑名单，违反 AGENTS.md §5.2；一旦将来有别的链路带上未知 `adviceOpt`，真实出站扣费会被静默跳过 —— 直接资损。现在未知取值走 `else` 分支：打 WARN 并**照常扣费**。

### 落单口径：「不扣款」≠「不落单」（2026-09-23 实测推翻本文原「零新增」表述）

⚠️ **本文 2026-09-10 写的「`GATE_TXN_PAY` 最大 ID 仍是 5175（零新增）」已经过期，NEVER 回退成「补站不落 GATE_TXN_PAY 行」。**
现行设计是**落单但不扣款**，`GateFarePaymentOrchestrator` 类注释原文给了理由：「不落单等于这趟行程在 APP 里根本不存在（BOM 补站曾因此整笔不可见）」。

2026-09-23 端到端实测（卡 `0426090949000003`，经 face-pay BOM 入口 IF5A-03）：

- `020` 免费更新 → 落 `GATE_TXN_PAY.ID=5308`：`ADVICE_OPT='020'`、`TRX_AMOUNT=0`、`ORIGINAL_FARE=200`、`TOTAL_AMOUNT=0`、`DEBIT_STATUS=SUCCESS`、**`EXPECTED_GATE_AMOUNT=0`**、`DISCOUNT_CALC_STATUS='SKIPPED'`、`REMARK='BOM补站现场已收款，不由ITP扣款'`
- `006` 付费更新 → 落 `GATE_TXN_PAY.ID=5309`：`ADVICE_OPT='006'`、`TRX_AMOUNT=700`、`ORIGINAL_FARE=700`、`TOTAL_AMOUNT=700`、`DEBIT_STATUS=SUCCESS`、**`EXPECTED_GATE_AMOUNT=0`**、`DISCOUNT_CALC_STATUS='SKIPPED'`、同一条 `REMARK`

⇒ **判「这笔补站有没有真扣钱」MUST 看 `EXPECTED_GATE_AMOUNT`（=0 表示无应扣款）与 `REMARK`/`DISCOUNT_CALC_STATUS`，NEVER 只看 `DEBIT_STATUS='SUCCESS'`** —— 后者在「落单不扣款」形态下同样为 `SUCCESS`，单看它会误判成「ITP 又向乘客扣了一笔」（实际 BOM 已现场收款，不存在二次扣款）。

原 2026-09-10 的修复后复测记录：18:07 `018` + 18:08 `005` 全流程成功，fep-dev 日志出现 `IF1A-01 BOM 补站交易不触发扣费, adviceOpt=005`（当时确实是零新增行；现行版本改为落单）。

## 幂等设计

`handleCardDataUpdate` 在调闸机前后各读一次库：先记录 `codeStatus` / `txnSeq` 快照，调闸机前二次读库比对。

**返回码已改**（2026-09-10）：命中变更时返回 `8305 票卡状态已变更，请重新做票卡分析后重试`，不再返回 `0000`。原先返回 `0000` + retMsg 提示，BOM 按 `0000` 判成功就会去写卡，而 ITP 侧并未执行本次更新 → 卡内与后台不一致。

实测重复提交同一笔 `005`：第二次被**状态白名单**先拦下（`codeStatus` 已推进到 `08`），返回 `8001 票卡状态不允许此操作`。`8305` 只在更窄的竞态（状态未变但 `txnSeq` 变了）下命中。

## 事务边界

`AgmRideStatusServiceImpl.requestCardDataUpdate` 与 `CardDataHandler.handleCardDataUpdate` 原先各挂一层 `@Transactional`，**2026-09-10 全部摘除**。两条理由：

1. 方法内串行调 account-server ×1、para-server（仅 006）、fep-dev-server，违反 AGENTS.md §5.2「事务内 NEVER 发 RPC」；
2. **`CardDataHandler` 一条写 SQL 都没有**——状态推进发生在 fep-dev 回调 `/ci/agm/notiVerifyResult` 那个独立请求里的 `GateTicketWriter`。所以 rollback 语义是空的，事务只带来连接占用与自回环双连接。

修复前实测单笔 `IF5A-03` 耗时 476~860ms，其中约 400ms 是业务判定结束后的事务收尾；修复后 18:08 那笔 52ms。

## IF5A-01 响应字段：`msisdn` / `cardIssueDate` 曾恒为空（2026-09-10 修复）

`CardDataHandler.handleCardDataAnalyse` 用局部变量在 `queryUserInfo(...)` **之后**无条件回写 `response.setMsisdn(...)` / `setCardIssueDate(...)`，把刚查到的值覆盖成空串。实测：account-server 明确返回 `msisdn` 与 `regTms`（fep-dev 日志 17:21:03 可见），而 IF5A-01 响应三次全是 `"msisdn":"","cardIssueDate":""`。

顺带清理：`queryUserInfo` 原先对非支付宝发行方**二次调 `accountClient.queryUserInfo`**，而第一次的 `queryCardTypeByCardId` 返回里已经带 `msisdn` + `regTms`，那次 RPC 是纯浪费，已删。支付宝发行方（`providerId=07`）的手机号在 alipay-account-server，仍单独查。

修复后实测（18:07）：`"msisdn":"15000000197","cardIssueDate":"20260908150121"`。

> 断言这两个字段时注意 face-pay-server 响应体的**既有拼写错误契约**：`lastTransAmout`、`lastTikcetTransSeq`（`BomResponses.java:73-93` 有说明，是刻意对齐 BOM 端的，**NEVER 顺手改正**）。

## 安全现状（未修复，用户 2026-09-10 裁决暂不处理）

IF5A-01/03 全链路 `signType=00`、`sign=""`，face-pay-server 与 ticket-server 都不验签，也无归属校验。`/ci/app/requestUpdateCardData` 在集群内裸暴露，任何网络可达方可按 `cardId` 对任意用户补站。且状态机成环：`05 --018--> 04 --005--> 08 --018--> 04 ...`，每轮 `TXN_SEQ+1`、每轮产生一条明细，无频次或时间窗限制（`005` 的 20 分钟窗口只约束单次，不约束循环）。

加验签会立刻打断现网 BOM 联调（BOM 端不发真签名），因此本轮不做，**上线前必须补**，且 MUST 对齐 `ItpRequestSignVerifier`，NEVER 自造。

## 超时（Test_022 的关键前提）

- **状态 `06`（超时出站）只由闸机上送 `trxType=03` 触发**：`GateTicketHandler.java:445-449`，`TrxTypeCodeEnum.EXIT_OVERTIME("03","超时出站")`（`model/.../TrxTypeCodeEnum.java:15-16`）

- **超时费用由闸机 / AGM 算好后上送**：`NotifyVerifyResultReqDTO.overtimeAmount`（`:18`）→ ticket-server 原样落 `QRCODE_TXN_DETAIL.OVERTIME_AMOUNT`（`GateTicketHandler.java:320`）
- **ITP 的两条补站链路都不算超时费**：`CardDataHandler.java:540` 与 `ExcessFareHandler.java:107`、`:132` 全部硬编码 `overtimeAmount = "0"`

## ⚠️ 测试前必读：容器时区为 UTC 会让 20 分钟窗判定整体失效（2026-09-23 实测）

**判据：只要 IF5A-01 对「同站 + 明显在 20 分钟内」的卡返回 `["006","020"]` 而不是 `["005"]`，先查容器/JVM 时区，不要再怀疑规则代码。**

`isWithinFreeWindow` 拿**设备侧的 `gateInTime`（CST）**与 **JVM 的 `LocalDateTime.now()`** 直接相减（`SupplementStateRules.java`，`isWithinFreeWindow` / `parseBizTime`）。两侧时区必须一致。若 JVM 跑在 UTC：

- `Duration.between(inTime, LocalDateTime.now()).toMinutes()` 得**负数**（设备时间看起来在未来 8 小时）
- 代码走 `minutes < 0` 分支 → 打 `进站时间晚于当前时间，按超窗处理` → 返回 false
- 于是 `isFreeWindowExpired` 恒为 true ⇒ **同站窗内也判超窗 ⇒ `005` 永不可达、BOM 默认取 `006` 收费**；同时 IF5A-03 的 `FREE_WINDOW_NOT_EXPIRED` 守卫也一并失效（本该拒的 006 会被放行）

2026-09-23 实测证据（**同一批代码、同一张卡，只改 `optDate` 的时区口径，结论相反**）：

| 卡状态 | `deviceId` | `optDate` 口径 | `adviceOpt` |
|---|---|---|---|
| 04，`GATE_IN_TIME=20260923114831` | `06220801`（同站 0622） | 本地 CST | `["006","020"]` ← **错**，此时 JVM 为 UTC |
| 04，`GATE_IN_TIME=20260923034935` | `06220801`（同站 0622） | 按 JVM 的 UTC 给 | `["005"]` ← 对 |

时区来源（实测）：**这条挂载就写在线上 Deployment 的 pod 模板里**（`spec.template.spec.volumes[].hostPath.path=/etc/localtime`，卷名 `hostpath-7w1p6nit0`，由 `kubectl get deploy ticket-server -o jsonpath='{.spec.template.spec.volumes}'` 读得）；但**仓库 `deploy/` 下查不到这条**（`grep -rn "localtime\|hostPath" deploy/` 零命中）⇒ **线上 manifest 与仓库不同源，改线上不会回写仓库、改仓库也不会影响线上**。因此**时区随 pod 落到的节点而变**。同日实测该挂载下容器内 `/etc/localtime` 实际内容 = `Etc/UTC`（`md5sum` 与 `/usr/share/zoneinfo/Etc/UTC` 一致）、`TZ` 环境变量为空 ⇒ JVM 取 UTC。

旁证（不依赖任何 DB 渲染）：`QRCODE_TXN_DETAIL.CREATE_TIME` 与 `QRCODE_STATUS.UPDATE_TIME` 都是 `TIMESTAMP(6)` 无时区列、由 Java `LocalDateTime.now()` 直写，实测比同一笔的 `HANDLE_DATE_TIME`（设备时间）**少 8 小时**；而 2026-09-22 及之前的同两列与设备时间**一致**（差 0~2 秒）⇒ JVM 时区是在 2026-09-23 那次重建 pod 后翻转的。应用日志时间戳同样呈 UTC。

**修法与验证（2026-09-23 已执行，部署侧修复）**：`kubectl -n itp set env deployment/<d> TZ=Asia/Shanghai` —— `TZ` 环境变量的优先级**高于 `/etc/localtime`**（glibc 与 JVM 都是先看 `TZ`），因此不必去动那条 hostPath 挂载，也**与 pod 落到哪个节点无关**。

- 范围：`itp` 命名空间 **23 个业务 deployment** 全部注入（ticket-server / face-pay-server / gate-txn-pay-server / para-server / account / alipay-account-server / alipay-pay-sign-server / blacklist-server / card-pool-server / collect-pay / daily-ticket-server / es-server / fep-acc / fep-alipay / fep-app / fep-dev-server / industry-data-server / key-server / pay-sign-server / recon-server / security-server / trans-query / web / web-admin）。
- **未注入**（非业务，本次刻意不动）：`database`、`kennethreitz-httpbin`、`victoria-logs`，以及 bookinfo 示例的 `details-v1` / `productpage-v1` / `ratings-v1` / `reviews-v1` / `reviews-v2` / `reviews-v3`。
- 验证：①容器内 `TZ=[Asia/Shanghai]`；②应用日志时间戳回到 CST（`2026-09-23 11:59:53` 对应墙钟 `11:59:53`）；③`QRCODE_TXN_DETAIL.CREATE_TIME` 与设备时间一致（`ID=15879`：`HANDLE_DATE_TIME=20260923120209`、`CREATE_TIME=2026-09-23 12:02:10`）；④**回归本节的窗内断言，`optDate` 用真实 CST 口径即得 `["005"]`**（修复前必须把 `optDate` 按 UTC 给才能得到 `005`）。
- ⚠️ **治理提示**：`TZ` 只存在于**线上 Deployment**，仓库 `deploy/` 里没有 ⇒ 若以后按仓库 manifest 重建 Deployment，**这个修复会丢**，需要重新注入（或改为在仓库里补上并去掉 hostPath 挂载）。另外**新增的业务模块 deployment 也要记得加**。
- ⚠️ **连带影响（定时任务口径）**：`@Scheduled` / Quartz 的 cron 按 JVM 默认时区解释，故归一到 CST 会一并**纠正**定时式任务的触发时刻。`face-pay-server` 的 7 个 `@Scheduled` 全是 `fixedDelay` 或 `*/5`、`*/10` 这种**间隔式**（不受影响）；`collect-pay-server` 的 `0 0 20 * * ?`、`0 0 9,15,21 * * ?` 与 `web-admin` 的 Quartz（`SYS_JOB`，`STATUS='0'` 为**启用**，其中 `0 0 20`/`0 0 1`/`0 0 2`/`0 30 2`/`0 0 4`/`0 0 10,16` 等为定时式）**会随之一并归位**。判断依据：今天的 UTC 是**当日翻转的异常态**（见上方旁证），而 cron 表达式是按北京时间业务意图写的，故 CST 才是它们本来的口径。

**NEVER 用直接改 `QRCODE_STATUS.GATE_IN_TIME` 的方式绕开**（会污染真实行程数据，且下次部署后问题照旧）。更彻底的做法是把窗口判定改成显式时区比较（`LocalDateTime.now(ZoneId.of("Asia/Shanghai"))`），使其不依赖 JVM 默认时区 —— **本次未做，作为长期项待评估**。
