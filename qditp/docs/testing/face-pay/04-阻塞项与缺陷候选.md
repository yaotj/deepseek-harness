# 04 · 阻塞项与缺陷候选（当面付）

冲突汇总，按影响排序。均来自 2026-09-08 代码实测（`main` @ `8e8b7bd`），矛盾不在本页裁决。

## A. 功能缺失 / 用例无法执行

### A1 STT 完全无接入实现 —— 影响 018 / 019 / 020

`STT` 全仓只有枚举常量与注释共 3 处，无任何业务代码、无 `/itpstt/**` 入口。且**编码口径冲突**：`DeviceTypeEnum.java:48-49` 是 `14`，`BaseRequestDTO.java:9` 注释是 `07`。
待确认：STT 复用 BOM 报文、复用 TVM 报文、还是新建入口。**方向 1 与 2 的支付方向相反**（操作员扫乘客 vs 乘客扫机器），属需求问题不是实现细节。详见 [[03-STT]]。

### A2 ITP 侧无补票金额计算 —— 影响 017 / 020

`ExcessFare` 唯一链路是 **APP 自助补站**（`ticket-server/.../ExcessFareHandler.java:33-242`），BOM/STT 侧无任何 `excessFare` 接口。BOM 与超程的唯一关联是 `requestGenNoCashOrder` 的业务类型字典值 `03`（`BomNoCashOrder.java:22`）。
即金额由 BOM 自己算，ITP 只收单收款。原用例「金额计算正确（超程里程×费率）」应改为「ITP 落库金额 == BOM 界面金额」，或转到 BOM 侧验。

另注：`ExcessFareHandler` 只在 `upgradeAreaType == "02"`（补出站）时算钱（`:119`），其余类型 `trxAmount` 恒 `"0"`（`:131`），`overtimeAmount` 恒 `"0"`（`:107`、`:132`）——APP 自助补站本身也只覆盖补出站一种收费场景。

### A3 扫码取票两套实现并存，同 URL 不同模块 —— 影响 014

- 实现 A：`collect-pay-server`（58101），表 `TVM_APP_ORDER`，**有失败退款**
- 实现 B：`collect-ticket-server`（9098），表 `Ticket_Collect_Info`，**无任何退款代码**

两者的 `/ci/app/requestOrder` 与 `/ci/app/requestPaymentInfo` **URL 完全相同**。执行 014 前必须确认生产路由到哪一个；若两套都在跑，需确认会不会重复下单。
`collect-ticket-server` 的 `CollectPayClient.requestRefund`（`:58`）**全模块无调用点**，`ticketCollectNotify`（`:288-345`）收到出票失败只更新订单不退款。

### A4 BOM 侧未找到失败自动退款 —— 影响 016

TVM 有 `notiTakeTicketFailResult` → 自动退款的完整实现（`TvmOrderServiceImpl.java:570`、`:636-637`、`:653`）。BOM 侧只有 `requestTicketRefund`（`BomOrderController.java:296`，**无任何 javadoc**），未找到 ITP 主动触发的证据。
待确认：BOM 充值/业务失败时退款由谁发起。

## B. 实现风险（建议开发确认）

### B1 `CollectPayController` 整个文件被注释

`collect-pay-server/.../controller/ci/app/CollectPayController.java` 从第 1 行起全被 `//` 注释，含 `@RequestMapping("/ci/app")`（`:25`）、`/requestPay`（`:35`，标 **IF8A-09**）、`/payQuery`（`:44`）、`/requestRefund`（`:53`）、`/refundQuery`（`:62`）。
排查「IF8A-09 打不通」时先看这里，别去翻 `collect-ticket-server` 的同号接口。

### B2 `NoticeAppTask` 非 `@RestController`，`testtbNoticeAppTask` 响应无法解析

`NoticeAppTask` 是 `@Component` + 类级 `@RequestMapping`（`:27-29`）。端点会注册（Spring `isHandler()` 认类级 `@RequestMapping`），三个补偿方法返回 `void` 不受影响；但 `testtbNoticeAppTask`（`:43-50`）返回 `CommonResult` 而类上无 `@ResponseBody`，**不会序列化成 JSON**，`F2FClient` 期望 `RequestApplicationResult`（`rpc/.../f2f/F2FClient.java:60-61`），结果是「方法体已执行、日志已打，调用方判定失败」。
排查 Quartz 任务「报错但实际跑了」时注意这一点。加 `@ResponseBody` 或改 `@RestController` 即可。

### B3 `requestPaymentInfo` javadoc 地址与实际不符

`TvmAppOrderController.java:90` 注释写接口地址是 `/ci/app/requestPayInfo`，实际 `@PostMapping` 是 `/ci/app/requestPaymentInfo`（`:98`）。按注释配 Apifox 会调不通。

### B4 IF2A-07 / IF2A-08 / IF2A-09 编号双义 —— 甲方规格自身缺陷，代码是对的

同一份《技术规范-第9部分》在两个章节各定义了一次这三个编号：

- `IF2A-07`：§7.5 TVM 域 = 充值失败通知（`/ci/tvm/topupCardFailNoti`）；§7.3 BOM 域 = 设备心跳（`/ci/bom/notiDeviceHeard`）
- `IF2A-08`：TVM 域 = 扫码取票订单查询（`/ci/tvm/requestTakeTicketAuth`，接口说明原文只有「预留接口」三字）；BOM 域 = 业务操作结果通知（`/ci/bom/notiBusResult`）
- `IF2A-09`：TVM 域 = 请求充值下单（`/ci/tvm/requestTopup`）；BOM 域 = BOM 上报充值结果通知（`/ci/bom/notiTopupResult`）

`collect-pay-server` 的 `TvmOrderController` 与 `BomOrderController` **两处都与各自章节一致**，不是代码标错。
`IF8A-04/05/06` 同理（§7.3 BOM 域 vs §7.6 APP 域），`AGENTS.md` §2.2.1 已记。

结论不变：用例、Apifox、缺陷单里 **MUST 写「模块 + URL」而非编号**，但归因是规格问题，不要给开发提「编号标错」的缺陷单。


### B5 `cancelTicketCollectOrder` 无独立取消态

`TicketCollectServiceImpl.java:378` 把 `orderStatus` 置回 `0`（未支付）。取消后的订单与从未支付的订单在库里**无法区分**，对账与客诉排查时缺证据。

### B6 `ticketCollectPayNotify` 在事务内发起 RPC

`TicketCollectServiceImpl.java:440` 在 `@Transactional` 方法内调 `notifyPayResultToPayServer`。这正是 `AGENTS.md` §5.2 明令禁止的模式，也是 2026-08-26 生产事故（`PaySignWorkflow.receivePayResult`）的同一形态：行锁持有时长等于对端响应时长，超时后连接被强杀、整个事务连证据一起丢弃。
支付回调是上游会重推的入口，**风险等级与那次事故相同**。

### B7 `paymentVendor="0C"` 硬编码

`PayCenterCommon.java:64`，TVM 拉码场景的支付渠道标识写死。新增渠道需改代码。

## D. ITP 侧不可验的预期（需转设备侧或删除）

原用例里这些断言不在 ITP 可验范围，写在 ITP 测试用例里会永远无法收口：

- 「票卡余额正确增加」（013 / 016 / 019）—— 余额在票卡上，TVM/BOM 写卡完成，ITP 只收结果通知
- 「票卡状态正确更新」（015 / 018）—— 同上
- 「打印业务凭证」（015 / 018）—— BOM/STT 本地行为，ITP 无相关代码
- 「TVM 正常出票，数量与购买一致」（012）—— ITP 能验的是 `actualNum` 与退款差额，实际出票动作在设备侧

## E. 规格逐条核对新增的缺口（2026-09-08 补）

依据《技术规范-第9部分-互联网业务规范》§7.5 TVM 章节与《非现金购票单程票退款功能3.docx》全文逐条比对。**规格有明确要求、代码零实现**的项：

### E1 充值限额未拦截 —— 规格明确、代码无实现

规格原文（§7.5 扫码充值→异常流程）：「充值金额+卡内余额大于1000元，ITP平台返回2004。」

- `RECHARGE_AMOUNT_EXCEED("2004")` 在 `collect-pay-server/.../constant/TvmPayCodeEnum.java:14` **只有定义、全模块零引用**
- `TvmTopupServiceImpl.requestTopup`（`:88-147`）**不读取请求里的 `beforeAmount`（卡内余额）**，无任何限额判断，直接生成订单并调支付中心

后果：可充值到任意金额，超限不拦。

### E2 取票订单锁定未实现 —— 重复出票风险

规格原文（§7.5 扫码取票→异常流程）：「订单已经分配给激活设备，其他取票设备也查下[扫码取票订单查询]，返回订单已经锁定2008，TVM取消交易。」

- `ORDER_LOCKED("2008")` 在 `TvmPayCodeEnum.java` **只有定义、零引用**
- `TvmTakeTicketServiceImpl.requestTakeTicketAuth`（`:100-130`）按 `deviceId + qrcodeGenDate + randomFact` 查订单，**无「该订单已被其他设备激活」的判断**

规格设计这条正是为防多台 TVM 同时出同一笔票。

### E3 「每日批量退款未取票交易」无对应任务

规格原文在 §7.5 出现两次（扫码购票、扫码充值的异常流程）：「如果用户已经支付，ITP平台每日批量退款未取票交易。」

- collect-pay-server 内三处 `@Scheduled` 已注释（`NoticeAppTask.java:55`、`:82`、`:108`）
- 迁到 web-server Quartz 后只有三个**通知类**任务（`TBNoticeAppTask.java:32/41/50/59`：出票结果、出票故障、退款结果通知）
- **没有批量退款任务**

后果：「已支付但二维码超时未取票」的款项当前不会自动退。本节影响面最大的一条。

### E4 BOM `transType` 九个取值中只实现了 `42` 的校验

规格原文（IF8A-04 请求参数 `transType`）九个取值：
`02` 超时更新 · `03` 超程更新/一卡通余额不足更新 · `04` 未出站更新处理 · `05` 无入站更新处理 · `06` 储值票即时退卡/单程票退票 · `22` 充值 · `2A` 黑名单卡锁定 · `2B` 卡锁定解除 · `42` 行政处理

代码侧：

- 仅 `42` 有校验（`BomOrderController.java:101-103`，要求 `adminTransType` 非空），`adminTransType` 规格有 10 个取值 `01`~`0A`
- **其余八个值无任何分支处理**，只作为字典值落库
- 注意 `02` 原文是「**超时**更新」，不是「超程更新」；「超程更新」是 `03`

影响 `../bom-oneside/01-用例.md` Test_023：规格给了 **`05` 无入站更新处理** 这个独立交易类型，属「规格有、代码无」，不是「换名等价于 020/021」。

### E5 单程票退款的 6 处业务规则未按需求实现

依据《非现金购票单程票退款功能3.docx》：

- **R6 故障通知链路被跳过**：文档设计「BOM 发起单程票故障通知 → ITP 按订单号/张数/金额判断 → 生成退款订单 → 向支付平台退款」。BOM 控制器**无故障通知入口**，实际是 `requestTicketRefund` 直接退款，少了 ITP 侧判断环节
- **R5「无订单号=现金购票」语义缺失**：文档要求 `retCode=0000` + `paymentResult=FAILED` + `paymentResultDesc=无订单号`；代码返回 `failMessage("没有查找到出票信息")`（`BomOrderServiceImpl.java:1211-1214`）。BOM **无法区分「现金票不该退」与「查询出错」**
- **R4「发售时间最近的一笔订单」未实现**：`TvmSubTicketMapper.xml:82-94` 只有 `WHERE TRANS_DATE = #{transDate}`，**无 `ORDER BY`、无取一行**，resultMap 是单对象。多笔命中会抛 `TooManyResultsException`，无处理
- **R24 系统异常码不符**：文档要求 `retCode=9999`；`BomOrderResult` 只定义 `0000` 与 `8999`
- **R33 `transType=06` 不校验值**：仅非空校验（`BomOrderController.java:314-316`）
- **R21 支付通道编码无映射**：文档指向「§2.6 支付通道编码定义」，代码直接透传库中 `channel` 原值（`BomOrderServiceImpl.java:1267`）

### E6 退款无幂等 —— 重复退款风险（本页最高优先级）

文档未写此要求，但按 `AGENTS.md` §5.2「涉及支付、订单、扣款的关键业务表 MUST 考虑幂等设计（唯一索引/防重表）」属硬约束：

- `TBL_TICKET_REFUND_RECORD` **无主键、无唯一索引**（`collect-pay-server/sql.txt:311-320`，全字段 `VARCHAR2(100)`）；`TBL_BOM_TICKET_REFUND` 同（`sql.txt:288-297`）
- 落库前**无先查后插**、无 `DuplicateKeyException` 捕获
- `requestTicketRefund` **不校验票卡 `RSV2` 是否已有退款单号**（退款成功后才回写 `RSV2`，`TvmSubTicketMapper.xml:96-100`）

后果：同一 `ticketLogicNum` 重复调用会**重复向支付中心发起退款**。BOM 操作员误触两次、或超时重试即可触发。

### E7 尚未完成的核对

「实现了但与规格不一致」这一类**只完成了部分**。已知待比对的具体数值（规格侧已提取，代码侧未逐个核）：

- 二维码显示时长：规格 **180 秒**
- TVM 轮询查询支付结果间隔：规格 **每 1 秒**
- 接口超时/重试：规格通用 **5 秒 / 最多 3 次**；**BOM 扫码支付特殊：15 秒且明确「不要重试」**
- 设备心跳：规格 **每 1 分钟**
- 代码侧待核配置键：`bom.payTimeOut`（`application.yml:61`）、`bom.payTimeInterval`（`:62`）、`app.retryTimes`（`:46`）

这些是可精确比对、也最容易出偏差的一组，需单独一轮核对后回填。
