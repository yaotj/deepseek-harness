# 当面付 · 链路事实与配置字典

来源：仓库代码实测（2026-09-08，`main` @ `8e8b7bd`）。只记录代码中确实存在的事实。

## 「当面付」的真实对接对象

**不是支付宝开放平台当面付。** 全仓库（含所有 `pom.xml`）检索 `alipay.trade.precreate` / `precreate` / `AlipayClient` / `DefaultAlipayClient` / `alipay-sdk` **零命中**，没有引入支付宝 SDK。

「当面付」只是 `collect-pay-server` 对 TVM/BOM 扫码收款业务的**内部命名**，出现在 6 处注释与类名：`TvmCommonServiceImpl.java:44`、`NoticeAppTask.java:25`、`FacePayOrderPageController.java:25`、`FacePayRefundRequest.java:3`、`FacePayOrderPageView.java:6`、`TvmOrderMapper.java:33`。

实际收款渠道是**支付中心（bestonepay）**，即 `docs/external/支付中心网关接口文档.md` 那一家。

## 二维码生成有两条路径

**路径 A：本地拼收银台 URL（`payType == "0"`，不调支付中心）**
`TvmOrderServiceImpl.java:96-104`：`payUrl = pay-center-jhm-url + "?orderNo=" + orderNo + "&sign=" + sign`，`sign` 来自 `signUtils.getJhmSign(orderNo)`。充值同形：`TvmTopupServiceImpl.java:107-112`。

**路径 B：调支付中心预下单取二维码内容**
`TvmOrderServiceImpl.java:105-131`：`payCenterCommon.buildTvmPayRequest(...)` → `payCenterService.callPayCenter(pay-center-pay-url, ...)`，从响应 `data.data` 取 `payUrl`（`:124`），写回 `URL` 字段返回设备（`:128-130`）。充值：`TvmTopupServiceImpl.java:130-136`。

`payUrl` 的语义在 `TvmOrderResult.java:26` 写明：**「二维码信息（支付URL），TVM 把整个字段显示为二维码」**——设备只负责把字符串画成码，不做解析。

**测试影响**：`payType` 决定走哪条路径，两条路径的失败模式完全不同（A 不产生支付中心订单，B 会）。执行前必须确认设备传的 `payType`。

## 支付场景 `scene` 三值

`PayCenterCommon.java`：

- `scene="qrcode"` + `paymentVendor="0C"` 硬编码（`:63-64`）——TVM 拉码，用户扫机器
- `scene="scan"` + `authCode`（`:95`、`:103`）——主动扫用户付款码
- `scene="app"`（`:127`）——APP 支付

请求体 `bizData` 为 Base64(JSON)，签名走 `SignUtils.signRequest`。

## 设备类型是 `providerId`，不是 `deviceType`

取值注释在 `collect-pay-server/.../model/request/BaseRequestDTO.java:9`：
`01` 青岛地铁APP / `02` TVM / `03` BOM / `04` AGM / `05` ACC / `06` ITP / `07` STT。

但**代码里真正参与分支判断的只有 `"03"`（BOM）**，三处：`TvmOrderController.java:78`（→ `createBomSaleOrder`）、`:169`（→ `bomOrderService.notiTakeTicketResult`）、`:188`（→ `bomOrderService.notiTakeTicketFailResult`）。

设备区分主要靠 **URL 前缀**：`/itptvm/ci/tvm/**`、`/itpbom/ci/bom/**`、`/ci/app/**`。

> ⚠️ 矛盾：`model/.../enums/DeviceTypeEnum.java:48-49` 定义 `STT("14", "STT")`，与 `BaseRequestDTO.java:9` 注释里的 `07` **不是同一个值**。两套设备编码并存，`DeviceTypeEnum.STT` 全仓无任何引用点。接 STT 前必须先定编码口径。

## 订单状态取值

**collect-ticket-server**（APP 扫码取票）`TicketCollectServiceImpl.java:51-62`，全部是 `int` 常量而非枚举：

- `ORDER_STATUS_UNPAID=0`、`ORDER_STATUS_PAID=100`；另有 `99` 硬编码在 `:241` 表示二维码超时
- `COLLECT_STATUS_NOT_COLLECTED=0`、`COLLECT_STATUS_SUCCESS=100`
- `PAY_RESULT_UNPAID=0`、`PAY_RESULT_PROCESSING=1`、`PAY_RESULT_SUCCESS=100`
- `QRCODE_EXPIRE_SECONDS=300`（5 分钟）、`ERROR_CODE_QRCODE_EXPIRED="2101"`

表：`Ticket_Collect_Info`（主订单）、`Ticket_Collect_Logs`、`Ticket_Collect_Log_Detail`（票明细）。

> ⚠️ `cancelTicketCollectOrder`（`:378`）把 `orderStatus` 置回 `0`（未支付），**没有独立的「已取消」状态**。取消后的订单与从未支付的订单在库里无法区分。

**collect-pay-server** TVM 侧表：`TVM_APP_ORDER`（`TvmAppOrder`，字段 `payStatus` / `activateFlag`）、`TvmMainTicket` / `TvmSubTicket`（出票故障记录）、BOM 侧 `BomNoCashOrder`。

## 补偿任务：已从模块内 `@Scheduled` 迁到 web-server Quartz

`collect-pay-server/.../task/NoticeAppTask.java` 三处 `@Scheduled` **被注释**（`:55`、`:82`、`:108`），但这不等于补偿失效——它改由 web-server 的 Quartz 任务经 HTTP 触发：

`web-server/web-admin/.../quartz/task/TBNoticeAppTask.java:32/41/50/59` → `rpc/.../f2f/F2FClient.java:61/68/75/82` → `POST pay/noticeAppTask/{testtbNoticeAppTask|noticeTakeTicketTask|noticeTakeTicketFailureTask|noticeRefundTask}`，地址键 `service.f2f.url`。

`NoticeAppTask` 是 `@Component` + 类级 `@RequestMapping("/pay/noticeAppTask")`（`:27-29`）。Spring 的 `RequestMappingHandlerMapping.isHandler()` 认类级 `@RequestMapping`，所以这些端点**确实会注册**。

> ⚠️ 但该类不是 `@RestController`、方法上也没有 `@ResponseBody`。三个补偿方法返回 `void`，不受影响；`testtbNoticeAppTask`（`:43-50`）返回 `CommonResult`，**不会被序列化成 JSON**，会走视图解析。`F2FClient` 期望 `RequestApplicationResult`，因此「方法体已执行、日志已打，但调用方判定失败」。

判断任务是否真的在跑 **MUST 查 `SYS_JOB_LOG`**：Quartz 用内存 JobStore，`QRTZ_JOB_DETAILS` / `QRTZ_TRIGGERS` 恒为 0 行（见 `AGENTS.md` §8）。

历史 cron（`doTime.noticeTakeTicketTask=*/5 * * * * ?`、`doTime.noticeRefundTask=*/2 * * * * ?`，即 5 秒 / 2 秒）**已不生效**，现由后台 `sys_job` 配置。`docs/ops/生产环境清单.md:203-204` 仍按旧 cron 记录，与代码现状不一致。

## 已被整体注释掉的接口

`collect-pay-server/.../controller/ci/app/CollectPayController.java` **整个文件从第 1 行起被 `//` 注释**，其中 `@RequestMapping("/ci/app")`（`:25`）、`/requestPay`（`:35`，标 IF8A-09）、`/payQuery`（`:44`）、`/requestRefund`（`:53`）、`/refundQuery`（`:62`）**全部不生效**。排查「IF8A-09 打不通」时先看这里。

`config/PayCenterProperties.java:11` 前缀 `pay.center`：`merchantNo` / `apiVersion` / `signType` / `charset` / `gatewayUrl` / `privateKey` / `paycenterPublicKey` / `callbackUrl` / `payCenterPayUrl` / `payCenterQueryUrl` / `payCenterRefundUrl` / `payCenterJhmUrl` / `queryRefundUrl`。

`collect-pay-server/src/main/resources/application.yml` 的问题（只列键名与位置，不回显值）：

- ⚠️ `pay.center.private-key`（`:25`）与 `jhm.key`（`:52`）是**硬编码明文**，未按 `${ENV_VAR:}` 外置，违反 `AGENTS.md` §5.2
