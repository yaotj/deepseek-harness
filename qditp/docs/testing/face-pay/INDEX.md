## 用例可执行性一览

- Payment_012 TVM 扫码购票：可测。重点是**部分出票的差额退款**（`refundNum = buyNum - actualNum`）
- Payment_013 TVM 扫码充值：可测通知与退款；⚠️「票卡余额增加」不在 ITP 可验范围
- Payment_014 TVM 扫码取票：⚠️ **先确认走哪套实现** — collect-pay-server（有退款）还是 collect-ticket-server（无退款），两者 URL 相同
- Payment_015 BOM 非现金收款：可测收单收款；⚠️「票卡状态更新」「打印凭证」不可验
- Payment_016 BOM 扫码充值：可测；⚠️ BOM 侧未找到 ITP 主动发起的失败退款
- Payment_017 BOM 补票-超程：⚠️ **金额计算段阻塞** — ITP 无补票计算，金额由 BOM 传入
- Payment_018 STT 非现金收款：⚠️ 阻塞 — STT 无接入实现
- Payment_019 STT 扫码充值：⚠️ 阻塞 — 同上
- Payment_020 STT 补票-超程：⚠️ 双重阻塞 — 无 STT 接入 + 无补票计算

## 三条最需要先确认的事

1. **STT 怎么落地**（影响 3 个用例）：复用 BOM 报文、复用 TVM 报文、还是新建入口。前两者的**支付方向相反**（操作员扫乘客 vs 乘客扫机器），是需求问题。且编码口径冲突：`DeviceTypeEnum` 是 `14`，`BaseRequestDTO` 注释是 `07`
2. **扫码取票走哪套实现**（影响 014）：两套并存、URL 相同、一套有退款一套没有
3. **补票金额算在哪一侧**（影响 017 / 020）：ITP 侧只有 APP 自助补站的计算，BOM/STT 无

## 一句话结论

「当面付」是内部命名，**对接的是支付中心（bestonepay），不是支付宝开放平台当面付**——全仓无支付宝 SDK、无 `precreate`。TVM/BOM 链路基本完整且 TVM 有失败自动退款；STT 完全没做；补票金额不由 ITP 算。
