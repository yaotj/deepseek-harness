# 01 · 参数管理（ACLC_ACC_Test_001~002）

## 定义

ACC 发布参数文件，ITP 侧由 `para-server`（9107）解析入库并按版本号生效，其他模块通过 `rpc` 的 `ParaClient` 读取。

## 链路事实

> ⚠️ 本节 2026-09-08 重写。此前记录的「无 FTP、无定时任务、只能人工放文件」已**不再成立**——FTP 拉取与 Quartz 定时任务已实现并在 `para-server:2.0.17` 上实测通过。下方保留原判断的时间戳以便对照历史结论。

**导入入口共 5 个**（`ParaImportController`，`@RequestMapping("/para/import")`）：

| 入口 | 用途 | 触发方 |
|---|---|---|
| `POST /para/import/ftp`（`:49-52`） | 扫 FTP 目录、按版本预筛、下载并解析入库，返回 `FtpScanResponse` 逐文件明细 | 人工 / 联调 |
| `POST /para/import/ftp/quartz`（`:58-72`） | 同一动作，返回 `CommonResult`（`0000` 全成功 / `9999` 有失败） | web-admin Quartz |
| `POST /para/import/directory`（`:74-77`） | 请求体 `{"directory":"..."}`，导入容器本地目录 | 人工兜底 |
| `GET /para/import/directory?directory=...`（`:79-82`） | 同上，GET 形态 | 人工兜底 |
| `POST /para/import/file`（`:84-110`） | multipart 单文件上传 | 人工兜底 |

**FTP 拉取链路**（`ParaFtpScanService`）：`connect()` → `changeWorkingDirectory(remoteDir)` → `findCandidates()` 按**文件名版本号**粗筛 → 下载到 `Files.createTempDirectory("para-ftp-")` → `ParaFileImportService.importLocalFile()` 按**版本号 + 全文 MD5** 单点裁决 → `finally` 删临时文件与目录。被动模式、二进制、UTF-8 控制编码，超时取自 `para.ftp.connect-timeout-millis` / `para.ftp.data-timeout-millis`。

**入库判据是「版本号 + MD5」**（2026-09-08 由「仅版本号」改成本形态，`para-server:2.0.18`）：

- 库中无该 paraType，或文件版本号更高 → 导入
- 文件版本号更低 → 跳过（版本回退不处理）
- 版本号相同：MD5 不同 → 导入；MD5 相同 → 跳过；库中 MD5 为空 → 导入（顺带补齐 MD5）

MD5 = `ParaFileReadUtils.md5Hex(bytes, 0, len-16)`，即「除尾部 16 字节校验值外的全文」，与 `TBL_PARA_VERSION.MD5_VALUE` 同源。

⚠️ **FTP 侧拿不到 MD5**（FTP LIST 无此信息），所以「版本号相同」的文件**也会被下载**，MD5 在下载后才判。代价是每轮固定下载 `0001` + `0004`（约 500KB）；收益是同版本号换内容能被发现。裁决只在 `ParaFileImportService` 一处，`/ftp` 与 `/directory` 两条路径判据一致。

**定时任务在 web-admin，不在 para-server**：`web-server/web-admin/.../quartz/task/ParaQuartzTask.java` 的 `scanFtpPara()` → `rpc/.../para/ParaClient.quartzScanFtpPara()` → `POST /para/import/ftp/quartz`。`retCode != 0000` 抛 `IllegalStateException`，Quartz 记为失败。para-server 本模块**仍然 0 处 `@Scheduled`**（这一点未变，符合项目约定）。

⚠️ **`sys_job` 记录尚未创建**：`paraQuartzTask.scanFtpPara()` 需要运维在管理后台新增定时任务才会跑。执行「自动同步」相关用例前 **MUST** 先确认该记录存在及其 cron。

**配置**（`para-server/src/main/resources/application.properties`，前缀 `para.ftp.*`）：

```properties
para.ftp.ip=${PARA_FTP_IP:172.20.214.101}
para.ftp.port=${PARA_FTP_PORT:21}
para.ftp.username=${PARA_FTP_USERNAME:}
para.ftp.password=${PARA_FTP_PASSWORD:}
para.ftp.remote-dir=${PARA_FTP_REMOTE_DIR:/parameter/cur/}
para.ftp.connect-timeout-millis=10000
para.ftp.data-timeout-millis=60000
```

⚠️ 前缀是 `para.ftp.*` / `PARA_FTP_*`，**与 acc-es-server 的 `ftp.*` / `FTP_*` 是两台不同的 FTP 服务器**，测试时别把凭据配串。

⚠️ **真实远端目录是 `/parameter/cur/`**（2026-09-08 实测）。甲方口述的 `/parameter/cur/97000000/` 在 FTP 上不存在，`CWD` 会被拒。

⚠️ **FTP 侧文件名正则只认 `0001` / `0004`**：`^PRM\.(0001|0004)\.(\d{4})\.(\d{6})(?:\.\d+)?$`（`ParaFtpScanService.java:40`）。而 `ParaFileImportService` 支持 `0001`~`0004`。`0002`（日历）/`0003`（票卡）已实测能正常解析入库，但**走 FTP 路径时会被正则挡掉**，只能用 `/para/import/directory|file` 导。这是待业务确认项。

`/para/import/file` 上传文件落到 `Files.createTempDirectory("para-import-")`，导入后删除（`:89`、`:152-159`）。

文件格式、`paraType` 四类、`PRM.` 前缀约束、`TBL_PARA_VERSION`、热生效机制均见 [[00-链路事实与配置字典]]。

### 用例 T002-3 新版本参数下载并入库（核心用例）

已实测通过（2026-09-08 13:11，`para-server:2.0.17`）。

造数方式：把 `TBL_PARA_VERSION.CURRENT_VER_NO` 回退到**表内实际存在的历史版本**，而不是随便减一。
⚠️ **别用「当前版本减 1」**：实测 `TBL_LINE_INFO` 只有 28 / 41 两个版本，`TBL_FARE_MATRIX` 只有 33 / 44，**40 和 43 都不存在**。指向一个没有明细数据的版本号，等价于把参数清空（下游子查询命中 0 行），和直接删版本行一样危险。正确目标是上一个真实存在的版本。

```sql
UPDATE TBL_PARA_VERSION SET CURRENT_VER_NO = 28 WHERE PARA_TYPE = '0001'
UPDATE TBL_PARA_VERSION SET CURRENT_VER_NO = 33 WHERE PARA_TYPE = '0004'
```

执行 `POST /para/import/ftp`，实际响应（HTTP 200，5.58s）：

```json
{"remoteDir":"/parameter/cur/","total":2,"downloaded":2,"imported":2,"skipped":0,"failed":0,
 "files":[{"fileName":"PRM.0001.9900.000041.02000000","paraType":"0001","fileVerNo":41,"currentVerNo":28,"success":true,"downloaded":true,"imported":true,"message":"导入成功"},
          {"fileName":"PRM.0004.9900.000044.02000000","paraType":"0004","fileVerNo":44,"currentVerNo":33,"success":true,"downloaded":true,"imported":true,"message":"导入成功"}]}
```

落库核对（导入前 → 导入后）：

- `TBL_PARA_VERSION`：`0001` 28 → **41**、`0004` 33 → **44**，`LAST_UPD_TMS` 13:11:41 / 13:11:46
- `TBL_LINE_INFO`：版本 41 共 8 行（历史版本 28 的 8 行仍在）
- `TBL_STATION_INFO`：版本 41 共 205 行（版本 28 的 189 行仍在）
- `TBL_FARE_MATRIX`：版本 44 共 41616 行（版本 33 的 35723 行仍在）

再次调 `/para/import/ftp` → `imported=0 / skipped=2`（2.0.17 当时的形态是 `total=0`，2.0.18 起改为下载后比 MD5）。幂等成立。

⚠️ **附带发现：`0001` 的 `CURRENT_FILE_NAME` 与 `MD5_VALUE` 都变了**——导入前是 `PRM.0001.9900.000041`（**4 段**）+ MD5 `73a787ca…`，导入后是 `PRM.0001.9900.000041.02000000`（**5 段**）+ MD5 `3cb3b5b3…`。说明库里原本那条版本 41 的记录**来自另一个物理文件**（4 段命名、内容不同），与当前 FTP 上的 5 段文件同版本号但不同内容。`0004` 的 MD5 前后一致（`830c76b1…`），只有 `0001` 有这个问题。
**这个发现直接催生了判据变更**：2.0.17 及更早只比版本号，同版本换内容会被永久跳过、两份数据无法收敛；2.0.18 起判据是「版本号 + MD5」，该场景可被发现并导入（见 T002-3b）。仍需与 ACC 确认 4 段命名是历史遗留还是仍在使用、同版本号不同内容是否属其发布缺陷。

结果：☑ 通过

### 用例 T002-3b 同版本号但内容变更 → 触发导入（MD5 判据）

已实测通过（2026-09-08 13:25，`para-server:2.0.18`）。这条是「版本号 + MD5」判据的核心验收点，旧版（仅比版本号）**必然失败**。

造数（改一个字段，可自愈，无需人工还原）：

```sql
UPDATE TBL_PARA_VERSION SET MD5_VALUE = '00000000000000000000000000000000' WHERE PARA_TYPE = '0001'
```


### 不可测的部分

⚠️ **「同步失败时自动回滚至上一版本」不成立**。没有任何按 `PARA_TYPE` 把 `CURRENT_VER_NO` 改回旧值的代码，`ParaVersionMapper` 只有 `selectByParaType` 与 `upsert`，无 `rollback`/`downgrade`/`revert`。代码里的「回滚」只有一层含义：**当前导入事务失败则不生效**，当前版本仍停在导入前的值（即 T002-5）。这与「回滚至上一版本」语义接近但不等同——若 v2 导入成功后才发现数据有问题，**没有任何接口能退回 v1**（历史明细还在表里，但指针无法后移）。

⚠️ **「参数同步日志记录完整」不成立**。全仓库 grep `IMPORT_LOG|PARA_IMPORT` 零命中，`para-schema.sql` 无导入流水表。FTP 扫描结果只作为 HTTP 响应体返回（`FtpScanResponse` / `FtpFileResult`），**不落库**。响应一丢就查不到历史，只能翻应用日志（`scripts/klog.sh para-server FTP 200`）。定时任务场景下**没有任何人看响应体**，这一条的影响比人工触发时大。

⚠️ **`0002` / `0003` 走不通 FTP 路径**：`ParaFtpScanService` 的正则只认 `0001` / `0004`，但解析层支持四类。日历与票卡参数目前只能人工走 `/para/import/directory`。是否放开需业务确认。

## 矛盾/待验证

- ~~手册假设「定时 + FTP + 自动同步」，代码是「人工触发 HTTP 导入」~~ → **2026-09-08 已闭合**：FTP + web-admin Quartz 已实现并实测。**2026-09-09 `sys_job` 记录亦已创建并跑通**（T002-8），⚠️ 具体 cron 表达式待补录。
- ⚠️ 「回滚至上一版本」需明确定义：是事务级不生效，还是可主动退回旧版本号。
- ⚠️ **`0001` 同版本号存在两份不同内容的文件**（4 段命名 MD5 `73a787ca…` vs 5 段命名 MD5 `3cb3b5b3…`，车站数 189 vs 205）。判据已改成「版本号 + MD5」能发现该情况，但**哪一份才是正确数据仍需业务裁决**。
- ⚠️ **每轮固定下载 `0001` + `0004` 约 500KB**：MD5 判据必须先拿到文件内容，FTP LIST 给不了 MD5。若后续 cron 加密或参数文件变大，需评估带宽与 FTP 侧压力；ACC 若能提供校验值清单（如同目录 `.md5` 文件或 FTP `XMD5` 命令），可退回「不下载即判定」。
- ⚠️ `0002` / `0003` 是否纳入 FTP 扫描（`ParaFtpScanService` 正则只认 `0001`/`0004`，解析层支持四类）。
- ⚠️ ACC 下发 `PRM.0005`~`PRM.0203` 共 16 个类型，ITP 是否需要解析入库。
- ⚠️ `/parameter/cur/97000000/` 这一层是否为规划中的目录（2026-09-08 实测不存在）。
- ⚠️ **`/para/import/**` 全部无鉴权**：5 个入口都是裸 POST/GET，任何网络可达方都能触发全量参数重导。按 `AGENTS.md` §5.2「新增状态变更型接口 MUST 有鉴权」这是一处偏离，需确认是靠 NetworkPolicy / Service 不暴露来兜底，还是要补验签。
- ⚠️ **旧版本明细数据永不清理**：`deleteByParaVerNo` 只删同版本，历史版本行一直堆积在 `TBL_LINE_INFO` 等表里。费率单版本 41616 行，长期累积后需要归档策略。
- `requestLineStationCodeVersion` 把线路与车站版本号返回同一个值（`AppParaServiceImpl.java:136-153`），APP 若按两者独立判断刷新会有偏差，需确认是否符合接口规范。
