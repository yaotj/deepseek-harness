# 03 · 阻塞项与缺陷候选（ITP-ACC）

冲突汇总，按影响排序。基线来自 2026-09-07 代码实测（`8e8b7bd`）；参数域（A2/A3）已按 2026-09-08 的 FTP + Quartz 上线实测更新，矛盾不在本页裁决。

## A. 功能缺失（用例无法执行）

### A1 ~~逻辑卡号文件链路整体缺失~~ 已闭合，方案改为 card-pool-server

**2026-09-15 事实基线变更**：以下旧结论针对的是「ACC 通过 FTP 下发 `ESLOGIC.日期.序号` 文件 → acc-es-server 下载解析 → 导入卡池」这条设想链路（甲方规格 `docs/接口规范文档/ACC与ITP之间的文件.docx` 原始设计），该方案已废弃。**实际落地的是 `card-pool-server` 新模块**（9111 端口），链路完全不同：IF7B-01 直连 ACC 申请卡号批次 → FTP 下载 ACC 生成的卡号文件 → 入库 `LOGIC_CARD_POOL_CARD`。调度由 web-admin Quartz `sys_job` job_id=107（**现为 240「卡池数据导入」**，2026-09-21 改名改号）每 5 分钟触发 `maintenance`。详见 `docs/business/card-pool.md`。

> 以下为旧结论存档，**不再代表现状**：

- `ESLOGIC` 全仓零命中（含文件名检索）
- 无 `LOGIC_CARD` / `CARD_POOL` 表；`CARD_POOL_*.txt` 只是 `CardPoolServiceImpl.java:73` 拼出来的文件名字符串，`handleFileNotice`（`:91-96`）整体是 TODO + 两行 log
- `acc-es-server` 无任何 `@Scheduled`，其 FTP 只传编码设备任务与报告文件
- 待确认：本期是否要做？还是方案已改为加密机 IF7B 实时取号（`acc-secure-server` 有出向入口但未接线）。两条路线的取号主体完全不同，用例需按定下的方向重写

### A2 ~~参数下载无 FTP、无定时~~ 已闭合，遗留 `sys_job` 未创建 —— 影响 Test_001 / Test_002

**2026-09-08 更新**：原判断（2026-09-07 `8e8b7bd`）已失效。FTP 拉取与定时任务已实现并在 `para-server:2.0.17` 实测通过：

- `ParaFtpScanService` + `ParaFtpProperties`（`para.ftp.*` 前缀），远端目录 `/parameter/cur/`
- `POST /para/import/ftp`（人工）与 `POST /para/import/ftp/quartz`（Quartz，`0000`/`9999`）
- 定时在 web-admin：`paraQuartzTask.scanFtpPara()` → `ParaClient.quartzScanFtpPara()`
- para-server 本模块**仍是 0 处 `@Scheduled`**，符合项目约定

遗留阻塞：

- ⚠️ **`sys_job` 记录未创建**，定时任务实际不会跑，需运维在管理后台新增并定 cron
- ⚠️ **`PARA_SERVICE_URL` 需在 web-admin 注入**，默认值 `127.0.0.1:9107` 在分 Pod 部署下不可达（属 `AGENTS.md` §8「`service.*.url` 键值错配」同类风险，本项键存在但默认值是回环）
- ⚠️ **`0002` / `0003` 走不通 FTP**：`ParaFtpScanService.java:40` 正则只认 `0001`/`0004`，解析层支持四类。日历与票卡参数只能人工走 `/para/import/directory`，需业务确认是否放开
- ⚠️ **核心用例 T002-3 无法执行**：FTP 上 `0001`=41、`0004`=44 与库中版本一致，没有更高版本文件可测「新版本下载并入库」

### A2b `/para/import/**` 全部无鉴权 —— 新增

5 个入口（`/ftp`、`/ftp/quartz`、`/directory` ×2、`/file`）都是裸 POST/GET，无验签、无 IP 白名单。任何网络可达方都能触发全量参数重导；`/directory` 还接受任意路径参数，等于允许读取容器内任意目录下的 `PRM.*` 文件。
按 `AGENTS.md` §5.2「新增状态变更型接口 MUST 有鉴权与归属校验」这是偏离。待确认：是靠 NetworkPolicy / Service 不对外暴露兜底，还是要补 `ItpRequestSignVerifier` 同构验签。

### A3 无参数导入日志表 —— 影响 Test_002 预期 4

grep `IMPORT_LOG|PARA_IMPORT` 零命中，`para-schema.sql` 无导入流水表。导入结果只在 HTTP 响应体里（`FtpScanResponse` / `DirectoryImportResponse`），不落库，响应一丢只能翻应用日志。「日志记录完整」无法验证。

**FTP + 定时上线后此项影响放大**：定时任务场景下**没有任何人看响应体**，`ParaQuartzTask` 只把汇总串塞进 `retMsg` 打一行 log，逐文件明细完全丢失。排查只能靠 `scripts/klog.sh para-server FTP 200`，而容器日志有滚动上限。

### A3b `total=0` 的两种含义无法从响应区分 —— 新增

`FtpScanResponse.total` 只统计通过版本预筛的候选，被版本短路的文件既不计入 `total` 也不计入 `skipped`。因此「库里已是最新」与「文件名一个都没匹配上」**响应体完全相同**（`total=0`，`files=[]`），只能靠日志区分（前者打「参数文件版本未升高, 跳过: ...」，后者一行都不打）。
这个歧义曾直接导致同事版本的正则缺陷难以发现——`(\d{6})$` 收尾时一个真实文件都匹配不上，但接口照样返回 200 且 `total=0`，看起来像「没有新参数」。建议在 `FtpScanResponse` 增加 `matchedButNotNewer` 计数。

### A3c ~~`0001` 存在「同版本号不同内容」的两份文件~~ 判据已修复，ACC 侧成因待确认

2026-09-08 T002-3 实测发现：库里原本的 `0001` 版本 41 记录是 `CURRENT_FILE_NAME=PRM.0001.9900.000041`（**4 段命名**）、`MD5_VALUE=73a787ca…`；而 FTP 上当前的同版本文件是 `PRM.0001.9900.000041.02000000`（**5 段命名**）、MD5 `3cb3b5b3…`。两者**版本号相同、内容不同**（车站数 189 vs 205）。

**已修复（2.0.18）**：入库判据从「仅版本号」改成「版本号 + MD5」，同版本换内容现在可被发现并导入。`ParaFileImportService.importLocalFile` 是唯一裁决点；FTP 侧因拿不到 MD5，等版本文件也会下载后再判（T002-1 / T002-3b 已实测两个分支）。
代价：每轮固定下载 `0001` + `0004` 约 500KB。`0004` 无此问题（MD5 前后一致）。

仍待确认（ACC 侧）：4 段命名是历史遗留还是仍在使用；同版本号发布不同内容是否属其发布缺陷。若属缺陷，我方判据已能兜住，但**数据到底该以哪一份为准仍需业务裁决**。

### A3b ~~`total=0` 的两种含义无法从响应区分~~ 已消除

原问题：`FtpScanResponse.total` 只统计通过版本预筛的候选，「库里已是最新」与「文件名一个都没匹配上」响应体完全相同（`total=0`），只能靠日志区分。这个歧义曾让同事版本的正则缺陷难以发现——`(\d{6})$` 收尾时一个真实文件都匹配不上，接口照样返回 200 且 `total=0`，看起来像「没有新参数」。

**2.0.18 起消除**：等版本文件进入候选并下载，「库里已是最新」的响应是 `total=2 / downloaded=2 / imported=0 / skipped=2`，每条 `files[].message` 带实际 MD5；`total=0` 现在**只**意味着文件名没匹配上。原建议的 `matchedButNotNewer` 计数字段不再需要。

⚠️ 回归提醒：按旧版预期断言 `total=0` 的测试脚本 / Apifox 用例**会误判成失败**，需同步改成 `imported=0 && skipped=total`。

### A4 无「回滚至上一版本」能力 —— 影响 Test_002 预期 3

`ParaVersionMapper` 只有 `selectByParaType` 与 `upsert`，无降级方法。代码里的回滚只是**当前导入事务失败则不生效**；v2 导入成功后若发现数据有问题，**没有接口能把 `CURRENT_VER_NO` 退回 v1**（历史数据仍在表里，指针无法后移）。
待确认：「自动回滚」的准确语义。若需要真回退，实现成本很低（`upsert` 已具备），但要定义谁有权触发。

## B. 配置与实现风险（建议开发/运维确认）

### B1 `account.card-pool.debug-manual-allocate=true` 默认开启 —— 优先级最高

`account-server/src/main/resources/application.properties:39`。开启时 `allocateTicketNo`（`AccountApplicationServiceImpl.java:673-682`）**直接用时间戳造卡号，完全不访问数据库**，卡池表形同虚设。
影响：任何针对卡池的测试在开关未关闭前都测的是假路径。**执行 Test_003 降级项前必须先确认该值的生效值。**
另有 `:40 account.card-pool.debug-manual-card-id=9900000000000001`。

### B2 卡池补池卡号本地伪造

`CardPoolServiceImpl.java:104-108` `buildCardId()` = `"QD" + yyMMdd + HHmmss + %06d(AtomicInteger)`，`:70` 留着 `// TODO 对接 Ticket/ACC 卡号申请接口`。
唯一性只靠 `updateAllocateCard` 的 `where THIRD_USER_ID is null` 乐观占用（`UserAccTicketNoMapper.xml`），未见唯一索引级保证。多实例部署时 `AtomicInteger` 是进程内计数器，同秒并发有撞号风险，值得压测。

### B3 `service.security.url = http://127.0.0.1:9012`

`account-server/src/main/resources/application.properties:26`。HCE 卡（`cardType` `03`/`04`）取号依赖该地址，回环地址在分 Pod 部署下不可达。对照 `AGENTS.md` §8 关于 `service.*.url` 配置的约束，请与运维核对目标环境。

### B4 acc-es-server FTP 配置存在环境问题

- `ftp.port=21` 是硬编码字面量，未走 `${ENV:}`（`acc-es-server/src/main/resources/application.properties:27-35`）
- `ftp.report-local-dir` / `ftp.excel-dir` / `ftp.custom-local-dir` 三项值是 **Windows 本地路径形态**，Linux 容器内不可用
- 按 `AGENTS.md` §8 要求，这类环境问题应追加到 `docs/ops/生产环境清单.md`

### B5 acc-es-server 内有两处死代码

- 自研 `util/FTP.java:16-372`（commons-net 版）全仓无引用；实际用的是 Hutool `cn.hutool.extra.ftp.Ftp`（3 处实例化：`EsReportServiceImpl.java:98`、`:236`，`EsTaskServiceImpl.java:369`）
- `netty/model/Constant.java:8-17` 定义的 `FILE_FOLDER="/UPLOAD"`、`FILE_NAME_TASK_PREFIX="9050"`、`FILE_NAME_CUSTOM_PREFIX="9060"`、`FILE_NAME_CUSTOM_REPORT_PREFIX="9061"` 全仓无引用；实际用的是 `EsTaskServiceImpl` 里的 `"9060"` 字面量与 `9050` 字面量（`:228/240/251/262/276/286`）

风险：改文件名规则时容易改到常量而漏掉字面量，改完不生效。

### B6 `requestLineStationCodeVersion` 线路与车站共用一个版本号

`AppParaServiceImpl.java:136-153` 读 `0001` 行，把同一个 `CURRENT_VER_NO` 同时作为线路版本与车站版本返回。若 APP 按两者独立判断刷新，行为会与接口规范预期不符，需核对甲方接口文档。

### B7 `fep-dev-server` 取参数失败静默降级

`GateTransactionHandler.java:305` 调 `ParaClient` 查车站线路信息，失败只 `log.warn` 并返回 null（`:306-307`）。参数服务不可用时闸机交易链路不会报错，而是带着空车站信息继续，排查时容易误判。
