# 02 · 逻辑卡号获取（ACLC_ACC_Test_003）

## 结论先行

> **2026-09-15 事实基线变更**：以下「完全不可执行」的结论针对的是「ACC 通过 FTP 下发 `ESLOGIC.日期.序号` 文件 → 下载解析 → 导入卡池」这条设想链路，该方案已废弃。**实际落地的是 `card-pool-server` 新模块**（9111），链路：IF7B-01 直连 ACC 申请批次 → FTP 下载卡号文件 → 入库卡池 → 卡号预占。详见 `docs/business/card-pool.md` 与本文末尾「事实基线变更」章节。

⚠️ **本用例当前完全不可执行**。手册描述的链路（ACC_FTP 目录 → `ESLOGIC.日期.序号` 文件 → 下载解析 → 导入卡池）在仓库中**没有任何一环存在**。现网开户用的卡号来自本地伪造或加密机接口，不来自 ACC 文件。

`AGENTS.md` §2.2.2 已记录同一事实：「ACC 对账与逻辑卡号文件：无对账代码；`acc-es-server` 的 FTP 仅传输编码设备任务与报告文件」。

## 逐项取证

**`ESLOGIC` 全仓零命中**（不分大小写，含 `.java/.xml/.properties/.sql/.md`），文件名层面 `-iname "*eslogic*"` 也零命中。解析 `ESLOGIC.日期.序号` 并导入卡池的代码：未找到。

仓库内唯一「按文件名下载并解析入库」的实现是 `acc-es-server` 的编码设备报告文件（定长逐行解析），与逻辑卡号无关，见 [[00-链路事实与配置字典]]。

**无 `LOGIC_CARD` / `CARD_POOL` 表**。`CARD_POOL` 唯一出现是拼接的文件名字符串：
`CardPoolServiceImpl.java:73` `"CARD_POOL_" + yyyyMMddHHmmss + ".txt"`，`:74` `filePath = "/download/cardPool"`
——**只写日志，不落库、不下载**。同类 `handleFileNotice`（`:91-96`）整体是 TODO 加两行 log。

**acc-es-server 无任何 `@Scheduled` / `@EnableScheduling`**（全模块 grep 零命中）。其 FTP 传输全部由请求或报文驱动：下载由 Netty `7004` 报告触发（`NettyServerHandler.java:45-47` → `BusinessHandler.taskStatReport` → `EsTaskServiceImpl.report` → `analysisFile`），上传由 HTTP 触发（`EsAssignController.java:30` → `EsAssignServiceImpl.java:82` → `EsTaskServiceImpl.customFile`，标 `@Async`）。定时扫 FTP 目录：未找到。

## 现网卡号的真实来源

`allocateCard` 按卡类型两分叉（`AccountApplicationServiceImpl.java:695-701`）：

**分叉 A：HCE 卡（`cardType` = `03` / `04`）→ 加密机**

- 判定 `isHceCard`：`"03".equals(trim) || "04".equals(trim)`（`:709-711`）
- 取号 `requestHceCardData`（`:724-736`）：调 `securityClient.requestHceCardData`，`iptUserId = "000000" + %08X(thirdUserId)`（`:727`、`:744-747`）；**卡号 = 响应的 `logicNum`**（`:735`）
- 校验 `retCode == "200"` 且 `logicNum`、`hceData` 均非空，否则返回 `null`（`:730-734`）
- 远端：`POST /ci/itp/requestHceCardData`（`rpc/.../SecurityClient.java:128-129`），地址键 `service.security.url`
- ⚠️ `account-server/src/main/resources/application.properties:26` 当前值是 `http://127.0.0.1:9012`——同机回环地址，K8s 分 Pod 部署时不可达，需与运维确认

**分叉 B：其他卡类型 → 本地表 `User_ACC_TicketNo`**

- `:699` → `allocateTicketNo`（`:669-683`）
- ⚠️ **该方法先看调试开关**：`debugManualAllocate` 为 true 时**直接用时间戳造号返回，完全不碰数据库**（`:673-682`，`String.format("%014d%02d", ...)`）。而 `application.properties:39` 的 `account.card-pool.debug-manual-allocate=true` **默认是开着的**；`:40` 另有 `account.card-pool.debug-manual-card-id=9900000000000001`
- 关闭开关才走 `CardPoolServiceImpl.allocateNextCard`（`:35-55`）：`monitorCardPool()` 补池 → 最多重试 3 次 `selectUnusedCard` + `updateAllocateCard` 乐观占用；阈值 `account.card-pool.threshold`（默认 10）、`account.card-pool.batch-size`（默认 20）（`CardPoolServiceImpl.java:28-31`，`application.properties:35-36`）
- ⚠️ **补池的卡号是本地伪造的**：`buildCardId()` = `"QD" + yyMMdd + HHmmss + %06d(AtomicInteger)`（`CardPoolServiceImpl.java:104-108`），`:70` 明确留着 `// TODO 对接 Ticket/ACC 卡号申请接口`
- 未找到 Oracle 序列（`SEQUENCE` / `.nextval`）

**相关但未接线**：`acc-secure-server` 有 IF7B-01「请求逻辑卡号」的出向入口与 DTO（`AccSecureController.java:41-45`、`RequestQrLogicNumListReqDTO.java:4`、`AccSecureServiceImpl.java:59`、`AccSecureProperties.java:112`）。该模块按 `AGENTS.md` §3.2 记录为**当前未接线**，本次只核对类存在，未追踪调用方。

## 原预期逐条核对

## 事实基线变更（2026-09-09 追加，不改写上文）

上文「完全不可执行」的结论针对的是 **ACC 通过 FTP 下发 `ESLOGIC.日期.序号` 文件** 这条链路。2026-09-09 复核：**`card-pool-server` 已存在并在测试集群运行**，逻辑卡号池走的是另一套实现，与上文描述的 `account-server` 本地伪造卡号、`acc-secure-server` 未接线**都不是同一条链路**。上文关于 `account-server` / `acc-es-server` 的取证仍然有效，**未推翻**；本节只补充 `card-pool-server` 这一条新增链路的可测项。

链路事实（详见 `docs/business/card-pool.md`）：

- 触发端 `web-admin` Quartz 任务 `cardPoolQuartzTask.runMaintenance()`，`sys_job` job_id=107（**现为 240「卡池数据导入」**，2026-09-21 改名改号），cron `0 0/5 * * * ?`，`misfire_policy=3`，`concurrent=1`
- 经 `rpc` 的 `CardPoolClient.runMaintenance(headers)` → `POST /internal/card-pools/maintenance`（card-pool-server 9111）
- 集群地址由 env `CARD_POOL_SERVICE_URL` 注入，当前值 `http://card-pool-server-86mc1-svc.itp.svc:30033`
- 接口是**受理式**：同步只返回 `data.accepted`（布尔），重活在平台线程池 `card-pool-maintenance` 异步跑
- trace：`QuartzTraceUtils.traceHeaders()` 下发 W3C `traceparent`；card-pool 侧 `CardPoolServiceImpl.withTraceContext` 建子 span 带进异步线程
- 当前版本 `itp/card-pool-server:1.0.14`、`itp/web-admin:1.1.15`

## 新增用例（card-pool-server 定时维护与链路追踪）

### T003-4 定时任务按 5 分钟准点触发

**前置**：`sys_job` job_id=240（现号，**原 107，2026-09-21 已重编号**）存在且 `status=0`；web-admin **单副本**且在 job 写表后重启过（Quartz 内存 JobStore，运行中改表不生效）。

**步骤**：等待两个整 5 分钟点。

**判据**：
1. `SELECT * FROM sys_job_log WHERE job_name='卡池数据导入' ORDER BY create_time DESC` 每 5 分钟一条，`status=0`（任务名 2026-09-21 由「卡池维护」改名，**按旧名查会 0 行**）
2. card-pool-server 日志同一秒出现 `[card-pool-maintenance]` 线程的 SQL 与 `卡池维护完成, stats={...}`
3. **NEVER 用 `QRTZ_JOB_DETAILS` / `QRTZ_TRIGGERS` 判断**——内存 JobStore 下恒 0 行

**结果**：☑ 通过（2026-09-09）。15:10:00 首跳 `sys_job_log` job_log_id=691 status=0 耗时 493ms；15:40:00 / 15:55:00 / 16:05:00 三跳均准点，`stats={releasedExpired=0, createdBatches=0, executedBatches=0, failedBatches=0}`。

### T003-5 异步线程 traceId 与调度端一致

**判据**：`[card-pool-maintenance]` 线程**整轮**日志（每条 SQL + `卡池维护完成`）的 `%X{traceId}` 为**同一个值**，且等于 `sys_job_log.job_message` 里 `traceId=` 后的值。

**结果**：☑ 通过（2026-09-09，两条独立路径）。
- 定时路径 15:40:00：`sys_job_log` 记 `traceId=f4638949ee4f4f2ba033c02751e97f08`，card-pool 侧 20 条 SQL + 完成行同为该值
- 手工路径 16:05:32：`curl -X POST http://127.0.0.1:9111/internal/card-pools/maintenance -H 'traceparent: 00-1111222233334444aaaabbbbccccdddd-1234567890abcdef-01'` 返回 200，异步线程整轮日志 traceId 即 `1111222233334444aaaabbbbccccdddd`
- 回归要点：**1.0.13 曾照 pay-sign 口径改成只拷 MDC，此项失败**（20 条 SQL 各自一个 traceId，完成行 traceId 为空）。改动 `withTraceContext` 后**必须重跑本用例**。



### T003-6 受理式语义与并发限流

**说明**：`runMaintenance` 用 `maintenanceRunning`（`AtomicBoolean`）挡重复提交。上一轮未结束时再调，返回 `accepted=false` + `message=上一轮卡池维护尚未结束，本次请求已忽略`。**`accepted=false` 是正常限流，不是失败**，`CardPoolQuartzTask.invokeOnce` 只记日志、不抛异常，`sys_job_log.status` 仍为 0。

**步骤**：先造一个待导入批次让维护耗时变长，在其执行期间连续调两次 `/internal/card-pools/maintenance`。

**判据**：首次 `accepted=true`；执行期间的后续调用 `accepted=false` 且带上述 message；`sys_job_log` 不出现 `status=1`；单线程池不堆积第二个任务。

**结果**：☐ 未执行（当前测试环境 `stats` 全 0、单轮约 150ms，难以自然重叠，需先造待导入批次）

### T003-7 tracing 关闭时的降级

**说明**：`withTraceContext` 经 `ObjectProvider<Tracer>` 取 Tracer，取不到（`management.tracing.enabled=false`）或无父 span 时**原样返回任务**。

**判据**：临时注入 `MANAGEMENT_TRACING_ENABLED=false` 后服务正常启动（不因缺 Tracer bean 失败），定时维护照常执行、`sys_job_log.status=0`，仅日志无 traceId。验证后**必须还原 env**。

**结果**：☐ 未执行

### T003-8 失败分支与任务日志

**说明**：`CardPoolQuartzTask.invokeOnce` 对「返回 null」「`!isSuccess()`」抛 `IllegalStateException`。

**判据**：把 `CARD_POOL_SERVICE_URL` 临时指向不可达地址，下一跳 `sys_job_log.status=1` 且 `job_message` 含异常信息，web-admin 日志有 `CardPoolQuartzTask` 的 ERROR。验证后**必须还原 env**。

**结果**：☐ 未执行

### T003-9 web-admin 多副本重复触发

**说明**：Quartz 内存 JobStore 无集群协调，多副本时每个副本各跑一份。

**判据**：`kubectl -n itp get deploy web-admin -o jsonpath='{.spec.replicas}'` 必须为 1；若扩到 2，同一 cron 点应出现两条 `sys_job_log`（用于确认该约束真实存在，验证后立即缩回）。

**结果**：☐ 未执行（当前副本数 1，符合约束）
