## 四、B2 / B15 处置建议（本轮追加，不动代码）

### B2 退款链路无出向通知 -- 处置建议

**缺陷本质**：`pay-sign-server` 的退款出向 `bizData`（`PaySignGatewayMessages.buildRequestRefundBizData:88-96`）不放 `notifyUrl`，`model` 的 `RequestRefundReqDTO` 连该字段都没有。因此退款回调结构上不可能到达。

**改哪里**：
1. **最小改动（推荐）**：在 `RefundDomainServiceImpl` 给 `PAY_REFUND_DETAIL` 加最大回查次数（如 `MAX_QUERY_COUNT=50`），超过即落 `FAIL` + 开工单（写 `ACCOUNT_EXCEPTION_TICKET` 或新增退款异常表均可）。这解决的是「永久空转」问题，不需要真的有通知到达。
2. **完整改动**：在 `model` 的 `RequestRefundReqDTO` 加 `notifyUrl` 字段，`PaySignGatewayMessages.buildRequestRefundBizData` 放入该键，值取 `pay.sign.default-notify-url`；同时在 `PaySignAppController` 增加 `POST /ci/app/receiveRefundResult` 退款回调端点。这需要先与支付中心确认该键是否被接受。

**为什么上线前必须修**：当前退款单的唯一天然出口是 `TXN_DATE >= 今天-7天` 窗口 -- 7 天后静默掉出扫描范围、永远停在 `PROCESSING`，端点每轮仍返 `0000`、调度日志一片绿，既不报警也不自愈。

### B15 退款单永久空转 -- 处置建议

**缺陷本质**：`selectCompensableRefundQuery`（`PayRefundDetailMapper.xml:97-110`）没有 `REQUEST_COUNT` 上限，也没有「超 N 次落 `FAIL` / 开工单」出口。

**改哪里**：`RefundDomainServiceImpl.compensateRefundQuery` 的扫表循环内，在 `delayNextRefundQuery` 之前加判断：`if (detail.getRequestCount() >= MAX_QUERY_COUNT) { markFail(detail, "回查超限"); continue; }`。同时 `markFail` 里 MUST 落一条异常工单（参照 `ACCOUNT_EXCEPTION_TICKET` 的形态），否则「落 FAIL 就等于丢」。

**与 B2 的关系**：B15 是 B2 的直接后果。即使补上了退款通知（B2 完整改动），B15 的最大回查次数仍然需要 -- 通知本身也可能丢（JVM 崩溃、APP 侧不可达等），没有上限就没有出口。两条修复互相独立、都需要做。
