## 二、Payment_004 设置默认支付方式

### 2.1 链路事实纠正（`00` §3.8 与 `01` Payment_004 的旧写法作废）

**旧写法**：`POST /ci/app/requestSetDefaultPayChannel`（`RequestApplicationController.java:96`）。
**实测结论**：`account-server` 的 `RequestApplicationController` **没有类级 `@RequestMapping`**，八个方法全是根级 `@PostMapping`（`/requestApplication:84`、`/requestAddPayChannel:90`、`/requestSetDefaultPayChannel:96`、`/requestRemovePayChannel:102`、`/requestAgreeRelease:111`、`/userCancel:120`、`/queryUserInfo:126`、`/requestUpdateChannelDefaultContract:132`）。`/ci/app/` 这个前缀属于 **fep-app 侧别名**，直连 account-server 时 **MUST 去掉**。

判据是这一轮复现出来的对照（11:38:38）：

```
--- N3 错误路径（带 /ci/app 前缀） ---
{"retCode":"99cdd52c-66bc-412a-a99d-b30aeaaade95","retMsg":null,"data":null}
http=200
```

服务端日志原文里对应的那一行是 `No static resource ci/app/requestSetDefaultPayChannel` —— 这就是 AGENTS.md §8「404 被伪装成 HTTP 200 + UUID retCode」那条的活样例：**HTTP 码是 200、`retCode` 是个 UUID、`retMsg` 是 `null`**，只有服务端那行 `No static resource` 能分辨「路径不存在」与另外四种成因。

### 3.1 三个重试端点 + 一个收敛端点，逐字应答

本轮 11:39:07 复跑（此时 `GT20260922112144141000014` 已被自己的退避闸门挡在窗口外，因此三条都是 0 笔 —— 这正是要验的）：

**这四条应答同时钉住四件事**：

- 三个端点**确实是三个独立入口**（`retMsg` 各自不同），对应 `sys_job` **345 / 220 / 255**，`CompensationInternalController` 的 `debit/retry/recent`、`debit/retry/default`、`debit/retry/alipay`。
- `recent` 返 0 笔 ⇒ `gate.debitRetry.recent.windowMinutes=10` 的**上界**生效（那笔单 11:21 创建，11:39 已超窗）。
- `default` / `alipay` 返 0 笔 ⇒ `DEBIT_NEXT_RETRY_TIME=2026-09-22 23:26:11` 这道**退避闸门**生效（`selectBatchRetryCandidates` 的 `DEBIT_NEXT_RETRY_TIME IS NULL OR <= SYSTIMESTAMP`，`GateTxnPayMapper.xml:633`）。
- `converge` 对不存在的订单返 `8001` + `converged=false`，**零写**。

### 3.2 早一轮（写入发生在这一轮）

| 端点 | 结果 | 库前后 |
|---|---|---|
| `debit/retry/recent` → `debit/retry/default` 依次各打一次 | 两次派发都作用在 `GT20260922112144141000014` 上 | `DEBIT_RETRY_TIMES` **只加了 1 次**（0→1），`DEBIT_NEXT_RETRY_TIME` `null→23:26:11` |
| `debit/converge`（带 `origOrderNo='GTTEST2026091500101'`） | `retCode=0000`，`converged=true` | `DEBIT_STATUS` `INIT→SUCCESS`、`REMARK` 写入；**已还原** |
| `debit/converge`（不带 `txnDate`） | `retCode=0000` | 见 §3.4 |

**「`DEBIT_RETRY_TIMES` 两次派发只加一次」不是 bug**，而是 ADR-D154 已接受的代价的直接证据：`prepareRecentRetry`（345 那条）**刻意不写** `DEBIT_RETRY_TIMES` / `DEBIT_NEXT_RETRY_TIME`，否则 10 分钟窗口内会烧光 220 / 255 的次数预算。因此计数只由 `default` 那次贡献。**NEVER 把它当成「重试计数漏记」去修。**

> 逐字响应保留情况：上表三行的**逐字响应未随上下文保留**，只记已核实的库前后差异与 `converged` 字段。

### 3.3 B1 已证明：没有独立的「扣费失败交易表」

- `gate-txn-pay-server` 全模块只有 `GATE_TXN_PAY` 一张扣费主表，失败态是它自己的 `DEBIT_STATUS` 列（`RETRY` / `FAIL`），**不存在第二张表**。
- 重试候选是 `selectBatchRetryCandidates`：`WHERE DEBIT_STATUS IN ('RETRY','FAIL')`（`GateTxnPayMapper.xml:633`）。
- 结论：原表「计入扣费失败交易（表）」这条**在代码里没有对应物**，对应的可验证形态只能是「`GATE_TXN_PAY` 该行 `DEBIT_STATUS` 落在 `RETRY`/`FAIL`」。`05` B1 **成立**。

### 3.4 converge 缺 `txnDate` 返 `0000` —— **不是缺陷**（差一步就误报）

现象：`debit/converge` 只送 `origOrderNo`、不送 `txnDate` 时返 `0000`，看起来像「必填项没校验」。
读码后推翻：`GateTxnPayServiceImpl.java:326` 只把 `origOrderNo` 列为必填；`:343` 是
```java
String effectiveTxnDate = txnDate != null ? txnDate : order.getTxnDate();
```
即**缺 `txnDate` 时按订单自身的 `TXN_DATE` 回填**，是**有意的补白设计**。已在本页明确记为 **not a defect**，避免后来者重新推导出同一个错误结论。

### 4.4 新缺陷（本轮最硬的一条）：支付中心两个端点口径互斥 ⇒ 这笔退款单永久空转

「已全部退款」与「未找到数据」**不能同时为真**。后果在我方是确定的：

- `resolveRefundQueryStatus` 拿不到终态 ⇒ 每轮都走 `delayNextRefundQuery`，`NEXT_REQUEST_TIME` 一直往后推 300 秒；
- `selectCompensableRefundQuery`（`PayRefundDetailMapper.xml:97-110`）**没有 `REQUEST_COUNT` 上限**，也没有「超过 N 次就落 `FAIL` 转人工」的出口；
- 唯一的天然出口是 `TXN_DATE >= 今天-7天` 这个窗口 —— **7 天后这一行悄悄掉出扫描范围，永远停在 `PROCESSING`**，端点每轮仍返 `0000`、调度日志一片绿，**既不报警也不自愈**。

这和 ADR-D92 记的那次（只送 `refundOrderNo` 被网关拒、退款单永久空转）是**同一类失效形态的第二次出现**：症状是「一片绿 + 永不收口」。修法方向有两个（需裁决）：给 `PROCESSING` 加最大回查次数 + 落 `FAIL`/开工单；或把「请求退款说已全退、查询说没数据」这种**互斥应答**单独识别成一个终态分支。

**同时记一条已被推翻的判断**：本轮一度把「补偿只扫 `PROCESSING`、而写入方会产出 `RETRY`」当成缺陷。复核代码后，`RefundDomainServiceImpl` **在退款方向已经没有任何 `"RETRY"` 写入**（该模块仅剩的两处 `"RETRY"` 字面量在 `PaymentDomainServiceImpl.java:154`/`:194`，属**支付**方向的 `PAY_TXN_DETAIL`，不是退款），代码注释 `:125-132` 明确写了「NEVER 回退成 `RETRY`」。**因此写入方与扫描方现在是对齐的。** 真正残留的是**历史行**：修复前产生的一批 `REFUND_STATUS='RETRY'` 的旧行，`selectCompensableRefundQuery` 只取 `PROCESSING`、`selectDriftedRefundSummary` 只取 `SUCCESS` ⇒ **这批旧行谁都不扫、永久悬挂**，需要一次性数据处置（转 `PROCESSING` 让补偿接手，或逐笔回查定性后落终态）。这条 `05` 里单列。

### 4.5 「退款必须送 `notifyUrl`」在当前代码里做不到

- `PaySignGatewayMessages.buildRequestRefundBizData`（`:88-96`）只放 `refundOrderNo` / `merchantOrderNo` / `orderNo` / `refundAmount` / `refundReason` —— **没有 `notifyUrl` 键**；而同文件的签约（`:27`）与请求支付（`:80`）都有。
- `model` 侧 `RequestRefundReqDTO` 只有 `orderNo` / `refundAmount` / `refundReason`，**连字段都不存在**。

因此「不送 `notifyUrl` 就永远收不到退款回调」这条纪律，在 pay-sign 的退款链路上**不是操作疏漏、是实现缺口**：想收回调必须先加字段 + 加 bizData 键 + 与支付中心确认该键是否被接受。这直接支撑 `05` B2（退款收敛只能靠 `sys_job` 305 轮询，最坏 10 分钟延迟）。

### 4.6 重复退款无幂等（同一原单被退了 3 次）

原单 `GT20260918160920819075710` 在 `PAY_REFUND_DETAIL` 里有 **3 行**独立退款记录（09-18 / 09-20 / 09-21），三次都被支付中心以「该订单已全部退款」拒掉。我方**没有任何前置拦截**：`validateRefundPayTxn` 不看「这张原单是否已存在未终结/已成功的退款行」。今天这笔（09-22）是第 4 次同型请求。

**当前是靠支付中心兜着**。一旦支付中心某次放行，就会出现重复退款。归入 `05` 新增项。
