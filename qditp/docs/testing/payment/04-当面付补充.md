### ITP_Payment_010 TVM扫码购票

主体用例见 [face-pay/01-TVM.md](../face-pay/01-TVM.md)（该页编号 012）。
**原表备注（问题）：部分发售成功；查询界面无显示，无法退款。**

本页补的可验证断言（代码侧定位，详见 `05` B3）：

1. **「无法退款」有明确代码成因，不是环境问题**：`web/src/views/trans/face-pay/order/index.vue:179-180`
   ```js
   const refundableOrderStatuses = ['PAID', 'FULFILLED', 'FULFILL_FAILED']
   return refundableOrderStatuses.includes(row.orderStatus) && row.refundStatus !== 'SUCCESS' && row.refundStatus !== 'PARTIAL'
   ```
   —— **`refundStatus === 'PARTIAL'` 时退款按钮直接不渲染**。而部分发售恰好把订单打成 `PARTIAL`（`refundShortfall` 退差额，`F2fTicketIssueService.java:159`）。**⇒ 部分发售的订单在运营端 100% 退不了款。**
2. **运营端只有全额退款入口**：`FacePayOrderPageController.refund`（`:82`）的方法注释就是「运营端发起**全额**退款」，调 `pageRefundService.refundWholeOrder(orderNo, reason, operator)`（`:92`）。请求体 `FacePayRefundRequest` 只有 `refundReason` / `operatorId`（`:86-91` 用到的字段），**没有金额字段**。前端弹窗里「退款金额」是只读展示 `formatAmount(refundOrder.orderAmount)`（`index.vue:86`）。**⇒ 没有任何「按金额部分退」的运营入口。**
3. **「查询界面无显示」的可验证判据**：`/page/face-pay/orders` 的 `orderStatus` 下拉**缺两个值** —— 前端选项只有 9 个（`index.vue:36-44`：`CREATED`/`PAYING`/`PAID`/`FULFILLED`/`FULFILL_FAILED`/`PAY_FAILED`/`EXPIRED`/`REFUNDING`/`REFUNDED`），而格式化函数 `formatOrderStatus`（`:161-163`）认 11 个（多 `TOPUP_SUSPECT` 与 `CANCELED`）。
   - 因此 **`TOPUP_SUSPECT` / `CANCELED` 的订单无法用状态筛选出来**（不选状态时仍会返回，因为后端 `orderStatus` 是可选参数）。
   - ⚠️ **但这解释不了「部分发售查不到」** —— 部分发售落 `FULFILL_FAILED`，下拉里有该选项。**「查询界面无显示」的真实成因未定位**，需复跑时抓服务端日志原文（UUID `retCode` 至少 5 种成因，MUST 每次取原文）。
4. 可验证的最小闭环：
   - 造一笔部分出票单（见 [03](03-退款.md) Payment_009 的 curl）
   - `GET /page/face-pay/orders?orderStatus=FULFILL_FAILED&beginTime=...&endTime=...` 应能查到
   - 页面上该行的退款按钮**应当不显示**（这是缺陷的确认，不是通过判据）

### ITP_Payment_011 TVM扫码充值

主体用例见 [face-pay/01-TVM.md](../face-pay/01-TVM.md)（该页编号 013）。
**原表备注（问题）：前台查询不到订单或无查询界面；微信与支付宝均可成功支付。**

本页补的可验证断言（详见 `05` B4）：

1. **综管台只有一个当面付查询页**：`web/src/views/trans/face-pay/order/index.vue`，API 定义在 `web/src/api/trans/facePayOrder.js`：
   - `:8` `url: '/face-pay-server/page/face-pay/orders'`（列表）
   - `:17` `url: '/face-pay-server/page/face-pay/orders/${orderNo}/refund'`（退款）
2. **`/page/app/orders` 在前端零引用**：`face-pay-server` 有 `AppOrderPageController`（`:17` 类级 `/page/app/orders`、`:33` `POST /{orderNo}/refund`），`collect-pay-server` 也有一份（`page/AppOrderPageController.java:18`），但 `grep -rn '/page/app/orders' web/src` **零命中**。**⇒ APP 域订单确实「无查询界面」**，原表备注成立。
3. **充值订单能不能查到，取决于 `bizType`**：前端 `bizType` 下拉有 `02` 充值（`index.vue:29`），后端 `page()` 也收该参数（`FacePayOrderPageController.java:52`）。因此**充值单本身是可查的** —— 可验证断言：
   ```
   GET /page/face-pay/orders?bizType=02&channel=02&beginTime=...&endTime=...
   ```
   应返回该笔充值单。若返回 0 行，MUST 先确认 `F2F_ORDER.BIZ_TYPE` 实际落的是不是 `'02'`（**列取值来源本轮未在代码里找到集中的枚举类，`find ... *BizType*.java` 零命中**，所以 `02` 这个值只有前端与页面控制器两处口径，**NEVER 假定后端一定写 `02`**）。
4. 「微信与支付宝均可成功支付」属渠道侧事实，我方侧可验证的是 `F2F_PAYMENT` 里两笔的渠道字段不同、都收敛到成功。

### ITP_Payment_012a BOM发售单程票

> **原表无编号，本库补临时编号 `ITP_Payment_012a`，编号为本库自拟。** 原表位置：012 之后。
> **face-pay 页没有「BOM 发售单程票」小节**（该页 BOM 三节是非现金收款 / 充值 / 补票），因此本条属未覆盖。

原表步骤：1、BOM 选择车票确认金额向 ITP 发起订单付款申请；2、扫码枪扫码完成支付；3、付款成功，写卡发售成功，BOM 向 ITP 发送发售结果通知；4、检查结果

原表结果：1、扫码支付成功；2、订单可查 ｜ 状态：通过

#### 改写后的可验证预期

1. **下单**：`POST /itpbom/ci/bom/requestGenNoCashOrder`（`BomOrderController.java:112`）返回 `retCode=0000`，`F2F_ORDER` 新增一行，`ORDER_STATUS='CREATED'`、`CHANNEL='03'`（BOM）。
   ⚠️ **「BOM 发售单程票」用的到底是 `requestGenNoCashOrder` 还是 TVM 侧的 `requestGenSjtOrder`（`TvmOrderController.java:138`，`Sjt` = 单程票）本轮未定论** —— BOM 前缀下**没有** `requestGenSjtOrder`，但 BOM 前缀有 `/itpbom/ci/tvm` 别名（`TvmOrderController.java:45`），**因此 BOM 设备完全可以打 `/itpbom/ci/tvm/requestGenSjtOrder`**。执行前 MUST 先与设备侧确认打的是哪条 URL，并在结果里写明。
2. **发起支付**：`POST /itpbom/ci/bom/requestPayment`（`:141`）→ `ORDER_STATUS` 推进到 `PAYING`。
3. **扫码付款**：**需人工（扫码枪扫乘客付款码）**。
4. **支付结果**：`ORDER_STATUS='PAID'`，`F2F_PAYMENT` 落一行。查询入口 `POST /itpbom/ci/bom/requestGetPayResult` ｜ `/requestPayResult`（`:162`）。
5. **发售结果通知**：`POST /itpbom/ci/bom/notiTakeTicketResult`（`:284`）成功 → `ORDER_STATUS='FULFILLED'`；`POST /itpbom/ci/bom/notiTakeTicketFailResult`（`:295`）失败 → `FULFILL_FAILED` + 触发 `refundShortfall` 差额退（见 [03](03-退款.md) Payment_009）。
6. **「原路退还」的断言**：`F2F_ORDER.REFUND_STATUS` 为 `SUCCESS`（全退）或 `PARTIAL`（部分），`ORDER_STATUS` 经 `REFUNDING` 到 `REFUNDED`。
7. 票明细落 `F2F_TICKET` / `F2F_TICKET_ORDER`。
8. ⚠️ **已知残留**：设备送**小写** `ticketLogicNum` 时 face-pay 返 `8999`（新应用 `F2fTicketMapper` 是精确等值比较，旧应用是 `UPPER()`）。已按裁决只做数据归一、未改代码。**测试时 MUST 送大写**，见 `docs/ops/流量切换.md` §四首条。

原表结果：1、扫码支付成功；2、订单可查 ｜ 状态：通过

#### 改写后的可验证预期

**⚠️ 本条当前阻塞，无法按「STT 专属链路」验证。**

1. `face-pay-server` **没有 STT 路由前缀**（证据见本页 §一 Payment_016~018 那段）。因此 STT 设备发出的报文只能落在 `/itptvm/**` 或 `/itpbom/**` 两套之一。
2. **在确认 STT 借用哪一套之前，本条只能退化成两个观察点**：
   - 观察点 1：抓一笔真实 STT 交易，确认它打的 URL 前缀。判据是逐 Pod grep face-pay 容器内日志文件的请求行；若 URL 在仓库里搜不到，就是**契约偏差**（上游按另一份文档取的 URL），修法是补别名。
   - 观察点 2：确认该笔在 `F2F_ORDER.CHANNEL` 里落的值。若落 `02`/`03`，说明它被当成 TVM/BOM；若落 `07` 或别的值，说明后端没按前端那三个值约束。
3. **支付方向是需求问题、不是编码问题**：TVM 语义是「乘客扫机器」，BOM 语义是「操作员扫乘客」，两者方向相反。借错一套会导致收款方向错。**MUST 先向甲方澄清，NEVER 自行挑一套当预期。**
4. 一旦澄清为「复用 BOM」，本条的预期可**逐字复用 Payment_012a**，只把设备号换成 STT 设备号。

#### 执行方式

① curl 骨架（**当前不给 STT 专属 URL** —— 那会是编造。澄清前只能按借用的那套打，形态同 Payment_012a）

```bash
# 前置：先确认 STT 实际在用哪个前缀
ssh k8s-master
for p in $(kubectl get pods -n itp -o name | grep face-pay); do
  kubectl exec -n itp ${p#pod/} -- sh -c 'grep -h "itpstt\|/stt/" /home/javaapp/app/logs/*/*.log | head -5'
done
# 同时看有没有 404 被伪装成 UUID retCode
for p in $(kubectl get pods -n itp -o name | grep face-pay); do
  kubectl exec -n itp ${p#pod/} -- sh -c 'grep -l "No static resource" /home/javaapp/app/logs/*/*.log'
done
```
> **NEVER 用 `scripts/klog.sh` 带关键字查这个** —— 它只看尾部窗口，且 Pod 一重启日志目录就消失。

② DB 核对 SQL

```sql
SELECT CHANNEL, BIZ_TYPE, COUNT(*), MIN(CREATE_TIME), MAX(CREATE_TIME)
  FROM F2F_ORDER WHERE CREATE_TIME > SYSDATE - 7
 GROUP BY CHANNEL, BIZ_TYPE ORDER BY 1, 2;
-- 若 STT 设备号已知，按设备号反查渠道
SELECT DISTINCT DEVICE_ID, CHANNEL FROM F2F_ORDER WHERE DEVICE_ID LIKE '<STT 设备号前缀>%';
```

③ 日志判据：同上的逐 Pod grep；另可查设备心跳落点 `SELECT * FROM F2F_DEVICE_STATUS WHERE DEVICE_ID = '<STT 设备号>';`（心跳入口 `notiDeviceHeard` ｜ `deviceHeartbeat`，TVM `:94` / BOM `:102`）。

#### 结果

阻塞（无 STT 路由，需求待澄清）
