## ITP_Payment_007 退款-异步退款至付款账号

原表步骤：用户申请退款 → 系统查询订单，向支付渠道发起退款 → 检查退款结果
原表预期：退款请求提交成功，订单状态更新为「退款中」；退款到账后状态更新为「已退款」
原表结果：1、退款成功 ｜ 状态：通过
**原表备注（问题）：1、退费成功，退款结果通知超时，界面提示退款超时**

### 改写后的可验证预期（链路 A）

1. `POST /ci/app/requestRefund` 返回 `retCode=0000`，响应体带 `refundOrderNo` / `merchantRefundNo` / `refundNo` / `channelRefundNo` / `refundTime`（赋值点 `PayRefundRules.fillRefundResponseFields:66-76`，逐字段取自支付中心 `data`）。
2. **前置校验**（`PayRefundRules.validateRefundPayTxn:24`）：按 `PAY_TXN_DETAIL` 原单校验，已退金额从 `payTxn.getRefundAmount()` 取（`:35`）。**具体拒绝文案 MUST 现读该方法，本页不猜。**
3. **落库断言**：`PAY_REFUND_DETAIL` 新增一行（`PayRefundDetailMapper.xml:31`），`REFUND_STATUS` 初值 **`INIT`**（`PayRefundRules.java:55`），`REFUND_ORDER_NO` 由 `buildRefundOrderNo`（`:79`）按原订单号派生。
4. 发起后由 `updateRefundRequestResult`（`RefundDomainServiceImpl.java:428`）把 `REFUND_STATUS` 改成支付中心应答对应的值。该文件内出现的状态字面量是 `SUCCESS`（`:107`）/ `RETRY`（`:126`）/ `PROCESSING`（`:139`）/ `FAIL`（`:166`）。
   - ⚠️ **原表说的「退款中」/「已退款」在代码里没有这两个字面量**。对应值是 `PROCESSING`（退款中）与 `SUCCESS`（已退款）。回填结果时 MUST 写代码值。
5. **收口靠主动回查，不靠通知**：`POST /internal/payment/compensateRefundQuery`（`PaymentInternalController.java:26`，`sys_job` **305「退款回查补偿」cron `0 0/10 * * * ?`**）→ `settleRefundByQuery`（`RefundDomainServiceImpl.java:281`）：
   - 出向 `bizData` **两个键都送**：`refundOrderNo` + `merchantRefundNo`（`:283-285`，**NEVER 只送一个**，只送 `refundOrderNo` 时网关返 `code=9999`）
   - 未得终态时走 `delayNextRefundQuery` 退避（`:295`），退避 CAS 命中 0 行只打日志
   - 得到终态后 `finishFromQuery` CAS 收口（`:318` 附近），命中 0 行时打 WARN「退款回查收口 CAS 命中 0 行，已被其它路径收口，本轮不重算汇总」
   - 金额不一致会打 `warnIfRefundAmountMismatch`（`:314`）
6. **跨表对账**：`POST /internal/payment/compensateRefundSummary`（`:33`，`sys_job` **310「退款汇总跨表对账」cron `0 15 * * * ?`**），完成日志「退款汇总跨表对账补偿完成, txnDateFrom=…, scanned=…, submitted=…, skipped=…, 其中不可自愈（原单不存在）=…」（`RefundDomainServiceImpl.java:410` 附近）。**`不可自愈（原单不存在）` 不为 0 即需人工。**
7. ⚠️ **原表备注「退款结果通知超时」的代码侧定位**：`pay-sign-server` 里 **grep `receiveRefundResult` / `notifyRefund` / 退款通知 全部零命中** —— **该模块没有任何「把退款结果推给 APP」的出向代码**。因此：
   - 「界面提示退款超时」的成因不可能是「通知发慢了」，只能是**前台在等一个永远不会来的通知**，或前台自己在轮询而超时阈值偏小。
   - 我方侧能验证的只有：`PAY_REFUND_DETAIL.REFUND_STATUS` 最终收敛到 `SUCCESS`。**收敛时延 = 回查任务周期（10 分钟）** —— 这就是「超时」的真实来源。
   - `/ci/app/receiveRefundResult`（`fep-app CollectPayController.java:70`）与 `/ci/app/receiveRefundResult`（`face-pay AppOrderController.java:147`）属**链路 B**（当面付），与本条无关。**NEVER 拿它们当链路 A 的退款通知。**
   - 归入 `05` B2。

## ITP_Payment_008 购单程票支付退款-原路全款退回

原表步骤：APP 打开单程票订单申请退款 → APP 向 ITP 发起退款申请，转发至支付平台 → 检查退款结果
原表预期：退款成功，全额原路退回；订单状态更新为「已退款」；APP 向 ITP 查询订单状态
原表结果：1、退款成功，全额原路退回；2、订单状态可查，且标记已退 ｜ 状态：通过

### 改写后的可验证预期（链路 B）

1. **入口归属 face-pay，不是 collect-ticket** —— `collect-ticket-server` 的 `TicketCollectController` **没有任何退款端点**（`:41`~`:105` 八个方法里零命中 refund）。APP 退款走 `fep-app CollectPayController.java:46` `/ci/app/requestRefundTicket` → `service.collectPay.url`（**该 env 现指向 face-pay `:30025`**）→ `face-pay AppOrderController.java:122`。
2. `POST /ci/app/requestRefundTicket` 返回 `retCode=0000`。
3. **前置状态白名单**：`F2F_ORDER.ORDER_STATUS` MUST 在 `REFUNDABLE` 集合内 = {`PAID`,`FULFILLED`,`FULFILL_FAILED`}（`F2fOrderStatus.java` 的 `REFUNDABLE`）。其余状态应被拒。
4. **状态推进断言**（`F2fOrderStatus` 的 ALLOWED 白名单）：`PAID`/`FULFILLED`/`FULFILL_FAILED` → `REFUNDING` → `REFUNDED`。**`REFUNDING` 的唯一出边是 `REFUNDED`**，因此「退款中」卡住时不会自己跳回。
5. **全额退的断言**：`F2F_ORDER.REFUND_STATUS='SUCCESS'`（`F2fOrderRefundStatus.java:12`，定义就是 `REFUND_AMOUNT >= ORDER_AMOUNT`）。**部分退是 `PARTIAL`**（`:10`）。
6. 「APP 查询订单状态」= `POST /ci/app/requestRefundTicketResult`（`AppOrderController.java:133`）与 `POST /ci/app/requestPayResult`（`:93`）。
7. 渠道回调落点：`POST /itpbom/ci/bom/receiveRefundResult` ｜ `/itptvm/ci/tvm/receiveRefundResult`（`RefundNoticeController.java:46`，**两条前缀同一个方法**）；APP 侧回调入口 `POST /ci/app/receiveRefundResult`（`AppOrderController.java:147`）。
8. ⚠️ **「已退款」在 face-pay 里有两个维度**：`ORDER_STATUS='REFUNDED'`（订单状态机终态）与 `REFUND_STATUS='SUCCESS'`（金额维度）。**核对时两个都要看** —— 只看一个会漏掉「金额退成功但订单状态没推进」这类不一致。

## ITP_Payment_009 购单程票支付退款-原路部分退回

原表步骤：TVM 部分出票成功 → TVM 向 ITP 发送出票故障通知 → 检查退款结果
原表预期：部分退款成功，金额正确；订单状态可正常查询
原表结果：1、退化成功，金额确认正确；2、订单信息可查 ｜ 状态：通过

### 改写后的可验证预期（链路 B，差额退）

1. **触发方是设备的出票故障通知，不是用户申请** —— `POST /itptvm/ci/tvm/notiTakeTicketFailResult`（`TvmOrderController.java:115`）或 BOM 侧 `POST /itpbom/ci/bom/notiTakeTicketFailResult`（`BomOrderController.java:295`）。
2. 处理入口 `F2fTicketIssueService`（`:116` 起）：`actualNum = request.actualNum()`，为 `null` 时走 `:117` 的分支（**具体处置 MUST 现读该分支，本页不猜**）。
3. **差额退的唯一自动实现是 `refundShortfall`（`F2fTicketIssueService.java:159`）**：
   - `shortfall = orderNum - actualNum`（`:167`）
   - `shortfall <= 0` 时 **只打 WARN「出票失败但应退张数非正，不退款」（`:169`）、不退款** —— 这是「金额正确」的反面判据：`actualNum` 上报大于订单张数时不会误退。
   - 返回 `refundNo`（`:148`），随后 `enqueueAppNotify(order, TYPE_TAKE_TICKET_FAIL, actualNum, ...)`（`:149`）入队 APP 通知
4. **金额正确的可验证断言**：`F2F_ORDER.REFUND_AMOUNT` 应等于 `单价 × shortfall`。⚠️ **单价的计算位置本轮未定位到**（`refundShortfall` 内部的金额算式未逐行读），核对时 MUST 现读 `F2fTicketIssueService.java:159-180` 并与 `F2F_TICKET` / `F2F_TICKET_ORDER` 的张数对齐。
5. **状态断言**：`ORDER_STATUS` 推进到 `FULFILL_FAILED`（`PAID` → `FULFILL_FAILED` 在白名单内），退款提交后 → `REFUNDING` → `REFUNDED`；`REFUND_STATUS='PARTIAL'`（因为 `REFUND_AMOUNT < ORDER_AMOUNT`）。
6. 同一条链路还有**补偿路径**：出票上报补偿（`F2fTicketIssueService.java:303` 起，`actualNum = report.getActualTicketNum()`），成功分支 `:317` 发 `TYPE_TAKE_TICKET_OK`、失败分支 `:325` 同样调 `refundShortfall`。**因此差额退有两个触发点，测试时 MUST 确认走的是哪一个。**
7. 通知 APP 的投递载体是 `F2F_NOTIFY_TASK`（`F2fNotifyTaskMapper.xml`），投递 payload 里带 `actualTakeTicketNum`（`:271`）。
8. ⚠️ **「部分退款后就再也退不了了」**：`REFUND_STATUS='PARTIAL'` 之后，运营端页面的退款按钮会被隐藏（`web/src/views/trans/face-pay/order/index.vue:180` 的判定含 `row.refundStatus !== 'PARTIAL'`）。这与 Payment_010 的备注是**同一个缺陷**，见 `05` B3。
