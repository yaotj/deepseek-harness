# 01 签约与解约（Payment_001~004）

链路事实与表结构见 [[00-链路事实与配置字典]]。本页每条用例的「预期结果」都按当前代码重写，原表原话保留在「原表预期」里作对照。

公共约定：
- APP 域报文是 `application/x-www-form-urlencoded` + 公共参数（`sign` / `charset` / `format` / `timestamp` / `deviceId` / `signType`）+ `bizData`（JSON 字符串）。`fep-app-server` **不验签、`sign` 原样透传**，因此打 fep-app 时 `sign` 可以给任意占位串。
- 直连 `pay-sign-server` 的 `/ci/app/**` 端点是 **JSON body**（`@RequestBody`），不是 form-data。
- 库一律是 `AFCITPDB`（`172.20.222.3:1521`，用户 `qditp`），走 `mcp_database_qd`。

## ITP_Payment_001 免密支付签约-支付宝

原表步骤：APP 点击「签约免密支付」→ 选择支付宝渠道完成身份验证 → 检查签约状态
原表预期：签约成功，用户可使用免密支付乘车；收到签约成功通知
原表结果：1、签约成功 ｜ 状态：通过

### 改写后的可验证预期

1. `POST /ci/app/requestContractAdvisory`（fep-app 无此别名，**直连 pay-sign 的 `PaySignAppController.java:40`**）返回 `retCode=0000`，响应体带支付中心下发的签约跳转信息（字段以 `RequestContractAdvisoryRespDTO` 为准）。
2. `APP_PAY_SIGN_REQUEST` 新增一行（`PaySignRequestMapper.xml:38` 的 INSERT），`REQUEST_SIGN_SEQ` 等于本次请求流水号。
3. **需人工（渠道侧完成身份验证）**：在支付宝 App 内完成签约。
4. 渠道回调到达后：`APP_PAY_SIGN_INFO` 出现该用户该渠道的一行（`PaySignInfoMapper.xml:47` 的 INSERT），签约状态为已签约；`APP_PAY_SIGN_LOG` 留一行（`PaySignLogMapper.xml:6`）。
5. 「收到签约成功通知」= 我方**出向**推 APP：地址键 `app.notify.sign-result-url`（`pay-sign-server/application.properties:59`，**当前是 `testngbackV2` 测试地址**）。判据是日志里该次推送的应答码落在 `app.notify.success-ret-codes=0000,7004` 内（`application.properties` 同文件）。
6. ⚠️ **「可使用免密支付乘车」不在本用例可验范围**：那要到 Payment_005 才验证。本条只验签约记录落库。

### 执行方式

① curl 骨架（**签约发起段可 curl，身份验证段需人工**）

```bash
# 直连 pay-sign-server：信用能力咨询 / 发起签约（JSON body）
curl -s -X POST 'http://172.20.211.23:<NodePort，待现查 kubectl get svc -n itp>/ci/app/requestContractAdvisory' \
  -H 'Content-Type: application/json' \
  -d '{"thirdUserId":"<用户号>","paymentVendor":"<支付宝渠道码，取值见 PaymentVendorEnum>","requestSignSeq":"<本次流水>"}'
```

> 字段名以 `pay-sign-server/.../model/request/RequestContractAdvisoryReqDTO.java` 为准，**本页不逐字抄该 DTO，构造报文前 MUST 现读它**。

**可自动化的替代路径（模拟回调）**：跳过渠道扫码，直接把签约结果灌给我方
```bash
# 模拟回调 = 非真实渠道链路：只验我方收单与状态机，不验渠道是否真的签了约
curl -s -X POST 'http://172.20.211.23:<NodePort>/ci/app/receiveSignResult' \
  -H 'Content-Type: application/json' \
  -d '{"requestSignSeq":"<上一步的流水>","status":"<支付中心的签约状态原值>", ...}'
```
真实渠道回调打到的是 `pay.sign.default-notify-url`（当前 `http://58.56.166.170:48000/ci/app/receiveSignResult`），即公网入口 → `fep-app-server` → `pay-sign-server`。

② DB 核对 SQL

```sql
SELECT * FROM APP_PAY_SIGN_REQUEST WHERE REQUEST_SIGN_SEQ = '<流水>';
SELECT * FROM APP_PAY_SIGN_INFO    WHERE THIRD_USER_ID   = '<用户号>';
SELECT * FROM APP_PAY_SIGN_LOG     WHERE THIRD_USER_ID   = '<用户号>' ORDER BY 1 DESC;
```
> 列名以 `pay-sign-server/.../entity/PaySignInfo.java`、`PaySignRequest.java`、`PaySignLog.java` 为准；本页不列全量列，**避免抄错**。

③ 日志判据

```
scripts/klog.sh pay-sign-server 接收到信用能力咨询报文 200
scripts/klog.sh pay-sign-server 接收到内部签约结果通知报文 200
```

### 结果

**未执行**（2026-09-22 批次二仍未跑）。原因：真实链路要渠道侧扫码，可自动化的替代只有「模拟回调 = 非真实渠道链路」。见 [[06-执行记录-2026-09-22]] §五。

## ITP_Payment_002 免密支付签约-微信

原表步骤：选择微信签约完成身份验证 → 检查签约状态
原表预期：微信签约成功，可使用微信免密支付；收到签约成功通知
原表结果：1、已签约支付宝，再签约微信成功；**2、支付渠道手动解约，无法接收通知** ｜ 状态：通过

### 改写后的可验证预期

1. 同 Payment_001，只把 `paymentVendor` 换成微信渠道码（取值域见 `pay-sign-server/.../constant/PaymentVendorEnum.java`，**本页不猜具体码值**）。
2. **多渠道并存可验证**：同一 `THIRD_USER_ID` 在 `APP_PAY_SIGN_INFO` 里应有 2 行（支付宝 + 微信），两行 `PAYMENT_VENDOR` 不同。
3. 微信签约用的外部入口是 `pay.sign.wechat.entrust-url=https://api.mch.weixin.qq.com/papay/entrustweb`（`application.properties`），`pay.sign.wechat.app-id` 同文件。
4. ⚠️ **原表结果第 2 条「支付渠道手动解约，无法接收通知」是真实缺口，不是操作问题**：用户**在渠道 App 内**手动解约时，支付中心的解约回调**不发往我方指定地址** —— 网关 §2.3 请求解约的 `bizData` 里**没有 `notifyUrl` 字段**，回调只发往支付中心侧的商户配置地址。因此我方收口 **MUST 靠主动查 §2.4 `queryResult`**（`pay.sign.contract-result-url`，`status=UNSIGNED` 即已解约），**NEVER 设计成只等回调**。
   - 可验证断言：渠道侧手动解约后，不做任何操作时 `APP_PAY_SIGN_INFO` 该行状态**不变**；只有在 `POST /ci/app/requestContractResult`（`PaySignAppController.java:46`）之后才会更新。
   - 这条归入 `05` B9。

### 执行方式

① curl 骨架：同 Payment_001，`paymentVendor` 换微信码。渠道侧确认段**需人工（渠道侧签约页）**。
② DB 核对 SQL

```sql
SELECT PAYMENT_VENDOR, COUNT(*) FROM APP_PAY_SIGN_INFO
 WHERE THIRD_USER_ID = '<用户号>' GROUP BY PAYMENT_VENDOR;
```
③ 日志判据：`scripts/klog.sh pay-sign-server 接收到签约结果咨询报文 200`

### 结果

**未执行**（2026-09-22 批次二仍未跑，原因同 Payment_001）。见 [[06-执行记录-2026-09-22]] §五。

## ITP_Payment_003 支付渠道解约

原表步骤：进入「支付管理」点「关闭免密支付」→ 确认解约 → 检查解约结果
原表预期：解约成功，无法再使用免密支付；收到解约成功通知
原表结果：1、解约成功；2、二维码无码展示 ｜ 状态：通过

### 改写后的可验证预期

1. `POST /ci/app/requestTermination`（fep-app `PaySignController.java:86` → pay-sign `PaySignAppController.java:52`）返回 `retCode=0000`。
2. `APP_TERMINATION_REQUEST` 新增一行（`AppTerminationRequestMapper.xml:38` 的 INSERT）。该表有 **19 条 `update` 语句**（`:124` 起，实测 `grep -c 'update APP_TERMINATION_REQUEST'`），说明解约是多阶段推进的状态机，**MUST 按 `docs/business/pay-sign.md` §解约链路逐阶段核对，NEVER 只看一次快照就判成功**。
3. 解约**发起前**会先查扣费失败订单：`gate-txn-pay` 的 `POST /ci/gateTxnPay/hasFailedOrder`（`GateTxnPayController.java:62`，日志「查询解约扣费失败订单」`:64`）。有未结清时应被拦。
4. 解约成功收口在 `CallbackDomainServiceImpl.receiveTerminationResult`，随后的渠道通道清理走 **`CHANNEL_SYNC_*` outbox + 提交后出网**（`ChannelSyncDeliverer`），补偿端点 `POST /internal/termination/compensateChannelSync`（`TerminationInternalController.java:49`）。
   - 可验证断言：`APP_TERMINATION_REQUEST` 该行的 `CHANNEL_SYNC_*` 列从中间态推进到成功；若卡住，手工调一次补偿端点后应推进。
5. **收口判据 MUST 以主动查 `queryResult` 为准**（见 Payment_002 第 4 条）。
6. ⚠️ **原表结果第 2 条「二维码无码展示」不是本用例的断言**：乘车码归 `ticket-server`，解约是否应导致无码展示**规格未定义**，本库不写成预期。记入 `05` B10 待业务确认。
7. **「收到解约成功通知」** 出向地址键 `app.notify.termination-result-url`（`application.properties:61`，**当前也是 `testngbackV2`**）；补偿端点 `POST /internal/termination/compensateNotify`（`:42`）与 `POST /internal/termination/notifyFailed`（`:70`）。

### 执行方式

① curl 骨架（可 curl）

```bash
# 经 fep-app（form-data + bizData）
curl -s -X POST 'http://172.20.211.23:<fep-app NodePort，待现查>/ci/app/requestTermination' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'charset=UTF-8' --data-urlencode 'format=json' \
  --data-urlencode 'signType=00' --data-urlencode 'sign=placeholder' \
  --data-urlencode 'timestamp=20260922120000' --data-urlencode 'deviceId=' \
  --data-urlencode 'bizData={"thirdUserId":"<用户号>","paymentVendor":"<渠道码>", ...}'

# 或直连 pay-sign（JSON body）
curl -s -X POST 'http://172.20.211.23:<pay-sign NodePort，待现查>/ci/app/requestTermination' \
  -H 'Content-Type: application/json' -d '{"thirdUserId":"<用户号>", ...}'

# 解约推进 / 补偿（内部端点，JSON）
curl -s -X POST 'http://172.20.211.23:<pay-sign NodePort>/internal/termination/process'            -H 'Content-Type: application/json' -d '{}'
curl -s -X POST 'http://172.20.211.23:<pay-sign NodePort>/internal/termination/compensateChannelSync' -H 'Content-Type: application/json' -d '{}'
curl -s -X POST 'http://172.20.211.23:<pay-sign NodePort>/internal/termination/checkFailedOrders'   -H 'Content-Type: application/json' -d '{}'
```

**模拟回调（= 非真实渠道链路）**：`POST /ci/app/receiveTerminationResult`（`PaySignAppController.java:105`）。真实回调的落点是支付中心侧商户配置地址，**不是我方能指定的**。

② DB 核对 SQL

```sql
SELECT * FROM APP_TERMINATION_REQUEST WHERE THIRD_USER_ID = '<用户号>' ORDER BY 1 DESC;
SELECT * FROM APP_PAY_SIGN_INFO       WHERE THIRD_USER_ID = '<用户号>';
-- 解约前置：是否还有扣费失败 / 未结清订单
SELECT ORDER_NO, DEBIT_STATUS, TOTAL_AMOUNT, TXN_DATE
  FROM GATE_TXN_PAY
 WHERE THIRD_USER_ID = '<用户号>' AND DEBIT_STATUS IN ('INIT','RETRY','FAIL','PROCESSING')
 ORDER BY CREATE_TIME DESC;
```

③ 日志判据

```
scripts/klog.sh pay-sign-server 接收到请求解约报文 200
scripts/klog.sh pay-sign-server 接收到内部解约结果通知报文 200
scripts/klog.sh gate-txn-pay-server 查询解约扣费失败订单 200
```
另：解约补偿是否跑过 **MUST 查 `SYS_JOB_LOG`**，`pay-sign-server` 里**一个 `@Scheduled` 都没有**。

### 结果

**PASS**（2026-09-22 批次三实跑，用户 `00522966` / `paymentVendor=07`）。全链 11 秒内完成：①`APP_TERMINATION_REQUEST` ID=61 从 `PENDING` -> `SCANNING` -> `SUCCESS`；②**`queryResult` 真的返回 `UNSIGNED`**（支付中心网关确认）；③`CHANNEL_SYNC_STATUS='SUCCESS'`，`ChannelSyncDeliverer` 调 account `:30013/requestRemovePayChannel` 返 `0000`，三表（`APP_PAY_SIGN_INFO` / `APP_USER_PAY_CHANNEL` / `USER_ITP_REG_INFO`）同步清理。逐笔证据见 [[07-执行记录-2026-09-22-批次三]] §一。刻意不还原 -- 支付中心侧已真实解约，单方面恢复本地签约行会造成不一致。

## ITP_Payment_004 支付渠道-设置默认支付方式

原表步骤：APP 选择「支付渠道」→ 设为默认支付方式
原表预期：默认支付方式设置成功；验证：用户查询默认支付渠道号跟随设置变动
原表结果：1、多渠道签约情况下，切换默认支付渠道成功 ｜ 状态：通过

### 改写后的可验证预期

1. `POST /ci/app/requestSetDefaultPayChannel`（fep-app `AppAccountController.java:69`，双别名 `/app/requestSetDefaultPayChannel`）→ account-server **根级** `POST /requestSetDefaultPayChannel`（`RequestApplicationController.java:96`）→ `PayChannelServiceImpl.requestSetDefaultPayChannel:190`，返回 `retCode=0000`。
   - ⚠️ **2026-09-22 实测订正**：`RequestApplicationController` **没有类级 `@RequestMapping`**，八个方法全是**根级** `@PostMapping`。`/ci/app/` 只是 **fep-app 侧别名**，**直连 account-server 时 MUST 去掉该前缀**。带前缀打 `30013` 会返 HTTP 200 + UUID `retCode`（服务端日志原文 `No static resource ci/app/requestSetDefaultPayChannel`），**NEVER 把它误判成业务失败**。本页与 `00` §3.8 此前把直连路径写成 `/ci/app/...` 已作废、NEVER 回退。
2. 参数校验分支在 `validateSetDefaultPayChannelRequest`（`PayChannelServiceImpl.java:567`），非法入参应返回该方法给出的 `validMsg`（**具体文案 MUST 现读该方法，本页不猜**）。
3. 落库断言：`User_ITP_Reg_Info` 该 `ID` 行的 **三列同时被改写** —— `THIRD_PAY_ID` / `CHANNEL` / `REQ_CONTRACT_NO`（`UserItpRegInfoMapper.xml:226-232`），影响行数 > 0（`PayChannelServiceImpl.java:234` 判 `updated`）。
4. 切换到另一渠道后，这三列应整组变成新渠道的值 —— **「跟随设置变动」的可验证形态就是这三列，不是单独一个「默认渠道号」列**。
5. 移除通道时三列一起置 `null`（`:242-248`，调用点 `PayChannelServiceImpl.java:393`，返回 0 行时报错）。
6. ⚠️ `updateChannelDefaultContractById`（`:234`）与 `updateDefaultPayChannelById`（`:226`）**SQL 逐字相同**。对应 APP 侧两个不同接口（`requestSetDefaultPayChannel` / `requestUpdateChannelDefaultContract`，`AppAccountController.java:69` 与 `:75`），落库效果完全一致。**测试时 MUST 用两个接口各打一次并比对库内差异，预期是「无差异」**；若业务认为两者该有区别，那是缺陷（见 `05` B5）。

### 执行方式

① curl 骨架（可 curl）

```bash
curl -s -X POST 'http://172.20.211.23:<fep-app NodePort，待现查>/ci/app/requestSetDefaultPayChannel' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'charset=UTF-8' --data-urlencode 'format=json' \
  --data-urlencode 'signType=00' --data-urlencode 'sign=placeholder' \
  --data-urlencode 'timestamp=20260922120000' --data-urlencode 'deviceId=' \
  --data-urlencode 'bizData={"thirdUserId":"<用户号>", ...}'

# 对照接口（预期落库结果与上面完全一致）
curl -s -X POST 'http://172.20.211.23:<fep-app NodePort>/ci/app/requestUpdateChannelDefaultContract' ...

# 直连 account-server（30013）：路径是根级，NEVER 带 /ci/app 前缀
curl -s -X POST 'http://172.20.211.23:30013/requestSetDefaultPayChannel' \
  -H 'Content-Type: application/json' \
  -d '{"thirdUserId":"<用户号>","cardId":"<卡号>","cardType":"<卡类型>","channel":"<渠道>"}'
```
> `bizData` 字段名以 `model/app/RequestSetDefaultPayChannelReqDTO.java` 为准。**注意 account-server 有入向验签（`AccountRequestVerifier`，摘要式，`signType=00` 免签）**，直连时 `signType` 给 `00`。

② DB 核对 SQL

```sql
SELECT ID, THIRD_USER_ID, CARD_ID, CARD_TYPE, THIRD_PAY_ID, CHANNEL, REQ_CONTRACT_NO
  FROM USER_ITP_REG_INFO
 WHERE THIRD_USER_ID = '<用户号>' AND DEL_YN = '1';
-- 切换前后各跑一次，比对这三列
SELECT THIRD_USER_ID, PAYMENT_VENDOR FROM APP_PAY_SIGN_INFO WHERE THIRD_USER_ID = '<用户号>';
```

③ 日志判据

`account-server` **不在 tracing 名单里**（`%X{traceId}` 恒为空，按 traceId 检索必然 0 条）。只能按时间窗看：
```
scripts/klog.sh account 200
```
> Deployment / 容器名是 `account`，**不是 `account-server`**。

### 结果

**PASS**（2026-09-22 批次二实跑，5 个分支全过：空入参 `8001 thirdUserId不能为空`、无开户记录用户 `8004 没有账号卡片数据`、错误路径 UUID `retCode`、同值幂等 `0000`、真实改写三列 `0000` 且已按原值还原）。逐笔证据、原样响应与还原 SQL 见 [[06-执行记录-2026-09-22]] §二。

同批得到两条新事实：
- **当前数据下「同一张卡上切换默认渠道」无法构造** —— `00522950` 的两条支付通道分别绑在不同卡类型上（`0441`+`03` 与 `0442`+`04`），而定位逻辑是 `thirdUserId + cardId + cardType` 先定开户行、再 `thirdUserId + cardType + channel` 定通道行。这不是接口缺陷，是**测试数据不具备该形态**，要验原表那句「多渠道签约情况下切换成功」MUST 先造同卡类型下有两个渠道的数据。
- 上面第 6 条那个双接口比对（`requestSetDefaultPayChannel` vs `requestUpdateChannelDefaultContract`）**本轮未做**，`05` B5 仍未闭合。
