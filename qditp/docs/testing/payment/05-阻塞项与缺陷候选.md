## A 口径冲突

### A1 face-pay 页与本期 sheet 的用例编号整体差 2（⚠️ 最先要对齐的一条）

**现象**：`docs/testing/face-pay/INDEX.md:11-13` 把 `ITP_Payment_012~014` 标成「TVM 购票 / 充值 / 取票」、`015~017` 标成「BOM 非现金 / 充值 / 补票」、`018~020` 标成 STT 三条。而本期 sheet 里 `010~012` 是 TVM 三条、`013~015` 是 BOM 三条、`016~018` 是 STT 三条。

**成因**：face-pay 页的来源是**另一份案例清单**（该 INDEX 自述「9 例，ITP_Payment_012~020」），本期 sheet 多了两条无编号行并整体前移。

**判据**：同一个编号 `015` 在两处分别指「BOM 非现金收款」（face-pay 页）与「BOM 补票-超程扣费」（本期 sheet）。

**处置**：
- **跨页引用一律按三级用例名对齐，NEVER 按编号对齐**（对照表在 [INDEX](INDEX.md#去重指向哪些条目已由别的页覆盖)）。
- **NEVER 去改 face-pay 页的编号** —— 那会破坏它与自己那份来源的对应关系。
- 建议向同事确认 sheet 是否会再重排；若会，本目录的 `012a` / `015a` 临时编号需同批复核。

### A2 「订单状态更新为已支付 / 退款中 / 已退款 / 待支付」四个措辞在代码里都不存在

**现象**：原表 Payment_005 / 006 / 007 用了这四个中文状态词。

**代码定位**：
- 出站扣费只有 `DebitStatus.java` 五个值：`INIT`(:6) / `PROCESSING` / `RETRY`(:10) / `SUCCESS`(:12) / `FAIL`(:14)
- 支付明细 `PAY_TXN_DETAIL.PAY_STATUS`：`INIT`（`PaymentDomainServiceImpl.java:348`）→ `PROCESSING`（`PayTxnDetailMapper.xml:115`）→ `convertPayStatus` 归一（`PaySignValues.java:62-74`）
- 退款 `PAY_REFUND_DETAIL.REFUND_STATUS`：`INIT`（`PayRefundRules.java:55`），后续 `SUCCESS`/`RETRY`/`PROCESSING`/`FAIL`（`RefundDomainServiceImpl.java:107/126/139/166`）
- **「待支付」没有对应值**，最接近的是 `INIT`

**处置**：回填测试结果时 MUST 写代码值。已在 `02` / `03` 各用例里逐条改写。

### A3 `convertPayStatus` 对未知状态原样透传

**现象**：支付中心若返回一个我方没见过的状态字符串，`convertPayStatus`（`PaySignValues.java:73`）**原样大写落库**，不报错不告警。

**判据**：
```sql
SELECT PAY_STATUS, COUNT(*) FROM PAY_TXN_DETAIL GROUP BY PAY_STATUS;
```
出现 `INIT`/`PROCESSING`/`SUCCESS`/`FAIL` 之外的值即命中。

**处置**：这是「宽松解析」的有意设计（与 `F2fOrderStatus.parseOrNull` 的取向相反 —— 后者未识别返 `null`）。**不建议在测试期改代码**，但巡检 SQL 应固化，出现新值即向支付中心核对口径。

### B2 `pay-sign-server` 没有任何出向退款通知（对应 Payment_007 原表备注）

**原表备注**：退费成功，退款结果通知超时，界面提示退款超时。

**实测结论**：`grep -rn 'receiveRefundResult|refund.*notify|notifyRefund' pay-sign-server/src/main/java` **零命中**。该模块只有签约与解约两条出向通知（键 `app.notify.sign-result-url` / `app.notify.termination-result-url`，`application.properties:59`/`:61`），**没有退款通知键、没有退款 Notifier**。

**因此「通知超时」的成因不是「发慢了」，而是「没有这条通知」**。退款结果只能靠：
- APP 主动查（入口未在 pay-sign 侧找到专用查询端点，**未找到**）
- 我方内部主动回查 `POST /internal/payment/compensateRefundQuery`（`PaymentInternalController.java:26`），`sys_job` 305 cron `0 0/10 * * * ?` ⇒ **收敛时延最坏 10 分钟**

**判据**：
```sql
SELECT REFUND_ORDER_NO, REFUND_STATUS, REFUND_TIME, PAY_CENTER_CODE
  FROM PAY_REFUND_DETAIL WHERE TXN_DATE >= '<yyyyMMdd>' AND REFUND_STATUS <> 'SUCCESS';
```
非终态单持续存在且日志里只有「退款回查支付中心返回」（`RefundDomainServiceImpl.java:287`）没有任何出向推送行 ⇒ 命中。

**处置**：需向 APP 侧确认「界面提示退款超时」是等推送还是自己轮询。若业务要求推送，那是**新增功能**（要先有出向载体表才能补偿 —— 参照 `docs/domain/outbox.md`）。**NEVER 声称可复用签约通知那套**（那两条走的是 `SignNotifyService` / `TerminationNotifyService`，与退款无关）。

### B3 部分退款后运营端退款按钮消失，且只有全额退入口（对应 Payment_010 原表备注）

**原表备注**：部分发售成功；查询界面无显示，无法退款。

**实测结论：「无法退款」成立，且成因明确。**

1. 前端判定 —— `web/src/views/trans/face-pay/order/index.vue:179-180`
   ```js
   const refundableOrderStatuses = ['PAID', 'FULFILLED', 'FULFILL_FAILED']
   return refundableOrderStatuses.includes(row.orderStatus) && row.refundStatus !== 'SUCCESS' && row.refundStatus !== 'PARTIAL'
   ```
   `refundStatus === 'PARTIAL'` ⇒ 按钮不渲染。
2. 而部分出票**必然**把订单打成 `PARTIAL` —— `F2fTicketIssueService.refundShortfall:159` 退差额 ⇒ `REFUND_AMOUNT < ORDER_AMOUNT` ⇒ `F2fOrderRefundStatus.PARTIAL`（`F2fOrderRefundStatus.java:10` 的定义）。
3. 后端也只有全额退 —— `FacePayOrderPageController.refund:82` 调 `pageRefundService.refundWholeOrder(...)`（`:92`），请求体 `FacePayRefundRequest` 只有 `refundReason` / `operatorId`，**无金额字段**；前端弹窗的「退款金额」是只读展示 `formatAmount(refundOrder.orderAmount)`（`index.vue:86`）。

⇒ **部分发售订单在运营端 100% 无法再退款，且系统里没有任何「按金额部分退」的运营入口。**

**判据**：
```sql
SELECT ORDER_NO, ORDER_STATUS, REFUND_STATUS, ORDER_AMOUNT, REFUND_AMOUNT
  FROM F2F_ORDER WHERE REFUND_STATUS = 'PARTIAL';
```
这些单在页面上都不会有退款按钮。

**处置**：两条路子任选，需业务定 —— ①放开前端判定并在后端补「按金额部分退」；②裁决「部分退后不允许再退」并把这条写成设计约束。**NEVER 只放开前端** —— 后端没有金额入口，放开后点下去还是全额退。

**另一半「查询界面无显示」未定位**：部分发售落 `FULFILL_FAILED`，而该状态在前端下拉里是有的（`index.vue:40`）。复跑时 MUST 抓服务端日志原文（UUID `retCode` 至少 5 种成因，`AGENTS.md` §8）。

### B9 渠道侧手动解约时我方收不到回调（对应 Payment_002 原表结果第 2 条）

**原表结果**：支付渠道手动解约，无法接收通知。

**判据**：渠道侧手动解约后不做任何操作，`APP_PAY_SIGN_INFO` 该行状态不变；调一次 `POST /ci/app/requestContractResult`（`PaySignAppController.java:46`）后才更新。

**处置**：需确认是否有定时回查签约状态的任务。**本轮在 `pay-sign-server` 的 10 个内部端点里未找到「签约状态批量回查」** —— 有的是解约侧的 6 个（`/internal/termination/**`）与退款侧的 2 个（`/internal/payment/**`），签约侧只有 `compensateNotify` / `resendNotify`（通知补偿，不是状态回查）。**若确实没有，那么「用户在渠道侧自行解约」这件事我方永远发现不了**，属真实缺口，建议升级为独立需求。

### B13 face-pay 运营端查询的状态下拉缺 2 个值

**定位**：`web/src/views/trans/face-pay/order/index.vue`
- 筛选下拉 9 个（`:36-44`）

有行即说明存在筛不出来的数据。

**处置**：前端补两个 `el-option` 即可，改动面极小。`TOPUP_SUSPECT` 的语义是「需人工核实」，**捞不出来等于人工环节缺入口**，建议优先补。

### B14 批量重试的 11 个配置键在仓库里一个都没写

**定位**：`gate-txn-pay-server/.../service/impl/DebitRetryProcessor.java:83-93` 的 11 个 `@Value`（`gate.debitRetry.*`），`application.properties` 里**零命中**。

**后果**：线上真实的重试上限 / 批量 / 窗口 / 退避**只能查 Deployment env**，仓库里连一个可核对的值都没有。原表 Payment_006 写「3 次重试」，而代码默认是 `maxTimes=5`。

**处置**：建议按 `AGENTS.md` §5.2 的形态把这 11 个键补进 `application.properties`（带 `${ENV:默认值}`），至少让仓库里有一份可读的基线。**NEVER 只改代码默认值** —— 那在 Deployment 有 env 时不生效。

### 已被实证证明

| 项 | 结论 | 判据 |
