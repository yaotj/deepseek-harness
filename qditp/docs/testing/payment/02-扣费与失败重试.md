## ITP_Payment_005 支付-实时扣费

原表步骤：用户出站，ITP 生成订单 → ITP 发起扣费，按默认支付渠道扣款 → 检查扣费结果
原表预期：扣费成功；订单状态更新为「已支付」；收到扣费成功通知
原表结果：1、扣费成功；2、验证：扣费订单生成成功；界面列表查询成功，订单状态 ｜ 状态：通过

### 改写后的可验证预期

1. **建单**：`GATE_TXN_PAY` 新增一行（`GateTxnPayMapper.xml` 的 `INTO GATE_TXN_PAY`），`ORDER_NO` 非空、`TXN_DATE` 为 8 位日期串、`DEBIT_STATUS` 初值 `INIT`（列默认值 `gate-txn-pay-schema.sql:30`）。
2. **发起扣费**：`PaySignInitiator` 是「出站扣费的唯一出账口」（类注释 `PaySignInitiator.java:16`）。落点三分支（`:112` / `:117` / `:123`）：
   - 被受理 → `DEBIT_STATUS='PROCESSING'`，`REMARK` 含「…已被…受理」
   - 业务拒绝 → `DEBIT_STATUS='FAIL'`
   - 未获答复 → `DEBIT_STATUS='RETRY'`
3. **收口**：支付中心回调 → pay-sign `PaymentDomainServiceImpl.receivePayResult` 落 `PAY_TXN_DETAIL`（`PAY_STATUS` 由 `convertPayStatus` 归一，`PaySignValues.java:62`）→ 再调 gate-txn-pay `POST /ci/gateTxnPay/syncDebitStatus`（`GateTxnPayController.java:84`）把 `DEBIT_STATUS` 收敛到终态。
   - **成功断言**：`GATE_TXN_PAY.DEBIT_STATUS='SUCCESS'` 且 `PAY_TXN_DETAIL.PAY_STATUS='SUCCESS'`、`PAY_TIME` 非空。
4. ⚠️ **原表说「订单状态更新为已支付」，代码里没有「已支付」这个字面量** —— 对应值是 `DEBIT_STATUS='SUCCESS'`（`DebitStatus.java:12`，注释「终态：已收到钱」）。回填结果时 MUST 写 `SUCCESS`。
5. ⚠️ **「收到扣费成功通知」在本链路里未找到对应的出向通知**：`gate-txn-pay-server` 里与 APP 出网相关的只有 `wallet.app-gateway-url` + `wallet.app-query-total-amt-path=/ci/app/v2/queryTotalAmt`（钱包总额**查询**，不是扣费结果通知）。APP 侧是**主动轮询** `POST /ci/app/requestPayOrder`（`fep-app GateTxnPayController.java:34`）与 IF8A-35 `requestUserAccInfo`（`:43`）。**因此本条改写为「APP 轮询能查到该单且状态为 SUCCESS」，NEVER 写成「收到推送」**。归入 `05` B11。
6. 「界面列表查询成功」= 运营端 `GET /page/gate-txn-pay`（`GateTxnPayPageController.java:39`）能查到该 `ORDER_NO`。
7. 折扣列的正常形态：非钱包渠道（`paymentVendor != '0B'`）时 `DISCOUNT_CALC_STATUS` 与 7 个折扣列**全为 null**，**这不是缺陷**（`calculateWalletDiscount` 首行就 `return`）。

## ITP_Payment_005a 支付-离线码扣费

> **原表无编号，本库补临时编号 `ITP_Payment_005a`，编号为本库自拟。** 原表位置：005 之后。

原表步骤：1、离线码进、在线码出；2、在线码进、离线码出；3、离线码进、离线码出
原表预期 / 结果（原表两列内容相同）：进站成功，扣费成功；出站成功，扣费成功；进出成功，扣费成功
状态：通过

### 改写后的可验证预期（按三个子场景拆）

共同前提：离线码出站时闸机可能拿不到准确金额，此时 gate-txn-pay 建单后把 `DISCOUNT_CALC_STATUS` 置 **`OFFLINE_FARE_PENDING`**（`DiscountCalcStatus.java:12`，注释「离线码入库时拿不到金额，落痕等 `OfflineFareRecoveryProcessor` 重算」），`OFFLINE_FLAG` 应为 `'Y'`（列默认 `'N'`，`gate-txn-pay-schema.sql:59`）。

1. **离线码进 + 在线码出**：出站侧是在线码 ⇒ 金额可算准 ⇒ `DISCOUNT_CALC_STATUS` 不应是 `OFFLINE_FARE_PENDING`，扣费按 Payment_005 的正常链路收敛到 `SUCCESS`。
2. **在线码进 + 离线码出**：出站侧离线 ⇒ 建单时可能落 `OFFLINE_FARE_PENDING` + `DEBIT_STATUS='INIT'`。
3. **离线码进 + 离线码出**：同 2。

后两种场景的**收口靠补偿任务**，不是同步扣费：
- 入口 `POST /internal/gate-txn-pay/offline-fare/recover`（`CompensationInternalController.java:74`）→ `OfflineFareRecoveryProcessor.java:41` → `OfflineFareRecoveryService.recoverOfflineFarePendingOrders(batchSize, lookbackDays)`
- 由 web-admin `sys_job`「离线码金额补偿」触发，cron `0 0/1 * * * ?`
- 开关 `gate.pay.offline-fare-recovery-enabled`（默认 `true`），关闭时日志只有一行「离线码金额补偿开关未开启（gate.pay.offline-fare-recovery-enabled=false），本轮跳过」（`OfflineFareRecoveryProcessor.java:37`）
- 窗口 `gate.pay.offline-fare-recovery-lookback-days`（默认 7 天）、批量 50、轮询 60 秒

**关键防重扣断言**：`POST /internal/gate-txn-pay/debit/retry/recent`（`sys_job` 345）的扫表**刻意排除 `DISCOUNT_CALC_STATUS='OFFLINE_FARE_PENDING'`** —— 理由是「离线码金额未算准，扣下去就是扣错钱」。因此：
- 一笔 `OFFLINE_FARE_PENDING` 的单，**在金额重算完成前 NEVER 被 345 捞去扣费**。这是可验证断言：连续跑几轮 345，该单 `DEBIT_RETRY_TIMES` 应保持 0、`DEBIT_STATUS` 不变。
- **NEVER 删掉这条排除条件**（与 `minAgeSeconds=60` 下界、`windowMinutes=10` 上界并列的三道闸之一）。

超时费口径（⚠️ **查无甲方出处，属实现自定义**）：`offline.billing.timeout-seconds` 默认 1200（20 分钟）、`offline.billing.timeout-fee-cents` 默认 300（3 元）、`offline.billing.transfer-reduction-cents` 默认 100。见 `docs/business/overtime-handling.md`。

## ITP_Payment_006 支付-扣费失败处理

原表步骤：ITP 推送扣费请求 → 支付渠道返回扣费失败 → 检查系统处理
原表预期：扣费失败，记录失败原因；订单保持「待支付」，触发重试机制，**3 次重试后，计入扣费失败交易**
原表结果：1、扣费失败；2、扣费订单生成成功；3、界面列表查询成功，扣费失败；4、待支付订单查询订单状态成功；5、计入扣费失败交易 ｜ 状态：通过
**原表备注（问题）：计入扣费失败交易表未实现**

### 改写后的可验证预期

1. **「记录失败原因」已实现**，落点是 `GATE_TXN_PAY` 的列，不是新表：
   - `DEBIT_STATUS` = `FAIL`（业务拒绝）或 `RETRY`（未获答复）
   - `REMARK` 写明细原因（`PaySignInitiator.java:117/123` 的 `remark(...)`）
   - 批量重试后追加 `DEBIT_FAIL_CODE`（只两个值：`BIZ_REJECTED` / `UNREACHABLE`）与 `DEBIT_FAIL_MSG`（`DebitRetryProcessor.java:260`）
2. ⚠️ **「计入扣费失败交易表」确实没有对应的表** —— 全仓 grep `DEBIT_FAIL` / `FAIL_TXN` / `FAILED_TXN` / `TXN_FAIL` / `扣费失败交易`，命中只有：
   - `GATE_TXN_PAY.DEBIT_FAIL_CODE` / `DEBIT_FAIL_MSG` 两列（`gate-txn-pay-schema.sql:81-82`、`sql/gate-txn-pay-debit-retry-migration.sql:4-5`）
   - 四处 Java 注释里的「扣费失败订单」字样（`GateTxnPayMapper.java:154`、`:162`、`GateTxnPayController.java:64`、`GateTxnPayQueryService.java:75`）
   **零个独立表**。原表备注成立，代码侧定位见 `05` B1。
   - **改写后的可验证断言**：扣费失败的可见形态是 `SELECT ... FROM GATE_TXN_PAY WHERE DEBIT_STATUS='FAIL'`，以及 IF8A-35 `requestUserAccInfo` 返回的「扣费失败订单数」（`GateTxnPayAppController.java:85` → `GateTxnPayQueryService.java:75`，SQL 是 `GateTxnPayMapper.java:162` 的「一条 SQL 同时统计未支付与扣费失败」）。**NEVER 再期望有一张独立表。**
3. ⚠️ **「3 次重试」与代码不符**：上限键是 `gate.debitRetry.maxTimes`，**默认 5**（`DebitRetryProcessor.java:87`），且该键**在 `application.properties` 里没有写**，线上真实值 **MUST 查 Deployment env**。回填结果时 MUST 写实际值，NEVER 照抄「3 次」。
4. ⚠️ **「订单保持待支付」这个措辞与状态机不符**：失败落的是 `FAIL`（终态）或 `RETRY`，**没有「待支付」这个值**。最接近的是 `INIT`（已落单未发起）。
5. **重试机制的可验证形态是三条独立链路，不可相互替代**：

| 端点 | `sys_job` | cron | 扫表状态白名单 | 退避 |
|---|---|---|---|---|
| `/internal/gate-txn-pay/debit/retry/default` | 220「行程扣费重试」 | `0 0 1 * * ?` | `isBatchRetryable` = `RETRY` + **`FAIL`**（`DebitStatus.java:47`） | 写 `DEBIT_RETRY_TIMES` + `DEBIT_NEXT_RETRY_TIME`（`backoffMinutes` 默认 720） |
| `/internal/gate-txn-pay/debit/retry/alipay` | 255「行程扣费重试(支付宝出行)」 | `0 0 1 * * ?` | 同上，只捞支付宝出行渠道 | 同上 |
| `/internal/gate-txn-pay/debit/retry/recent` | 345「补站扣费周期查询更新」 | `0 0/1 * * * ?` | **多捞 `INIT`**：`INIT`/`RETRY`/`FAIL`（`GateTxnPayMapper.java:226`），只看 `CREATE_TIME` 落在近 10 分钟内 | **刻意不写退避**（业主裁决） |

   - 345 **刻意不写 `DEBIT_RETRY_TIMES` / `DEBIT_NEXT_RETRY_TIME`**，代价是一笔 `RETRY` 单在 10 分钟窗口内**最多被重发 10 次**。**这是已知并接受的代价，不是缺陷，测试时看到「同一笔被发多次」NEVER 报成 bug。**
   - 防重扣只剩三道闸：`recent.minAgeSeconds=60` 下界、`recent.windowMinutes=10` 上界、排除 `DISCOUNT_CALC_STATUS='OFFLINE_FARE_PENDING'`。**三者 NEVER 删任何一个。**
6. **运营页面的单笔重试与批量重试口径不同**：页面走 `isRetryable`（只 `INIT`/`RETRY`，**不含 `FAIL`**，`DebitStatus.java:33`），批量走 `isBatchRetryable`（含 `FAIL`）。**因此「页面上点不动的单，批量任务会重发」是设计，不是缺陷。**
7. 达到 `maxTimes` 后的可验证断言：该单不再被扫表谓词命中（判定写在扫表 SQL 的 `DEBIT_RETRY_TIMES < :maxTimes`，列注释 `gate-txn-pay-debit-retry-migration.sql:8`），人工排查用 `DEBIT_RETRY_TIMES >= 上限` 过滤。

② DB 核对 SQL

```sql

  FROM GATE_TXN_PAY WHERE ORDER_NO = '<订单号>';

-- 已到上限、不再被扫的单（<上限> 用 Deployment env 实际值，默认 5）
SELECT COUNT(*) FROM GATE_TXN_PAY WHERE DEBIT_RETRY_TIMES >= <上限>;

-- 按语义码分类
SELECT DEBIT_FAIL_CODE, COUNT(*) FROM GATE_TXN_PAY
 WHERE DEBIT_FAIL_CODE IS NOT NULL GROUP BY DEBIT_FAIL_CODE;
```

### 结果

**PASS（补偿端点部分）+ B1 已证明**（2026-09-22 批次二实跑）。

- 三个重试端点确认是**三个独立入口**，逐字应答分别为「补站扣费周期查询更新本轮处理 0 笔」/「行程扣费重试(非支付宝)本轮处理 0 笔」/「支付宝出行重试扣费本轮处理 0 笔」（对应 `sys_job` 345 / 220 / 255）。
- 早一轮对 `GT20260922112144141000014` 连打 `recent` + `default`，`DEBIT_RETRY_TIMES` **只加 1 次**（0→1）、`DEBIT_NEXT_RETRY_TIME` `null→2026-09-22 23:26:11` —— 这正是 ADR-D154「345 刻意不写记账」的实证，**不是重试计数漏记**。
- 补款收敛对不存在的订单返 `{"retCode":"8001","retMsg":"未找到对应的过闸扣费订单","converged":false}`（零写）；对真实 `INIT` 单能推成 `SUCCESS`（已按原值还原）。**缺 `txnDate` 返 `0000` 不是缺陷** —— `GateTxnPayServiceImpl.java:343` 按订单自身 `TXN_DATE` 回填，属有意补白。
- **B1 成立**：`gate-txn-pay-server` 没有独立的「扣费失败交易表」，失败态就是 `GATE_TXN_PAY.DEBIT_STATUS IN ('RETRY','FAIL')`（`GateTxnPayMapper.xml:633`）。原表第 5 条「计入扣费失败交易」与备注「未实现」的矛盾，按代码判定为**没有这张表**。
- **B14 成立且被加强**：11 个 `gate.debitRetry.*` 键在仓库 properties 里全部缺失、只有 `@Value` 默认值（`DebitRetryProcessor.java:83-93`），本轮三条 0 笔应答同时证明默认值**确实在线上生效**。
