## cardId 从哪来

`0426090951000084` 这个卡号的完整来源链，每一步都有代码位置：

1. **ACC 下发** — `card-pool-server` 经 IF7B-01 向 ACC 申请，ACC 只回 `fileName`、不回卡号（`CardPoolServiceImpl.java:662-679`）；FTP 取回文件后逐行解析，`parseCardNo` 取空白分列的**第 0 列**（`:1071-1085`，类注释 `:1063` 的真实样例行是 `0426090935000008 41`），入库 `LOGIC_CARD_POOL_CARD.CARD_NO`。所以 `0426...` 前缀不是 ITP 生成的，是 ACC 的编号规则。
2. **开户预占** — APP 点激活时先调开户，`AccountApplicationServiceImpl.java:1148-1155` 对非 HCE 票种一律 `reserveFromPool(issueCardType, "ACCOUNT_OPEN", thirdUserId + ":" + 票种, thirdUserId)` → `:1060` `cardPoolClient.reserve` → `:1075` 取 `data.getCardNo()`
3. **写注册表** — `:1348` / `:1476` `regInfo.setCardId(cardId)` → `USER_ITP_REG_INFO.CARD_ID`，本例 `REG_TMS=20260910130548`
4. **写乘车状态** — `:194` `ticketClient.registerRideStatus(buildTicketRequest(regInfo))`（`:1429` 把 `CARD_ID` 塞进 `request.setCardId`）→ `TicketRideStatusServiceImpl.java:85,99` → `QRCodeStatusMapper.upsert`，`CODE_STATUS` 取 `${ticket.default-code-status:03}`
5. **APP 拿去用** — 取码（IF8A-03）原样透传这个 cardId（`fep-app-server/.../IndustryDataServiceImpl.java:285`），闸机上送的也是它

关键点：**开户与日票激活各自向卡池预占一次，拿到的是两张不同的卡**。`LOGIC_CARD_POOL_CARD` 上有 `UK_LOGIC_CARD_POOL_BUSINESS UNIQUE (BUSINESS_TYPE, BUSINESS_ID)`，`ACCOUNT_OPEN` 与 `DAILY_TICKET_ACTIVATE` 必然落在不同行。

## 断点

APP 的激活请求**已经带了正确的 cardNum**：

```json
{"thirdUserId":"00522943","orderNo":"0E202609101131510006",
 "cardNum":"0426090951000084","ticketType":"12","cardIssue":"5412",
 "actualTimes":-99,"period":1,"countingStart":1789016749074,
 "transDate":1789011111850,"transSeq":0,"transAmount":1,
 "discountAmount":0,"showType":"12","payChannel":"03",
 "ticketCode":"2097890772727889920","ticketName":"地铁一日票",
 "operationDate":"20260910"}
```

但 `DailyTicketServiceImpl.java:521` 丢弃了它，改用第二次预占的卡号：`ticket.setCardNum(reservation.getCardNo())`。于是：

- 预占成功时 → `DAILY_TICKET_INSTANCE.CARD_NUM` 是另一张卡，`entryCheck` 按 `CARD_NUM` 精确匹配（`DailyTicketInstanceMapper.xml:137-143`）必然 0 行
- 预占失败时（本例）→ 整个激活回滚，实例根本不落库，同样 0 行

两条路都通向 `无有效日票记录`。ticket-server 侧三处把开户卡号当 `CARD_NUM` 用：`GateTicketHandler.java:114` `entryCheck`、`:188` `markUsed`、`:248` → `DailyTicketServiceImpl.java:641-642`（字段名 `cardId`、查的列 `CARD_NUM`）。

## 本次失败的直接原因

`cardType=45` 传给卡池，卡池按票种分区挑卡（实测 SQL `SELECT COUNT(1) FROM LOGIC_CARD_POOL_CARD WHERE CARD_TYPE = '0445' AND STATUS = 'AVAILABLE'`），`45` 不对应任何分区，预占返回 `code=null / msg=null`，被 `handleReserveFailure` 归为 `CALL_FAILED`。

`45` 的来路要往前推两层，**不是激活接口漏了映射**：

- `DailyTicketServiceImpl.java:504` 确实调了 `CardTypeMapping.toIssueCardType(order.getCardType())`
- 但入参取的是 `order.getCardType()`，即**下单时存进 `DAILY_TICKET_ORDER.CARD_TYPE` 的值**。本例下单入参是 `"cardType":"45"`
- `CardTypeMapping.java:12-19` 的映射表键只有 `03 / 04 / 11 / 12 / 13 / 14 / 15`，**没有 `45`**；`:33` 的 `ISSUE_CARD_TYPES.getOrDefault(normalized, normalized)` 对未知键**原样返回**
- 所以 `45` 一路穿到卡池

同一张票，APP 在两个接口用了两种票种口径：下单送 `cardType=45`，激活送 `ticketType=12`。规范口径是 `12`（映射表的键，`:27` `"12" → "0445"`）。这里要么是 APP 下单传参错，要么是 ITP 下单接口该校验/归一化却没做——`requestCountingOrder` 目前对 `cardType` 无白名单校验，非法值直接落库。

对比开户侧的正确做法：`AccountApplicationServiceImpl.java:169` 先 `toIssueCardType(request.getCardType())` 把 `12` 转成 `0445`，`:1049` 再用 `CardPoolTicketType.POOL_ENABLED_TYPES.contains(cardType)` 拦一道，非法票种当场 `log.error` 并返回 null，**不会把脏值送到卡池**。daily-ticket-server 侧缺这道白名单校验。


## 排查速查

按顺序核对，第一个不符的就是断点：

- 订单是否存在且已支付 → `daily-ticket-server` 日志搜 `orderNo`，或查 `DAILY_TICKET_ORDER.ORDER_STATUS`
- 支付回调是否到达 → 搜 `receivePayResult`，看 `payResult=SUCCESS`
- 卡号是否已注册 → `account` 日志（**Pod 名是 `account`，不是 `account-server`**）搜 `queryCardTypeByCardId`，或查 `USER_ITP_REG_INFO.REG_TMS`
- 乘车状态是否建行 → `ticket-server` 日志里 `IF1A-01 当前票卡状态` 那行，或查 `QRCODE_STATUS`
- **激活是否成功** → `daily-ticket-server` 搜 `updateTicket`，重点看有没有 `handleReserveFailure`；成功的标志是 `DAILY_TICKET_INSTANCE` 新增行
- 进站为何被拒 → `ticket-server` 搜 `日票进站校验`，`entryCheck` 的 `retMsg` 直接给出原因

日志命令：`scripts/klog.sh <服务名> <关键字> <行数>`。用卡号或 `orderNo` 当关键字最省事，`klog.sh` 会带出上下文。
