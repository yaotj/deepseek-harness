## D-001 `/app/payment/requestPay` 路由被占用 — 已修复待回归

**现象** APP 调 if8a_61 日票支付，返回 `retCode=8001 retMsg=amount不能为空`，APP 展示「创建支付渠道订单失败」。

**根因** 该地址在《ITP与APP接口规范R6》中属 if8a_61 日票支付，但 `PaySignController.java:45` 曾把它挂为 IF8A-19 通用请求支付的别名，请求被透传到 pay-sign-server；`PaySignWorkflow.validateRequestPay`（`:1297`）要求 `amount` / `subject` / `body` / `cardId` / `cardType` 五个必填，而日票 bizData 里都没有，第一个校验点即拦截。

**影响** 日票支付自 APP 侧上线以来不可用。2026-09-09 19:41 与 19:47 的两笔订单（`0E202609091941230001`、`0E202609091947130004`）因此卡在 `CREATED/INIT`。

**修复** 2026-09-09，`fep-app-server` 2.0.75：从 `PaySignController` 摘除该别名（只留 `/ci/app/requestPay`），归还给 `AppDailyTicketController.java:53`。同时补 `:61` `/app/payment/requestPayResult` 与 `:100` `/app/payment/receivePayResult` —— 这两条**此前根本未注册**，即使支付发起成功，结果查询与回调也进不来，订单会卡在 `PAYING`。

**回归** DailyTicket_Test_002 / 003 / 004 已于 2026-09-09 20:02~20:03 实测通过。

**遗留风险** 摘除 `PaySignController` 别名的前提是「没有其他调用方经该路径走 pay-sign」。判断依据是 pay-sign 的五个必填字段 APP 侧无场景能凑全、且规范里没有这个接口——**属推断，未实测排除**。需 APP 侧确认。

## D-002 激活 / 退款 / 取消订单缺扁平别名 — 未验证

## D-003 `DAILY_TICKET_PAY_LOG` 回调行不落 `RESULT_CODE` — 观察项

实测 `0E202609092002570005` 的两条日志：`BIZ_TYPE=PAY` 行 `RESULT_CODE=0` / `RESULT_MSG=成功`，`BIZ_TYPE=CALLBACK` 行两字段**均为 null**。

回调报文里有 `payResult=SUCCESS`，但没被抽取到 `RESULT_CODE`。对账时无法只靠该表判断回调结果，必须回查 `RESPONSE_BODY` 或订单状态。属可用性缺陷候选，未确认是否有意设计。

## D-004 未支付订单无过期回收 — 观察项

生产库 36 单订单中 **29 单停在 `CREATED/INIT`**，最早的是 2026-07-23。`daily-ticket-server` 全模块 grep `@Scheduled` / `@EnableScheduling` **零命中**，即没有任何定时任务把超时未付订单置为取消或失败。

后果：订单表长期堆积无效数据；APP 侧若展示「待支付订单」列表，会越积越多。取消订单接口存在（`cancelOrder`），但需 APP 主动调。

## D-005 `PLATFORM_REFUND_NO` 全为 null — 观察项

`DAILY_TICKET_REFUND` 抽样 7 条，`PLATFORM_REFUND_NO` 全部为 null，**包含已 `REFUNDED` 的那条**（`0E202607231550010001`）。

代码里有 `restorePlatformRefundNoFromPayLog`（`DailyTicketServiceImpl.java:870`）专门从历史网关响应恢复该字段，说明设计上期望它有值。退款查询依赖它做幂等关联（`:342` 起同时用 `refundOrderNo` 与 `merchantRefundNo`，注释明确「恢复失败时不降级为单字段查询，防止错误关联到其他退款单」）。该字段恒空是否影响退款收口，需在 Test_011 / 012 执行时重点观察。

## D-006 全程通（旅游票）激活缺失支付渠道字段 — 待确认/待跟进

**现象**（2026-10-10 测试跟进）：全程通票（= 全城通日票 = 旅游票，`orderType=2`，`DailyTicketOrderSupport.java:28`）激活后，`DAILY_TICKET_INSTANCE.PAY_CHANNEL` 缺失。

**代码事实**：
- 激活服务**没有从订单/主单回填支付渠道的逻辑**：`DailyTicketInstanceLifecycleService.updateTicket` 里只有
  `ticket.setPayChannel(request.getPayChannel())`（`:121`），`PAY_CHANNEL` 完全依赖 APP 在激活请求里传 `payChannel`。
- 激活入参 `DailyTicketActivateReqDTO` **有** `payChannel` 字段（`:78-80`），但无 Bean Validation、空值不会 400
  （`docs/business/README.md` 全局事实：全对外 DTO 零 Bean Validation）。
- 普通旅游票子单 `buildTravelSubOrder` **不写 `PAY_CHANNEL_CODE`**（`DailyTicketOrderCreationService.java:402-419`），
  子单恒 `CREATED/INIT`、`PAY_CHANNEL_CODE` 恒 null（主单聚合支付、子单恒不回写是设计，见 `docs/business/daily-ticket.md:136`）。
- 主单 `TRAVEL_TICKET_ORDER.PAY_CHANNEL_CODE` **有值**（2026-10-10 库实测：已支付旅游票主单 `PAY_CHANNEL_CODE=03`）。
- 免费旅游票子单 `requestFreeTravelOrder:328` 会写 `PAY_CHANNEL_CODE`，普通旅游票子单不写。

**库实测**（2026-10-10，`AFCITPDB`）：
- 已激活旅游票 `0E202609291647210012`（主单 `0T202609291647210011`，`PAID/PAID`，主单 `PAY_CHANNEL_CODE=03`）：
  `DAILY_TICKET_INSTANCE.PAY_CHANNEL=03`（有值，说明 APP 激活时主动传了 `payChannel`）；
  子单 `DAILY_TICKET_ORDER.PAY_CHANNEL_CODE=null`。
- 其余 10 个旅游票主单均未激活（无实例行），无法判断。

**影响**：
- **ACC 发售通知报文受影响**：激活时就地生成 ACC 通知 payload（`DailyTicketAccActiveNotifyService.preparePending:61` → `buildBizData`），
  其中 `payChannel` 取 `ticket.getPayChannel()`（`:129`，来自激活请求）。若 APP 激活不传 `payChannel`，ACC 通知报文 `payChannel` 为空。
- **IF8A-34 交易详情不受影响**：`queryDailyTicketPayInfo` 对旅游票用**主单**渠道码回填
  （`DailyTicketPaymentService.java:385`：`parent == null ? order.getPayChannelCode() : parent.getPayChannelCode()`），
  主单 `PAY_CHANNEL_CODE` 有值，因此详情接口能拿到支付渠道。
- 需进一步确认：ACC 侧对 `payChannel` 为空的发售通知是否拒收 / 是否影响后续对账。

**下一步**：①向 APP 侧确认激活旅游票时是否上送 `payChannel`；②确认服务端是否应从主单
`TRAVEL_TICKET_ORDER.PAY_CHANNEL_CODE` 回填实例 `PAY_CHANNEL`（目前无回填）；③补一条「APP 不传 payChannel 激活旅游票」的实测。
