# 01 下单与支付

公共请求形态：`POST application/x-www-form-urlencoded`，表单字段 `providerId=01&charset=UTF-8&format=json&signType=00&timestamp=<yyyyMMddHHmmss>` + `bizData=<JSON>`。

`fep-app-server` 无验签代码、`sign` 原样透传，`signType=00` 即免签，因此用例可不带 `sign`（2026-09-09 实测通过）。网关入口 `http://58.56.166.170:48000/fep-app/...`，集群内可直连 `http://fep-app-hr32k-svc.itp.svc:9101/...`。

## DailyTicket_Test_002 日票支付发起

**接口** `/app/payment/requestPay`（if8a_61）

**前置** Test_001 的订单处于 `CREATED/INIT`

**bizData**
```json
{"thirdUserId":"00522949","orderType":"1","orderNo":"<Test_001 的 orderNo>","payChannelCode":"03","phone":"19037529560","channelType":"1"}
```

**预期**
- 响应 `retCode=0000`，`paymentInfo` 为支付宝 app 支付串（含 `app_id=`、`biz_content=`、`sign=`），`signType=01`，`payChannelCode=03`
- 订单更新为 `ORDER_STATUS=PAYING`、`PAY_STATUS=PAYING`，并回填 `THIRD_USER_ID`、`PAY_CHANNEL_CODE=03`、`CHANNEL_TYPE=1`、`PAY_SCENE=app`
- `DAILY_TICKET_PAY_LOG` 新增 `BIZ_TYPE=PAY` 行，`RESULT_CODE=0`、`RESULT_MSG=成功`
- daily-ticket-server 日志有 `日票服务准备调用支付网关支付接口`，出参 `amount` 等于订单 `TICKET_PRICE`、`subject`/`body` 为 `el-ticket`

**注意** `amount` / `subject` / `body` 由 daily-ticket-server 从订单补齐，**APP 不传**。若响应是 `retCode=8001 amount不能为空`，说明请求被路由到了 pay-sign-server，见 03 页 D-001。

**结果** 2026-09-09 20:02:58 通过，网关返回 `code=0`、`orderNo=287539830177300480`，fep-app 侧耗时 1144ms。

## DailyTicket_Test_003 支付成功回调置终态

**接口** `/app/payment/receivePayResult`（网关 → ITP，`JSON` body，非表单）

**触发方式** 在 APP 内完成支付宝付款，由网关主动回调。回调地址来自 daily-ticket-server 自己上报的 `daily-ticket.pay.notify-url`（`daily-ticket-server/src/main/resources/application.properties:28`），**不由 APP 指定**。

**回调报文（实测）**
```json
{"orderNo":"0E202609092002570005","tradeNo":"287539830177300480","paymentOrderNo":"287539830177300480","payResult":"SUCCESS","payAmount":1,"payDate":"2026-09-09T12:02:38.000+00:00"}
```

**预期**
- 订单变为 `ORDER_STATUS=PAID`、`PAY_STATUS=PAID`
- 回填 `TRADE_NO`、`PAYMENT_ORDER_NO`、`PAY_AMOUNT`、`PAY_DATE`
- `PAY_AMOUNT` 与订单 `TICKET_PRICE` 一致（不一致即为金额不符缺陷）
- `DAILY_TICKET_PAY_LOG` 新增 `BIZ_TYPE=CALLBACK` 行
- **此时 `DAILY_TICKET_INSTANCE` 仍无该订单的行**，票实例要到激活（Test_009）才生成

**结果** 2026-09-09 20:03:06 通过。`PAY_DATE=2026-09-09 20:02:38.0`（注意回调用 UTC，落库转为本地时间，比 `CREATE_TIME` 早 19 秒属正常）。

## DailyTicket_Test_007 同一订单重复发起支付

**前置** 订单处于 `PAYING/PAYING`（Test_002 之后、未付款）

**步骤** 再次调 `/app/payment/requestPay`

**预期**（`DailyTicketServiceImpl.java:137-147` 分支）
- 先主动向网关查一次支付结果并刷新本地状态
- 若网关侧已成功 → 直接返回 `retCode=0000`（幂等成功，不重复下单）
- 若网关侧已失败 → `支付已失败，请重新下单`
- 否则 → `支付处理中，请查询支付结果`

**关注点** 三个分支都**不会**再次调用网关 `requestPay`，因此不应产生第二条 `BIZ_TYPE=PAY` 日志。若出现两条，即为重复下单缺陷。

**结果** 未执行。
