# route-sentinel 分流功能测试与性能评估方案

---

## 1. 测试目标

1. **功能正确性**：验证 6 条设备域接口在新订单 / 旧订单 / 新用户 / 老用户 / 无标识各场景下，请求被正确路由到**新 ITP（`face-pay-server`）**或**旧 ITP（`172.20.202.10`）**，并拿到预期业务响应。
2. **fail-safe 兜底**：验证 DB 查询失败 / 标识缺失时，请求降级到旧 ITP 而非报错或丢失。
3. **性能评估**：给出「是否需要做性能测试」的明确结论与依据（见 [§8](#8-性能测试评估)）。

## 4. 分发判定逻辑（测试设计依据）

网关对每条分流请求按「命中即返回」顺序判定，返回 `true` → 旧 ITP，`false` → 新 ITP：

1. **非分流路径** → 直接走默认路由（新 ITP），不进入判定。
2. **订单归属优先**（TVM 4 条）：报文不带用户标识，取 `bizData.orderNo`，缺失则取 `randomFact`，反查 `F2F_ORDER`：
   - 查到订单 → `NEW`（新 ITP）
   - 查不到 / 查询失败 → `LEGACY`（旧 ITP，fail-safe）
   - 两者都缺 → 继续走步骤 3
3. **有 `cardId`** → `NEW`（新系统用户）
4. **`cardId` 与 `thirdUserId` 都缺** → `LEGACY`（兜底，fail-safe）
5. **有 `thirdUserId`** → 查 `USER_ITP_REG_INFO`（Caffeine 缓存，max 10000 / TTL 5min）：
   - 有记录 → `NEW`；无记录 / 查询失败 → `LEGACY`（fail-safe）

**关键：TVM 走订单归属判定，BOM 走用户属性判定，两者测试数据准备方式不同。**

## 5. 测试数据准备

### 5.1 订单归属数据（TVM 4 条用）

准备两组订单号，分别代表「新 ITP 订单」与「非新 ITP 订单」：

```sql
-- 查询测试环境已有的新 ITP 订单号（取一个作为「新订单」样本）
SELECT order_no, random_fact FROM QDITP.F2F_ORDER WHERE ROWNUM <= 5;

-- 验证某订单是否为新 ITP 订单（有返回 = 新订单 → NEW）
SELECT COUNT(*) FROM QDITP.F2F_ORDER
 WHERE order_no = '<订单号>' OR random_fact = '<二维码>';
```

- **新订单样本**：从上面查询结果中取一个真实存在的 `order_no`（预期 → NEW）。
- **旧订单样本**：用一个确定不存在的订单号，如 `NOT_EXIST_ORDER_20261116`（预期 → LEGACY）。

### 5.2 用户数据（BOM 2 条用）

```sql
-- 新用户样本（已存在）
SELECT third_user_id FROM QDITP.USER_ITP_REG_INFO WHERE third_user_id = '00522967';

-- 老用户样本：确认不在名单表中的 thirdUserId
SELECT COUNT(*) FROM QDITP.USER_ITP_REG_INFO WHERE third_user_id = 'legacy_test_20261116';
-- 期望返回 0
```

> **缓存注意**：`USER_ITP_REG_INFO` 有 Caffeine 缓存（TTL 5 分钟）。增删测试用户后，等待 5 分钟或由后端重启 route-sentinel Pod 使缓存失效，否则判定可能沿用旧值。

### 5.3 bizData 与报文格式

设备域请求为 `application/x-www-form-urlencoded` 表单，`bizData` 是表单里的一个字段，值为 **JSON 字符串**（不支持 Base64）。公共字段见 `docs/testing/api-inventory/05a-face-pay-tvm.md` §0。

最小表单字段：

| 字段 | 示例值 | 说明 |
|---|---|---|
| `providerId` | `02`（TVM）/ `03`（BOM） | 商户编码 |
| `charset` | `UTF-8` | |
| `format` | `json` | |
| `timestamp` | `20261116150000` | YYYYMMDDHHMMSS |
| `deviceId` | `TEST_TVM_001` | 设备编码 |
| `signType` | `00` | 不签名 |
| `bizData` | `{"orderNo":"..."}` | 业务数据 JSON 字符串 |

bizData 示例：

```text
订单归属（新订单）: bizData={"orderNo":"<真实新订单号>"}
订单归属（旧订单）: bizData={"orderNo":"NOT_EXIST_ORDER_20261116"}
用户属性（新用户）: bizData={"cardId":"..."}  或  bizData={"thirdUserId":"00522967"}
无标识（兜底）    : 不传 bizData 或 bizData={}
```

## 8. 性能测试评估

### 8.1 结论

**建议做一轮轻量级性能验证，无需做完整大规模压测。** 理由是网关本身逻辑轻量，但存在一个明确的容量风险点值得量化验证（缓存未命中穿透 DB）。

### 8.2 评估依据

| 维度 | 现状 | 风险判断 |
|---|---|---|
| 网关逻辑 | 纯路由判定，`BizDataExtractor` 字符串扫描零 JSON 解析 | 单次 CPU 开销极低，非瓶颈 |
| 资源 | 1 核 / 2Gi，单副本 | 单副本是单点，但测试环境量级下够用 |
| 用户缓存 | Caffeine max 10000 / TTL 5min，启动预热（测试环境当前预热 1017 个） | 命中时无 DB 访问，性能极好 |
| **DB 回源** | **缓存未命中的老用户/新用户首次请求要查 `F2F_ORDER` / `USER_ITP_REG_INFO`；Hikari 池 max 30 / connect-timeout 3s** | **唯一容量风险点：高并发 + 大量缓存未命中时，可能打满连接池、请求悬挂** |
| 订单归属查询 | 每条 TVM 请求都查 `F2F_ORDER`（无缓存，`SELECT COUNT(*)`） | 与用户缓存不同，**每请求必查 DB**，是持续 DB 压力来源 |
| 下游 | 新旧 ITP 各自处理能力 | 压测会传导到下游，需 CONTROL 范围 |

### 8.3 建议的性能验证项（轻量，非全链路压测）

| 项 | 方法 | 关注指标 | 通过参考 |
|---|---|---|---|
| P1 基准吞吐 | 对 1 条 TVM 接口（新订单，命中订单查询）逐步加压 | TPS、P95/P99 延迟、CPU | 单核下 CPU 未持续打满，P99 在业务可接受范围（建议 < 500ms） |
| P2 缓存命中路径 | 对 1 条 BOM 接口用已预热新用户压测 | TPS、DB 查询次数 | 命中缓存时 DB 无新增查询，延迟显著低于 P1 |
| P3 缓存未命中穿透 | 用大量不同 `thirdUserId` 并发请求 | DB 连接池占用、错误率、延迟 | 无大量超时/5xx，连接池未耗尽 |
| P4 稳定性 | 按预期日常峰值 QPS 持续 10~15 分钟 | 内存、GC、延迟抖动 | 无内存泄漏、延迟稳定 |

> P1 与 P3 是关键：P1 代表「每请求必查订单表」的常态压力，P3 代表「缓存击穿」的极端压力。若这两项有余量，则无需更大规模压测。

### 8.4 何时升级为完整性能测试

出现以下任一情况，建议升级为完整性能压测（含生产规格资源、全链路、长稳压测）：

1. 预计上线后设备域峰值 QPS 超过 **单副本 1 核**的承载能力（P1/P3 指标触顶）；
2. 用户规模使 `USER_ITP_REG_INFO` 远超缓存容量（10000），或缓存命中率低导致 DB 回源频繁；
3. 生产环境资源规格与测试环境差异大，需按生产规格重新标定；
4. 业务方给出明确的性能指标要求（如「支持 X TPS、P99 < Y ms」）。
