## A 系列：预期不成立或功能缺失

### A1 · APP 域入向无强制验签（是「能 curl 模拟」的前提，也是安全缺口）

- **事实**：`fep-app-server` 无验签代码，`sign` 原样透传（`AGENTS.md` §2.2.1）。落 `account-server` 的请求走 `AccountRequestVerifier` 摘要式校验，**`signType=00` 免签**。`POST /app/changePhone`（`fep-app-server/.../controller/PhoneChangeController.java:27`）与 `POST /app/cancelAccount`（`AppAccountController.java:104`）都是**状态变更型**接口，当前无验签、无归属校验。
- **影响**：本库全部用例之所以能用 curl 造，靠的就是这条；反过来说，任何网络可达方都能按第三方用户号操作他人数据。
- **与规范的冲突**：`AGENTS.md` §5.2「新增状态变更型接口 MUST 有鉴权与归属校验」。
- **处置**：未裁决。销户侧的同一问题已在 `docs/testing/user-card/05-阻塞项与缺陷候选.md` 记为 B7、换绑侧记为 B1，**本条不重复裁决**。

### A2 · P0：`trxType=03` 出站时多日计次票一次都不扣（两头落空）

- **代码定位**：`GateDailyTicketCoordinator.java:125` 用 `TrxTypeCodeEnum.EXIT.getCode()` **精确等值只认 `"02"`**；而同枚举 `TrxTypeCodeEnum:43` 的 `isExitTxn()` 明确把 `02`/`03` **都当出站**。
- **后果**：闸机送 `trxType=03` 时整段扣次逻辑直接 `return` —— 不扣次、不推进 `TICKET_STATUS`、不发 §3.63 通知；而同一笔照常触发扣费链路（`GateFarePaymentOrchestrator.shouldPay` 用的是 `isExitTxn`），金额又已被 `GateCardTypeEnricher.java:158` 连同车费一起清零 ⇒ **既没扣次也没扣钱，等于免费乘车一次**。
- **影响的用例**：`APP_test_002`（断言 6）、`APP_test_007`（断言 7）。
- **来源**：`AGENTS.md` §2.2.2「超时处理」；唯一入口文档 `docs/business/overtime-handling.md`。
- **处置**：未修复。**修它会连带推翻 §3.63 的「`times` 恒传 1」口径**（一旦可能为 2，通知宿主 MUST 从 `GateDailyTicketCoordinator` 迁到 daily-ticket 侧），因此不是单点小改。

### A3 · 「有欠款时不能进站」在服务端不成立

- **事实**：IF1A-01 进站链路里**未找到**任何「欠费即拒绝」的判定。`GateTxnPayAppController.java:85`（IF8A-35）只是**查询**未支付 + 扣费失败订单数，供 APP 自行提示；`BlacklistController.java:84`（IF8A-73 `queryBlackList`）也是 APP 主动查。
- **同族已记事实**：黑名单是「APP 查了、服务端不拦」（`docs/testing/user-card/05-阻塞项与缺陷候选.md` 的 A3）。
- **影响的用例**：`APP_test_004` 子场景 5。
- **待澄清**：拦截到底应该在 APP、闸机本地黑名单，还是 ITP 服务端？**必须真机 + APP 才能确认现状拦在哪一层。**

## B 系列：预期不可直接验证 / 口径需澄清

### B1 · `IF8A-73` 编号撞号（查询黑名单 vs 免费票下单）

- **事实**：两处都标 `IF8A-73`：
  - 查询黑名单 `POST /ci/app/queryBlackList`（`fep-app-server/.../controller/AppTicketController.java:37`，编号在 `:39`）
  - 免费票请求下单 `POST /app/ticket/requestOrderFree` 等（`AppDailyTicketController.java:62`，编号在 `:65`）
- **背景**：`AGENTS.md` §2.2.1 已记「接口编号不唯一映射到一处代码」（IF8A-04/05/06 在 APP 域与 BOM 域含义不同；IF8A-09/10/11/20 多模块重复实现）。本条是该现象的**又一个实例**。
- **约束**：定位实现 **MUST 以「模块 + URL」为准，NEVER 按编号查**。

### B2 · 「二维码变为进站码 / 出站码」「乘车码切换」不可直接验证

- **事实**：`QRCODE_STATUS` 只有 `CODE_STATUS`（`02`/`03`/`04`/`05`/`06`/`08`/`09`/`10`/`80`/`81`），**没有「码类型」列**。「该出示进站码还是出站码」「切到日票码」都是 APP 依 `CODE_STATUS` 自行判定的**展示逻辑**。
- **影响的用例**：`APP_test_001` / `002` / `003` / `005` / `006`（切换页面）/ `007`（切换日票）/ `009` / `017`。
- **本库处置**：统一改写为 `CODE_STATUS` 的状态取值断言，并把「界面切换」列入「真机才能覆盖的部分」。

### B3 · 「次票次数限制」与 `requestBuySinlgeTicketMaxNum` 不是一件事

- **事实**：IF8A-09 `requestBuySinlgeTicketMaxNum`（`AppParaController.java:33`，`collect-ticket-server` 另有同名 `TicketCollectController.java:41`）返回的是**单次购买单程票的最大张数**。`AGENTS.md` §2.2.2 明确「`ParaClient` 的 `requestBuySinlgeTicketMaxNum` 是购票张数、**不是票价**」。
- **原表预期**「超过次数作废，不能继续使用」指的是**乘车次数**（多日计次票的次数），落在 `GATE_TXN_PAY.COUNTING_TIMES` / `DAILY_TICKET_USAGE_LOG`。
- **影响的用例**：`APP_test_008` 第 4 步。
- **待澄清**：原表这一步到底测张数上限还是乘车次数上限。

### B4 · 「支付宝中扣款标题『票务事务』」未找到我方字段

- **事实**：`票务事务` 全仓 grep 零命中。该标题由支付宝侧商户配置或出向报文的商品名决定。
- **影响的用例**：`APP_test_017` 第 2 步。
- **待澄清**：**MUST 先确认是我方哪个字段在传**（若确实是我方传，则应能在 `face-pay-server` / `alipay-pay-sign-server` 的出向组装里找到）。本库不推断。

### B5 · IF8A-05 / 34 / 41 落点二义（`ticket-server` 与 `trans-query-server` 并存）

- **事实**：`trans-query-server`（9113）的三条 URL 与 `ticket-server` 的 `TicketTransController`（`:33` / `:45` / `:57`）**逐字一致、并存未替换**。`trans-query-server` 已接线并在承接**支付宝渠道**的真实流量（`fep-alipay` 的 `/channel/findTravelList` 转发到它）；**APP 域那三条尚未切过来**（`fep-app-server` 的 `service.ticket.url` 仍指向 ticket-server）。

### B7 · tracing 名单决定了「按 traceId 串链路」能串到哪

- **事实**：`%X{traceId}` 只在 **8 个模块**里有值：`pay-sign-server`、`card-pool-server`、`recon-server`、`gate-txn-pay-server`、`daily-ticket-server`、`collect-pay-server`、`face-pay-server`、`alipay-pay-sign-server`。

### B9 · ~~**P1 真缺陷：IF8A-41 账单统计漏做日期归一化，按契约格式调用恒返 count=0**~~ → **已修复（`trans-query:1.0.14`，2026-09-22 已部署 + 回归通过）**

- **代码定位（一行之差）**：`trans-query-server/src/main/java/com/chinasofti/huateng/transquery/query/TransStatisticsQueryHandler.java` 的 `requestTransStatistics`（`:30`~`:47`）**从不调用 `paramNormalizer.normalizeDate`**；而同模块 `TransListQueryHandler.java:60-66` 调了：

  ```java
  String startDate = paramNormalizer.normalizeDate(request.getStartDate());
  String endDate = paramNormalizer.normalizeDate(request.getEndDate());
  ```
  `TransQueryParamNormalizer.java:26` 的 `normalizeDate` 是「按 `yyyy-MM-dd` 解析后 `replace("-","")`」。
- **为什么恒 0**：下游 `gate-txn-pay-server/src/main/resources/mapper/GateTxnPayMapper.xml:459-490` 的 `selectTransStatistics` 直接把这两个值与 8 位 `TXN_DATE` 做字符串比较（`AND TXN_DATE &gt;= #{request.startDate}` / `&lt;= #{request.endDate}`）。`'20260920'` vs `'2026-09-22'` 第 5 位 `'0'`(0x30) > `'-'`(0x2D) ⇒ `<=` **恒 false**。

### B11 · 契约事实：`cardType` 是 **APP 侧码**，送发卡卡类型必 `8001`

### B12 · 落点事实订正：IF8A-05 / 34 / 41 三条实际落在 `trans-query-server`，不是 `ticket-server`

### B14 · 响应字段名与 DB 列名不同源，金额格式也不统一

- **`totalAmount` 不等于 DB 列 `TOTAL_AMOUNT`**：详情返 `totalAmount=700`，而按 `TOTAL_AMOUNT` 汇总的 `totalDebit` 是 `0`（04 的 B5 vs B6e）。**NEVER 拿应答字段名去猜列名。**
- **同一字段两种格式**：账单统计 count=0 那支返 `"0.00"`（两位小数），有数据那支返 `"9"`（无小数）。**前端按定长解析会出错**；本库断言 MUST 按「数值相等」而非「字符串相等」写。

### B15 · 口径疑问（不裁决）：多日计次票的「优惠金额」等于全额原价

- **待澄清**：甲方对「优惠金额」的定义是否包含「按次票种的免扣金额」？**MUST 向业务确认，NEVER 自行改 SQL 口径。**

### B16 · 判据更正：APP 域「端点不存在」也是 HTTP 200 + UUID，NEVER 用 404

- 实测 `POST /ci/app/requestTransListXX` → `{"retCode":"b75d6159-ddb6-4945-a424-f086de5a8f18","retMsg":null,"data":null}`，`http=200`（04 的 B14）。

### B17 · 码值字典补漏：`8002` / `8004` / `1001` / `8001` 的实测语义

| 码 | `retMsg` 实测原文 | 语义 | 注意 |
|---|---|---|---|
| `8001` | `无效的参数` / `日期格式非法: ...` / `卡类型非法: 0445` | 参数非法，`retMsg` 带具体原因 | ⚠️ 黑名单查询返 `8001` 时 **`inBlack` 仍是 `"0"`** —— **只看 `inBlack` 会把「查询失败」误读成「不在黑名单」**，断言 MUST 先钉 `retCode=0000`（04 的 B3） |
