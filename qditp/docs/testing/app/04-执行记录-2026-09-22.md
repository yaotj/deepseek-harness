# 04 · 执行记录 · 2026-09-22（APP 域只读用例第一批）

本页是**执行记录，只增不改**。每条含：真实请求（可原样重放）、**逐字应答原文**、DB 核对（库 `AFCITPDB`，经 `mcp_database_qd`）、结论。

**本轮口径（用户明确）**：

- **只跑只读接口**。票卡状态 / 行程查询 / 交易列表 / 账单统计 / 欠费查询 / 黑名单查询 / 参数类查询。**写操作一律不做**，相关用例在 `01`~`03` 里标「本轮未执行（写操作，待批次二）」。
- 全部经 `ssh k8s-master`，直打 NodePort（**NEVER 用 `<svc>.itp.svc:<port>`** —— 那台宿主节点无 CoreDNS，一律 `http=000`）。
- **每条都记 http 状态码与 body**。`http=200` 不代表业务成功。
- **报文字段名一律取自 DTO 源码**，不照抄甲方文档 —— Fastjson2 宽松模式**静默丢弃目标 DTO 里不存在的字段、不报错不告警**，字段名写错的表现是「那个条件像没生效」而不是报错。
- **模拟上送 ≠ 真机链路**：本页所有请求都是 curl 造的报文，`sign` 未验（`fep-app-server` 无验签代码、`sign` 原样透传）。**真机才能覆盖的部分**：APP 客户端自己的加签、码体本地解签、闸机物理开合、APP 页面渲染与轮询节奏。

## ⚠️ 本轮两条方法论更正（MUST 先读）

**① 判「端点是否存在」NEVER 用 HTTP 404。** 我方 `/ci/**` 入向端点打错名字返的是 **HTTP 200 + UUID 形态 `retCode`**：

```

http=200
{"retCode":"b75d6159-ddb6-4945-a424-f086de5a8f18","retMsg":null,"data":null}
```

`AGENTS.md` §2.2.2 §3.63 那条「404 = 不存在」**只适用于我方出网打 APP（第三方）侧的 `/app/receiveXxx` 通知端点**（对端是 APP 的容器、没有我方这套全局异常处理器）。两者 **NEVER 混用**，详见 `docs/testing/device-sle/02-阻塞项与缺陷候选.md` C12。

**② 拿到 UUID `retCode` 时 MUST 去服务端日志取那行原文**，NEVER 直接判「接口不存在」。UUID 至少 5 种成因：事务内 RPC 超时 / `service.*.url` 指向自身 / 路径无 handler / SQL 被 Druid WallFilter 拒 / 入参反序列化失败。取法 `scripts/klog.sh <服务名> <关键字> 300`（仓库根执行）。**NEVER 套用上次结论。**

## B6 · IF8A-41 账单统计 · **FAIL（真缺陷，根因已定位到行）**

六次探针，用同一个用户与卡：

| 探针 | `cardType` | 日期格式 | 应答 |
|---|---|---|---|
| B6a | `0445` | `yyyy-MM-dd` | `8001 卡类型非法` |
| B6b | `0441` | `yyyy-MM-dd` | `8001 卡类型非法` |
| B6c | 不送 | `yyyy-MM-dd` | `0000`，**count=0** |
| **B6d** | `12` | `2026-09-01` ~ `2026-09-22` | `0000`，**count=0 ← FAIL** |
| **B6e** | `12` | `20260901` ~ `20260922` | `0000`，`{"totalPrice":"9","totalDebit":"0","totalDiscount":"9","totalOvertime":"0","count":2}` |
| B6f | `12` | 不送日期 | 同 B6e，count=2 |

**B6d 应答原文**

```
http=200
{"retCode":"0000","retMsg":"成功","tripData":{"totalPrice":"0.00","totalDebit":"0.00","totalDiscount":"0.00","totalOvertime":"0.00","count":0}}
```

**根因（代码定位，一行之差）**

- `trans-query-server/.../query/TransStatisticsQueryHandler.java`（全文 110 行）的 `requestTransStatistics`（`:30`~`:47`）：校验 `thirdUserId` → `paramNormalizer.expandCardTypes`（`:38`）→ `setCardIdList`（`:45`）→ RPC `gateTxnPayClient.requestTransStatistics(request)`（`:47`）。**整段从不调用 `paramNormalizer.normalizeDate`。**
- 对照 `TransListQueryHandler.java:60-66` —— 交易列表**有**这一步：

  ```java
  String startDate = paramNormalizer.normalizeDate(request.getStartDate());
  String endDate = paramNormalizer.normalizeDate(request.getEndDate());
  ...
  request.setStartDate(startDate);
  request.setEndDate(endDate);
  ```

- 下游 `gate-txn-pay-server/src/main/resources/mapper/GateTxnPayMapper.xml:459-490` 的 `selectTransStatistics` 直接拿这两个值比 `TXN_DATE`：

  ```sql
  <if ...>AND TXN_DATE &gt;= #{request.startDate}</if>
  <if ...>AND TXN_DATE &lt;= #{request.endDate}</if>
  ```

  `TXN_DATE` 是 8 位串（`20260920`），与 `'2026-09-22'` 做字符串比较时第 5 位 `'0'`(0x30) > `'-'`(0x2D) ⇒ `<=` **恒为 false** ⇒ **count 恒 0**。

**判定链（四步全闭合）**

1. DB 等价 SQL 经 MCP：`CNT=2, TOTALPRICE=9, TOTALDEBIT=0` ⇒ 数据存在。
2. `ticket-server` 日志零条 IF8A-41 命中 ⇒ 不在那儿。
3. `fep-app` 日志 `TicketAppServiceImpl.java:79` 显示转发到 `http://trans-query-57wpd-svc.itp.svc:30035/ci/app/requestTransStatistics` ⇒ **落点是 `trans-query-server`**。
4. `trans-query` 日志 `TransStatisticsQueryHandler.java:58`：`cardTypeList=[0445], cardIdList=[0426090951000129]` 而 count=0 ⇒ 卡类型展开正常，问题在日期。
5. B6e / B6d 对照（8 位有数据、`yyyy-MM-dd` 无数据）**决定性确认**。

**影响**：IF8A-05 要求 `yyyy-MM-dd`（B4a），**APP 按同一规范送 IF8A-41 就必然拿到全 0** —— 账单统计对正常调用方从上线起从未返回过正确数字。

**结论：FAIL。** 已记进 `0X`。**NEVER 用「改成 8 位就好了」当修法** —— 那会让 IF8A-05 与 IF8A-41 契约不一致；正确修法是在 `TransStatisticsQueryHandler` 补 `normalizeDate`，与 `TransListQueryHandler:60-66` 对齐。

**另记一条口径疑问（不裁决）**：B6e 里 `totalPrice=9` 且 `totalDiscount=9`、`totalDebit=0` —— 多日计次票按次扣、不逐笔扣钱，于是「原价」全额进了「优惠」。**这是否符合甲方对「优惠金额」的定义 MUST 向业务确认**，已记进 `0X`。

**顺带两条格式事实**：count=0 那支金额是 `"0.00"`（两位小数），有数据那支是 `"9"`（无小数）—— **同一字段两种格式**，前端按定长解析会出错。

## 追加 · B9 修复与回归（2026-09-22 11:1x~11:3x，`trans-query:1.0.14`）

> 本段是**追加**，上面各节一字未改。本段只覆盖 B9 那一条 P1，其余 FAIL / 待澄清项不在本次范围。

### 一、缺陷 → 根因（复核结论：与 B9 记载一致，仅有一处需订正）

**缺陷**：IF8A-41 `POST /ci/app/requestTransStatistics` 按契约日期格式 `yyyy-MM-dd` 调用恒返 `count=0`。

**根因（复核后确认）**：`trans-query-server/src/main/java/com/chinasofti/huateng/transquery/query/TransStatisticsQueryHandler.java` 的 `requestTransStatistics` **从不调 `paramNormalizer.normalizeDate`**，而同包 `TransListQueryHandler.java:60-66` 调了。未归一的 `2026-09-22` 原样传到 `gate-txn-pay-server/src/main/resources/mapper/GateTxnPayMapper.xml` 的 `selectTransStatistics`（`:484-489`），那里是 `AND TXN_DATE <= #{request.endDate,jdbcType=VARCHAR}` —— 与 8 位 `TXN_DATE` 做**字符串**比较，第 5 位 `'-'`(0x2D) < 任何数字 ⇒ `<=` 恒 false ⇒ 0 行。**方向正确，修法即「补归一」。**

**唯一需订正的一处（与 B9 / B10 的表述有出入）**：B9 与 B10 合起来读会给人「IF8A-41 的入口也会拒 8 位」的印象，**修复前并不成立** —— 统计链路压根没调 `normalizeDate`，所以 8 位对它是**被接受**的（这正是 B6e 能出数的原因）。「8 位被拒成 `8001`」在修复前**只对 IF8A-05 列表成立**。修复后统计才与列表同源、8 位才开始被拒（见下面回归第 2 条）。
