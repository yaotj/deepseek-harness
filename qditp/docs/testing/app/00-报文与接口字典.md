## 一、报文骨架（对外契约）

- `Content-Type: application/x-www-form-urlencoded`
- 公共参数：`sign` / `charset` / `format` / `timestamp` / `deviceId` / `signType`（另有 `providerId`）
- 业务参数：`bizData`（JSON 字符串）
- 绑定类：`model/src/main/java/com/chinasofti/huateng/model/app/ItpCommonFormRequest.java`（继承 `ItpCommonRequest<String>`）。**全项目只有这一份 form 入向骨架**，`fep-app-server` 下已无自有副本。
- `toString()` 对 `sign` 恒定脱敏，但 `bizData` 会完整进日志 —— 日志判据可以直接 grep `bizData=`。

### 验签现状（决定 curl 能不能造）

- `fep-app-server` **没有验签代码**，`sign` 原样透传（`AGENTS.md` §2.2.1）。
- 落到 `account-server` 的请求由 `AccountRequestVerifier` 做摘要式校验，**`signType=00` 免签**。
- `ItpRequestSignVerifier`（SHA1 / MD5）用于另一批链路；`SHA256WithRSA` 只用于渠道（支付中心 / 支付宝）出向。

> **可 curl 模拟的前提就是这一条**：APP 域入向没有强制 RSA 验签，因此用 `signType=00` + 任意 `sign` 占位值即可打通 `fep-app-server`。**这是测试期现状，不是设计目标**，见 `0X-阻塞项与缺陷候选.md` A1。

## 二、入口地址形态（两种，任选其一）

### 形态 A：直打 NodePort（推荐，链路短、好定位）

```
http://172.20.211.23:<NodePort>/<Controller 路径>
```

- `<NodePort>` **待现查**：`ssh k8s-master "kubectl get svc -n itp"`，取冒号右边那个数。
- **NEVER 用 `<svc>.itp.svc:<port>`** —— `k8s-master` 不在 Pod 网络里、没有 CoreDNS，一律 `http=000`。
- 本页涉及的 Service 名同样**待现查**（Deployment / 容器 / Service 名不等于模块名）。

### 形态 B：经入向网关

```
http://58.56.166.170:48000/<VS 前缀>/<rewrite 后路径>
```

- APP 域前缀 `/fep-app/`，设备域前缀 `/fep-dev/`、`/itpagm/`、`/itptvm/`、`/itpbom/`。
- **`rewrite.uri` 与目标 host 都 MUST 现查**：`ssh k8s-master "kubectl get vs fep-app-vr -n itp -o yaml"`。`/itptvm/` 与 `/itpbom/` 两条的 rewrite **带前缀、不是 `/`**，照抄会 404。
- 判断某个业务域的流量落在哪个应用，**MUST 现查两处**：①上面那条 VS；②`fep-app` Deployment 的 `service.collectPay.url` env。**NEVER 在本文档里写死结论。**

## 五、日志判据通用写法

```bash
scripts/klog.sh <服务名> <关键字> 500
```

- **NEVER 用本机 `kubectl logs`** —— 本机 kubeconfig 只有 `orbstack` context。
- 关键字优先用接口编号（`IF8A-01`、`IF1A-01`…），Controller 里的 `log.info` 全部以编号打头。
- `scripts/klog.sh` **只看尾部窗口，且 Pod 一重启日志目录就消失**。要做全量巡检（比如找 `No static resource`）**MUST** `ssh k8s-master` 后逐 Pod `kubectl exec ... grep /home/javaapp/app/logs/*/*.log`。
- **`%X{traceId}` 只在 8 个模块里有值**（`pay-sign` / `card-pool` / `recon` / `gate-txn-pay` / `daily-ticket` / `collect-pay` / `face-pay` / `alipay-pay-sign`）。**`fep-app-server` / `ticket-server` / `account-server` / `key-server` / `blacklist-server` 都不在名单里**，按 traceId 检索这几个服务的日志恒 0 条 —— **这不是日志丢了**。
- **HTTP 200 + UUID 形态的 `retCode` 不是业务码**，是全局异常处理器的兜底，至少 5 种成因（事务内 RPC 超时 / `service.*.url` 指向自身 / 路径无 handler / SQL 被 Druid WallFilter 拒 / 入参反序列化失败）。遇到 **MUST** 去服务端日志取那行原文。

## 六、「模拟上送 ≠ 真机链路」的统一口径

本库全部用例的执行方式都是 **curl 直打端点、用构造报文替代真机动作**。以下部分**任何 curl 都覆盖不到**，每条用例会单列「真机才能覆盖的部分」：

1. **APP 客户端本身**：界面展示、页签切换、二维码渲染、弹窗文案、本地缓存。
2. **NFC 写卡 / HCE**：手机安全单元内的卡片数据、APDU 交互、卡片余额与状态写入。
3. **闸机本地校验**：码体解签验签、密钥版本匹配、黑名单本地表比对、闸门物理开合、离线判定。
4. **码体生成的正确性**：curl 拿到的是 `bizData` 里的码串，但「闸机能不能扫得出来 / 解得开」只有真机能证。
5. **TVM / BOM 设备**：现金模块、票箱、出票机构、打印。
6. **第三方 App 内的展示**：支付宝账单标题、微信扣款通知、SDK 宿主 App 的页面。
7. **时序与并发的真实分布**：真机是人操作，curl 是即时连发，`20 分钟` / `4 天` 这类时间窗只能靠改数据或等待。

### 7.1 端点存在性判据（**更正，优先级最高**）

**我方 `/ci/**` 入向端点不存在时返 HTTP 200 + UUID 形态 `retCode`，NEVER 用 404 判断。** 实测 `POST /ci/app/requestTransListXX` → `{"retCode":"b75d6159-ddb6-4945-a424-f086de5a8f18","retMsg":null,"data":null}`，`http=200`。

`AGENTS.md` §2.2.2 §3.63 那条「404 = 不存在」**只适用于我方出网打 APP（第三方）侧的 `/app/receiveXxx` 通知端点**，两者 NEVER 混用。拿到 UUID 后 **MUST 去服务端日志取那行原文**（`scripts/klog.sh <服务名> <关键字> 300`），`No static resource` 才是「路径无 handler」；UUID 至少 5 种成因，**NEVER 套用上次结论**。

### 7.2 码值表（本轮实测，`retMsg` 为原文）

| 码 | 实测 `retMsg` | 含义 | 陷阱 |
|---|---|---|---|
| `0000` | `成功` | 成功 | **仅表示「本次调用没抛错」**，不代表业务结果符合预期（假行程那条也是 `0000`） |
| `1001` | `bizData不能为空` / `bizData格式错误` / `keyCurVerList不能为空` / `cardId不能为空` | 参数缺失或格式错，**点名缺哪个键** | `retMsg` 可断言，MUST 按原文钉 |
| `8001` | `无效的参数` / `日期格式非法: 20260901，期望格式 yyyy-MM-dd` / `卡类型非法: 0445` | 参数非法，`retMsg` 带具体原因 | ⚠️ 黑名单查询返 `8001` 时 **`inBlack` 仍是 `"0"`** —— 断言 MUST 先钉 `retCode=0000` 再读 `inBlack` |
| `8002` | `无数据` | 目标单据不存在 | **本轮新增** |

### 7.6 响应字段与 DB 列不同源（断言时 MUST 分清）

- **应答 `totalAmount` ≠ DB 列 `TOTAL_AMOUNT`**：详情返 `totalAmount=700`，而按 `TOTAL_AMOUNT` 汇总的 `totalDebit` 为 `0`。**NEVER 拿应答字段名去猜列名。**
- **IF8A-29 的 `transSeq` 取 `QRCODE_TXN_DETAIL.TICKET_TRANS_SEQ`**，不是 `QRCODE_STATUS.TXN_SEQ`（后者是 CAS 推进后的值、大 1）。两者不同源、不是缺陷，但**核对时 NEVER 拿状态表那列去比**。
- **金额格式不统一**：账单统计 count=0 那支返 `"0.00"`、有数据那支返 `"9"`。断言 MUST 按「数值相等」写，NEVER 按字符串。

### 7.7 假行程的四项联合判据（IF8A-29）

未过闸的卡会返 `retCode=0000` + `thisStationName="FFFF"` + `thisTransTime="00000000000000"` + `transSeq="0"` + `ticketStatus="03"`。**四项同时出现即假行程**；链路是「`QRCODE_TXN_DETAIL` 查 0 行 → 回落 `QRCODE_STATUS` 占位 → para `requestStationNameBatch([FFFF])` 返空 → 原样回显」。**NEVER 只看 `retCode`，NEVER 把 `FFFF` 直接渲染给用户。**
