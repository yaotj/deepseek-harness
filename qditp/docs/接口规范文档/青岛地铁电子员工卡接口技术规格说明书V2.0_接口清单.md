## 二、ACC→ITP 接口

### 2.1 IF3A-01 员工信息推送

| 属性 | 值 |
|------|-----|
| 接口名称 | 员工信息推送 |
| 接口方向 | ACC → ITP |
| 场景描述 | ACC侧有用户新增、修改时，推送员工信息给ITP，一次推送一个用户 |
| 触发条件 | ACC系统中有员工信息新增或修改时 |
| 通信方式 | 同步HTTP POST |

#### 接口地址
```
http://[ITP_IP]:[port]/fep-acc/employee_card/push
```

#### 请求参数

| 参数名 | 类型 | 必填 | 长度 | 说明 |
|--------|------|------|------|------|
| phone | String | 是 | 11 | 员工手机号 |
| employeeNo | String | 是 | ≤20 | 员工编号 |
| company | String | 是 | ≤50 | 所属公司 |
| center | String | 是 | ≤50 | 所属中心 |
| cardNo | String | 是 | ≤20 | 员工卡号 |
| photoUrl | String | 是 | ≤250KB | 照片链接（Base64编码） |

#### 响应参数

| 参数名 | 类型 | 说明 |
|--------|------|------|
| code | String | 响应码："0000"表示成功 |
| msg | String | 响应描述信息 |

#### 请求示例
```json
{
  "phone": "13800138000",
  "employeeNo": "EMP2024001",
  "company": "青岛地铁运营有限公司",
  "center": "运营一中心",
  "cardNo": "QD20240001",
  "photoUrl": "Base64编码的照片数据"
}
```

#### 响应示例
```json
{
  "code": "0000",
  "msg": "员工信息推送成功"
}
```

| 属性 | 值 |
|------|-----|
| 接口名称 | 员工卡激活/禁用请求 |

| 通信方式 | 同步HTTP POST |
| 前置条件 | 电子卡须处于「待启用」状态方可激活 |

#### 接口地址
```
http://[ITP_IP]:[port]/api/v1/employee_card/activate
```

| 参数名 | 类型 | 必填 | 长度 | 说明 |
|--------|------|------|------|------|

**actionFlag 操作标志说明**：
| 值 | 说明 |
|----|------|
| 1 | 启用（激活） |
| 0 | 禁用 |

| 参数名 | 类型 | 说明 |
|--------|------|------|
| code | String | 响应码："0000"成功，其他为失败 |
| msg | String | 响应描述信息 |

#### 请求示例
**激活请求**：
```json
{
  "cardNo": "QD20240001",
  "actionFlag": 1
}
```

**禁用请求**：
```json
{
  "cardNo": "QD20240001",
  "actionFlag": 0
}
```

#### 响应示例
**成功响应**：
```json
{
  "code": "0000",
  "msg": "电子员工卡激活成功"
}
```

**失败响应**：
```json
{
  "code": "2002",
  "msg": "电子卡当前状态不允许激活操作"
```

## 六、错误码定义

### 6.1 通用错误码

| 错误码 | HTTP Status | 说明 | 建议处理方式 |
|--------|-------------|------|--------------|
| 0000 | 200 | 请求成功 | 正常处理 |
| 1001 | 400 | 参数校验失败：手机号不存在或格式错误 | 检查手机号格式 |
| 1002 | 400 | 参数校验失败：卡号不存在 | 检查卡号是否正确 |
| 1003 | 400 | 参数校验失败：必填字段缺失 | 补充必填参数 |
| 2001 | 403 | 无权限操作该卡 | 确认操作权限 |
| 2002 | 409 | 电子卡当前状态不允许该操作 | 检查卡当前状态 |
| 3001 | 401 | Token已过期 | 重新登录获取Token |
| 3002 | 401 | Token无效 | 重新登录获取Token |
| 4001 | 500 | ACC系统内部错误 | 重试，若持续报错联系运维 |
| 4002 | 502 | ITP网关错误 | 重试，若持续报错联系运维 |
| 4003 | 504 | ACC服务超时 | 重试并设置合理超时时间 |
| 9999 | 500 | 未知系统错误 | 记录日志并联系技术人员 |

### 6.2 错误码使用规范
- 第一位数表示错误来源：1-参数错误，2-业务错误，3-认证错误，4-系统错误，9-未知错误
- 所有错误响应必须包含code和msg字段
- 客户端应根据code而非msg进行逻辑判断

## 七、非功能需求

### 7.1 性能要求

| 指标 | 要求 |
|------|------|
| 接口响应时间（P95） | ≤ 500ms（不含ACC内部处理时间） |
| 接口响应时间（P99） | ≤ 2000ms |
| 并发处理能力 | ≥ 500 TPS（ITP网关层） |
| 推送到达延迟（P99） | ≤ 3秒（消息从ACC到APP端） |
| 系统可用性 | ≥ 99.9%（全年） |

### 7.2 容错与重试
- 接口调用失败时，调用方须实现指数退避重试策略（初始间隔1s，最大30s，最多3次）
- ACC推送失败时须将失败记录写入重试队列，定时重推
- ITP作为中转层，须实现熔断机制：下游ACC异常时快速失败，避免请求堆积

### 7.3 日志与监控
- 所有接口调用须记录请求流水号（traceId），实现全链路追踪
- 关键接口须上报监控指标：调用量、成功率、响应时间分布
- 异常情况（错误码非0000）须触发告警通知

## 九、业务流程说明

### 9.1 员工信息推送流程
① ACC侧员工信息新增/修改 → 
② ACC调用IF3A-01推送员工信息（包含手机号、员工编号、公司、员工卡号、照片链接、公司、中心） → 
③ ITP接收并存储员工信息 → 
④ ITP通知APP端更新员工信息

### 9.2 员工卡启用/禁用通知流程
① ACC侧员工卡启用/禁用操作 → 
② ACC调用IF3A-02发送启用/禁用通知 → 
③ ITP接收并更新卡状态 → 
④ ITP通知APP端更新卡状态显示

**说明**：首次开通时，员工信息推送(IF3A-01)和启用通知(IF3A-02)可合并一次发送。

### 9.3 员工卡开户流程
① 员工打开APP → 
② APP携带实体员工卡卡号调用IF3A-03 → 
③ ITP验证卡号有效性 → 
④ ITP创建电子员工卡账户 → 
⑤ ITP返回开户结果给APP

### 9.4 删除员工票流程
① ACC侧删除员工票 → 
② ACC调用IF3A-04发送删除通知 → 
③ ITP接收并删除卡号 → 
④ ITP通知APP端删除电子员工卡

### 9.5 员工卡激活/禁用流程
① 员工在APP点击「开通电子卡」或「暂停使用」→ 
② APP调用IF3A-06发送激活/禁用请求 → 
③ ITP转发请求至ACC → 
④ ACC校验业务规则并更新员工卡状态 → 
⑤ ACC返回处理结果 → ITP转发 → APP展示结果
