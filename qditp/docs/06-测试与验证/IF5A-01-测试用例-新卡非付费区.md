# IF5A-01 请求票卡分析 - 测试用例记录

## 核心业务规则：AFC 系统 BOM 票卡状态更新矩阵（v6.0 终版）

### 一、核心业务矩阵

| CODE_STATUS | 状态含义 | 状态分类 | 付费区 (updateType=01) | 非付费区 (updateType=00) | 核心业务逻辑与校验点 |
|-------------|---------|---------|---------------------|------------------------|-------------------|
| 02 | 结束行程 | 闭环 | 018 补进站 | 000 无需操作 | 行程已闭环却在付费区 = 尾随进站，需建立新行程 |
| 03 | SJT发售/新卡 | 新卡 | 018 补进站 | 000 无需操作 | 新卡无进站记录，在付费区属异常，需补录进站 |
| 04 | 已进站 | 开环 | 000 无需操作 | 006 补出站 | 有进站记录在付费区正常；在非付费区属有进无出，需补出站 |
| 05 | 已出站 | 闭环 | 018 补进站 | 000 无需操作 | 已出站却在付费区 = 尾随进站，需建立新行程 |
| 06 | 超时出站 | 闭环 | 018 补进站 | 000 无需操作 | 超时出站仅闭环历史行程，在付费区属新尾随，需补进站 |
| 08 | 20分钟内免费更新 | 更新 | 005 免费更新出站 | 005 免费更新进站 | 需校验 gateInTime ≤ 20min 且进出站点匹配 |
| 09 | 20分钟外付费更新 | 更新 | 006 付费更新出站 | 006 付费更新进站 | 需计算超时时费或同站折返票价 |
| 10 | 入站码更新 | 乘车码 | 000 或 018 | 006 补出站 | 乘车码专用：验证云端进站码状态及同步情况 |
| 80 | 自助补出站 | 闭环 | 018 补进站 | 000 无需操作 | 自助补出站已闭环历史行程，在付费区属新尾随，需补进站 |
| 81 | 自助补进站 | 开环 | 000 无需操作 | 006 补出站 | 自助补进站已建立有效记录，在非付费区属有进无出，需补出站 |

### 二、FFFF 初始态专项处理规范

**核心认知**：FFFF 是票卡/账户初始化时的合法默认值（Empty/Null State），代表"信息待填充"，不是异常、不是错误、不是脏数据。所有 UI 交互与日志记录必须遵循中性、引导原则。

| 涉及操作代码 | 适用 CODE_STATUS 场景 | BOM 界面交互规范 | 计费与业务处理规范 | 系统日志规范 |
|-------------|----------------------|-----------------|------------------|------------|
| 018补进站 | 02, 03, 05, 06, 80（付费区场景） | 站点下拉框默认为空，显示中性提示："ℹ️ 请选择本次进站站点"。❌ 禁用 ⚠️ 警告图标 ❌ 禁用错误/阻断提示 | 操作员手动选择站点后正常提交，建立新行程。❌ 历史闭环记录中的站点/费用不参与本次计费参考 | 记录为 INFO 级别业务流水日志 |
| 006补出站 | 04, 09, 81（非付费区场景） | 显示中性提示："ℹ️ 进站站点未记录，按基础票价计费"。❌ 禁用 ⚠️ 警告图标 ❌ 禁用"违规/逃票"等负面文案 | 无法获取进站站点时，按线网最低票价（基础票价）扣费。此为规则结果，非惩罚措施 | 记录为 INFO 级别业务流水日志 |
| 005免费更新 | 08, 09（付费区/非付费区场景） | 不自动执行 005，转入"人工核实模式"界面。操作员确认满足免费条件后手动执行，或转 006/018。❌ 禁用"禁止/拦截"提示 | 因无法验证同站折返等条件，系统不自动放行，保留免费更新的业务可能性，由人工兜底 | 记录为 INFO 级别业务流水日志 |
| 000/018/006 | 10（乘车码场景） | 显示中性提示："ℹ️ 乘车码信息同步中，请手动选择站点或稍后重试"。❌ 禁用"异常/联系客服"提示 | 引导乘客手动处理或等待云端同步完成 | 记录为 INFO 级别业务流水日志 |

### 三、通用设计原则

**本原则为 AFC 系统票卡状态处理的强制性基准，适用于所有现有及未来新增的状态码：**

1. **闭环状态原则（02/05/06/80）**：
   - 付费区(01) → 一律 018 补进站（视为新尾随）
   - 非付费区(00) → 一律 000 无需操作（状态正常）

2. **开环状态原则（04/81）**：
   - 付费区(01) → 一律 000 无需操作（状态正常）
   - 非付费区(00) → 一律 006 补出站（视为有进无出）

3. **新卡状态原则（03）**：
   - 付费区(01) → 018 补进站
   - 非付费区(00) → 000 无需操作

4. **FFFF 初始态原则**：
   - FFFF 为合法初始态，所有处理必须遵循：018 场景默认为空+手选引导；006 场景按基础票价计费；005 场景转人工核实。全程使用中性提示，不告警、不阻断、不记 ERROR 日志。

5. **数据隔离原则**：
   - 票卡状态的合法性由"状态语义"决定，物理位置的合法性由"有效的本次对应记录"决定。历史记录永远不参与新行程的计费与站点预填。

### 6.3 潜在问题

| 问题 | 说明 | 建议 |
|------|------|------|
| `cardId` 十六进制编码 | 之前测试中 `cardId=2F2F2F2F2F2F7745`（`FFFF` 的十六进制） | 需确认 BOM 是否对特殊字符做了额外编码 |

### 6.4 已知问题：bizData.providerId 错误

| 项目 | 内容 |
|------|------|
| **问题描述** | BOM 发送的 `bizData` 中 `providerId` 字段值为 `11280801`（实际是 `deviceId`），而非正确的商户编码 `03` |
| **问题原因** | BOM 终端参数封装错误，将 `deviceId` 的值错误地填入了 `bizData.providerId` |
| **影响范围** | 仅影响 `bizData` 内部的 `providerId` 值，不影响业务处理 |
| **当前处理逻辑** | `collect-pay-server` 的 `TransforUtils.copyBaseParams` 会先用公共参数覆盖 bizData 中的值：<br>`request.setProviderId(baseRequest.getProviderId())`<br>因此最终传递给 `ticket-server` 的 `providerId` 是正确的 `03` |
| **日志表现** | `baseRequest` 中 `providerId='03'`，但 `bizData` 中 `providerId='11280801'`，日志中两者不一致 |
| **修复建议** | 需修复 BOM 终端代码，确保 `bizData.providerId` 填入正确的商户编码 `03`，而非 `deviceId` |
| **风险等级** | 低（当前已通过公共参数覆盖规避，但 BOM 端缺陷应修复） |

### 6.5 优化：FFFF 站点跳过线路查询

| 项目 | 内容 |
|------|------|
| **优化描述** | `FFFF` 是默认/无效车站编码，代表未进站/未出站状态，无需查询线路信息 |
| **修改前** | 即使 `stationCode=FFFF`，仍调用 `para-server` 的 `requestStationLineInfo`，返回 `未找到车站信息`，产生无效日志 |
| **修改后** | 在调用 `requestStationLineInfo` 前判断：若 `stationCode=FFFF`，跳过查询，直接使用空字符串 |
| **修改文件** | `TicketRideStatusServiceImpl.java`（`requestCardDataAnalyse` 方法） |
| **影响范围** | IF5A-01 票卡分析接口，仅影响 `FFFF` 站点的线路查询逻辑 |
| **优化效果** | 减少无效 RPC 调用，日志更清晰，不改变业务结果 |

### 6.6 重构：按 CODE_STATUS 的 adviceOpt 计算逻辑（v6.0 矩阵）

| 项目 | 内容 |
|------|------|
| **重构描述** | `resolveAdviceOpt` 方法从"基于进出站记录判断"重构为"基于 CODE_STATUS + updateType 判断"，进出站记录作为兜底 |
| **修改前** | 基于 `gateInStation/lastTxnStation/updateType/gateInTime` 的 if-else 嵌套判断 |
| **修改后** | 基于 `CODE_STATUS` 分类判断：闭环(02/05/06/80)、开环(04/81)、新卡(03)、更新(08/09)、乘车码(10) |
| **核心规则** | `adviceOpt = f(CODE_STATUS, updateType)`，进出站记录仅用于 FFFF 计费降级和告警日志 |
| **校验规则** | `requestCardDataUpdate` 中增加 `isUpdateAllowed(codeStatus, adviceOpt, updateType)` 校验，防止非法状态-操作组合 |
| **修改文件** | `TicketRideStatusServiceImpl.java`（`resolveAdviceOpt`、`requestCardDataAnalyse`、`requestCardDataUpdate`） |
| **影响范围** | 全部票卡分析和票卡更新接口 |
| **重构效果** | 逻辑更清晰，易于维护，符合 v6.0 业务矩阵 |
