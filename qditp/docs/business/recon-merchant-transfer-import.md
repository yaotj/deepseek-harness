## 一、背景与目标

「商户号平台转账金额」是互联网支付对账里**唯一没有自动获取通道**的输入：支付宝次日资金管家、钱包大数据截图结算金额、微信后付费+预付费入账金额，均靠上传方（财务 / 运营待确认）按日从渠道侧人工汇总（`docs/business/recon-qdt.md` 表 4 判定 ❌、差距清单第 2 条）。链路（用户 2026-11-13 补充「ITP 需共享给 ACC」）：

```
上传方按日人工汇总 → 上传到 ITP 平台 → ITP 校验 / 留痕 → 共享给 ACC（对外契约见设计稿 6.4）
```

> ACC 侧接收路径、凭据、投递频率在整理版原文留空（文件级契约 Q8 / Q15），NEVER 据截图或本文推断。

**目标**：把这条人工闭环系统化——让导入件可校验、可留痕、可重传、可审计，与既有对账口径对齐，并把「ITP → ACC 共享」纳入统一的对外接口契约；同时**不污染交易流水、不改动四域分库导入数据**。

**非目标（本期明确不做）**：
- 不自动抓取支付宝资金管家 / 钱包大数据截图 / 微信入账（属渠道侧通道，另案）；
- 不重做琴岛通四方对账工作簿（`recon-qdt.md` 范围），本期只承接其中「商户平台转账核对」这一个输入；
- 不改动 `docs/sql/01_qditp_ddl.sql` / `docs/sql/02_qditp_data.sql` 的分库重建产物；
- 不新建表、不写建表 / 导入 SQL（待第七节确认后再走增量需求流程）。

## 四、功能需求（FR）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-01 | 综管台提供该类别的上传入口，按角色控权 | 无权限用户不可上传 / 不可查看；菜单与权限口径复用现有综管台体系；上传角色定稿 = 财务（Q13） |
| FR-02 | 模板校验：两级表头、列数、列顺序、清分日期格式、支付方式枚举、金额可解析、说明行跳过 | 缺列 / 多列 / 非法日期 / 未知支付方式 / 非数值金额整单拒绝并给出可读原因 |
| FR-03 | 账期唯一与幂等：同一清分日期同类别只保留一份；重复导入按既有口径「替换 + 旧件改名留存」 | 重复上传不产生第二份有效数据；旧件可追溯；NEVER 静默覆盖 |
| FR-04 | 口径校验：各渠道合计 = 全额汇总；合计手续费与费率一致；应转账金额 = 合计金额 − 合计手续费；平台转账金额与应转账差异留痕 | 校验结果可查询；差异不为零时 MUST 记录差异原因（人工填），NEVER 自动抹平 |
| FR-05 | 单位与精度统一：元 / 分二选一，金额精度与舍入规则固定，落库前换算一次 | 与 `recon-file-catalog.md` Q5 / Q9 结论一致，NEVER 出现分元混算 |
| FR-06 | 数据留存（依赖 Q8）：若裁决落明细表，MUST 有账期 + 支付方式唯一键、状态机白名单、幂等兜底；若只留元数据，则复用 `RECON_UPLOAD_FILE` 的 `FILE_CATEGORY` 分类 | 两种方案 MUST 先出对比再定，NEVER 边写边定 |
| FR-07 | 共享给 ACC：按账期投递，失败可重传 | 生产 FTP 路径 / 凭据 / 频率 / 账期窗口 MUST 由甲方补齐（Q9 / Q15）；共享形态（原样转发 / 转换后投递）与清单、回执契约见 `docs/business/recon-acc-interface-design.md` 的 6.4 节，待会签 N12 |
| FR-08 | 查询与审计：按清分日期、支付方式、状态查询导入批次与校验结果；记录操作人、时间、审核 / 复核信息 | 每笔导入可回溯到原始文件与校验结论 |
| FR-09 | 异常与重试：投递失败走「落库状态 + `@Scheduled` 扫表重试」，**NEVER 引入 Redis / MQ / Kafka** | 重试有上限与终态，失败可人工重传；状态迁移用白名单、NEVER 用黑名单 |
| FR-10 | 可观测：关键节点打日志、带 traceId， VictoriaLogs 可检索；日志 NEVER 打印无关敏感信息 | 导入 / 校验 / 替换 / 投递四类事件可检索 |

## 五、非功能与架构约束

承接 `AGENTS.md` 第 4 节 STRICT RULES，落实现阶段 MUST 遵守：

- **异步 / 重试**：落库状态 + `@Scheduled` 扫表重试；**NEVER** 引入 Redis / RabbitMQ / Kafka。
- **并发 / 幂等**：数据库唯一索引 + `DuplicateKeyException` 兜底；状态机用枚举 + 迁移表 + `canTransitTo` / `isTerminal`，配 `*WhitelistTest` / `*StatusMachineTest` 单测。
- **事务边界**：`@Transactional` 方法内 NEVER 发起 RPC / 网络调用，细则见 `docs/architecture/transaction-and-consistency.md`。
- **服务间调用**：走 `rpc` 模块 + HTTP 直连，NEVER 引入 Feign / Dubbo；新增内部 DTO MUST 放 `model`。
- **序列化**：Fastjson2，NEVER Jackson / Gson 处理业务报文。
- **持久层**：统一走自研 `mybatis-adaptor` / `sql-datasource`；写 Mapper XML 前 MUST 读 `docs/architecture/mybatis-oracle-runtime-traps.md`。
- **安全复核**：若改动涉及支付、密钥、签名，NEVER 擅自改现有加密 / 签名逻辑，MUST 提示人工复核。
- **分库归属（待裁决 Q8）**：若新增明细表，候选 `QDITP_PLAT`（综管台侧文件管理，与 `RECON_UPLOAD_FILE` 同域）或 `QDITP_TXN`（对账数据域）。两者取舍 MUST 基于「谁写谁读 + 跨域只读同义词」原则评审，**NEVER 擅自定域**；定域后 MUST 回写 `docs/ops/数据库按域分库计划.md` 的表归属清单与 `docs/business/README.md`。

## 六、与分库执行包的关系（边界硬约束）

- `docs/sql/by-domain/` 的产物是**库表 DDL + 库表数据 INSERT**，用于重建四域 schema；本件是**上传方导入的 Excel 文件**，两者粒度与载体不同，**NEVER 把这份 Excel 灌进那套 INSERT**，否则会把「按支付方式汇总的人工确认金额」混进 `PAY_TXN_DETAIL` 等交易流水口径，污染对账。
- 现有 `RECON_UPLOAD_FILE`（PLAT 域）只存**文件元数据**：`ID / FILE_NAME / FILE_PATH / FILE_SIZE / FILE_TYPE / RECON_DATE / STATUS / CREATE_* / UPDATE_* / REMARK / FILE_CATEGORY`，**不存金额明细**。是否新增明细分表见 Q8。
- 若后续裁决「落明细表 + 出建表 / 导入语句」，MUST 走增量需求流程与迁移脚本审批，**NEVER 手改 `docs/sql/by-domain/` 生成物**（改口径只改生成器后重跑）。
- 本件与 `docs/business/recon-qdt.md` 表 4 的 49~52 指标是**输入与消费**关系：49（应转）= 47−48、51 = 商户号平台转账金额、50 = 51−49、52 = 51−35+48；本期只保证 51 的输入可追溯，不负责整套公式落系统。

## 八、验收口径（需求评审通过后适用）

1. 用甲方提供的真实 xls 样例可完成一次导入，字段与第二节契约逐列对应，无漏列 / 错列。
2. 篡改任一必填列、非法清分日期、未知支付方式、非数值金额时，导入被拒且提示能定位到具体单元格。
3. 同账期重复导入：只保留一份有效件，旧件按既有命名规则留存，操作可审计。
4. 合计行、应转账金额、平台转账金额三者差异按裁决口径处理，差异原因可查询且不被自动抹平。
5. 单位与精度在「分 / 元」两条路径各跑一笔，结果与人工计算一致。
6. FTP 投递成功、失败重传、达到重试上限三种场景均有可检索日志与正确终态。
7. 若裁决落明细表：唯一索引与状态机单测通过，`@Transactional` 边界内无 RPC / 网络调用。
8. 全程 traceId 可追，VictoriaLogs 能按账期检索到导入 / 校验 / 替换 / 投递四类事件。
