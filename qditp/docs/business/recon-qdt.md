## 一、需求解读：按产品拆分的每日三方对账工作簿

《对账.xls》不是文件接口规格，而是**琴岛通（卡公司）每日人工对账的工作簿模板**，参与方三方：

- **ACC（清分中心）**——提供「ACC 交易明细（出站 / BOM 处理 / 充值）」；
- **地铁 / ITP**——义务是「**打包上传琴岛通**」（每日把包传给琴岛通）；
- **琴岛通**——提供「琴岛通汇总（正常 / 可疑 / 调整 / 拒付 / 挂账 / 补账）」与「财务确认金额」，发起了对账。

四张日对账表 = 四个产品线，表内结构高度同构：**两条外部输入（ACC 明细、琴岛通汇总）+ 一条 ITP 上传义务 + 一组差异公式 + 人工闭环（手续费 / 财务确认 / 审核人 / 复核人）**。

| 表 | 产品线 | ITP 侧义务列 | 关键差异口径 |
|---|---|---|---|
| 琴岛通消费对账 | 琴岛通卡乘车消费 | 打包上传琴岛通金额 | ACC 出站 + BOM 处理 − 上传包；地铁汇总 vs 琴岛通汇总（正常 + 可疑）；当日可疑应调整 vs 上日（**周一例外**）；T+1 / T+2 / 未结算 |
| 琴岛通充值对账 | 琴岛通卡充值 | 打包上传琴岛通金额 | ACC 充值明细 − 上传包；地铁汇总 vs 琴岛通汇总；挂账 / 补账 |
| 互联互通对账 | 交通部互联互通卡 + APPLY PAY | 打包上传琴岛通金额 | ACC 出站 + BOM 处理 − 上传包；琴岛通反馈拒付；ACC 出站 − 可疑；次日调整差异 |
| 互联网支付对账 | 二维码 / 第三方支付（按支付方式逐行） | ITP 反馈 + 平台侧六类特殊交易 | 52 指标公式链（见 §一.4）；ITP vs ACC vs 第三方商户号三方互对；手续费核对；商户平台应转 / 实转 |

样本数据（2026-10-01 ~ 10-04）量级：消费约 20 万笔 / 59 万元每日、互联互通约 2 ~ 4 万笔 / 8 ~ 15 万元每日、APPLY PAY 约 2.8 万笔 / 9.4 万元每日。**均为真实生产量级，不是演示数据。**

### 1.1 「琴岛通消费对账」结构（31 列）

- ACC 交易明细（出站）正常金额、ACC 交易明细（BOM 处理）正常金额；
- **打包上传琴岛通金额**（正常金额）、差异 = ACC 票卡交易 − 打包上传金额；
- 地铁汇总（出站 + BOM 处理）正常笔数 / 金额；
- 琴岛通汇总：正常笔数 / 金额、**可疑笔数 / 金额、调整笔数 / 金额**、当日可疑金额内应调整笔数 / 金额、可疑调整差异（当日 K 减 T-1 日 M、周一例外）；
- 消费总计、**消费手续费**（样本约 0.5%）、琴岛通财务确认金额、对账确认差异、对账确认手续费；
- **上日金额至今日结算 / 今日金额至次日结算 / 未结算（空白必须上报）**、差异、备注。

### 1.2 「琴岛通充值对账」结构（22 列）

ACC 票卡交易明细（充值）、打包上传琴岛通金额、差异；地铁汇总 vs 琴岛通汇总（正常 / 可疑 / 调整）；**挂账金额、补账金额**；琴岛通财务确认金额 / 对账确认差异 / 对账确认手续费；备注（样本：「50 元拒付；9.30 日 1 笔 50 元充值延迟至 10.1 日」「20 元拒付，120 元挂账」）。

### 1.3 「互联互通对账」结构（32 列）

左右两大产品块（交通部互联互通卡 / APPLY PAY 消费对账），每块都是「ACC 出站 + BOM 处理 − 打包上传 vs 琴岛通汇总」同构；另有**琴岛通反馈拒付**、ACC 出站 − 可疑、与次日调整差异、财务确认金额，以及合并块的 T+1 / T+2 / 未结算跟踪。

### 1.4 「互联网支付对账」结构（60 列，按支付方式逐行）

指标分组与**公式链**（下表「序号」为工作簿第 3 行自编号，公式原文照录）：

**「琴岛通消费」的口径是本节最大不确定项**，两种读法结论完全不同：

- **读法 A：ITP 互联网渠道乘车票款**（二维码 / 日票 / 设备域）。则 ITP 侧数据**基本可对齐**（gate-txn-pay 过闸组 + face-pay + daily-ticket 已有源），缺的只是上传通道与台账。样本量级（20 万笔 / 59 万元每日）与互联网渠道规模吻合，此读法有依据。
- **读法 B：实体琴岛通卡 / 手机交通卡消费**（AGM 出站、BOM 处理的卡域交易，样本中「周一例外」「可疑调整」等清扣语义支持此读法）。则 ITP **完全不持有**这些交易，要么 ACC 向 ITP 开放明细（新通道），要么本表不由 ITP 承担。

**MUST 与琴岛通确认后重判**（见 §六第 1 条）。

## 四、差距清单（按层，供排期与估算用）

1. **通道层**
   - 缺「ITP → 琴岛通」上传通道（新 FTP 目标 + 新文件契约，可复用 recon-server 现有编排 / 分片 / 投递机制，改动集中在配置与新增文件类型）；
   - 缺「琴岛通 → ITP」反馈接收（拒付 / 挂账 / 补账 / 调整 / 财务确认文件）；
   - 第三方账单投递仅落地「本地放置」，FTP 拉取未实现（`recon-thirdparty.md` §八 P2）。
2. **数据层**
   - 表 4 三个特殊交易维度无对账导出：ITP 离线码出站、超时全量（现仅多日票子集）、单边全量（EXP 无 TVM/BOM 7~15 类）；
   - 表 1 / 表 3 产品数据（实体卡消费、互联互通卡、Apple Pay）ITP 不持有；表 2 的 APP 充值 ITP 无业务；
   - 微信 / 龙支付渠道仓库零实现；
   - 商户平台转账金额（资金管家 / 大数据截图 / 微信入账）无自动获取。
3. **口径层**：产品与支付方式映射、可疑 / 调整 / 拒付 / 挂账 / 补账定义、T+1/T+2 判定基准（支付时间 / 清分日期 / 到账日期）、手续费率与计算基准、支付方式码表——**全部未与琴岛通对齐**。
4. **状态台账层**：无「可疑 / 调整 / 挂账 / 补账 / 拒付 / 结算（T+1 / T+2 / 未结算）」任何台账；这是四张表的共同底座，**建议一次设计覆盖四表**，不要每表各建一套。
5. **呈现层**：需求是人工 Excel（含审核 / 复核签字）；ITP 侧无对账结果报表 / 台账查询入口（综管台无对账页面）。若琴岛通要求 ITP 出对账结果（而非只传包），需新增报表能力。

## 五、对齐路径建议（三阶段 + 横切，均未立项）

- **阶段 1（表 4，互联网支付）**：以已落地的 TXNDIFF + 渠道账单链路为基座——①补三个特殊交易维度的导出（离线码出站 / 超时 / 单边，改动落在 gate-txn-pay、ticket-server、face-pay 的对账导出器）；②落实账单投递通道（FTP 拉取）；③与甲方敲定渠道枚举映射与失败原因值域（改配置即可）；④明确商户平台转账金额的数据来源与责任方。
- **阶段 2（表 2，充值）**：TVM/BOM 充值已有源，补「上传琴岛通」通道与充值维度账期口径；APP 充值若在范围内属新产品，需先问「要不要做」。
- **阶段 3（表 1 / 表 3，消费与互联互通）**：**阻塞在口径确认**——先按 §六第 1 条定性「琴岛通消费 / 互联互通 / APPLY PAY」分别指哪些交易，再决定是「加导出维度」（轻）还是「接新产品 / 接 ACC 明细通道」（重，超出对账范畴）。
- **横切（四表共用，建议先行设计）**：可疑 / 调整 / 挂账 / 补账 / 拒付 / 结算状态台账 + 琴岛通反馈文件接收 + 对账结果呈现。设计时 MUST 遵守 `AGENTS.md` §4「STRICT RULES (严格开发准则 - AI 必读)」：落库状态 + 扫表重试（禁 Redis/MQ）、状态机白名单、`@Transactional` 与 RPC 边界按 `docs/architecture/transaction-and-consistency.md`。

## 六、待琴岛通 / 甲方确认项（阻塞，未确认前不建议排期）

1. **产品口径**：「琴岛通消费」「琴岛通充值」「互联互通」「APPLY PAY」各指哪些交易（实体卡 / 手机卡 / 乘车码 / Apple Pay）？ITP 需要上传的是哪几类？
2. **上传契约**：「打包上传琴岛通」的文件格式、字段、路径、频率、账期（是否沿用 ACC 四类文件的分片 + FTP 机制）？
3. **ACC 明细归属**：「ACC 交易明细」由谁提供、给谁？ITP 是否需要（反向）接收 ACC 明细？
4. **状态定义**：可疑 / 调整 / 拒付 / 挂账 / 补账的定义与状态流转；琴岛通反馈文件的格式与投递方式？
5. **结算口径**：T+1 / T+2 / 未结算的判定基准（支付时间 / 清分日期 / 到账日期）；「未结算有数据必须上报」的上报对象与格式？
6. **手续费**：各产品费率（表 1 样本约 0.5%、表 4 公式按 0.1% 核对）与计算基准（含税 / 不含税、是否含退款）？
7. **对账结果落点**：ITP 只负责「传包 + 出差异」，还是也要出对账结果报表 / 台账（人工 Excel 由琴岛通维护）？
8. **表 4 支付方式码表**：取值清单与「三渠道组」映射（当面付 BOM / 钱包 / 微信后付费；快捷 TVM / 龙支付 / 微信预付费；商家扣款 APP 免密）——微信、龙支付是否在 ITP 经支付中心路由？
9. **商户平台转账金额来源**：支付宝资金管家 / 钱包大数据截图 / 微信入账金额由谁提供、什么形式（文件 / 截图 / 接口）？

## 七、结论

**总体：部分可对齐，且四张表的成熟度差异极大。**

- **表 4（互联网支付对账）：大部分可对齐。** ITP 反馈侧与第三方账单比对侧的链路已设计落地（TXNDIFF + `RECON_THIRD_BILL` / `RECON_TXN_DIFF`），主要补三个特殊交易维度导出、账单投递通道、商户平台转账金额来源，以及微信 / 龙支付产品确认。**注意两个执行级前置：两表是否已在库内建好（MUST 实查）、7 个外部契约默认假设是否已被甲方接受。**
- **表 2（充值对账）：部分可对齐。** TVM/BOM 设备充值有源；APP 充值、挂账 / 补账 / 拒付、ACC 明细、上传通道均缺。
- **表 1（消费对账）：当前不可对齐。** 「琴岛通消费」口径未定是首要阻塞；即便按读法 A（互联网票款），也缺上传通道与结算 / 可疑 / 调整台账；按读法 B（实体卡）则 ITP 无数据源。
- **表 3（互联互通对账）：当前不可对齐。** 互联互通卡与 Apple Pay 在 ITP 无产品无数据，拒付反馈无接收通道。
- **横切差距（通道 / 口径 / 台账 / 呈现）四表共通**，其中「可疑 / 调整 / 挂账 / 补账 / 拒付 / 结算状态台账」建议作为统一底座一次设计，避免四表各建一套。

**给业主的一句话**：现有 recon-server 的「批次编排 + 分片抽取 + 聚合 + FTP 投递」机制可以直接复用到「上传琴岛通」，真正的成本不在文件链路，而在**产品口径确认、琴岛通反馈接收、结算状态台账**这三件外部依赖上——建议先按 §六清单与琴岛通开一次口径会，再排期。
