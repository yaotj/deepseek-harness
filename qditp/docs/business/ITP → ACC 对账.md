# ITP → ACC 对账

## 一、ITP 向 ACC 投递对账文件

ITP 生成对账文件后上传到固定路径，投递完成即收口。

| 项      | 约定                                                                                                                                                                                                                               |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 方向     | **ITP → ACC 单向**                                                                                                                                                                                                                 |
| 投递路径   | 根目录 `/itp/recon/`，**按渠道分一级子目录**：ITP 自有对账文件 → `/itp/recon/itp/`；第三方渠道账单 → `/itp/recon/<渠道码>/`，如 `03` 支付宝、`04` 微信、`05` 支付宝出行、`07` 云闪付、`08` 建行、`0B` 钱包、`0C` 数币、`0601` 招行一网通（码表见 2.4.1），商户入账确认件的约定码 `MT`（见 2.3）、HCE 黑名单的 `/itp/recon/hce/`（见第五章）。不按账期再分子目录，账期由文件名区分 |
| 测试环境   | `ip: 172.20.215.3`　`port: 21`　用户名 `ftpuser`　密码 `ftp@ITP`                                                                                                                                                                         |
| 生产环境   | 地址 / 账号 / 密码 **待双方书面交付**，当前为空                                                                                                                                                                                              |
| 传输协议   | 明文 FTP，沿用现有在跑通道；加密通道（SFTP / 文件网关 + TLS）在与 ACC 约定后替换，判据见 3.1                                                                                                                                                                      |
| 触发     | 每日 T 日 2 点，统计 T-2 日 2 点 ~ T-1 日 2 点，文件名日期取 T-2                                                                                                                                                                                   |
| 文件名日期  | 日期段只含账期日 `yyyyMMdd`（T-2），**不是生成日、不是投递时刻**，不含时分秒；重传版本走 `.r<n>` 后缀而非日期段；生成时间见 manifest 的 `generatedAt` 与报文 `timestamp` |
| 命名与可见性 | 正式名 = 基础名（原始版本）或「扩展名前插 `.r<n>`」（第 n 版）；先传 `<正式名>.uploading`，全部写完再远端 rename 为正式名；正式名出现即代表内容完整可取，ACC 只认正式名 |
| 版本     | 首次投递即**原始版本**（`revision = 1`）；此后任何新版本 MUST 由 ACC 通过 IR-02 要求产生，ITP NEVER 自行升版；版本号递增并体现在文件名 `.r<n>` 后缀，同版本禁止覆盖                                                                                                                                                  |
| 自校验    | 每份文件随附 `byteSize` / `recordCount` / `amountTotal` / `sha256` 四元组，由 ITP 上传前自校验、随 IR-01 送交供 ACC 独立复核                                                                                                                                                 |
| 成功判据   | 仅「远端 rename 成功 + 字节数回查」，不含接收方校验                                                                                                                                                                                                  |

|                     | `ITP.DETAIL.yyyyMMdd`                               | 交易明细，全票种（22 段）                                                  |

|                     | `银联pos交易yyyyMMdd.xls`                              | 车站现场 POS 机具收款明细，运营导入后**原样转投**（26 列，首行为 14 列汇总，表头在第 2 行） |

## 二、对账数据

### 2.1 单位、编码与格式约定（全链路统一）

| 项     | 约定                                                                                              |
| ----- | ----------------------------------------------------------------------------------------------- |
| 编码    | UTF-8，无 BOM                                                                                     |
| 分隔    | 半角 `\|`，字段用半角单引号包裹                                                                              |
| 表头    | 无                                                                                               |
| 行尾    | `\n`                                                                                            |
| 金额    | ITP 自有文件与报文业务字段统一**分**、整数、字符串化传输，禁止小数与科学计数法；**第三方渠道账单（2.4.2）与四张报表（4.3）为元**，两者 NEVER 混算 |
| 空值    | 空段与 `0` 语义必须区分；金额类空段定义为「不适用」而非 0                                                                |
| 文件名账期 | `yyyyMMdd`，取账期日而非生成日                                                                            |
| 格式版本  | 段数 / 字段语义 / 单位变更 MUST 升 `formatVersion`，NEVER 用「兼容解析」冒充同版本；当前 `ITP.TXNDIFF` 为 v2（26 段），其余四类为 v1 |
| 适用范围  | 本表只适用于**文本型**文件（五类交换文件、第三方渠道账单、MT 确认件）；**第五章 HCE 黑名单为纯二进制**（编码见 5.2），银联 POS / 收款码为原样转投件（见第一章），两者 NEVER 套用本表 |
| 控制文件  | 每份数据文件配 `<正式名>.manifest.json`，与数据文件同批到达，含文件清单、四元组、协议版本、账期窗口、生成时间、`revision`；`<正式名>` 含版本后缀时一并保留 |

### 2.2 ITP 五类交换文件

| 文件名                    | 用途        | 粒度                  | 生成方 |
| ---------------------- | --------- | ------------------- | --- |
| `ITP.EXP.yyyyMMdd`     | 单边交易明细    | 逐笔                  | ITP |
| `ITP.PAY.yyyyMMdd`     | 统计汇总      | 线路 × 车站 × 设备 × 支付方式 | ITP |
| `ITP.BUS.yyyyMMdd`     | 商业优惠汇总    | 账期汇总                | ITP |
| `ITP.DETAIL.yyyyMMdd`  | 交易明细（全票种）    | 逐笔                  | ITP |
| `ITP.TXNDIFF.yyyyMMdd` | 对账差异明细    | 逐笔差异                | ITP |

#### 2.2.1 单边交易明细 `ITP.EXP.yyyyMMdd`（13 段）

| 段 | 字段                     | 段  | 字段                     |
| - | ---------------------- | -- | ---------------------- |
| 1 | 逻辑卡号                   | 8  | 出站处理设备类型               |
| 2 | 票卡交易序列号（**比对键**）       | 9  | 出站设备编码                 |
| 3 | 订单金额（分）                | 10 | 出站时间（`yyyyMMddHHmmss`） |
| 4 | 实际扣款金额（分）              | 11 | 订单异常类型（1~15）           |
| 5 | 优惠金额（分）                | 12 | 支付方式（标准定义码，见 2.4.1）    |
| 6 | 进站设备编码                 | 13 | 交易日期（`yyyyMMdd`）       |
| 7 | 进站时间（`yyyyMMddHHmmss`） |    |                        |

订单异常类型取值：`1` 单边账（入站）、`2` 单边账（出站）、`3` 单边入站（人工处理单）、`4` 单边出站（人工处理单）、`5` 乘客自主补进站、`6` 乘客自主补出站、`7` TVM 补币找零不足、`8` TVM 卡票、`9` TVM/BOM 发售无效票、`10` 闸门无用、`11` 无票出闸、`12` 人为单程票无效、`13` 非人为单程票无效、`14` 储值票无效、`15` 其他情况。

**字段约定**：

- 段 2 票卡交易序列号是**全局唯一比对键**：逐笔比对、晚传判定、重复去重一律以它为准，NEVER 用订单号或流水号替代。比对在 ACC 侧执行，本文只保证该键稳定唯一。
- 空值：单边入站（异常类型 `1` / `3` / `5`）段 8 / 9 / 10 传空；单边出站（`2` / `4` / `6`）段 6 / 7 传空。**空段不等于 `0`**（见 2.1）。
- 订单异常类型只描述成因，**不决定应收**；应收认定在 ACC 侧。`3` / `4` 已经人工处理单确认、`1` / `2` 未确认，两者口径差异需在会签中告知 ACC。

#### 2.2.2 统计汇总 `ITP.PAY.yyyyMMdd`（21 段）

| 段  | 字段                  | 段  | 字段            |
| -- | ------------------- | -- | ------------- |
| 1  | 日期（`yyyyMMdd`）      | 12 | 过闸笔数          |
| 2  | 线路                  | 13 | 过闸金额（分）       |
| 3  | 车站                  | 14 | APP 购票笔数      |
| 4  | 设备编号                | 15 | APP 购票金额（分）   |
| 5  | 支付方式（标准定义码，见 2.4.1） | 16 | BOM 行政处理笔数    |
| 6  | BOM/TVM 发售笔数        | 17 | BOM 行政处理金额（分） |
| 7  | BOM/TVM 发售金额（分）     | 18 | 单边交易笔数        |
| 8  | BOM/TVM 充值笔数        | 19 | 单边交易金额（分）     |
| 9  | BOM/TVM 充值金额（分）     | 20 | BOM 处理笔数      |
| 10 | 旅游票张数（发售）           | 21 | BOM 处理金额（分）   |
| 11 | 旅游票金额（分）            |    |               |

**汇总维度**：一行 = 日期 + 线路 + 车站 + 设备编号 + 支付方式 的一个组合；无交易的组合不出现，**不补零行**。

**勾稽等式（ACC 复核的主要手段）**：

- 段 18/19（单边交易）MUST 与 2.2.1 逐笔文件按同维度聚合后的行数 / 金额之和一致；不一致即 `BOTH + AMOUNT`。
- 段 12/13（过闸）是 ITP 侧全量口径，与单边是**包含**还是**并列**尚未定；未定前 **MUST NOT** 用「过闸 − 单边」反算正常交易，否则会把子集关系算成差额。

#### 2.2.3 商业优惠汇总 `ITP.BUS.yyyyMMdd`（4 段）

| 段 | 字段             |
| - | -------------- |
| 1 | 日期（`yyyyMMdd`） |
| 2 | 对账金额（分）        |
| 3 | 付款金额（分）        |
| 4 | 优惠金额（分）        |

三者关系：`对账金额 = 付款金额 + 优惠金额`，任一不成立即为金额差异。

**维度**：本文件是**账期级汇总**，不含商户 / 合作方维度。若商业优惠涉及多个合作方，MUST 增加商户维度并升 `formatVersion`，NEVER 把多个合作方合并成一行。

#### 2.2.4 交易明细 `ITP.DETAIL.yyyyMMdd`（22 段）

**本文件承载全部票种的交易明细**（普通二维码、NFC 储值、单程票、员工票、虚拟电子多日计次票等），票种由段 8 / 9 区分；多日计次票另受下列特别约定约束。

| 段  | 字段                     | 段  | 字段                 |
| -- | ---------------------- | -- | ------------------ |
| 1  | 运营日期（`yyyyMMdd`）       | 12 | 数量（1）              |
| 2  | 交易类型（发售 / 出站）          | 13 | 交易流水号（同二维码车票里程序列号） |
| 3  | 逻辑卡号                   | 14 | 交易订单号（**分组键**）     |
| 4  | 交易日期（`yyyyMMddHHmmss`） | 15 | 订单金额（分）            |
| 5  | 交易原价（分/次）              | 16 | 实际扣款金额（分）          |
| 6  | 当前车站名称                 | 17 | 优惠累计消费金额（分）        |
| 7  | 设备编码                   | 18 | 超时金额（分）            |
| 8  | 票卡类型                   | 19 | 订单状态               |
| 9  | 票卡子类型                  | 20 | 补扣订单号              |
| 10 | 原支付渠道                  | 21 | 补扣金额（分）            |
| 11 | 激活时间（`yyyyMMddHHmmss`） | 22 | 退款金额（分）            |

**多日计次票（虚拟电子）特别约定**（会签重点）：

- 虚拟电子多日计次票的**交易金额传 0**（沿用闸机侧口径）；票种细分由 ACC 按 `SIGN_CHANNEL_CODE` 区分，该字段不在本文件（见下条字段约定）。
- 多日计次票**正常乘车交易不对账**，只对**车票购买（发售）**与**超时费**对账。
- 车票购买：交易类型 = `发售`，当前车站名称与设备编码**传空**。
- 超时行程：交易类型 = `出站`，费用为**线网最高票价或 1**（单位与二选一条件待会签）。
- 订单状态枚举：`正常订单`、`超时订单`、`退款订单`（有退款金额，否则填 0）、`单边订单`、`未支付订单`。

**字段约定**：

- 金额单位一律**分**：段 15 / 16 / 17 / 18 / 21 / 22 均为整数分，与 2.1 一致；NEVER 按元投递（历史 7 段日票版曾用元，已废弃）。
- 票种区分：ITP 侧以段 8 / 9 的票卡类型 / 子类型表达；**本文件不含** `SIGN_CHANNEL_CODE`，该字段只在 ACC 侧线路上传文件中出现，两侧票种口径需在会签中对齐。
- 补扣（段 20 / 21）MUST **独立成行**，原订单行不因补扣重复出现；补扣行 MUST 在段 20 填原订单号，否则无法归组。`recordCount` = 文件行数，金额合计 = 各行之和，ACC 按段 14 交易订单号分组核对。
- 超时扣款（闸机超时费）**已包含在本文件的交易明细内**，由段 18 超时金额体现，**不另设超时报表、不单独投递**；如需按票卡视角看超时扣款，由 ACC 按段 3 逻辑卡号聚合段 18 得到。
- 段 2 交易类型当前只有 `发售` / `出站` 两值（沿用多日计次票口径）；超时行程属 `出站`，靠段 18 超时金额非 0 识别。若其他票种需要表达充值、退款、补扣等动作，MUST 会签后扩展枚举并升 `formatVersion`，NEVER 借用现有两值凑合。

#### 2.2.5 对账差异明细 `ITP.TXNDIFF.yyyyMMdd`（26 段）

> 数据源：库内比对对象 `OBJ_GZ_DIFF_ITP-<渠道>`（如 `OBJ_GZ_DIFF_ITP-ZFB`，28 列）。本文件的差异字段由该对象裁剪：`diff_desc` 决定段 21 / 23 / 24 的取值，`shishou`（实收）与 `diff_amount`（差额）决定段 25 / 26；对象内的 `id`、`acc_pay_method` 等不进文件。

| 段  | 字段                     | 段  | 字段                                                                                 |
| -- | ---------------------- | -- | ---------------------------------------------------------------------------------- |
| 1  | 运营日期（`yyyyMMdd`）       | 14 | 交易流水号                                                                              |
| 2  | 交易类型                   | 15 | 交易订单号                                                                              |
| 3  | 逻辑卡号                   | 16 | 订单金额（分）                                                                            |
| 4  | 交易日期（`yyyyMMddHHmmss`） | 17 | 实际扣款金额（分）                                                                          |
| 5  | 交易原价（分）                | 18 | 优惠累计消费金额（分）                                                                        |
| 6  | 当前车站名称                 | 19 | 超时金额（分）                                                                            |
| 7  | 设备编码                   | 20 | 订单状态                                                                               |
| 8  | 票卡类型                   | 21 | 差异原因（兼容码 `01~04`）                                                                  |
| 9  | 票卡子类型                  | 22 | 扣款失败原因（平台返回）                                                                       |
| 10 | 次数                     | 23 | `diffDirection`（`ITP_ONLY` / `COUNTERPART_ONLY` / `BOTH`）                          |
| 11 | 支付渠道                   | 24 | `diffType`（`MISSING` / `AMOUNT` / `STATUS` / `LATE` / `DUPLICATE` / `CHARGE_FAIL`） |
| 12 | 激活时间（`yyyyMMddHHmmss`） | 25 | 对方金额（分）：对方渠道侧金额，`ITP_ONLY` 时空（不是 0），`COUNTERPART_ONLY` 时必有值                        |
| 13 | 数量（1）                  | 26 | 差额（分）：`BOTH` = 段 17 − 段 25；`ITP_ONLY` = 段 17；`COUNTERPART_ONLY` = `0 − 段 25`（为负）   |

- **责任方不单设段**：文件只给事实（方向 + 类型），责任方由 ACC 按其判定规则映射，避免同一事实两处可写不一致。
- 段 21 兼容码 MUST 与段 23 / 24 映射一致；两者冲突时以 23 / 24 为准。兼容码含义与实测分布（2026-10-07 支付宝组样本，5489 行差异）如下：

  | 兼容码 | 原文含义 | 实际指向 | 对应两维 | 实测条数 |
  |---|---|---|---|---|
  | `01` | ITP 无 | 渠道有、ITP 无 | `COUNTERPART_ONLY` + `MISSING` | 该组未出现 |
  | `02` | 第三方无 | ITP 有、渠道无 | `ITP_ONLY` + `MISSING` | **4752** |
  | `03` | 金额不一致 | 双方都有、实扣金额不等 | `BOTH` + `AMOUNT` | **737** |
  | `04` | 扣款失败 | 渠道扣款未成功 | `ITP_ONLY` + `CHARGE_FAIL` | 该组未出现 |

  > `01` 与 `02` 的原文含义（「ITP 无」/「第三方无」）与实测口径存在冲突：样本中 4752 条全部是「ITP 有 ZFB 无」，实际落在 `02`。**本文以实测口径为准**，兼容码的最终语义 MUST 在会签中一次性定死，NEVER 两套并存。
- 金额单位一律**分**（段 5 / 16 / 17 / 18 / 19 / 25 / 26），与 2.1 一致。

### 2.3 商户入账确认件（渠道 `MT`）

**定位**：它不是支付渠道，但**按渠道处理**——给它一个约定渠道码 `MT`，走与第三方账单同一条投递链路：目录 `/itp/recon/MT/`、文件按 `ITP.THIRD.MT.SETTLE.yyyyMMdd.csv` 命名、四元组与就绪通知按第四章执行。这样不必为一份人工汇总表另立文件类型、批次类型与重传规则。

| 项          | 设计                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------- |
| 渠道码        | `MT`（双方约定码，**不属于** 2.4.1 的 23 类支付渠道）                                                     |
| `bizGroup` | `SETTLE`（资金结算侧），与 `POSTPAID` / `PREPAID` / `FACE2FACE` / `TRAVEL` 并列                            |
| 上传原件       | 财务上传 Excel（`商户号平台转账金额yyyyMMdd.xls`），**仅 ITP 留存**，投递与归档均不使用该格式                                   |
| 投递文件       | `ITP.THIRD.MT.SETTLE.yyyyMMdd.csv` —— UTF-8 无 BOM、首行表头、金额为元两位小数                                 |
| 字段         | **汇总粒度**（商户号 × 到账日期 × 金额），不是 22 字段逐笔标准；列定义随会签确定，MUST 至少含 `商户号` / `到账日期` / `金额` / `笔数` / `币种` 五项 |
| 转换责任       | ITP 负责 `.xls` → CSV 的逐列转换，原件与投递件按 `账期 + revision` 成对留存、可回查；NEVER 直接把 Excel 投给 ACC               |
| 性质         | **人工确认的汇总金额，不是交易流水**                                                                            |
| 投递         | 上传至 ITP → ITP 转 CSV → 按独立批次投递                                                            |
| 对账角色       | 只确认「收妥」，**不出逐笔差异、不参与清分、不灌入交易流水表**                                                               |
| 校验         | 仅格式与公式校验（合计 = 各组金额之和）；数值正确性归上传方                                                                 |
| 重传         | 仅当 ACC 要求（驳回 / 差异 / 同意申请）后重传，`revision` 递增、文件名在 `.csv` 前追加 `.r<n>`；禁止 ITP 侧改数，因承载财务签字金额，MUST 双方书面确认 |

### 2.4 第三方渠道账单

## 三、通道架构

### 3.1 文件面：FTP / SFTP

| 项  | 设计                                                       |
| -- | -------------------------------------------------------- |
| 承载 | 交易明细、汇总、差异明细、财务确认件等批量成件数据                                |
| 方向 | 主体单向（ITP→ACC）；ACC→ITP 只用于 IR-02 重传请求与 IR-03~06 报表查询，不传文件 |
| 规模 | 单文件可达百万行；确认件为单个 Excel，投递前转 CSV                           |
| 时机 | 日切后批量                                                    |
| 协议 | 生产建议 **SFTP 或专用文件网关 + TLS**；测试期可沿用现有 FTP，但控制面 MUST HTTPS |

**为什么保留文件交换而不是改成实时接口**（会签答辩要点）：

1. **量与时机**：单文件可达百万行、日切后一次性批量，接收方以目录前缀取件；分页拉明细需自建断点、限流与一致性快照，等于把文件传输重做一遍。
2. **可重放与可审计**：金融对账要求「某一账期的确定快照」可归档、可逐笔复核；文件天然满足，实时分页读会引入「读到哪一版」的问题，与版本机制冲突。
3. **既有链路已稳定运行**：接收方取件进程按文件名前缀匹配，改名或改协议都会破坏在跑链路。
4. **本仓架构约束**：无注册中心与网关、服务间 HTTP 直连、禁用 Redis / MQ、单副本 + Oracle 分片聚合，不具备实时承载百万行批量查询的条件。

**唯一重新评估的条件**：接收方明确要求实时逐笔核对，且单账期数据量小到可 API 化。目前不成立。

### 3.2 控制面：HTTPS 表单 / JSON 报文

| 项    | 设计                                                                                                                                |
| ---- | --------------------------------------------------------------------------------------------------------------------------------- |
| 承载   | 文件清单与四元组（IR-01）、重传请求（IR-02）、四张地铁报表的查询结果（IR-03~06）                                                                                    |
| 方向   | 双向：IR-01 由 ITP 发起；IR-02~06 由 ACC 发起 |
| 时机   | 事件触发                                                                                                                              |
| 规模   | 单请求 ≤ 数十 KB                                                                                                                       |
| 协议   | HTTPS + `application/x-www-form-urlencoded`（`POST` 表单）；业务报文 JSON 放 `bizData` 字段；响应为 JSON                                          |
| 信封对齐 | 沿用应用内既有 ACC 客户端的公共字段 `providerId / charset / format / timestamp / deviceId / signType / sign / bizData`，仅追加 `requestId` / `nonce` |

**判据**：任何「逐笔」数据走文件；任何「关于这批数据的说明与结论」走控制面。

## 四、接口设计

### 4.1 接口总表

| 编号 | 接口 | 方法 | 方向 | 触发时机 | 幂等键 |
|---|---|---|---|---|---|
| IR-01 | 文件就绪 `fileReady` | POST | ITP→ACC | 整批文件全部 rename 完成后 | `settlementDate + batchNo + revision` |
| IR-02 | 重传请求 `retransmitRequest` | POST | ACC→ITP | ACC 发现某文件不可用（缺件 / 损坏 / 版本错） | `基础名 + currentRevision` |
| IR-03 | 地铁交易报表 `metroTradeReport` | POST | ACC→ITP | ACC 按日查询 / 导出 | 只读，无副作用 |
| IR-04 | 地铁扣款报表 `metroChargeReport` | POST | ACC→ITP | ACC 按日查询 / 导出 | 只读，无副作用 |
| IR-05 | 地铁退款报表 `metroRefundReport` | POST | ACC→ITP | ACC 按日查询 / 导出 | 只读，无副作用 |
| IR-06 | 地铁在线补款报表 `metroSupplementReport` | POST | ACC→ITP | ACC 按日查询 / 导出 | 只读，无副作用 |

**本文定义六条接口，分两类**：

- **投递类（2 条）**：ITP 把文件放好并告诉 ACC（IR-01）；ACC 发现某个文件不可用时要求重投（IR-02）。
- **报表查询类（4 条）**：ACC 按条件查询四张地铁报表（IR-03 ~ IR-06），由接口返回分页数据，供页面筛选与展示；**整日全量导出不走接口**，见 4.2 的分页约束。

取件、校验、核对、关账全部在 ACC 侧完成，**除重传请求外不回传任何结论**——所以不需要回执、结果、投递状态查询、差异下发类接口（报表查询是数据取数，不是投递状态查询，两者不冲突）。

| 常被问到的接口 | 为什么本文不设 |
|---|---|
| 批次声明 | 并入 IR-01：`files[]` 就是本批清单，缺失渠道在 `remark` 声明 |
| 逐文件接收回执 | 正常收妥不回传；文件不可用时走 IR-02 单点要求重投，不必逐文件报状态 |
| 核对结果 / 关账通知 | 属 ACC 内部流程，不回传 |
| 状态查询 | 没有回执就没有状态可查；ITP 只维护自己的投递状态，不对外提供查询接口 |
| 结算日历 | 静态约定，会签定一次 |
| 差错工单 | ITP 内部台账，不进接口 |

**幂等键**：IR-01 为 `settlementDate + batchNo + revision`（一个批次一个版本只发一次）；IR-02 为 `基础名 + currentRevision`（同一文件的同一版本只受理一次，重复请求回同一 `targetRevision`）。两者重试 MUST 复用同一个 `requestId`（见 4.2）。

### 4.2 公共协议

**传输格式：表单提交，不是 JSON body。**

请求 MUST 为 `POST`，`Content-Type: application/x-www-form-urlencoded;charset=UTF-8`。外层是公共参数的表单字段，业务字段全部放在 `bizData` 一个字段里（**JSON 字符串**）：MUST NOT 把业务字段平铺到外层，MUST NOT 对 `bizData` 做 Base64。表单值逐项做 URL 编码（UTF-8）。

| 表单字段         | 必填 | 说明                                 |
| ------------ | -- | ---------------------------------- |
| `providerId` | Y  | 机构标识，独立取值，NEVER 沿用业务实时通道           |
| `charset`    | Y  | 固定 `UTF-8`                         |
| `format`     | Y  | 固定 `json`                          |
| `timestamp`  | Y  | `yyyyMMddHHmmss`，与服务端时差超过窗口即拒绝     |
| `deviceId`   | N  | 终端标识，无则传空串                         |
| `signType`   | Y  | 签名类型                               |
| `sign`       | Y  | 签名值，对约定字段排序后计算；算法与字符集待会签（安全合规复核前置） |
| `requestId`  | Y  | 幂等键（本设计新增），重试 MUST 复用同一值，接收方据此去重   |
| `nonce`      | Y  | 防重放（本设计新增），单次有效，有效期建议 5 分钟         |
| `bizData`    | Y  | 业务报文 JSON 字符串，见下                   |

URL 编码前的原始报文示例（字段顺序固定）：

```
providerId=06&charset=UTF-8&format=json&timestamp=20260820020000&deviceId=&signType=00&sign=<签名值>&requestId=REQ20260820020000001&nonce=a1b2c3d4e5&bizData={"settlementDate":"20190818","batchNo":"B20190818001","revision":1,"batchType":"DAILY","files":[]}
```

`bizData` 内的业务 JSON（以 IR-01 为例）：

```json
{
  "settlementDate": "20190818",
  "batchNo": "B20190818001",
  "revision": 1,
  "batchType": "DAILY",
  "files": []
}
```

**multipart/form-data 变体**：仅当对端明确要求或报文含大段文本时使用。字段名与顺序不变，每个字段一个 part，`bizData` 原样放 JSON 字符串、**不做 URL 编码**。同一条链路 MUST 只选一种格式并在会签中固定，NEVER 两套并行。

**方法约定**：统一 `POST` 表单，不使用 URL query；条件全部放 `bizData` 内，避免长参数与编码差异。

**报表查询的公共约定（IR-03 ~ IR-06）**：统一 `POST` 表单，入参全在 `bizData`；**必须分页**——`pageSize` 默认 500、上限 5000，`pageNo` 自 1 起，结果按主键（订单号 / 退款单号 / 补款单号）升序，保证翻页稳定；同一 `settlementDate` 翻页期间数据 MUST 只读不变，NEVER 边翻页边重算导致跨页重复或漏行。

四张表的实测规模是**单日 60 万行级**（交易 29.8 万 + 扣款 37.3 万，见 4.3）。所以接口只承担「按条件筛选后的页面展示」：调用方 MUST 先用 `merchantName` / `payChannel` 收窄，再翻页；**整日全量导出走文件通道**（落地为 CSV 投递，见第一章），NEVER 用接口翻页硬拉全量——按 `pageSize = 5000` 拉完一天也要上百次调用，且期间数据任何变动都会破坏翻页一致性。

**响应：JSON**（`Content-Type: application/json;charset=UTF-8`）：

```json
{
  "requestId": "REQ20260820020000001",
  "retCode": "0000",
  "retMsg": "执行成功",
  "bizData": { }
}
```

调用方（ITP）解析 MUST 兼容两种既有返回结构：业务字段直接在**外层**，或包在 `bizData` 内；取 `retCode` / `retMsg` 时先取外层，外层缺失再取 `bizData`。调用方判定成功以 `retCode = 0000` 为准，HTTP 2xx 本身不算成功。

| `retCode` 段 | 含义                | 调用方处置           |
| ----------- | ----------------- | --------------- |
| `0000`      | 成功                | 按业务结果继续          |
| `1xxx`      | 参数 / 校验错误         | **不重试**，修正后重发   |
| `2xxx`      | 业务拒绝（重复版本、越权、窗口外） | **不重试**，按返回结论处理 |
| `3xxx`      | 系统错误 / 繁忙         | 退避重试            |
| `4xxx`      | 认证 / 签名失败         | **不重试**，告警并人工介入 |

**重试与幂等**：网络超时与 `3xxx` 才重试；重试 MUST 复用 `requestId`；退避采用指数间隔并设上限（建议 6 次，总时长 ≤ 30 分钟），超限转「落库状态 + 扫表补偿」。

**两层去重不能混用**：`requestId` 管**传输层**——同一次请求因超时重发时复用同一个值，接收方据此丢弃重复报文、直接回原结果；4.1 表里的业务键管**业务层**——不同请求命中同一业务键即判重复受理并拒绝。两层同时生效，NEVER 只做一层：只做传输去重时，换了 `requestId` 的重发会被当成新请求、重复记账；只做业务去重时，同一次请求的超时重发只会拿到「已存在」错误，而不是原结果。

**拒绝时必须回当前版本**：判 `DUPLICATE_REVISION` 或业务键冲突时，响应 `bizData` MUST 带 `currentRevision`（对方当前生效版本），否则调用方无从得知最新版本，只能反复试探。

### 4.3 关键接口字段

以下字段均位于 `bizData` 内（不是外层表单字段）；外层只放 4.2 的十个公共字段。

**IR-01 文件就绪**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `settlementDate` | string(8) | Y | 唯一账期键 |
| `batchNo` | string | Y | 批次号，规则待会签 |
| `revision` | int | Y | 版本号。**1 为原始版本**；仅 ACC 要求重传时递增，并体现在文件名 `.r<n>` 后缀（见第一章） |
| `batchType` | string | Y | `DAILY` / `RETRANSMIT` |
| `windowStart` / `windowEnd` | string(14) | Y | 数据窗口起止，`yyyyMMddHHmmss`；同批所有文件同一窗口，NEVER 混批 |
| `files[]` | array | Y | 本批文件清单，元素见下 |
| `remark` | string | N | 缺失渠道、直出渠道等声明，如「渠道 `03` 账单缺失，本账期不可比」 |

`files[]` 元素：`fileName` / `fileType`（`EXP` / `PAY` / `BUS` / `DETAIL` / `TXNDIFF` / `THIRD_BILL`）/ `byteSize` / `recordCount` / `amountTotal`（**分**，字符串化）/ `sha256` / `formatVersion` / `sourceType`（`SYSTEM_GENERATED` 系统生成 / `FINANCE_UPLOAD` 财务上传件，即渠道 `MT` 的入账确认件）。

四元组（`byteSize` / `recordCount` / `amountTotal` / `sha256`）的作用是**让 ACC 自行校验**，不是等 ACC 回报——校验结果与差异结论都留在 ACC 侧，本文不接收。

**IR-02 重传请求**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `fileName` | string | Y | ACC 手上那份文件的完整名（可带 `.r<n>` 后缀）；ITP 按**基础名**归并同族版本，不用 `fileType` 定位 |
| `settlementDate` / `batchNo` | — | N | 原批次定位，便于 ITP 核对；允许为空 |
| `currentRevision` | int | Y | ACC 当前持有的版本，即被判不可用的那一版 |
| `reason` | string | Y | `MISSING` 缺件 / `CORRUPT` 大小或摘要不符 / `FIELD_COUNT` 结构不符 / `WRONG_VERSION` 版本错 / `OTHER`（须带说明） |
| `requestedBy` | string | Y | ACC 侧操作人 |
| `requestedAt` | string(14) | Y | 请求时间 |

**ITP 侧处理**：校验该文件当前版本是否等于 `currentRevision`。

- 相等 → `revision + 1` 重新生成并投放，投放完成后发 IR-01（`batchType = RETRANSMIT`）；
- 不等（ITP 已有更新版本）→ 回 `2xxx` 拒绝，并在 `bizData` 带 `currentRevision` 与当前 `fileName`，提示 ACC 直接取现有版本，NEVER 再生成一版。

响应 `bizData`：`accepted`（true/false）/ `targetRevision`（本次将产生的新版本，受理时必填）/ `currentRevision`（拒绝时必填）/ `rejectReason`。

## 五、HCE 卡全量黑名单文件

### 5.1 用途与命名

ITP 每日定时生成 **HCE 卡全量黑名单**，经 FTP 推送至 ACC，由 ACC 下发闸机拦截。

| 项 | 约定 |
|---|---|
| 文件名 | `PRM.0013.9700.<版本号>`，版本号为 **6 位十进制数字**（不足左补 `0`），单调递增、**只进不退**；示例 `PRM.0013.9700.000001` |
| 生成 | 每日定时全量生成（默认 `02:00`），新版本**全量覆盖**旧版本语义，不做增量 |
| 投递 | 与对账文件同走 FTP 通道，**独立目录 `/itp/recon/hce/`**（与对账数据分家）；**不纳入 IR-01 通知**——版本号在文件名中自表达，ACC 按版本号取最新即可 |
| 性质 | **参数文件**，不是对账数据：不参与比对、**不产 manifest、不进四元组口径**（校验内嵌在文件尾 MD5，见 5.3） |

### 5.2 编码规则

| 规则 | 含义 |
|---|---|
| BCD | 每两个十进制数字压进 1 字节；奇数位左补 `0`（`"1300"` → `13 00`，16 位卡号 → 8 字节） |
| 4 字节无符号整数 | **小端序**（little-endian） |
| Hex | 十六进制文本直接转字节（`"01"` → `0x01`） |
| 整体 | 纯二进制，**无任何字符编码文本段**；NEVER 按 UTF-8 解析 |

### 5.3 文件结构

**文件头（22 字节）**

| # | 字段 | 长度 | 编码 | 取值 |
|---|---|---|---|---|
| 1 | 文件标识 | 1 | BCD | 固定 `20`（参数文件） |
| 2 | 生成时间 | 7 | BCD | `yyyyMMddHHmmss` |
| 3 | 更新方式 | 1 | Hex | 固定 `01`（全量更新） |
| 4 | 参数标识 | 2 | BCD | 固定 `1300` |
| 5 | 文件版本号 | 4 | 小端整数 | 与文件名尾段一致（版本 1 → `01 00 00 00`） |
| 6 | 生效时间 | 7 | BCD | `yyyyMMddHHmmss`，当前取生成时间 |

**记录区**

| # | 字段 | 长度 | 编码 | 说明 |
|---|---|---|---|---|
| 1 | 记录数 | 4 | 小端整数 | 黑名单卡数量 N，无记录时为 0 |

随后 N 条记录，每条：

| # | 字段 | 长度 | 编码 | 说明 |
|---|---|---|---|---|
| 1 | 票种 | 1 | BCD | 卡类型**末两位**（`0442` → `42`，`0443` → `43`） |
| 2 | 卡号 | 卡号位数 / 2 | BCD | HCE 逻辑卡号（纯数字，16 位即 8 字节） |
| 3 | 黑名单标志 | 1 | Hex | 固定 `01` |
| 4 | 保留域 | 4 | 小端整数 | 固定 `00 00 00 00` |

> 以 16 位卡号计，**每条记录 14 字节**。

**文件尾（20 字节）**

| # | 字段 | 长度 | 编码 | 说明 |
|---|---|---|---|---|
| 1 | 保留域 | 4 | 小端整数 | 固定 `00 00 00 00` |
| 2 | MD5 | 16 | 原始字节 | 对**文件头 + 记录区 + 保留域**全部字节计算 MD5，取 16 字节原始 digest（**不是 hex 文本**） |

### 5.4 样例与校验

样例 `PRM.0013.9700.000001` 共 **88 字节**，含 3 条记录（票种 0442 两张、0443 一张）：

```
00000000: 2020 2611 1110 3513 0113 0001 0000 0020
00000010: 2611 1110 3513 0300 0000 4201 7860 6904
00000020: 5864 1901 0000 0000 4201 7860 6904 5864
00000030: 2001 0000 0000 4301 7860 6904 5864 3301
00000040: 0000 0000 0000 0000 01bf 181e 5ff2 3517
00000050: 427a 347e 3a14 e17c
```

| 偏移 | 字节 | 含义 |
|---|---|---|
| `0x00` | `20` | 文件标识 |
| `0x01` | `20 26 11 11 10 35 13` | 生成时间 2026-11-11 10:35:13 |
| `0x08` | `01` | 更新方式：全量 |
| `0x09` | `13 00` | 参数标识 1300 |
| `0x0B` | `01 00 00 00` | 版本号 = 1 |
| `0x0F` | `20 26 11 11 10 35 13` | 生效时间 |
| `0x16` | `03 00 00 00` | 记录数 = 3 |
| `0x1A` | `42` + `01 78 60 69 04 58 64 19` + `01` + `00 00 00 00` | 记录 1：票种 42，卡号 0178606904586419 |
| `0x28` | `42` + `01 78 60 69 04 58 64 20` + `01` + `00 00 00 00` | 记录 2：票种 42，卡号 0178606904586420 |
| `0x36` | `43` + `01 78 60 69 04 58 64 33` + `01` + `00 00 00 00` | 记录 3：票种 43，卡号 0178606904586433 |
| `0x44` | `00 00 00 00` | 保留域 |
| `0x48` | `01 bf 18 1e 5f f2 35 17 42 7a 34 7e 3a 14 e1 7c` | MD5（前 72 字节的 digest） |

**校验**：长度 MUST 满足 `22 + 4 + 14 × N + 20`；尾 16 字节 MUST 等于前 `长度 − 16` 字节的 MD5 原始 digest。任一条不符即整份拒收，NEVER 部分加载。
