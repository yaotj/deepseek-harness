## 2. Project Context (项目上下文)
本项目是城市轨道交通自动售检票系统（AFC）的互联网业务层，连接 APP、闸机（AGM）、TVM、BOM、ACC、支付渠道及支付宝等第三方，支撑乘客互联网票务全生命周期。

### 2.1 核心技术栈 (严格遵循版本)
- **后端**: Java 21, Spring Boot 3.2.6, Maven 多模块
- **数据库**: Oracle (ojdbc8 19.18), 部分兼容达梦 DM8
- **ORM/持久层**: MyBatis + PageHelper + **自研 sql-datasource / mybatis-adaptor**
- **序列化**: Fastjson2 (2.0.57+)
- **安全**: Spring Security, JJWT 0.12.6, SHA256WithRSA 签名
- **连接池**: Druid
- **接口文档**: Knife4j / OpenAPI (springdoc 2.5.0)
- **部署**: Docker + Kubernetes (Eclipse JKube 1.19.0)
- **前端**: Vue 3.5, Vite 6, Element Plus 2.10, Pinia, Vue Router 4
- **管理后台**: 基于 RuoYi-Vue3 架构改造 (web-server + web)

#### 2.2.1 全局事实（勿再推断）
- **IF8A-01 开户数量从 account-server 2.0.75 起完全由必填 ticketLimit 控制（2026-09-17，ADR-D122，已部署）**：1 按第三方用户+所属方原值 ISSUE_ORG_CODE+映射卡类型查唯一卡，2 每次新卡。新行 TICKET_LIMIT=1 才参与查重/唯一索引；NULL 历史行仍按 COMPANION_FLAG 非 Y/C 判唯一，不回填。N/Y/C 保留订单用途，新 C 不自动多开。主卡查重 NEVER 命中 TICKET_LIMIT=2 同行卡；CARD_ISSUE_CODE 是码体发行渠道，NEVER 用它代替所属方。原两字段/Y-C 自动多开规则仅属历史。独立迁移已执行并回查，见 docs/ops/account-ticket-limit切换.md。
- **接口编号不唯一映射到一处代码**：IF8A-04/05/06 在 APP 域与 BOM 域含义不同；IF8A-09/10/11/20 存在多模块重复实现。定位实现 **MUST** 以「模块 + URL」为准。
- **入向验签并非统一 SHA256WithRSA**：`fep-app-server` 无验签代码，`sign` 原样透传；实际校验分散在 `AccountRequestVerifier`（摘要式，`signType=00` 免签）、`ItpRequestSignVerifier`（SHA1/MD5）与各渠道 RSA 工具类。SHA256WithRSA 仅用于渠道对接方向。

- **多数模块用 String 字面量而非枚举表达状态**，改动状态值 **MUST** 全局 grep 确认所有比较点。
- **运营后台接口分布在各业务模块的 `/page/**`**，web-server 的 HTTP 接口层不调用任何业务服务。**唯一例外是 Quartz 定时任务**：前台可配的定时任务建在 web-server，任务 Bean 经 `rpc` 调下游（`@EnableRpcAccount` / `@EnableRpcF2f` / `@EnableRpcPaySign`，`service.account.url` / `service.f2f.url` / `service.paySign.url`）；模块内部的补偿重试仍是本模块 `@Scheduled`（**在跑的只剩两个模块：`face-pay-server`（7 个、分布在 6 个类，见 §3.2）与 `collect-pay-server`（`SingleTicketRefundTask`，4 处）**；`gate-txn-pay-server` **现在一个 `@Scheduled` 都没有**（2026-09-16 逐模块实测：行首锚定匹配、已排除 Javadoc 注释里的字样）——原 `SupplementOrderCloseProcessor` 的补款任务**已连同该类整体迁到 `face-pay-server`**（`facepay/scheduler/SupplementOrderCloseProcessor.java`，现为 `converge`（cron `0 */5 * * * ?`）与 `closeTimeout`（cron `0 */10 * * * ?`）**两个，不再是 3 个**），**NEVER 在 gate-txn-pay-server 里加回**；`OfflineFareRecoveryProcessor` / `MetroTransferPushTaskProcessor` 那两个类**仍留在** gate-txn-pay-server，但已迁到 web-admin `sys_job`「离线码金额补偿」/「公交换乘推送」，cron 均 `0 0/1 * * * ?`，入口是 `CompensationInternalController` 的 `POST /internal/gate-txn-pay/offline-fare/recover` 与 `POST /internal/gate-txn-pay/metro-transfer/push`（**该 Controller 只有这两个端点，没有补款端点**），见 ADR-D80，**NEVER 在那两个类上加回 `@Scheduled`**）；`pay-sign-server` 现在一个都没有**——2026-09-11 全模块 grep 实测，该模块当时唯一的 `@Scheduled` 字样在 `AppNotifyService.java` 的注释里（原文即「本方法不再由服务内 `@Scheduled` 驱动，改由外部定时任务调用」）；**2026-09-17（ADR-D127）该接口已按聚合拆成 `SignNotifyService` + `TerminationNotifyService`、那行注释随之不存在，因此该模块 `@Scheduled` 字样已彻底为 0，NEVER 再按旧文件名去找它**。其 **10 个** `/internal/**` 补偿端点全部由 web-admin Quartz 触发（`/internal/termination/**` 6 个 + `/internal/paySign/**` 2 个 + **`/internal/payment/**` 2 个**，最后那两个是 2026-09-15 新增的 `compensateRefundQuery` / `compensateRefundSummary`，对应 `sys_job` **122「退款回查补偿」cron `0 0/10 * * * ?`** 与 **123「退款汇总跨表对账」cron `0 15 * * * ?`**，见 ADR-D91；**本处此前写「7 个」已过期，NEVER 回退**）。**本文件此前把 `pay-sign-server` 列进「各有在跑的」是错的，NEVER 回退**；排查「pay-sign 的补偿有没有跑」MUST 查 `SYS_JOB_LOG`，NEVER 在该模块里找 `@Scheduled`）。新增定时任务 **MUST** 先读 `docs/architecture/web-server.md` §七。

## 3. Architecture & Modules (架构与模块)

### 3.1 系统分层
微服务架构，四层：**接入层（FEP）→ 业务服务层 → 公共能力层 → ACC / 安全层**，外加管理后台与公共构件。

服务间通信的真实形态（**勿按常规 Spring Cloud 假设**）：
- **无注册中心、无网关、无 Feign / Dubbo**。调用全部由 `rpc` 模块的 `ProxyWebClient`（WebClient）发起 HTTP 直连，目标地址硬编码在各模块 `application.properties` 的 `service.*.url`。
- **不使用 Redis 与消息队列**。异步与重试靠 `@Scheduled` 扫库补偿。
- 所有模块位于**仓库根目录**（如 `fep-app-server/`），不存在 `micro/`、`common/` 之类的父目录。
- 部署：`docker/Dockerfile`（`jdk:21` + `COPY app.jar`）+ 各模块 JKube `kubernetes-maven-plugin` + `scripts/deploy-to-harbor.sh`。

## 5. STRICT RULES (严格开发准则 - AI 必读)

### 5.1 代码生成与修改 (Do's and Don'ts)
- **MUST** 使用 JDK 21 语法特性（如 Record, Pattern Matching, Virtual Threads 等，视场景而定）。
- **MUST** 使用 `jakarta.*` 包，**NEVER** 使用 `javax.*` 包（Spring Boot 3.x 强制要求）。
- **NEVER** 直接写原生 JDBC 或标准 MyBatis 注解，**MUST** 统一走自研 `mybatis-adaptor` / `sql-datasource`。
- **NEVER 在 SQL 正文中写注释**（`--` 行注释或 `/* */` 块注释）。全部服务共用 `resource/micro/sql-datasource/src/main/resources/sql.properties:40` 的 `spring.datasource.druid.filter.wall.enabled=true`，Druid WallFilter 默认 `commentAllow=false`，SQL 带注释会被判定为注入并抛 `SQLException: sql injection violation ... comment not allow`，该语句**静默失效**（编译与单测都发现不了，只在运行时炸）。注释 **MUST** 写在 mapper XML 的 `<!-- -->` 或 Java 注释里。**NEVER** 靠放宽 `wall.config.comment-allow` 绕过——那是全局降低注入防护等级。注意 `dm.properties:5` 在达梦环境关闭了 WallFilter，因此**该类缺陷只在 Oracle 生产环境暴露**。已发生事故：`PayTxnDetailMapper.updatePayCallback` 的 WHERE 内两行 `--` 注释导致支付成功回调的 UPDATE 全部失败，`PAY_STATUS` 长期卡在 `PROCESSING`、`PAY_TIME` 恒为空（2026-08-25 修复）。
- **同一个 Druid WallFilter 还有第二条规则：NEVER 写 `where 1 = 1` 打头 + 全部谓词都是可选 `<if>`**（2026-09-16 实测，ADR-D97 续）。所有可选条件都不传时，恒真条件成为唯一谓词，Druid 报 `sql injection violation ... select alway true condition not allow`，该查询整条失败、退化成 UUID `retCode`。**MUST 用 MyBatis `<where>` 标签**（无条件时不产出 `WHERE`）。与上面那条注释规则同源、同样只在运行时炸，而且**只在「筛选条件全空」那一支上踩** —— 而那一支往往正是前台首次进页面、不选任何条件的默认加载。已发生：`account-server` 的 `UserItpRegInfoMapper.countGroupByCardType`（综管台注册量统计，不选日期即失败，2.0.73 修复）。
- **mapper XML 的 `<!-- -->` 注释里 NEVER 出现两个连续减号**。XML 规范禁止注释文本内含连续减号，MyBatis 解析该 mapper 直接失败 ⇒ `sqlSessionFactory` 建不起来 ⇒ **整个服务启动即挂**（`Failed to parse mapping resource: '.../XxxMapper.xml'`；异常链最外层报的是某个无关 mapper 的 `sqlSessionTemplate` 注入失败，极易误判成依赖问题，**MUST 一直往下翻到 `Failed to parse mapping resource` 那一行看文件名**）。这与上一条是**孪生陷阱**：上一条要求把「禁止在 SQL 正文写行注释」的说明写进 XML 注释，而说明里若原样引用那两个符号就会踩本条。已发生（2026-09-11）：`account-server` 2.0.47 因 `AccountExceptionTicketMapper.xml` 的注释里原样写了行注释符号，部署后启动失败、Pod 虽 `2/2 Running` 但端口不监听（表现为 envoy 返 `Connection refused`）。新增或改动 mapper XML 后 **MUST** 跑 `xmllint --noout <file>` 逐个校验。
- **NEVER** 主动创建新的工具类（如 DateUtils, StringUtils），**MUST** 优先在 `model`, `rpc`, `micro` 模块中查找并复用现有组件。
- **公共请求报文骨架全项目只有两个类**：`model/app/ItpCommonRequest<T>` 与 `ItpCommonFormRequest`（`extends ItpCommonRequest<String>`，form-data 入向用）。2026-09-11 已把 7 份字段完全相同的副本删除并收口（`fep-app-server` / `fep-acc-server` 的 `CommonRequest` + `CommonFormRequest`、`fep-dev-server` / `fep-alipay-server` 的 `CommonFormRequest`、`account-server` 的 `CommonRequest`、`collect-pay-server` 的 `AppCommonRequest`、`acc-secure-server` 的 `AccCommonRequest`），涉 23 个引用文件、8 个模块（同批 +0.0.1 重建镜像）。**NEVER 再在业务模块新建同形副本**。这两个类**只承载报文骨架、不承载签名语义**——四条链路的加签验签互不相同（见 §4「签名算法」），**NEVER 因为共用同一个类就顺手统一签名逻辑**（属本节末「安全红线」）。`toString` 已对 `sign` 恒定脱敏、**NEVER 改成打印真值**；但 `bizData` 会完整进日志，`fep-alipay-server` 的 8 处 `log.info("...{}", request)` 因此由「只打对象 hash」变为「打全部字段」。
- **MUST** 使用 Fastjson2 进行 JSON 序列化/反序列化，**NEVER** 引入 Jackson 或 Gson 处理核心业务报文。
- **NEVER** 引入 Redis / RabbitMQ / Kafka 等中间件：本项目不使用缓存与消息队列。需要异步或重试时 **MUST** 采用「落库状态 + `@Scheduled` 扫表重试」；需要并发控制时 **MUST** 采用数据库唯一索引 + `DuplicateKeyException` 兜底。`resource/micro/rabbitmq-adaptor` 是历史遗留基础构件，**NEVER** 在业务模块中引用。

### 5.2 业务与架构约束
- **幂等与一致性**: 涉及支付、订单、扣款的关键业务表，**MUST** 考虑 ACC 对账、幂等设计（如唯一索引/防重表）及分布式事务一致性。
- **「按业务键幂等」的远端资源 NEVER 在失败分支回滚**。卡池预占是活样例：`reserveFromPool` 按 `businessId`（开户唯一卡现为用户+所属方+票种的长度前缀键，见 ADR-D122；旧版为 `thirdUserId + ":" + 票种`）幂等，**两条并发请求拿到的是同一个 `cardNo` 和同一个 `reservationId`** —— 预占是**共享的**，不是本请求私有的。于是「我失败了就 `releaseReservation`」会把兄弟请求正要 `confirm` 的卡号抽回池子，而那条兄弟已经把卡号写进 `USER_ITP_REG_INFO` 并对 APP 返了 `0000`，结果**同一个卡号在账户表是「已发给 A」、在 `LOGIC_CARD_POOL_CARD` 是 `AVAILABLE`（可再发给 B）**，只留一行 ERROR 日志。2026-09-14 真实并发实测到（ADR-D52；全库扫出 1 条即当次造的，属潜伏缺陷首次触发）。**判据**：远端资源的键是业务键、不是本次请求的唯一键时，本请求就**不是该资源的唯一持有者**，MUST 放弃「失败即回滚」，改为**留给对方的超时回收**（卡池是 `sys_job` 107「卡池维护」，cron `0 0/5 * * * ?`）。**NEVER 试图用「只有创建者才释放」或对 `reservationId` 做 CAS 来兜** —— 兄弟请求持有的就是同一个 id，任何以它为键的判断都分不清彼此。连带一条：这类「先占远端 → 落本地 → 再确认远端」的链路，**最后那步确认失败时 MUST NOT 返成功**，MUST 落异常工单转人工（`ACCOUNT_EXCEPTION_TICKET` 的 `CARD_POOL_CONFIRM_REJECTED`），否则不一致对上游完全不可见。
- **跨模块写操作的顺序**：一个事务内既要调远端（RPC）又要改本地时，**MUST 先调远端、后改本地**，远端失败即抛异常回滚，把状态留在中间态等对方重试。顺序颠倒会留下「本地已完成、远端未清理」的不一致，且无法自愈。链路见 `docs/business/pay-sign.md` §解约链路 —— **宿主已变**：解约申请在 `ContractDomainServiceImpl.requestTermination`、解约成功收口在 `CallbackDomainServiceImpl.receiveTerminationResult`，`PaySignWorkflow` 已于 2026-09-15 删除（ADR-D87）。**注意该收口分支本身已按 ADR-D48 改成「本地短事务 + `CHANNEL_SYNC_*` outbox + 提交后出网」**，因为它的远端调用**不允许**被事务包住（见下面「`@Transactional` 方法内 NEVER 发起任何 RPC」）；本条只约束「远端调用确实在事务内」的场景。
- **返回 boolean 的 RPC 包装方法**：本项目多个 RPC 包装方法内部 `catch` 全部异常后 `return false`，**从不抛异常**（活例子只剩 `PaySignClient.updatePaySignDisplayAccount`；**原先并列的 `PaySignWorkflow.removeAccountPayChannel` 已随 god class 于 2026-09-15 一并删除**——拆分时确认它零调用方，通道清理的唯一实现改为 `ChannelSyncDeliverer`，见 ADR-D87 / ADR-D48，**NEVER 再引用那个类名**）。调用这类方法 **MUST** 显式检查返回值并自行抛异常，**NEVER** 假定「没抛异常就是成功」——已发生两起：①远端清理失败仍写成功状态并通知 APP；②2026-09-11 `AccountApplicationServiceImpl.syncDisplayAccountToPayDomain` 丢弃 `updatePaySignDisplayAccount` 的返回值，而支付域在 `APP_PAY_SIGN_INFO` UPDATE 影响 0 行时就返回 FAIL（`PaySignAppController:159`），于是「该用户在支付域没有签约记录」被写成 `SIGN_SYNC_STATUS='SUCCESS'`，既不重试也不开工单（合成数据端到端实测到，已修，见 `docs/domain/decisions.md` ADR-D13）。**排查这类静默不一致 MUST 先看调用点有没有接住 boolean**。**2026-09-12（ADR-D45）起，这两处已换成 `rpc` 模块的 sealed `RpcOutcome`**（`Ok` / `BizRejected` / `Unreachable`，`rpc/src/main/java/com/chinasofti/huateng/rpc/outcome/RpcOutcome.java`）：调用点改成穷尽 `switch` 模式匹配，**少写一个分支直接编译失败**，不再依赖人记规则。收益不在类型优雅，而在于「业务拒绝」与「网络不可达」终于可区分 —— 前者重推一万次也不会成功、MUST 一次即终态 + 开工单，后者才进补偿队列。**新写 RPC 包装方法 MUST 返回 `RpcOutcome`，NEVER 再返回 boolean**；`PaySignClient.updatePaySignDisplayAccount` 仅作为 `@Deprecated` 兼容壳保留（`rpc` 版本号锁死、被 21 个模块引用，只能增方法不能改签名），**NEVER 在它内部重复一份解析逻辑**。
- **NEVER 在切面 / 包装层把异常换类型**（`throw new RuntimeException(e)`）。本项目的幂等主写法是「唯一索引 + `catch (DuplicateKeyException / DataIntegrityViolationException)` 兜底」（§5.1 末条），而 `resource/micro/web` 的 `MapperAspectToTrace` / `ServiceAspectToTrace` 曾用 `observation.observe(Supplier)`，Micrometer 会把受检异常之外的一切重新包一层 `RuntimeException`——**于是所有这类兜底 catch 全部落空、静默退化成对上游报错**。只在**打开 tracing 的 7 个模块**中招（`shouldSkipAopTraceLogic()` 会短路其余模块，名单见 §2.2.1），因此**同一份代码在 A 模块好、在 B 模块坏**；单测更看不到（单测里没有切面）。2026-09-14 实测：卡池 `reserveFromPool` 的唯一索引竞态兜底因此失效，并发开户返 `8003 无卡资源`（ADR-D53）。修法是切面 **MUST 用 `observation.start()` + `openScope()` + `catch (Throwable e) { observation.error(e); throw e; }` + `finally observation.stop()`，NEVER 回退成 `observe(Supplier)`**；调用侧再补一层 `isIntegrityViolation(Throwable)` 沿 `getCause()` 链判定（样例 `card-pool-server/.../CardPoolServiceImpl.java`）。**排查「兜底 catch 明明写了却没生效」MUST 先看目标模块有没有开 tracing**，其次沿 `getCause()` 逐层看异常有没有被换过类型，**NEVER 只看最外层类名**。**全模块 grep 已于 2026-09-14 补做（ADR-D53 续）**：7 个 tracing 模块里的裸 catch 只剩 `pay-sign-server/TerminationInternalServiceImpl`（`UK_ATR_REQUEST_SIGN_SEQ` 补建回查）与 `recon-server/ReconPartService`（分片重复接收回查）两处，**均已改成 cause 链判定**；gate-txn-pay / daily-ticket / collect-pay / alipay-pay-sign **一处都没有**。**`face-pay-server` 那 12 处裸 `catch (DuplicateKeyException)` 已于 2026-09-15 全部改成 cause 链判定（ADR-D84，1.0.32）；本条此前记载的「还有 12 处、开 tracing 前 MUST 先改完」已作废、NEVER 回退**：现统一走 `domain/F2fDuplicateKey.isConflict(Throwable)`，模板 `catch (RuntimeException e) { if (!F2fDuplicateKey.isConflict(e)) { throw e; } ... }`，`src/main` 下真实的 `catch (DuplicateKeyException)` **语句已为 0**（2026-09-15 复核：`grep -rn 'catch (DuplicateKeyException' face-pay-server/src/main` 仍有 **2 处命中，但两处都在注释里** —— `F2fScanPayService.java:217` 的「NEVER 退回」告示与 `F2fDuplicateKey.java:11` 的类注释；**NEVER 据这个 grep 计数判断已经回退**），因此**给 face-pay 开 tracing 不再有这条前置阻塞**（「三行成组」那条要求仍适用）。`F2fDuplicateKey` 是对 §5.1「NEVER 新建工具类」的**有意破例**（12 处散在 9 个类，抄私有方法等于 9 份逐字副本），理由写在类注释里。
- **`@Transactional` 方法内 NEVER 提交异步通知任务**。事务未提交时发出的通知，若随后回滚会造成「对方已收到成功通知、本地状态已回退」。**MUST** 用 `@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = false)`（首个落地样例：`pay-sign-server` 的 `paysign/event/SignResultCommittedEvent` + `SignResultCommittedListener`，2026-09-11 / 2.0.75）、`TransactionSynchronizationManager.registerSynchronization(...)` 的 `afterCommit`，或把通知移出事务方法。**Spring Event 在本项目只准用于这一件事**：一个事件类只挂一个监听器、两者同包成对命名、事件只带主键 + 不可变入向 DTO（**NEVER 带实体**，事务内的实体可能是脏快照，监听器 MUST 自己按键回查）；**NEVER** 拿它做解耦或跨模块通信（服务间只有 `rpc` 的 HTTP 直连，没有事件总线），**NEVER** 拿它替代「落库状态 + 扫表补偿」——事件是**进程内非持久**的，JVM 崩溃即丢，它只能当已落库任务的**快速路径**。监听器 **NEVER 加 `@Async`**（异常会彻底无声，默认执行器在虚拟线程下还有 pin 风险），内部 **MUST** `catch` 全部异常只记日志：`AFTER_COMMIT` 里抛异常回滚不了已提交的事务，只会让本已成功的回调对上游报错、引来重推。
- **`fallbackExecution = false` 在不带事务的类上等于「静默不执行」**，编译与单测都发现不了。因此**据文档挑「事务内通知」的改造点前 MUST 先 grep 目标类有没有 `@Transactional`** —— `face-pay-server` 整批服务类是**有意不带事务**的（`F2fTicketIssueService.java:49`、`F2fAppOrderService.java:62`，因为链路里有支付中心调用），在那里挂监听器会把通知直接丢掉；改成 `fallbackExecution = true` 更糟，等于「无事务时立刻同步发 HTTP」，退回该模块重写前的旧行为。详见 `docs/domain/decisions.md` 撤回 7。
- **`@Transactional` 方法内 NEVER 发起任何 RPC / 网络调用**。与上一条不是同一件事：上一条约束通知的**时机**，本条约束网络调用**不能被事务包住**。事务内调远端 ⇒ 行级排他锁的持有时长等于对端响应时长，上游对同一笔的重推会全部堆在同一行上串行等待；等待超过 Druid `remove-abandoned-timeout`（`resource/micro/sql-datasource/src/main/resources/sql.properties:44`）后连接被强杀，`commit` 抛 `connection closed`，**整个事务连同「留证据」的 INSERT 一起丢弃**，响应退化成全局异常处理器的 UUID `retCode`，上游继续重推——自我放大且没有出口。**MUST** 用 `afterCommit` 触发，或让该方法不带事务（每条 SQL 自动提交）。已发生事故：2026-08-26 21:07~21:14 生产，`PaySignWorkflow.receivePayResult` 事务内调 `syncDebitStatus`，订单 `GT20260826210647653586419` 循环重推 8 分钟，单次请求 287233ms、`UPDATE` 等锁 44997ms、`enq: TX - row lock contention` 持续；**循环期间 `PAY_CALLBACK_LOG` 零条落库**（每轮都被回滚），说明「回滚不丢证据」的前提在事务内并不成立。**该方法现宿主是 `PaymentDomainServiceImpl.receivePayResult`（2026-09-15 随拆分迁入，ADR-D87），事务注解自 ADR-D48 摘掉后一直没有、且是刻意的，NEVER 加回**（上面的事故事实不变）。

- **给 `model` 的 DTO 加字段后，MUST 重建链路上每一个经手该 DTO 的模块镜像，NEVER 只重建终点服务**。`model` 版本号恒为 2.0.0（见上一条），旧镜像里打进去的是**旧 DTO 的 class**，`mvn install` 只更新本机 `~/.m2`、对已在跑的 Pod 毫无影响。而 Fastjson2 宽松模式**静默丢弃目标 DTO 里不存在的字段、不报错不告警**，于是 APP 明明上送了新字段，接入层用旧 class 一反序列化就没了，再转发给下游时字段也不存在——下游即便已是新 class，收到的也是 `null`。已发生（2026-09-10）：IF8A-41 给 `RequestTransStatisticsReqDTO` 加 `cardType`，只重建了 `itp/ticket-server:2.1.51`，端到端打 fep-app 时 ticket-server 日志里 `cardType='null'`，一度误判成代码没生效；重建并部署 `itp/fep-app:2.0.77` 后立即正常。**排查「加了字段但收不到」MUST 先确认接入层镜像是否也重建过**，判据是「链路上有几个模块的 `parseBizData` / RPC 序列化会经过这个 DTO」，APP 类接口至少是 `fep-app-server` + 目标业务服务两个。
- **改了 `resource/micro/*` 或 `model` / `rpc` 后，`mvn install` 只更新本机 `~/.m2`，对已在跑的 Pod 零影响 —— MUST 逐个重建受影响模块的镜像**。与上一条同一个机理（公共构件版本号恒定 + 旧 class 已打进旧镜像），但**上一条只影响报文字段、这一条能影响行为语义**。活样例：ADR-D53 修 `resource/micro/web` 的两个观测切面（把「异常包一层」改回原样抛出）后，**只重建并滚更了 `card-pool-server:1.0.17`**，因此**其余 6 个 tracing 模块的线上镜像里仍是旧切面、它们的幂等兜底 catch 在线上依然失效**。**判据：改动落在公共构件里时，「谁受影响」= 依赖它且真正走到那段代码的全部模块**（切面这种按开关生效的，就是 §2.2.1 那份 tracing 名单里的 7 个）。**NEVER 认为「`mvn install` 过了 / Deployment env 改过了」就等于生效** —— 只有重建镜像 + `kubectl set image` 才算。

- **`service.*.url` 有三类问题，排查调用不通 MUST 三类都查**：①**键值错配**；②**键缺失**（`fep-app-server` 缺 `service.collectPay.url`、`pay-sign-server` 缺 `service.gateTxnPay.url`，运行时落到 `rpc` 默认服务名 `*-service`，与集群实际 Service 名不一致、DNS 解析不到；**`ticket-server` 缺 `service.paySign.url` 已于 2026-09-11 补齐，NEVER 再列**；**`fep-dev-server` 缺 `service.key.url` 已于 2026-09-14 补齐（ADR-D67），NEVER 再列** —— 这条是本类里**最难发现的形态**：该键在那个文件里**从来没出现过**，而 `KeySyncHandler` 一直在注 `KeyClient`，线上只靠 Deployment 一条 env 兜着，于是**仓库里连一个写错的键都没有**。因此排查一个模块的 `service.*.url` **MUST 先 grep 出本模块用了哪些 `*Client` / `@EnableRpcXxx`，再逐个回头对键**，**NEVER 只顺着 properties 逐行看**——顺着看永远发现不了「压根没写」的那种）；③**键存在但值指向自身 Pod**（`fep-app-server/application.properties:36` 是 `service.gateTxnPay.url=http://127.0.0.1:9106`，在 K8s 里等于打到自己，表现为响应退化成全局异常处理器的 UUID `retCode`，2026-09-08 实测）。
- **判断线上真实地址 MUST 查 Deployment env，NEVER 只看仓库 properties**：K8s Deployment 的 env 会覆盖 jar 内 `application.properties` 的同名键，因此「仓库里写错」不等于「线上是错的」，反之亦然。改 env 会触发滚动重启并立即生效，**不需要重新构建镜像**；已实测正确形态如 `http://gate-txn-pay-server-jomf4-svc.itp.svc:30019`。仓库配置与集群 env 不一致时改哪一边 **MUST** 先问用户（属改服务间路由）。
- **切设备 / APP 入向流量 MUST 改 `fep-app-vr` 这条 VirtualService，NEVER 改 K8s Service selector**（2026-09-15 实测确立，ADR-D85）。**操作步骤、现成命令与验证清单已收口到 `docs/ops/流量切换.md`，切之前 MUST 先读那份 Runbook，本条只留判据摘要。** 操作 **MUST 用 `kubectl patch --type=json` 且带 `test` op** 校验下标与原值（走 `ssh k8s-master`），改对应前缀那条 route 的 `destination.host` / `port.number`；交互式 `kubectl edit vs fep-app-vr -n itp` 也能改但没有校验、易改错位置；`rewrite.uri` 一般不动（`/itptvm/` 与 `/itpbom/` 两条的 rewrite 带前缀、不是 `/`）。**这是本项目唯一的入向路由开关**：公网 `58.56.166.170:48000` → 节点 `172.20.211.200`（= `k8s02-gateway-866a2`，集群的入向网关节点，不是业务节点）→ `itp-gateway`（ns `itp-gateway`，`image: auto` 的 istio 网关，svc `:50908`）→ ns `itp` 的 `fep-app-vr` → 各业务 Service。当前该 VS 里有 8 条前缀：`/fep-app/`、`/fep-dev/`、`/fep-acc/`、`/fep-alipay/`、`/itptvm/`、`/itpbom/`、`/itpagm/`、`/para-server/`。
  - **NEVER 用 `kubectl get vs -A` 的摘要表判断某个前缀归谁** —— 那张表只显示 name / gateways / hosts，**不显示 path**，据它得出的「没有 VirtualService 定义 `/itptvm`」是错的（2026-09-15 因此推出两版错方案）。查现行路由 **MUST** 读 envoy：`kubectl exec -n itp-gateway <itp-gateway-pod> -- curl -s '127.0.0.1:15000/config_dump?resource=dynamic_route_configs'`，或直接 `kubectl get vs fep-app-vr -n itp -o yaml`。
  - **为什么不能改 Service selector**：`collect-pay-c23ku-svc` 的 `targetPort` 是 **8080**（collect-pay 靠 Deployment env `server.port=8080` 顶掉 yml 里的 58101），而目标服务未必听同一个端口 —— 翻 selector 可能把全量流量打到无人监听的端口。**改 selector 还会连带打断所有「直连该 Service、不经网关」的内部调用方**（`recon-server` 的对账源、`gate-txn-pay` 的补款、`web-admin` 的 Quartz 任务都是这种），而改路由只影响入向流量、内部链路一行不动。
  - **APP 域不走这条 VS**：`fep-app` 收到请求后经 `rpc` 的 `service.*.url` 转发，要切 APP 侧目标得改 `fep-app` Deployment 的对应 env（如 `service.collectPay.url`，**键名带点、不是 `SERVICE_COLLECT_PAY_URL`**），会触发滚动重启。因此「切一个业务域的全部流量」通常是**网关路由 + fep-app env 两处**。
  - **改前 MUST 记下原值作为回滚命令**；`patch` 用 `--type=json` 时**建议带 `test` op 校验索引与原值**，避免数组下标漂移打错位置。切完 **MUST** 用「同一份报文分别打新旧服务、比对 retCode」做契约基线核对，并在目标服务日志里确认落点。

- **「代码有 mapper、生产库无表」是本项目的一类高频缺陷**：`acc-es-server` 13 张表全缺（已按 mapper 反推建表，长度待甲方复核）。新增或排查落库功能 **MUST** 先核对生产库实际表结构，**NEVER** 假定「仓库里有 DDL 就等于生产库已建表」；反过来 **NEVER** 仅凭一次「MCP 枚举不到」就断定缺表——`APP_TERMINATION_REQUEST` 曾据此被误记为缺失，2026-08-26 双路径核对确认表存在且解约链路已跑通。详见清单 §六。
- **外部网关地址 MUST 实测，不能只看仓库配置**：2026-08-26 实测支付中心网关路径必须带 `/v1`，不带时返回 `code=600 操作失败`（不是 404，容易被误判成业务原因）。`pay-sign-server` 原有 5 条路径缺 `/v1`，导致免密扣款自上线以来 `GATE_TXN_PAY` 零条 `SUCCESS`（已修复）。同时已把 `pay.sign.*-path` + `gateway-url` 拼接改成 7 条完整 URL（`pay.sign.*-url`），与 `service.*.url` 形态一致；**NEVER 退回拼接**——路径带版本号，拆两半后漏 `/v1` 不报 404、极难定位。改动或排查这组配置 **MUST** 先用只读接口 `/api/v1/contract/queryResult` 验证。**字段名同样 MUST 实测**：2026-09-15 实测退款查询 §3.2 只认 `merchantRefundNo`，按供方文档只送 `refundOrderNo` 时网关返 `code=9999「退款流水号或商户退款流水号必填」`，表现为**退款单永久空转、而端点每轮返 `0000`、调度日志一片绿**（既不报警也不自愈，已修：两个键都送）。因此外部网关的**任何**契约细节（路径、字段名、必填性）都 **MUST 有一次真实应答做证据，NEVER 只凭供方文档就认为对**，见 ADR-D92。
- **解约回调地址不由我方指定**：网关 §2.3 请求解约的 bizData 没有 `notifyUrl` 字段，回调只发往支付中心侧的商户配置地址。解约收口 **MUST** 以主动查 §2.4 `queryResult`（`status=UNSIGNED` 即已解约）为准，回调只作为快速路径，**NEVER** 设计成只等回调。
